# راه‌حل — ۱.۲.۵ `Drop` و RAII

```rust
pub fn scope_order() -> Vec<String> {
    {
        let _a = Tracker::new("a");
        let _b = Tracker::new("b");
        let _c = Tracker::new("c");
    }
    take_log()
}

pub fn release_early() -> Vec<String> {
    {
        let early = Tracker::new("early");
        let _late = Tracker::new("late");
        drop(early);
    }
    take_log()
}

pub fn handed_over() -> Vec<String> {
    {
        let given = Tracker::new("given");
        consume(given);
        let _kept = Tracker::new("kept");
    }
    take_log()
}

pub fn from_a_vec(names: Vec<String>) -> Vec<String> {
    {
        let mut group = Vec::with_capacity(names.len());
        for name in names {
            group.push(Tracker::new(&name));
        }
    }
    take_log()
}

pub fn custom_order() -> Vec<String> {
    {
        let a = Tracker::new("a");
        let b = Tracker::new("b");
        let _c = Tracker::new("c");
        drop(b);
        drop(a);
    }
    take_log()
}
```

در هر پنج تابع، تنها چیزی که تو نوشتی این است که هر مقدار **کجا** زندگی می‌کند. هیچ خطی «پاکسازی کن» نمی‌گوید.

## `scope_order` — قاعده‌ی پایه

```rust
let _a = Tracker::new("a");
let _b = Tracker::new("b");
let _c = Tracker::new("c");
```

لاگ `["c", "b", "a"]` برمی‌گردد. سه بایندینگ در یک بلاک، برعکسِ ترتیبِ اعلام آزاد می‌شوند.

دو نکته که راحت از قلم می‌افتند:

**اسم‌ها با زیرخط شروع می‌شوند، ولی `_` تنها نیستند.** اگر `let _ = Tracker::new("a");` می‌نوشتی، آن مقدار هیچ بایندینگی پیدا نمی‌کرد و همان جا، سرِ همان خط، آزاد می‌شد — و لاگ `["a", "b", "c"]` می‌شد، یعنی دقیقاً برعکسِ چیزی که تست می‌خواهد. یک زیرخطِ تنها یعنی «این را نمی‌خواهم»؛ `_a` یعنی «می‌خواهمش، فقط استفاده‌اش نمی‌کنم».

**`take_log()` بیرونِ بلاک است.** اگر داخلِ بلاک صدایش می‌زدی، هنوز هیچ‌کدام از سه مقدار آزاد نشده بودند و یک لیستِ خالی می‌گرفتی. جای این فراخوانی، خودش بخشی از جواب است.

## `release_early` — گرفتنِ اختیار از دامنه

```rust
let early = Tracker::new("early");
let _late = Tracker::new("late");
drop(early);
```

بدونِ آن خطِ آخر جواب `["late", "early"]` بود. با آن، `["early", "late"]`.

`drop(early)` مالکیت را از این بلاک می‌گیرد و به تابعِ `drop` می‌دهد؛ آن تابع بدنه‌ای ندارد، پس دامنه‌اش بلافاصله تمام می‌شود و مقدار همان جا می‌میرد. کامپایلر هم این را می‌داند و دیگر سرِ آکولاد فراخوانیِ دومی نمی‌گذارد.

دقت کن که `early` دیگر `_early` نیست: چون واقعاً استفاده‌اش می‌کنی، اسمش نباید عذرخواهی کند.

## `handed_over` — حرکت، زمانِ آزادسازی را می‌برد

```rust
let given = Tracker::new("given");
consume(given);
let _kept = Tracker::new("kept");
```

لاگ `["given", "kept"]` است. `"given"` قبل از اینکه `"kept"` اصلاً وجود داشته باشد آزاد شد، چون `consume` مالکش شد و دامنه‌ی `consume` بلافاصله تمام شد.

این تابع همان `release_early` است با یک روایتِ دیگر، و مقایسه‌ی این دو نکته‌ی مهم را نشان می‌دهد: `drop(x)` هیچ توانایی‌ای ندارد که `consume(x)` نداشته باشد. **هر** تابعی که مقدار را با مالکیت بگیرد و برنگرداند، آزادسازی را به خودش می‌کشد. `std::mem::drop` فقط اسمِ روشنی برای این کار است.

## `from_a_vec` — همان تابعی که برعکس نیست

```rust
let mut group = Vec::with_capacity(names.len());
for name in names {
    group.push(Tracker::new(&name));
}
```

`["a", "b", "c"]` می‌دهد، نه `["c", "b", "a"]`.

اینجا سه بایندینگ نداری؛ **یک** بایندینگ داری به اسمِ `group`. آن یک مقدار سرِ آکولاد آزاد می‌شود، و تخریب‌گرِ `Vec` عناصرش را از خانه‌ی صفر تا آخر می‌گردد. ترتیبِ معکوس قاعده‌ی بایندینگ‌هاست، نه قاعده‌ی داده.

این تفاوت در کدِ واقعی مهم می‌شود. اگر ترتیبِ بسته شدنِ چند اتصال برایت اهمیت دارد، اینکه آن‌ها را در چند `let` نگه داری یا در یک `Vec`، دو رفتارِ متفاوت است.

و `for name in names` خودِ `names` را مصرف می‌کند — درست همان چیزی که می‌خواهی، چون بعدش لازمش نداری. `Vec::with_capacity` هم اینجا رایگان است، چون تعداد از قبل معلوم است ([۱.۲.۳](../../03-clone-and-copy/README.fa.md)).

## `custom_order` — هر دو قاعده با هم

```rust
let a = Tracker::new("a");
let b = Tracker::new("b");
let _c = Tracker::new("c");
drop(b);
drop(a);
```

`b`، بعد `a`، بعد `c`.

دو `drop`ِ صریح ترتیبِ دلخواه را می‌سازند و `c` به قاعده‌ی پیش‌فرض واگذار می‌شود. اگر برای `c` هم `drop` می‌نوشتی جواب همان می‌شد، ولی خواندنش سخت‌تر بود: هر `drop`ِ صریح یعنی «اینجا یک دلیلِ خاص داشتم»، و نوشتنش برای مقداری که همان‌طوری هم درست آزاد می‌شود، سروصداست.

اینکه `c` تنها متغیری است که هنوز زیرخط دارد اتفاقی نیست — تنها متغیری است که هیچ‌وقت در کد استفاده نمی‌شود.

## این درس واقعاً درباره‌ی چه بود

- **پاکسازی یک فراخوانی است که کامپایلر می‌نویسد**، سرِ آکولادِ مالک، روی هر مسیرِ خروج.
- **بایندینگ‌ها برعکس آزاد می‌شوند؛ عناصرِ یک مجموعه از اول تا آخر.** یک قاعده نیست، دو قاعده است.
- **زمانِ آزادسازی همان مالکیت است.** هر حرکتی — به یک تابع، به یک `Vec`، به `drop` — زمان را هم جابه‌جا می‌کند.
- **`drop(value)` امتیازِ ویژه‌ای ندارد.** فقط یک تابع است که مالکیت می‌گیرد؛ `value.drop()` رد می‌شود چون «دقیقاً یک بار» را می‌شکست.
- **اگر نوعت تخریب‌گر دارد، `Copy` نیست** — و این همان سطرِ [۱.۲.۳](../../03-clone-and-copy/README.fa.md) است که حالا دلیلش را می‌دانی.

قدمِ بعدی [ماژولِ ۱.۳](../../../03-borrowing-and-references/README.fa.md) است: به‌جای دادنِ مالکیت، فقط نگاه کردن به یک مقدار — که یعنی آزادسازی همان‌جا می‌ماند که بود.
