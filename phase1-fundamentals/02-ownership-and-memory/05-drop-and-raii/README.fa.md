# ۱.۲.۵ — `Drop` و RAII

## در یک نگاه

بعد از این درس می‌توانی:

- پیش‌بینی کنی مقدارهای یک بلاک به چه ترتیبی آزاد می‌شوند، و بگویی چرا آن ترتیب برعکس است.
- یک `impl Drop` بنویسی و آزادسازی را از یک ادعا به چیزی تبدیل کنی که روی صفحه می‌بینی.
- با `drop(value)` چیزی را زودتر از آکولادِ بسته رها کنی، و بگویی چرا `value.drop()` رد می‌شود.
- بگویی چرا یک نوع یا `Copy` است یا تخریب‌گر دارد، و هرگز هر دو.

**زمان:** حدود ۴۵ دقیقه · **پیش‌نیاز:** [۱.۲.۴ — مالکیت در عبور از توابع](../04-ownership-across-functions/README.fa.md)

---

## چرا اهمیت دارد

چهار درسِ گذشته یک جمله را تکرار کردند: «وقتی مالک از دامنه بیرون برود، مقدار آزاد می‌شود.»

تا اینجا این یک قولِ نادیدنی بوده. چیزی که پذیرفتی چون کامپایلر گفت، نه چون دیدی‌اش.

امروز می‌بینی‌اش. یک نوع می‌سازی که موقعِ آزاد شدن حرف می‌زند، و بعد کلِ ۱.۲.۱ تا ۱.۲.۴ به‌شکلِ خطِ خروجی جلوی چشمت اجرا می‌شود: دامنه‌های تودرتو، حرکت، پس گرفتنِ مالکیت از یک تابع.

و یک چیزِ تازه هم اضافه می‌شود که فقط درباره‌ی حافظه نیست. فایل، سوکت، اتصالِ دیتابیس، قفل — هر چیزی که باید بسته شود، با همین یک مکانیزم بسته می‌شود.

در پایتون بستن روی دوشِ توست:

```python
f = open("data.txt")
# ... کار ...
f.close()          # اگر بینِ این دو خط استثنا بلند شود، هرگز اجرا نمی‌شود
```

جوابِ پایتون `with` است، ولی `with` اختیاری است: هم نویسنده‌ی کلاس باید `__enter__` و `__exit__` را نوشته باشد، هم تو باید یادت بماند بنویسی‌اش. یک `with` جاافتاده هیچ خطایی نمی‌دهد — فقط یک فایلِ باز می‌ماند تا وقتی زباله‌روب سراغش برود.

در Rust هر نوعی می‌تواند بگوید موقعِ آزاد شدن چه کند، و **کامپایلر آن فراخوانی را خودش سرِ آکولاد می‌گذارد**. راهی برای فراموش کردنش نیست، چون اصلاً کسی ننوشته که یادش برود.

## مفهوم

### آزادسازی‌ای که می‌بینی‌اش

این یک نوعِ کوچک است با یک فیلد. `struct` و `impl` درسِ کاملِ خودشان را در [۱.۵.۱](../../05-your-own-types/01-structs-and-methods/README.fa.md) دارند؛ فعلاً یعنی «نوعی که از یک فیلد ساخته شده» و «کدی که به آن نوع چسبیده است».

```rust
struct Guard {
    name: String,
}

impl Guard {
    fn new(name: &str) -> Guard {
        println!("open  {name}");
        Guard {
            name: name.to_string(),
        }
    }
}
```

تا اینجا چیزِ تازه‌ای نیست. تازه این است:

```rust
impl Drop for Guard {
    fn drop(&mut self) {
        println!("close {}", self.name);
    }
}
```

و حالا این را اجرا کن:

```rust
println!("-- before the block");
{
    let _inner = Guard::new("inner");
    println!("-- inside the block");
}
println!("-- after the block");
```

```text
-- before the block
open  inner
-- inside the block
close inner
-- after the block
```

آن `close inner` را هیچ‌کس صدا نزد. در کد هیچ خطی نیست که بگوید «این را ببند». کامپایلر موقعِ ساختنِ برنامه، فراخوانی را **سرِ همان آکولادِ بسته** گذاشت.

حالا اسمش را بگذاریم: `Drop` یک صفت (trait) است — یعنی مجموعه‌ای از رفتار که یک نوع قول می‌دهد داشته باشد — و تنها متدش `drop` است. به کدی که موقعِ نابود شدنِ یک مقدار اجرا می‌شود **تخریب‌گر (destructor)** می‌گویند. صفت‌ها درسِ کاملشان را در [فاز ۲](../../../phase2-intermediate/03-generics-and-traits/02-defining-and-implementing-traits/README.fa.md) دارند؛ امروز فقط همین یکی را لازم داری.

### ترتیب برعکس است

[۱.۲.۱](../01-stack-and-heap/README.fa.md) این را در یک جمله گفته بود: «به ترتیبِ معکوسِ اعلام آزاد می‌شوند». حالا ببینش:

```rust
{
    let _a = Guard::new("a");
    let _b = Guard::new("b");
    let _c = Guard::new("c");
    println!("      all three alive");
}
```

```text
open  a
open  b
open  c
      all three alive
close c
close b
close a
```

ساخت `a`، `b`، `c`. آزادسازی `c`، `b`، `a`.

```senpai-visual
{"kind":"ownership","labels":["ساختِ a","ساختِ b","ساختِ c","آزادیِ c","آزادیِ b","آزادیِ a"]}
```

چرا برعکس؟ چون چیزی که دیرتر ساخته شده ممکن است به چیزی که زودتر ساخته شده تکیه کرده باشد — مثلاً یک اتصال که به یک تنظیمات نگاه می‌کند. ترتیبِ مستقیم یعنی زیرِ پای دومی را قبل از خودش خالی کنی. ترتیبِ معکوس تنها ترتیبی است که همیشه امن است.

همان نظمِ پرانتزهای تودرتو: از داخل به بیرون بسته می‌شوند، هیچ‌وقت برعکس.

### مجموعه‌ها از جلو به عقب آزاد می‌شوند

«معکوس» قاعده‌ی کاملی نیست. ببین یک `Vec` چه می‌کند:

```rust
let mut group = Vec::new();
for name in ["first", "second", "third"] {
    group.push(Guard::new(name));
}
```

```text
open  first
open  second
open  third
      the Vec owns all three
close first
close second
close third
```

هیچ معکوسی در کار نیست. اینجا `group` **یک** مقدار است که در انتهای بلاک آزاد می‌شود، و تخریب‌گرِ `Vec` عناصرش را از خانه‌ی صفر تا آخر می‌گردد.

پس قاعده دقیق‌تر از چیزی است که فکر می‌کردی:

> **بایندینگ‌های یک بلاک برعکسِ ترتیبِ اعلام آزاد می‌شوند؛ عناصرِ یک مجموعه از اولی تا آخری.**

سه `let` جدا و یک `Vec` سه‌تایی دو ترتیبِ متفاوت به تو می‌دهند، و این تفاوت واقعی است، نه جزئیاتِ پیاده‌سازی.

### RAII — منبع همان مقدار است

اسمِ این الگو **RAII** است: *Resource Acquisition Is Initialization*، یعنی «گرفتنِ منبع، همان مقداردهیِ اولیه است». اسمِ بدی است و از C++ آمده، ولی حرفش ساده است:

> **منبع را موقعِ ساختنِ مقدار بگیر، و در `drop` پسش بده. از آن به بعد دامنه مسئولِ بستن است، نه حافظه‌ی تو.**

`Guard` بالا دقیقاً همین است: `Guard::new` باز می‌کند، `drop` می‌بندد. هر مسیری که از بلاک بیرون برود — رسیدن به آکولاد، `return` زودهنگام، `break` از یک حلقه — از همان تخریب‌گر رد می‌شود.

|  | پایتون | Rust |
|---|---|---|
| کِی بسته می‌شود | وقتی `close()` را صدا بزنی، یا وقتی بلاکِ `with` تمام شود | سرِ آکولادِ مالک |
| چه کسی باید یادش بماند | نویسنده‌ی کلاس، و بعد هر کسی که استفاده می‌کند | نویسنده‌ی نوع، یک بار |
| اگر یادت برود | باز می‌ماند، بی‌هیچ خطایی | نمی‌شود یادت برود |

**کجا این قیاس می‌شکند:** بلاکِ `with` را در کد می‌بینی؛ آزادسازیِ Rust نامرئی است. یعنی وقتی می‌خواهی بدانی چیزی کِی بسته می‌شود، باید بپرسی «مالکش کیست و دامنه‌اش کجا تمام می‌شود؟» — و همین سؤال کلِ درس‌های ۱.۲.۲ و ۱.۲.۴ بود.

### حرکت، زمانِ آزادسازی را جابه‌جا می‌کند

اگر آزادسازی به مالک وصل است، آن‌وقت هر حرکتی زمانِ آزادسازی را هم جابه‌جا می‌کند:

```rust
let given = Guard::new("given");
consume(given);
println!("      back in main, and it is already closed");

fn consume(_guard: Guard) {
    println!("      inside consume");
} // <- مالکِ آن حالا این تابع است، پس همین‌جا بسته می‌شود
```

```text
open  given
      inside consume
close given
      back in main, and it is already closed
```

`given` در `main` ساخته شد و در `consume` مُرد. این همان چیزی است که [۱.۲.۴](../04-ownership-across-functions/README.fa.md) گفت، از سمتِ دیگرش: حرکت فقط انتقالِ داده نیست، انتقالِ **مسئولیتِ پاکسازی** است.

و سایه‌انداختن از [۱.۱.۱](../../01-foundations/01-variables-mutability-shadowing/README.fa.md) اینجا یک نتیجه‌ی غافلگیرکننده دارد:

```rust
let _slot = Guard::new("shadowed");
let _slot = Guard::new("replacement");
println!("      both are still alive; the name just points elsewhere");
```

```text
open  shadowed
open  replacement
      both are still alive; the name just points elsewhere
close replacement
close shadowed
```

مقدارِ اول آزاد **نشد**. سایه‌انداختن اسم را دوباره می‌بندد، نه اینکه مقدارِ قبلی را نابود کند: آن مقدار هنوز هست، فقط دیگر اسمی برای صدا زدنش نداری، و سرِ آکولاد به نوبتِ خودش — یعنی معکوس — آزاد می‌شود.

### زودتر رها کردن با `drop`

گاهی آخرِ بلاک دیر است. یک قفل که تا آخرِ تابع نگه‌داشته شده، بقیه را بی‌دلیل معطل می‌کند:

```rust
let first = Guard::new("first");
let _second = Guard::new("second");
drop(first);
println!("      first is closed, second is not");
```

```text
open  first
open  second
close first
      first is closed, second is not
close second
```

`std::mem::drop` هیچ جادویی ندارد. کلِ ماجرا یک تابعِ معمولی است که آرگومانش را با مالکیت می‌گیرد و بدنه‌ای خالی دارد. مقدار به این دلیل آزاد می‌شود که دامنه‌ی خودِ آن تابع بلافاصله تمام می‌شود — همان قاعده‌ی همیشگی، فقط با یک دامنه‌ی خیلی کوتاه.

و چون مالکیت را می‌گیرد، بعد از `drop(x)` دیگر `x` را نداری. این یک حرکت است مثل هر حرکتِ دیگری، و خطایش را در بخشِ بعد می‌بینی.

### چرا نمی‌توانی `.drop()` را خودت صدا بزنی

`drop` یک متد است، در دسترس است، و دقیقاً همان کاری را می‌کند که می‌خواهی. پس:

```rust
let guard = Guard::new("early");
guard.drop();
```

```text
error[E0040]: explicit use of destructor method
```

رد شد. توضیحِ کاملش در بخشِ خطاهاست، ولی خلاصه‌اش این است: کامپایلر از قبل یک فراخوانی سرِ آکولاد گذاشته. اگر تو هم یکی صدا می‌زدی، پاکسازی **دو بار** اجرا می‌شد — و آزادسازیِ دوباره‌ی حافظه یکی از همان سه باگی است که [۱.۲.۱](../01-stack-and-heap/README.fa.md) اسم برد.

### `Drop` و `Copy` با هم جمع نمی‌شوند

جدولِ [۱.۲.۳](../03-clone-and-copy/README.fa.md) یک سطر داشت که آن موقع بی‌دلیل به‌نظر می‌رسید: «هر چیزی که `Drop` داشته باشد `Copy` نیست». حالا دلیلش را داری.

```rust
#[derive(Clone, Copy)]
struct Ticket {
    id: u32,
}

impl Drop for Ticket {
    fn drop(&mut self) {
        println!("returning ticket {}", self.id);
    }
}
```

```text
error[E0184]: the trait `Copy` cannot be implemented for this type; the type has a destructor
```

هر فیلدِ `Ticket` یک `u32` است، پس از دیدِ ۱.۲.۳ این derive باید مجاز باشد. `Drop` است که غیرممکنش می‌کند، چون دو قول با هم نمی‌خوانند:

- `Copy` می‌گوید: **کپیِ بایتی کافی است و چیزی برای تمیز کردن نمی‌ماند.**
- `Drop` می‌گوید: **دقیقاً چیزی برای تمیز کردن هست.**

اگر هر دو ممکن بود، یک انتساب دو بلیت می‌ساخت و هر دو در پایانِ دامنه‌شان همان یک بلیت را پس می‌دادند. این همان مسئله‌ی `String` است، فقط این بار خودت نوشته‌ای‌اش.

## خطاهایی که خواهی دید

### `E0040` — صدا زدنِ مستقیمِ تخریب‌گر

```text
error[E0040]: explicit use of destructor method
  --> examples\05-calling-drop-yourself.rs:27:11
   |
27 |     guard.drop();
   |           ^^^^ explicit destructor calls not allowed
   |
help: consider using `drop` function
   |
27 -     guard.drop();
27 +     drop(guard);
   |
```

**کامپایلر به چه اعتراض دارد:** تخریب‌گر مالِ اوست، نه مالِ تو. او یک فراخوانی سرِ آکولاد گذاشته و روی اجرا شدنِ آن حساب کرده است. اگر `guard.drop()` مجاز بود، بدنه دو بار اجرا می‌شد و هر منبعی که آزاد می‌کند دو بار آزاد می‌شد.

**راه‌حل:** `drop(guard)` به‌جای `guard.drop()` — و کامپایلر خودش دقیقاً همین را با `-` و `+` جلوی چشمت گذاشته.

**چرا این راه‌حل است:** `drop(guard)` مالکیت را از تو می‌گیرد. مقدار داخلِ آن تابع می‌میرد، کامپایلر می‌داند که مرده، و دیگر سرِ آکولاد فراخوانیِ دومی نمی‌گذارد. یعنی «دقیقاً یک بار» همچنان تضمین است. تفاوت این نیست که کدام قشنگ‌تر است؛ این است که یکی‌شان قابلِ شمردن است و دیگری نه.

### `E0184` — `Copy` روی نوعی که تخریب‌گر دارد

```text
error[E0184]: the trait `Copy` cannot be implemented for this type; the type has a destructor
  --> examples\06-copy-and-drop.rs:8:8
   |
 7 | #[derive(Clone, Copy)]
   |                 ---- in this derive macro expansion
 8 | struct Ticket {
   |        ^^^^^^ `Copy` not allowed on types with destructors
   |
note: destructor declared here
  --> examples\06-copy-and-drop.rs:13:5
   |
13 |     fn drop(&mut self) {
   |     ^^^^^^^^^^^^^^^^^^
```

**کامپایلر به چه اعتراض دارد:** دو قولِ ناسازگار. `Copy` یعنی «انتساب یک دومی می‌سازد و مبدأ سالم می‌ماند، چون چیزی برای تمیز کردن نیست». `Drop` یعنی «چیزی برای تمیز کردن هست». هر دو با هم یعنی هر انتساب یک مسئولِ اضافه می‌سازد.

**راه‌حل:** یکی را انتخاب کن. یا `Copy` را از derive بردار:

```rust
#[derive(Clone)]
struct Ticket {
    id: u32,
}
```

یا `impl Drop` را بردار و بلیت را جای دیگری پس بده.

**چرا این راه‌حل است:** به `note: destructor declared here` دقت کن — کامپایلر هر دو نقطه‌ی درگیر را کنارِ هم گذاشته، نه فقط نقطه‌ی خطا را. برای تصمیم‌گیری دقیقاً همین را لازم داری: کدام‌یک از این دو خط را واقعاً می‌خواستی؟

و این محدودیت به تو تحمیل نشده؛ خودت درخواستش کردی. لحظه‌ای که برای نوعی تخریب‌گر می‌نویسی، گفته‌ای «این چیز آزادسازی لازم دارد» — و از همان لحظه، تکثیرِ خاموش سرِ هر انتساب اشتباه است.

### `E0382` — استفاده بعد از `drop`

```text
error[E0382]: borrow of moved value: `text`
  --> examples\07-used-after-drop.rs:12:16
   |
 6 |     let text = "a heap buffer".to_string();
   |         ---- move occurs because `text` has type `String`, which does not implement the `Copy` trait
...
10 |     drop(text);
   |          ---- value moved here
11 |
12 |     println!("{text}");
   |                ^^^^ value borrowed here after move
```

**کامپایلر به چه اعتراض دارد:** هیچ چیزِ ویژه‌ای درباره‌ی `drop` نمی‌گوید. می‌گوید `text` در خطِ ۱۰ حرکت کرد. `drop` تابعی است که آرگومانش را با مالکیت می‌گیرد، پس `drop(text)` دقیقاً همان `consume(text)`ای است که در ۱.۲.۲ و ۱.۲.۴ دیدی.

**راه‌حل:** هر کاری با `text` داری، قبل از `drop` انجامش بده:

```rust
let text = "a heap buffer".to_string();
println!("{text}");
drop(text);
```

**چرا این راه‌حل است:** به پیشنهادِ `help` کامپایلر دقت کن: `drop(text.clone())`. کامپایل می‌شود و کاملاً بی‌معناست — یک بافرِ تازه تخصیص می‌دهد فقط برای اینکه بلافاصله آزادش کند، و بافرِ اصلی همچنان سرِ آکولاد آزاد می‌شود. این همان هشدارِ [۱.۲.۳](../03-clone-and-copy/README.fa.md) است در طبیعی‌ترین حالتش: `.clone()` خطا را ساکت می‌کند بی‌آنکه به سؤالِ اصلی جواب بدهد.

اگر بعد از `drop(x)` هنوز `x` را لازم داری، یعنی کارت با آن تمام نشده بوده — و `drop` جای اشتباهی بوده، نه آن استفاده.

## تمرین

### گرم‌کردن

<details>
<summary>سه <code>let</code> در یک بلاک به چه ترتیبی آزاد می‌شوند؟</summary>

برعکسِ ترتیبِ اعلام. آخرین چیزی که ساخته شد اولین چیزی است که می‌رود.

</details>

<details>
<summary>سه عنصرِ یک <code>Vec</code> به چه ترتیبی آزاد می‌شوند؟</summary>

از اولی تا آخری. خودِ `Vec` یک مقدار است و تخریب‌گرش عناصر را از خانه‌ی صفر می‌گردد. سه `let` جدا و یک `Vec` سه‌تایی دو ترتیبِ متفاوت می‌دهند.

</details>

<details>
<summary>وقتی یک مقدار را به تابعی می‌دهی، تخریب‌گرش کجا اجرا می‌شود؟</summary>

سرِ آکولادِ آن تابع، مگر اینکه تابع مقدار را برگرداند. مالکیت تعیین می‌کند کِی، نه اینکه کجا ساخته شده بود.

</details>

<details>
<summary><code>let _slot = a;</code> و بعد <code>let _slot = b;</code> — چه وقت <code>a</code> آزاد می‌شود؟</summary>

سرِ آکولاد، بعد از `b`. سایه‌انداختن اسم را دوباره می‌بندد ولی مقدارِ قدیمی را نمی‌کشد؛ فقط دیگر اسمی برای صدا زدنش نداری.

</details>

<details>
<summary><code>std::mem::drop</code> چطور کار می‌کند؟</summary>

یک تابعِ معمولی که آرگومانش را با مالکیت می‌گیرد و بدنه‌اش خالی است. مقدار آزاد می‌شود چون دامنه‌ی آن تابع بلافاصله تمام می‌شود. هیچ چیزِ ویژه‌ای در آن نیست.

</details>

<details>
<summary>چرا <code>value.drop()</code> رد می‌شود ولی <code>drop(value)</code> نه؟</summary>

چون `value.drop()` بدنه‌ی تخریب‌گر را اجرا می‌کرد بی‌آنکه فراخوانیِ خودکارِ سرِ آکولاد را لغو کند، یعنی دو بار پاکسازی. `drop(value)` مالکیت را می‌برد، پس کامپایلر می‌داند فراخوانیِ دومی لازم نیست.

</details>

<details>
<summary>چرا یک نوع نمی‌تواند هم <code>Copy</code> باشد هم تخریب‌گر داشته باشد؟</summary>

`Copy` قول می‌دهد چیزی برای تمیز کردن نمانده؛ `Drop` می‌گوید هست. اگر هر دو ممکن بود، هر انتساب یک مسئولِ اضافه برای یک منبع می‌ساخت.

</details>

### پیاده‌سازی

پنج تابع در `src/lib.rs`:

```sh
cargo test -p p1-02-05-drop-and-raii
```

بالای فایل یک `Tracker` هست که موقعِ آزاد شدن نامش را در یک لاگ می‌نویسد؛ همان کاری که `Guard` روی صفحه می‌کرد، فقط طوری که یک تست بتواند بخواندش. آن قسمت آماده است و کاری با آن نداری.

چهار تا از پنج تابع فقط به یک بلاک، `Tracker::new` و `drop` احتیاج دارند. جوابِ یکی از آن‌ها برعکس **نیست**؛ کامنتِ خودش این را می‌گوید، ولی اینکه *چرا* این‌طور است همان درسِ امروز است.

### بساز

یک `pub fn transaction(steps: Vec<String>) -> Vec<String>` بنویس که برای هر گام یک `Tracker` بسازد و همه را تا آخرِ یک بلاک زنده نگه دارد — به‌جز گام‌هایی که با `"skip:"` شروع می‌شوند، که باید بلافاصله بعد از ساخته شدن رها شوند. تابع لاگ را برمی‌گرداند.

قبل از اجرا حدس بزن: برای `["a", "skip:b", "c"]` لاگ چه می‌شود؟ بعد اجرا کن و ببین درست حدس زدی یا نه.

بعد یک جمله بنویس درباره‌ی اینکه اگر همه‌ی گام‌ها را در یک `Vec<Tracker>` نگه می‌داشتی چه چیزی عوض می‌شد.

### چالش (اختیاری)

**بخشِ یک.** این دو تکه را اجرا کن و توضیح بده چرا خروجی‌شان یکی نیست:

```rust
let _ = Guard::new("wildcard");
println!("      after the wildcard line");
```

```rust
let _named = Guard::new("underscore-name");
println!("      after the named line");
```

یکی از این دو بلافاصله بسته می‌شود و آن یکی تا آخرِ بلاک زنده می‌ماند. **کدام، و چرا؟** این تفاوت در کدِ واقعی گران تمام می‌شود: قفلی که با `let _` گرفته شود، در همان خط آزاد می‌شود و هیچ چیزی را محافظت نمی‌کند.

**بخشِ دو.** یک `Guard` بساز و بعد `std::mem::forget` را رویش صدا بزن. تخریب‌گر اجرا می‌شود؟ مستنداتش را بخوان و بگو چرا آن تابع `unsafe` نیست، با اینکه دقیقاً همان کاری را می‌کند که این درس برای جلوگیری از آن نوشته شده. (سرنخ: نشتِ حافظه در Rust ناامن حساب نمی‌شود.)

**بخشِ سه.** اگر برنامه `panic` کند تخریب‌گرها اجرا می‌شوند؟ امتحان کن: در `01-drop-runs` بعد از ساختنِ `_last` یک `panic!("boom")` بگذار. این جلو می‌زند به [۱.۶.۴](../../06-absence-and-failure/04-panic-vs-result/README.fa.md)، ولی جوابش دقیقاً همان چیزی است که RAII را در Rust قابلِ‌اتکا می‌کند.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به کارت می‌آید |
|---|---|---|
| `Drop` | صفتی با یک متد، که هنگامِ آزاد شدنِ مقدار اجرا می‌شود | بستنِ هر چیزی که باز شده |
| تخریب‌گر (destructor) | همان کدِ پاکسازی، به‌عنوانِ یک اصطلاح | خطاهای `E0040` و `E0184` |
| RAII | منبع را موقعِ ساخت بگیر، در `drop` پس بده | فایل، سوکت، اتصال، قفل |
| ترتیبِ معکوس | بایندینگ‌های یک بلاک برعکس آزاد می‌شوند | دامنه‌های تودرتو |
| ترتیبِ مجموعه | عناصرِ یک `Vec` از اولی تا آخری | `Vec` در برابرِ چند `let` |
| `drop(value)` | تابعی که مالکیت می‌گیرد و بدنه‌اش خالی است | رها کردنِ زودهنگام |
| `E0040` | صدا زدنِ مستقیمِ `.drop()` | یعنی `drop(value)` را می‌خواستی |
| `E0184` | `Copy` روی نوعی که تخریب‌گر دارد | یکی از آن دو باید برود |

### الان می‌دانی

- کامپایلر فراخوانیِ پاکسازی را سرِ آکولاد می‌گذارد، و هیچ مسیری از بلاک بیرون نمی‌رود که از آن رد نشود.
- بایندینگ‌های یک بلاک برعکسِ ترتیبِ اعلام آزاد می‌شوند؛ عناصرِ یک مجموعه از اولی تا آخری.
- حرکت دادنِ یک مقدار، زمانِ آزادسازی‌اش را هم جابه‌جا می‌کند.
- سایه‌انداختن مقدارِ قبلی را زودتر آزاد نمی‌کند.
- `drop(value)` یک تابعِ معمولی است که مالکیت می‌گیرد؛ `value.drop()` رد می‌شود چون پاکسازی را دو بار اجرا می‌کرد.
- یک نوع یا `Copy` است یا تخریب‌گر دارد، و هرگز هر دو.
- RAII یعنی آزادسازی به دامنه گره خورده است، نه به حافظه‌ی برنامه‌نویس.
