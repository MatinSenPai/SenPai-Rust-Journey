# ۱.۲.۳ — `Clone` و `Copy`

## در یک نگاه

بعد از این درس می‌توانی:

- بگویی `.clone()` دقیقاً چه هزینه‌ای دارد — و برای یک `Vec<String>` چند تخصیص می‌گیرد.
- بگویی چرا `String` هرگز نمی‌تواند `Copy` باشد، هرچقدر هم کوتاه باشد.
- تفاوتِ «کپی شدن» و «کلون شدن» را بگویی و بگویی کدام‌شان کاری است که *تو* می‌نویسی.
- به یک `E0382` نگاه کنی و تصمیم بگیری که آیا `.clone()` جواب است یا فقط ساکت‌کننده‌ی خطاست.

**زمان:** حدود ۴۵ دقیقه · **پیش‌نیاز:** [۱.۲.۲ — معناشناسیِ حرکت](../02-move-semantics/README.fa.md)

---

## چرا اهمیت دارد

درسِ قبل با یک هشدار تمام شد: `.clone()` هر `E0382`ای را ساکت می‌کند، و همین است که خطرناکش می‌کند.

این درس آن هشدار را به یک عدد تبدیل می‌کند.

مسیرِ معمولِ یک تازه‌کارِ Rust این است: خطای قرض می‌گیرد، `.clone()` می‌زند، خطا می‌رود، تکرار می‌کند. شش ماه بعد یک کدبیس دارد که هزاران `.clone()` در آن پخش شده و از نسخه‌ی پایتونی‌اش کندتر است، و نتیجه می‌گیرد که Rust ارزشش را نداشت.

مشکل `.clone()` نبود. مشکل این بود که هیچ‌وقت اندازه‌اش را نگرفت.

پس این درس اندازه‌گیری می‌کند. و در همان حال یک تفاوتِ ظریف را روشن می‌کند که آدم‌ها ماه‌ها با آن گیج می‌مانند: **`Copy` نسخه‌ی سریعِ `Clone` نیست. قولِ دیگری است.**

---

## مفهوم

### `.clone()` واقعاً چه می‌کند

```rust
let original = String::from("hello");
let copy = original.clone();
```

```text
original:   hello
copy:       hello
original @: 0x1c3fea31920
copy     @: 0x1c3fea31940
```

آن دو نشانی را ببین. **متفاوت‌اند.**

درسِ قبل نشان داد که حرکت نشانی را دست نمی‌زند: سه بار حرکت، یک نشانی. کلون آن را عوض می‌کند، چون کلون از تخصیص‌دهنده یک بافرِ **دوم** خواسته و محتوا را داخلش کپی کرده.

این کلِ تفاوت است، در دو خطِ خروجی:

| | نشانی | تخصیص |
|---|---|---|
| حرکت | همان می‌ماند | هیچ |
| کلون | عوض می‌شود | یکی (حداقل) |

### هزینه با عمقِ داده بالا می‌رود

```rust
let lines = vec![
    String::from("alpha"),
    String::from("beta"),
    String::from("gamma"),
];
let copied = lines.clone();
```

```text
vec     @: 0x1c3fea32160
its copy@: 0x1c3fea31f80
line 0  @: 0x1c3fea31960
its copy@: 0x1c3fea319c0

that clone made 4 allocations: the Vec, and one per String
```

هم بافرِ خودِ وکتور نو است و هم بافرِ هر رشته. **کلونِ یک `Vec<String>` با `n` عنصر یعنی `n + 1` تخصیص.**

این آن عددی است که باید در ذهنت باشد. `.clone()` روی یک `Vec<String>` که هزار سطر دارد، هزار و یک بار به تخصیص‌دهنده مراجعه می‌کند. اگر داخلِ یک حلقه باشد، ضرب در تعدادِ دورها.

### یک نکته‌ی جانبیِ کاربردی

```text
roomy len/cap:  3/100
clone len/cap:  3/3
```

**کلون ظرفیت را حفظ نمی‌کند.** دقیقاً به اندازه‌ی طول تخصیص می‌دهد. یعنی `.clone()` یک راهِ کوچک کردنِ یک بافرِ بیش‌ازحد بزرگ است — هرچند `shrink_to_fit()` نیتت را بهتر می‌گوید و لحظه‌ای هر دو بافر را هم‌زمان نگه نمی‌دارد.

### `Copy` — و اینکه چرا کلونِ سریع نیست

```rust
let a = 5_i32;
let b = a;
println!("a: {a}, b: {b}");
```

```text
a: 5, b: 5
```

هیچ متدی صدا زده نشد. هیچ چیزی ننوشتی. `a` هنوز کار می‌کند.

نوع‌هایی که این خاصیت را دارند صفتِ **`Copy`** را پیاده‌سازی کرده‌اند، و معنایش یک جمله است:

> **کپی کردنِ بایت‌های این مقدار، کلِ مقدار را کپی می‌کند، و چیزی برای تمیز کردن نمی‌ماند.**

برای یک `i32` این بدیهی است: چهار بایت، تمام. برای یک `String` غلط است: کپی کردنِ آن سه کلمه دو مسئول برای یک بافر می‌سازد. برای همین `String` نمی‌تواند `Copy` باشد — و «کوتاه بودنِ رشته» هیچ ربطی ندارد.

| `Copy` | `Copy` نیست |
|---|---|
| `i32`، `u8`، `usize`، `f64` | `String` |
| `bool`، `char` | `Vec<T>` |
| `&T` | هر چیزی که یکی از این‌ها را داشته باشد |
| آرایه و تاپلی که همه‌ی اجزایش `Copy` باشد | هر چیزی که `Drop` داشته باشد |

### رابطه‌ی این دو

اینجا همیشه سوءتفاهم می‌شود، پس صریح:

```rust
let c = a.clone();   // روی یک i32 کار می‌کند
```

**هر نوعِ `Copy` نوعِ `Clone` هم هست.** زبان اجبارش می‌کند. پس `.clone()` روی یک `i32` مجاز است — و دقیقاً همان کاری را می‌کند که انتساب می‌کرد، فقط با اسمی طولانی‌تر. clippy با لینتِ `clone_on_copy` تذکر می‌دهد.

**عکسش برقرار نیست.** `String` نوعِ `Clone` است و هرگز `Copy` نخواهد بود.

پس تفاوتِ واقعی این نیست که کدام سریع‌تر است. این است:

| | چه کسی می‌نویسدش | کِی اتفاق می‌افتد |
|---|---|---|
| `Copy` | هیچ‌کس — ضمنی است | سرِ هر انتساب |
| `Clone` | تو، صریح | فقط وقتی `.clone()` بنویسی |

**`Copy` رفتارِ پیش‌فرضِ انتساب را عوض می‌کند. `Clone` یک متد اضافه می‌کند.** برای همین است که Rust مجبورت می‌کند `.clone()` را تایپ کنی: تخصیص باید در کد دیده شود.

### یک ارجاع `Copy` است

این را راحت می‌شود از قلم انداخت و بعداً گیج‌کننده می‌شود:

```rust
let owned = String::from("hello");
let first = &owned;
let second = first;
println!("both refs work: {first} / {second}");
```

```text
both refs work: hello / hello
```

`first` بعد از انتساب هنوز کار می‌کند، چون `&String` نوعِ `Copy` است. **کپی کردنِ فلش، چیزی که سرِ فلش است را کپی نمی‌کند.** یک فلشِ دوم به همان چیز داری، و هیچ‌کدامشان مالکِ چیزی نیستند.

این تله‌ای هم می‌سازد که در بخشِ خطاها می‌بینی: `.clone()` روی چیزی که یک ارجاع است ممکن است ارجاع را کلون کند نه مقصدش را.

### پس کِی کلون کنی؟

سه وضعیت، سه جواب:

```rust
// ۱. فقط می‌خواهی بخوانی‌اش → قرض بگیر
println!("length: {}", length_of(&name));

// ۲. یکی را نگه می‌داری و یکی را می‌دهی → یک بار کلون کن، عمداً
let for_them = template.clone();

// ۳. کارت با آن تمام است → حرکتش بده
let consumed = consume(finished);
```

```text
length:     5
still ours: Matin
kept:       report-
given:      report-
consumed:   4
```

و اشتباهی که باید بشناسی‌اش:

```rust
for line in &lines {
    let copy = line.clone();     // تخصیص می‌گیرد
    wasteful += copy.len();
}                                 // و آزادش می‌کند، بی‌آنکه چیزی یاد گرفته باشد
```

```text
same answer: 14 / 14
first version allocated 3 times for nothing
```

همان جواب، سه تخصیصِ بی‌فایده. `.len()` فقط لازم بود نگاه کند.

> **قاعده‌ی عملی:** قبل از هر `.clone()` بپرس «آیا واقعاً به دو نسخه‌ی مستقل احتیاج دارم؟» اگر جواب نه است، چیزی که می‌خواستی یک `&` بود. و اگر جواب بله است، کلون کن و احساسِ بدی هم نداشته باش — یک کلونِ درست از یک معماریِ پیچیده برای فرارش بهتر است.

### `Clone` روی نوع‌های خودت

وقتی به [۱.۵.۱](../../05-your-own-types/01-structs-and-methods/README.fa.md) برسی و نوعِ خودت را بنویسی، این را می‌نویسی:

```rust
#[derive(Clone)]
struct Reading { /* ... */ }
```

`derive` یعنی «پیاده‌سازیِ بدیهی را برایم بنویس»: هر فیلد را کلون کن. و اگر همه‌ی فیلدها `Copy` باشند می‌توانی `#[derive(Clone, Copy)]` بنویسی. اگر یکی از فیلدها یک `String` باشد نمی‌توانی، و خطایش در بخشِ بعدی است.

## خطاهایی که خواهی دید

### `E0204` — `Copy` روی چیزی که مالکِ حافظه است

```text
error[E0204]: the trait `Copy` cannot be implemented for this type
  --> examples\04-copy-needs-no-heap.rs:9:8
   |
 8 | #[derive(Clone, Copy)]
   |                 ---- in this derive macro expansion
 9 | struct Reading {
   |        ^^^^^^^
10 |     value: i32,
11 |     label: String,
   |     ------------- this field does not implement `Copy`
```

**کامپایلر به چه اعتراض دارد:** `Copy` یعنی «کپی کردنِ بایت‌ها کلِ مقدار را کپی می‌کند». آن `String` بافری روی هیپ دارد، پس کپی کردنِ بایت‌هایش دو مسئول برای یک بافر می‌سازد. قول قابلِ ارائه نیست.

**راه‌حل:** `Copy` را بردار و فقط `#[derive(Clone)]` بگذار. حالا کپی گرفتن ممکن است ولی باید `.clone()` بنویسی.

**چرا این راه‌حل است:** دقت کن خطا چقدر دقیق است — **دقیقاً همان فیلدی** را زیرخط کشیده که مقصر است. برای یک ساختارِ بیست‌فیلدی این تفاوتِ بینِ یک ثانیه و ده دقیقه است.

و بدان که این مجازات نیست. `Copy` نبودن یعنی «کپی گرفتنِ این چیز هزینه دارد و باید در کد دیده شود» — که برای هر چیزی که مالکِ حافظه است، درست است.

### `E0308` — کلون کردنِ فلش به‌جای مقصد

```text
error[E0308]: mismatched types
  --> examples\05-cloning-a-reference.rs:11:25
   |
11 |     let first: String = lines.first().clone();
   |                ------   ^^^^^^^^^^^^^^^^^^^^^ expected `String`, found `Option<&String>`
   |                |
   |                expected due to this
   |
   = note: expected struct `String`
                found enum `Option<&String>`
```

**کامپایلر به چه اعتراض دارد:** `lines.first()` خودِ رشته را نمی‌دهد؛ یک **نگاه** به آن می‌دهد، پیچیده در `Option` چون ممکن است عنصری نباشد. `.clone()` روی آن، همان بسته را کلون می‌کند — و چون یک ارجاع `Copy` است، کلونش دوباره همان ارجاع است. هیچ رشته‌ای کپی نشد.

**راه‌حل:**

```rust
let first: Option<String> = lines.first().cloned();
```

`.cloned()` — با `d` آخر — «داخلش را کلون کن» است، نه «خودش را کلون کن».

**چرا این راه‌حل است:** این خطا معمولاً یعنی داری زودتر از موعد کلون می‌کنی. `lines.first()` از قبل همان نگاهی است که می‌خواستی؛ اگر فقط قرار بود طولش را بخوانی، هیچ کلونی لازم نبود.

و به تفاوتِ `.clone()` و `.cloned()` عادت کن، چون در سراسرِ Rust تکرار می‌شود. اولی روی *این مقدار* کار می‌کند، دومی روی *مقدارِ داخلِ این پوشش*. `Option` کاملش در [۱.۶.۱](../../06-absence-and-failure/01-option-and-null-safety/README.fa.md) است.

### بساز

یک `pub fn cheapest_join(parts: Vec<String>, separator: char) -> String` بنویس که همان کارِ `joined` از [۱.۱.۶](../../01-foundations/06-vec-and-string-basics/README.fa.md) را بکند — ولی این بار **هیچ کلونی نگیرد**.

بعد بشمار: نسخه‌ی تو چند بار تخصیص گرفت؟ حالا با `String::with_capacity` امتحان کن و ببین می‌توانی به یکی برسانی‌اش.

بعد یک جمله بنویس درباره‌ی اینکه چرا `parts` را مصرف کردن اینجا از قرض گرفتنش ارزان‌تر است.

### چالش (اختیاری)

**بخشِ یک.** این چند بار تخصیص می‌گیرد؟ حدس بزن، بعد با چاپ کردنِ نشانی‌ها بررسی کن:

```rust
let a = vec![String::from("x"), String::from("y")];
let b = a.clone();
let c = b;
let d = c.clone();
```

**بخشِ دو.** این را اجرا کن و هر دو خطِ خروجی را توضیح بده:

```rust
let text = String::from("hello");

let r: &String = &text;
let cloned_ref = r.clone();
println!("{:p} {:p}", r.as_ptr(), cloned_ref.as_ptr());

let rr: &&String = &r;
let cloned_rr = rr.clone();
println!("{:p} {:p}", rr.as_ptr(), cloned_rr.as_ptr());
```

یکی از این دو جفت نشانی یکی است و آن یکی نه. **کدام، و چرا؟** و به تذکری که کامپایلر روی یکی‌شان می‌دهد دقت کن — خودش دقیقاً می‌گوید چه اتفاقی افتاده. (سرنخ: جستجو کن «auto-deref».)

**بخشِ سه.** `cargo clippy` را روی کلِ درس بگیر. کدام لینت‌ها درباره‌ی کلون هستند؟ یکی‌شان را در مستنداتش پیدا کن و بخوان.

---

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به کارت می‌آید |
|---|---|---|
| `Clone` | متدی که یک نسخه‌ی مستقل می‌سازد | وقتی واقعاً دو تا می‌خواهی |
| `Copy` | انتساب کپی می‌کند و مبدأ زنده می‌ماند | اعداد، `bool`، `char`، `&T` |
| `.clone()` | صریح، تخصیص می‌گیرد | باید در کد دیده شود |
| `.cloned()` | داخلِ پوشش را کلون می‌کند | `Option<&T>` به `Option<T>` |
| `#[derive(Clone)]` | پیاده‌سازیِ بدیهی را بساز | نوع‌های خودت، از ۱.۵.۱ |
| `E0204` | `Copy` روی چیزی که مالکِ حافظه است | فیلدِ مقصر زیرخط می‌خورد |
| عمقِ کلون | `n + 1` تخصیص برای `Vec<String>` | عددی که باید بدانی |

### الان می‌دانی

- کلون نشانی را عوض می‌کند چون بافرِ دومی می‌گیرد؛ حرکت این کار را نمی‌کند.
- کلونِ یک `Vec<String>` با `n` عنصر `n + 1` تخصیص می‌گیرد.
- کلون ظرفیت را حفظ نمی‌کند؛ دقیقاً به اندازه‌ی طول می‌گیرد.
- `Copy` یعنی کپیِ بایتی کافی است و چیزی برای تمیز کردن نمی‌ماند.
- هر `Copy` نوعِ `Clone` هم هست؛ عکسش نه.
- `&T` نوعِ `Copy` است، حتی وقتی `T` نباشد.
- آخرین استفاده از یک مقدار باید یک حرکت باشد، نه یک کلون.

### می‌توانی توضیح بدهی؟

- `.clone()` چه چیزی را می‌سازد که حرکت نمی‌ساخت؟
- کلونِ یک `Vec<String>` با صد عنصر چند تخصیص می‌گیرد؟
- چرا `String` نمی‌تواند `Copy` باشد؟
- تفاوتِ `Copy` و `Clone` را در یک جمله بگو.
- چرا `&T` نوعِ `Copy` است حتی وقتی `T` نیست؟
- قبل از نوشتنِ `.clone()` چه سؤالی از خودت می‌پرسی؟
