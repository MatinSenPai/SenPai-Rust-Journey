# ۰۴.۱ — `String` در برابر `&str`

## دو نوع برای یک کار

- `String`: buffer دارای مالکیت، رشدپذیر و heap-allocated از متن UTF-8. با پایان محدوده مالک drop می‌شود و `Copy` نیست.
- `&str`: نمای قرض‌گرفته‌شده از متن UTF-8 در جایی دیگر؛ داخل `String`، بخشی از متن یا string literal. مقدار `"hello"` یک `&'static str` است چون bytes آن در فایل اجرایی قرار دارند.

هر `String` را می‌توان با `&my_string` یا `my_string.as_str()` به‌شکل `&str` قرض داد. تبدیل `&str` به `String` به تخصیص حافظه و copy واقعی با `.to_string()` یا `.to_owned()` نیاز دارد.

```rust
fn greet(name: &str) -> String {
    format!("Hello, {name}!")
}
```

ورودی فقط خوانده می‌شود، پس `&str` literal، قرض‌گرفته‌شده `String` و slice متن بزرگ‌تر را بدون copy می‌پذیرد. خروجی متن تازه است و باید دارای مالکیت باشد؛ تابع نمی‌تواند ارجاع به local data نابودشونده برگرداند.

## مثال ایرانی و بک‌اند

پردازشگر برای خواندن نام مشتری بهتر است `&str` بگیرد، ولی برای ساخت پیام پاسخ `String` تازه برمی‌گرداند. شبیه دیدن یک صفحه از کتاب کتابخانه در برابر داشتن نسخه‌ی شخصی کتاب است؛ اما ارجاع واقعاً «عکس صفحه» نیست و lifetime آن با کامپایلر دنبال می‌شود.

## UTF-8 و نبودن `s[3]`

هر مقدار `char` در UTF-8 بین ۱ تا ۴ بایت جا می‌گیرد. یک اندیس عددی ممکن است وسط یک کدپوینت قرار بگیرد، پس `String` از `s[3]` پشتیبانی نمی‌کند. برای `"سلام"`، مقدار `len()` برابر ۸ بایت و `chars().count()` برابر ۴ مقدار اسکالر Unicode است؛ حتی تعداد نویسه‌های دیداری هم همیشه با تعداد `char`ها یکی نیست.

برای parameter فقط‌خواندنی متن، معمولاً `&str` را به `&String` ترجیح بده. وقتی متن تازه یا مالکیت مستقل می‌سازی، `String` برگردان.
