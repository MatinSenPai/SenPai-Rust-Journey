# راه‌حل

```rust
pub fn chained_division(a: f64, b: f64, c: f64) -> Result<f64, String> {
    let step1 = safe_divide(a, b)?;
    let step2 = safe_divide(step1, c)?;
    Ok(step2)
}
```

اگه فقط بخوای همون اولین `?` رو با یه معادل بر اساس `match` بنویسی، می‌شه این:

```rust
let step1 = match safe_divide(a, b) {
    Ok(v) => v,
    Err(e) => return Err(e),
};
```

پنج خط کد فقط برای گفتن همون چیزی که `?safe_divide(a, b)` تو یه خط می‌گه — و اون الگو (الگوی `Ok(v) => v, Err(e) => return Err(e)`) تقریباً *همیشه* همون چیزیه که `?` بهش تبدیل می‌شه، و دقیقاً به خاطر همینه که به عنوان یه سینتکسِ ساده‌ساز (sugar) وجود داره: حالتِ «خطا رو بدون تغییر بده بالا، وگرنه با همون مقدارِ موفقیت‌آمیز به کارت ادامه بده» انقدر تو کدها رایجه که اگه قرار بود هر دفعه اینطوری بلند نوشته بشه، تبدیل به یه شلوغ‌کاری و نویز خالص می‌شد.

```rust
pub fn parse_positive(s: &str) -> Result<u32, String> {
    s.parse::<u32>().map_err(|e| e.to_string())
}
```

متد `()parse::<u32.` یه `<Result<u32, ParseIntError` برمی‌گردونه — یه نوع خطای *متفاوت* نسبت به خطایِ `<Result<u32, String` که تو امضای این تابع اعلام شده. عملگر `?` فقط یه نوعِ خطایی رو پاس می‌ده بالا که دقیقاً هم‌خونی داشته باشه (یا بشه از طریق traitِ `From` تبدیلش کرد، که اینجا `String` و `ParseIntError` این کار رو به صورت خودکار برای هم انجام نمی‌دن) — در نتیجه اول باید با متدِ `(|map_err(|e| e.to_string.` به‌طور صریح اون نوع خطا رو تبدیل کنیم، یعنی `<Result<u32, ParseIntError` رو به `<Result<u32, String` تبدیل کنیم؛ حالا این خطا با امضای تابعمون هم‌خونی داره و حتی اگه بخوایم می‌تونیم تو خط بعدی از عملگر `?` هم براش استفاده کنیم.

در مورد سؤال چهارم مرور: گونه‌ی `Result::Err` یه *مقدار* (`E`) رو با خودش حمل می‌کنه که توصیف می‌کنه دقیقاً چه اتفاقی افتاده که با شکست مواجه شده؛ اما گونه‌ی `Option::None` ماهیتاً و بر اساسِ طراحیش، هیچ چیزی رو با خودش حمل نمی‌کنه — مقدار `None` فقط یعنی «وجود نداره»، نه اینکه بگه «وجود نداره، و اینم دلیلشه.» اگه یه زمانی حس کردی می‌خوای توضیح بدی که *چرا* یه چیزی غایبه، این معمولاً یه نشونه‌ست که اون تابع باید به جای `Option`، یه `Result` برگردونه.
