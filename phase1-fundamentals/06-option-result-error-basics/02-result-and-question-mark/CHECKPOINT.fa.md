# چک‌پوینت

1. بدنه‌ی تابع `chained_division` رو بازنویسی کن و به جای `?` از یه `match` کامل استفاده کن (و همچنان همون دو تا فراخوانی به تابع `safe_divide` رو داشته باش). اینطوری کدت چند خط طولانی‌تر می‌شه، و چند تا بازویِ `match`ِ بیشتر نوشتی در حالی که فقط به یه بخش از منطقش اهمیت می‌دی؟
2. سعی کن از عملگر `?` داخل `{ ... } ()fn main` استفاده کنی (حالا یا تو یه فایل چک‌نویس یا اینکه تو ذهنت تصورش کن) بدون اینکه امضای تابع `main` رو عوض کنی. انتظار داری با چه خطای کامپایلی مواجه بشی، و برای درست کردنش چه چیزی رو تو نوعِ بازگشتیِ `main` باید تغییر بدی؟
3. تابع `parse_positive` با استفاده از `(|map_err(|e| e.to_string.`، یه خطای نوع `ParseIntError` رو به یه `String` تبدیل می‌کنه. اصلاً چرا این تبدیل لازمه — اگه نوعِ بازگشتیِ `parse_positive` فقط `<Result<u32, String` می‌موند، ولی تو سعی می‌کردی همونجا مستقیماً یه عملگر `?` بذاری تهِ فراخوانی `()parse::<u32.` (بدون استفاده از `map_err`)، چه مشکلی به وجود می‌اومد؟
4. انواعِ `<Option<T` و `<Result<T, E` هر دوتاشون enum هستن و دو تا گونه (variant) دارن که می‌تونی روشون pattern-match انجام بدی. اون تیکه‌اطلاعاتِ اساسی و مهمی که `Result::Err` با خودش حمل می‌کنه اما ساختارِ `Option::None` توانایی انتقال اون رو نداره، چیه؟
