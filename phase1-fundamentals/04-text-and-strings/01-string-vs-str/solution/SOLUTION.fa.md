# راه‌حل — ۱.۴.۱ `String` در برابرِ `&str`

```rust
pub fn byte_length(text: &str) -> usize {
    text.len()
}

pub fn shout(text: &str) -> String {
    text.to_uppercase()
}

pub fn joined(first: &str, second: &str) -> String {
    let mut out = String::with_capacity(first.len() + second.len());
    out.push_str(first);
    out.push_str(second);
    out
}

pub fn extended(text: String, extra: &str) -> String {
    let mut text = text;
    text.push_str(extra);
    text
}

pub fn all_owned(items: &[&str]) -> Vec<String> {
    let mut out = Vec::with_capacity(items.len());
    for item in items {
        out.push(item.to_string());
    }
    out
}
```

پنج تابع، و هر کدام یک تصمیمِ متفاوت دربارهٔ اینکه چه کسی مالکِ بایت‌هاست.

## `byte_length` — یک نما وارد، یک عدد خارج

```rust
text.len()
```

کوتاه‌ترینشان و نمونه‌ی کاملِ نیمه‌ی اولِ قاعده‌ی امضا. تست همین تابع را سه جور صدا می‌زند:

```rust
assert_eq!(byte_length("سلام"), 8);
let owned = "سلام دنیا".to_string();
assert_eq!(byte_length(&owned), 17);
assert_eq!(byte_length(owned.as_str()), 17);
```

یک لیترال، یک `&String`، یک `&str` — و هر سه بدونِ کپی شدنِ حتی یک بایت. اگر امضا را `&String` می‌نوشتی، خطِ اول اصلاً کامپایل نمی‌شد و فراخواننده مجبور بود اول یک `String` بسازد. یک تخصیص، فقط برای رد شدن از نگهبانِ امضا.

و آن ۸ و ۱۷ را نگه دار. `"سلام"` چهار حرف است و هشت بایت؛ `"سلام دنیا"` نُه حرف است و هفده بایت. `len()` بایت می‌شمارد و همیشه همین کار را می‌کند. اینکه آن بایت‌ها دقیقاً چه هستند [۱.۴.۲](../../02-utf8-bytes-chars-graphemes/README.fa.md) است.

## `shout` — یک نما وارد، یک مالک خارج

```rust
text.to_uppercase()
```

نیمه‌ی دومِ قاعده. `to_uppercase` نمی‌تواند نما برگرداند چون متنی که می‌سازد در ورودی وجود نداشت. در آلمانی `ß` به `SS` تبدیل می‌شود — یک حرف به دو حرف — پس جواب حتی تکه‌ای از ورودی هم نیست. متنِ تازه یعنی بافرِ تازه یعنی مالکِ تازه.

تست عمداً فارسی هم دارد:

```rust
assert_eq!(shout("سلام"), "سلام");
```

فارسی حرفِ بزرگ ندارد، پس متن دست‌نخورده برمی‌گردد — ولی **همچنان یک `String` تازه است**، نه همان ورودی. تابع نمی‌تواند از قبل بداند که کاری لازم نیست؛ امضا قبل از اجرا تصمیم گرفته می‌شود.

## `joined` — یک بار تخصیص، نه دو بار

```rust
let mut out = String::with_capacity(first.len() + second.len());
out.push_str(first);
out.push_str(second);
out
```

این هم کار می‌کرد:

```rust
let mut out = first.to_string();
out.push_str(second);
out
```

و تست را رد می‌کرد — به‌جز خطِ ظرفیت:

```rust
assert_eq!(persian.capacity(), persian.len(), "ask for the room once");
```

`first.to_string()` یک بافر به اندازه‌ی `first` می‌گیرد؛ بعد `push_str` می‌بیند جا کم است و بافرِ بزرگ‌تری می‌گیرد و همه‌چیز را کپی می‌کند. دو تخصیص و یک کپیِ اضافه، برای متنی که از اول طولش معلوم بود.

`with_capacity` جوابِ همان چیزی است که در [۱.۱.۶](../../../01-foundations/06-vec-and-string-basics/README.fa.md) درباره‌ی رشدِ دوبرابری خواندی: وقتی عدد را می‌دانی، بگو.

و به `first.len() + second.len()` دقت کن — بایت، نه حرف. برای `"سلام"` و `" دنیا"` می‌شود ۸ + ۹ = ۱۷، و تست همین ۱۷ را می‌خواهد. اگر حرف می‌شمردی عدد غلط می‌شد و بافر یک بار دیگر رشد می‌کرد. **ظرفیت به بایت است، چون بافر به بایت است.**

## `extended` — تنها تابعی که مالک می‌گیرد

```rust
let mut text = text;
text.push_str(extra);
text
```

اینجا `String` در امضا اشتباه نیست، تصمیم است. تست ثابتش می‌کند:

```rust
let was_at = roomy.as_ptr();
let grown = extended(roomy, " دنیا");
assert_eq!(grown.as_ptr(), was_at);
```

نشانی عوض نشده. بافری که فراخواننده داشت، همان بافری است که برگشت — هیچ تخصیصی در کل تابع نگرفتیم.

اگر امضا را `&str` می‌گذاشتی، مجبور بودی یک `String` تازه بسازی و همه‌چیز را کپی کنی، چون یک نما را نمی‌شود رشد داد. آن هم درست کار می‌کرد و یک تخصیصِ کامل گران‌تر بود.

قاعده پس این می‌شود: **`&str` بگیر وقتی می‌خوانی، `String` بگیر وقتی نگه می‌داری.** اولی به فراخواننده اجازه می‌دهد مالکیتش را حفظ کند؛ دومی از او یک بافر می‌گیرد که کارش با آن تمام شده.

آن `let mut text = text;` فقط برای این است که پارامتر تغییرپذیر شود. می‌شد `mut text: String` هم در امضا نوشت و دقیقاً همان است — از بیرون هیچ فرقی ندارد، چون `mut` روی پارامتر بخشی از امضا نیست.

## `all_owned` — n نما وارد، n تخصیص خارج

```rust
let mut out = Vec::with_capacity(items.len());
for item in items {
    out.push(item.to_string());
}
out
```

هیچ‌چیزِ این کد نمی‌گوید «اینجا n بار به تخصیص‌دهنده مراجعه می‌شود»، ولی همین اتفاق می‌افتد: یکی برای خودِ وکتور و یکی برای هر عنصر. دقیقاً همان `n + 1` که در [۱.۲.۳](../../../02-ownership-and-memory/03-clone-and-copy/README.fa.md) شمردی، فقط این بار به‌شکلِ تبدیلِ نما به مالک نوشته شده.

قبل از نوشتنِ چنین تابعی همیشه یک سؤال بپرس: **واقعاً به مالک احتیاج داری؟** اگر فقط قرار است طول‌ها را جمع بزنی یا چاپشان کنی، `&[&str]` را همان‌طور که هست نگه دار و صفر تخصیص بگیر. اینجا امضا گفته `Vec<String>`، پس بله — ولی این تصمیمی است که یک نفر گرفته، نه چیزی که مجبور بوده.

`Vec::with_capacity(items.len())` هم همان حرکتِ `joined` است در یک جای دیگر: تعدادِ نهایی معلوم است، پس یک بار جا بگیر.

## این درس واقعاً درباره‌ی چه بود

- **`String` سه کلمه است و `&str` دو کلمه.** کلمه‌ی سوم ظرفیت است و رشد را ممکن می‌کند.
- **بالا رفتن تخصیص است، پایین آمدن مجانی است.** هر `.to_string()` یک مراجعه به تخصیص‌دهنده است؛ هر `.as_str()` دو کلمه روی پشته.
- **`&str` بگیر، `String` برگردان** — مگر آنکه بافر را نگه داری (مثلِ `extended`) یا جواب تکه‌ای از ورودی باشد ([۱.۴.۴](../../04-slicing-text-safely/README.fa.md)).
- **ظرفیت به بایت است.** برای متنِ فارسی این با تعدادِ حرف‌ها یکی نیست، و همین موضوعِ [۱.۴.۲](../../02-utf8-bytes-chars-graphemes/README.fa.md) است.
- **تبدیلِ ضمنیِ deref فقط `&` را باز می‌کند.** هرگز به‌جای تو تخصیص نمی‌گیرد؛ اگر تخصیصی لازم است، در کد نوشته شده است.
