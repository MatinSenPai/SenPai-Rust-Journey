# راه‌حل — ۱.۱.۳ انواعِ مرکب و واکافت

```rust
pub fn split_duration(total_seconds: u32) -> (u32, u32, u32) {
    let hours = total_seconds / 3_600;
    let minutes = total_seconds % 3_600 / 60;
    let seconds = total_seconds % 60;
    (hours, minutes, seconds)
}

pub fn seconds_from(parts: (u32, u32, u32)) -> u32 {
    let (hours, minutes, seconds) = parts;
    hours * 3_600 + minutes * 60 + seconds
}

pub fn celsius_of(sample: (u32, f64, f64)) -> f64 {
    let (_, celsius, _) = sample;
    celsius
}

pub fn endpoints(readings: [i32; 5]) -> (i32, i32) {
    (readings[0], readings[readings.len() - 1])
}

pub fn midpoint(a: (f64, f64), b: (f64, f64)) -> (f64, f64) {
    let ((ax, ay), (bx, by)) = (a, b);
    ((ax + bx) / 2.0, (ay + by) / 2.0)
}
```

## `split_duration` — خطِ وسط جالبش است

```rust
let minutes = total_seconds % 3_600 / 60;
```

`hours` و `seconds` آسان‌اند. جایی که آدم‌ها اشتباه می‌کنند `minutes` است، و جوابِ اشتباه `total_seconds / 60` است که *همه‌ی* دقیقه‌ها را می‌شمارد، نه آن‌هایی را که بعد از برداشتنِ ساعت‌ها می‌مانند. برای ۹۰۴۵ ثانیه این می‌دهد ۱۵۰ به‌جای ۳۰.

ترتیب مهم است و هیچ زرنگی‌ای در آن نیست: `% 3_600` ساعت‌های کامل را دور می‌ریزد، و تازه بعدش `/ 60` دقیقه‌های باقی‌مانده را می‌شمارد. اگر خواندنش سخت است، این دقیقاً همان را می‌گوید:

```rust
let left_over = total_seconds % 3_600;
let minutes = left_over / 60;
```

`%` و `/` در Rust هم‌اولویت‌اند و از چپ به راست خوانده می‌شوند، پس تک‌خطی و دوخطی یک کدِ یکسان‌اند. هرکدام را که شش ماهِ دیگر می‌توانی بخوانی، بردار.

**تستِ رفت‌وبرگشت همان بررسیِ واقعی است.** `seconds_from(split_duration(n)) == n` باید برای هر `n` برقرار باشد، و این حرفی به‌مراتب قوی‌تر از سه نمونه است. همین ایده — تستِ یک *خاصیت* به‌جای فهرستی از حالت‌ها — اسم دارد: property-based testing، و در [فاز ۲ — تستِ واحد، یکپارچه و مستندات](../../../../phase2-intermediate/06-project-organization-and-testing/02-unit-integration-doc-tests/README.fa.md) برمی‌گردد.

## `seconds_from` — چرا واکافت به‌جای `parts.0`

هر دو کار می‌کنند:

```rust
parts.0 * 3_600 + parts.1 * 60 + parts.2   // کار می‌کند
```

```rust
let (hours, minutes, seconds) = parts;     // بهتر
hours * 3_600 + minutes * 60 + seconds
```

دومی بهتر است، و دلیلش ارزشِ نام بردن دارد: **`parts.1` هیچ چیزی به تو نمی‌گوید، و `minutes` همه‌چیز را می‌گوید.** توی یک تاپلِ سه‌تایی، به‌زحمت می‌شود جای‌ها را در ذهن نگه داشت. توی یک کدبیس، شش ماهِ بعد، `parts.1` هر بار یک معمای کوچک است.

این دقیقاً همان استدلالِ صادقانه علیهِ تاپل‌ها به‌طورِ کلی است، و دلیلِ وجودِ [۱.۵.۱ — ساختارها](../../../05-your-own-types/01-structs-and-methods/README.fa.md). یک struct به فیلدها اسمِ دائمی می‌دهد، پس هرگز مجبور نیستی یادت بماند که جایگاهِ ۱ دقیقه بود.

## `celsius_of` — `_` یک متغیر نیست

```rust
let (_, celsius, _) = sample;
```

`_` اسم نیست و چیزی را نمی‌بندد. یعنی «اینجا یک فیلد هست، شمرده‌امش، و از آن چیزی نمی‌خواهم».

این تمایز مهم‌تر از آن است که به‌نظر می‌آید. **الگو همچنان باید کلِ شکل را تطبیق بدهد.** نمی‌توانی بنویسی `let (celsius) = sample;` و امیدوار باشی Rust وسطی را بردارد — هیچ راهی ندارد بفهمد کدام را می‌خواستی، و بررسیِ تعدادِ عناصر (`E0308`) جلویت را می‌گیرد. نوشتنِ آن دو `_` یعنی تو داری می‌گویی «سه فیلد، و می‌دانمش».

اینجا `sample.1` هم کار می‌کند و کوتاه‌تر است. همان معامله‌ی بالا: توی تابعِ دوخطی خوب است و همان لحظه که کسِ دیگری بخواندش، دیگر خوب نیست.

## `endpoints` — `readings.len() - 1` در برابر `readings[4]`

```rust
(readings[0], readings[readings.len() - 1])
```

`readings[4]` هم درست است، و برای یک `[i32; 5]` تا ابد درست می‌ماند، چون طول بخشی از نوع است — بدون عوض شدنِ امضای تابع نمی‌تواند تغییر کند.

با این حال نسخه‌ی `len() - 1` عادتِ بهتری است، چون نسخه‌ای است که دوام می‌آورد. همان لحظه که این یک `Vec` بشود در [۱.۱.۶](../../06-vec-and-string-basics/README.fa.md)، یا یک برش در [۱.۳.۴](../../../03-borrowing-and-references/04-slices/README.fa.md)، طول دیگر از قبل معلوم نیست و `[4]` می‌شود یک پنیک که منتظرِ یک ورودیِ کوتاه نشسته.

یک تله، که بهتر است همین حالا ببینی نه ساعتِ دو نصفِ‌شب: **`len() - 1` روی یک مجموعه‌ی خالی پنیک می‌کند**، چون `len()` یک `usize` است و `0 - 1` به‌جای منفی شدن، از زیر سرریز می‌کند. روی `[i32; 5]` این اتفاق ممکن نیست. روی `Vec` کاملاً ممکن است، و راه‌حلش `.last()` است که یک `Option` برمی‌گرداند.

## `midpoint` — یک الگو برای دو آرگومان

```rust
let ((ax, ay), (bx, by)) = (a, b);
```

آن خط در یک نفس هم از دو نقطه یک تاپل می‌سازد و هم بازش می‌کند — چهار اسم از دو آرگومان، در یک خط. نسخه‌ی ساده‌تر همان چیز است که دو بار نوشته شده:

```rust
let (ax, ay) = a;
let (bx, by) = b;
```

هر دو خوب‌اند. دلیلِ نشان دادنِ اولی این است که **الگوها دقیقاً به همان عمقی که مقدار دارد تو در تو می‌شوند**، و ماشینِ زیرینش در هر دو حالت یکی است.

### چرا مقدارهای تست این‌شکلی‌اند

هر عددی در آن تست یک نصف است، یک چهارم، یا یک عددِ درست. این تصادفی نیست و ارجاعی است به [۱.۱.۲](../../02-scalar-types-and-overflow/README.fa.md): آن مقدارها در مبنای دو دقیقاً قابلِ نمایش‌اند، پس `assert_eq!` روی `f64` اینجا امن است.

اگر تست از `(0.1, 0.2)` استفاده می‌کرد، ممکن بود به دلایلی که هیچ ربطی به کدِ تو ندارد شکست بخورد. وقتی خودت تستِ اعشاری می‌نویسی، یا عمداً مقدارهای دقیق بردار، یا با یک آستانه مقایسه کن. هیچ‌وقت فرض نکن مقدارها بی‌گناه‌اند.

## این درس واقعاً درباره‌ی چه بود

نه تاپل و آرایه. درباره‌ی دو ایده بود:

- **یک الگو یک شکل است، و Rust بررسی‌اش می‌کند.** غلط نوشتنِ شکل یک خطای کامپایل است، نه یک غافلگیریِ زمانِ اجرا. مدام از این استفاده می‌کنی — در [`match`](../../../05-your-own-types/04-match-in-depth/README.fa.md)، در `if let`، و در هر تابعی که یک مقدارِ مرکب را باز می‌کند.
- **دسترسیِ مکانی کوتاهی می‌خرد و بهایش را با خوانایی می‌دهد.** تاپل‌ها برای دو سه مقدار که کوتاه‌مدت با هم سفر می‌کنند مناسب‌اند. فراتر از آن، دنبالِ اسم می‌گردند، و اسم یعنی struct.
