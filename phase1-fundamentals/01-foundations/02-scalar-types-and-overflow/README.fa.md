# ۱.۱.۲ — انواعِ اسکالر و سرریز

## در یک نگاه

بعد از این درس می‌توانی:

- بگویی `u8` و `i32` و `usize` هر کدام چه محدوده‌ای دارند و کدام را کجا انتخاب کنی.
- پیش‌بینی کنی وقتی یک عددِ صحیح از محدوده‌اش بیرون می‌زند چه اتفاقی می‌افتد — و بدانی جوابش در حالتِ debug و release فرق دارد.
- توضیح بدهی چرا `0.1 + 0.2 == 0.3` نادرست است و به‌جایش چه بنویسی.

**زمان:** حدود ۴۰ دقیقه · **پیش‌نیاز:** [۱.۱.۱ — متغیرها و سایه‌زنی](../01-variables-mutability-shadowing/README.fa.md)

---

## چرا اهمیت دارد

در پایتون یک نوعِ عددِ صحیح داری و بی‌نهایت بزرگ می‌شود. هیچ‌وقت لازم نبوده به اندازه‌اش فکر کنی.

در Rust یازده نوعِ عددِ صحیح داری و هر کدام یک سقف دارند. این اول اذیت‌کننده به نظر می‌رسد، و بعد می‌فهمی چرا اهمیت دارد: **این سقف‌ها همیشه بوده‌اند.** پایتون داشت پنهانشان می‌کرد، و در لحظه‌ای که واقعاً مهم می‌شد — یک شمارنده در پایگاه‌داده، یک شناسه، یک مبلغِ ریالی — همان پنهان‌کاری تبدیل به یک باگ می‌شد که خیلی دیر پیدا می‌شود.

و یک تله‌ی دوم هست که در هر زبانی وجود دارد ولی کمتر کسی جدی‌اش می‌گیرد: **اعداد اعشاری تقریبی‌اند.** `0.1 + 0.2` در پایتون هم `0.30000000000000004` است. تفاوت این است که Rust وادارت می‌کند تصمیم بگیری با آن چه کنی.

## مفهوم

### انواعِ عددِ صحیح: عرض و علامت

اسمِ هر نوع دو چیز می‌گوید: علامت‌دار است یا نه، و چند بیت.

| | ۸ بیت | ۱۶ بیت | ۳۲ بیت | ۶۴ بیت | ۱۲۸ بیت | اندازه‌ی معماری |
|---|---|---|---|---|---|---|
| **بدون علامت** | `u8` | `u16` | `u32` | `u64` | `u128` | `usize` |
| **علامت‌دار** | `i8` | `i16` | `i32` | `i64` | `i128` | `isize` |

- **بدون علامت (`u`)** فقط صفر و مثبت. `u8` از ۰ تا ۲۵۵.
- **علامت‌دار (`i`)** منفی هم می‌گیرد. `i8` از ۱۲۸- تا ۱۲۷.

```text
u8                         0 .. 255
i8                      -128 .. 127
u32                        0 .. 4294967295
i32              -2147483648 .. 2147483647
u64                        0 .. 18446744073709551615
usize                      0 .. 18446744073709551615
```

**`usize` و `isize` اندازه‌شان به معماریِ ماشین بستگی دارد** — روی یک سیستمِ ۶۴ بیتی، ۶۴ بیت. هر جا که با اندازه یا ایندکس سروکار داری `usize` می‌بینی: `.len()` یک `usize` می‌دهد، و ایندکس‌ها `usize` می‌خواهند. دلیلش این است که هیچ مجموعه‌ای نمی‌تواند از فضای آدرس‌دهیِ ماشین بزرگ‌تر باشد.

### کدام را انتخاب کنی؟

| موقعیت | انتخاب |
|---|---|
| نمی‌دانی، چیزِ خاصی نیست | `i32` — پیش‌فرضِ Rust، سریع، جا برای منفی دارد |
| شمارش، اندازه، ایندکس | `usize` |
| شناسه‌ای از پایگاه‌داده | `i64` یا `u64` — `i32` زودتر از چیزی که فکر می‌کنی تمام می‌شود |
| یک بایت | `u8` |
| پول | **هیچ‌کدام از اعشاری‌ها.** `i64` بر حسبِ کوچک‌ترین واحد (ریال، سِنت) |

آن ردیفِ آخر مهم‌ترین است و بعداً برمی‌گردیم بهش.

### سرریز — و اینکه چرا جوابش دو تاست

این اتفاقی است که هیچ‌وقت در پایتون ندیده‌ای:

```rust
let mut count: u8 = 250;
count += 1;   // ... و همین‌طور تا 256
```

در **حالتِ debug** (که `cargo run` پیش‌فرض است) برنامه پنیک می‌کند:

```text
start:      250
plus five:  255

thread 'main' (7560) panicked at examples\04-overflow-panics.rs:17:5:
attempt to add with overflow
```

در **حالتِ release** (`cargo run --release`) پنیک نمی‌کند. می‌پیچد:

```text
start:      250
plus five:  255
plus one:   0
```

**یک برنامه، دو رفتار.** این عمدی است و ارزشش را دارد که بفهمی چرا:

- بررسیِ سرریز در زمانِ اجرا هزینه دارد. در حالتِ release که سرعت مهم است، Rust حذفش می‌کند.
- در حالتِ debug نگهش می‌دارد، چون همان‌جاست که باگ را پیدا می‌کنی.

نتیجه‌ی عملی: **هیچ‌وقت به پنیکِ سرریز به‌عنوانِ محافظ تکیه نکن.** در production وجود ندارد.

### چهار روشِ صریح

Rust برای هر عملیاتِ حسابی چهار نسخه دارد. با اسمشان می‌گویی چه رفتاری می‌خواهی:

```rust
let nearly_full: u8 = 250;

nearly_full.checked_add(10)      // None — جواب جا نمی‌شود
nearly_full.checked_add(5)       // Some(255)
nearly_full.saturating_add(10)   // 255 — روی سقف می‌ماند
nearly_full.wrapping_add(10)     // 4 — عمداً می‌پیچد
nearly_full.overflowing_add(10)  // (4, true) — هم جواب، هم اینکه سرریز شد
```

```text
checked_add(10):     None
checked_add(5):      Some(255)
saturating_add(10):  255
wrapping_add(10):    4
overflowing_add(10): (4, true)
```

کدام کِی:

| روش | وقتی که |
|---|---|
| `checked_` | سرریز یک خطاست که باید مدیریتش کنی — **پیش‌فرضِ درست در کدِ بک‌اند** |
| `saturating_` | ماندن روی سقف معنا دارد (نوارِ پیشرفت، شمارنده‌ی نمایشی) |
| `wrapping_` | واقعاً می‌خواهی بپیچد (هش، شمارنده‌ی چرخشی) |
| `overflowing_` | هم جواب را می‌خواهی هم خبر از سرریز |

آن `None` و `Some(255)` که در خروجی دیدی، `Option` هستند — روشِ Rust برای «شاید مقداری نباشد». درسِ کاملش [۱.۶.۱](../../06-absence-and-failure/01-option-and-null-safety/README.fa.md) است. فعلاً همین‌قدر: `checked_` وقتی جواب جا نشود، هیچی نمی‌دهد.

### اعداد اعشاری: `f32` و `f64`

دو نوع: `f32` و `f64`. پیش‌فرض `f64` است و تقریباً همیشه همان را می‌خواهی.

و حالا آن تله:

```rust
let sum = 0.1 + 0.2;
println!("{sum}");
println!("{}", sum == 0.3);
```

```text
0.30000000000000004
false
```

**این باگِ Rust نیست.** پایتون هم همین را می‌دهد. جاوااسکریپت هم. دلیلش این است که `0.1` در مبنای دو دقیقاً نمایش‌پذیر نیست، همان‌طور که `۱/۳` در مبنای ده نیست.

کاری که به‌جایش می‌کنی:

```rust
let close_enough = (sum - 0.3_f64).abs() < f64::EPSILON;
```

```text
within epsilon ? true
```

یعنی: «آیا اختلافشان از یک آستانه کوچک‌تر است؟» آستانه را خودت انتخاب می‌کنی — `f64::EPSILON` برای عددهای نزدیکِ ۱ خوب است، ولی برای عددهای خیلی بزرگ یا خیلی کوچک باید تناسبی حساب کنی.

**و بارِ دوم می‌گویم چون مهم است: برای پول از اعشاری استفاده نکن.** یک `f64` نمی‌تواند «۱۰٫۱۰ تومان» را دقیق نگه دارد. عددِ صحیح بر حسبِ کوچک‌ترین واحد نگه دار و فقط موقعِ نمایش تقسیم کن.

### `bool` و `char`

```text
bool is 1 byte
char is 4 bytes — it holds one Unicode scalar, not one byte
```

- **`bool`** فقط `true` یا `false`. برخلافِ پایتون، یک عددِ صحیح نیست و `if 1` کامپایل نمی‌شود.
- **`char`** یک **اسکالرِ یونیکد** است، نه یک بایت. چهار بایت می‌گیرد و `'س'` یا `'字'` یا `'🦀'` هم در آن جا می‌شود.

آن دوم برای تو مهم است: `'س'` یک `char` است، ولی در یک رشته چند بایت اشغال می‌کند. این تفاوت درسِ اختصاصیِ خودش را دارد — [۱.۴.۲ — یوتی‌اف-۸، بایت، کاراکتر](../../04-text-and-strings/02-utf8-bytes-chars-graphemes/README.fa.md) — و برای کسی که با متنِ فارسی کار می‌کند از همه مهم‌تر است.

### تبدیل با `as` — و تله‌اش

Rust بینِ نوع‌های عددی تبدیلِ خودکار ندارد. `u8` را نمی‌شود همین‌طوری به یک `u32` داد.

```rust
let small: u8 = 250;
let big = small as u32;      // 250 — بی‌خطر، جا می‌شود
let back = 300_u32 as u8;    // 44  — بی‌سروصدا برید!
```

**`as` هیچ‌وقت شکایت نمی‌کند.** اگر جا نشود، بیت‌های اضافه را دور می‌ریزد. برای همین `as` را فقط وقتی به‌کار ببر که مطمئنی جا می‌شود.

روشِ امنش `try_into` است که به تو می‌گوید جا نشد — ولی `Result` می‌خواهد که هنوز نخوانده‌ای. [فاز ۲ — `TryFrom`](../../../phase2-intermediate/08-rust-toolbox/04-tryfrom-fallible-conversions/README.fa.md) کاملش می‌کند. تا آن موقع: `as` را کم و با دقت استفاده کن.

### جداکننده‌ی خوانا

یک چیزِ کوچک که خیلی کمک می‌کند:

```rust
let big = 1_000_000;      // همان 1000000، فقط خوانا
let bytes = 0xFF_u8;      // مبنای شانزده
let flags = 0b1010_0011;  // مبنای دو
```

آن `_` هیچ اثری روی مقدار ندارد. فقط برای چشمِ توست.

## خطاهایی که خواهی دید

### پنیکِ سرریز — که یک خطای کامپایل نیست

```text
thread 'main' (7560) panicked at examples\04-overflow-panics.rs:17:5:
attempt to add with overflow
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**چه چیزی اتفاق افتاده:** برنامه بدونِ هیچ خطایی کامپایل شد. مشکل زمانِ **اجرا** پیش آمد.

این با هر خطایی که تا حالا دیده‌ای فرق دارد و ارزشِ توجه دارد: کامپایلر نمی‌تواند بداند یک عدد در زمانِ اجرا چقدر می‌شود. سرریز یک خطای نوع نیست؛ یک واقعیتِ زمانِ اجراست.

**راهِ حل:** اگر سرریز واقعاً ممکن است، صریح انتخاب کن: `checked_add` (و مدیریتِ حالتِ «نشد»)، یا `saturating_add`، یا `wrapping_add`. اگر ممکن نیست، نوعِ بزرگ‌تری بگیر.

**چرا این راهِ حل درست است:** پنیک در حالتِ release وجود ندارد، پس اگر رویش حساب کنی در production ساکت می‌شود و عددِ غلط می‌دهد. آن چهار متد در هر دو حالت یکسان رفتار می‌کنند.

### `E0308` روی نوع‌های عددیِ متفاوت

اگر یک `u8` را جایی بدهی که `u32` می‌خواهد:

```text
error[E0308]: mismatched types
  --> src/main.rs:4:20
   |
 4 |     let total: u32 = small;
   |                ---   ^^^^^ expected `u32`, found `u8`
   |                |
   |                expected due to this
   |
help: you can convert a `u8` to a `u32`
   |
 4 |     let total: u32 = small.into();
   |                           +++++++
```

**کامپایلر از چه چیزی شاکی است:** `u8` و `u32` دو نوعِ متفاوت‌اند، حتی اگر مقدارش جا شود. Rust هیچ تبدیلِ خودکاری بینشان انجام نمی‌دهد.

**راهِ حل:** `.into()` وقتی تبدیل همیشه امن است (کوچک به بزرگ)، یا `as` وقتی خودت مطمئنی.

**چرا این راهِ حل درست است:** پیشنهادِ `into()` را کامپایلر داد چون *می‌داند* `u8` همیشه در `u32` جا می‌شود. اگر جهت برعکس بود (`u32` به `u8`) پیشنهادش را نمی‌داد — چون آن تبدیل می‌تواند داده از دست بدهد و باید خودت آگاهانه انتخابش کنی.

### تعمیر

`examples/04-overflow-panics.rs` را طوری تغییر بده که پنیک نکند و به‌جایش وقتی به سقف رسید همان‌جا بماند — بدونِ اینکه نوعِ `count` را عوض کنی.

بعد یک نسخه‌ی دوم بساز که عمداً بپیچد. هر دو را در حالتِ release هم اجرا کن و ببین حالا هر دو حالت یکسان رفتار می‌کنند. **همین نکته‌ی اصلیِ این تمرین است.**

### پیاده‌سازی

چهار تابع در `src/lib.rs`:

```sh
cargo test -p p1-01-02-scalar-types-and-overflow
```

`is_close` را با دقت بخوان: تست بررسی می‌کند که ترتیبِ آرگومان‌ها فرقی نکند. اگر نسخه‌ات فقط برای یک ترتیب کار می‌کند، چیزی را جا انداخته‌ای.

### بساز

یک تابعِ `pub fn safe_price_total(unit_rial: i64, quantity: i64) -> i64` بنویس که مجموعِ قیمت را بر حسبِ ریال حساب کند، و در صورتِ سرریز روی `i64::MAX` بماند.

بعد بنویس چرا این تابع `f64` نمی‌گیرد، حتی اگر «قیمت» در ذهنِ آدم اعشاری به نظر برسد. اگر بتوانی این را برای یک نفرِ دیگر توضیح بدهی، یکی از رایج‌ترین باگ‌های بک‌اند را از زندگی‌ات حذف کرده‌ای.

### چالش (اختیاری)

این را اجرا کن و توضیح بده:

```rust
println!("{}", 300_u32 as u8);
println!("{}", -1_i32 as u32);
println!("{}", 3.99_f64 as i32);
```

هر سه بدونِ هیچ هشداری کامپایل می‌شوند. برای هر کدام بگو چه اتفاقی افتاد و چرا `as` بی‌صدا ماند.

بعد ببین `u8::try_from(300_u32)` چه می‌دهد. تفاوتِ این دو رویکرد — «بی‌صدا ببر» در برابر «بگو نشد» — همان چیزی است که [فاز ۲ — `TryFrom`](../../../phase2-intermediate/08-rust-toolbox/04-tryfrom-fallible-conversions/README.fa.md) کاملش می‌کند.

| بدون علامت / علامت‌دار | `u` فقط نامنفی، `i` منفی هم دارد | انتخابِ نوع |
| عرض (۸، ۳۲، ۶۴ …) | چند بیت، و بنابراین چه محدوده‌ای | هر اعلانِ نوعِ عددی |
| `usize` | اندازه‌ی معماری؛ نوعِ طول‌ها و ایندکس‌ها | `.len()`، ایندکس‌گذاری |
| سرریز (overflow) | نتیجه از محدوده بیرون می‌زند | پنیک در debug، پیچش در release |
| `checked_` / `saturating_` / `wrapping_` / `overflowing_` | چهار پاسخِ صریح به سرریز | هر حسابی که ممکن است سرریز کند |
| `f32` / `f64` | اعشاریِ تقریبی | اندازه‌گیری، آمار — **نه پول** |
| `as` | تبدیلِ بی‌صدا که می‌تواند ببرد | فقط وقتی مطمئنی جا می‌شود |
| `_` در عدد | جداکننده‌ی خوانایی | `1_000_000` |

### الان می‌دانی

- نوع‌های عددی با علامت و عرض مشخص می‌شوند، و `usize` اندازه‌ی معماری است.
- سرریز در debug پنیک می‌کند و در release می‌پیچد — پس محافظ نیست.
- چهار متدِ صریح داری که در هر دو حالت یکسان رفتار می‌کنند.
- اعشاری‌ها تقریبی‌اند؛ با آستانه مقایسه‌شان می‌کنی، نه با `==`.
- پول را عددِ صحیح نگه می‌داری.
- `as` بی‌صدا می‌بُرد.

### می‌توانی توضیح بدهی؟

- `u32` و `i32` چه فرقی دارند و کدام را کِی می‌گیری؟
- `usize` چیست و چرا `.len()` همان را برمی‌گرداند؟
- یک `u8` که به ۲۵۶ می‌رسد در debug چه می‌کند و در release چه؟
- چهار متدِ سرریز را نام ببر و بگو هر کدام کِی درست است.
- چرا `0.1 + 0.2 == 0.3` نادرست است، و به‌جایش چه می‌نویسی؟
- چرا پول را در `f64` نگه نمی‌داری؟
