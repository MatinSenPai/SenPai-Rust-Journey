# راه‌حل — ۱.۱.۲ انواعِ اسکالر و سرریز

```rust
pub fn clamped_add(a: u8, b: u8) -> u8 {
    a.saturating_add(b)
}

pub fn wrapped_add(a: u8, b: u8) -> u8 {
    a.wrapping_add(b)
}

pub fn is_close(a: f64, b: f64) -> bool {
    (a - b).abs() < TOLERANCE
}

pub fn to_fahrenheit(celsius: f64) -> f64 {
    celsius * 9.0 / 5.0 + 32.0
}

pub const TOLERANCE: f64 = 1e-9;
```

## آن دو جمع

هر دو یک فراخوانیِ متد هستند، و درسش همین است: **Rust همان رفتاری را که می‌خواهی از قبل دارد، با اسمی که می‌گوید چه‌کار می‌کند.** اگر دستی نوشتی `if a > 255 - b { 255 } else { a + b }`، درست است و در زبانی که این متدها را ندارد همین را می‌نوشتی — ولی نسخه‌ی نام‌دار نیتش را می‌گوید، نمی‌تواند به‌طورِ نامحسوس غلط باشد، و به همان کدِ ماشین کامپایل می‌شود.

ارزشِ توجه دارد که `a + b` هیچ‌کدام از دو تست را قابلِ اعتماد پاس نمی‌کرد. در debug روی حالت‌های سرریز پنیک می‌کند؛ در release می‌پیچد، که تصادفاً `wrapped_add` را پاس می‌کند و `clamped_add` را می‌اندازد. **تستی که فقط در release پاس می‌شود، باگی است که هنوز پیدایش نکرده‌ای** — یکی از دلایلی که `cargo test` به‌طور پیش‌فرض بیلدِ debug می‌گیرد.

## `is_close` — چرا `.abs()` و نه یک مقایسه‌ی ساده

```rust
(a - b).abs() < TOLERANCE
```

تست اصرار دارد که `is_close(0.3, 0.1 + 0.2)` هم مثلِ `is_close(0.1 + 0.2, 0.3)` کار کند. اگر بدونِ `.abs()` نوشتی `a - b < TOLERANCE`، یکی از دو جهت عددِ منفی می‌دهد که همیشه از آستانه کوچک‌تر است — پس تابعت برای `is_close(1.0, 1000.0)` هم `true` می‌داد.

این یک باگِ واقعی است و خیلی راحت به production می‌رسد. `.abs()` همان چیزی است که مقایسه را درباره‌ی *فاصله* می‌کند نه *ترتیب*.

### درباره‌ی `TOLERANCE` در برابر `f64::EPSILON`

`f64::EPSILON` تقریباً `2.2e-16` است — کوچک‌ترین تفاوتی که *برای مقادیرِ نزدیکِ ۱٫۰* معنا دارد. برای عددهای میلیونی آستانه‌ی اشتباهی است، چون فاصله‌ی بینِ مقادیرِ قابلِ نمایش آنجا خیلی بزرگ‌تر از اپسیلون است؛ و برای عددهای نزدیکِ صفر هم بی‌دلیل سخت‌گیر است.

`1e-9` یک آستانه‌ی ثابت و کلی است. برای این درس و برای بیشترِ کدِ روزمره خوب کار می‌کند. چیزی که باید با خودت ببری این است: **آستانه‌ی درست به بزرگیِ عددها بستگی دارد.** کدِ عددیِ جدی دقیقاً به همین دلیل از مقایسه‌ی نسبی استفاده می‌کند.

## `to_fahrenheit` — چرا `9.0` و نه `9`

```rust
celsius * 9.0 / 5.0 + 32.0
```

اگر بنویسی `celsius * 9 / 5` کامپایل نمی‌شود: `celsius` یک `f64` است و `9` یک عددِ صحیح، و Rust هیچ تبدیلِ خودکاری بینشان انجام نمی‌دهد. `E0308` می‌گیری.

این همان سخت‌گیریِ `"7"` در برابر `7` از فاز ۰ است، این بار روی عددها. گاهی آزاردهنده است و دلیلِ نوشتنِ صریحِ `9.0 / 5.0` همین است.

ولی پشتِ همان آزار یک باگِ واقعی پنهان است. در زبانی که خودکار تبدیل می‌کند، `celsius * 9 / 5` با تقسیمِ عددصحیح بی‌سروصدا می‌بُرد: ۳۷ درجه‌ی سلسیوس می‌شود ۹۸ فارنهایت به‌جای ۹۸٫۶. Rust از کامپایلِ نسخه‌ی مبهم سر باز می‌زند، پس آن باگ اصلاً به تو نمی‌رسد.

## این درس واقعاً درباره‌ی چه بود

نه این چهار تابع. درباره‌ی این عادت‌ها بود:

- **سرریز یک تصمیم است.** `a + b` یعنی تو از گرفتنِ آن تصمیم شانه خالی کرده‌ای.
- **برابریِ اعشاری یک تصمیم است.** `==` یعنی تو اشتباه گرفتی‌اش.
- **نوع‌های عددی خودشان تبدیل نمی‌شوند**، و همان سخت‌گیری دارد چیزی برایت می‌خرد.

تمرین‌ها کوچک‌اند تا تصمیم‌ها دیده شوند. در فاز ۳ که داری آفستِ صفحه‌بندی و مجموعِ مبالغ را داخلِ یک وب‌سرویس حساب می‌کنی، دقیقاً همین تصمیم‌ها را با پیامدهای واقعی می‌گیری.
