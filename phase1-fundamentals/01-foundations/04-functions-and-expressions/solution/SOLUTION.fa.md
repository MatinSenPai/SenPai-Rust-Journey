# راه‌حل — ۱.۱.۴ توابع و عبارت‌ها

```rust
pub fn hypotenuse(a: f64, b: f64) -> f64 {
    (a * a + b * b).sqrt()
}

pub fn box_count(items: u32, per_box: u32) -> u32 {
    items.div_ceil(per_box)
}

pub fn is_leap_year(year: u32) -> bool {
    (year % 4 == 0 && year % 100 != 0) || year % 400 == 0
}

pub fn total_price(unit_price_rial: u64, quantity: u64, discount_percent: u64) -> u64 {
    let subtotal = unit_price_rial * quantity;
    let discount = subtotal * discount_percent / 100;
    subtotal - discount
}

pub fn diagonal_inches(width_px: f64, height_px: f64, dpi: f64) -> f64 {
    hypotenuse(width_px, height_px) / dpi
}
```

هر پنج بدنه بدونِ سمی‌کالن تمام می‌شوند. این یک سلیقه‌ی نگارشی نیست — آخرین عبارت *همان* مقدارِ بازگشتی است، و یک سمی‌کالن آن را به دستور تبدیل می‌کند و تابع را وادار می‌کند `()` برگرداند. اگر `return` و سمی‌کالن گذاشتی، کد درست است و مثلِ ترجمه از یک زبانِ دیگر خوانده می‌شود؛ برنامه‌نویسِ Rust فرمِ بدونِ کلیدواژه را سریع‌تر می‌خواند.

## `hypotenuse` — و نسخه‌ای که از مالِ تو بهتر است

```rust
(a * a + b * b).sqrt()
```

این جوابِ موردِ انتظار است و اشکالی ندارد. ولی `f64` از قبل این را دارد:

```rust
a.hypot(b)
```

همان جواب، و بهتر به شکلی که از تست پیدا نیست: `hypot` وقتی `a` و `b` بزرگ‌اند سرریز نمی‌کند. `a * a` برای `a`ای نزدیکِ `1e200` می‌شود بی‌نهایت و جواب از دست می‌رود؛ `hypot` اول عددها را مقیاس می‌کند و درست درمی‌آورد.

انتظار نمی‌رفت این را بدانی. **انتظار می‌رفت که بالاخره بروی دنبالش بگردی**، و همین عادت است که این تمرین دارد می‌سازد: هر وقت یک حسابِ ساده حس می‌کنی «استاندارد» است، معمولاً کتابخانه‌ی استاندارد از قبل اسمی برایش گذاشته.

## `box_count` — اصطلاحِ قدیمی، و متدی که جایش را گرفت

راهِ کلاسیکِ تقسیم با گرد کردن به بالا، در هر زبانی که تقسیمِ صحیح دارد:

```rust
(items + per_box - 1) / per_box
```

کار می‌کند و دهه‌ها جوابِ درست بود. یک بار که بخوانی‌اش دلیلش را می‌بینی: اضافه کردنِ یکی کمتر از مقسوم‌علیه، هر باقی‌مانده‌ی غیرِصفر را از مرزِ بعدی رد می‌کند.

Rust برایش اسم دارد:

```rust
items.div_ceil(per_box)
```

نسخه‌ی نام‌دار را بردار. نیتش را می‌گوید، نمی‌شود اشتباه تایپش کرد و بی‌سروصدا تقریباً درست کار کند، و — بخشی که از دست می‌رود — **آن اصطلاحِ قدیمی می‌تواند سرریز کند.** اگر `items` نزدیکِ `u32::MAX` باشد، `items + per_box - 1` از بالا رد می‌شود و در debug پنیک می‌کند و در release می‌پیچد؛ دقیقاً همان چیزی که [۱.۱.۲](../../02-scalar-types-and-overflow/README.fa.md) هشدارش را داد. `div_ceil` چنین مشکلی ندارد.

این همان درسِ `hypot` است، دو بار در یک تمرین: **متدِ نام‌دار فقط مرتب‌تر نیست، معمولاً درست‌تر هم هست.**

## `is_leap_year` — یک تصمیم، بدونِ هیچ `if`ای

```rust
(year % 4 == 0 && year % 100 != 0) || year % 400 == 0
```

نکته‌ی این یکی این است که یک قاعده‌ی سه‌شاخه را در قالبِ یک عبارتِ واحد نوشتی و اصلاً سراغِ شرط نرفتی.

`==` و `!=` و `&&` و `||` همگی *مقدار تولید می‌کنند*. `year % 4 == 0` یک `bool` است، دقیقاً به همان معنایی که `2 + 2` یک `i32` است. همین که این را ببینی، یک دسته‌ی کاملِ کد که قبلاً پنج خط `if` می‌نوشتی، در یک خط جمع می‌شود که مثلِ خودِ قاعده خوانده می‌شود.

پرانتزها بی‌کار نیستند. `&&` از `||` محکم‌تر می‌چسبد، پس اکیداً لازم نیستند — ولی قاعده یک شکل دارد («این، مگر آن، مگر آن یکی») و پرانتزها آن شکل را نشان می‌دهند. برای خواننده بنویس.

**`&&` و `||` اتصالِ کوتاه دارند.** برای `year = 2023` عبارتِ `year % 4 == 0` نادرست است، پس `year % 100 != 0` اصلاً ارزیابی نمی‌شود. اینجا فرقی نمی‌کند. جایی خیلی فرق می‌کند که سمتِ راست یک فراخوانیِ تابع باشد که پنیک می‌کرد، یا یک کوئریِ دیتابیس — و همین دلیلی است که می‌شود بررسی و استفاده را در یک خط نوشت.

## `total_price` — دو `let` و بعد یک عبارت

```rust
let subtotal = unit_price_rial * quantity;
let discount = subtotal * discount_percent / 100;
subtotal - discount
```

تک‌خطی‌اش ممکن است و بدتر:

```rust
unit_price_rial * quantity - unit_price_rial * quantity * discount_percent / 100
```

اسم گذاشتن روی گام‌های میانی مجانی است. کامپایلر در هر دو حالت همان کدِ ماشین را می‌سازد، و خواننده اسم‌ها را می‌گیرد. `let` داخلِ بدنه‌ی تابع دقیقاً برای همین است.

**چرا `* discount_percent / 100` و نه `* (discount_percent / 100)`:** دومی تقسیمِ صحیح است و `33 / 100` می‌شود `0`، پس هر تخفیفی هیچ می‌شد. اول ضرب، آخر تقسیم. همان تله‌ی `celsius * 9 / 5` از [۱.۱.۲](../../02-scalar-types-and-overflow/README.fa.md) است، و تا وقتی حسابِ صحیح می‌نویسی تله می‌ماند.

**چرا عددها `u64`اند:** پول. قیمت به ریال سریع بزرگ می‌شود، و `subtotal * discount_percent` از آن هم بزرگ‌تر است — مقدارِ میانی تا صد برابرِ جمعِ کل. دقیقاً همان‌جایی که یک `u32` سرریز می‌کرد. کدِ production یک قدم جلوتر می‌رود و `checked_mul` می‌گیرد، تا یک تعدادِ مسخره به‌جای پنیک، خطا بشود.

## `diagonal_inches` — تک‌خطی‌ای که از همه مهم‌تر است

```rust
hypotenuse(width_px, height_px) / dpi
```

هیچ زرنگی‌ای در آن نیست، و نکته همین است. این تابع از صفحه‌نمایش و اینچ خبر دارد؛ از مربع و جذر هیچ نمی‌داند. اگر فردا `hypotenuse` با `a.hypot(b)` عوض شود، این تابع تکان نمی‌خورد.

فراخوانیِ توابعِ خودت نگرانیِ کارایی نیست. Rust توابعِ کوچک را با سخت‌گیری inline می‌کند، پس `diagonal_inches` تقریباً حتماً به همان دستورهایی کامپایل می‌شود که اگر حساب را دستی می‌نوشتی. **اینجا خوانایی را با سرعت معامله نمی‌کنی.** تابعِ کوچک را بنویس.

## این درس واقعاً درباره‌ی چه بود

- **تقریباً همه‌چیز در Rust یک عبارت است**، پس تقریباً همه‌چیز ارزشی دارد. بلوک‌ها، مقایسه‌ها، زنجیره‌های `&&`، و — از درسِ بعد — `if` و `match` هم.
- **سمی‌کالن یک عملگرِ واقعی است.** چیزی را که ارزشِ یک مقدار دارد تبدیل می‌کند به چیزی که ارزشش `()` است. تقریباً هر «expected `u32`, found `()`»ای که در عمرت ببینی، یک سمی‌کالنِ اضافه است.
- **`return` برای زودتر بیرون آمدن است**، و تقریباً فقط برای همان. مقدارِ آخرِ یک بدنه به هیچ کلیدواژه‌ای احتیاج ندارد.
- **متدِ نام‌دار معمولاً درست‌تر است.** `hypot` و `div_ceil` و `checked_mul` — هرکدامشان یعنی کسی از قبل به حالتِ مرزی‌ای فکر کرده که تو هنوز به آن نرسیده‌ای.
