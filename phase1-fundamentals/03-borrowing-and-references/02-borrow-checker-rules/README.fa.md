# ۰۳.۲ — قواعد borrow checker

خواندن پیام کامپایلر خودش یک مهارت است. در این درس عمداً چند نمونه‌ی خراب می‌بینی تا پیش از آن‌که در پروژه‌ی واقعی غافلگیرت کنند، منطق خطاهایشان را بفهمی.

## دو قانون دقیق

در هر نقطه و برای یک مقدار می‌توانی یکی از این دو حالت را داشته باشی:

- هر تعداد `&T` فعال، یا
- دقیقاً یک `&mut T` فعال.

همچنین ارجاع نباید از مقدار مقصد بیشتر زنده بماند.

```rust
let mut s = String::from("hello");
let r1 = &s;
let r2 = &mut s; // error: shared and mutable borrow overlap
println!("{r1}");
```

```rust
let mut s = String::from("hello");
let r1 = &mut s;
let r2 = &mut s; // error: second mutable borrow
println!("{r1} {r2}");
```

```rust
fn dangle() -> &String {
    let s = String::from("hello");
    &s
}
```

نمونه‌ی آخر می‌خواهد ارجاعی به یک `String` برگرداند، اما خود `String` در پایان تابع از بین می‌رود. Rust چنین ارجاع آویزانی (Dangling Reference) را کامپایل نمی‌کند؛ در C/C++ همین اشتباه می‌تواند به `use-after-free` و یک آسیب‌پذیری امنیتی تبدیل شود.

## مثال صف نانوایی و بک‌اند

در صف نانوایی چند نفر می‌توانند تابلوی شماره‌ها را بخوانند، اما برای عوض‌کردن شماره‌ی در حال سرویس فقط یک نفر باید اختیار داشته باشد. در کد هم اگر یک `String` هنگام وجود یک برش رشد کند، ممکن است بافر آن جابه‌جا و برش قبلی نامعتبر شود؛ بررسی‌کننده‌ی قرض‌گیری پیش از اجرا جلوی این هم‌پوشانی را می‌گیرد.

## این تشبیه کجا دیگر دقیق نیست؟

بررسی‌کننده‌ی قرض‌گیری درباره‌ی نام‌های هم‌زمان برای یک داده و طول عمر حافظه است، نه عدالت صف یا مجوز انسانی. «تغییرپذیری درونی» (Interior Mutability) هم می‌تواند تغییر را از پشت یک ارجاع اشتراکی ممکن کند، اما نوع‌هایی مثل `Cell`، `RefCell` و `Mutex` قواعد و هزینه‌ی این کار را صریح می‌کنند.
