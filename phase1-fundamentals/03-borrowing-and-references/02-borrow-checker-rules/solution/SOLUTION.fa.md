# راه‌حل

```rust
pub fn first_word_len_then_clear(s: &mut String) -> usize {
    let len = s.split_whitespace().next().unwrap_or("").len();
    s.clear();
    len
}
```
عبارتِ `()s.split_whitespace().next` یه قرض‌گرفتنِ موقت و اشتراکی از `s` رو می‌سازه تا یه بُرش از نوع `&str` تولید کنه — اما بلافاصله تو همون دستور، متد `.len()` روش صدا زده می‌شه و فوراً تبدیلش می‌کنه به یه `usize` ساده (که یه مقدار دارای مالکیت یا owned با قابلیت `Copy` هست که دیگه اصلاً هیچ ربطی به `s` نداره). تا زمانی که خطِ بعدی بخواد `()s.clear` رو اجرا کنه، اون قرض‌گرفتنِ موقت خیلی وقته که تموم شده — پس هیچ تداخلی در کار نیست.

```rust
pub fn make_greeting(name: &str) -> String {
    format!("Hello, {name}!")
}
```
راه‌حل برای مشکل «ارجاع آویزون (dangling reference)» اصلاً یه حقه‌ی هوشمندانه با borrow-checker نیست — بلکه یه کار معماریه: سعی نکن ارجاعی رو برگردونی که داره به یه داده‌ای اشاره می‌کنه که قراره همون موقع نابود بشه. به جاش یه داده دارای مالکیت (owned value) رو برگردون، تا مالکیت به صورت تمیز به فراخواننده‌ی تابع (caller) منتقل بشه.

```rust
pub fn describe_and_grow(s: &mut String) -> String {
    let description = {
        let first_char = s.chars().next().unwrap_or(' ');
        format!("{} chars, starts with '{}'", s.len(), first_char)
    };
    s.push_str(" (grown)");
    description
}
```
بلاک درونیِ `{ ... }` دقیقاً کلکِ کار ماست: متغیر `first_char` (که یه قرض از `s` هست) و اون فراخوانی `!format` که داره ازش استفاده می‌کنه، هر دوتاشون داخل همین بلاک محدود (confined) شدن. لحظه‌ای که این بلاک تموم می‌شه، تنها چیزی که ازش می‌مونه متغیر `description` هستش (که یه `String` دارای مالکیته — و `!format` همیشه همچین چیزی می‌سازه)؛ در نتیجه، تمامِ قرض‌هایی که برای ساختنش ایجاد شده بودن تا همون موقع منقضی شدن. وقتی که خطِ بعدی `(...)s.push_str` می‌خواد روی `s` کار کنه، اصلاً هیچ ارجاعِ زنده‌ای (live borrow) رو این متغیر نمی‌بینه.

در مورد سؤال اول مرور: از کامنت خارج کردنِ `conflicting_borrows_demo` تقریباً این خطا رو میده: `E0502: cannot borrow s as mutable because it is also borrowed as immutable`. اینطوری نیست که تو حالت انتزاعی «کامپایلر از اینکه دوتا قرض همزمان باشه خوشش نیاد» — در واقع کامپایلر داره دقیقاً در برابر یه سناریوی خاص ازت محافظت می‌کنه: فرض کن `r2` برای تغییر دادنِ `s` استفاده بشه (مثلاً به خاطر بزرگ شدنش، حافظه‌ی بافرش (buffer) رو جابه‌جا و دوباره تخصیص (reallocate) بده) در حالی که `r1` هنوز انتظار داره بتونه از همون مکان/محتویاتِ *قدیمی* حافظه داده‌ها رو بخونه. تو زبانی که همچین بررسی‌ای نداره، این دقیقاً همون شکلیه که یه باگِ use-after-free یا باگِ iterator-invalidation واقعی رخ میده.
