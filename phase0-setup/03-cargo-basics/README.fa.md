# ۰۳ — مبانی Cargo

ابزار `cargo` تو Rust هم ابزار `build` ئه، هم مدیر بسته، هم اجراکننده‌ی تست و هم خط مقدم formatter/linter — همه‌ی اینا فقط تو یه رابط خط فرمان (CLI). اگه تا حالا از ترکیب `pip` + `venv` + یه `Makefile` استفاده می‌کردی، `cargo` جای هر سه‌ی اینا رو پر می‌کنه.

## ساختار `Cargo.toml`

فایل `Cargo.toml` این درس رو باز کن:

```toml
[package]
name = "p0-03-cargo-basics"
version = "0.1.0"
edition.workspace = true

[dependencies]
rand.workspace = true
```

- `[package]` — شامل متادیتاهای *همین* crate می‌شه: اسمش (که بقیه‌ی crateها اونو با این اسم به عنوان وابستگی می‌شناسن)، نسخه‌اش (در مورد semver پایین‌تر توضیح می‌دم) و اینکه کدوم ویرایش زبان (edition) رو هدف قرار داده.
- `[dependencies]` — لیست بقیه crateهایی که این پروژه بهشون نیاز داره و همون بار اولی که برنامه رو build می‌کنی، از سایت [crates.io](https://crates.io) (معادل PyPI تو Rust) دانلود می‌شن. خط `rand.workspace = true` یعنی «هر نسخه‌ای از `rand` که تو `Cargo.toml` ریشه‌ی مخزن (تحت عنوان `[workspace.dependencies]`) قفل شده رو استفاده کن» — کل این مخزن یک **workspace** کارگو حساب می‌شه؛ بنابراین هر درسی که به `rand` (یا `tokio` یا `serde` و غیره) نیاز داشته باشه، به جای اینکه نسخه‌ی خودش رو انتخاب کنه، از همون یه نسخه‌ی قفل‌شده به اشتراک می‌ذاره. برای دونستن دلیل کامل این کار به `docs/conventions.md` یه سر بزن.

## نسخه‌گذاری معنایی (Semantic versioning یا semver)

مقدار `version = "0.1.0"` از الگوی `MAJOR.MINOR.PATCH` پیروی می‌کنه. وقتی یه crate به نقطه‌ی `1.0.0` می‌رسه، این قول رو می‌ده که: بالا رفتن نسخه‌ی PATCH هیچ‌وقت کدهای شما رو خراب نمی‌کنه، افزایش نسخه‌ی MINOR بدون شکستن کدهای قبلی ویژگی‌های جدید اضافه می‌کنه و افزایش نسخه‌ی MAJOR ممکنه تغییراتی بده که کدهای قبلی رو بشکنه. اما قبل از `1.0.0` (مثل همین درس که `0.1.0` هستش)، حتی تغییر نسخه‌ی MINOR هم ممکنه چیزها رو بشکنه — این همون نشانه‌ایه که نشون میده یه crate هنوز داره به ثبات می‌رسه. این دقیقاً همون قاعده‌ایه که پکیج‌های `pip` *معمولاً* ازش پیروی می‌کنن، با این تفاوت که `cargo`/`crates.io` خیلی سفت و سخت‌تر اجراش می‌کنن و بهش تکیه دارن — این منطق تو دل روشی که وابستگی‌ها (dependency resolution) کار می‌کنن جا افتاده.

## دستوراتی که مدام استفاده می‌کنی

اینا رو از داخل پوشه‌ی همین درس (`phase0-setup/03-cargo-basics/`) اجرا کن:

| دستور | کاری که می‌کنه |
|---|---|
| `cargo check` | سریع‌ترین راه برای پرسیدن اینه که «آیا این کد کامپایل می‌شه؟» — این دستور از مرحله تولید کد نهایی (codegen) صرف‌نظر می‌کنه و فقط نوع‌ها (types) رو بررسی می‌کنه. موقع کد زدن دائماً از این استفاده کن. |
| `cargo build` | کد رو واقعاً تبدیل به یه باینری می‌کنه (که میره تو مسیر `target/debug/`). |
| `cargo run` | برنامه رو `build` می‌کنه (اگه نیاز باشه) و بلافاصله همون باینری رو اجرا می‌کنه. |
| `cargo test` | همه‌ی توابعی که تگ `#[test]` دارن رو کامپایل و اجرا می‌کنه. |
| `cargo add <crate>` | یه وابستگی به `Cargo.toml` اضافه می‌کنه (مثلاً `rand` تو اول کار همینطوری اومده بود تو پروژه — یه وقت روی یه پروژه‌ی تستی `cargo add anyhow` رو امتحان کن تا توی عمل ببینیش). |
| `cargo fmt` | کدت رو به‌صورت خودکار بر اساس استایل استاندارد فرمت می‌کنه. |
| `cargo clippy` | کدهات رو اسکن می‌کنه تا الگوهای غیراستاندارد رو پیدا کنه (درس بعدی مفصل‌تر در این مورد صحبت می‌کنیم). |

## وظیفه‌ی تو

فایل `src/lib.rs` رو باز کن. تابع `format_greeting` رو طوری پیاده‌سازی کن که یه رشته‌ی احوال‌پرسی (greeting) بسازه و به تعداد متغیر `times`، هر کدوم تو یک خط تکرارش کنه. فایل `src/main.rs` یه اسم رو از خط فرمان می‌خونه و این تابع رو صدا می‌زنه — فعلاً نگران فهمیدن تمام جزئیات `main.rs` (مثل پارس کردن آرگومان‌های خط فرمان یا تفاوت `&str` و `String`) نباش — تو فاز یک همه‌ی اینا رو از پایه‌ترین مفاهیم بررسی می‌کنیم. برای این درس، تمرکزت رو بذار رو *گردش کار (workflow)* کارگو: اول `cargo check` ← بعد `cargo test` ← آخرش `cargo run -- YourName`.

```sh
cargo test
cargo run -- Matin
cargo run -- Matin 3
```
