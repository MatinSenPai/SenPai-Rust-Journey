# ۰۴ — مبانی Cargo

## در یک نگاه

بعد از این درس می‌توانی:

- هر بخشِ یک `Cargo.toml` را بخوانی و بگویی چه‌کار می‌کند — از `[package]` تا `[dependencies]`.
- یک وابستگی اضافه کنی، ببینی از کجا آمد، و بگویی `Cargo.lock` چه چیزی را تضمین می‌کند.
- شش دستوری را که هر روز می‌زنی از هم تفکیک کنی و بدانی هر کدام کِی درست است.

**زمان:** حدود ۴۰ دقیقه · **پیش‌نیاز:** [۰۳ — سلام Rust](../03-hello-rust/README.fa.md)

---

## چرا اهمیت دارد

درسِ قبل `cargo` را زیاد تایپ کردی بدون اینکه بدانی چیست. حالا نوبتش است.

از دنیای پایتون می‌آیی، جایی که این کارها بین چند ابزار پخش است: `pip` بسته نصب می‌کند، `venv` محیط می‌سازد، یک `Makefile` یا `tox.ini` دستورها را جمع می‌کند، `pytest` تست می‌گیرد، `black` فرمت می‌کند، `flake8` لینت می‌کند. هر کدام تنظیماتِ خودش، هر کدام مستنداتِ خودش.

`cargo` همه‌ی این‌ها است، در یک ابزار، با یک فایلِ تنظیمات، که در هر پروژه‌ی Rust دنیا یکسان است.

این یکی از دلایلی است که Rust با وجودِ سخت بودنِ زبانش، کار کردن باهاش لذت‌بخش است. ارزشِ یک بعدازظهر وقت گذاشتن دارد.

## مفهوم

### `cargo` چند ابزار را یک‌جا جایگزین می‌کند

| کارِ تو | پایتون | Rust |
|---|---|---|
| ساختنِ پروژه‌ی جدید | `mkdir` + دست‌کاری | `cargo new` |
| نصبِ وابستگی | `pip install` | `cargo add` |
| جداسازیِ محیط | `venv` | خودکار، هر پروژه جداست |
| ساخت | `setup.py` / `build` | `cargo build` |
| اجرا | `python app.py` | `cargo run` |
| تست | `pytest` | `cargo test` |
| فرمت | `black` | `cargo fmt` |
| لینت | `flake8` / `ruff` | `cargo clippy` |
| قفلِ نسخه‌ها | `pip freeze` / `poetry.lock` | `Cargo.lock` (خودکار) |

آن ردیفِ «جداسازیِ محیط» را ببین: در Rust اصلاً چیزی به اسمِ محیطِ مجازی وجود ندارد، چون هیچ‌وقت وابستگی‌ها را «به‌طورِ سراسری» نصب نمی‌کنی. هر پروژه وابستگی‌های خودش را دارد، همیشه. کلِ آن دسته‌ی مشکلات ناپدید می‌شود.

### آناتومیِ `Cargo.toml`

`Cargo.toml`ِ همین درس را باز کن:

```toml
[package]
name = "p0-04-cargo-basics"
version = "0.1.0"
edition.workspace = true

[dependencies]
rand.workspace = true
```

- **`[package]`** — اطلاعاتِ *همین* کریت: اسمش (که دیگران با آن بهش وابسته می‌شوند)، نسخه‌اش، و ویرایشِ زبانی که هدف گرفته.
- **`[dependencies]`** — کریت‌های دیگری که این یکی لازم دارد. بارِ اول که بیلد کنی، از [crates.io](https://crates.io) دانلود می‌شوند — همان چیزی که PyPI برای پایتون است.

آن `edition.workspace = true` و `rand.workspace = true` یعنی «هر چیزی که `Cargo.toml`ِ ریشه‌ی مخزن پین کرده، همان را استفاده کن».

### کریت، پکیج، ورک‌اسپیس

سه واژه که مدام قاتیشان می‌کنند:

- **کریت (crate)** — یک واحدِ کامپایل. یا یک کتابخانه است یا یک باینری. `src/lib.rs` یک کریت است؛ `src/main.rs` یکی دیگر.
- **پکیج (package)** — چیزی که یک `Cargo.toml` دارد. می‌تواند حداکثر یک کریتِ کتابخانه‌ای و هر تعداد کریتِ باینری داشته باشد. همین درس یک پکیج است با دو کریت.
- **ورک‌اسپیس (workspace)** — چند پکیج که یک `Cargo.lock` و یک پوشه‌ی `target/` مشترک دارند.

**کلِ این مخزن یک ورک‌اسپیس است.** یعنی وقتی `tokio` را یک بار کامپایل می‌کنی، همه‌ی ۱۰۰ درسی که بهش نیاز دارند از همان استفاده می‌کنند — نه اینکه ۱۰۰ بار کامپایل شود. به همین دلیل است که `-p` را در دستورها می‌بینی: `-p` می‌گوید «کدام پکیج».

```sh
cargo test                          # همه‌ی پکیج‌های ورک‌اسپیس
cargo test -p p0-04-cargo-basics    # فقط این یکی
```

قواعدِ کاملِ نام‌گذاری و اینکه چرا هر درس اسمِ پکیجِ پیشونددار دارد، در [`docs/conventions.fa.md`](../../docs/conventions.fa.md) است.

### وابستگی‌ها و crates.io

اضافه کردنِ یک وابستگی یک دستور است:

```sh
cargo add rand
```

این خودش `Cargo.toml` را ویرایش می‌کند، آخرین نسخه‌ی سازگار را پیدا می‌کند، و دفعه‌ی بعد که بیلد کنی دانلودش می‌کند. دیگر لازم نیست دستی فایل را باز کنی.

ببین همین درس چه چیزی می‌کشد:

```sh
cargo tree -p p0-04-cargo-basics --depth 1
```

```text
p0-04-cargo-basics v0.1.0 (M:\SenPai-Rust-Journey\phase0-setup\04-cargo-basics)
└── rand v0.8.6
```

`--depth 1` را بردار تا کلِ درخت — یعنی وابستگی‌های وابستگی‌ها — را ببینی. عادت خوبی است: پیش از اینکه یک کریت را به یک پروژه‌ی واقعی اضافه کنی، ببین چه چیزهایی را با خودش می‌آورد.

### نسخه‌بندیِ معنایی و `Cargo.lock`

`version = "0.1.0"` قالبِ `MAJOR.MINOR.PATCH` را دارد. قرارداد این است:

| افزایش | معنایش | مثال |
|---|---|---|
| PATCH (`1.2.3` → `1.2.4`) | رفعِ باگ، چیزی نمی‌شکند | همیشه امن |
| MINOR (`1.2.3` → `1.3.0`) | ویژگیِ جدید، چیزی نمی‌شکند | امن |
| MAJOR (`1.2.3` → `2.0.0`) | ممکن است بشکند | با احتیاط |

**پیش از `1.0.0` قاعده فرق می‌کند:** برای `0.x.y`، افزایشِ MINOR هم می‌تواند بشکند. یعنی `rand 0.8` می‌تواند با `rand 0.9` ناسازگار باشد. این همان علامتی است که یک کریت به تو می‌دهد که «هنوز دارم تثبیت می‌شوم».

پایتون هم *معمولاً* همین قرارداد را دارد، ولی cargo و crates.io خیلی جدی‌تر رویش حساب می‌کنند — حلِ وابستگی مستقیماً بر پایه‌ی همین ساخته شده.

**`Cargo.lock`** نسخه‌ی *دقیقی* را که واقعاً انتخاب شد ثبت می‌کند. `Cargo.toml` می‌گوید «هر `0.8.x`ی»؛ `Cargo.lock` می‌گوید «دقیقاً `0.8.6`». قاعده‌اش:

- برای یک **باینری** (چیزی که deploy می‌شود): `Cargo.lock` را کامیت کن. می‌خواهی سرور دقیقاً همان چیزی را بسازد که تو تست کردی.
- برای یک **کتابخانه** (چیزی که منتشر می‌شود): کامیتش نکن. مصرف‌کنندگانت باید بتوانند نسخه‌ی خودشان را انتخاب کنند.

این مخزن کامیتش می‌کند، چون همه باید بیلدِ یکسان بگیرند.

### شش دستوری که هر روز می‌زنی

| دستور | کارش | کِی |
|---|---|---|
| `cargo check` | فقط بررسیِ کامپایل، بدونِ ساختِ باینری | مدام، حینِ نوشتن |
| `cargo build` | ساختِ باینری زیرِ `target/debug/` | وقتی واقعاً باینری می‌خواهی |
| `cargo run` | بیلد (اگر لازم باشد) و اجرا | امتحانِ برنامه |
| `cargo test` | اجرای هر تابعِ `#[test]` | وقتی فکر می‌کنی درست شد |
| `cargo fmt` | قالب‌بندیِ خودکار به سبکِ استاندارد | پیش از هر کامیت |
| `cargo clippy` | لینت برای الگوهای غیراصطلاحی | پیش از هر کامیت (درسِ ۰۶) |

اختلافِ `check` و `build` روی این پروژه‌ی کوچک از صفر شروع می‌شود:

```text
cargo check → 0.87s
cargo build → 1.20s
```

روی این اندازه ناچیز است. روی یک پروژه‌ی واقعی با پنجاه وابستگی، همان اختلاف می‌شود ده ثانیه در برابر دو دقیقه. برای همین `check` را می‌زنی.

### `target/` چیست و چرا این‌قدر بزرگ می‌شود

هر چیزی که `cargo` می‌سازد در `target/` می‌رود: کدِ کامپایل‌شده‌ی کریتِ تو، کدِ کامپایل‌شده‌ی هر وابستگی، اجراییِ تست‌ها، همه‌چیز.

راحت به چند گیگابایت می‌رسد. این عادی است و در gitignore هست.

```sh
cargo clean    # همه‌اش را پاک کن
```

بعدش بیلدِ بعدی از صفر است و کند. `cargo clean` را وقتی بزن که یا جای دیسک لازم داری یا مشکوکی که کشِ بیلد خراب شده — نه به‌عنوانِ عادت.

## دست‌به‌کد

اول ببین یک وابستگی چه چیزی برایت می‌آورد:

```sh
cargo run -p p0-04-cargo-basics --example 01-dependency-tour
```

```text
a random number: 215
a coin flip:     true

Neither of those lines is in the standard library.
They work because `Cargo.toml` says `rand.workspace = true`.
```

(عددها هر بار فرق می‌کنند — همین نکته‌ی `rand` است.)

بعد این‌ها را بزن و خروجی را بخوان:

```sh
cargo tree -p p0-04-cargo-basics                 # همه‌ی وابستگی‌ها، تا ته
cargo tree -p p0-04-cargo-basics --depth 1       # فقط وابستگی‌های مستقیم
```

و آخر، یک پروژه‌ی کاملاً جدا در جای دیگری بساز تا `cargo new` را ببینی:

```sh
cd /tmp            # یا هر جای دیگری بیرون از این مخزن
cargo new hello-cargo
cd hello-cargo
cargo run
```

چهار فایل ساخته شد. هر چهار تا را نگاه کن — مخصوصاً اینکه `cargo new` خودش `git init` هم زده.

## خطاهایی که خواهی دید

### `error: package ID specification ... did not match any packages`

```text
error: package ID specification `p0-04-cargo` did not match any packages

help: a package with a similar name exists: `p0-04-cargo-basics`
```

**کامپایلر از چه چیزی شاکی است:** اسمی که به `-p` دادی، اسمِ هیچ پکیجی در این ورک‌اسپیس نیست.

**راهِ حل:** اسمِ کامل را بنویس. `cargo` خودش نزدیک‌ترینش را پیشنهاد می‌دهد.

**چرا این راهِ حل درست است:** `-p` اسمِ **پکیج** را می‌گیرد (همان `name` در `[package]`)، نه مسیرِ پوشه را. آن‌ها معمولاً شبیه‌اند ولی یکی نیستند — اسمِ پوشه با عدد شروع می‌شود و اسمِ پکیج نمی‌تواند. `cargo metadata --no-deps` هر اسمِ موجود را فهرست می‌کند.

### وابستگی‌ای که در `Cargo.toml` نیست

اگر در کدت `rand` را استفاده کنی ولی از `Cargo.toml` برداری:

```text
error[E0432]: unresolved import `rand`
 --> src/lib.rs:1:5
  |
1 | use rand::random;
  |     ^^^^ use of unresolved module or unlinked crate `rand`
  |
  = help: you might be missing a crate `rand`
```

**کامپایلر از چه چیزی شاکی است:** کدت به کریتی اشاره می‌کند که این پکیج بهش وابسته نیست.

**راهِ حل:** `cargo add rand` — یا در این مخزن، `rand.workspace = true` را برگردان.

**چرا این راهِ حل درست است:** برخلافِ پایتون که هر چیزی روی سیستم نصب باشد قابلِ import است، در Rust هر پکیج باید صریحاً بگوید به چه چیزی وابسته است. سخت‌گیرانه‌تر است، و دلیلِ همان است که «روی سیستمِ من کار می‌کرد» در Rust تقریباً هیچ‌وقت پیش نمی‌آید.

### تعمیر

در `Cargo.toml` این درس، خطِ `rand.workspace = true` را کامنت کن و `cargo check -p p0-04-cargo-basics` بزن.

خطایی را که می‌گیری بخوان و از روی همان بگو کدام فایل و کدام خط شکسته. بعد برش گردان.

### پیاده‌سازی

دو تابع در `src/lib.rs`:

```sh
cargo test -p p0-04-cargo-basics
```

دومی — `pick_encouragement` — عمداً به `rand` نیاز دارد. مستنداتش را همان روی کامپیوترت باز کن:

```sh
cargo doc -p p0-04-cargo-basics --open
```

این مستنداتِ هر وابستگی‌ات را می‌سازد و در مرورگر باز می‌کند. عادت به این کن به‌جای گشتن در گوگل — این نسخه دقیقاً همانی است که داری استفاده می‌کنی، نه یکی که سه سال پیش منتشر شده.

بعد برنامه را اجرا کن، با آرگومان و بدونش:

```sh
cargo run -p p0-04-cargo-basics
cargo run -p p0-04-cargo-basics -- Matin
```

آن `--` مهم است: هر چیزی قبلش برای `cargo` است و هر چیزی بعدش برای برنامه‌ی تو.

### بساز

در `/tmp` (یا هر جایی بیرونِ این مخزن) یک پروژه‌ی جدید بساز و یک وابستگی بهش اضافه کن:

```sh
cargo new my-first-crate
cd my-first-crate
cargo add rand
```

`Cargo.toml` را قبل و بعد از `cargo add` نگاه کن. بعد در `main.rs` چیزی بنویس که واقعاً از `rand` استفاده کند و اجرایش کن.

هدف این است که یک بار کاملاً از صفر این کار را کرده باشی، تا وقتی در فاز ۳ یک سرویس می‌سازی، این قسمتش برایت جا افتاده باشد.

### چالش (اختیاری)

`cargo tree -p p0-04-cargo-basics` را کامل اجرا کن. `rand` خودش چند وابستگی می‌آورد.

حالا دو کریتِ زیر را در [crates.io](https://crates.io) نگاه کن و تعدادِ وابستگی‌هایشان را مقایسه کن: `serde_json` و `reqwest`. بعد از خودت بپرس چرا اضافه کردنِ یک کریت به یک پروژه‌ی واقعی، تصمیمی است که باید بهش فکر کرد — نه فقط برای زمانِ بیلد، بلکه برای اینکه به کدِ چه کسانی داری اعتماد می‌کنی.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| کریت (crate) | یک واحدِ کامپایل: یک کتابخانه یا یک باینری | هر فایلِ `lib.rs` یا `main.rs` |
| پکیج (package) | چیزی که یک `Cargo.toml` دارد | هر پوشه‌ی درس |
| ورک‌اسپیس (workspace) | چند پکیج با `Cargo.lock` و `target/` مشترک | کلِ همین مخزن |
| `-p <name>` | «روی این پکیج کار کن» | هر دستوری در این مخزن |
| crates.io | مخزنِ عمومیِ بسته‌ها | معادلِ PyPI |
| نسخه‌بندیِ معنایی | `MAJOR.MINOR.PATCH` و قولی که می‌دهد | خواندنِ هر `Cargo.toml` |
| `Cargo.lock` | نسخه‌های دقیقی که واقعاً انتخاب شدند | باینری‌ها کامیتش می‌کنند، کتابخانه‌ها نه |
| `--` | مرزِ بینِ آرگومان‌های cargo و آرگومان‌های برنامه‌ی تو | `cargo run -- ...` |

### الان می‌دانی

- `cargo` جای `pip` و `venv` و `pytest` و `black` و `flake8` و یک `Makefile` را با هم می‌گیرد.
- پکیج یک `Cargo.toml` دارد؛ کریت یک واحدِ کامپایل است؛ این مخزن یک ورک‌اسپیس است.
- `cargo add` وابستگی اضافه می‌کند و `cargo tree` نشان می‌دهد چه چیزی با خودش آورد.
- نسخه‌های `0.x` قواعدِ متفاوتی دارند و `Cargo.lock` بیلدت را تکرارپذیر می‌کند.
- `cargo check` سریع است و `cargo build` باینری می‌سازد.
- `target/` بزرگ می‌شود و اشکالی ندارد.

### می‌توانی توضیح بدهی؟

- `cargo` جای چه ابزارهایی از دنیای پایتون را می‌گیرد؟
- کریت، پکیج و ورک‌اسپیس چه فرقی دارند؟
- `-p` چه‌کار می‌کند و چرا در این مخزن لازم است؟
- `Cargo.toml` و `Cargo.lock` چه فرقی دارند، و کدام را کامیت می‌کنی؟
- چرا `rand = "0.8"` تو را به `0.9` نمی‌برد؟
- در `cargo run -- Matin`، آن `--` چه‌کار می‌کند؟
