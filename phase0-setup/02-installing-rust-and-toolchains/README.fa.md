# ۰۲ — نصبِ Rust و زنجیره‌ابزارها

## در یک نگاه

بعد از این درس می‌توانی:

- Rust را نصب کنی و با یک دستور ثابت کنی که واقعاً درست نصب شده.
- بگویی `rustup`، `rustc` و `cargo` هر کدام چه‌کاره‌اند و چرا سه تا اسمِ جداگانه‌اند.
- توضیح بدهی کانال (channel) و ویرایش (edition) چه فرقی دارند، و چرا `rust-toolchain.toml`ِ این مخزن مهم است.

> دستورهای دقیقِ نصب در [`docs/setup-guide.fa.md`](../../docs/setup-guide.fa.md) هستند تا یک‌جا بمانند و بعداً هم بتوانی چکشان کنی. **الان برو نصب کن**، بعد برگرد و بقیه‌ی این صفحه را بخوان.

هر سه در بیست دقیقه توضیح‌دادنی‌اند. بگذار همین حالا توضیح داده شوند.

## مفهوم

### `rustup` یک نصب‌کننده نیست، یک مدیر است

تو «Rust» را مستقیم نصب نمی‌کنی. `rustup` را نصب می‌کنی، و `rustup` بقیه را می‌آورد.

نزدیک‌ترین معادلِ پایتونی‌اش `pyenv` است — همان ابزاری که می‌گذارد پایتونِ ۳٫۹ و ۳٫۱۱ و ۳٫۱۳ را کنارِ هم داشته باشی و بینشان جابه‌جا شوی. با یک تفاوتِ مهم: `pyenv` یک ابزارِ جانبیِ اختیاری است، ولی `rustup` **روشِ رسمی و همگانی** مدیریتِ نسخه‌های Rust است. عملاً همه از همین استفاده می‌کنند.

سه اسمی که مدام می‌بینی:

| اسم | چیست | معادلِ تقریبیِ پایتونی |
|---|---|---|
| `rustup` | نسخه‌ها و اجزا را مدیریت می‌کند | `pyenv` |
| `rustc` | خودِ کامپایلر | `python` (خودِ مفسر) |
| `cargo` | ابزارِ ساخت و مدیرِ بسته | `pip` + `venv` + `build` + `pytest`، یک‌جا |

تو تقریباً هیچ‌وقت `rustc` را مستقیم صدا نمی‌زنی. با `cargo` کار می‌کنی و `cargo` است که `rustc` را صدا می‌زند. (استثنایش `rustc --explain` است که در درسِ ۰۵ می‌بینی.)

**زنجیره‌ابزار (toolchain)** یعنی بسته‌ی `rustc` و `cargo` و چند تکه‌ی دیگر که همه با هم نسخه‌گذاری شده‌اند.

### کانال‌ها: stable، beta، nightly

Rust روی سه کانال منتشر می‌شود:

- **stable** — هر شش هفته یک نسخه‌ی پایدارِ جدید. هر چیزی در این مخزن، و تقریباً هر شغلی، روی همین است.
- **beta** — نسخه‌ی پایدارِ بعدی، در حالِ آزمایش.
- **nightly** — هر شب از آخرین کدِ زبان ساخته می‌شود و امکاناتِ آزمایشی دارد که پشتِ `#![feature(...)]` قفل‌اند.

آن ریتمِ شش‌هفته‌ای عمدی است: Rust نسخه‌های بزرگ و پرسروصدا نمی‌دهد؛ چیزهای کوچک را مرتب می‌فرستد. یعنی به‌روزرسانی معمولاً بی‌درد است.

**کِی به nightly نیاز پیدا می‌کنی؟** در این دوره هیچ‌وقت. بعضی ابزارها (بعضی لینت‌های clippy، بعضی کتابخانه‌های ماکرو) روی nightly تجربه‌ی بهتری می‌دهند، ولی هیچ‌کدامش لازم نیست. اگر یک آموزش گفت nightly لازم است، اول بگرد ببین چرا — معمولاً به یک ویژگیِ خاص نیاز دارد، نه به nightly به‌طورِ کلی.

### `rust-toolchain.toml` — چرا نسخه‌ی تو با نسخه‌ی من یکی است

در ریشه‌ی همین مخزن یک فایل هست:

```toml
[toolchain]
channel = "stable"
```

اثرش این است: **هر دستورِ `cargo` یا `rustc` که داخلِ این مخزن بزنی، از stable استفاده می‌کند**، فارغ از اینکه پیش‌فرضِ سراسریِ تو روی سیستم چه باشد. `rustup` این فایل را می‌بیند و خودش عوض می‌کند.

همان ایده‌ی `.python-version` برای `pyenv` است، یا تگِ ایمیجِ پایه در `Dockerfile`: **نسخه را پین کن، به «هرچه نصب است» تکیه نکن.** وقتی روی استریم کاری می‌کنی و کسی می‌خواهد دنبال کند، این همان چیزی است که باعث می‌شود خروجی‌اش با خروجیِ تو یکی باشد.

### ویرایش‌ها (editions) — و چرا شبیهِ پایتون ۲ و ۳ نیستند

در هر `Cargo.toml` این را می‌بینی:

```toml
edition = "2021"
```

یک **ویرایش (edition)** راهی است برای اینکه هر چند سال یک بار، تغییراتِ کوچکِ ناسازگار وارد زبان شود بدون اینکه کدهای موجود بشکنند. تا الان ۲۰۱۵، ۲۰۱۸، ۲۰۲۱ و ۲۰۲۴ داشته‌ایم.

نکته‌ی کلیدی — و همان چیزی که آن را از پایتون ۲ به ۳ جدا می‌کند: **کدِ ویرایشِ قدیمی تا ابد کامپایل می‌شود**، و در یک برنامه‌ی واحد، کریت‌های مختلف می‌توانند ویرایش‌های مختلف داشته باشند. `cargo` فقط باید بداند هر کریت کدام را هدف گرفته.

پس اگر آموزشی دیدی که `edition = "2024"` دارد و مالِ تو `2021` است، چیزی خراب نیست. فقط ممکن است چند نکته‌ی نحوی فرق کند.

### چه چیزی کجا نصب می‌شود

خوب است بدانی، چون یک روز لازم می‌شود:

| مسیر | داخلش چیست |
|---|---|
| `~/.rustup/` | خودِ زنجیره‌ابزارها. اینجا بزرگ می‌شود. |
| `~/.cargo/bin/` | فایل‌های اجرایی: `cargo`، `rustc`، `rustup`، و هر ابزاری که با `cargo install` نصب کنی |
| `~/.cargo/registry/` | کدِ منبعِ دانلودشده‌ی کریت‌ها. کشِ اشتراکیِ همه‌ی پروژه‌هایت. |
| `target/` (در هر پروژه) | خروجیِ ساخت. gitignore شده و می‌شود هر وقت خواستی پاکش کرد. |

روی ویندوز، `~` همان `C:\Users\<اسمِ تو>` است.

آن `~/.cargo/bin` باید در `PATH` باشد — نصب‌کننده خودش اضافه‌اش می‌کند، ولی **باید ترمینال را ببندی و دوباره باز کنی** تا اثر کند. شایع‌ترین «نصب نشد»ِ دنیا همین است.

### دو دستوری که بعداً لازمت می‌شوند

```sh
rustup show      # چه چیزی نصب است و الان کدام فعال است
rustup update    # همه‌چیز را به آخرین نسخه ببر
```

`rustup show` وقتی گیج شدی که «کدام نسخه دارد اجرا می‌شود؟»، جوابِ قطعی است.

و یکی دیگر که کمتر کسی می‌داند و خیلی خوب است:

```sh
rustup doc       # کلِ مستنداتِ Rust را آفلاین در مرورگر باز می‌کند
```

کتابِ رسمی، مرجعِ کتابخانه‌ی استاندارد، همه‌اش. بدونِ اینترنت. اگر اینترنتت پایدار نیست، این خیلی به‌کارت می‌آید.

## دست‌به‌کد

نصب کن (طبقِ [`docs/setup-guide.fa.md`](../../docs/setup-guide.fa.md))، بعد این چهار دستور را بزن. هر چهار تا باید شماره‌ی نسخه چاپ کنند:

```sh
rustc --version
cargo --version
rustup --version
rustup show
```

نمونه‌ی خروجی (عددها فرق می‌کنند):

```text
rustc 1.97.0 (a3b1b2c4d 2026-07-14)
cargo 1.97.0 (b8f2e1a90 2026-07-09)
rustup 1.28.1 (2026-05-22)
```

بعد داخلِ همین مخزن این را بزن و ببین `rust-toolchain.toml` دارد کارش را می‌کند:

```sh
rustup show
```

باید stable را به‌عنوانِ زنجیره‌ابزارِ فعال نشان بدهد، با اشاره به همین دایرکتوری.

و آخر، مستندات را آفلاین باز کن تا بدانی وجود دارد:

```sh
rustup doc
```

## خطاهایی که خواهی دید

### `cargo: command not found` بلافاصله بعد از نصب

نصب موفق بوده؛ فقط ترمینالِ فعلیِ تو `PATH`ِ به‌روزشده را ندیده.

**راهِ حل:** ترمینال را کاملاً ببند و دوباره باز کن. اگر با VS Code کار می‌کنی، خودِ VS Code را هم ببند و باز کن، نه فقط پنجره‌ی ترمینالش را.

**چرا:** نصب‌کننده `~/.cargo/bin` را به `PATH` اضافه می‌کند، ولی یک پروسه‌ی در حالِ اجرا محیطش را از نو نمی‌خواند. این ربطی به Rust ندارد؛ همین اتفاق برای هر ابزاری می‌افتد.

### روی ویندوز: `linker 'link.exe' not found`

```text
error: linker `link.exe` not found
  |
  = note: program not found

note: the msvc targets depend on the msvc linker but `link.exe` was not found
note: please ensure that Visual Studio 2017 or later, or Build Tools for Visual Studio
      were installed with the Visual C++ option.
```

**کامپایلر از چه چیزی شاکی است:** `rustc` کدِ ماشین تولید کرد، ولی برای اینکه آن را به یک `.exe` تبدیل کند به یک **لینکر (linker)** نیاز دارد — و روی ویندوز، لینکر بخشی از ابزارهای مایکروسافت است، نه بخشی از Rust.

**راهِ حل:** «Build Tools for Visual Studio» را نصب کن و حتماً بارِ کاریِ «Desktop development with C++» را تیک بزن. (خودِ Visual Studioی کامل لازم نیست، فقط Build Tools.)

**چرا این راهِ حل درست است:** Rust کامپایل را انجام می‌دهد، لینک کردن را نه. روی لینوکس همین نقش را `cc` بازی می‌کند و معمولاً از قبل هست؛ روی ویندوز باید جداگانه بیاوری‌اش. این آزاردهنده‌ترین قدمِ نصب روی ویندوز است و تنها باری است که با آن روبه‌رو می‌شوی.

### `error: no override and no default toolchain set`

`rustup` نصب است ولی هیچ زنجیره‌ابزاری فعال نیست.

**راهِ حل:** `rustup default stable`

**چرا:** معمولاً وقتی پیش می‌آید که نصب نیمه‌کاره مانده یا دستی دستکاری شده. یک دستور حلش می‌کند.

### بساز

`rustup show` را اجرا کن و خروجی‌اش را بخوان. برای خودت بنویس:

۱. چند زنجیره‌ابزار نصب داری؟
۲. کدام الان فعال است، و **چرا** آن یکی؟
۳. `default host` که نشان می‌دهد چیست؟ (این «هدف (target)» توست — معماریِ CPU و سیستم‌عاملی که برایش کامپایل می‌شود. فاز ۴ که برای لینوکس بیلد می‌گیری، دوباره می‌بینی‌اش.)

### چالش (اختیاری)

`rustup component list` را بزن. فهرستِ بلندی می‌بینی از تکه‌های اختیاری که می‌شود به یک زنجیره‌ابزار اضافه کرد.

پیدا کن `clippy` و `rustfmt` و `rust-src` کجای این فهرست‌اند و آیا نصب‌اند. دو تای اول را در درسِ ۰۶ استفاده می‌کنی؛ سومی همان چیزی است که rust-analyzer را قادر می‌کند وقتی روی یک تابعِ کتابخانه‌ی استاندارد کلیک می‌کنی، منبعش را نشانت بدهد.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| `rustup` | مدیرِ زنجیره‌ابزار | عوض کردن یا به‌روزرسانیِ نسخه |
| `rustc` | خودِ کامپایلر | تقریباً همیشه غیرمستقیم، از راهِ `cargo` |
| `cargo` | ابزارِ ساخت و مدیرِ بسته | هر روز |
| زنجیره‌ابزار (toolchain) | `rustc` + `cargo` + اجزا، با نسخه‌ی مشترک | `rustup show` |
| کانال (stable/beta/nightly) | سرعتِ انتشار | خواندنِ نیازمندی‌های یک پروژه |
| `rust-toolchain.toml` | پین کردنِ نسخه برای یک مخزن | همین مخزن؛ هر پروژه‌ی تیمی |
| ویرایش (edition) | تغییراتِ ناسازگارِ اختیاری، هر چند سال | هر `Cargo.toml` |
| لینکر (linker) | چیزی که کدِ ماشین را به یک اجرایی تبدیل می‌کند | خطای نصبِ ویندوز |

### الان می‌دانی

- `rustup` مدیر است، `rustc` کامپایلر، `cargo` چیزی که واقعاً صدا می‌زنی.
- stable چیزی است که استفاده می‌کنی؛ nightly را در این دوره لازم نداری.
- `rust-toolchain.toml` باعث می‌شود نسخه‌ی همه در این مخزن یکی باشد.
- ویرایش‌ها پایتون ۲ به ۳ نیستند؛ کدِ قدیمی تا ابد کامپایل می‌شود.
- `rustup doc` کلِ مستندات را آفلاین دارد.

### بعداً کامل‌تر می‌بینی

- **`cargo` به‌طورِ جدی** — ساختِ پروژه، وابستگی‌ها، تست: [۰۳ — مبانی Cargo](../04-cargo-basics/README.fa.md)
- **`clippy` و `rustfmt`، همان اجزایی که اینجا فهرستشان را دیدی** — [۰۶ — ابزارها](../06-tooling-clippy-fmt-rust-analyzer/README.fa.md)
- **هدف‌ها (targets) و کامپایلِ متقاطع برای لینوکس** — [فاز ۴ — استقرار و عملیات](../../phase4-backend-advanced/07-deployment-and-operations/README.fa.md)

### می‌توانی توضیح بدهی؟

- `rustup` و `cargo` چه فرقی دارند؟
- سه کانالِ Rust کدام‌اند، و کدام را استفاده می‌کنی؟
- `rust-toolchain.toml` چه‌کار می‌کند و چرا برای کارِ تیمی مهم است؟
- چرا ویرایش‌های Rust مثلِ پایتون ۲ به ۳ نیستند؟
- روی ویندوز `link.exe` را چه چیزی می‌آورد و چرا Rust خودش نمی‌آوردش؟
