# ۰۷ — گیت و گردشِ کارِ مخزن

## در یک نگاه

بعد از این درس می‌توانی:

- بعد از سه هفته غیبت، در کمتر از یک دقیقه بفهمی کجای دوره بودی.
- برای هر درسِ تمام‌شده یک کامیتِ تمیز بزنی که ماه‌ها بعد هم معنا داشته باشد.
- بگویی CI روی هر push چه چیزی را بررسی می‌کند و چرا بعضی کدها سخت‌گیرانه لینت می‌شوند و بعضی نه.

**زمان:** حدود ۲۵ دقیقه · **پیش‌نیاز:** [۰۶ — ابزارها](../06-tooling-clippy-fmt-rust-analyzer/README.fa.md)

## چرا اهمیت دارد

این درس Rust ندارد. درباره‌ی چیزی است که تعیین می‌کند این دوره را تمام می‌کنی یا نه.

مسیرِ یادگیریِ چندماهه با نفهمیدنِ مطلب شکست نمی‌خورد. با **گم شدن** شکست می‌خورد. دو هفته کار می‌کنی، بعد یک هفته گرفتار می‌شوی، بعد برمی‌گردی و ده دقیقه می‌گردی که کجا بودی، و آن ده دقیقه آن‌قدر بی‌رمق‌ات می‌کند که فردا اصلاً باز نکنی.

پس این درس یک ساختارِ کوچک می‌سازد که آن ده دقیقه را به بیست ثانیه تبدیل کند.

و یک چیزِ دوم هم هست: تو داری این را روی استریم انجام می‌دهی و مخزن عمومی است. تاریخچه‌ی گیتِ تو بخشی از همان چیزی است که مردم می‌بینند. یک `git log` که هر خطش معنا دارد، خودش یک رزومه است.

---

## مفهوم

### چهار چیزی که می‌گویند کجایی

| کجا | چه می‌گوید |
|---|---|
| `PROGRESS.fa.md` | چک‌لیستِ اصلی، یک تیک برای هر درس، گروه‌بندی‌شده بر اساسِ فاز |
| `.course-progress.json` | همان چیز، برای رابطِ وب — و بیشتر: زمان، اعتماد، یادداشت |
| صفحه‌ی `/fa/progress` در رابطِ وب | همه‌ی این‌ها به شکلِ نمودار، به‌همراهِ جدولِ تسلط بر مفاهیم |
| `git log` | چه چیزی را واقعاً تمام کرده‌ای و کِی |

اولی دستی است، دومی و سومی خودکار، چهارمی غیرقابلِ جعل.

آن چهارمی مهم‌ترین است. یک تیک را می‌شود از سرِ خوش‌بینی زد. یک کامیت یعنی کدی نوشته شده و تست‌هایش سبز شده‌اند.

### قراردادِ کامیت

**یک کامیت برای هر درسِ تمام‌شده**، با پیامی که به اسمِ پکیجِ همان درس محدود شده:

```
feat(p1-02-01-move-semantics): complete exercise
```

و تیکِ همان درس را در `PROGRESS.fa.md` **در همان کامیت** بزن:

```sh
git add phase1-fundamentals/02-ownership-and-memory/01-move-semantics PROGRESS.fa.md
git commit -m "feat(p1-02-01-move-semantics): complete exercise"
```

چرا در یک کامیت؟ چون آن‌وقت چک‌لیست و تاریخچه هیچ‌وقت از هم جدا نمی‌شوند. اگر شش ماه بعد شک کردی «واقعاً این را تمام کردم؟»:

```sh
git log --grep=move-semantics --oneline
```

جوابِ قطعی می‌دهد.

قالبِ `feat(scope): description` قراردادی است به اسمِ **Conventional Commits** و در پروژه‌های واقعی همه‌جا هست. پیشوندهای رایج:

| پیشوند | برای |
|---|---|
| `feat` | یک درسِ تمام‌شده، یک قابلیتِ جدید |
| `fix` | تعمیرِ چیزی که خراب بود |
| `docs` | فقط تغییرِ مستندات |
| `refactor` | تغییرِ کد بدونِ تغییرِ رفتار |
| `chore` | کارهای نگهداری، به‌روزرسانیِ وابستگی |

الان عادتش را بگذار. در فاز ۴ که درباره‌ی CI/CD حرف می‌زنیم، می‌بینی که ابزارها از همین پیشوندها برای تولیدِ خودکارِ تغییرات‌نامه و تعیینِ نسخه استفاده می‌کنند.

### پیامِ کامیتی که ارزشِ نوشتن دارد

خطِ اول یعنی *چه چیزی*. اگر تصمیمی گرفته‌ای، بدنه‌ی پیام یعنی *چرا*:

```
feat(p1-04-02-slices): complete exercise

The obvious `&s[0..n]` panics on Persian text — n lands mid-character.
Used `char_indices` to find a real boundary instead. Worth remembering
for anything that touches user-supplied text.
```

آن پاراگرافِ دوم برای «آینده‌ی خودت» است. شش ماه بعد کد را می‌بینی و یادت نمی‌آید چرا این‌طور نوشتی؛ کامیت یادت می‌آورد.

قاعده‌ی ساده: **اگر موقعِ نوشتنش چیزی یاد گرفتی، بنویسش.**

### برچسب‌گذاریِ پایانِ فاز

نقاطِ عطفِ کوچک، مجانی، و انگیزه‌بخش:

```sh
git tag -a phase1-complete -m "Finished Phase 1: Language foundations"
```

ماه‌ها بعد، این یک خطِ زمانیِ کاملِ سفرت می‌سازد:

```sh
git log --oneline --decorate --tags
```

اگر روی استریم کار می‌کنی، همین برای مخاطبت هم لحظه‌ی خوبی است.

### CI روی هر push چه‌کار می‌کند

فایلِ `.github/workflows/ci.yml` این‌ها را اجرا می‌کند:

```sh
cargo fmt --all -- --check          # همه‌چیز باید فرمت‌شده باشد
cargo clippy ... -- -D warnings     # فقط روی کدِ تمام‌شده
cargo test --workspace --no-run     # همه‌چیز باید کامپایل شود
cargo test ...                      # فقط کدِ تمام‌شده باید سبز باشد
cargo run -q -p lesson-lint         # استانداردِ درس‌ها
```

آن تفکیکِ «فقط کدِ تمام‌شده» عمدی است و ارزشِ فهمیدن دارد:

- **فرمت** روی *همه‌چیز* اعمال می‌شود. یک اسکلتِ ناتمام هم باید فرمت‌شده باشد.
- **کامپایل شدن** روی همه‌چیز اعمال می‌شود. یک اسکلت باید کامپایل شود؛ `todo!()` این را نمی‌شکند.
- **clippy سخت‌گیرانه و تست‌های سبز** فقط روی کدی که *قرار است* تمام باشد. اسکلتِ درس عمداً ناتمام است: بدنه‌های `todo!()` پارامترها را استفاده‌نشده می‌گذارند و تست‌ها پنیک می‌کنند. آن‌ها راهنماییِ درس‌اند، نه خرابی.

اگر این تفکیک نبود، CI روی یک کلونِ دست‌نخورده برای همیشه قرمز می‌ماند — و CIِ همیشه‌قرمز، CIِ نادیده‌گرفته‌شده است.

### `lesson-lint` و آن فهرستِ در حالِ کوچک شدن

آخرین قدمِ CI یک ابزارِ مخصوصِ همین مخزن است:

```sh
cargo run -q -p lesson-lint
```

بررسی می‌کند هر درس از [`docs/lesson-standard.fa.md`](../../docs/lesson-standard.fa.md) پیروی کند: بخش‌های اجباری، تطابقِ فارسی و انگلیسی، رزولوِ شدنِ لینک‌ها، و مهم‌تر از همه اینکه **هیچ درسی مفهومی را پیش از تدریسش استفاده نکند**.

درس‌هایی که هنوز بازسازی نشده‌اند در `docs/lesson-lint-allow.txt` فهرست شده‌اند. یافته‌هایشان شمرده می‌شود ولی CI را نمی‌شکند. آن فایل **فقط کوچک می‌شود**؛ وقتی خالی شد، بازسازی تمام است.

می‌توانی خودت هر وقت خواستی اجرایش کنی:

```sh
cargo run -q -p lesson-lint                       # کلِ دوره
cargo run -q -p lesson-lint -- phase1-fundamentals # فقط یک فاز
```

### کارِ انفرادی در برابر تمرینِ گردشِ کارِ PR

تو تنها مشارکت‌کننده‌ای، پس هیچ الزامی به شاخه و pull request نیست. مستقیم روی `main` کامیت کن اگر می‌خواهی.

ولی «آماده شدن برای بازارِ کار» یکی از هدف‌های صریحِ این سفر است، و کارِ واقعیِ تیمی هیچ‌وقت این‌طور نیست. پیشنهاد: **برای هر فاز یک PR باز کن.** یک شاخه بساز، فاز را کار کن، PR بزن، دیفِ خودت را مثلِ یک غریبه بخوان، بعد merge کن.

هزینه‌اش نزدیکِ صفر است و همان مهارتی را می‌سازد که هر تیمی روزِ اول ازت انتظار دارد: خواندنِ دیفِ خودت پیش از اینکه کسی دیگر بخواندش.

</details>

### بساز

یک روالِ «شروعِ جلسه» برای خودت بساز و امتحانش کن. یک بار بنویسش، بعد هر بار که برمی‌گردی همان را اجرا کن:

```sh
git log --oneline -5                    # آخرین کاری که کردم چه بود؟
cargo run -p course-ui                  # صفحه‌ی پیشرفت را باز کن
```

هدف این است که «کجا بودم؟» به یک تصمیم نیاز نداشته باشد. تصمیم گرفتن انرژی می‌برد؛ عادت نمی‌برد.

بعد یکی از درس‌های همین فاز ۰ را با قراردادِ کامل کامیت کن — پیامِ scope-دار، تیکِ `PROGRESS.fa.md` در همان کامیت — و `git show` بزن تا ببینی چه شکلی است.

### چالش (اختیاری)

پایانِ فاز ۰ را برچسب بزن:

```sh
git tag -a phase0-complete -m "Finished Phase 0: Setup and orientation"
git log --oneline --decorate --tags -10
```

بعد یک شاخه برای فاز ۱ باز کن و همان‌جا کار کن:

```sh
git switch -c phase1
```

وقتی فاز ۱ تمام شد، یک PR باز کن و **دیفِ خودت را کامل بخوان** پیش از اینکه merge کنی. احتمالاً چیزی پیدا می‌کنی که دوست داری عوض کنی. همین است کلِ نکته.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| Conventional Commits | قالبِ `feat(scope): description` | هر کامیت، اینجا و در کارِ واقعی |
| scope | اسمِ پکیجِ درس داخلِ پرانتز | `git log --grep` را مفید می‌کند |
| برچسب (tag) | یک اشاره‌گرِ نام‌دار به یک کامیت | پایانِ هر فاز |
| CI | بررسی‌های خودکار روی هر push | `.github/workflows/ci.yml` |
| `-D warnings` | هر هشدار را خطا حساب کن | فقط روی کدِ تمام‌شده |
| `lesson-lint` | مجریِ استانداردِ درس‌ها | آخرین قدمِ CI |
| فهرستِ مجاز | درس‌هایی که هنوز بازسازی نشده‌اند | فقط کوچک می‌شود |

### الان می‌دانی

- چهار جا می‌گویند کجایی، و `git log` تنها جایی است که نمی‌شود سرِ خودت کلاه بگذاری.
- یک کامیت برای هر درس، با تیکِ `PROGRESS.fa.md` در همان کامیت.
- قالبِ `feat(scope): description` و اینکه چرا اهمیت دارد.
- CI فرمت و کامپایل را روی همه‌چیز بررسی می‌کند، ولی clippy و تست‌ها را فقط روی کدِ تمام‌شده.
- `lesson-lint` نمی‌گذارد درسی مفهومی را پیش از تدریسش استفاده کند.
- کارِ روی شاخه اختیاری است، و تمرینِ خوبی است.
