# راه‌حل

```rust
impl Queue for InMemoryQueue {
    async fn enqueue(&self, payload: String) -> Result<i64, QueueError> {
        let mut state = self.state.lock().unwrap();
        let id = state.next_id;
        state.next_id += 1;
        state.pending.push_back(Job { id, payload });
        Ok(id)
    }

    async fn claim_next(&self) -> Result<Option<Job>, QueueError> {
        let mut state = self.state.lock().unwrap();
        let Some(job) = state.pending.pop_front() else {
            return Ok(None);
        };
        state.in_progress.insert(job.id, job.clone());
        Ok(Some(job))
    }

    async fn complete(&self, id: i64) -> Result<(), QueueError> {
        let mut state = self.state.lock().unwrap();
        if state.in_progress.remove(&id).is_some() {
            state.completed.push(id);
            Ok(())
        } else {
            Err(QueueError::NotClaimed(id))
        }
    }
}
```

هر کدوم از این متدها کلِ منطقِ درونیشون رو با همون قفلِ `Mutex<InMemoryQueueState>` محافظت می‌کنن — کلاً کلِ ضمانتِ "هرگز دوبار برداشته نمی‌شه" واسه `InMemoryQueue` تو همون یه دونه قفل خلاصه می‌شه: متدِ `claim_next` عملیات بیرون کشیدن از `pending` و قرار دادنش تو `in_progress` رو کاملاً به صورت یه عملیاتِ اتمی و یکپارچه انجام می‌ده (حداقل از دید بقیه‌یِ فراخواننده‌های سیستم که اینطوریه)، در نتیجه هیچ‌جوره امکان نداره که دو تا تسکِ همروند بتونن همزمان یه کارِ یکسان رو از ابتدایِ این صف بردارن و پاپ (pop) کنن. تو متد `complete` هم، کار حتماً اول باید داخل متغیرِ `in_progress` حضور داشته باشه — در واقع سعی برای تکمیلِ کاری که اصلاً هیچ‌وقت برداشته (claim) نشده (یا اینکه قبلاً تکمیل شده و تموم شده)، یه اشتباه و باگ از سمتِ فراخواننده‌ست، که به شکلِ خطایِ `QueueError::NotClaimed` بهش گوشزد می‌شه و به هیچ وجه بی‌سروصدا نادیده گرفته نمی‌شه.

## چرا `PostgresQueue` اصلاً به هیچ قفلِ `Mutex` نیازی نداشت؟

نسخه‌ی در-حافظه (in-memory) کلِ ایمنی و امنیتِ خودش رو منحصراً از وجودِ یه `std::sync::Mutex` متعلق به یه پروسه وام گرفته بود. اما `PostgresQueue::claim_next` دقیقاً همون گارانتیِ معادل رو مستقیماً از دلِ خودِ دیتابیس دریافت می‌کنه:

```sql
WITH claimed AS (
    SELECT id FROM toy_jobs
    WHERE status = 'pending'
    ORDER BY id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE toy_jobs SET status = 'running'
WHERE id IN (SELECT id FROM claimed)
RETURNING id, payload
```

عبارتِ `FOR UPDATE SKIP LOCKED` اون یه ردیفی رو که انتخاب می‌کنه قفل می‌زنه (تا هیچ تراکنشِ دیگه‌ای نتونه دوباره اونو انتخاب کنه) و تو بخشِ حساسِ ماجرا، از روی هر ردیفی که *از قبل* توسطِ یه تراکنشِ همروند (concurrent transaction) قفل شده می‌پره، به جای اینکه بخواد پشتش منتظر بمونه و بلوک (blocking) بشه — اینطوری اگه دو تا کارگر تو یه لحظه‌یِ دقیقاً یکسان تابعِ `claim_next` رو صدا بزنن، هرکدومشون یه ردیفِ کاملاً متفاوت می‌گیره، اونم با هماهنگیِ کاملاً صفر بین خودشون، جز اینکه فقط هردوشون دارن با یه Postgresِ یکسان حرف می‌زنن. این دقیقاً همون قابلیتیه که اجازه می‌ده سیستم بتونه تو سطحِ **پروسه‌هایِ مجزا و جداگانه** هم کارایی داشته باشه و مقیاس‌پذیر بمونه (یعنی برنامه‌های کارگرِ کاملاً مستقل که ممکنه رو سرورها و ماشین‌های کاملاً متفاوتی اجرا بشن)، که دقیقاً همون چیزیه که یه صفِ تولیدی (production job queue) به شدت بهش نیاز داره و از طرفی قفلِ `Mutex` — که فقط تو شعاعِ مموریِ همون یه پروسه کارایی داره — از نظر ساختاری و فیزیکی از فراهم کردنش عاجزه. این کوئری رو با کوئری `claim_next` تو فایل `taskforge-storage/src/postgres.rs` مقایسه کن: دقیقاً همون الگو، همون ترکیبِ `FOR UPDATE SKIP LOCKED` با ساختار CTE-وبعد-`UPDATE`، با این تفاوت که چون اونجا واقعاً قراره یه صفِ واقعی باشه (و نه فقط یه اسباب‌بازی با سه تا وضعیتِ ساده)، ستون‌هایِ خیلی بیشتری بهش اضافه شدن (مثل مقادیر enum برای وضعیت‌ها، و فیلدهای مربوط به حسابداریِ تلاشِ مجدد).

تو متد `complete`، عبارتِ `'WHERE id = $1 AND status = 'running` به اضافه‌یِ اون بررسیِ `0 == ()rows_affected`، دقیقاً معادل و نسخه‌یِ سمت-Postgresِ همون قراردادِ "این کار حتماً باید اولِ کار claim شده باشه" هستش که تو `InMemoryQueue` با حضور داشتن تو متغیر `in_progress` تضمین می‌شد — هر دویِ این پیاده‌سازی‌ها از تکمیلِ کاری که تو اون لحظه تو وضعیتِ claimشده نیست جلوگیری می‌کنن، که باعث می‌شه این دو تا پیاده‌سازی از `Queue`، از نگاه یه فراخواننده‌یِ بیرونی از لحاظِ رفتاری (behaviorally) کاملاً با هم یکسان و برابر باشن، دقیقاً همون هدفی که مرزِ خصیصه‌ی `JobStore` تو پروژه‌یِ نهایی کپستون (بخونید `docs/adr/0001`) طوری طراحی شده بود تا بتونه اونو گارانتی و ضمانت کنه.

## چرا هر دو تا تستی که برچسب `#[ignore]` داشتن، حتماً به صفتِ `#[serial(p4_03_01_toy_queue_db)]` هم نیاز دارن؟

دستور `cargo test` کلاً عادت داره توابع `#[test]` مختلف رو به طور پیش‌فرض به شکل همزمان و موازی (concurrently) اجرا کنه، و تو این درس، هر دو تست مربوط به Postgres از یک جدول مشترک یعنی `toy_jobs` استفاده می‌کنن — تو یکی از این تست‌ها ۲۰ تا کار تو صف گذاشته (enqueues) می‌شه و بعدش به طور همزمان توسط ۵ تا تسک، اون کارا از صف برداشته می‌شن؛ حالا اگه اون یکی تست، دقیقاً همون وسط کار بیاد و دستور `DELETE FROM toy_jobs` رو واسه ریست کردنِ جدولش اجرا کنه (land mid-flight)، ردیف‌هایی که هر کدوم از تست‌ها انتظارِ دیدن و کار کردن باهاشون رو داشتن کلاً تو هوا دود می‌شه و از بین می‌ره (vanish out from under it). این یه فرضیه یا خیال‌پردازی نیست: این دقیقاً یه شرط مسابقه‌ایه (race) که وقتی این مخزنِ کُد داشت آزمایش می‌شد خودش رو نشون داد، اونم فقط تو حالت پیش‌فرضِ اجرای موازیِ تست‌ها، و هیچ‌وقت با اجرای دستوری مثل `1=test-threads--` اتفاق نمی‌افتاد. صفتِ `#[serial]` فقط زمانی می‌تونه از تداخل جلوگیری کنه که *هر دوی* این تست‌ها (نه فقط یکی‌شون) تگ و برچسبِ کاملاً یکسانِ *همانند* رو رو خودشون داشته باشن — اگه تستی اون تگ رو نداشته باشه، کلاً از دید سیستم مخفی و نامرئی می‌مونه و خیلی راحت به شکل همزمان با اون تستی که تگ داره ران می‌شه، در نتیجه فقط یه دونه تستِ بدونِ محافظت هم کافیه تا تغییرات (mutation) رو اون جدول مشترک همچنان با مشکلِ مسابقه (racy) روبرو بشه.
