# ۰۴.۴.۲ — مروری بر کریت `async-graphql`

درس قبلی: gRPC — به شدت نوع-بندی‌شده، با رویکرد شِما-اول (schema-first)، و مختصِ ارتباط‌های سرویس-به-سرویس. این درس: GraphQL — اینم رویکردش شِما-اولی (schema-first) هستش، اما جامعه‌ی هدفش دقیقاً نقطه‌ی مقابلِ قبلی و تو لبه‌ی سیستم قرار داره: یعنی APIهایِ کلاینت‌محور (client-facing APIs)، جایی که کلاینت‌های مختلف (اپلیکیشن وب، اپلیکیشن موبایل، یا یهپارچه‌سازی‌های شخص ثالث) هر کدومشون فقط یه بُرش و تیکه‌ی خاص از یه دیتای یکسان رو می‌خوان.

## ایده‌ی اصلی: این کلاینت هست که شکلِ خروجی رو تعیین می‌کنه

یه درخواستِ REST مثل `GET /notes/1`، صرف نظر از اینکه کلاینت به همه‌ی فیلدهاش نیاز داره یا نه، دقیقاً همون فیلدهایی رو برمی‌گردونه که سرور تصمیم گرفته — هر کسی که صداش بزنه، دقیقاً همون ساختار و شکلِ ثابت رو می‌گیره. اما یه کوئریِ GraphQL دقیقاً و منحصراً همون فیلدهایی رو درخواست می‌کنه که واقعاً بهشون نیاز داره:

```graphql
query { note(id: "1") { title } }
```

این درخواست دقیقاً خروجیِ `{"note": {"title": "..."}}` رو برمی‌گردونه — نه خبری از `id` هست، نه خبری از `body`، چون کلاینت اصلاً اونا رو نخواسته بوده. با همون سرور و دقیقاً روی همون داده‌های زیربنایی، فراخواننده‌های مختلف (callers) می‌تونن ساختارهای کاملاً متفاوتی رو درخواست کنن، بدون اینکه تیم بک‌اند مجبور باشه به ازای هر تغییری تو ظاهرِ UI، بیاد یه نقطه‌پایانی (endpoint) جدید بسازه یا نسخه‌ی API رو عوض کنه. تستِ `notes_query_returns_every_field_a_client_asked_for` تو این درس دقیقاً همین مفهوم رو به صورت عملی نشون می‌ده: کوئریِ `{ notes { title } }` رو می‌فرسته و چک می‌کنه (assert) که اشیایِ تو خروجی مطلقاً هیچ کلیدی به اسم `id` تو خودشون نداشته باشن.

## خوندنِ شِما (schema): تفاوت `Object` با `SimpleObject`

```rust
#[derive(Clone, SimpleObject)]
pub struct Note {
    pub id: ID,
    pub title: String,
    pub body: String,
}
```

نوعِ `Note` اینجا "فقط داده" (just data) محسوب می‌شه — تک‌تکِ فیلدهاش فقط با خوندن مستقیم از روی خودِ ساختار برطرف و پاسخ داده می‌شن (resolved)، در نتیجه صفتِ `#[derive(SimpleObject)]` میاد رزولورِ (resolver) مربوط به هر سه تا فیلد رو کاملاً خودکار برات تولید می‌کنه؛ که تو دنیای GraphQL دقیقاً معادل و همتایِ صفتِ `#[derive(Serialize)]` محسوب می‌شه.

```rust
pub struct QueryRoot;

#[Object]
impl QueryRoot {
    async fn note(&self, ctx: &Context<'_>, id: ID) -> Option<Note> { ... }
    async fn notes(&self, ctx: &Context<'_>) -> Vec<Note> { ... }
}
```

نوع‌هایِ `QueryRoot` و `MutationRoot` داستانشون فرق داره: تک‌تکِ متدهاشون به جای اینکه صرفاً یه فیلد رو بخونن و نشون بدن، باید واقعاً یه *کاری* انجام بدن (یعنی دیتای مشترکِ سیستم رو بخونن)، بنابراین تک‌تک‌شون به طور دستی و داخل یه بلوکِ اجرایی با صفتِ `#[Object]` نوشته می‌شن — یه دونه متد به ازای هر کوئری/جهشی (query/mutation) که شِما تو خروجیِ خودش ارائه می‌ده. خروجیِ تابعِ `note` از نوعِ `<Option<Note>` هست و دقیقاً همینه که باعث می‌شه این فیلد تو شِمای ما به صورتِ "مقدارِ پذیرنده‌یِ null" یا همون nullable دربیاد؛ یعنی پیدا نشدنِ یه نُت (note) تو خروجی مقدارِ `null` می‌گیره، و اصلاً ارور یا خطا به حساب نمیاد (این رو با درس قبلی مقایسه کن که توش صراحتاً خطایِ `Status::not_found` برگردونده می‌شد — اینجا هر دو پروتکلِ GraphQL و gRPC پیش‌فرض‌هایِ متفاوتی رو انتخاب کردن، که هر کدومشونم برای مورداستفاده‌یِ خودشون کاملاً منطقی و درستن).

## دیتایِ به اشتراک گذاشته‌شده (Shared state): متدِ `<ctx.data_unchecked::<T`

```rust
pub fn build_schema() -> NotesSchema {
    Schema::build(QueryRoot, MutationRoot, EmptySubscription)
        .data(Mutex::new(NotesState::default()))
        .finish()
}
```

متدِ `.data(...)`، میاد دیتای مشترکِ سیستم رو (که مستقل از درخواست‌هاست) به شِما متصل می‌کنه — از لحاظ مفهومی، دقیقاً همون نقشی رو بازی می‌کنه که `axum::extract::State` تو فاز ۳ داشت، یا متغیر `<<Arc<AppState`ای که تو درسِ `tonic` پاس می‌دادی. تک‌تکِ رزولورها با استفاده از دستورِ `!()ctx.data_unchecked::<Mutex<NotesState>>` می‌تونن دوباره اون دیتا رو بکشن بیرون. پسوندِ `unchecked_` تو این متد به این معنیه که اگه تو نوعی رو فراخوانی کنی که قبلاً هیچ‌وقت توسط متدِ `.data(...)` ثبت نشده بوده، این دستور کلاً پنیک (panics) می‌کنه (به جای اینکه بخواد `<Result>` برگردونه) — که البته تو این تمرین کاملاً قابل قبوله، چون تابع `()build_schema` همیشه این نوع رو ثبت می‌کنه، در نتیجه خطایِ پنیک ناشی از پیدا نشدن دیتا تو این برنامه، فقط و فقط به معنیِ یه باگ و اشتباه از طرف برنامه‌نویسه، نه یه ورودیِ خراب از سمت کاربر. (نوعِ امن‌ترِ این تابع یعنی `()ctx.data::<T>`، واسه جاهایی که نمی‌تونی همچین ضمانت سفت و سختی بدی وجود داره و استفاده می‌شه).

## نوعِ `EmptySubscription`

`Schema<QueryRoot, MutationRoot, EmptySubscription>` — پروتکلِ GraphQL غیر از Query و Mutation، یه ریشه‌یِ سوم هم داره: **اشتراک یا Subscription**، واسه کلاینت‌هایی که می‌خوان از طریق یه اتصال پایدار (persistent connection) مثل وب‌سوکت، یه جریان زنده (live stream) از آپدیت‌ها رو دریافت کنن (مثلاً "هر وقت یه نُتِ جدید ساخته شد به منم خبر بده"). از اونجایی که ما تو این درس اصلاً نیازی بهش نداریم، نوعِ `EmptySubscription` یه نوع واقعی و ازپیش‌ساخته‌ست که می‌ذاریمش اونجا تا جایِ خالی رو پُر کنه، بدون اینکه بخواد چیزی رو پیاده‌سازی کنه — در نتیجه شِمایِ ما کلاً هیچ فیلدی واسه subscription نداره. پشتیبانی کردنِ واقعی از این ویژگی، نیازمندِ یه بلوک با صفتِ `#[Subscription]` هستش که باید تو خروجیش نوعِ `Stream` برگردونه، که از چهارچوبِ این درس کلاً خارجه.

## تست کردنِ دوباره‌ی کدها، اونم بدون حضور سرور

دقیقاً هم‌شکل با درسِ `tonic`، اینجا هم تمامِ تست‌ها مستقیماً میان متدِ `(...)schema.execute` رو با استفاده از یه رشته‌ی متنیِ کوئریِ (query string) مربوط به GraphQL صدا می‌زنن — نه خبری از روترِ `axum` هست، نه کتابخونه‌یِ رابطِ `async-graphql-axum`، و نه کلاً هیچ‌گونه درخواستِ HTTPای. متدِ `Schema::execute` خیلی ساده فقط یه متدِ غیرهمگام (async) معمولیه؛ وصل کردنِ این شِما به پشتِ یه نقطه‌پایانیِ HTTP (مثل نقطه‌پایانیِ `POST /graphql` که کوئری رو تو دلِ یه بدنه‌ی JSON تحویل می‌گیره، که معمولاً با استفاده از اکسترکتورِ (extractor) `GraphQL` تو کریتِ `async-graphql-axum` انجام می‌شه) کلاً یه کارِ کاملاً مجزا و مکانیکی هستش که تو یه سرویس واقعی به سیستم اضافه می‌کنی، و می‌ذاریش روی شِمایی که به تنهایی و واسه خودش به طور کامل قابل تسته — دقیقاً همون رویکرد و انضباطِ "منطق رو تست کن، به شبکه‌ی انتقال (transport) اعتماد کن" که تو تک‌تکِ درس‌های این ماژول پیاده شده بود.
