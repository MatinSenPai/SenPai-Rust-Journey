# راه‌حل

```rust
pub fn parse_env_file(contents: &str) -> HashMap<String, String> {
    let mut vars = HashMap::new();
    for line in contents.lines() {
        let line = line.trim();
        if line.is_empty() || line.starts_with('#') {
            continue;
        }
        let Some((key, value)) = line.split_once('=') else {
            continue; // اگه ساختار مشکل داشت: کلاً هیچ علامت '=' تو خط پیدا نشد
        };
        let key = key.trim();
        if key.is_empty() {
            continue; // اگه ساختار مشکل داشت: خط با `value=` شروع می‌شد و اسمی واسه متغیر وجود نداشت
        }
        vars.insert(key.to_string(), value.trim().to_string());
    }
    vars
}
```

اینم از همون ۲۰ خطی که قولشو داده بودیم. دو تا متد از کتابخونه‌ی استاندارد (stdlib) هستن که اینجا صفر تا صدِ کار رو گردن می‌گیرن:
متدِ `str::split_once('=')` فقط از روی **اولین** علامت `=` متنی که داره رو می‌شکونه و هر دو نیمه‌ی کُد رو بهت تحویل می‌ده — که این دقیقاً دلیل اصلیِ جواب دادن و کار کردنِ این کد با مقادیری شبیه به `postgres://...?sslmode=disable` هستش (اگه قرار بود رو آخرین `=` اسپلیت کنه، یا حتی از متدِ `.split('=')` استفاده کنه و کلاً متن رو تکه‌تکه کنه، اون مقدارِ پایانی خیلی بی‌سروصدا و بدون ارور بخشِ آخر خودش یعنی دُمِش (tail) رو از دست می‌داد). و بخشِ `let ... else` باعث می‌شه که منطقِ "اگه خراب بود → بی‌خیالش شو" کلاً فقط تو یه خط و بدون اینکه بخواد تو یه بلوک `match` تو در تو (nested) گم بشه خودش رو نشون بده. توجه کن که ما از اون قضیه‌ی "خط‌های مشکل‌دار و نامعتبر رو کلاً بی‌صدا بی‌خیالشون شو" دقیقاً چه چیزی رو به دست آوردیم: پارسری (parser) که فقط به خاطر پیدا کردن یه خط سرگردان تو یه فایل `.env` کل برنامه رو پنیک (panics) می‌کنه، دقیقاً همون پارسریه که یه روز یه نفر وسط یه بحران تو پروداکشن با نهایت عجله کلاً کداشو از پروژه پاک می‌کنه.

کلاً یه خطه، اما به شدت بارِ سنگینی (load-bearing) رو دوشش داره: استفاده از صفتِ `#[derive(Debug)]` رو تک‌تکِ ساختارها (structs) تو زبان Rust *عملیات رو همیشه واگذار می‌کنه و به پیاده‌سازی `Debug`ِ مختصِ همون فیلد محول می‌کنه (delegates)*. در نتیجه ساختارِ `Config` می‌تونه با خیالِ راحتِ راحت `Debug` رو روش derive کنه — وقتی این روندِ اتوماتیک می‌رسه به پردازشِ فیلدِ `database_url`، میاد و *همین* پیاده‌سازی‌ای که بالا نوشتی رو برای اون فیلد صدا می‌زنه، نه پیاده‌سازی متعلق به کلاسِ `String` رو، و کلاً باعث می‌شه کُل اون آبجکت بدون هیچ خطری بتونه لاگ زده بشه. عمیق‌ترین مفهومی که تو این درس باید یادش بگیری همینه: تو کلاً فقط با پیاده‌سازی یه خصیصه (trait) تو *یک دونه جا* از کد، اومدی و رفتارِ تمامِ ساختارهایِ فعلی *و همچنین در آینده*یِ سیستم رو که تو دلشون یه `SecretString` دارن، کاملاً و با موفقیت تغییر دادی و کنترل کردی. اگه می‌خواستیم اینو تو ترمینولوژی و زبانِ جنگو (Django) ترجمه کنیم، این دقیقاً همون تفاوتِ بین "سعی کن یادت نره پسوردها رو به طور دستی از همه‌ی توابعِ `__repr__` سانسور کنی و حذفشون کنی (exclude)" و "از اساس اون ساختار (type) رو جوری بنویس که کلاً خودش ذاتاً از نمایش دادن و پرینت کردنِ خودش امتناع کنه" هستش. (کریتِ `secrecy` دقیقاً همین کارو می‌کنه — و البته تو سطح پروداکشن خیلی فراتر از این حرفا می‌ره و حتی موقع drop شدن، متغیر رو تو مموری پر از صفر می‌کنه و کارهای دیگه (zeroize-on-drop)).

دلیل استفاده از تابعِ `.expose()` به جایِ اینکه از `Deref`/`AsRef<str>` کمک بگیریم: تو این سیستم، این درهم‌تنیدگی و اصطکاکِ اضافه کلاً با هدف ساخته شده و یه ویژگیِ اصلیه (the friction is the feature). هر بار که یه برنامه‌نویس می‌خواد محتوایِ یه داده‌یِ حساس رو از تو این پوشش بخونه، مجبوره که تو کُدش یه فراخوانیِ کاملاً صریح (explicit)، تو چشم، و قابل جستجو (searchable) از خودش جا بذاره.

```rust
fn required(merged: &mut HashMap<String, String>, key: &str) -> Result<String, ConfigError> {
    merged
        .remove(key)
        .ok_or_else(|| ConfigError::Missing(key.to_string()))
}

pub fn resolve(
    defaults: HashMap<String, String>,
    file_vars: HashMap<String, String>,
    env_vars: HashMap<String, String>,
) -> Result<Config, ConfigError> {
    let mut merged = defaults;
    merged.extend(file_vars);
    merged.extend(env_vars);

    Ok(Config {
        database_url: SecretString::new(required(&mut merged, "DATABASE_URL")?),
        bind_addr: required(&mut merged, "BIND_ADDR")?,
        log_level: required(&mut merged, "LOG_LEVEL")?,
    })
}
```

کُلِّ این سیاستِ اولویت‌بندی (precedence policy) فقط و فقط از دو تا فراخوانیِ ساده‌ی متدِ `extend` به دست اومده: متدِ `HashMap::extend` تو ذاتِ خودش همیشه مقادیرِ کلیدهایی رو که از قبل موجود باشن بی‌رحمانه بازنویسی می‌کنه (overwrites)، پس وقتی تو میای اول مقادیر پیش‌فرض رو (defaults) با فایل‌های کانفیگ (`.env`) extend می‌کنی، و بعد دوباره همونو با متغیرهای محیطی سیستم (`env_vars`) extend می‌کنی، خودبه‌خود همون سیاستِ "پیش‌فرض < فایل < سیستم" بدونِ اینکه نیاز باشه حتی یه دونه شرطِ `if` واسه هر کلید بنویسی اعمال می‌شه. استفاده از `remove` (به جای `get` به علاوه‌یِ متدِ `clone`) دقیقاً واسه این انجام شده که این هش‌مپِ ادغام‌شده (merged) فقط یه داربستِ یک‌بارمصرفه (scaffolding) که مال خودمون بوده و تا چند ثانیه دیگه کلاً قراره تو سیستم بمیره و drop بشه؛ و استفاده از `ok_or_else` (و نه `ok_or`) واسه اینه که اون هزینه‌یِ سنگینِ اختصاص فضایِ مموری (allocation) برای ساختِ `String` خطامون، کلاً فقط زمانی اتفاق بیفته که اون خطا واقعاً رخ داده و تو مسیر شکست (failure path) هستیم. اون علامتِ `?` تو آخرِ هرکدوم از فراخوانی‌های `required` دقیقاً همون ویژگیِ توقف و سقوط سریع (fail-fast) هستش: اولین کلیدی که تو سیستم پیدا نشه و غایب باشه، درجا کُل روندِ اجرای متد سازنده رو قطع (aborts) می‌کنه و تو ارورِ نهاییشم اسم همون کلیدِ پیدا نشده رو بالا میاره و وصل می‌کنه.

## در مورد سؤال‌های مرور

**پاسخ ۱ (اولویت محیطِ سیستم رو فایلِ `.env`):** اون لایه‌ی فایل فقط به خاطر *راحتی و آسایش برنامه‌نویس (developer's convenience)* به وجود اومده؛ محیط سیستم، در واقع زبان و حرفی هست که خودِ محیط استقرار و پروداکشن (deployment itself speaking) داره می‌زنه. اگه فایل تو سیستم اولویتِ بالاتری می‌داشت، و یه روزی اشتباهی فایل `.env` تو محیطِ لوکالِ یه نفر می‌رفت قاطیِ فایل‌های ایمیجِ کانتینرش می‌شد و همراهش منتشر می‌شد (که کلاً یه خط جا انداختنِ `.dockerignore` واسه این فاجعه کافیه)، اون فایل کلاً و تو سکوتِ کامل هر چیزی رو که ارکستراتور (orchestrator) تو پروداکشن تنظیم کرده بود نادیده می‌گرفت و روش می‌شست (silently override) — این همون سناریوی معروفیه که توش سیستم پروداکشن اشتباهی وصل می‌شه به دیتابیس رویِ لپ‌تاپ برنامه‌نویس و کل پروژه می‌ره رو هوا.

**پاسخ ۲ (تو همون ثانیه‌ی اول اِرور بده و متوقف شو):** اینکه صبر کنی و خوندن دیتارو بندازی واسه وقتی که بهش نیاز داری (lazy read)، در واقع همون نقطه‌یِ شکسته. چون به جای اینکه سیستم زمان دیپلوی کردن کِرش کنه (وقتی همه بیدارن، چشما به مانیتوره، راحت می‌شه رول‌بک کرد، و کاملاً واضحه مشکل از آخرین آپدیته)، می‌ذاری تا زمانی که واسه اولین بار به اون متغیر نیاز شد سقوط و کِرش اتفاق بیفته — یعنی احتمالاً ساعت‌ها بعد، دقیقاً تو وسط اجرای یه هندلر که درخواستِ کلاینت زیر دستشه، اونم با یه لاگ استک ترِیسی (stack trace) که داره بهت آلارم خطای اتصال به کانکشن‌پول می‌ده و کلاً ردِ گم‌کنیه. اما اعتبارسنجیِ استارت‌آپ (Startup validation)، اون فاجعه‌ی مرموز و عجیب‌غریب ساعت ۳ نصفه‌شب رو تبدیل می‌کنه به کلاً یه "دیپلویِ ناموفق" و نمیذاره اصلاً کُدی ران بشه. اون پیام ارور هم حتماً باید *اسمِ همون متغیر* رو تو دلش داشته باشه؛ پیام "missing required config variable: DATABASE_URL" خودش یه دستورالعملِ کاملاً مشخصه، اما پیام کُلیشه‌ایِ "invalid configuration" کلاً یعنی برو کل پروژه رو از زیرِ سنگ بگرد پیدا کن.

**پاسخ ۳ (چرا خصیصه‌ی ماکروی Debug کلاً امنه):** ماکروی تولیدکننده‌یِ `Debug` به ترتیب میاد و متدِ `Debug::fmt` رو رویِ تک‌تکِ فیلدهای همون ساختار یکی‌یکی صدا می‌زنه. تو فیلدِ `database_url`، چون نوعِ گیرنده (receiver type) و صاحبش، کلاسِ `SecretString` بود، پس اون کُدِ سانسورکننده‌ای که خودمون نوشته بودیم دقیقاً واسه این فیلد اجرا (runs) می‌شه. اگه قرار بود که اون فیلد یه متغیر خام با جنس `String` باشه، این بار دیگه پیاده‌سازی متعلق به `String` ران می‌شد و کلِ آدرس URL رو پرینت می‌گرفت — که یعنی پسوردت رو هم دقیقاً باهاش چاپ می‌کرد — بدون اینکه کامپایلر اصلاً بهت اخطاری بده، چرا؟ چون از نظر کامپایلر *هر دویِ این برنامه‌ها از نظرِ منطقِ کامپایل کدهایِ کاملاً بی‌نقص و ولیدی (perfectly valid) محسوب می‌شن*. اون امنیتِ سیستم منحصراً و تماماً به انتخابِ جنس و نوعِ فیلدی بستگی داشت که ما براش انتخاب کرده بودیم (type choice).

**پاسخ ۴ (جاهایی که ممکنه اطلاعات هنوز نشت کنن):** هر کجایی که یه خط کُد بیاد متدِ `.expose()` رو صدا بزنه و بعدش اون رشته‌ی `&str` رو یه جایی که قراره لاگ‌زده بشه بندازه: مثلاً اینکه بیای URL رو تو بدنه‌ی یه متنی که قراره *ارور قطع اتصال (error message)* رو پرینت کنه جاگذاری (interpolating) کنی ("...failed to connect to postgres://app:***@") که این یه خطای کلاسیک تو برنامه‌نویسیه، یا حتی وقتی بخوای کُلِّ متغیر تنظیمات رو سریالایز کنی (متدِ `Serialize` ربطی به `Debug` نداره — اگه ماکروی `Serialize` رو روی فیلد بذاری اون کلاً به حرفِ تو گوش نمی‌ده و خیلی راحت همون مقدار واقعی رو برمی‌گردونه) که این یکی خیلی موذیانه‌تر و پنهان‌تره (sneaky one). و دقیقاً واسه همینه که اسمِ دسترسی‌دهنده (accessor) این‌قدر عامدانه با یه فعل بلند و پرسروصدا انتخاب شده: ازین به بعد بررسی امنیتیِ کُدها و پیدا کردنِ نشتی‌ها فقط با یه سرچ ساده مثل `rg 'expose\(\)'` تو کدهای کل برنامه انجام می‌شه.

**پاسخ ۵ (اسپلیت از روی اولین `=`):** کلاً هر URL مربوط به Postgres که پارامترهایِ کوئری (query parameters) داشته باشه — مثلِ `postgres://app:***@localhost/dev?sslmode=disable` — یا هر مقدارِ رمزگذاری‌شده‌ای با base64 که تو ته‌ش پدینگِ و مساویِ (padding) کلمه‌ی `=` رو داشته باشه. اگه اسپلیت کردنِ خط رو بندازی رو آخرین `=` نتیجه‌اش این می‌شه که عبارتِ `sslmode=disable` از روی مقدار کنده می‌شه و می‌چسبه به انتهای قسمتِ کلمه کلیدی؛ و اگه کلاً این متد رو رو تمامِ `=`ها انجام می‌دادی، کلاً اون مقدار کاملاً تیکه‌تیکه و خُرد (shatters) می‌شد.

**پاسخ ۶ (کی اصلاً حق داره مقدار پیش‌فرض داشته باشه):** قانون اول: مقادیر محرمانه (secrets) کلاً و مطلقاً هیچ‌وقت، پیش‌فرض (defaults) نمی‌گیرن — یه سکرتِ پیش‌فرض در واقع همون پسوردیه که گذاشتیش رو سورس کنترل برنامه (source control) اما واسه مخفی کردنش فقط یه سری مراحلِ اضافه‌تر تراشیدی. قانون دوم: فقط مقادیری که جوابشون واسه همه‌ی شرایط کاملاً صادق و یکسانه (truthful universal answer) حق دارن پیش‌فرض بگیرن — کلاً عبارتِ `LOG_LEVEL=info` تو تک‌تک استقرارهای نرم‌افزار (deployment) یه عبارت و گزاره‌یِ کاملاً معقول و منطقیه، اما عبارتِ `DATABASE_URL=anything` کلاً یه حدس زدنِ از روی بی‌دقتیه نسبت به زیرساختی (infrastructure) که خود فایلِ باینری اصلاً تو جایگاهی نیست که بدونه کجاست. متغیر `DATABASE_URL` دقیقاً و همزمان هر دو تای این قوانین رو نقض می‌کنه، و دقیقاً واسه همینم هست که غیبتش تو سیستم یه *خطای مهلک (error)* محسوب می‌شه نه فقط یه چیزی که بشه واسش مقدار جایگزین (fallback) گذاشت.
