# راه‌حل

```rust
#[tracing::instrument]
pub async fn process_order(order_id: &str, amount_cents: u64) -> Result<(), OrderError> {
    tracing::info!("processing order");
    charge_payment(order_id, amount_cents).await?;
    send_confirmation(order_id).await;
    tracing::info!("order processing complete");
    Ok(())
}

#[tracing::instrument]
async fn charge_payment(order_id: &str, amount_cents: u64) -> Result<(), OrderError> {
    if amount_cents == 0 {
        tracing::warn!("refusing to charge a zero-amount order");
        return Err(OrderError::PaymentDeclined {
            order_id: order_id.to_string(),
        });
    }
    tracing::info!(amount_cents, "payment charged");
    Ok(())
}

#[tracing::instrument]
async fn send_confirmation(order_id: &str) {
    tracing::info!("confirmation sent");
}

pub fn build_subscriber(json: bool) -> Box<dyn tracing::Subscriber + Send + Sync> {
    let filter = tracing_subscriber::EnvFilter::from_default_env();
    if json {
        Box::new(tracing_subscriber::fmt().with_env_filter(filter).json().finish())
    } else {
        Box::new(tracing_subscriber::fmt().with_env_filter(filter).finish())
    }
}
```

## بازه‌ها (Spans) در مقایسه با رویدادها (events)، کاملاً واضح و مشخص

ماکرویِ `#[tracing::instrument]` روی توابعِ `process_order`، `charge_payment`، و `send_confirmation` به هرکدوم از این فراخوانی‌ها یه **بازه (span)** کاملاً اختصاصی میده — یه ناحیه‌یِ نام‌گذاری‌شده و زمان‌دار — که به طور خودکار با آرگومان‌هایِ همون تابع به عنوانِ فیلدهای داخلی پر شده (مثل `order_id`، `amount_cents`)، و اصلاً نیازی به الصاق دستی فیلدها (manual field-attaching) نیست. هر کدوم از ماکروهای `!tracing::info`/`!warn` که تو بدنه‌ی این توابع صدا زده بشن، در واقع یه **رویداد (event)** هستن — یه اتفاق لحظه‌ای تو زمان، که تگ‌خورده و پیوند زده شدن (بازم کاملاً اتوماتیک) به هر کدوم از بازه‌هایی (spans) که هم‌اکنون تو اون لحظه باز و فعال بودن. به طور کاملاً ملموس، رویدادِ `"payment charged"` که داخلِ تابعِ `charge_payment` شلیک می‌شه، هم فیلدِ صریح و اختصاصیِ خودش (`amount_cents`، که مستقیماً به ماکروِ `!info` پاس داده شده بود) رو حمل می‌کنه *و هم* کلاً توسطِ خروجی‌ساز (subscriber) به بازه‌ی (span) تابعِ `charge_payment` نسبت داده می‌شه، بدون اینکه تابعِ `charge_payment` مجبور باشه کلاً با دست متغیرِ `order_id` رو به ماکروِ `!info` پاس بده — این دقیقاً همون هدف و فلسفه‌ی تودرتو (nesting) کردنِ بازه‌ها (spans) هستش، به جایِ اینکه خودمون بخوایم همش با دست یه شناسه (request ID) رو تو تک‌تکِ فراخوانی‌هایِ لاگ وصله‌پینه و پاس بدیم، کاری که حتماً با یه `!println`ِ خالی مجبور بودیم انجامش بدیم.

## چرا متغیرِ `order_id` که تو بدنه‌یِ `send_confirmation` کلاً بی‌استفاده بوده، کماکان بدون مشکل و تمیز کامپایل می‌شه

بدنه‌یِ تابعِ `send_confirmation` فقط این رو صدا می‌زنه `("tracing::info!("confirmation sent` — و کلاً هیچ‌وقت دستی به `order_id` نمی‌زنه و مستقیماً کاری باهاش نداره. این یه باگ نیست و لینتر clippy هم بهش گیر نمی‌ده: ماکرویِ `#[tracing::instrument]` تو مرحله‌یِ ماکرو-اکسپند (macro-expands)، گسترش پیدا می‌کنه و تبدیل می‌شه به کُدی که *دقیقاً* تک‌تک آرگومان‌های ورودی رو می‌خونه و استفاده می‌کنه (تا به عنوان یه فیلد تو span رکوردشون کنه)، پس در نتیجه، اون زمان که تازه کامپایلر قراره نسخه‌یِ گسترش‌یافته و بزرگ‌شده‌یِ (expanded) این تابع رو ببینه، می‌فهمه که `order_id` کاملاً استفاده شده و بی‌استفاده نبوده. این قضیه واقعاً می‌ارزه که تو ذهنت حکش کنی (internalize)، چون دفعه اولی که باهاش روبه‌رو می‌شی واقعاً غافلگیرکننده‌ست — یه پارامتر تو امضای تابع که در ظاهر کاملاً بی‌استفاده و معطله (apparently-unused)، اما در واقعیت توسطِ یه ماکروی صفت (attribute macro) که بالایِ سر تابع نوشته شده، کاملاً مصرف شده (consumed)، نه توسط هیچ کدِ واضحی که تو بدنه‌ی تابع بتونی با چشمت ببینیش.

## ساختار `<Box<dyn Subscriber`، و اینکه چرا تو این شرایط `impl Trait` کلاً کار نمی‌کنه

تابعِ `()tracing_subscriber::fmt` یه builder (سازنده) برمی‌گردونه که روی نوعِ فرمت‌کننده‌اش (formatter) جنریک و متغیره؛ وقتی متدِ `.json()` رو صدا می‌زنی، قبل از اینکه برسی به `.finish()`، کلاً یه نوع (type parameter) دیگه رو واسه فرمت‌کننده‌اش می‌کاره و عوضش می‌کنه. معنیش اینه که اون دو تا شاخه‌یِ (branches) مربوط به `if json { ... } else { ... }` کلاً دو نوعِ ساختار ملموس و فیزیکیِ کاملاً *متفاوت* (concrete types) رو که هردوشون خصیصه‌ی `Subscriber` رو پیاده‌سازی کردن تولید می‌کنن — و کلمه‌ی کلیدیِ `impl tracing::Subscriber` برای اینکه بتونه کار کنه، کامپایلر رو مجبور می‌کنه که کلاً فقط و فقط یه نوعِ تک و واحد و زیربنایی رو برای تموم مسیرهای خروجِ اون تابع انتخاب کنه، و وقتی دو تا نوع (struct types) کاملاً متمایز و واقعی داری که شبیه هم نیستن، این خواسته اصلاً محاله برآورده بشه (can't satisfy). وقتی نتیجه رو پنهان (Boxing) می‌کنی پشتِ خصیصه‌یِ `dyn tracing::Subscriber + Send + Sync`، نوع واقعی و ملموس (concrete type) کلاً و از بیخ پاک (erases) می‌شه، در نتیجه از زاویه‌یِ دیدِ فراخواننده‌ی این تابع، هر دویِ این شاخه‌ها (branches) دقیقاً دارن یه چیزِ کاملاً یکسان برمی‌گردونن: "یه شیء نامشخص که از قضا خروجی‌ساز (subscriber) هست." حضورِ قیودِ (bounds) مربوط به `Send + Sync` هم کاملاً حیاتی و مهمه، چون تو یه برنامه‌ی واقعیِ `main.rs`، این خروجی قراره مستقیم بره تو شکمِ متدِ `.init()` (و از اونجایی که زمان‌اجرا (runtime) تو tokio به طور پیش‌فرض کارها رو روی تعداد زیادی از ریسمان‌های کارگر (worker threads) پخش و زمان‌بندی (schedules) می‌کنه، متدِ `init` هم حتماً به یه مشترک و خروجی‌ساز نیاز داره که قابلیت استفاده تو ریسمان‌هایِ مختلف (across threads) رو داشته باشه).

## الگوی تست‌نویسی: استفاده از `set_default`، به جای `.init()`

دستورِ `()build_subscriber(...).init` یه خروجی‌سازِ (subscriber) کُلی و پیش‌فرض نصب می‌کنه که ماهیتش **جهانی (global)**، تو مقیاسِ **کلّ پروسه (process-wide)**، و **برای همیشه و تا ابد (permanent)** هستش — که این دقیقاً همون کارِ ایده‌آل و درستیه که تابعِ `main` باید و باید فقط و منحصراً *یک بار* انجام بده، و دقیقاً همون چیزیه که یه مجموعه‌تست (test suite) امکان نداره بتونه پشت‌سرهم تکرارش کنه (دومین فراخوانیِ `.init()` تو هرجایِ دیگه‌ای از همون فایل باینری تست، مستقیماً پنیک (panics) می‌کنه با این پیام: "a global default trace dispatcher has already been set"). اما تابع کمکی و دستیارِ `()recorder` تو برنامه‌یِ ما، میاد از `tracing::subscriber::set_default(subscriber)` استفاده می‌کنه، که کارش اینه:

- کلاً فقط و فقط رویِ **ریسمانِ فعلی (current thread)** اثر می‌ذاره، و فقط هم تا همون زمانی که متغیر خروجی‌اش یعنی `DefaultGuard` زنده باشه و از بین نرفته باشه (وقتی که از محدوده‌ی کُدیش خارج بشی و متغیر کلاً رها و drop بشه، خودش همه چی رو برمی‌گردونه رو همون وضعیتی که قبل از فراخوانیِ این تابع بوده).
- می‌تونه به هر تعداد باری که دلت خواست، یعنی به ازایِ هر تست یک بار، بدون هیچ خطر تصادف و تداخلی (collision risk) بین تست‌هایی که دارن رو ریسمان‌هایِ مختلف و مجزا ران می‌شن، صدا زده بشه — دقیقاً همون استدلالی که تو سرویسِ `capstone-taskforge/taskforge-api`، واسه تابع `()metrics_handle` که با یه متغیر `OnceLock` قفل و محافظت شده بود تا یه منبعِ کاملاً *سراسری و جهانیِ* یک‌بارمصرف رو تحویل سیستم بده (بخش رکوردر تو Prometheus واقعاً و حقیقتاً نمی‌تونه دو بار نصب بشه)، فقط با این تفاوت که اینجا راه‌حل کلاً برعکس بود: خروجی‌سازِ (subscriber) تو `tracing` از خودش یه جایگزینِ (alternative) کاملاً *محدود به بلوک کد (scoped)* در مقابلِ نصب جهانی و سراسری داره، پس در نتیجه تست‌سوییت (test suite) به جای اینکه اصلاً نیازی به محافظِ یک‌بارنصب (once-guard) داشته باشه، میاد مستقیم دست می‌ذاره رو همین ویژگی و همینو استفاده می‌کنه.

## لایه‌ی کاملاً دست‌ساز (hand-rolled Layer)

نوعِ `RecordingLayer` فقط و فقط یک دونه متد رو پیاده‌سازی می‌کنه، یعنی متد `on_event`، و کارشم اینه که یه رکورد از نوعِ صاف‌شده و تختِ `RecordedEvent` (که شامل اسمِ بازه، سطح، پیام، و فیلدهای ساخت‌یافته‌ست) رو با عمل push می‌ریزه تو شکمِ یه `Vec` مشترک، تا تست‌ها بتونن بعداً بیان و اونو تو کار خودشون چک (assert) کنن. این کُد یه مکانیزم کلاً مربوط به پروداکشن (production machinery) محسوب می‌شه، نه فقط یه حقه‌یِ زیرکانه‌ی تستی و تست-اُنلی — خصیصه‌ی `tracing_subscriber::Layer` دقیقاً همون خصیصه‌ایه که یه فرمت‌کننده‌ی (formatter) مربوط به JSON یا یه اکسپورتر (exporter) واسه OpenTelemetry اون رو پیاده‌سازی می‌کنه و روش نوشته می‌شه؛ فقط کُدِ این درس اومد نسخه‌ی دست‌ساز خودشو نوشت که به جای اینکه بخواد داده‌ها رو رو خروجیِ stdout یا رویِ یه سوکتِ شبکه‌ای (network socket) بنویسه، اونارو تو دل حافظه‌یِ رَم می‌نوشت. عبارتِ `Context::event_span(event)` دقیقاً همون قطعه کدی هستش که می‌تونه بازیابی کنه که "کدوم بازه (span) تو لحظه‌یِ این رویداد فعال بوده" اونم از تو دلِ یه دفتریِ (Registry) کاملاً محیطی و سراسری (و اینکه کلاً این جستجو (lookup) اصلاً ممکنه و شدنیه فقط به خاطر قیدِ (bound) مربوط به `S: LookupSpan` هست)، و این دقیقاً همون چیزیه که به تست‌ها اجازه میده تا بتونن چک کنن (assert) که رویدادِ `"payment charged"` مشخصاً و فقط از تو دلِ بازه‌یِ (span) مربوط به `charge_payment` متولد شده و نه اینکه کلاً فقط بگن "یه رویدادی یه جایی از کُد بالاخره شلیک و صادر شد."

## چرا تستِ رد کردنِ تراکنش (decline test) اصرار داره اثبات کنه که تابعِ `send_confirmation` اصلاً و کلاً اجرا نشده

مقدارِ `Err` که تابع `charge_payment` تولید می‌کنه، مستقیماً از دلِ عملگرِ `?` تو تابعِ `process_order` عبور (propagates) می‌کنه، که باعث می‌شه درجا و بدون وقفه (immediately) از همونجا `return` کنه — و اینجوریه که خطِ مربوط به `send_confirmation(order_id).await` کلاً تو قدم و سطرِ بعدی رنگ اجرا شدن هم نمی‌بینه. این تست میاد و دقیقاً همین موضوع رو تو لایه‌ی *نظارت‌پذیری (observability)* اثبات می‌کنه (چون کلاً هیچ رویدادی که به بازه‌ی (span) تابع `send_confirmation` نسبت و تگ داده شده باشه، تو خروجی رکوردشده وجود و حضور نداره) به جای اینکه بیاد یه ابزارِ جانبی و فرعی (side channel) مثل یه متغیر شمارنده (counter) به برنامه اضافه کنه، چون تو دنیای واقعی، تو دقیقاً همونجوری یه سرویس دیپلوی‌شده‌یِ عملیاتی (deployed service) رو حسابرسی و بررسی (audit) می‌کنی: اگه لاگ‌ها بهت بگن که کُلاً فلان قدم اجرا و ران (ran) نشده، خب کلاً اجرا نشده.
