# راه‌حل

## تابعِ `cache_key`

```rust
pub fn cache_key(namespace: &str, id: &str) -> String {
    format!("{namespace}:{id}")
}
```

اینجا هیچ‌چیزی جادویی‌تر از یه فرمت کردنِ ساده‌ی رشته (string formatting) وجود نداره — ارزشِ واقعیِ این کار اصلاً تو کدهایی که نوشته شده نیست، بلکه تو *انضباطِ (discipline)* استفاده‌ی همیشگی از این تابعه به جای اینکه تو هر کجای برنامه بیای با دستِ خودت رشته‌های کلید (key strings) بسازی، تا در نهایت تمامِ کلیدهای کَش تو کلِ codebase یه شکل و قالب یکسان داشته باشن و فضای‌نام‌ها (namespaces) هیچ‌وقت برحسب تصادف با هم تصادم (collide) نکنن.

## پیاده‌سازیِ خصیصه‌ی `Cache` رویِ `InMemoryCache`

```rust
async fn get(&self, key: &str) -> Result<Option<String>, CacheError> {
    match self.store.get(key) {
        Some((value, expires_at)) if self.clock.now() < *expires_at => Ok(Some(value.clone())),
        _ => Ok(None),
    }
}

async fn set(&mut self, key: &str, value: String, ttl: Duration) -> Result<(), CacheError> {
    self.store
        .insert(key.to_string(), (value, self.clock.now() + ttl));
    Ok(())
}

async fn invalidate(&mut self, key: &str) -> Result<(), CacheError> {
    self.store.remove(key);
    Ok(())
}
```

اون نگهبانِ مچ (match guard) تو دستور `match` (یعنی `if self.clock.now() < *expires_at`) دقیقاً کلِ مکانیزمِ TTL رو رو دوشش می‌کشه: یه رکورد تو کش تنها و تنها تو صورتی موفق (hit) حساب می‌شه که اولاً اونجا وجود داشته باشه، *و ثانیاً* ساعت هنوز از مرزِ زمانِ انقضایِ ثبت‌شده‌اش عبور نکرده باشه. اون بازویِ `_ => Ok(None)` کاملاً از روی قصد نوشته شده تا دو تا حالتِ کاملاً متفاوت رو زیرِ یه چتر پوشش بده — "اصلاً رکوردی با این کلید ذخیره نشده بود" و "ذخیره شده بود اما الان دیگه منقضی و کهنه شده" — چون از زاویه‌ی دیدِ متدِ `get_or_set` جفتِ این دو تا حالت یه معنی بیشتر نمی‌دن: دیتایی پیدا نشد (miss)، برو از نو محاسبه کن.

دقت کن که متدِ `set` اصلاً چک نمی‌کنه که آیا اون `key` از قبل تو کش وجود داشته یا نه؛ متدِ `HashMap::insert` تو Rust مقادیر رو بدونِ هیچ شرطی رونویسی می‌کنه (overwrites)، که دقیقاً همون رفتارِ موردنظر تو عملیاتِ نوشتن برای الگویِ cache-aside هست — یه `set` تازه، همیشه و در هر صورت برنده‌ست و روی قبلی می‌شینه.

## تابعِ `get_or_set`

```rust
pub async fn get_or_set<C, F, Fut>(
    cache: &mut C,
    key: &str,
    ttl: Duration,
    compute: F,
) -> Result<String, CacheError>
where
    C: Cache,
    F: FnOnce() -> Fut,
    Fut: Future<Output = String>,
{
    if let Some(value) = cache.get(key).await? {
        return Ok(value);
    }
    let value = compute().await;
    cache.set(key, value.clone(), ttl).await?;
    Ok(value)
}
```

این دقیقاً کلِ الگوی cache-aside تو پنج خط کده: اول چک کن، اگه دیتا تو کش بود سریع (early-return) اونو برگردون، در غیر این صورت محاسبه کن-ذخیره کن-برگردون. متغیرِ `compute: F` نسبت به `Fut <- ()FnOnce` جنریک (generic) نوشته شده به جای اینکه از اول یه `String` که مقداری توش محاسبه و جا داده شده رو تو ورودیش بخواد — دقیقاً همین ذاتِ تنبل‌بودنه (laziness) که باعث می‌شه کش کردن تو دنیای واقعی برامون کارهای سنگین رو ذخیره و صرفه‌جویی کنه. اگه قرار بود فراخواننده حتماً قبل از زدنِ تابعِ `get_or_set` خودش با دست اون مقدار رو محاسبه کنه، اونوقت تو *تک‌تک* فراخوانی‌ها، فارغ از اینکه دیتا تو کش بود یا نه، مجبور بود اون هزینه‌ی سنگین محاسبه رو پرداخت کنه، که خب کلاً فلسفه و هدفِ کش رو زیر سؤال می‌برد. تستِ `compute_only_runs_once_on_repeated_hits` این موضوع رو دقیقاً و مستقیماً با شمردنِ تعدادِ دفعات اجرا با یه `<<Rc<Cell<i32` بهمون ثابت می‌کنه.

## پاسخ‌های تشریحی

**۱. چرا `compute` به صورت تنبلانه؟** بالاتر توضیح دادیم — مکانیزمِ تنبل‌بودن دقیقاً همون سازوکاریه که باعث می‌شه یه مقدارِ پیدا شده تو کش (hit)، اصلاً اون کارِ سنگین رو از بیخ انجام نده. یه API حریص (مثلِ `get_or_set_eager(cache, key, ttl, value: String)`) همچنان می‌تونه فرآیندِ *ذخیره‌سازی* رو برات بهینه انجام بده، اما فراخواننده در هر صورت اون بار و فشارِ سنگین رو همون اول کار قبل از زدنِ اون تابع کشیده بود، چه اون دیتا تو کش می‌بود چه نبود.

**۲. چرا واسه `get` از `&self` استفاده شده، و رکوردهای منقضی‌شده سر جاشون باقی می‌مونن؟** پاک کردنِ یه رکوردِ منقضی‌شده موقعِ خوندنش نیازمندِ `&mut self` بود، که باعث می‌شد *تک‌تک* درخواست‌کننده‌هایِ `get` (که یه عمل خوندنه!) مجبور بشن برای خودشون یه قرضِ انحصاری (exclusive borrow) بگیرن — که خب کار خیلی ناجور و عجیب‌غریبی می‌شد، و از طرفی برای درستیِ کد هم اصلاً نیازی به این کار نبود چون همون بررسیِ انقضایِ اولیه باعث می‌شه یه رکوردِ تاریخ‌گذشته دقیقاً شبیه یه دیتای پیدا نشده (miss) عمل کنه. هزینه‌ای (trade-off) که بابت این کار می‌دیم مصرفِ مموریه: یه رکورد که بعد از تاریخِ انقضاش دیگه هرگز و توسط هیچ‌کسی خونده نشه، تا ابد تو دلِ اون `HashMap` می‌مونه و هیچ‌وقت آزاد نمی‌شه (freed). کش‌هایِ واقعی (از جمله خود Redis) واقعاً یه فرآیند پاک‌سازیِ پس‌زمینه (background sweep) دارن ("انقضای فعال یا active expiry") دقیقاً برای اینکه رشدِ مموری رو تو این سناریو کنترل کنن — در غیر این صورت، الگوهایی که مدام دارن دیتایِ جدید تو کش می‌نویسن و کلاً داده‌های تاریخ‌گذشته رو کم می‌خونن، تو یه مکانیزمی که تماماً تنبل (lazy-only) هستش به طور بی‌نهایت باعث نشت مموری (leak memory) می‌شدن.

**۳. هجوم و رم کردنِ گله تو کش (Cache stampede).** با این کدی که ما واسه `get_or_set` نوشتیم، اگه همزمان N تا درخواستِ همروند واسه یه کلید مشخص، جوابِ miss دریافت کنن، همگی و مستقل از هم میرن `compute` رو صدا می‌زنن و همگی هم مستقل از هم رو کش `set` می‌کنن — این یعنی کش تو اون لحظه دقیقاً هیچ کمکی بهت نمی‌کنه و هیچ ارزشی برات خلق نمی‌کنه، و دیتابیسِ تو (یا هر چی که اون `compute` داره صداش می‌زنه) دقیقاً تو همون بدترین لحظه‌ی ممکن که یه کلیدِ خیلی مهم و محبوب منقضی شده، فشاری معادلِ N برابرِ حالت عادی رو روی دوش خودش می‌بینه. راه‌حلِ استاندارد واسه این مشکل، یه قفلِ "در حال پرواز (in-flight)" به ازای هر کلیده: یعنی اولین فراخواننده‌ای که می‌بینه جوابِ کش miss هست، همون لحظه اون کلید رو می‌ذاره رو حالتِ "داره محاسبه می‌شه" (مثلاً از طریقِ یه `<<HashMap<String, tokio::sync::Mutex<()>>` یا یه ساختارِ اختصاصی و single-flight)، و بقیه‌یِ درخواست‌هایِ همروندی که دقیقاً واسه همون کلید دارن میان، به جای اینکه برن و دوباره `compute` رو صدا بزنن، مجبورن پشت همون قفل منتظر بمونن تا اون یکی که تو این مسابقه اول شده (whoever wins the race) بره محاسبه‌اش رو انجام بده و کش رو برای بقیه هم پر (populates) کنه تا همه بتونن از روش بخونن.

**۴. چرا `FakeClock` از `<<Cell<Instant` استفاده کرده؟** امضایِ متد `(&self)Clock::now` دقیقاً و عمداً داره یه رفرنسِ مشترک (shared reference) می‌گیره — یه ساعت که می‌تونه همزمان از جاهای مختلفی خونده بشه (مثل یه کش که تو نقاط مختلف برنامه بهش رجوع می‌شه) نباید واسه اینکه صرفاً بتونه تایم رو نشون بده، مجبور باشه یه دسترسی انحصاری (exclusive access) بگیره. اما خب از اون طرف، متدِ `advance` هنوزم برای جلو بردن زمان، مجبوره که متغیرِ ذخیره‌شده رو *تغییر (mutate)* بده. نوعِ `<Cell<T>` دقیقاً همون ایده‌ی "تغییرپذیریِ درونی (interior mutability) برای نوع‌هایِ `Copy` که تو یک دونه ریسمان (thread) در دسترس قرار می‌گیرن" رو پیاده می‌کنه: یعنی بهت اجازه می‌ده متد `(self&)now` (که مشترکه) رو به طور مسالمت‌آمیزی در کنار متدِ `(self&)advance` (که اونم مشترکه، اما داره از طریق اون سلول محتویاتشو تغییر می‌ده) قرار بدی، بدون اینکه هیچ نیازی به یه `Mutex` یا قانون‌های دست‌وپاگیرِ چک کردن-قرض‌گرفتن‌ها (borrow-checking) توسط `RefCell` تو زمان اجرا باشه؛ هزینه‌شم اینه که کلاً خصیصه‌ی `Sync` رو نداره — که خب اینجا هم اصلاً هیچ مشکلی واسمون درست نمی‌کنه، چون فیوچرهایِ (futures) این درس عمداً و از قصد طوری نوشته شده بودن که اصلاً به خصیصه‌هایِ `Send`/`Sync` نیازی نداشته باشن (برو یه نگاه به کامنت‌های مستنداتیِ روی خصیصه‌ی `Cache` بنداز).

**۵. اگه فقط رو TTL حساب کنی و باطل‌سازیِ صریح (invalidation) نداشته باشی چی می‌شه؟** فرض کن یه کاربر میاد و بیوگرافی پروفایلشو (bio) تغییر میده، و اون کشی که واسه صفحه‌ی پروفایل‌ها در نظر گرفته شده یه TTL پنج دقیقه‌ای داره بدون اینکه صریحاً موقعِ ذخیره شدن، چیزی رو پاک کنه. اون کاربر روی "ذخیره" کلیک می‌کنه، سریع هدایت می‌شه به صفحه‌ی پروفایل خودش، و بعد می‌بینه که کماکان بیوگرافیِ *قدیمیِ* خودش به مدت نهایتاً ۵ دقیقه داره بهش نمایش داده می‌شه — اونم رو پروفایل شخصیِ خودش، دقیقاً یه ثانیه بعد از اینکه خودش با دستِ خودش ادیتش کرده. این دقیقاً یه تجربه‌ی کاربریِ افتضاح و به شدت گیج‌کننده‌ست دقیقاً چون توسط شخص خودِ کاربر اتفاق افتاده و همون لحظه جلو چشمشه، نه اینکه یه باگِ خیلی نادر و فرعی باشه. باطل کردن کش به صورت صریح تو زمان نوشتن دیتابیس (یعنی فراخوانیِ `(((cache.invalidate(&cache_key("user-profile", &user_id` دقیقاً یه ثانیه بعد از اینکه عمل نوشتن رو دیتابیس موفقیت‌آمیز تموم می‌شه) دقیقاً همین یه دونه مشکلو خیلی راحت حل می‌کنه؛ و TTL هم فقط در جایگاه یه تورِ ایمنی واسه همون مواردی که باطل کردن کش از زیر دست برنامه‌نویس در رفته یا ناموفق بوده، سر جاش باقی می‌مونه.
