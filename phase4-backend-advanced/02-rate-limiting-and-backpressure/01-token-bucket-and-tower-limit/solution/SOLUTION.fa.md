# راه‌حل

## تابع `TokenBucket::new`

```rust
pub fn new(capacity: u32, refill_rate: f64, now: Instant) -> Self {
    Self {
        capacity: capacity as f64,
        refill_rate,
        tokens: capacity as f64,
        last_refill: now,
    }
}
```

سطل کلاً از همون اول پُر شروع می‌شه — یعنی `tokens == capacity` — تا همون اولین موجِ رگباری از درخواست‌ها که تا سقفِ `capacity` میان، درجا با موفقیت عبور کنن، که این دقیقاً با همون ویژگیِ "رگبارها تا سقفِ capacity کاملاً مجازن" تو README می‌خونه.

## متد `refill`

```rust
fn refill(&mut self, now: Instant) {
    let elapsed = now.saturating_duration_since(self.last_refill).as_secs_f64();
    self.tokens = (self.tokens + elapsed * self.refill_rate).min(self.capacity);
    self.last_refill = now;
}
```

استفاده از متدِ `saturating_duration_since` (به جای یه تفریقِ ساده و خام) کلاً این محافظت رو ایجاد می‌کنه که اگه یه روزی متغیر `now` زمانش کلاً قبل از `last_refill` بود مشکلی پیش نیاد — که خب تو تست‌های این درس عملاً نباید همچین چیزی پیش بیاد (چون زمان کلاً فقط رو به جلو می‌ره)، اما دقیقاً همون رفتارِ دفاعیِ (defensive habit) استانداردی هست که تو کدهای محیطِ پروداکشن به شدت بهش نیاز داری، چون اونجا ممکنه مقدارِ `now` از یه سورس و منبعی بیاد که کلاً روش کنترلِ صددرصدی نداری. عبارتِ `.min(self.capacity)` همون کلاهکِ (cap) معروف واسه جلوگیری از سرریز شدن (never overflow) هستش. اینم دقت کن که مقدارِ `last_refill` کاملاً بدون هیچ شرطی، تو تک‌تک فراخوانی‌ها آپدیت می‌شه — که جواب سؤال مرور شماره ۳ رو میده.

## متد `try_acquire`

```rust
pub fn try_acquire(&mut self, now: Instant) -> bool {
    self.refill(now);
    if self.tokens >= 1.0 {
        self.tokens -= 1.0;
        true
    } else {
        false
    }
}
```

اول سطل رو پر کن (refill)، بعد تصمیم بگیر — این تقدم و تأخرِ اجرا به شدت مهمه: درخواستی که بعد از سپری شدنِ زمانِ کافی برای اضافه شدنِ یه توکن تازه از راه می‌رسه، باید و باید *قبل از* اجرایِ شرطِ قبول/رد شدن، اون توکنِ تازه‌نفس رو تو سطل ببینه، در غیر این صورت یه سطل که دقیقاً واسه تولید ۱ دونه توکنِ جدید بیکار بوده، در کمال ناباوری همون درخواستی رو که باید و حقش بود اجازه ورود بگیره رو رد (reject) می‌کرد.

## پاسخ‌های تشریحی

**۱. چرا `now: Instant` به عنوان پارامتر اومده؟** اگه می‌اومدی و مستقیماً متدِ `()Instant::now` رو تو خودِ بدنه‌ی `try_acquire` صدا می‌زدی، اون‌وقت هر کدوم از تست‌ها که می‌خواستن ادعا کنن (assert) "هنوز هیچ توکنی پر نشده" یا "دقیقاً و دقیقاً ۱ ثانیه گذشته" یا باید به شدت ناپایدار و شانسی (flaky) می‌شدن (چون زمان‌بندیِ واقعی با توابع مبتنی بر `sleep` کلاً لرزش و پرش (jitter) داره) یا اینکه به شدت کُند می‌شدن (چون واسه هر تست باید ثانیه‌های واقعی رو به طور فیزیکی منتظر می‌موندی). پاس دادن صریحِ `now` باعث می‌شه تا زمانِ سپری‌شده (elapsed time) کلاً تبدیل بشه به یه مقداری که تستِ تو روش تسلطِ صددرصدی و کامل داره — عبارتِ `now + Duration::from_secs(1)` کاملاً دقیق و تو لحظه (instantaneous) انجام می‌شه، و از لحاظ مفهومی مطلقاً هیچ فرقی با ابزارِ `FakeClock` تو درسِ کش کردن نداره.

**۲. چرا `tokens` از نوعِ `f64` تعریف شد؟** فرض کن مقدار `2.0 = refill_rate` باشه و ما با گام‌هایِ 100 میلی‌ثانیه‌ای پیش بریم؛ تو هر فراخوانی تو دقیقاً `0.2` تا توکن به دست میاری. اگه `tokens` یه نوع عددی صحیح (integer) می‌بود، این مقدارِ `0.2` یا باید به صورت کامل قطع (truncation) می‌شد (که نتیجه‌اش این بود که تو تک‌تک فراخوانی‌ها، پیشرفتِ زیرِ یک‌توکنت (sub-token progress) رو از دست می‌دادی — و بعد از ۵۰ تا فراخوانی با 100ms و نرخ ۲ توکن-بر-ثانیه، عملاً کل اون انباشت‌های اعشاریت رو از دست می‌دادی و دچار یه کم‌شماریِ (undercounting) فاجعه‌بار می‌شدی) یا اینکه مجبور بودی یه مکانیزمِ کاملاً جداگانه برای ثبت اعداد ثابت‌نقطه (fixed-point) و باقی‌مانده‌ها (remainder scheme) بسازی تا جلوی این هدر رفتن‌ها رو بگیری. اما استفاده از `f64` از بیخ و بُن کل این دردسر رو دور می‌زنه: پیشرفت‌های اعشاری و خُرد خیلی راحت و طبیعی لایه‌لایه تو دفعاتِ مختلفِ فراخوانی روی هم جمع می‌شن، و این دقیقاً و مو به مو همون چیزیه که تستِ `sustained_rate_matches_refill_rate_over_a_long_window` به شدت بهش تکیه کرده تا مطمئن بشه خروجی حتماً تو اون بازه‌یِ موردانتظارِ `12..=9` فرود میاد.

**۳. چرا `last_refill` حتی زمانی که صفر تا توکن بهش اضافه می‌شه هم آپدیت می‌شه؟** چون وظیفه و رسالتِ `last_refill` اینه که نشون بده "آخرین لحظه‌ای که ما حسابرسی‌مون رو تا اون نقطه انجام دادیم کی بوده"، نه اینکه بگه "آخرین باری که با موفقیت یه توکن رو کامل اضافه کردیم کی بوده." اگه قرار بود فقط رویِ افزایش‌های غیرصفر (nonzero gain) آپدیت بشه، اون‌وقت اگه دو تا فراخوانی با فاصله‌یِ کلاً یه میکروثانیه از هم انجام می‌شد، جفتشون واسه محاسبه‌ی `elapsed` به *همون* مقدارِ تاریخ‌گذشته و قدیمیِ `last_refill` تو دفعه‌یِ سومی که مدت‌ها بعد انجام می‌شد تکیه می‌کردن، اما فاجعه‌تر از اون: زمانِ سپری‌شده‌یِ بینِ فراخوانی اول و دوم تا ابد هیچ‌موقع به حساب نمیومد (کلاً تباه می‌شد می‌افتاد رو زمین)، و سطلِ ما تو کمالِ سکوت اعتبار و توکنی که حقش بود رو دریافت نمی‌کرد (under-crediting). آپدیتِ بی‌قید و شرط، دقیقاً گارانتی و تضمین می‌کنه که زمانِ سپری‌شده فقط و فقط دقیقاً *یک بار* محاسبه بشه، بدون هیچ شکافِ (gaps) زمانی و بدون هیچ دوباره‌شماریِ (double-counting) اضافه‌ای.

**۴. مقایسه‌ی সطلِ توکن (Token bucket) با زمان انقضا (Cache TTL).** هردوشون میان یه تایم‌استمپ (timestamp) رو ذخیره می‌کنن و با زمانِ "اکنون (now)" مقایسه‌اش می‌کنن، اما دقیقاً دارن از دو تا چیزِ کاملاً متضاد و متفاوت محافظت می‌کنن. زمانِ انقضا تو کش (Cache TTL) سیستم رو در برابر کهنگیِ دیتای (staleness) محافظت می‌کنه — وظیفه‌اش پاسخ به این سؤاله: "آیا این *داده‌یِ* ذخیره‌شده هنوزم قابل اعتماده و کار می‌کنه؟" و، به محض اینکه تاریخ مصرفش بگذره، دیتا کلاً از بین می‌ره (باید از نو محاسبه بشه). اما سطلِ توکن از *نرخ (rate)* محافظت می‌کنه — وظیفه‌اش پاسخ به این سؤاله: "آیا خیلی تازگیا حجمِ زیادی *کآر* (too much work) رو سیستم ریخته نشده؟" و اون "مقدار"ِ موجودیش (یعنی همون تعدادِ توکن) کاملاً آگاهانه و عمداً اجازه داره که با گذشتِ زمان یواش‌یواش و بخشی از خودش رو بازیابی کنه (partially recover)، به جای اینکه یه روند صفر و صدی و همه‌یاهیچ (all-or-nothing) داشته باشه.

**۵. کدوم استراتژی از فشار متقابل، و تابعِ `async fn acquire` به چی نیاز داره.** اینکه خروجیِ تابعِ `try_acquire` از نوعِ `bool` هستش، نشون‌دهنده‌یِ استراتژی شماره ۱ یعنی همون "درجا رد کن" هست — فراخواننده به صورت کاملاً همگام (synchronously) خبردار می‌شه و این دیگه وظیفه‌ی خودشه که تصمیم بگیره بعدش چی کار کنه (بعداً دوباره تلاش کنه، کدِ `429` برگردونه، یا کلاً درخواست رو قطع کنه). یه تابع به شکلِ `async fn acquire(&mut self)` که به جاش برای یه توکن *منتظر بمونه (waits)*، به این دو تا چیز نیاز داره: (الف) یه روشی که بتونه باهاش دقیقاً همون لحظه‌ای که یه توکن آزاد شد بیدار (woken up) بشه، به جای اینکه دائم به صورت مسدودکننده (busy-polling) بپرسه — که برای این کار یا باید محاسبه کنه که "دقیقاً چقدر طول می‌کشه تا حداقل یه توکن دیگه متولد بشه" (یعنی `seconds (1.0 - self.tokens) / self.refill_rate`) و برای همون تایم به کمکِ تابع `tokio::time::sleep` متوقف بشه و بخوابه و بعدِ بیدار شدن دوباره چک کنه، یا اینکه خودش رو تو یه ساختار `Notify`/بیدارکننده (waker) ثبت کنه تا یه تسکِ پس‌زمینه‌ای (background task)ِ کمکی رو یه تایمر بهش پینگ بده؛ (ب) یه تصمیمِ کاملاً واضح و قاطع برای زمانی که همزمان تعداد زیادی از فراخواننده‌ها پشت در منتظر شدن — عدالت در صف‌بندی (FIFO fairness) قرار نیست به صورت خودکار و فقط به خاطر استفاده از کلمه‌ی `.await` ظاهر بشه، بلکه تو احتمالاً واسه این کار به یه صفِ (queue) کاملاً مشخص نیاز داری (این دقیقاً همون استراتژی شماره ۲ یعنی "صف با ظرفیتِ سقفِ مشخص" هست، و دقیقاً نزدیک‌ترین چیزیه که خودِ `tower::limit::RateLimitLayer` با کمک گرفتن از `tower::buffer` تو کُدش پیاده کرده).
