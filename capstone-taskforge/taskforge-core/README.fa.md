# کریت `taskforge-core`

لایه‌یِ دامنه‌یِ پروژه (Domain layer). مشخص می‌کنه که یه جاب اصلاً چی *هست* (`Job`، `JobId`، `JobStatus`، `NewJob`)، چه قوانینی واسه تغییرِ وضعیتِ یه جاب وجود داره (برو فایلِ [`../docs/adr/0003-job-state-machine.fa.md`](../docs/adr/0003-job-state-machine.fa.md) رو ببین)، و دو تا Trait که کریت‌های دیگه به جای اینکه مستقیماً به همدیگه وابسته بشن، به اونا وابسته می‌شن:

- **`JobStore`** — پورتِ ذخیره‌سازی (storage port). کریتِ `taskforge-storage` دو بار پیاده‌سازیش می‌کنه: یه بار واقعی (با Postgres)، و یه بار هم تو حافظه به عنوان دابلِ تستی (test double). برو سندِ [`../docs/adr/0001-architecture-overview.fa.md`](../docs/adr/0001-architecture-overview.fa.md) رو بخون.
- **`JobHandler`** — توسط هر کُدی که واقعاً کارِ یه جاب رو انجام می‌ده پیاده‌سازی می‌کنه؛ و تو استخرِ کارگرها (worker pool) تو کریتِ `taskforge-worker` ثبت می‌شه، که کلیدشم اسمِ `()job_type` هستش.

این کریت **صفر وابستگیِ I/O داره** — نه خبری از `sqlx` هست، نه شبکه و امکاناتِ `tokio`. این کاملاً عامدانه و حساب‌شده‌ست، نه از روی اتفاق: همون چیزیه که باعث می‌شه تست‌های تک‌تکِ کریت‌های دیگه بتونن روی `InMemoryJobStore` بدون نیاز به هیچ دیتابیس، داکر، یا شبکه‌ای تو هر جایی ران بشن.

## ران کردن تست‌ها

```sh
cargo test -p taskforge-core
```

هیچ ستاپ و راه‌اندازی‌ای لازم نیست — تست‌های این کریت فقط منطقِ خالصن (قوانینِ `is_terminal`/`is_cancellable` تو ماشین حالت، ساختِ `Job` از روی `NewJob`، و یکتا بودنِ `JobId`).
