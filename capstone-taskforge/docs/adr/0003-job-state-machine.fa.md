# ADR-0003: ماشین حالتِ جاب‌ها (Job state machine)

## وضعیت (Status)
پذیرفته‌شده (Accepted)

## زمینه و کانتکست (Context)

یه جاب نیاز به وضعیتی داره که همیشه و تحت هر شرایطی معنی‌دار باشه — هیچ ترکیبی از فیلدها نباید بتونه یه وضعیتِ بی‌پایه و بی‌معنی رو نشون بده (مثلاً "با موفقیت تموم شده، اما در عین حال زمان‌بندی شده واسه تلاش مجدد"). این دقیقاً همون فکریه تحت عنوان "حالت‌های غیرقانونی رو غیرقابل‌بازنمایی کن (make illegal states unrepresentable)" از سؤال‌های مرورِ درس `phase1-fundamentals/05-structs-enums-pattern-matching/02-enums-and-match`، که حالا تو دنیای واقعی به کار گرفته شده.

## تصمیم (Decision)

مدل‌سازیِ `JobStatus` تو قالبِ یه enum، نه یه رشته‌ی متنی واسه وضعیت به علاوه‌یِ یه مشت ستونِ نال‌پذیر (nullable):

```rust
pub enum JobStatus {
    Pending,
    Running,
    Succeeded,
    Retrying { attempt: u32, next_attempt_at: DateTime<Utc> },
    Failed { error: String },
    DeadLetter { error: String },
}
```

انتقال‌های معتبر بین وضعیت‌ها (Valid transitions) که توسط پیاده‌سازی‌های `JobStore` اجبار و کنترل می‌شن (نه فقط توسط شِمای دیتابیس — Postgres فرمتِ سریالایزشده‌ی enum رو ذخیره می‌کنه، اما *قوانین* تو زبان Rust زندگی می‌کنه جایی که کامپایلر و تست‌ها می‌تونن اونا رو تایید کنن):

```
Pending → Running
Running → Succeeded
Running → Retrying   (تعداد تلاش‌ها < max_attempts)
Running → DeadLetter (تعداد تلاش‌ها >= max_attempts)
Retrying → Running   (وقتی که next_attempt_at بگذره و یه کارگر اونو مال خودش کنه)
```

وضعیتِ `Failed` (به عنوان یه وضعیت پایانیِ مستقل، متمایز از `DeadLetter`) برای جابی رزرو شده که رسماً و صریحاً توسط کاربر از طریق API کنسل شده — نه به عنوان بخشی از مسیرِ تلاشِ مجددِ اتوماتیک.

## پیامدها (Consequences)

- یه جاب هیچ‌وقت نمی‌تونه تو حالتِ "موفقیت‌آمیز اما منتظرِ تلاش مجدد" یا هر ترکیبِ بی‌معنیِ دیگه‌ای قرار بگیره — چون سیستمِ نوع‌ها (type) اصلاً اجازه ساخت همچین چیزی رو نمی‌ده.
- فیلدِ `next_attempt_at` تو حالتِ `Retrying` تایم‌استمپِ محاسبه‌شده با فرمول backoff رو مستقیماً رو خودِ وضعیت حمل می‌کنه، بنابراین پاسخ به سؤالِ "آیا یه کارگر باید الان اینو بردداره یا نه" کلاً یه مقایسه‌ی ساده و روشنه (`next_attempt_at <= now()`)، نه یه محاسبه‌ی مشتق‌شده که تو کل کدبیس پخش شده باشه.
- ذخیره کردنِ این enum تو Postgres یعنی انتخابِ یه روش سریالایز (TaskForge از یه ستونِ متنیِ `status` واسه نامِ تگ به علاوه‌یِ ستون‌هایِ نال‌پذیرِ `attempt`/`next_attempt_at`/`error` استفاده می‌کنه) — این تنها جاییه که تضمینِ "نبودِ حالت‌های بی‌معنی" به طور اتوماتیک توسط خودِ شِمای دیتابیس اجبار *نمی‌شه*، بلکه توسط تمام رایت‌هایی که از متدهای نوع‌بندی‌شده‌ی `JobStore` می‌گذرن تضمین می‌شه. یه ایده واسه توسعه: اجبار کردنِ این قضیه با یه شرطِ `CHECK` تو Postgres واسه لایه‌ی امنیتی بیشتر.
