# ADR-0002: دیتابیس PostgreSQL به عنوان بک‌اندِ صف برای نسخه ۱

## وضعیت (Status)
پذیرفته‌شده (Accepted)

## زمینه و کانتکست (Context)

یه صفِ وظایف (job queue) به یه جای باثبات و پایدار واسه ذخیره‌سازیِ وضعیت جاب‌ها نیاز داره و همینطور یه روشی که چندین پروسه‌ی کارگر (worker processes) بتونن با امنیت کامل کارهای جدید رو مالِ خودکنن (claim) بدون اینکه دو تا کارگر همزمان یه کارِ یکسان رو ران کنن. گزینه‌های "واقعی" و بدیهی واسه این کار: یه پیام‌رسانِ اختصاصی یا همون message broker (مثل RabbitMQ، Kafka، NATS — که تئوری‌هاشون تو درس `phase4-backend-advanced/03-background-jobs-and-message-queues/02-broker-concepts-rabbitmq-kafka-nats` بررسی شد)، یا همین دیتابیسِ رابطه‌ای که سیستم احتمالاً از قبل واسه بقیه‌ی بخش‌هاش داره استفاده می‌کنه.

## تصمیم (Decision)

استفاده از PostgreSQL، از طریقِ دستورِ `SELECT ... FOR UPDATE SKIP LOCKED` به عنوانِ بک‌اندِ صفِ TaskForge — دقیقاً همون الگویی که تو مقیاسِ کوچیک تو درس `phase4-backend-advanced/03-background-jobs-and-message-queues/01-postgres-skip-locked-toy-queue` تمرین شده بود، و حالا تو قالبِ یه سیستمِ واقعی توسعه داده شده.

دلایل این تصمیم:
- **سادگیِ عملیاتی (Operational simplicity).** اکثر سیستم‌های بک‌اند (از جمله تمام چیزایی که تو فاز 3 و 4 این دوره ساخته شد) همین الانشم دارن Postgres رو ران می‌کنن. اضافه کردنِ Kafka یا RabbitMQ به عنوان یه وابستگیِ سخت واسه صف جاب‌ها معنیش اینه که باید یه سیستمِ با وضعیتِ (stateful) دوم رو نگهداری و مدیریت کنی، اونم با حالت‌های شکستِ خاصِ خودش، مانیتورینگِ مجزا، و نیازمندِ دانشِ عملیاتیِ اختصاصی — که یه هزینه‌یِ واقعی محسوب می‌شه، نه یه چیز رایگان.
- **یکپارچگیِ تراکنشی (Transactional consistency).** استفاده از `SELECT ... FOR UPDATE SKIP LOCKED` داخلِ یه تراکنشی که همزمان کارهایِ رایتِ دیگه‌ی منطقِ برنامه رو هم انجام میده، بهت این قابلیت رو میده که "این جاب رو دقیقاً تو همون تراکنشی ثبت کنی (enqueue) که ردیفِ مربوط به اون کار ایجاد شده" بدون هیچ هزینه‌ی اضافه‌ای — چیزی که گرفتن اون با یه broker بیرونی بدون استفاده از الگوی outbox جداگانه واقعاً سخت و پیچیده‌ست.
- **توان خروجی (Throughput) کاملاً کافی واسه اکثر سیستم‌های واقعی.** صف‌های متصل به Postgres خیلی راحت و با خیال راحت هزاران جاب تو ثانیه رو روی سخت‌افزارهای معمولی پردازش می‌کنن — فراتر از این نقطه تازه استفاده از یه broker اختصاصی توجیه‌پذیر می‌شه، و مرزِ Traitِ `JobStore` (طبق ADR-0001) معنیش اینه که اون تغییر تو آینده صرفاً یه اضافه‌کردنه، نه یه بازنویسیِ کاملِ کدها.

## پیامدها (Consequences)

- **مثبت**: یک قطعه زیرساخت کمتر واسه اجرا/مدیریت/یادگیری تو نسخه ۱؛ تضمین‌های تراکنشی به صورت "مجانی"؛ استفاده‌ی مجددِ مستقیم از مهارت‌های sqlx/Postgres فاز 3 به جای معرفیِ یه کتابخونه‌ی کلاینتِ کاملاً جدید.
- **منفی**: دیتابیس Postgres کلاً واسه اینکه "صف" باشه *طراحی نشده بود* — مدلِ سرک کشیدن و چک کردن (polling - متد `claim_next` که تو فواصل زمانی توسط کارگرها صدا زده می‌شه) تاخیرِ واقعیِ بیشتری نسبت به مدلِ تحویلیِ مبتنی بر پوشِ (push-based) یه broker داره، و توان خروجیِ بسیار بالا (ده‌ها هزار جاب تو ثانیه به صورت مداوم) در نهایت نیازمندِ یه broker اختصاصی خواهد بود. این یه بده‌بستانِ کاملاً شفاف و مستندشده است، نه یه بی‌دقتی — عنوان همین سند رو ببرید: "واسه نسخه ۱."
- **محرکِ تجدید نظر (Revisit trigger)**: اگه پروژه TaskForge زمانی نیاز به تحویل تو چند دیتاسنتر مختلف، الگوی واقعیِ pub/sub بین چندین مصرف‌کننده‌ی مستقل، یا توان خروجیِ مداومی داشت که Postgres از پسش برنمی‌اومد، اون موقع سیگنالِ لازم واسه ساختنِ یه `KafkaJobStore` یا مشابه اون پشتِ همون Traitِ `JobStore` صادر می‌شه.
