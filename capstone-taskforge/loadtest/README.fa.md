# تست فشار و بارگذاریِ TaskForge

آخرین چیزی که بین "تست‌هاش پاس می‌شه" و "حاضرم اسممو پاش بذارم" قرار داره اینه که بدونی سیستم زیر فشار و ترافیک چطوری رفتار می‌کنه — و بتونی دقیقاً و به طور ملموس بگی برای اینکه ۱۰ برابر بزرگترش کنی چیا رو تغییر می‌دادی. این خروجیِ اصلیِ اینجاست: تست بارگذاری رو ران کن، عددها رو بخون، بعد تحلیلت رو بنویس.

## چیزایی که نیاز داری

- کُلِ پشته باید بالا باشه: از روتِ مخزن،
  دستورِ `docker compose -f capstone-taskforge/docker-compose.yml up --build` رو بزن.
  همه‌ی سرویس‌های `api`، `worker`، `scheduler` باید **سالم باشن و بالا بمونن** —
  اگه تو لوپِ کرش افتادن، معنیش اینه که هنوز تمرین‌های `src/main.rs` رو تموم نکردی.
- نصب بودنِ ابزارِ [k6](https://k6.io/docs/get-started/installation/)
  (`brew install k6` یا `choco install k6` یا ایمیج داکر `grafana/k6`).

## ران کردنش

```sh
# مقادیر پیش‌فرض: BASE_URL=http://localhost:8080, API_TOKEN=dev-token
k6 run capstone-taskforge/loadtest/load.js

# یا متصل کردنش به یه جا دیگه / استفاده از یه توکن متفاوت
BASE_URL=http://localhost:8080 API_TOKEN=dev-token \
  k6 run capstone-taskforge/loadtest/load.js
```

اسکریپت تعداد کاربران مجازی (VU) رو تو ~۲.۵ دقیقه از 0 → 20 → 50 میبره بالا، یه جابِ `send_email` ثبت می‌کنه و تو هر تکرار اونو بازخوانی می‌کنه. اگه از مرزهایِ (thresholds) تعیین‌شده تو `options` بگذره **فِیل می‌شه** (با کد خروجی غیرصفر): یعنی خطای درخواست‌ها بیشتر از 1% بشه یا تاخیر پکیج‌ها (p95) بالای 250 میلی‌ثانیه بره. وقتی خط‌پایه‌ی خودت رو شناختی اینا رو سخت‌تر یا شل‌تر کن — آستانه‌ای که هیچ‌وقت دستش نمی‌زنی آستانه‌ایه که درکش نکردی.

## به چی باید نگاه کنی

خلاصه‌ی پایانیِ k6 همون گزارشِ اصلیته. خطایی که مهمن:

- **`http_req_duration` p95 / p99** — تاخیرِ انتهایی (tail latency). میانگین دروغ می‌گه؛ تاخیرِ انتهایی همون چیزیه که کاربرِ واقعی حس می‌کنه. تغییرات p95 رو بین مرحله‌ی باثباتِ 20-VU و مرحله‌ی فشارِ 50-VU تماشا کن.
- **`http_req_failed`** — هر چیزی بالای صفر زیر این ترافیکِ ملایم معنیش اینه که یه جایی همین الانشم گلوگاه شده.
- **نرخ `iterations` / `http_reqs`** — توانِ خروجی (throughput). اونو با `WORKER_CONCURRENCY` و سقفِ پُولِ دیتابیس `(10)max_connections` مقایسه کن.
- **لاگ‌های کارگر** (`docker compose logs -f worker`) — آیا جاب‌ها به همون سرعتی که ثبت می‌کنی تخلیه می‌شن، یا صفِ `Pending` داره بزرگتر می‌شه؟ اینطوری کوئری بزن:
  `curl -H "Authorization: Bearer ***" localhost:8080/jobs | jq length`.

## گزارشِ تحلیلی (تحویل‌شدنیِ واقعی)

وقتی عددها رو به دست آوردی، به این سؤالات تو یه فایلِ کوتاه به اسم `SCALE.md` از طرف خودت جواب بده — این همون تحلیلِ "چیا رو تو مقیاس 10× عوض می‌کردم" هستش که پروژه‌ی پایانی می‌خواد. دقیق باش و هر جواب رو به چیزی که *مشاهده کردی* ربط بده، نه چیزی که خوندی:

1. **رقابت برای برداشتن جاب (job claiming) کجا رخ میده؟** استور جاب‌ها رو با `SELECT … FOR UPDATE SKIP LOCKED` می‌بره. با N تا حلقه‌ی کارگر و پُول ۱۰تایی دیتابیس، سقف واقعیِ برداشت تو ثانیه چقدره — قفل، پُول، یا تاخیر رفت‌وبرگشت Postgres؟ به کدومش اول خوردی؟
2. **وقتی بار رو می‌بری بالا چی اول اشباع می‌شه** — پُول کانکشن‌های API، مقدار `WORKER_CONCURRENCY`، یا CPU/IO دیتابیس Postgres؟ چطوری فقط از روی متریک‌ها از هم تفکیکشون می‌کنی؟
3. **تو نرخ ثبت ۱۰ برابر، چی اول می‌شکنه، و راه‌حلت چیه؟**
   (پُول بزرگتر؟ رپلیکاهای بیشترِ worker — و آیا طراحیِ `SKIP LOCKED` اجازه می‌ده فقط تعداد بیشتری ازشون ران کنی؟ پارتیشن‌بندیِ صف بر اساس `job_type`؟)
4. **آیا تو مقیاس ۱۰ برابر بازم Postgres رو نگه می‌داری؟** دقیقا همون نقطه‌ای رو نام ببر که می‌ری سراغ Redis / NATS / Kafka، و نشونه‌ی ملموسی که بهت میگه به اون نقطه رسیدی. (به ADR 0002 برگرد — آیا استدلال‌هاش هنوزم تو این مقیاس معتبره؟)
5. **چه تغییری مجبور شدی تو خودِ تستِ فشار بدی** تا به عدداش اعتماد کنی (warm-up، زمان فکر کردن، مدل باز در برابر بسته)؟ تست فشاری که بهش شک نکردی عددیه که نمی‌تونی ازش دفاع کنی.
