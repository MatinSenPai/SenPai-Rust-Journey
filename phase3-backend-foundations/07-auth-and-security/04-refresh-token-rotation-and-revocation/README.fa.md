# ۳.۷.۴ — چرخشِ refresh token و باطل‌سازیش

## در یک نگاه

بعد از این درس می‌توانی:

- توضیح بدهی چرا یک API هم یک توکنِ دسترسیِ کوتاه‌عمر می‌دهد و هم یک refresh tokenِ بلندعمر، و هر کدام به چه دردی می‌خورد.
- refresh tokenها را بچرخانی تا هر توکن فقط یک بار کار کند، و بگویی وقتی یک توکنِ مصرف‌شده دوباره پیدا می‌شود یعنی چه.
- از هر refresh token فقط هشِ SHA-256 را نگه داری، تا نشتِ دیتابیس نشتِ نشست‌هایِ زنده نباشد.
- یک نشست را (خروج) یا همه‌ی نشست‌هایِ یک کاربر را (خروج از همه‌جا) باطل کنی، و صادقانه بگویی باطل‌سازی چه چیزی را نمی‌تواند برگرداند.
- تابعِ `rotate` را با همه‌ی نتیجه‌هایش (جفتِ جدید، `Expired`، `Unknown`، `ReuseDetected`) بنویسی و بدونِ یک ثانیه صبر کردن تستش کنی.

**زمان:** حدود ۷۵ دقیقه · **پیش‌نیاز:**
[۳.۷.۳ — JWT و میان‌افزار در `tower`](../03-jwt-and-tower-middleware/README.fa.md)

## چرا اهمیت دارد

توکنِ دسترسیِ امضاشده، همان‌طور که در ۳.۷.۳ دیدی، یک ویژگیِ دردسرساز دارد: وقتی صادر شد، سرور نمی‌تواند پسش بگیرد. تا وقتی منقضی نشود معتبر است، چون بررسی‌اش به هیچ جست‌وجویی نیاز ندارد، و دلیلِ اصلیِ استفاده از آن همین است. اگر یک هفته عمر داشته باشد، نسخه‌ی دزدیده‌شده‌اش یک هفته کار می‌کند. اگر پانزده دقیقه عمر داشته باشد، کاربر ساعتی چهار بار باید دوباره وارد شود.

راهِ معمول دو توکن است. یک **توکنِ دسترسی (access token)** کوتاه‌عمر روی هر درخواست می‌رود. یک **refresh token** بلندعمر کم استفاده می‌شود، فقط برایِ گرفتنِ توکنِ دسترسیِ تازه. کوکیِ نشستِ جنگو هر دو کار را با هم می‌کرد، و سرور می‌توانست ردیفِ نشست را پاک کند تا تو را بیرون بیندازد. اینجا refresh token کلیدِ همان ردیف است: یک جست‌وجو که دستِ سرور است، پس جایی است که نشست را می‌شود تمام کرد.

ولی یک رازِ بلندعمر که در گوشی یا مرورگر می‌نشیند دقیقاً همان چیزی است که مهاجم می‌خواهد. این درس درباره‌ی این است که سوءاستفاده از آن راز را سخت کنیم: هر توکن فقط یک بار کار می‌کند، تکرارِ آن دزدی حساب می‌شود، و سرور خودِ توکن را هیچ‌وقت ذخیره نمی‌کند. راهنمایِ نشستِ OWASP و رویه‌ی برتر امنیتیِ OAuth 2.0 هر دو همین ایده را توصیف می‌کنند، به اسمِ چرخشِ refresh token. تو آن را در حافظه می‌سازی، بدونِ دیتابیس.

## مفهوم

### دو توکن، دو کار

| | توکنِ دسترسی | refresh token |
|---|---|---|
| فرستاده می‌شود برای | هر درخواستِ API | فقط نقطه‌ی تازه‌سازی |
| عمر | کوتاه (اینجا ۱۵ دقیقه) | بلند (اینجا ۷ روز) |
| بررسی با | امضایش، بدونِ جست‌وجو | جست‌وجو در انبارِ سرور |
| سرور می‌تواند باطلش کند؟ | نه، تا وقتی منقضی نشده | بله، رکوردش را پاک می‌کند |

در این درس توکنِ دسترسی یک رشته‌ی جایگزین است، `access.<user_id>.<expires_at>`؛ ۳.۷.۳ نشان داد چطور آن را یک توکنِ امضاشده‌ی واقعی کنی، و هیچ‌چیزِ اینجا به این تفاوت بستگی ندارد. چیزِ جالب refresh token و انبارِ پشتِ آن است.

### چرخش: هر refresh token یک بار کار می‌کند

refresh token یک‌بارمصرف است. وقتی کلاینت یکی را می‌فرستد، سرور آن را **مصرف‌شده (used)** علامت می‌زند و یک جفتِ *تازه* پس می‌دهد، شاملِ یک refresh tokenِ کاملاً نو. کلاینت قدیمی را دور می‌اندازد. بعد از چند دور، انبار زنجیره‌ای از توکن‌ها دارد که همه جز آخری مصرف‌شده‌اند:

```senpai-visual
{"kind":"concept","labels":["ورود: توکنِ A صادر می‌شود","تازه‌سازی با A: A مصرف‌شده، توکنِ B صادر می‌شود","تازه‌سازی با B: B مصرف‌شده، توکنِ C صادر می‌شود","فقط C هنوز قابلِ استفاده است","A و B و C یک خانواده‌اند"]}
```

`examples/01-login-and-rotate.rs` این را اجرا می‌کند. refresh tokenها تصادفی‌اند، پس مال تو فرق دارد؛ توکنِ دسترسی قطعی است چون ساعت یک `ManualClock` است که مثال با دست جلو می‌برد:

```text
login   access=access.matin.1700000900
        refresh=c19ea5a230d24616
rotate1 access=access.matin.1700001500
        refresh=bda069e2c1904fd4
rotate2 access=access.matin.1700002100
        refresh=21f110143ad1435f
rotate3 access=access.matin.1700002700
        refresh=18968df2fd994054
records stored: 4
hash of newest: 0c88bc768479d8f5
```

یک ورود به‌علاوه‌ی سه چرخش چهار رکورد می‌شود: قدیمی‌ها نگه داشته می‌شوند و مصرف‌شده علامت می‌خورند، و این عمدی است. بخشِ بعد می‌گوید چرا.

### تشخیصِ استفاده‌ی دوباره: بازگشتِ توکنِ قدیمی یعنی دزدی

فکر کن بعد از اینکه کلاینتِ واقعی توکنِ A را به B چرخاند، چه کسی هنوز می‌تواند A را در دست داشته باشد. فقط کسی که قبلاً از آن کپی گرفته: یک دزد. کلاینتِ واقعی دیگر آن را ندارد. پس وقتی یک توکنِ *مصرف‌شده* ارائه می‌شود، سرور نمی‌تواند دزد را از قربانی تشخیص بدهد، ولی می‌داند یکی از دو طرف کلاینتِ واقعی نیست. پاسخِ امن این است که به کلِ **خانواده** (همه‌ی توکن‌هایی که از یک ورود می‌آیند) اعتماد نکنی و همه را مجبور به ورودِ دوباره کنی.

```senpai-visual
{"kind":"concept","labels":["دزد از توکنِ A کپی می‌گیرد","کلاینتِ واقعی A را به B می‌چرخاند","دزد A را ارائه می‌کند: قبلاً مصرف شده","سرور کلِ خانواده را باطل می‌کند","B کلاینتِ واقعی هم مرده است: ورودِ دوباره"]}
```

`examples/02-reuse-detection.rs`:

```text
client rotated, records: 2
thief replays old token:  Err(ReuseDetected)
records after the replay: 0
client's newest token:    Err(Unknown)
```

دزد باخت، ولی کلاینتِ درست‌کار هم باخت: توکنِ تازه‌اش هم رفت. این بهایش است. دلیلِ اینکه رکوردهای مصرف‌شده باید در انبار بمانند هم همین است: اگر رکورد پاک شده بود، توکنِ تکراری فقط `Unknown` به نظر می‌آمد و سرور تکرار را از آشغال تشخیص نمی‌داد.

### هش را نگه دار، نه توکن را

انبارِ refresh token را جدولی فرض کن که روزی کسی از آن دامپ می‌گیرد. اگر خودِ توکن‌ها در آن باشند، دامپ یک انبوه نشستِ زنده است. پس انبار `hash_token(token)` را نگه می‌دارد، یعنی SHA-256 به شکلِ hex با حروفِ کوچک، و سرور هر چه کلاینت می‌فرستد را اول هش می‌کند و بعد جست‌وجو. `examples/03-what-a-leak-shows.rs` نقشِ مهاجمی را بازی می‌کند که یک کپی از انبار دارد (مقدارها تصادفی‌اند و هر اجرا فرق می‌کنند):

```text
leaked rows:     1
leaked value:    5a524203b1b10f931aad0641a20e488e3e5675a791c42cfa4eb892750bc8c0fc
real token:      ef7443cb876f408d9e72318f917e4dcfd2cd08947247402998a2d0870d9513e2
leak == token?   false
hash of token:   true
replay the hash: Err(Unknown)
```

مقدارِ نشت‌کرده به عنوانِ توکن به دردی نمی‌خورد: دوباره هش شدنش مقدارِ دیگری می‌دهد که در انبار نیست. ۳.۷.۱ گفت رمزعبور را با یک تابعِ عمداً کند هش کن. refresh token به چنین چیزی نیاز ندارد. ۶۴ کاراکترِ hexِ تصادفی است، یعنی ۲۵۶ بیت، پس چیزی برایِ حدس زدن نیست و یک هشِ سریع کافی است. رمزعبور کوتاه است و آدم انتخابش می‌کند، برای همین آن یکی هشِ کند می‌خواهد.

### خروج یعنی پاک کردنِ یک خانواده

خروج نیمه‌ی دیگرِ باطل‌سازی است: این بار کاربر است نه دزد که نشست را تمام می‌کند. سرور خانواده‌ی توکنِ ارائه‌شده را پاک می‌کند، پس حتی تازه‌ترین توکن هم از کار می‌افتد. `logout_all(user)` همه‌ی خانواده‌هایِ یک کاربر را پاک می‌کند، یکی برایِ هر دستگاه. چیزی که باطل‌سازی نمی‌تواند برگرداند توکنِ دسترسیِ صادرشده است: تا منقضی شدن معتبر می‌ماند، اینجا حداکثر پانزده دقیقه. کوتاه‌کردنِ این پنجره، یا نگه‌داشتنِ فهرستِ سیاه از توکن‌هایِ دسترسی، مبادله‌ای است که با جست‌وجو می‌پردازی، و دلیلِ اینکه باطل‌کردنِ refresh token ارزشش را دارد همین است.

### زمان تزریق می‌شود

`rotate` باید بپرسد توکن منقضی شده یا نه. اگر مستقیم ساعتِ سیستم را صدا می‌زد، تستِ انقضایِ هفت‌روزه باید هفت روز صبر می‌کرد. پس سرویس نسبت به یک صفتِ (Trait) کوچکِ `Clock` با `now() -> u64` جنریک است. در تولید `SystemClock` و در تست `ManualClock` استفاده می‌شود که `advance(seconds)` آن آنی جلو می‌پرد. کلون‌هایِ `ManualClock` یک شمارنده را به اشتراک می‌گذارند، پس تست یکی را نگه می‌دارد و دیگری را به سرویس می‌دهد.

```senpai-visual
{"kind":"result","labels":["rotate(presented)","توکن را هش کن و جست‌وجو کن","پیدا نشد: Unknown","قبلاً مصرف شده: خانواده باطل، ReuseDetected","منقضی: Expired","معتبر: مصرف‌شده علامت بزن، Ok جفتِ جدید"]}
```

**کامپایلر به چه اعتراض دارد:** `save_to_cookie` یک `String` را by value می‌گیرد، پس دادنِ `pair.refresh_token` توکن را از `pair` بیرون می‌کشد (move). خطِ بعد مقداری را قرض می‌گیرد که دیگر آنجا نیست.

**راهِ درست:** بگذار تابع قرض بگیرد:

```rust
fn save_to_cookie(token: &str) { /* write the cookie */ }
save_to_cookie(&pair.refresh_token);
```

**چرا این راهِ درست است:** نویسنده‌ی کوکی فقط باید توکن را بخواند. قرض‌گرفتن صاحبش را سالم می‌گذارد، و `&` در محلِ فراخوانی به خواننده می‌گوید نسخه‌ی دومی از راز ساخته نشده.

### پانیکِ زمانِ اجرا: `unwrap` رویِ چرخشی که رد شد

```text
thread 'main' (22032) panicked at phase3-backend-foundations\07-auth-and-security\04-refresh-token-rotation-and-revocation\examples\05-unwrap-on-reuse-broken.rs:14:50:
called `Result::unwrap()` on an `Err` value: ReuseDetected
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
error: process didn't exit successfully: `target\debug\examples\05-unwrap-on-reuse-broken.exe` (exit code: 101)
```

(عددِ داخلِ پرانتز شناسه‌ی ریسمان است و هر اجرا عوض می‌شود.)

**واقعاً چه چیزی خراب است:** `rotate` مقدارِ `Err(ReuseDetected)` برگرداند و مثال رویش `.unwrap()` زد. چرخشِ ردشده باگِ برنامه‌ی تو نیست؛ یک پاسخِ عادی است، و اغلب جالب‌ترینش. از کار انداختنِ هندلر یک نشانه‌ی امنیتی را به خطای ۵۰۰ تبدیل می‌کند.

**راهِ درست:** رویِ خطا `match` بزن و هر حالت را عمداً جواب بده:

```rust
match svc.rotate(&token) {
    Ok(pair) => println!("new pair: {pair:?}"),
    Err(RefreshError::ReuseDetected) => println!("log this: possible theft"),
    Err(other) => println!("log in again: {other:?}"),
}
```

**چرا این راهِ درست است:** برایِ کلاینت همه‌ی خطاها به «دوباره وارد شو» ختم می‌شوند، ولی سرور می‌تواند با `ReuseDetected` جور دیگری رفتار کند، چون تنها خطایی است که بویِ حمله می‌دهد.

### هیچ خطایی نیست: `rotate`ای که توکن را مصرف‌شده علامت نمی‌زند

```text
client rotates: Some("token-2")
thief replays:  Some("token-3")  (should have been refused)
```

**واقعاً چه چیزی خراب است:** `examples/06-never-marks-used-trap.rs` کامپایل و اجرا می‌شود و هر فراخوانی یک `Some`ِ باورپذیر برمی‌گرداند. `rotate`ِ آن توکنِ تازه می‌دهد ولی قدیمی را معتبر می‌گذارد. آن‌وقت چرخش فقط انبار را بزرگ‌تر می‌کند؛ توکنِ دزدیده‌شده هر قدر دزد بخواهد کار می‌کند و کسی خبردار نمی‌شود.

**راهِ درست:** وقتی توکنِ تازه صادر می‌شود، حالتِ رکوردِ قدیمی را عوض کن: مصرف‌شده علامتش بزن (یا پاکش کن)، تا ارائه‌ی بعدی به عنوانِ تکرار شناخته شود.

**چرا این راهِ درست است:** قول این است که «هر توکن یک بار کار می‌کند»، و هیچ‌چیز در تایپ‌ها آن را تضمین نمی‌کند. فقط تستی که یک توکن را دو بار ارائه می‌کند و انتظار دارد بار دوم رد شود این کار را می‌کند، و تست‌هایِ این درس دقیقاً همین را می‌کنند.

### تعمیر

هر سه مثالِ خراب را درست کن:

1. `examples/04-token-moved-broken.rs` بدونِ کلون‌کردنِ توکن کامپایل شود.
2. `examples/05-unwrap-on-reuse-broken.rs` به جایِ پانیک، نتیجه‌ی چرخشِ دوم را چاپ کند.
3. `examples/06-never-marks-used-trap.rs` تکرارِ دزد را رد کند: دومین `rotate` رویِ همان توکن `None` برگرداند.

### پیاده‌سازی

دو تابع در `src/lib.rs`. هر کدام در کامنتِ مستندش کامل مشخص شده، پس هیچ‌وقت لازم نیست تست‌ها را باز کنی:

```sh
cargo test -p p3-07-04-refresh-token-rotation-and-revocation
```

- `hash_token`: SHA-256ِ توکن به شکلِ hex با حروفِ کوچک، ۶۴ کاراکتر. `sha2::{Digest, Sha256}` در اسکلت import نشده، پس `use` را خودت اضافه کن.
- `rotate`: چهار نتیجه به ترتیب: `Unknown`، بعد `ReuseDetected` (خانواده باطل)، بعد `Expired`، بعد جفتِ تازه برایِ همان کاربر و همان خانواده.

### بساز

`logout` و `logout_all` در همان فایل. `logout` با گرفتنِ یکی از توکن‌هایِ یک خانواده، کلِ آن را پاک می‌کند و می‌گوید توکن شناخته‌شده بود یا نه. `logout_all` همه‌ی خانواده‌هایِ یک کاربر را پاک می‌کند و تعدادِ خانواده‌ها را می‌شمارد.

### چالش (اختیاری)

چرخشِ سخت‌گیرانه تلاشِ دوباره‌ی درست‌کار را هم تنبیه می‌کند. سیستم‌هایِ واقعی یک **پنجره‌ی مهلت (grace window)** کوتاه اضافه می‌کنند: توکنِ مصرف‌شده‌ای که ظرفِ مثلاً ۱۰ ثانیه بعد از چرخشش دوباره ارائه شود، بدونِ باطل‌کردنِ خانواده رد می‌شود. یک زمانِ `used_at` به رکورد و یک ثابتِ `GRACE_SECONDS` اضافه کن و تست‌ها را با `ManualClock` بنویس. تصمیم بگیر استفاده‌ی دوباره داخلِ پنجره چه برگرداند، و آن تصمیم را در کامنتِ مستند بنویس.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا استفاده‌اش می‌کنی |
|---|---|---|
| توکنِ دسترسی (access token) | اعتبارنامه‌ی کوتاه‌عمر که با هر درخواست می‌رود | هر فراخوانیِ احرازشده‌ی API |
| refresh token | اعتبارنامه‌ی بلندعمر و یک‌بارمصرف برایِ گرفتنِ جفتِ تازه | نقطه‌ی تازه‌سازی |
| چرخش (rotation) | صادرکردنِ refresh tokenِ نو در هر تازه‌سازی و بازنشسته‌کردنِ قدیمی | محدودکردنِ عمرِ توکنِ دزدیده‌شده |
| خانواده‌ی توکن (token family) | همه‌ی refresh tokenهایِ برآمده از یک ورود | باطل‌کردنِ یک نشست یکجا |
| تشخیصِ استفاده‌ی دوباره (reuse detection) | دزدی حساب‌کردنِ بازگشتِ توکنِ مصرف‌شده و باطل‌کردنِ خانواده‌اش | نتیجه‌ی `ReuseDetected` |
| باطل‌سازی (revocation) | تمام‌کردنِ یک نشست از سمتِ سرور | خروج، خروج از همه‌جا، واکنش به دزدی |
| ساعتِ تزریق‌شده (injectable clock) | زمان به شکلِ مقدار داده می‌شود تا تست کنترلش کند | هر کدی که انقضا را می‌سنجد |

### الان می‌دانی

- توکن‌های دسترسی ارزان بررسی می‌شوند و پس‌گرفتنی نیستند؛ refresh tokenها با انبار سنجیده می‌شوند و پس باطل‌شدنی‌اند.
- چرخش هر refresh token را یک‌بارمصرف می‌کند، و این تکرار را به یک رویدادِ قابل‌تشخیص تبدیل می‌کند.
- استفاده‌ی دوباره از توکنِ مصرف‌شده کلِ خانواده‌اش را باطل می‌کند، و کلاینتِ درست‌کار با یک ورودِ تازه بهایش را می‌دهد.
- انباری که فقط هش‌هایِ SHA-256ِ توکن‌هایِ پرانتروپی را نگه می‌دارد چیزی نشت نمی‌دهد که دزد بتواند ارائه کند.
- خروج یک خانواده را پاک می‌کند؛ `logout_all` همه‌ی خانواده‌هایِ یک کاربر را؛ هیچ‌کدام توکنِ دسترسیِ صادرشده را پس نمی‌گیرند.
- یک `Clock`ِ تزریق‌شده اجازه می‌دهد انقضایِ هفت‌روزه در چند میکروثانیه تست شود.

### می‌توانی توضیح بدهی؟

- چرا سرور نمی‌تواند توکنِ دسترسی را باطل کند ولی refresh token را می‌تواند؟
- چرا refresh tokenهایِ مصرف‌شده باید در انبار بمانند و پاک نشوند؟
- چرا توکنِ تکراری کلِ خانواده را باطل می‌کند، حتی تازه‌ترین توکن را؟
- چرا برایِ refresh token همین SHA-256 کافی است ولی رمزعبور هشِ کند می‌خواهد؟
- چرا `rotate` «قبلاً مصرف شده» را قبل از «منقضی» بررسی می‌کند؟
