# راه‌حل

```rust
pub fn parse(token: &str) -> Method {
    match token {
        "GET" => Method::Get,
        "POST" => Method::Post,
        "PUT" => Method::Put,
        "DELETE" => Method::Delete,
        "HEAD" => Method::Head,
        other => Method::Other(other.to_string()),
    }
}
```

این فقط یه بلوکِ `match` خیلی ساده روی مقادیرِ ثابت متنی (literal `str&`) هستش — بازویِ `((Other(other.to_string` نقشِ همون بازوی همه‌گیر (catch-all) رو بازی می‌کنه، در نتیجه این تابع هرگز نمی‌تونه با شکست مواجه بشه (fail کنه)؛ یه فِعل (verb) ناشناخته هنوز هم یه داده‌ی *معتبر و مجاز* محسوب می‌شه، فقط جزء اون متدهای معروف و اسم‌داری که تعریف کردیم نیست.

```rust
pub fn header(&self, name: &str) -> Option<&str> {
    self.headers
        .iter()
        .find(|(k, _)| k.eq_ignore_ascii_case(name))
        .map(|(_, v)| v.as_str())
}
```

متدِ `()find.` به محض اینکه اولین تطبیق رو (با ویژگی case-insensitive و بدون حساسیت به حروف کوچیک و بزرگ) پیدا می‌کنه، فوراً حلقه رو متوقف می‌کنه (short-circuits) و متدِ `()map.` اون جفتِ مچ‌شده (pair) رو می‌گیره و فقط بخش مقدارش (value) رو بیرون می‌کشه، اونم به شکل قرضی (`str&`) نه به شکل یه نسخه‌ی کپی‌شده (cloned) — فراخواننده‌ی تابع واسه اینکه بتونه یه هدر رو بخونه، اصلاً نیازی به گرفتن مالکیتِ (ownership) اون نداره.

```rust
pub fn parse_request(raw: &[u8]) -> Result<HttpRequest, HttpParseError> {
    let text = std::str::from_utf8(raw).map_err(|_| HttpParseError::InvalidUtf8)?;
    if text.is_empty() {
        return Err(HttpParseError::EmptyRequest);
    }

    let mut lines = text.split("\r\n");
    let request_line = lines.next().ok_or(HttpParseError::EmptyRequest)?;

    let mut parts = request_line.split(' ');
    let (method_token, target, version) =
        match (parts.next(), parts.next(), parts.next(), parts.next()) {
            (Some(method), Some(target), Some(version), None) => (method, target, version),
            _ => return Err(HttpParseError::MalformedRequestLine(request_line.to_string())),
        };

    let method = Method::parse(method_token);
    let (path, query) = match target.split_once('?') {
        Some((path, query)) => (path.to_string(), Some(query.to_string())),
        None => (target.to_string(), None),
    };

    let mut headers = Vec::new();
    for line in lines {
        if line.is_empty() {
            break;
        }
        let (name, value) = line
            .split_once(':')
            .ok_or_else(|| HttpParseError::MalformedHeaderLine(line.to_string()))?;
        headers.push((name.trim().to_string(), value.trim().to_string()));
    }

    Ok(HttpRequest { method, path, query, version: version.to_string(), headers })
}
```

اینجا با یه سری انتخاب‌های کاملاً عمدی روبه‌رو هستیم:

- **خالی بودن متن (`()text.is_empty`)، *قبل از* تکه‌تیکه کردن متن (splitting) چک شده**، نه بعدش. عبارت `("")split("\r\n.")` در کمال تعجب یه دونه آیتم تولید می‌کنه — یعنی یه رشته‌ی کاملاً خالی — بنابراین اگه این چکِ اولیه انجام نمی‌شد، متدِ `()lines.next` مقدار `("")Some` رو به جای `None` برمی‌گردوند، و اون خط درخواست به جای اینکه اون ارورِ دقیق‌تر و متناسبِ `EmptyRequest` رو که تست‌ها انتظار دارن برگردونه، با یه خطای عمومی‌تر مثل `(("".to_string)MalformedRequestLine)` روبرو می‌شد.
- **خط درخواست (request line) در قالب یه توپل 4-تایی از نوع `Option` مچ می‌شه**، که دقیقاً فرمتِ `(Some, Some, Some, None)` رو اجبار می‌کنه. اون `None`ِ چهارمی دقیقاً هم‌وزنِ اون سه تا `Some` قبلی ارزش و اهمیت داره: اگه اون نبود، خطی مثلِ `"GET / HTTP/1.1 extra-garbage"` (که چهار تا کلمه داره که با فاصله از هم جدا شدن) کاملاً بی‌سروصدا و طوری که انگار اون کلمه‌ی چهارم اصلاً وجود نداشته پارس می‌شد. اجبار کردنِ اینکه *چهارمین* فراخوانیِ `()next.` باید حتماً برابر با `None` باشه، دقیقاً همون چیزیه که قانونِ "دقیقاً و فقط ۳ تا توکن، نه یه دونه بیشتر، نه یه دونه کمتر" رو تحمیل و تضمین می‌کنه.
- **متد `('?')target.split_once`** متن رو فقط و فقط بر اساس *اولین* علامت `?` تیکه می‌کنه — چون خودِ رشته‌های کوئری (query string) هم از لحاظ قانونی می‌تونن تو دلِ خودشون کاراکتر `?` داشته باشن (معمولاً اونایی که به فرمت URL درکد شدن (URL-encoded))، پس تکه‌تیکه کردن (splitting) بر اساس اولین برخورد به جای آخرین برخورد (یا تکه‌تیکه کردن کل متن از دم با هر علامتی که دید) تنها انتخابِ درسته.
- **متد `(':')line.split_once`**، و نه به شکلِ `(" :")split_once`. دنیای واقعیِ HTTP کاملاً اجازه میده (و کلاینت‌ها هم بعضی وقتا همین کارو می‌کنن) که یه دونقطه با هیچ فاصله‌ای جلوش ارسال بشه، یا حتی یه عالمه فاصله‌ی خالی قبل از رسیدن به مقدارِ هدر وجود داشته باشه — تکه‌تیکه کردن صرفاً بر اساسِ کاراکترِ `:` و بعد از اون `()trim.` کردنِ جفتِ سمت‌هاش، تک‌تک این حالت‌ها رو به صورتِ یک‌دست پوشش می‌ده به جای اینکه از اول فرض رو بر این بذاره که همیشه بین اسم و مقدار دقیقاً همون فرمتِ ۲ کاراکتریه `": "` وجود داره.

```rust
pub fn to_bytes(&self) -> Vec<u8> {
    let mut out = format!("HTTP/1.1 {} {}\r\n", self.status, self.reason);
    for (name, value) in &self.headers {
        out.push_str(&format!("{name}: {value}\r\n"));
    }
    out.push_str(&format!("Content-Length: {}\r\n", self.body.len()));
    out.push_str("\r\n");
    out.push_str(&self.body);
    out.into_bytes()
}
```

پاسخ رو تو قالب یه `String` سرهم می‌کنه (که از نظر منطقی برای خط به خط پیش رفتن خیلی راحت‌تره) و در نهایت، فقط تو همون گامِ آخر با استفاده از متد `()into_bytes.` تبدیلش می‌کنه به یه `Vec<u8>` — این کار به شدت کم‌هزینه و ارزونه، چون یه نوع `String` تو زبان Rust تو لایه‌های زیرینش از قبل یه سری بایتِ معتبر از نوع UTF-8 هستش و در نتیجه به هیچ پروسه‌یِ تبدیلِ رمزگذاریِ (re-encoding) دوباره‌ای نیاز نداره.

## در مورد سؤالات چک‌پوینت

**سؤال ۱ (نادیده گرفتن اعتبارسنجیِ UTF-8):** استفاده از متدِ `str::from_utf8` فقط یه تشریفاتِ الکی نیست — تو زبان Rust، یه نوع `[u8]&` که ذاتا یه UTF-8ِ معتبر نباشه، واقعاً نمی‌تونه به هیچ وجهی باهاش مثلِ یه `str&` رفتار بشه؛ تک‌تکِ متدهایِ مربوط به `str&` (مثل `trim.` ،`split.`، ایندکس گرفتن بر اساسِ بازه‌ی بایت‌ها) همگی رو این اصل استوارن که این بایت‌ها یه UTF-8 کاملاً معتبرن، و اگه با استفاده از کلمه‌ی `unsafe` این قانون رو زیر پا بذاری، درجا مرتکبِ یه رفتارِ تعریف‌نشده (undefined behavior) می‌شی. رد شدن و جا انداختنِ این بررسی، و استفاده از جایگزینِ `from_utf8_unchecked` (که تنها راه واسه دور زدن چک کردن و در عین حال گرفتنِ یه `str&` هست) تو دنیای واقعی رسماً یه باگ امنیتی خفن به حساب میاد: یه کلاینت می‌تونه با فرستادنِ بایت‌هایِ ناقص و خراب (malformed)، باعث پنیک (panic) شدن سرور بشه، کاری کنه داده‌های بی‌ربط (garbage) خونده بشن، یا حتی بدتر از اینا. دقیقاً به همین دلیله که سیستمِ نوع‌ها (type system) مجبورت می‌کنه که قبل از اینکه حتی یه بایت از کُدهای مربوط به منطقِ متنی (text logic) رو اجرا کنی، اول بری و با اون `Result` تسویه‌حساب کنی.

**سؤال ۲ (گونه‌های خطای اختصاصی و مشخص):** عبارتِ `(assert!(matches!(result, Err(HttpParseError::MalformedRequestLine(_))))` دقیقاً ثابت می‌کنه که پارسرِ ما تونسته با دقت تشخیص بده که *دقیقاً کدوم مرحله* از کار به مشکل خورده. اگه فقط یه گونه‌ی واحدِ `ParseFailed` وجود داشت، این بررسی و ادعا — و بالطبع کارِ هر فراخواننده‌ی واقعی دیگه‌ای که می‌خواست تصمیم بگیره که "آیا الان باید یه ارور 400 با یه پیام راهگشا برگردونم، یا این مشکل کلاً یه جنسِ باگِ دیگه‌ایه؟" — هیچ راهی برای تشخیص و تمایزِ بین "خط درخواست تعداد توکن‌هاش اشتباهه" با "یه خط هدر اصلاً دونقطه توش نداره" یا "اینا اصلاً هیچکدومشون UTF-8 نبودن" نمی‌داشت. داشتنِ گونه‌های اسم‌گذاری‌شده و جداگانه (Named variants)، کارِ دیباگ کردن (و تو یه سرور واقعی، کار ساختنِ یه پاسخِ ارور مفید و به درد بخور) رو از یه فرآیندِ مبتنی بر چک کردن متون خام و بی‌قاعده (string-matching)، تبدیل می‌کنه به یه فرآیندِ تطبیق الگو (pattern matching) که هم جامع‌ومانعه و هم کامپایلر روش نظارت کامل داره.

**سؤال ۳ (چرا همون اول کار حروف رو کوچیک نکنیم):** کوچیک کردن (lowercasing) همه حروف همون اولِ پروسه‌ی پارس شدن از نظر عملکردی کار می‌کنه و جواب می‌ده، اما در واقع داره بدون هیچ دلیلِ موجهی دیتایِ ما رو دور می‌ریزه: فیلدِ `headers` وظیفه‌اش اینه که دقیقاً همون چیزی که کلاینت *تو واقعیت و به صورتِ بایت‌به‌بایت فرستاده بود* رو تو خودش ذخیره کنه، و این موضوع تو وقتایی که یه زمانی نیاز داشته باشی درخواست خام رو لاگ (log) کنی، درخواست رو دوباره عیناً و مو به مو همون‌طور که بود سریالایز (re-serialize) کنی (مثل وقتایی که یه پراکسی داره درخواست رو واسه یکی دیگه فوروارد می‌کنه)، یا وقتایی که بخوای یه کلاینت رو دیباگ کنی که داره با یه مدل حروف‌گذاری (casing) عجیب و نامتعارف داده‌ها رو می‌فرسته، به شدت حیاتی و مهم می‌شه. جستجوی یه هدر *تنها و تنها* جاییه که طبق مشخصاتِ HTTP، کوچیک یا بزرگ بودن حروف اصلاً اهمیتی نداره، پس اون نقطه، *تنها و تنها* جاییه که اون هزینه‌ی مربوط به چک کردن با `eq_ignore_ascii_case` رو به جون می‌خره — و اونم تازه فقط و فقط زمانی اجرا می‌شه که یه نفر واقعاً متد `(...)header.` رو صدا زده باشه، نه اینکه بخواد بدونِ توجه به اینکه آیا اصلاً قراره کسی رو این هدر جستجو کنه یا نه، واسه تک‌تکِ هدرها و تو هر دفعه پارس شدن این هزینه‌ی الکی رو پرداخت کنه.

**سؤال ۴ (تعداد بایت در برابر تعداد کاراکتر):** مقدارِ `()len."café"` برابر با `5` هست (چرا که اون کاراکترِ `é` تو یونیکدِ UTF-8 دو بایت جا می‌گیره) در حالی که مقدارِ `()chars().count."café"` دقیقاً برابر با `4` هستش. یه کلاینت که داره پاسخ (response) رو می‌خونه، برای اینکه بفهمه بدنه‌ی (body) جواب کی تموم می‌شه، دقیقاً به تعداد همون بایت‌هایی که تو `Content-Length` براش تعیین شده، از روی جریانِ اتصالی (TCP stream) **بایت‌ها** رو می‌خونه — اون کلاینت تو اون نقطه اصلاً هیچ راهی نداره که از قبل بفهمه مرزِ بین کاراکترها (encoding boundaries) کجاست و چطوریه. اگه تو متدِ `to_bytes` برای یه بدنه که شامل یه کاراکتری مثلِ `é` می‌شد، به جای `()len.` از `()chars().count.` استفاده می‌کردیم، اون‌وقت سرور میومد تو هدرها اعلام می‌کرد که طول بدنه `4` هست اما موقع ارسال بدنه تو واقعیت `5` بایت اطلاعات می‌نوشت روی شبکه، و اونوقت هر کلاینتی که دقیقاً و با طنابِ سرور می‌رفت تو چاه و فقط 4 بایت می‌خوند، با یه بدنه‌ی قطع‌شده و نصفه‌نیمه روبه‌رو می‌شد، و تازه اون یه بایتِ آواره و جا مونده که تو سیم گیر کرده بود، واسه درخواستِ *بعدی* (اگه اتصالِ مربوطه از همون سوکتِ قبلی (reuse) استفاده می‌کرد) به صورت اشتباهی خونده می‌شد و کلاً همه‌چیز رو به هم می‌ریخت. متدِ `()len.` (یعنی شمارشِ طول بایت‌ها) تنها و تنها مقداریه که کاملاً و مو به مو با اون بایت‌های خامی که در نهایت نوشته می‌شن رو سوکت، تطابق داره.

**سؤال ۵ (تبدیل یه رشته‌ی کوئریِ خام به یه چیزی شبیه DRF):** برای این کار باید اون رشته‌یِ خام رو بر اساس علامت `&` تکه‌تیکه کنی (split) تا یه سری جفت‌هایِ منفرد و تکیِ `key=value` به دست بیاری، بعدش باید هرکدوم از اون جفت‌ها رو باز بر اساسِ اولین علامت `=` تیکه کنی (دقیقاً مشابهِ منطقِ `(':')split_once` که بالاتر توضیحش دادیم، چون ممکنه یه مقدارِ URL-encoded تو دلِ خودش علامت `=` هم داشته باشه)، بعدِ این کار باید هر کلمه و مقدار رو با استانداردهای مربوط به URL، *دی‌کُد (URL-decode)* کنی (مثلاً `%20` رو تبدیل کنی به جای خالی (space)، یا تو یه سری ساختارها علامتِ `+` رو بکنی جای خالی، یا `%3D` رو بکنی `=` و الی آخر — تو این درس و تو تابعِ `parse_request` به صورت کاملاً آگاهانه و عمدی، واسه اینکه این درس کلاً فوکوسش روی مبحث پارس‌کردنِ متن‌های خط‌محور بمونه اصلاً سراغ این کارا نرفته)، و تو قدم آخر، تمام این جفت‌ها رو در قالب یه چیزی شبیه `<HashMap<String, String>` جمع‌آوری و ذخیره کنی (یا اگه یه کلیدی این حقِ قانونی رو داشت که بخواد چند بار تکرار بشه، مثلاً تو چیزی مثلِ `tag=b&tag=a?`، باید از یه `<Vec<(String, String>` استفاده کنی، چون یه `HashMap`ِ ساده، بی‌سروصدا کپی‌ها رو می‌ریخت دور و فقط یکی‌شونو نگه می‌داشت).
