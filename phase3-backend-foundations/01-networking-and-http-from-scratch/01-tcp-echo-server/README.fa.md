# ۳.۱.۱ — سرورِ اکویِ TCP (TCP echo server)

## در یک نگاه

بعد از این درس می‌توانی:

- توضیح بدهی چرا یک اتصالِ TCP فقط ترتیب و رسیدنِ کاملِ بایت‌ها را تضمین می‌کند، نه مرزِ نوشتن‌ها را، و این را با چشمِ خودت رویِ یک سوکتِ واقعی ببینی: دو `write` جدا، در یک `read` می‌رسند.
- یک حلقه‌ی پذیرشِ اتصال با `TcpListener` و `TcpStream` بنویسی، و در یک جمله بگویی چرا هسته‌ی `run_echo` به‌جایِ یک `TcpStream`ِ ملموس، رویِ `R: BufRead, W: Write` جنریک نوشته شده.
- سروری را که بعدِ یک خط هنگ می‌کند بخوانی، جای‌خالیِ چکِ EOF را که باعثش شده پیدا و رفع کنی — و بگویی چرا یک سرورِ واقعی به‌ازایِ هر اتصال یک ریسمانِ تازه می‌سازد، نه اینکه کلاینت‌ها را یکی‌یکی سرویس بدهد.

## چرا اهمیت دارد

تا همین‌جایِ دوره، هر ویویی (view) که تو جنگو (Django) نوشتی، با این خیالِ راحت بوده که یک ماشین‌آلاتِ سنگین از قبل آماده است: یک سرورِ WSGI/ASGI اتصالِ خامِ TCP را قبول کرده، بایت‌ها را از رویِ سیم خوانده، پارسشان کرده به یک درخواستِ HTTP، یک URL را باهاش تطبیق داده، و در نهایت یک آبجکتِ تروتمیز به اسمِ `request` گذاشته کفِ دستت. فاز ۳، از همین درس، دقیقاً همین ماشین‌آلات را از پایین‌ترین سطحِ ممکن — خودِ سوکت — دوباره می‌سازد، تا وقتی چند درسِ دیگر با یک فریم‌ورکِ واقعی کار کنی، آن به‌جایِ یک جادویِ سیاه، برایت بشود «همینِ الان، فقط خودکارشده».

این درسِ اول عمداً هیچ فریم‌ورک و هیچ وابستگی‌ای (dependency) ندارد — فقط ابزارهایِ پایه‌ی شبکه‌سازیِ خودِ کتابخانه‌ی استاندارد. یک سرورِ اکو (echo server) — هر چه کلاینت بفرستد، عیناً برگرداندنش — کوچک‌ترین سرویسِ شبکه‌ای است که می‌شود نوشت، و دقیقاً به همین دلیل بهترین جا برایِ رودررو شدن با یک واقعیتِ سختِ TCP است که هیچ فریم‌ورکی از تو پنهانش نمی‌کند، فقط برایت هموارش می‌کند: بایت‌ها به همان شکلی که فرستادی نمی‌رسند، پشتِ سرِ هم می‌رسند. هر چیزِ دیگری که تویِ فاز ۳ می‌سازی — پارس‌کردنِ یک درخواستِ HTTP دستی در درسِ بعدی، و بعدش خودِ `axum` در ماژولِ ۲ — رویِ همین واقعیت ساخته شده.

## مفهوم

### یک اتصالِ TCP یک جریانِ بایت است، نه یک صفِ پیام

یک **اتصالِ TCP (TCP connection)** یک جریانِ بایتِ دوطرفه، منظم و قابلِ‌اعتماد بینِ دو پردازش است (که ممکن است رویِ دو ماشینِ مختلف باشند). «منظم و قابلِ‌اعتماد» یعنی: اگر یک طرف اول `b"hello\n"` و بعد `b"world\n"` را در دو فراخوانیِ `write` جدا بنویسد، طرفِ مقابل تضمین دارد که اول `hello` را بخواند و بعد `world` را — چیزی گم یا جابه‌جا نمی‌شود (سیستم‌عامل و خودِ پروتکلِ TCP ارسالِ‌مجددِ بسته‌هایِ گم‌شده را خودشان حل می‌کنند).

اما این تضمین چیزی درباره‌ی **مرزِ** نوشتن‌ها نمی‌گوید. یک `read` می‌تواند چند `write` را با هم، یک‌جا، تحویل بدهد — یا برعکس، یک `write`ِ بزرگ می‌تواند چند `read`ِ جداگانه بخواهد. کدِ زیر این را رویِ یک سوکتِ واقعیِ لوپ‌بک ثابت می‌کند: یک ریسمان می‌پذیرد و بعدِ کمی مکث یک `read` می‌زند، ریسمانِ اصلی دو `write_all` جدا می‌کند.

```rust
let listener = TcpListener::bind("127.0.0.1:0")?;
let addr = listener.local_addr()?;

let reader = thread::spawn(move || {
    let (mut stream, _) = listener.accept().unwrap();
    thread::sleep(Duration::from_millis(200)); // بگذار هر دو write برسند
    let mut buf = [0u8; 64];
    let n = stream.read(&mut buf).unwrap();
    println!("one read() call got {n} bytes: {:?}", String::from_utf8_lossy(&buf[..n]));
});
```

```rust
let mut client = TcpStream::connect(addr)?;
client.write_all(b"hello\n")?; // اولین فراخوانیِ write
client.write_all(b"world\n")?; // دومین فراخوانیِ write، کاملاً جدا

reader.join().unwrap();
```

```text
one read() call got 12 bytes: "hello\nworld\n"
```

یک `read()`، هر دو `write_all` را با هم گرفت. کدِ کامل و اجراپذیرش `examples/01-two-writes-one-read.rs` است. این دقیقاً همان چیزی است که بعداً «جریانِ بایت» می‌خوانیمش: TCP یک صفِ پیام نیست که هر `write` یک بسته‌ی مجزا بسازد — یک لوله‌ی پیوسته از بایت است، و تشخیصِ اینکه یک «پیام» از کجا تمام می‌شود، کاملاً بر عهده‌ی خودِ برنامه است (این‌جا: با جستجویِ `\n`).

### `TcpListener` می‌شنود، `accept()` یک `TcpStream` می‌دهد

یک **`TcpListener`** رویِ یک آدرس (`host:port`) می‌نشیند و برایِ درخواست‌هایِ اتصالِ واردشونده گوش می‌ایستد. هر اتصالی که قبول (accept) شود، به یک **`TcpStream`** تبدیل می‌شود — یک لوله‌ی بایتِ باز و دوطرفه که دقیقاً مثلِ یک دستگیره‌ی فایل، هم ازش می‌خوانی هم توش می‌نویسی.

```rust
use std::net::TcpListener;

let listener = TcpListener::bind("127.0.0.1:7878")?;
for stream in listener.incoming() {
    let stream = stream?;
    // این یک اتصال را هندل کن
}
```

اگر از پایتون آمده باشی، این دقیقاً همان رابطه‌ی `socket.socket()` + `.bind()` + `.listen()` + `.accept()` است — ماژولِ `std::net`ِ Rust عمداً خیلی شبیهِ همان طراحی شده، فقط با یک سیستمِ نوعِ سفت‌وسخت و بدونِ هیچ GILی. جایی که تشبیه می‌شکند: `TcpListener::bind` خودش هم `listen()` و هم `bind()` را با هم انجام می‌دهد (یک فراخوانی به‌جایِ دو تا)، و `Result`ی که برمی‌گرداند دقیقاً همان `Result<T, E>`ی است که از فاز ۱ می‌شناسی — یک آدرسِ اشغال یا یک مجوزِ ناکافی، استثنا نمی‌شود، مقدار برمی‌گردد.

### خواندنِ خط‌به‌خط به `BufRead` نیاز دارد، نه فقط `Read`

سرورِ اکویِ این درس خط‌به‌خط کار می‌کند (بر اساسِ جداکننده‌ی `\n`‌)، نه بایت‌به‌بایت — دقیقاً همان چیزی که در درسِ بعد برایِ خواندنِ یک درخواستِ HTTP لازم داری: یک خط بخوان، تا برسی به چیزی معنی‌دار.

`std::io::Read` فقط بایتِ خام می‌دهد؛ هیچ ایده‌ای از «خط» ندارد. **`std::io::BufRead`** رویِ آن یک لایه‌ی بافردار می‌گذارد و متدِ `read_line` را اضافه می‌کند — دقیقاً همان چیزی که لازم داریم. `TcpStream` خودش `BufRead` را پیاده نمی‌کند (فقط `Read` و `Write`)، پس باید اول تویِ یک `BufReader` بپیچیمش:

```rust
use std::io::{BufRead, BufReader};

let reader = BufReader::new(stream); // حالا read_line دردسترس است
```

### یک هسته‌ی تست‌پذیر: جنریک رویِ `R: BufRead, W: Write`

منطقِ اصلیِ `src/lib.rs`، یعنی `run_echo`، به‌جایِ اینکه مستقیماً رویِ نوعِ ملموسِ `TcpStream` نوشته شود، رویِ پارامترهایِ **جنریکِ** `R: BufRead` و `W: Write` نوشته شده:

```rust
pub fn run_echo<R: BufRead, W: Write>(mut reader: R, mut writer: W) -> io::Result<usize> {
    // ...
}
```

این همان الگویِ «هسته‌ی منطقی را تست‌پذیر نگه‌دار، لایه‌یِ I/O را نازک کن» است که در فاز ۲ (side-quest anime-quote-cli) دیدی، این‌بار برایِ شبکه: یک `TcpStream`ِ واقعی هم `Read` را پیاده می‌کند هم `Write` را، اما `std::io::Cursor<&[u8]>` و `Vec<u8>` هم دقیقاً همین دو صفت را دارند. برایِ همین، تست‌هایِ `run_echo` تویِ `tests/echo_test.rs` هرگز یک سوکتِ واقعی باز نمی‌کنند — فقط یک بافرِ بایت بهش می‌دهند و یک بافرِ دیگر پس می‌گیرند. تنها `serve_once` (و بعدش `main.rs`) هستند که واقعاً دستشان به یک `TcpListener`ِ واقعی می‌خورد. این تقسیم را در تکِ‌تکِ درس‌هایِ فاز ۳ دوباره می‌بینی: منطقِ ناب در توابعِ تست‌پذیر، I/O هل‌داده‌شده به لبه‌ها.

### همروندی: یک ریسمان به‌ازایِ هر اتصال

`TcpListener::incoming()` اتصالات را یکی‌یکی، رویِ همان ریسمانی که دارد آن‌ها را می‌پذیرد، تحویل می‌دهد. اگر `run_echo` را مستقیماً همان‌جا صدا بزنی، یک کلاینتِ کند یا ساکت سرویس‌دهی به همه‌ی کلاینت‌هایِ دیگر را قفل می‌کند — کلِ سرور رویِ همان یک اتصال می‌ماند. راهِ‌حلِ کلاسیک (و قبل از این‌که ماژولِ ۲ مدلِ async را با `tokio` معرفی کند، هنوز یک انتخابِ کاملاً معقول برایِ یادگیری) این است که **به‌ازایِ هر اتصال یک ریسمانِ سیستم‌عامل بسازیم**:

```rust
for stream in listener.incoming() {
    let stream = stream?;
    std::thread::spawn(move || {
        // این اتصال را رویِ ریسمانِ اختصاصیِ خودش هندل کن
    });
}
```

ریسمان‌ها رایگان نیستند — هرکدام یک استکِ حافظه و یک جایگاهِ زمان‌بندی از سیستم‌عامل می‌گیرند — و دقیقاً به همین دلیل زمانِ‌اجراهایِ async مثلِ `tokio` وجود دارند: می‌گذارند هزاران اتصالِ هم‌زمان را رویِ یک استخرِ کوچک از ریسمان‌هایِ واقعی جابه‌جا کنی، نه یکی‌به‌ازایِ‌هرکدام. تویِ ۲.۸.۵ و ۲.۸.۶ خودِ `async`/`await` و پایه‌هایِ `tokio` را از قبل دیده‌ای؛ این درس عمداً همان‌ها را کنار می‌گذارد و رویِ ریسمانِ ساده می‌ماند، چون ماژولِ ۲، وقتی `axum` وارد می‌شود، دقیقاً همین‌جایی است که آن ریسمان را با یک زمانِ‌اجرایِ async واقعی عوض می‌کنی و تفاوتش را مستقیم حس می‌کنی.

## خطاهایی که خواهی دید

### `E0499` — دو بار قرضِ تغییرپذیرِ همان `stream`

تلاشِ طبیعیِ اول برایِ ساختنِ یک reader و یک writer از رویِ همان اتصال، این است که هر دو را از رویِ همان متغیر بسازی:

```text
error[E0499]: cannot borrow `stream` as mutable more than once at a time
  --> phase3-backend-foundations\01-networking-and-http-from-scratch\01-tcp-echo-server\examples\02-double-mut-borrow-broken.rs:14:18
   |
13 |     let reader = BufReader::new(&mut stream);
   |                                 ----------- first mutable borrow occurs here
14 |     let writer = &mut stream;
   |                  ^^^^^^^^^^^ second mutable borrow occurs here
15 |     run_echo(reader, writer)
   |              ------ first borrow later used here

For more information about this error, try `rustc --explain E0499`.
```

**کامپایلر دقیقاً از چه چیزی شاکی است:** `BufReader::new(&mut stream)` اولین قرضِ تغییرپذیرِ `stream` را می‌گیرد و تا صدا زدنِ `run_echo` هم زنده نگهش می‌دارد (چون `reader` بعداً استفاده می‌شود). خطِ بعدی می‌خواهد دومین قرضِ تغییرپذیرِ همان `stream` را بگیرد — دقیقاً همان قاعده‌ی هم‌نامی‌ای که از فاز ۱ می‌شناسی: هر تعداد قرضِ اشتراکی، یا دقیقاً یک قرضِ تغییرپذیر، هرگز هر دو با هم.

**راهِ‌حل:** به‌جایِ قرض‌گرفتنِ همان `stream` دوبار، `TcpStream::try_clone` را صدا بزن تا یک دستگیره‌ی کاملاً مستقلِ دوم به همان سوکتِ سیستم‌عامل بگیری:

```rust
let writer = stream.try_clone()?;
let reader = BufReader::new(stream);
run_echo(reader, writer)
```

**چرا این راهِ‌حل درست است:** `try_clone` سوکت را دوتا نمی‌کند — دستگیره را دوتا می‌کند (زیرِ پوست، یک `dup()` رویِ فایل‌دیسکریپتور). حالا `stream` و آن دستگیره‌ی کلون‌شده دو مقدارِ کاملاً مجزا و مالکیت‌دارند، پس هرکدام می‌تواند مستقلاً، بدونِ هیچ تداخلِ قرضی، به `run_echo` منتقل (move) شود. خواندن از یکی و نوشتن رویِ آن یکی دقیقاً همان گفتگویِ TCP را می‌بیند که یک `stream`ِ تنها می‌دید.

### یک هنگِ زمانِ‌اجرا — چکِ `Ok(0)` فراموش‌شده

این حتی یک خطایِ کامپایلر نیست: برنامه کامل کامپایل و اجرا می‌شود.

```text
$ cargo run -p p3-01-01-tcp-echo-server --example 03-missing-eof-check-broken
hello
```

و همین. دیگر هیچ‌وقت چیزِ دیگری چاپ نمی‌شود و برنامه هم برنمی‌گردد — باید با Ctrl+C متوقفش کنی.

**دقیقاً چه اتفاقی می‌افتد:** `read_line` وقتی چیزی برایِ خواندن نمانده (EOF) مقدارِ `Ok(0)` برمی‌گرداند — نه یک خطا، یک `Ok` با طولِ صفر. کدِ خراب این مقدار را هیچ‌وقت چک نمی‌کند: خط را پاک می‌کند، `read_line` صدا می‌زند، و — چون بعدِ EOF هر `read_line`ِ بعدی هم بلافاصله همان `Ok(0)` را می‌دهد، بدونِ اینکه منتظر بماند — حلقه هیچ‌وقت `break` نمی‌کند. نوشتنِ یک رشته‌ی خالی هم خطا نمی‌دهد (فقط صفر بایت می‌نویسد)، پس حلقه بی‌صدا و بی‌وقفه برایِ همیشه می‌چرخد، بدونِ اینکه هیچ‌جایِ آن منتظرِ چیزی بماند.

**راهِ‌حل:** رویِ همان مقداری که `read_line` برمی‌گرداند چک بزن، و وقتی صفر بود از حلقه بیرون بیا:

```rust
let bytes_read = reader.read_line(&mut line)?;
if bytes_read == 0 {
    break; // EOF — دیگر چیزی برایِ خواندن نمانده
}
```

**چرا این راهِ‌حل درست است:** `Ok(0)`ِ `read_line` تنها سیگنالی است که «طرفِ مقابل بخشِ نوشتنش را بست» را نشان می‌دهد — یک خطِ خالی (`"\n"`) هم یک بایت است، نه صفر. بدونِ این چک، کد فرض می‌کند هر `Ok` یعنی «یک خطِ تازه رسید»، درحالی‌که EOF یعنی دقیقاً برعکس: هرگز چیزِ تازه‌ای نمی‌رسد.

نه. TCP فقط ترتیب و رسیدنِ کاملِ بایت‌ها را تضمین می‌کند، نه مرزِ نوشتن‌ها را. یک `read`ِ تنها می‌تواند هر دو `write` را با هم بگیرد — دقیقاً همان چیزی که `examples/01-two-writes-one-read.rs` نشانت داد.

</details>

<details>
<summary>چرا <code>run_echo</code> رویِ <code>R: BufRead, W: Write</code> جنریک نوشته شده، نه رویِ پارامترهایِ ملموسِ <code>TcpStream</code>؟</summary>

قبل از دیدنِ جواب، خودت فکرش را بکن.

</details>

<details>
<summary>جواب</summary>

تا هسته‌ی منطقی تست‌پذیر بماند. یک `TcpStream`ِ واقعی هم `Read` را پیاده می‌کند هم `Write` را، اما یک `Cursor<&[u8]>`/`Vec<u8>`ِ درون‌حافظه‌ای هم همین دو صفت را دارد — پس تست‌ها هرگز نیازی به بازکردنِ سوکتِ واقعی ندارند.

</details>

<details>
<summary>کامپایل می‌شود؟</summary>

```rust
let reader = BufReader::new(&mut stream);
let writer = &mut stream;
run_echo(reader, writer)
```

</details>

<details>
<summary>جواب</summary>

نه — `E0499`. `BufReader::new(&mut stream)` اولین قرضِ تغییرپذیر را می‌گیرد و زنده نگهش می‌دارد؛ خطِ بعدی می‌خواهد دومینِ آن را از همان `stream` بگیرد. راهِ‌حل: `stream.try_clone()` به‌جایِ قرضِ دوباره.

</details>

<details>
<summary>کلاینت <code>"hi"</code> را بدونِ <code>\n</code>ِ آخر می‌فرستد و بلافاصله اتصالش را می‌بندد. اولین <code>read_line</code>ِ بعدِ آن چه برمی‌گرداند: <code>Ok(0)</code>، یا <code>Ok(2)</code> با <code>line == "hi"</code>؟</summary>

قبل از دیدنِ جواب، خودت فکرش را بکن.

</details>

<details>
<summary>جواب</summary>

`Ok(2)` با `line == "hi"`. تا وقتی دستِ‌کم یک بایتِ تازه برسد، `read_line` آن را با `Ok(n)` پس می‌دهد — حتی اگر خط بدونِ `\n` تمام شده باشد. `Ok(0)` فقط برایِ **بعدی**‌ترین صدازدن است، وقتی واقعاً دیگر چیزی نمانده.

</details>

### تعمیر

هر دو مثالِ خراب را درست کن:

۱. `examples/02-double-mut-borrow-broken.rs` را با گرفتنِ یک `stream.try_clone()` به‌جایِ قرضِ دوباره‌ی همان `stream` درست کن.
۲. `examples/03-missing-eof-check-broken.rs` را با اضافه‌کردنِ چکِ `bytes_read == 0` و `break` درست کن، تا بعدِ خواندنِ همه‌ی ورودی، خودش تمیز برگردد نه اینکه برایِ همیشه بچرخد.

### پیاده‌سازی

دو تابع تویِ `src/lib.rs`، مشخصاتِ کاملِ هرکدام همان کامنتِ مستندسازِ بالایِ خودش است:

```sh
cargo test -p p3-01-01-tcp-echo-server
```

- `run_echo` — خط‌به‌خط از `reader` بخوان تا EOF، هر خط را بلافاصله همان‌طور به `writer` برگردان، و تعدادِ کلِ بایت‌هایِ خوانده‌شده را برگردان.
- `serve_once` — دقیقاً یک اتصال را از رویِ `listener` بپذیر، یک دستگیره‌ی خواننده و یک دستگیره‌ی نویسنده‌ی مستقل ازش بگیر، و `run_echo` را رویِ آن‌ها اجرا کن.

بعدِ سبزشدنِ تست‌ها، یک بارِ دیگر هم رویِ یک سوکتِ واقعی امتحانش کن — `cargo run -p p3-01-01-tcp-echo-server` سرور را رویِ `127.0.0.1:7878` بالا می‌آورد؛ در یک ترمینالِ دیگر:

```sh
python3 - <<'PY'
import socket
s = socket.create_connection(("127.0.0.1", 7878))
s.sendall(b"hello\n")
s.sendall(b"world\n")
s.shutdown(socket.SHUT_WR)
data = b""
while chunk := s.recv(4096):
    data += chunk
print(data)
PY
```

```text
b'hello\nworld\n'
```

### بساز

نسخه‌ی خودت از `run_echo` را بنویس — مثلاً یکی که هر خط را قبل از برگرداندن بزرگ (uppercase) می‌کند، یا هر خط را با یک شمارنده‌ی درحالِ‌افزایش جلو می‌اندازد (`1: hello`، `2: world`، ...). دقیقاً همان‌طور تستش کن که تست‌هایِ موجود تست شده‌اند — یک `Cursor`/`Vec<u8>`ِ درون‌حافظه‌ای، بدونِ هیچ سوکتِ واقعی. مطمئن شو نسخه‌ی خودت هم EOF را درست تشخیص می‌دهد و آخرین خط را حتی بدونِ `\n` درست می‌دهد.

### چالش (اختیاری)

**بخشِ اول.** `examples/03-missing-eof-check-broken.rs`ِ درست‌شده را طوری گسترش بده که یک تستِ واقعی هم داشته باشد: یک کلاینتِ واقعی که وسطِ یک خط (بدونِ `\n`) اتصالش را می‌بندد. مطمئن شو `serve_once` همان بخشِ ناقص را عیناً پس می‌دهد و بدونِ هنگ‌کردن برمی‌گردد — دقیقاً همان رفتاری که تستِ `echoes_a_final_line_with_no_trailing_newline` رویِ یک `Cursor` ثابتش کرده، این‌بار رویِ یک `TcpStream`ِ واقعی.

**بخشِ دوم.** تابعی بنویس که به‌جایِ خودِ متنِ اکوشده، فقط تعدادِ خط‌هایِ متمایزی را که اکو شده‌اند برمی‌گرداند. این آخرین‌باری است که «یک خط را بخوان تا برسی به یک چیزِ معنی‌دار» را این‌قدر ساده می‌بینی — درسِ بعد همین ایده را برایِ پارس‌کردنِ یک درخواستِ HTTP واقعی به‌کار می‌برد.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| اتصالِ TCP | جریانِ بایتِ دوطرفه، منظم و قابلِ‌اعتماد؛ مرزِ نوشتن‌ها را حفظ نمی‌کند | هر جا که باید یک پروتکلِ خودت، رویِ بایت‌هایِ خام، تشخیص بدهی یک «پیام» کجا تمام می‌شود |
| `TcpListener` | رویِ یک آدرس می‌نشیند و برایِ اتصال‌هایِ واردشونده گوش می‌ایستد | هر سرورِ TCPی که با یک حلقه‌ی پذیرش شروع می‌شود |
| `TcpStream` | یک اتصالِ پذیرفته‌شده؛ `Read` + `Write` را دارد، دقیقاً مثلِ یک دستگیره‌ی فایل | خواندن/نوشتنِ بایت به یک کلاینتِ مشخص |
| `BufRead` | صفتِ `std::io` که `read_line`/`.lines()` را رویِ `Read` اضافه می‌کند | پروتکل‌هایِ خط‌محور — اکویِ همین درس، درخواست‌هایِ HTTPِ درسِ بعد |
| یک ریسمان به‌ازایِ هر اتصال | هر اتصالِ پذیرفته‌شده رویِ ریسمانِ خودش هندل می‌شود، تا یک کلاینتِ کند بقیه را قفل نکند | `main.rs`ِ همین درس؛ با تسک‌هایِ `tokio` عوض می‌شود همین‌که ماژولِ ۲ شروع شود |

### الان می‌دانی

- چرا TCP فقط ترتیب و رسیدنِ بایت‌ها را تضمین می‌کند نه مرزِ نوشتن‌ها را، و این را رویِ یک سوکتِ واقعی دیدی.
- رابطه‌ی `TcpListener` / `accept()` / `TcpStream`، و اینکه چطور دقیقاً همان `socket()`+`bind()`+`listen()`+`accept()`ِ پایتون است.
- چرا `BufRead` برایِ خواندنِ خط‌به‌خط لازم است، و چرا هسته‌ی منطقیِ سرور رویِ آن جنریک نوشته می‌شود — تا بشود بدونِ هیچ سوکتِ واقعی تستش کرد.
- چرا `try_clone` لازم است (`E0499`)، و چرا فراموش‌کردنِ چکِ `Ok(0)`ِ `read_line` یک هنگِ زمانِ‌اجراست، نه یک خطایِ کامپایلر.
- چرا یک سرورِ واقعی به‌ازایِ هر اتصال یک ریسمان می‌سازد، و ریسمان‌ها دقیقاً چه چیزی هزینه می‌کنند.

### بعداً کامل‌تر می‌بینی

- **پارس‌کردنِ یک پروتکلِ واقعی رویِ همین جریانِ خط‌به‌خط (یک درخواستِ HTTP)** — [۳.۱.۲ — پارسرِ HTTP دست‌ساز](../02-hand-rolled-http-parser/README.fa.md)
- **همین حلقه‌ای که برایِ هر اتصال یک ریسمان می‌سازد، این‌بار با تسک‌هایِ `tokio` زیرِ `axum`** — [ماژولِ ۲ — `axum` و طراحیِ REST API](../../02-axum-and-rest-api-design/README.fa.md)

### می‌توانی توضیح بدهی؟

- چرا «TCP یک جریانِ بایت است، نه یک صفِ پیام» یعنی چه، با یک مثالِ عینی؟
- رابطه‌ی `TcpListener`، `accept()` و `TcpStream` چیست، و معادلِ پایتونی‌اش کدام است؟
- چرا `run_echo` رویِ `R: BufRead, W: Write` جنریک نوشته شده، نه رویِ `TcpStream`؟
- چرا `serve_once` به `try_clone` نیاز دارد، و اگر بجایش دو بار `&mut stream` بدهی چه خطایی می‌گیری؟
- فراموش‌کردنِ چکِ `Ok(0)`ِ `read_line` دقیقاً چه اتفاقی می‌افتد، و چرا این یک هنگ است نه یک خطایِ کامپایلر؟
