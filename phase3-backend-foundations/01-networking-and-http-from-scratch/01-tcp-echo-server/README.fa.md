# ۰۱.۱ — سرور اکوی TCP (TCP echo server)

## اصلاً چرا از یه سطح پایین‌تر از فریم‌ورک شروع کنیم

تا الان هر ویویی (view) که تو جنگو (Django) نوشتی، با این پیش‌فرض و خیال راحت بوده که یه ماشین‌آلات سنگین از قبل وجود داشته: یه سرورِ WSGI/ASGI اومده یه اتصالِ خامِ TCP رو قبول کرده، بایت‌ها رو از روی سیم خونده، اونا رو پارس کرده و به یه درخواستِ HTTP تبدیلشون کرده، یه URL رو باهاش تطبیق (match) داده، و در نهایت یه آبجکتِ تروتمیز به اسم `request` گذاشته تو بغلت. کُلِ هدفِ فاز ۳ اینه که این درک شهودی و پایه رو از پایین‌ترین سطح ممکن یعنی سوکت‌ها دوباره بسازه، تا دو درسِ بعد، وقتی می‌نویسی `(...)axum::Router::new().route`، *دقیقاً* بدونی اون زیر داره چه اتفاقی می‌افته و اونو یه جادویِ سیاهِ نامفهوم نبینی. تو این درسِ اول هیچ فریم‌ورک و وابستگی‌ای (dependency) وجود نداره — فقط ابزارهای پایه‌ی شبکه‌سازیِ (networking primitives) خود کتابخونه‌ی استاندارد.

## یه سوکت واقعاً چیه

یه **اتصال TCP (TCP connection)**، یه جریانِ بایتِ دوطرفه، منظم و قابل‌اعتماد بین دو تا پردازش (processes) (که ممکنه رو ماشین‌های مختلف باشن) هست. منظور از "منظم و قابل‌اعتماد" اینه: اگه یه طرف اولِ عبارتِ `"b"hello` و بعد `"b"world` رو بنویسه (write کنه)، بهت تضمین داده می‌شه که طرفِ مقابل اول `hello` رو بخونه و بعد `world` رو، بدون اینکه چیزی این وسط گم بشه یا ترتیبش به هم بریزه (سیستم‌عامل و پروتکل TCP خودشون زحمت ارسال مجددِ بسته‌های گم‌شده (retransmission) رو می‌کشن). اما این اصلاً به این معنی **نیست** که بایت‌ها به شکلِ یه تیکه‌ی شیک و مرتب دستت می‌رسن — یه عملیاتِ `write` تو یه سمت، می‌تونه موقع دریافت تو سمتِ دیگه تو قالب چند تا عملیاتِ `read`ِ تیکه‌تیکه خودش رو نشون بده، یا برعکس، چند تا `write`ِ کوچیک می‌تونن با هم ترکیب (coalesce) بشن و تو یه دونه `read` تو اون سمت دریافت بشن. این قضیه دقیقاً چند لحظه‌ی دیگه اهمیت پیدا می‌کنه.

یه **`TcpListener`** میاد روی یه آدرس مشخص (`host:port`) می‌شینه (bind می‌شه) و واسه درخواست‌های اتصالی که از بیرون میان *گوش وایمیسته (listens)*. هر اتصالی که قبول (accept) بشه، تبدیل می‌شه به یه **`TcpStream`** — یعنی یه لوله‌ی بایتِ دوطرفه و باز، که تو دقیقاً مثل یه دستگیره‌ی فایل (file handle)، هم ازش می‌خونی و هم توش می‌نویسی. این دقیقاً همون رابطه‌ایه که بینِ توابع پایتونیِ `()socket.socket` + `.bind()` + `.listen()` + `.accept()` وجود داره — ماژول `std::net` زبان Rust به عمد خیلی شبیه همونا طراحی شده، فقط با این تفاوت که سیستمِ انواع (typed) سفت‌وسختی داره و هیچ خبری از قفلِ GIL توش نیست.

```rust
use std::net::TcpListener;

let listener = TcpListener::bind("127.0.0.1:7878")?;
for stream in listener.incoming() {
    let stream = stream?;
    // این اتصال (connection) رو هندل کن
}
```

## چرا رویکردِ خط‌به‌خط (line-based)، و چرا یه تابعِ جنریک (generic)

یه **سرور اکو (echo server)** تو دنیای شبکه مثل نوشتن برنامه‌ی "hello world" می‌مونه: کلاینت هر چی بفرسته، سرور عین همونو برمی‌گردونه سمتش. ما اینجا به جای اینکه بایت‌به‌بایت کار کنیم، می‌خوایم خط‌به‌خط (بر اساس جداکننده‌ی `n\`) پیش بریم، چون این روش مستقیماً منطبق می‌شه با همون کاری که قراره تو درس بعدی واسه خوندنِ درخواست‌های HTTP بکنی — یعنی یه خط رو می‌خونی، تا زمانی که برسی به یه چیزِ معنی‌دار (مثل یه خط خالی، یا یه هدر شناخته‌شده).

هسته‌یِ منطقیِ اصلی تو فایلِ `src/lib.rs`، یعنی همون تابعِ `run_echo`، به جای اینکه مستقیماً با نوعِ واقعی و ملموسِ `TcpStream` نوشته بشه، با استفاده از پارامترهایِ **جنریکِ** `R: BufRead` و `W: Write` طراحی شده:

```rust
pub fn run_echo<R: BufRead, W: Write>(mut reader: R, mut writer: W) -> io::Result<usize> {
    // ...
}
```

این دقیقاً همون الگویِ «هسته‌ی منطقیت رو تست‌پذیر نگه‌دار و لایه‌ی I/O رو نازک کن» از ماموریت جانبیِ anime-quote-cli هستش که حالا تو دنیای شبکه (networking) پیاده شده: یه `TcpStream`ِ واقعی هر دو خصیصه‌ی `Read` و `Write` رو پیاده‌سازی می‌کنه، اما یه `std::io::Cursor<&[u8]>` / `<Vec<u8` که داخل حافظه (in-memory) می‌شینه هم دقیقاً همونا رو پیاده‌سازی کرده. این یعنی تست‌های تابعِ `run_echo` تو فایلِ `tests/echo_test.rs`، اصلاً و ابداً نیازی ندارن که واقعاً یه سوکت واقعیِ شبکه رو باز کنن — فقط خیلی راحت بهش یه سری بافرِ بایت (byte buffers) پاس می‌دن. فقط توابعِ `serve_once`/`main.rs` (یعنی همون پوسته‌ی نازکِ بیرونی) هستن که واقعاً دستشون به یه `TcpListener`ِ واقعی می‌خوره. تو تک‌تک درس‌های فاز ۳، دقیقاً قراره همین جداسازی رو ببینی: یه منطقِ ناب (pure logic) تو توابعِ تست‌پذیر، و هل دادن عملیات‌های I/O به لبه‌های بیرونیِ برنامه.

## همروندی (Concurrency): یه ریسمان (thread) به ازای هر اتصال

متدِ `()TcpListener::incoming` اتصالات رو یکی‌یکی رو همون ریسمانی (thread) که داره اونا رو *می‌پذیره (accepting)* بهت تحویل می‌ده. اگه تو بیای تابعِ `run_echo` رو مستقیماً تو دلِ همون حلقه صدا بزنی، یه کلاینتِ کند یا ساکت باعث می‌شه که سرویس‌دهی به تک‌تک کلاینت‌های دیگه قفل بشه (block بشن) — کلِ سرور روی همون یه دونه اتصال متوقف و معطل می‌مونه. راه‌حلِ کلاسیکِ این مشکل (که هنوزم قبل از اینکه ماژول ۲ تو فاز ۳ بخواد مدلِ غیرهمگام (async) مربوط به `tokio` رو معرفی کنه، یه روش کاملاً منطقی واسه یادگیریه) اینه که **به ازایِ هر اتصالِ جدید، یک ریسمان سیستم‌عامل (OS thread) مجزا ساخته بشه**:

```rust
for stream in listener.incoming() {
    let stream = stream?;
    std::thread::spawn(move || {
        // این اتصال رو روی ریسمانِ اختصاصیِ خودش هندل کن
    });
}
```

ریسمان‌ها کلاً رایگان نیستن (هر کدومشون نیازمندِ یه سری منابع واقعی از سیستم‌عاملن — مثل یه پشته‌ی حافظه (stack)، و یه جایگاه برای زمان‌بندی (scheduler slot))، و دقیقاً به همین دلیله که *اصلاً* زمان‌های اجرایی (async runtimes) مثل `tokio` به وجود اومدن: اونا بهت اجازه می‌دن تا هزاران اتصال همروند رو، به جای اینکه واسه هرکدوم یه ریسمان بسازی، روی یه استخرِ (pool) خیلی کوچیک از ریسمان‌های واقعی سیستم‌عامل مدیریت کنی (juggle کنی). وقتی که `axum` وارد تصویر بشه، این تفاوت رو خیلی مستقیم و واضح حس می‌کنی.

## وظیفه‌ی تو

دو تا `todo!()` تو فایل `src/lib.rs` پیاده‌سازی کن:

1. `run_echo` — تا رسیدن به نشانه‌ی پایان فایل (EOF) خط‌ها رو از `reader` بخون (یعنی همونجایی که متد `read_line` مقدارِ `Ok(0)` رو برمی‌گردونه)، و هر خط رو مستقیماً و بلافاصله تو `writer` بنویس (write)، و در نهایت تعداد کل بایت‌های خونده‌شده رو برگردون.
2. `serve_once` — دقیقاً و دقیقاً فقط *یک دونه* اتصال رو از روی یه `TcpListener` که به پورت متصل شده (bound)، بپذیر (accept کن)، با استفاده از `TcpStream::try_clone` اونو بشکون و تبدیلش کن به یه جفتِ reader/writer (خوننده و نویسنده)، و در نهایت تابع `run_echo` رو روشون اجرا کن. (سرور واقعی تو یه حلقه‌ی بی‌نهایت اتصالات رو می‌پذیره؛ اما `serve_once` همون‌طور که از اسمش پیداست فقط یکیش رو هندل می‌کنه، که دقیقاً همون چیزیه که تست‌ها لازم دارن و در ضمن باعث می‌شه کدهای مربوط به همروندی کلاً تو `main.rs` بمونه، که اون فایل به صورت عمدی تحت پوششِ تست قرار نگرفته — تو نمی‌تونی به راحتی یه تستِ واحد واسه کُدی بنویسی که "تا ابد حلقه می‌زنه.")

کدهای فایل `src/main.rs` از قبل برات نوشته شدن — این فایل همون مدلِ هندل‌کردنِ `serve_once` رو می‌گیره و تو یه حلقه‌ی بی‌نهایت تکرارش می‌کنه، برای هر اتصال یه ریسمان رو spawn می‌کنه، و به آدرس `127.0.0.1:7878` متصل (bind) می‌شه.

## تو دنیای واقعی امتحانش کن

```sh
cargo run -p p3-01-01-tcp-echo-server &
printf 'hello\nworld\n' | nc 127.0.0.1 7878
# یا اگه ابزار netcat یا nc رو نداری:
python3 -c "
import socket
s = socket.create_connection(('127.0.0.1', 7878))
s.sendall(b'hello\n')
print(s.recv(1024))
"
```
