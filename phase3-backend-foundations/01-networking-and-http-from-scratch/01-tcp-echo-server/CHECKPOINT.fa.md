# چک‌پوینت

1. چرا تابعِ `run_echo` به جایِ یه پارامتر از نوع `R: Read`، یه پارامترِ `R: BufRead` می‌گیره؟ اون متدی که `BufRead` بهت میده اما `Read`ِ خالی نمی‌تونه، چیه؟
2. تستِ end-to-end (انتها-به‌-انتها) قبل از اینکه بخواد جوابِ سرور رو بخونه، متدِ `(client.shutdown(Shutdown::Write` رو صدا می‌زنه. اگه اون خط رو پاک کنی چه اتفاقی برای حلقه‌ی (loop) داخلِ `run_echo` می‌افته — آیا متدِ `read_line` هرگز خروجیِ `(Ok(0` رو برمی‌گردونه؟ سعی کن اون خط رو پاک کنی و تست رو ران کنی تا ببینی چی می‌شه (بعدش حتماً دوباره برش گردون سر جاش).
3. تابعِ `serve_once` متدِ `()stream.try_clone` رو صدا می‌زنه تا به جای استفاده از یه دونه `mut stream&`ِ مشترک برای هم خوندن و هم نوشتن، دو تا دستگیره (handle) مجزا به یک اتصالِ یکسان دریافت کنه. امضای (signature) تابعِ `run_echo` به این شکل طراحی شده: `run_echo<R: BufRead, W: Write>(reader: R, writer: W)` — یعنی دو تا پارامترِ *کاملاً مجزا*. با توجه به چیزایی که در موردِ قرض گرفتن‌ها (borrowing) می‌دونی (اینکه تو هر لحظه فقط یه دونه قرضِ تغییرپذیر (mutable borrow) مجازه)، چرا ممکن نیست که هر دوی `R` و `W` فقط باشن `mut TcpStream&` که جفتشون هم به همون یه دونه جریانِ یکسان (stream) اشاره کنن؟
4. فایل `main.rs` به ازای هر اتصالِ کلاینت، دقیقاً یه دونه ریسمان سیستم‌عامل (OS thread) مجزا رو متولد می‌کنه (spawn می‌کنه). وقتی تعداد کلاینت‌هایِ همزمانمون به مرز هزاران نفر برسه، هزینه‌ی واقعیِ منابعِ مصرفی واسه این کار چقدره، و اکوسیستمِ زبان Rust چه چیزی رو به عنوان جایگزین برای حل این مشکل پیشنهاد می‌ده (همون چیزی که از ماژولِ بعدی قرار ازش استفاده کنی)؟
5. تو زبان پایتون، عبارتِ `(...)socket.create_connection(...).recv` دقیقاً با همون روشی که `TcpStream::read` تو زبان Rust انجام می‌ده، ریسمانی رو که صداش زده متوقف و مسدود (blocks) می‌کنه. با توجه به وجود قفلِ GIL تو پایتون، اگه می‌خواستی هزاران سوکتِ همروند رو با تخصیص یه ریسمانِ OS به ازای هر اتصال (دقیقاً شبیه کاری که `main.rs` اینجا انجام می‌ده) هندل کنی، چه اتفاقی می‌افتاد؟ (این دقیقاً همون *دلیل اصلی و مهمیه* که اصلاً `asyncio`/ASGI تو دنیای پایتون به وجود اومدن — همون معادلِ Rustای اینا که تو ماژول بعدی باهاش آشنا می‌شی رو نام ببر.)
