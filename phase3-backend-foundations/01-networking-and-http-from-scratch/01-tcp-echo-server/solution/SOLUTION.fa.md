# راه‌حل

```rust
pub fn run_echo<R: BufRead, W: Write>(mut reader: R, mut writer: W) -> io::Result<usize> {
    let mut total = 0usize;
    let mut line = String::new();

    loop {
        line.clear();
        let bytes_read = reader.read_line(&mut line)?;
        if bytes_read == 0 {
            break;
        }
        writer.write_all(line.as_bytes())?;
        writer.flush()?;
        total += bytes_read;
    }

    Ok(total)
}
```

حلقه میاد اولِ هر چرخه (iteration) متغیر `line` رو با `()clear.` خالی می‌کنه، به جای اینکه هر بار بخواد یه `String` تر و تازه از اول بسازه — متد `read_line` اطلاعات رو به انتهای همون چیزی که از قبل تو بافر بوده *اضافه می‌کنه (appends)*، و اونو رونویسی نمی‌کنه؛ در نتیجه اگه `line` که از چرخه‌ی قبلی مونده رو پاک نکنی، بی‌سروصدا خط‌به‌خطِ هرچیزی رو که کلاینت تا ابد بفرسته تو خودش جمع می‌کنه. این یه باگ خیلی واقعی و راحت‌الوقوعه: اولین اجرای تست کاملاً درست به نظر میاد (چون تو اجرای اول `line` کلاً خالی بوده) و تازه زمانی می‌شکنه که کلاینت بیشتر از یه خط پیام بفرسته.

عبارتِ `0 == bytes_read` همون سیگنالِ رسیدن به انتهای فایل (EOF) هستش که `read_line` بهت می‌ده — نه یه خط خالی (`"n\"` که یعنی یه دونه بایت)، بلکه واقعاً و مطلقاً دیگه هیچ‌چیزی برای خوندن وجود نداره، که خب این اتفاق فقط وقتی می‌افته که طرفِ مقابل، بخشِ نوشتنِ (write) اتصال خودش رو قطع (close) کنه. هر عدد مثبت دیگه‌ای که برگرده، حتی اگه مربوط به خطی باشه که آخرش `"n\"` نداره (یعنی مثلاً اتصال همون وسطِ خط قطع شده باشه)، بازم معنیش اینه که «اینجا هنوز داده‌ی جدیدی هست»، پس ما همونو دقیقاً برمی‌گردونیم به خودش.

```rust
pub fn serve_once(listener: &TcpListener) -> io::Result<usize> {
    let (stream, _addr) = listener.accept()?;
    let writer: TcpStream = stream.try_clone()?;
    let reader = io::BufReader::new(stream);
    run_echo(reader, writer)
}
```

متدِ `try_clone` اتصال رو از وسط به دو قسمت تکثیر (duplicate) نمی‌کنه — بلکه میاد *دستگیره‌ی (handle)* همون سوکتِ واقعیِ سیستم‌عامل رو دو تا می‌کنه (در واقع تو لایه‌های زیرین، این کار فقط فراخوانیِ تابع `()dup` رو یه فایل دیسکریپتور (file descriptor) هستش). هر دو متغیرِ `stream` و `writer` دارن به یک گفتگویِ مشترکِ واحد با کلاینت اشاره می‌کنن؛ خوندن از روی یکی و نوشتن روی اون یکی دقیقاً و مو به مو مثل همونه که از روی یه دونه `stream`ِ اورجینال بخونی و بنویسی. این کار دقیقاً یکی از همون دیوارهای معروفِ بررسی‌کننده‌ی قرض‌گرفتن‌ها (borrow-checker) رو دور می‌زنه: امضایِ تابعِ `run_echo` متغیرهای `reader: R` و `writer: W` رو به عنوان دو تا پارامتر کاملاً مستقل و مجزا (independent) در نظر می‌گیره، و borrow checker عمراً بهت اجازه نمی‌ده که بتونی `&mut stream` رو دو بار بهش بدی (قانونِ «تو هر لحظه فقط یه دونه قرض تغییرپذیر» — که تو ماژول borrowing بهش رسیدیم). در حالی که دو تا دستگیره‌ی کپی‌شده (cloned)، دو تا ارزشِ (values) کاملاً مجزا و واقعی حساب می‌شن، در نتیجه هر کدومشون می‌تونه به صورت مستقل و بدون ایجاد هیچ‌گونه تداخلِ قرضی (borrow conflict) به داخلِ `run_echo` منتقل و موو (move) بشه.

## در مورد سؤال ۴ مرور (هزینه‌ی استفاده از ریسمان به ازای هر اتصال)

هر فراخوانیِ `std::thread::spawn` میاد و یه ریسمان واقعی سیستم‌عامل رو برای تو رزرو می‌کنه — که خب به طور معمول شامل یه پشته‌ی حافظه (stack) چند مگابایتی می‌شه، و البته حالا زمان‌بندِ (scheduler) کرنلِ سیستم‌عامل هم بازم یه چیز جدید داره تا بینش جابه‌جا بشه (context-switch). وقتی قرار باشه هزاران اتصالِ *بی‌کار و معطل (idle)* رو هندل کنی (مثلاً یه برنامه‌ی چت با کاربرای خیلی ساکت، یا دریافت‌کننده‌ی وب‌هوک که منتظر رویدادهای خیلی نادره)، یعنی هزاران ریسمان داری که اونجا نشستن، کلاً هیچ کاری نمی‌کنن اما حافظه مصرف می‌کنن و سربارِ بی‌خود به زمان‌بند اضافه می‌کنن. 
کریتِ `tokio` (که تو ماژول بعدی باهاش کار می‌کنی) این مشکل رو از این طریق حل می‌کنه که میاد تعداد خیلی زیادی از تسک‌های *سبک، و زمان‌بندی‌شده به صورت همیاری‌طور (cooperatively-scheduled)* رو روی تعداد کم و محدودی از ریسمان‌های سیستم‌عامل (OS threads) تو یه استخر (pool) می‌چینه و پخش می‌کنه (multiplex می‌کنه) — تسکی که فقط داره منتظرِ رسیدن نتیجه از یه عملیات I/O (ورودی/خروجی) می‌مونه، اون ریسمان رو گروگان نمی‌گیره، بلکه ریسمان رو پس می‌ده به زمان‌اجرا (runtime)، که اونم بلافاصله برش می‌داره و می‌ده به تسکِ دیگه‌ای که واقعاً آماده‌ی کار کردنه. این دقیقاً همون ایده‌ی بنیادینِ `asyncio` تو پایتونه، فقط با این تفاوت که اینجا بدون قفل GIL پیاده‌سازی شده و به جای اینکه تفسیر (interpreted) بشه، کامپایل می‌شه.
