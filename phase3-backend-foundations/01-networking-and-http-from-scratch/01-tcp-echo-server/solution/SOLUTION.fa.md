# راه‌حل — ۳.۱.۱ سرور اکوی TCP

```rust
pub fn run_echo<R: BufRead, W: Write>(mut reader: R, mut writer: W) -> io::Result<usize> {
    let mut total = 0usize;
    let mut line = String::new();

    loop {
        line.clear();
        let bytes_read = reader.read_line(&mut line)?;
        if bytes_read == 0 {
            break;
        }
        writer.write_all(line.as_bytes())?;
        writer.flush()?;
        total += bytes_read;
    }

    Ok(total)
}
```

حلقه اولِ هر چرخه (iteration) متغیرِ `line` را با `.clear()` خالی می‌کند، به‌جایِ اینکه هر بار یک `String`ِ تازه بسازد — `read_line` به انتهایِ همان چیزی که از قبل تویِ بافر هست *اضافه می‌کند*، رونویسی نمی‌کند؛ پس اگر `line`ِ چرخه‌ی قبلی پاک نشود، بی‌صدا خط‌به‌خطِ هرچه کلاینت تا ابد بفرستد را تویِ خودش جمع می‌کند. این یک باگِ خیلی واقعی و آسان‌الوقوع است: اولین اجرا کاملاً درست به‌نظر می‌رسد (چون تویِ چرخه‌ی اول `line` خودش خالی بوده) و تازه وقتی بیش از یک خط برسد می‌شکند.

`bytes_read == 0` همان سیگنالِ EOFی است که `read_line` می‌دهد — نه یک خطِ خالی (`"\n"`، یک بایت)، بلکه واقعاً دیگر چیزی برایِ خواندن نمانده، که فقط وقتی اتفاق می‌افتد که طرفِ مقابل بخشِ نوشتنش را بسته باشد. هر عددِ مثبتِ دیگری، حتی برایِ خطی که `\n`ِ آخر را ندارد (جریان همان‌وسط تمام شده)، یعنی «این‌جا داده‌ی تازه‌ای هست»، پس مستقیم به کلاینت برگردانده می‌شود. `examples/03-missing-eof-check-broken.rs` دقیقاً نشان می‌دهد وقتی این چک نباشد چه می‌شود: `read_line` برایِ همیشه همان `Ok(0)` را برمی‌گرداند، بدونِ اینکه هیچ‌وقت منتظر بماند، پس حلقه به‌جایِ `break`زدن، می‌چرخد.

```rust
pub fn serve_once(listener: &TcpListener) -> io::Result<usize> {
    let (stream, _addr) = listener.accept()?;
    let writer: TcpStream = stream.try_clone()?;
    let reader = io::BufReader::new(stream);
    run_echo(reader, writer)
}
```

`try_clone` اتصال را دوتا نمی‌کند — *دستگیره‌ی* همان سوکتِ واقعیِ سیستم‌عامل را دوتا می‌کند (زیرِ پوست، یک `dup()` رویِ فایل‌دیسکریپتور). هر دویِ `stream` و `writer` به همان یک گفتگویِ مشترک با کلاینت اشاره می‌کنند؛ خواندن از یکی و نوشتن رویِ آن یکی دقیقاً همان کاری را می‌کند که خواندن/نوشتنِ رویِ همان `stream`ِ تنها می‌کرد. این دقیقاً یک دیوارِ واقعیِ borrow checker را دور می‌زند: امضایِ `run_echo` پارامترهایِ `reader: R` و `writer: W` را کاملاً مستقل می‌گیرد، و borrow checker هرگز اجازه نمی‌دهد `&mut stream` را دوبار بهش بدهی — دقیقاً همان `E0499`ی که در «خطاهایی که خواهی دید»یِ `../README.fa.md` آمده. دو دستگیره‌ی کلون‌شده دو مقدارِ کاملاً مجزا و مالکیت‌دارند، پس هرکدام مستقلاً به `run_echo` منتقل می‌شود، بدونِ هیچ تداخلِ قرضی.

## درباره‌ی هزینه‌ی یک ریسمان به‌ازایِ هر اتصال

هر فراخوانیِ `std::thread::spawn` یک ریسمانِ واقعیِ سیستم‌عامل رزرو می‌کند — معمولاً یک استکِ چند مگابایتی، به‌علاوه‌یِ یک چیزِ تازه که زمان‌بندِ کرنل باید بینش سوییچ کند. هزاران اتصالِ *بی‌کار* (یک اپِ چت با کاربرهایِ ساکت، یک دریافت‌کننده‌ی وب‌هوک که منتظرِ رویدادهایِ نادر است) یعنی هزاران ریسمانی که فقط نشسته‌اند و حافظه و سربارِ زمان‌بندی مصرف می‌کنند. `tokio` (که در فاز ۲ از قبل دیده‌ای، و از ماژولِ ۲ به‌بعد واقعاً به‌کارش می‌بری) این را با پخش‌کردنِ تسک‌هایِ *سبک و همیاری‌طور* رویِ یک استخرِ کوچک و ثابت از ریسمان‌هایِ سیستم‌عامل حل می‌کند — تسکی که فقط منتظرِ I/O است ریسمان را گروگان نمی‌گیرد، آن را به زمانِ‌اجرا پس می‌دهد، که آن هم می‌دهدش به هر تسکی که واقعاً آماده‌ی کار است. همان ایده‌ی بنیادیِ `asyncio`ی پایتون، فقط بدونِ GIL و کامپایل‌شده به‌جایِ تفسیرشده.
