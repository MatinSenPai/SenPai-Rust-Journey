# راه‌حل

```rust
pub async fn greet(Path(name): Path<String>) -> String {
    format!("Hello, {name}!")
}
```

تا زمانی که اجرای کُد به این خط برسه، خودِ `axum` از قبل زحمتِ استخراجِ `{name}` رو از تو دلِ آدرسِ URL کشیده و اونو به عنوان یه نوعِ `String` دارای مالکیت (owned String) دودستی تقدیمت کرده — اون بخشِ مربوط به "استخراج‌کننده‌ها" (extractor) که تو تیترِ «مسیریابی (routing)، هندلرها، استخراج‌کننده‌ها» دیدی، در واقع تمام و کمال تو همون قسمتِ *امضای (signature)* تابع نوشته می‌شه، نه تو دلِ بدنه‌اش.

```rust
pub async fn echo(Json(payload): Json<EchoRequest>) -> Json<EchoResponse> {
    let length = payload.message.len();
    Json(EchoResponse { message: payload.message, length })
}
```

محاسبه‌ی مقدار `length` دقیقاً قبل از این انجام می‌شه که فیلدِ `payload.message` واردِ متغیرِ (move into) `EchoResponse` بشه — چون `()payload.message.len` متغیر رو قرض (borrow) می‌گیره، اما ساختارِ `} EchoResponse` `.. ,message: payload.message` اونو انتقال (move) می‌ده. اینکه تو اول قرض بگیری (borrow) و در قدمِ دوم جابه‌جایی (move) رو انجام بدی (نه اینکه سعی کنی خروجیِ `.len()` رو روی یه متغیری که کلاً قبلاً انتقال داده شده بخونی)، دقیقاً همون الگو و انضباطِ ترتیبی‌ایه که تو درسِ «انتقال‌ها (move-semantics)» تو فاز ۱ برای متغیر `total_length` یاد گرفتی: یعنی تو همیشه آزادی که یه متغیر رو *قبل از* واگذاری کاملش به جای دیگه اندازه بگیری، اما هرگز *بعد از* واگذاری حق همچین کاری رو نداری.

```rust
pub async fn get_counter(State(state): State<AppState>) -> Json<CounterResponse> {
    let count = *state.counter.lock().unwrap();
    Json(CounterResponse { count })
}
```

عبارتِ `.lock().unwrap()` — متدِ `()Mutex::lock` تو خروجی مقدارِ `<LockResult<MutexGuard<T>>` رو برمی‌گردونه، و تنها راهی که می‌تونه حالتِ `Err` رو بهت بده اینه که یه ریسمانِ (thread) دیگه تو زمانی که همون قفل رو تو دست داشته پنیک (panic) کرده باشه (که به این حالت می‌گن یه قفلِ "مسموم‌شده" یا "poisoned" mutex). تو یه تمرین آموزشی که کانترت داخل مموریه (in-memory counter)، استفاده از `unwrap` کلاً یه کار استاندارد و پذیرفته‌شده‌ست؛ اما تو یه سرویس که واسه محیطِ واقعی و پروداکشن ساخته می‌شه، این یه تصمیمیه که باید خیلی آگاهانه (deliberately) گرفته بشه: اینکه مسموم‌شدنِ یه قفل آیا باید باعثِ کرش‌کردن (crash) کل اون ریکوئست بشه، یا اینکه باید یه جوری از اون وضعیت ریکاور و بازیابی بشه.

```rust
pub async fn increment_counter(State(state): State<AppState>) -> Json<CounterResponse> {
    let mut guard = state.counter.lock().unwrap();
    *guard += 1;
    let count = *guard;
    drop(guard);
    Json(CounterResponse { count })
}
```

این دقیقاً همون تله‌ی شماره ۸ تو درس‌های قبلیه که حالا برامون ملموس شده: اگه عبارتِ `guard*` رو تو همون خط آخرِ بلوکی (block) که خودش مالکِ منبعِ متغیرِ `guard` هم هست بنویسی (یعنی به عنوان یه tail expression)، تو یه سری از مدل‌های خاص از این الگو، می‌تونی دقیقاً با ارورِ واقعیِ `E0597` یعنی "borrowed value does not live long enough" رو‌به‌رو بشی، چون کامپایلر مجبوره که تو زمانِ drop شدنِ `guard`، رابطه‌ی اون رو با مقداری که داره ازش استخراج می‌شه (read out) بررسی و محاسبه کنه. گره‌زدنِ (Binding) مقدارِ `guard*` به یه متغیر محلیِ مشخص (`count`) *قبل از* اینکه متغیرِ `guard` خودش drop بشه، کلاً صورتِ مسئله رو پاک می‌کنه — همون ثانیه‌ای که این خط اجرا می‌شه، متغیرِ `count` تبدیل می‌شه به یه متغیرِ کاملاً مستقل از نوعِ `i64` که هیچ ربط و وابستگی‌ای به `guard` نداره. تو این حالت خاص، استفاده‌یِ صریح از کلمه‌یِ `drop(guard)` واقعاً ضروری نبود (چون این متغیر به صورت خودکار تو انتهای بلوک drop می‌شد)، اما دقیقاً همون لحظه‌ای رو که "کارمون با قفل تموم شد" رو برای خواننده کاملاً واضح و مشخص (visible) می‌کنه، که خب این کار به موازات بزرگتر شدن بدنه‌ی هندلرها، ارزشش رو بیشتر نشون میده — نگه داشتنِ یه قفل (lock) واسه حتی یه لحظه بیشتر از اون چیزی که واقعاً بهش نیاز داری، دقیقاً همون چیزیه که تو شرایطی که بار و ترافیکِ همروندی روی سرورت زیاده، یه `Mutex` رو از یه محافظ تبدیل می‌کنه به یه گلوگاهِ (bottleneck) وحشتناک.

```rust
pub fn app(state: AppState) -> Router {
    Router::new()
        .route("/", get(hello))
        .route("/greet/{name}", get(greet))
        .route("/echo", post(echo))
        .route("/counter", get(get_counter))
        .route("/counter/increment", post(increment_counter))
        .with_state(state)
}
```

هر بار فراخوانیِ متدِ `.route` به قبلی زنجیر شده (chained) (`()Router::new` مقدارِ `Self` رو برمی‌گردونه، متدِ `.route` اون رو مصرف می‌کنه (consumes) و بازم مقدارِ `Self` برمی‌گردونه)، و کلِ فرآیند ساختِ روتر تو یه عبارت (expression) واحد انجام می‌شه — دقیقاً همون الگوی سازنده‌ای (builder pattern) که قبلاً تو درسِ move-semantics و برای ساختارِ `reclaim_and_extend` دیده بودیش، منتهی این بار تو مقیاسِ یه سطح API کامل پیاده‌سازی شده.

## در مورد سؤال‌های مرور

**سؤال ۱ (چیزی که باید تو DRF با دست بنویسی):** یه ویو (view) تو DRF مجبوره که به صورت خیلی صریح متدِ `()serializer.is_valid` رو صدا بزنه، خروجیِ بولینِ (boolean) این تابع رو چک کنه، و تو شاخه‌ی شکستِ اون (failure branch) با دست بنویسه که خروجیِ `Response(serializer.errors, status=400)` برگردونده بشه — اگه تو یادت بره که این چک رو بنویسی، همون داده‌های نامعتبر به صورت کاملاً بی‌سروصدا می‌ریزن تو متغیرِ `serializer.validated_data` (یا اینکه بعداً و تو عمقِ کدهات با یه خطایِ به مراتب گنگ‌تر برنامه رو متوقف می‌کنن). استخراج‌کننده‌ی (extractor) نوعِ `<Json<T>` تو فریم‌ورکِ `axum`، تضمینِ اینکه "بدنه‌ی هندلر تو تنها و تنها با یه `T`ِ معتبر و کاملاً پارس‌شده کارش رو شروع می‌کنه" رو تبدیل کرده به یه تضمینِ *سطحِ-نوع (type-level)* که حتی قبل از اینکه کدت بخواد یه خط اجرا بشه به طور کامل اعمال (enforced) می‌شه، نه اینکه صرفاً یه قانون نانوشته یا یه قراردادِ عرفی (convention) باشه که تو هر فراخوانی مجبوری یادت بمونه رعایتش کنی.

**سؤال ۲ (چرا کلون‌گرفتنِ `AppState` باعث نمی‌شه که هر درخواست یه شمارنده‌ی مجزا برای خودش داشته باشه):** ساختارِ `<Arc<Mutex<i64>>>` تو دو لایه کار می‌کنه: نوعِ `Arc` (که شمارشگرِ ارجاعِ اتمیه یا atomic reference count) باعث می‌شه تا عمل کلون کردن کلاً ارزون باشه و در ضمن کاری می‌کنه که تک‌تک اون کلون‌ها، یه پوینتر به *همون* حافظه‌ی مشترک روی هیپ (heap) دریافت کنن؛ و از طرفی نوعِ `Mutex` هم مراقبته که به محتویات داخل اون فضای مشترک، با رعایت نوبت دسترسی پیدا بشه. وقتی که متغیرِ `AppState` رو کلون (clone) می‌کنی، در واقع داری اون `Arc` رو کلون می‌کنی (فقط مقدار یه شمارنده رو بالا می‌بری، نه اینکه بیای خودِ عددِ `i64` رو تو حافظه کپی کنی) — در نتیجه هرکدوم از هندلرها با صدا زدنِ استخراج‌کننده‌یِ `<State<AppState>`، به یه کپی می‌رسن که نوکِ پیکانِ پوینترش، مستقیماً به همون ساختارِ `<Mutex<i64>`ِ یگانه‌ی تو مموری اشاره می‌کنه. این دقیقاً همون نقشِ «به اشتراک گذاشتن حافظه، به شکل *ایمن* تو شرایط دسترسیِ همروند (concurrent access)» رو بازی می‌کنه که تو ماژول همروندی دیدی، منتهی این بار اون «دسترسیِ همروند»، به‌جایِ ریسمان‌هایی (threads) که تو دستی spawn کرده بودیشون، همون درخواست‌های همروندِ HTTP هستن.

**سؤال ۳ (کدوم کارها از ماژول ۴ به بعد تو هندلرها منتظرِ `.await` می‌مونن):** کوئری‌های دیتابیس — مثل کدِ `sqlx::query(...).fetch_one(&pool).await` (ماژول ۴). اگه یه تابعِ همگام (synchronous) بخواد کدی شبیه به این رو فراخوانی کنه، چاره‌ای نداره جز اینکه اون ریسمانِ سیستم‌عامل (OS thread) که داره روش ران می‌شه رو تا وقتی دیتابیس جواب بده فلج و قفل (block) کنه، و از اونجایی که `tokio` میاد یه عالمه تسکِ همروند رو می‌ریزه رو دوشِ یه استخر (pool) کوچیک از ریسمان‌ها (بحثِ ریسمان-به-ازای-اتصال تو ماژول ۱ یادت بیاد)، قفل شدن یکی از اون فراخوانی‌ها، تمام تسک‌های *دیگه‌ای* که برنامه‌ریزی شدن تا رو همون ریسمان اجرا بشن رو به طور کامل معطل و از کارافتاده (stall) می‌کنه. اما کلمه‌یِ `.await`، موقعِ منتظر موندن برای رسیدن نتیجه، کنترلِ اون ریسمان رو پس می‌ده دستِ زمان‌اجرا (runtime)، دقیقاً همون‌طوری که کلمه‌ی `await` تو کتابخونه‌ی `asyncio`، کنترل رو پس می‌داد دستِ حلقه‌یِ رویداد (event loop).

**سؤال ۴ (فریم‌ورکِ `axum` دقیقاً قبل از اینکه اون الگو (pattern) بیاد استخراجش کنه، چی به دستِ هندلر `greet` میده):** نوعِ `<Path<String>` — که تو زبانِ Rust بهش می‌گن یه structیِ توپل-مانند (tuple struct) که داره اون مقدارِ کشیده‌شده از مسیر رو تو دلِ خودش قایم می‌کنه (wrap می‌کنه). عبارتِ `Path(name)` تو جایگاهِ پارامترها، در واقع یه *الگوی استخراج‌کننده (destructuring pattern)* برای اون ظرف و پوسته‌ی روییه، که مستقیماً اون `String`ِ داخلی رو از تو شکمش در میاره و تو همون لحظه و یه تیکه‌، تو متغیر `name` ذخیره‌اش (bind) می‌کنه — این کار دقیقاً معادلِ اینه که امضای تابعت رو بنویسی `<path: Path<String` و بعد تو خط اولِ بدنه‌یِ تابع بنویسی `;let name = path.0`، فقط با این تفاوت که اینجا برای سادگی خیلی ترتمیز رفته تو دل همون امضای تابع (inlined).

**سؤال ۵ (خطای ۴۰۴ خودکار، و چیزایی که واقعاً نیاز به کد کاستوم دارن):** روتینگ (URL resolver) تو فریم‌ورکِ جنگو (Django) دقیقاً با همین روش کار می‌کنه — پیدا نشدنِ یه آدرس (unmatched path) تو هر دو فریم‌ورک کاملاً بدونِ نیاز به کدنویسیِ تو با خطای 404 مواجه می‌شه؛ تو فقط زمانی میری سراغ نوشتن یه ویوی ۴۰۴ِ سفارشی (custom 404 view) که دلت بخواد یه *محتوای (content)* متفاوت با اون ظاهرِ پیش‌فرض به کاربر نشون بدی. اما اونجایی که قضیه جالب می‌شه اینه: رسوندنِ یه درخواست به مسیری که وجود داره، اما با یه متدِ HTTPِ کاملاً غلط و اشتباه. کلاسِ `Router` تو فریم‌ورکِ `axum` این مشکل رو هم باز به طور اتوماتیک هندل می‌کنه — عبارتِ `.route("/echo", post(echo))` فقط و فقط متدِ `POST` رو روی اون آدرس ثبت می‌کنه، بنابراین اگه یه درخواستِ `echo/ GET` بهش برسه، باز هم با صفر خط کدنویسی از طرف تو، مستقیماً خطای `405 Method Not Allowed` رو برمی‌گردونه، چون هر مسیری، متدهایِ مجازِ خودش رو جدای از اینکه اصلاً مسیر پیدا می‌شه یا نه، تو خودش ثبت می‌کنه و نگه می‌داره. کلاس‌ویوهای جنگو (class-based `View`) هم دقیقاً همین کارو می‌کنن (یعنی به ازای هر متد، درخواست رو ارجاع (dispatch) می‌دن و واسه متدهای نامعتبر 405 می‌دن) — اما یه ویوی ساده‌ی تابعی (function-based view) تو جنگو *هرگز* این کار رو نمی‌کنه، و این تویی که با دستای خودت باید بری ببینی `request.method` چیه و مسیرهای درست و غلط رو براش تفکیک (branch) کنی.
