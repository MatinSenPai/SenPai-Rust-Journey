# ۰۲.۱ — مسیریابی (Routing)، هندلرها، استخراج‌کننده‌ها (extractors)

## هر چیزی که تو ماژول ۱ با دستِ خودت ساختی، الان دیگه وظیفه‌ی یه کتابخونه‌ست

ماژول ۱ اومد و با دست‌های خالی، یه حلقه‌ی `TcpListener`، یه خواننده‌ی درخواست خط‌به‌خط، و یه پارسرِ HTTP در سطح بایت رو نوشت. اما `axum` (که روی دوشِ `tokio` و `hyper` سواره) تمام این کارا رو برات انجام می‌ده — یعنی قبول کردنِ اتصالات (connections)، خوندن و پارس کردنِ درخواست‌ها، تطبیق دادنِ یه مسیر (path) با یه تابع مشخص، و تو مرحله‌ی آخر، سریالایز کردنِ خروجیِ تو و تبدیلش به یه پاسخ (response) استانداردِ HTTP. چیزی که باقی می‌مونه تا تو زحمتِ نوشتنشو بکشی، دقیقاً و دقیقاً همون بخشیه که جنگو هم به عهده‌ی تو می‌ذاره: نوشتنِ **مسیرها (routes)** و **ویوها (views)** (که اینجا بهشون "هندلر - handlers" می‌گیم).

## هندلرها، توابعی از جنسِ async هستن با پارامترهایی که نوعشون مشخصه

```rust
async fn greet(Path(name): Path<String>) -> String {
    format!("Hello, {name}!")
}
```

اگه از دنیای جنگو میای دو تا چیز اینجا کاملاً جدیده، و جفتشونم خیلی مهم هستن:

1. **کلمه‌ی `async fn`.** تک‌تکِ هندلرهای `axum` روی زمان‌اجرایِ غیرهمگامِ (async runtime) کریتِ `tokio` اجرا می‌شن (این دقیقاً همون راه‌حل برای بحثِ "چرا ریسمان‌ها (threads) تو مقیاس‌پذیری جوابگو نیستن" تو ماژول ۱ هست). هیچ‌کدوم از مثال‌های این درس هنوز از `await.` برای هیچ‌چیزی *درونِ* بدنه‌ی یه هندلر استفاده نمی‌کنن — سر و کله‌ی `await.` تازه تو ماژول ۴ و زمانی که یه هندلر بخواد با دیتابیس حرف بزنه پیدا می‌شه — اما تابعِ تو همچنان باید با کلمه‌ی کلیدیِ `async fn` تعریف بشه، چون این دقیقاً همون traitایه که `axum` از یه هندلر انتظار داره تا پیاده‌سازیش کرده باشه.
2. **لیستِ پارامترها در واقع خودِ درخواسته (request)، که بر اساسِ نوع (type)، قطعه‌قطعه (destructure) شده.** فریم‌ورکِ `axum` میاد به *نوعِ (type)* هرکدوم از پارامترهات نگاه می‌کنه و متدِ `FromRequest` (یا `FromRequestParts`) که مربوط به همون نوع هست رو صدا می‌زنه تا اون دیتا رو از تو دلِ درخواستِ ورودی بکشه بیرون. نوعِ `<Path<String>` یکی از بخش‌هایِ (segment) مسیرِ URL رو استخراج می‌کنه. نوعِ `<Json<T>` یه بدنه‌ی درخواستِ JSON رو پارس (و از طریقِ `serde` اعتبارسنجی (validates)) می‌کنه و تبدیلش می‌کنه به نوعِ `T`. نوعِ `<State<S>` هم هر وضعیتِ مشترک و سراسری‌ای (shared state) که به `Router` وصل کردی رو برات استخراج می‌کنه (که پایین‌تر توضیح داده شده). این یه پارس‌کردنِ *مبتنی بر نوع (type-directed)* هست — اینجا دیگه خبری از یه جستجوی دستی تو دیکشنری مثلِ `[...]request.GET` نیست؛ تو فقط بهش می‌گی که تو امضای تابعِت (signature) چه چیزایی رو لازم داری، و اونا به صورت خودکار و پارس‌شده تو بدنه‌ی تابع در اختیارت قرار می‌گیرن، و اگه هم نتونن پارس بشن، اون درخواست اصلاً به تابع تو نمی‌رسه که بخوای درگیرش بشی (بخش بعدی رو بخون).

## استخراج‌کننده‌ها (Extractors): ابزارهای `Path`، `Json`، `State`

- **ابزار `<Path<T>`** — وظیفه‌اش اینه که یه دونه یا تعدادِ بیشتری از بخش‌های نام‌گذاری‌شده‌ی `{name}` رو از الگوی مسیر (route pattern) استخراج کنه، و اون رو تبدیل کنه به نوعِ `T` (که ممکنه یه دونه `<String>/<i64>` و... باشه، یا برای مچ کردنِ چندتا پارامتر با هم، یه توپل (tuple)/ساختار (struct) باشه). با کدِ `((Router::new().route("/greet/{name}", get(greet` تو به `axum` می‌فهمونی که `{name}` یه پارامتر تو مسیره؛ و با کدِ `Path(name): Path<String>` تو امضای هندلرِت، اون پارامتر رو از مسیر می‌کشی بیرون.
- **ابزار `<Json<T>`** — وظیفه‌اش اینه که بدنه‌ی درخواست رو از فرمتِ JSON بخونه (deserializes) و تبدیلش کنه به نوعِ `T` (البته `T` باید خصیصه‌ی `serde::Deserialize` رو پیاده‌سازی کرده باشه)، که این کار دقیقاً هم‌وزن و معادلِ همون کاریه که `()serializer.is_valid` به علاوه‌یِ `serializer.validated_data` تو DRF انجام می‌دادن. اگه هم از تو یه هندلر خروجیِ `<Json<T>` رو برگردونی، دقیقاً همین کار رو برعکس برات انجام میده: متغیرِ نوع `T` رو دوباره به شکل یه پاسخِ JSON سریالایز می‌کنه و به طور کاملاً اتوماتیک هدرِ `Content-Type` درست و مناسب رو هم روش تنظیم می‌کنه.
- **ابزار `<State<S>`** — وظیفه‌اش اینه که یه کپی (clone) از همون مقداری که موقع ساختنِ روتر به تابعِ `(Router::with_state(s` پاس دادی رو، در اختیارت بذاره. این دقیقاً همون روشیه که یه هندلر می‌تونه به یه وضعیتِ مشترک و طولانی‌مدت (مثلِ connection pool یا یه فضایِ ذخیره‌سازی داخلِ حافظه تو درس بعدی) دسترسی پیدا کنه، اونم بدونِ اینکه اصلاً نیازی به ساختنِ متغیرهایِ عمومیِ تغییرپذیر (global mutable variables) باشه — نقشی که این ابزار بازی می‌کنه، دقیقاً معادلِ همون نقشیه که تو جنگو فایلِ `apps.py` با `AppConfig` + اتصال به دیتابیس (که توسط ORM مدیریت می‌شه و اکثراً از دید تو پنهونه) انجام می‌ده، اما اینجا همه چی کاملاً صریح و واضحه.

## ترتیبِ قرارگیری استخراج‌کننده‌ها به شدت مهمه، و فرآیندِ شکست خوردن کاملاً خودکاره

فریم‌ورکِ `axum` استخراج‌کننده‌ها (extractors) رو **دقیقاً به همون ترتیبی که تو امضایِ (signature) تابع نوشتیشون، یکی‌یکی اجرا می‌کنه**، و اگه تو این مسیر *هرکدوم* از این استخراج‌کننده‌ها با خطا مواجه بشن (مثلاً یه بخش `<Path<i64>` که کلاینت توش یه متن فرستاده نه یه عددِ معتبر، یا یه بدنه‌ی `<Json<T>` که موفق نمی‌شه به نوع `T` دی‌سریالایز (deserialize) بشه)، `axum` همونجا درجا عملیات رو متوقف (short-circuit) می‌کنه و یه پاسخ خطا (تو مایه‌های کدِ 400 یا 422) رو **قبل از اینکه حتی یه خط از بدنه‌ی هندلر تو اجرا بشه** برای کلاینت می‌فرسته — اینطوری تو هیچ‌وقت تو کدت با یه درخواست که "نصفه‌ونیمه پارس شده" مواجه نمی‌شی. این رفتار به مراتب سخت‌گیرانه‌تر از رفتاریه که DRF تو پایتون داره، اونجا صدا زدنِ `()is_valid.` تو سریالایزر، مرحله‌ایه که *خود تو* باید حواست باشه که صداش بزنی و بعد براش یه دستور شرطی بنویسی (branch کنی)؛ اما اینجا تو `axum`، ورودیِ نامعتبر اصلاً و از همون ابتدا شانسِ این رو نداره که پاشو تو بدنه‌ی تابعِ تو بذاره.

## ترکیب کردن و ساختنِ یه `Router`

```rust
pub fn app(state: AppState) -> Router {
    Router::new()
        .route("/", get(hello))
        .route("/greet/{name}", get(greet))
        .route("/echo", post(echo))
        .route("/counter", get(get_counter))
        .route("/counter/increment", post(increment_counter))
        .with_state(state)
}
```

هر فراخوانیِ `(route(path, method_router.` میاد یه مسیر رو برای یه (یا حتی چند) متدِ HTTP ثبت می‌کنه (مثلاً `(get(handler` ، `(post(handler` و... — این متدها در واقع اون تابعِ غیرهمگامِ (async) تو رو، می‌پیچونن و می‌ذارن تو دلِ یه ساختاری که `axum::Router` می‌تونه کارها رو بهش ارجاع (dispatch) بده). دستورِ `with_state.` همون `AppState`ِ مشترک رو به این روتر متصل (attach) می‌کنه، تا از این به بعد هر استخراج‌کننده‌یِ `<State<AppState>` که تو هندلرها داری، بتونه یه کپی (clone) از همون وضعیتِ مشترک رو تحویل بگیره.

## تست کردنِ کدها بدون باز کردن یه سوکتِ (socket) واقعی، دوباره و دوباره

دقیقاً همون‌طوری که تابعِ `run_echo` تو ماژول ۱ اصلاً هیچ `TcpListener`ِ واقعی‌ای تو تست‌هاش باز نکرد، تو اینجا هم ساختارِ `axum::Router` خصیصه‌ی `tower::Service` رو پیاده‌سازی کرده؛ که معنیش اینه که تو می‌تونی یه درخواست کامل رو بگیری و از مرحله‌ی مسیریابی (routing) + استخراج داده‌ها (extraction) + اجرای هندلر + سریالایز کردنِ جواب، کلاً با تابعِ `(tower::ServiceExt::oneshot(request` عبورش بدی — **بدون اینکه اصلاً هیچ پورتی رو اِشغال (bind) کنی، یا بخوای درگیرِ یه عملیات ورودی/خروجیِ (I/O) شبکه‌ای بشی**. این کار دقیقاً همونیه که فایلِ `tests/routes_test.rs` داره انجام میده. اینم دوباره همون ایده‌ی «هل دادنِ I/O به لبه‌های برنامه، و تست‌پذیر نگه داشتنِ هسته‌ی کد» از تک‌تک درس‌های قبلیِ فاز ۳ هستش، که این‌بار فقط تو لایه‌ی فریم‌ورکِ HTTP و سطح بالاتری اعمال شده به جای اینکه مثل قبل تو سطحِ سوکت‌های خام باشه.

## وظیفه‌ی تو

بخش‌های `!()todo` تو فایل `src/lib.rs` رو پیاده‌سازی کن:

- هندلرِ `greet` — از مقدارِ استخراج‌شده‌ی `<Path<String>` استفاده کن تا یه پیامِ سلام (greeting) بسازی.
- هندلرِ `echo` — از مقدارِ استخراج‌شده‌ی `<Json<EchoRequest>` استفاده کن تا یه شیء از نوع `EchoResponse` بسازی.
- هندلرهایِ `get_counter` و `increment_counter` — از مقدارِ استخراج‌شده‌ی `<State<AppState>` استفاده کن تا اون شمارنده‌ی (counter) مشترک رو بخونی/تغییر بدی.
- تابعِ `app` — هر پنج تا مسیر (routes) رو رویِ یه دونه `Router` سیم‌کشی کن (wire up)، و در نهایت `state` رو هم بهش متصل (attach) کن.

کدهای فایل `src/main.rs` از قبل برات آماده شده — این فایل میاد یه `AppState` می‌سازه، تابعِ `(app(state` رو صدا می‌زنه، و با کمکِ `tokio` اون رو روی آدرسِ `127.0.0.1:3000` بالا میاره (serve می‌کنه).
