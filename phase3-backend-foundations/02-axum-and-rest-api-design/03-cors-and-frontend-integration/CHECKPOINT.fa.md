# چک‌پوینت

1. متدِ `prod_cors` طوری تنظیم شده که آدرسِ `https://anime.example.com` رو تأیید می‌کنه، و بعدش یهو یه پیش‌پرواز (preflight) از آدرسِ `https://evil.example.com` از راه می‌رسه. سرور با چه کُدِ وضعیتی (status code) جوابش رو می‌ده، و کدوم هدره که تو این جواب به صورت کاملاً (عامدانه) حذف شده و نمی‌آد؟ با زبونِ خودت بگو چرا جواب سرور تو این سناریو `403` نیست — *کدوم بازیگره* که تو واقعیت جلوی اون صفحه‌یِ شیطانی رو واسه خوندنِ پاسخِ سرور می‌گیره، و دقیقاً تو کدوم لحظه؟
2. کدوم یکی از این درخواست‌ها باعث راه افتادنِ یه پیش‌پرواز (preflight) می‌شه، و چرا: (الف) یه درخواستِ ساده‌یِ `GET /anime` بدون هیچ هدرِ سفارشی (custom headers)، (ب) یه درخواستِ `POST /anime` که هدرش `Content-Type: application/json` هست، (پ) یه درخواستِ `GET /anime` که توش هدرِ `*** Authorization: Bearer` قرار داره؟
3. تابعِ `app` هیچ مسیرِ `OPTIONS`ای رو هیچ‌کجایِ خودش ثبت و رجیستر نکرده، اما با این وجود تک‌تکِ درخواست‌های preflight تو تست‌هایِ `tests/cors_test.rs` دارن یه جوابِ `200`ِ تروتمیز با هدرهای کاملاً درست برمی‌گردونن. این درخواستِ `OPTIONS` دقیقاً داره از کدوم بخش و کجا جواب می‌گیره، و این موضوع در موردِ اینکه لایه‌ها (layer) و روترها (router) با چه ترتیبی یه درخواست رو ملاقات می‌کنن، چه رازی رو برات برملا می‌کنه؟
4. چرا قوانینِ وب (spec) (و همینطور کتابخونه‌ی `tower-http`، از طریق یه پنیکِ کاملاً عامدانه) ترکیب کردنِ متغیر `Any` با `(allow_credentials(true.` رو مطلقاً ممنوع می‌کنن؟ یه حمله‌ی فرضی رو توضیح بده که اگه این ترکیب مجاز بود، قابل پیاده‌سازی و اجرا می‌شد.
5. یکی از هم‌تیمی‌هات تابعِ `()dev_cors` رو "موقتاً" رو سرورِ پروداکشن شیپ و دیپلوی می‌کنه. API شما کلاً احراز هویت مبتنی بر کوکی (cookie-based auth) نداره — فقط با هدرهایِ `Authorization` کار می‌کنه که کدهایِ فرانت‌اند هم با دست به درخواست‌هاشون می‌چسبوننش. با این شرایط، وجودِ یه وایلدکارد (`*`) چه چیزایی رو تو سیستم به خطر می‌ندازه و تو دید قرار میده، و اصولاً چرا همون تابعِ `prod_cors` با تنظیمِ دقیقِ یه دونه origin خاص تو این سناریو همون تصمیم و رویکردِ درستیه که باید انجام بشه؟
