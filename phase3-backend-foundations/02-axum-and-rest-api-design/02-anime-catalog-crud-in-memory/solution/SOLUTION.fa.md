# راه‌حل

```rust
pub fn create(&self, input: CreateAnime) -> Result<Anime, AnimeError> {
    validate_rating(input.rating)?;

    let mut inner = self.inner.lock().unwrap();
    inner.next_id += 1;
    let id = inner.next_id;
    let anime = Anime { id, title: input.title, status: input.status, rating: input.rating };
    inner.items.insert(id, anime.clone());
    Ok(anime)
}
```

عملِ اعتبارسنجی (Validation) **قبل از اینکه** اصلاً قفلی (lock) گرفته بشه انجام شده — اصلاً هیچ دلیلی نداره بخوای تمامِ درخواست‌های دیگه رو پشتِ درِ بسته و روی یه mutex معطل کنی، فقط به خاطر اینکه می‌خوای یه ورودیِ پرت و پلایی رو که از همون اولش معلوم بوده قراره رد بشه (reject بشه) رو چک کنی. دستورِ `1 =+ inner.next_id` و بعدش `let id = inner.next_id` (به جای اینکه بیای از مقدارِ *قدیمی و قبلی* استفاده کنی و تازه بعدش اونو بالا ببری) باعث می‌شه تا آیدی‌های (IDs) ساخته‌شده همیشه از ۱ شروع بشن و نه از ۰، که خب این دقیقاً همون چیزیه که تستِ `create_assigns_an_id_starting_at_one` می‌خواد و چکش می‌کنه.

```rust
pub fn update(&self, id: u64, input: UpdateAnime) -> Result<Anime, AnimeError> {
    validate_rating(input.rating)?;
    let mut inner = self.inner.lock().unwrap();
    let anime = inner.items.get_mut(&id).ok_or(AnimeError::NotFound)?;
    if let Some(title) = input.title { anime.title = title; }
    if let Some(status) = input.status { anime.status = status; }
    if input.rating.is_some() { anime.rating = input.rating; }
    Ok(anime.clone())
}
```

متدِ `get_mut` (و نه `get` خالی) دقیقاً همون چیزیه که اجازه می‌ده بتونی تو همون نقطه‌ای که مقدار وجود داره (in-place) روی فیلدهاش رونویسی (overwriting) کنی — تو این خط، متغیر `anime` از نوعِ `mut Anime&` هستش که مستقیم از تو دلِ خود `HashMap` قرض (borrow) گرفته شده، بنابراین دستورِ `anime.title = title` دقیقاً و مستقیماً همون مقداری که تو ذخیره‌گاه هست رو تغییر می‌ده (mutate می‌کنه)، و در نتیجه اصلاً هیچ نیازی به جایگذاری و درج دوباره‌ی اون (re-insertion) نیست. دستورِ `()input.rating.is_some` (به جایِ استفاده از الگوها مثل `(if let Some(rating) = input.rating`) یه کار کاملاً عمدیه: نوعِ `<Option<u8>` خصیصه‌ی `Copy` رو پیاده‌سازی کرده، پس کُدِ `anime.rating = input.rating` می‌تونه بدونِ اینکه نیاز باشه متغیر `Option` رو اول باز (unwrap) کنه و بعدش دوباره اونو ببنده (rewrapping)، کلاً با همون یه انتسابِ ساده کُلِ اون `Option` رو مستقیماً منتقل (move) کنه.

```rust
pub async fn create_anime(
    State(store): State<Arc<AnimeStore>>,
    Json(input): Json<CreateAnime>,
) -> Result<(StatusCode, Json<Anime>), AnimeError> {
    let anime = store.create(input)?;
    Ok((StatusCode::CREATED, Json(anime)))
}
```

علامت `?` که اینجا گذاشته شده بدون هیچ دردسری کار می‌کنه، چرا که خروجی خطای `AnimeError` از قضا همون نوع خطای اختصاصیِ خودِ هندلر هم هست — در نتیجه خروجیِ `<Result<Anime, AnimeError>` که از `store.create` برمی‌گرده خیلی راحت و مستقیم منتشر و پاس داده می‌شه (propagates). خروجیِ `<(StatusCode, Json<Anime>)>` در واقع یه توپله (tuple) که خودش خصیصه‌ی `IntoResponse` رو پیاده‌سازی می‌کنه (کریتِ axum این خصیصه رو واسه هر توپلِ `<(StatusCode, T)>`ای که توش اون `T`ِ بدنه خودش از قبل `IntoResponse` رو پیاده‌سازی کرده باشه، تأمین می‌کنه) — و این دقیقاً همون مکانیزمیه که بهت اجازه میده تا بتونی اون حالتِ پیش‌فرض یعنی پاسخِ `200 OK`ای که اگه یه `<Json<Anime>`یِ خالی رو برمی‌گردوندی خودبه‌خود تولید می‌شد، رو باطل (override) کنی و کد وضعیتِ دلخواهت رو برگردونی.

```rust
pub fn app(store: Arc<AnimeStore>) -> Router {
    Router::new()
        .route("/anime", get(list_anime).post(create_anime))
        .route("/anime/{id}", get(get_anime).patch(update_anime).delete(delete_anime))
        .with_state(store)
}
```

## در مورد سؤالات چک‌پوینت

**سؤال ۱ (کجای برنامه واقعاً اصلِ منطق قرار داره):** کُلِ منطق، دقیقاً و به تمام کمال تو ساختار `AnimeStore` جا خوش کرده — هندلرها فقط یه سری آداپتور و مبدّلِ نازک (thin adapters) هستن که کارشون اینه که داده رو از تو استخراج‌کننده (extractor) بکشن بیرون (unwrap کنن)، یکی از متدهای store رو صدا بزنن، و در نهایت نتیجه‌ی اون رو بپیچونن و به شکل جواب برگردونن. اگه می‌خواستی منطقِ `create` رو مستقیماً تو شکمِ هندلر `create_anime` بنویسی، اونوقت هر تستت مجبور بود صرفاً واسه اینکه چک کنه "آیا اگه یه انیمه با ریتینگ ۱۱ بدم رد می‌شه و ارور می‌ده یا نه؟"، کُلِ پشته‌ی وب و مسیریابی رو به کمکِ `tower::ServiceExt::oneshot` همراه با یه ریکوئست HTTP واقعی (یا in-memory) بالا بیاره — در واقع برای تست کردن یه قانون ساده‌ی اعتبارسنجی (validation rule) که رسماً یه منطقِ همگام (synchronous) و خالصه، باید کُلِ ماشین‌آلات مربوط به HTTP رو فعال می‌کردی. نگه داشتن این منطق تو داخلِ `AnimeStore` دقیقاً همون کلید و رازیه که به فایلِ `tests/store_test.rs` اجازه‌ی حیات می‌ده: یه مجموعه‌تستِ فوق‌العاده سریع، بدون نیاز به بالا آوردن محیط async با `[tokio::test]#`، بدون هیچ درگیری و زحمتی بابت لوله‌کشی‌هایِ request/response، و صرفاً به شکلِ یه فراخوانی تابع ساده به ازای هر ادعا و تست (assertion).

**سؤال ۲ (چطور مفهومِ "پاک کردن کامل فیلد" رو در مقابلِ مفهوم "کلاً به این فیلد دست نزن" نشون بدیم):** ترفند استاندارد واسه این کار استفاده از یه ساختار دوگانه‌یِ (double) `Option` هستش: یعنی `<<rating: Option<Option<u8`، یا اینکه بیای یه دونه enum کوچیک دقیقاً با همین الگو بسازی، مثلاً `enum Patch<T> { Unset, SetTo(T), Clear }`. با ساختارِ `<<Option<Option<u8>>`: اگه اون لایه‌یِ بیرونی کلاً `None` باشه = یعنی فیلد تو اون بدنه‌ی JSON اصلاً فرستاده نشده = معنیش می‌شه "کلاً بهش دست نزن"؛ اگه لایه‌ی بیرونی `Some` و لایه‌ی داخلی `None` باشه یعنی `(Some(None` = یعنی فیلد به طور واضح با یه دیتای `null` تو فایلِ JSON فرستاده شده = معنیش می‌شه "کلاً محتویاتِ قبلیشو پاک کن"؛ و اگه تو لایه‌های بیرونی و داخلی مقدار باشه یعنی مثلاً `((Some(Some(9` = یعنی هم فیلد فرستاده شده و هم مقدار داره = معنیش می‌شه "مقدارشو بذار رو این عدد جدید." البته واسه اینکه بتونی به `serde` حالی کنی تا بتونه واقعاً موقعِ خوندن دیتا، تفاوتِ "کلاً فیلدی تو فایل نبود" رو با "فیلد بود ولی مقدارش خالی و null بود" رو برای این ساختار متوجه بشه، به استفاده از صفتِ `["(serde(default, with = "::serde_with::rust::double_option#]` (از طریقِ کریتِ `serde_with`)، و یا پیاده‌سازی کاملاً دستی و سفارشیِ خصیصه‌ی `Deserialize` نیاز داری — استفاده از یه `[(derive(Deserialize#]` ساده و خالی رو یه نوعِ `<<Option<Option<u8>` باعث می‌شه تا `serde` به طور پیش‌فرض هر دوتا حالتِ بالا رو یکی کنه و کلاً جفتشونو بریزه تو همون قالبِ `None`، که خب این دقیقاً همون تله‌ایه که اگه یروزی خواستی از این الگو استفاده کنی باید حتماً حواست بهش باشه.

**سؤال ۳ (چرا خیلی ساده فقط `<Json<Anime>` برنگردونیم):** فریم‌ورکِ `axum` به طور پیش‌فرض کُدِ وضعیتِ (status code) تمام پاسخ‌های موفقیت‌آمیزش رو می‌ذاره روی `200 OK`، مگه اینکه تو صراحتاً خلافشو بگی. کُدِ `200` تو دنیای وب به معنیه "بفرما، این وضعیتِ فعلیِ چیزیه که از همون اولش هم وجود داشت" — در حالی که برای یه درخواست `POST` که دقیقاً همین الان یه منبعِ (resource) *جدید* رو به وجود آورده، طبق عرف و قراردادِ HTTP (و البته طبقِ انتظاراتِ هر کسی که داره از API استفاده می‌کنه، و این شامل همون رفتار پیش‌فرض `CreateAPIView` تو DRF هم می‌شه) کُدِ وضعیت باید `201 Created` باشه. اگه فقط `<Json<Anime>` رو برمی‌گردوندی کدِ تو صددرصد کامپایل می‌شد و به صورت فنی و مکانیکی هم کار می‌کرد، اما هر کلاینتی (و هر ابزاری که میاد از روی اون کدِ وضعیت تصمیم‌گیری می‌کنه که مثلاً این درخواست باید دوباره تلاش بشه (retry)، کَش بشه (cache)، یا اینکه باید کلاً به عنوان یه پاسخ خطا در نظر گرفته بشه) یه سیگنالِ کاملاً ظریف و کاملاً اشتباه دریافت می‌کرد.

**سؤال ۴ (یه پاکت (envelope) یکسان واسه هرچیزی که با موفقیت انجام شد):** این کلاً از اون چیزی که واسه مدیریت خطاها انجام دادیم یه تغییر **خیلی بزرگتر** و اساسی‌تریه. تو حالتِ خطاها، ما فقط به یه دونه `impl IntoResponse for AnimeError` نیاز داشتیم چون به هر حال تک‌تکِ خطاهایی که رخ می‌دادن مثل یه قیف می‌ریختن تو دلِ همون یه دونه نوع (type). اما پاسخ‌های موفقیت‌آمیز اصلاً هیچ نوعِ (type) مشترکی ندارن — تابعِ `list_anime` مقدار `<Json<Vec<Anime>>` برمی‌گردونه، تابعِ `get_anime` مقدار `<Json<Anime>>` برمی‌گردونه، تابع `delete_anime` فقط یه دونه `StatusCode` خالی رو بدون هیچ بدنه‌ای (body) برمی‌گردونه. قرار دادنِ همه‌ی اینا تو دلِ یه پاکتِ مشترکِ یکسان، یا نیازمند اینه که بیایم یه نوعِ سفارشی و پوششیِ جنریک مثلِ `} { ApiResponse<T> { data: T` تعریف کنیم و بعدش نوعِ بازگشتی (return type) تک‌تکِ هندلرها رو تغییر بدیم تا از اون استفاده کنن، یا اینکه (و این دقیقاً همون رویکردِ ماژول ۷ هستش) بیایم یه میان‌افزار (middleware) از طریق `tower::Layer` اعمال کنیم که وظیفه‌اش این باشه که تو آخرین لایه‌ی سرور، بدنه‌ی تمام پاسخ‌های خروجی رو به صورت کاملاً یکدست و ترتمیز از اول بازنویسی (rewrite) کنه، که این روش دوم اصلاً نیازی به دست بردن تو تک‌تک هندلرها نداره اما خب از طرفی، این یه ابزارِ فوق‌العاده پیشرفته‌تر و پیچیده‌تر از تمام چیزاییه که ما تا الان تو این درس خوندیم و یادشون گرفتیم.

**سؤال ۵ (چرا یه قفل `Mutex` به جای دو تا):** اگه دو تا قفل مجزا داشتیم، یه درخواست `create`ِ دیگه می‌تونست دقیقاً بیاد و خودشو وسطِ اون پروسه‌ی "خوندن/اضافه‌کردن متغیر `next_id`" و مرحله‌یِ "ثبت کردن نتیجه (insert) تو فیلد `items`" جا کنه (interleave بشه) — مثلاً، دو تا فراخوانیِ همروند (concurrent) از تابعِ `create`، هردوشون می‌تونستن همون لحظه مقدار متغیر `next_id` رو `0` بخونن، هردوشون بیان اونو به علاوه ۱ بکنن و تبدیلش کنن به `1`، و هردوشون همزمان سعی کنن دیتای جدیدشون رو روی همون کلیدِ (key) برابر با `1` درج کنن (insert کنن)، و در نتیجه دومین درخواستی که عمل insert رو انجام می‌داد، کاملاً بی‌سروصدا می‌اومد تمام دیتای اولین درخواست رو برای همیشه رونویسی و پاک می‌کرد (متد `HashMap::insert` اگه کلیدی که می‌خواد ذخیره کنه از قبل وجود داشته باشه، خیلی راحت اون مقدار قدیمی رو پرت می‌کنه بیرون). این دقیقاً همون یه باگ و شرط مسابقه‌ایِ (race condition) کلاسیک تو از دست رفتن اطلاعاته (lost-write). داشتنِ یه دونه `Mutex` واحد که وظیفه‌ی محافظت و نگهبانی از هردویِ این فیلدها رو به صورتِ هم‌زمان و یک‌جا به عهده داره، باعث می‌شه که کلِ فرآیندِ "اضافه کردن به `next_id`، و در پی اون درج کردن (insert) تو لیست"، کلاً تبدیل به یه واحد اتمیِ (atomic unit) یکپارچه از نگاه بقیه‌ی ریسمان‌ها/تسک‌ها بشه — بنابراین هیچ شخص دیگه‌ای نمی‌تونه تو اون فاصله‌ی کوتاه بین اون دو تا مرحله، وضعیتِ برنامه‌رو کلاً ببینه یا وسطش دخالتی داشته باشه.
