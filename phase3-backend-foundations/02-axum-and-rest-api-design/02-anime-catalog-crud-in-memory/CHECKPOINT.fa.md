# چک‌پوینت

1. فایل تستِ `tests/store_test.rs` هرگز و به هیچ وجه فریم‌ورکِ `axum` رو ایمپورت نکرده و هیچ‌کجا هم چیزی شبیه به `Request` نساخته، اما با این وجود داره تمام و کمال تک‌تک قوانینِ اعتبارسنجی (validation) و سناریوهایِ "پیدا نشد" (not-found) که این API داره رو چک می‌کنه و پوشش میده. این قضیه چه چیزی رو در موردِ اینکه منطقِ *واقعیِ* این درس کجا قرار داره بهت ثابت می‌کنه — تو دلِ هندلرهاست یا تو دلِ store؟ اگه بیایم و تمام منطقِ متدِ `AnimeStore::create` رو برداریم و کلاً بندازیمش تو شکمِ همون هندلرِ `create_anime` (به جای اینکه واسه خودش یه نوعِ مستقل و جدا باشه)، دقیقاً چی تو استراتژی و مدلِ تست‌نویسیت تغییر می‌کنه و عوض می‌شه؟
2. تستِ `update_overwrites_only_the_fields_that_were_set` بررسی می‌کنه و مطمئن می‌شه که اگه تو نوعِ ورودیِ `UpdateAnime`، فیلدِ `title` به صورتِ `None` پاس داده شده بود، عنوان و تایتلِ اون انیمه تو ذخیره‌گاه (store) کلاً دست‌نخورده و بدون تغییر باقی بمونه. از طرفی ساختارِ `UpdateAnime` هیچ راهی نداره که بخواد مفهومِ «از قصد این امتیازِ (rating) قبلی رو پاک کن و برگردون به همون حالتِ امتیازنداده‌شده» رو ابراز کنه — پاس دادنِ `rating: None` تو این ساختار، همیشه و همیشه فقط یعنی "کلاً بهش دست نزن". به نظرت چه تغییری تو شکلِ نوعِ `UpdateAnime` می‌شه داد تا بتونه واسه فیلدی مثل `Option<u8>`، هم مفهومِ "بهش دست نزن" رو ساپورت کنه و هم مفهومِ "صریحاً اینو از مقدارِ قبلیش پاک کن" رو؟ (نیازی نیست حتماً کدش رو پیاده‌سازی کنی — فقط شکل اون نوعِ جایگزین (type) رو توصیف کن.)
3. نوع خروجیِ (return type) هندلرِ `create_anime` به این صورته: `<Result<(StatusCode, Json<Anime>), AnimeError>`. تو شاخه‌ی موفقیتِ این هندلر، اصولاً چه نیازی بود که صریحاً از عبارتِ `StatusCode::CREATED` استفاده بشه — اگه کلاً اون رو نمی‌نوشتی و فقط همون مقدارِ `<Json<Anime>` رو خالی و مستقیم برمی‌گردوندی، فریم‌ورکِ `axum` از چه کد وضعیتی (status code) برای خروجی استفاده می‌کرد، و اصلاً چرا استفاده از اون کدِ پیش‌فرض برایِ درخواستی که از نوع `POST`ه و داره یه چیزی رو ایجاد (create) می‌کنه، کلاً یه اشتباه و یه حرکتِ غلطه؟
4. تک‌تکِ پاسخ‌های خطا (error response) تو این درس یه شکلِ ثابت دارن: `"..." :"error"}`، که دلیلش هم همون پیاده‌سازیِ یک‌باره‌یِ `impl IntoResponse for AnimeError` هستش. اگه می‌خواستی کاری کنی که تک‌تکِ پاسخ‌های *موفقیت‌آمیزِ (successful)* تو هم همه‌شون از یه پاکت یا قالبِ یکسان و ثابت (مثلاً `} ... :"data"{`) استفاده کنن، دقیقاً چه چیزایی رو تو این فایل باید تغییر می‌دادی — آیا در مقایسه با اون حالتِ خطا (error case)، این یه تغییرِ بزرگتر حساب می‌شد یا یه تغییر کوچیکتر، و چرا؟
5. ساختارِ `AnimeStore` داره از یه `<Mutex<StoreInner>` استفاده می‌کنه — یعنی از یک دونه قفلِ واحد، واسه محافظت از هر دویِ `next_id` و `items` به طور همزمان، به جای اینکه بخواد واسه هر فیلد یه `Mutex`ِ جداگونه بذاره. متد `create` وظیفه داره که هم متغیر `next_id` رو یکی بالا ببره و *هم* نتیجه رو داخلِ `items` ذخیره (insert) کنه، و این دو تا کار باید حتماً به عنوان یه عملیاتِ یکپارچه انجام بشن. اگه به جای این کار، واسه هرکدوم از این دو تا فیلد یه قفلِ جدا و مستقل (independently-locked) گذاشته بودیم، و همون وسط یه درخواستِ دیگه واسه فراخوانیِ متدِ `create` سر می‌رسید و اجراش می‌افتاد دقیقاً تو فاصله‌ی زمانیِ بینِ بالا بردن `next_id` توسط درخواست اول، و ذخیره شدنِ دیتای اون (insert) تو `items`، چه فاجعه و اتفاق بدی ممکن بود رخ بده؟
