# راه‌حل

```rust
pub fn group_joined_rows(rows: Vec<JoinedRow>) -> Vec<PostWithComments> {
    let mut posts: Vec<PostWithComments> = Vec::new();
    let mut index_of: HashMap<i64, usize> = HashMap::new();

    for row in rows {
        let index = *index_of.entry(row.post_id).or_insert_with(|| {
            posts.push(PostWithComments {
                post: Post { id: row.post_id, title: row.post_title.clone() },
                comments: Vec::new(),
            });
            posts.len() - 1
        });

        if let Some(comment_id) = row.comment_id {
            posts[index].comments.push(Comment {
                id: comment_id,
                post_id: row.post_id,
                body: row.comment_body.unwrap_or_default(),
            });
        }
    }

    posts
}
```

متغیرِ `<HashMap<i64, usize>` دقیقاً داره اینجا یه وظیفه رو انجام می‌ده: به یاد داشتنِ این موضوع که "من قبلاً واسه این `post_id` خاص یه آبجکتِ `PostWithComments` ساختم، و الانم دقیقاً تو ایندکسِ شماره‌ی N از متغیرِ `posts` نشسته،" در نتیجه پستی که ردیف‌هاش تو خروجی دیتابیس به صورت پشت‌سرهم و پیوسته (contiguous) نباشن (یا پستی که به تعداد کامنت‌هاش چندین و چند بار هی تو خروجی تکرار شده) فقط و فقط همون یه بارِ اول تو آرایه‌یِ `posts` وارد و اِپند (push) می‌شه. الگو و فرمِ `(...)index_of.entry(row.post_id).or_insert_with`، همون روشِ کاملاً استاندارد و مرسوم تو زبان Rust (idiomatic) واسه بیانِ این جمله‌ست که "برو دنبال این کلید بگرد، و اگه نبودش، این کلوژر رو اجرا کن تا مقدارش رو تولید کنه و واسه بعداً هم تو حافظه‌اش نگهش داره"، اونم همش تو یه فراخوانیِ ساده — این کلوژر علاوه بر اینکه یه `PostWithComments` جدید رو پوش (push) می‌کنه، همون لحظه ایندکس (index) اونو تو آرایه هم برمی‌گردونه، واسه همین توابعِ `entry`/`or_insert_with` خیلی راحت اون ایندکس رو مستقیم و بدون وقفه پاس می‌دن بیرون (thread out). اگه فیلدِ `comment_id` برابر با `None` باشه (همون حالتی که به خاطر `LEFT JOIN` یه پست هیچ کامنتی نداره)، برنامه خیلی ساده شرطِ `if let Some` رو نادیده می‌گیره و بی‌خیالش می‌شه، و اون متغیرِ `comments` واسه اون پست رو تو همون حالتی که از اولش بوده رها می‌کنه — که خب تو این حالت طبیعتاً همون آرایه‌یِ کاملاً خالیِ اولیه‌ست.

```rust
pub async fn posts_with_comments_naive(&self) -> Result<Vec<PostWithComments>, sqlx::Error> {
    let posts = self.list_posts().await?;
    let mut result = Vec::with_capacity(posts.len());
    for post in posts {
        let comments = self.comments_for_post(post.id).await?;
        result.push(PostWithComments { post, comments });
    }
    Ok(result)
}
```

این دقیقاً همون الگوی خطرناکِ N+1 هستش که کاملاً تر و تمیز نوشته شده: دستورِ `?await.list_posts()` می‌شه کوئریِ شماره ۱، و بعدش تو حلقه‌ی `for post in posts` به ازای **تک‌تک پست‌ها** یه بار متدِ `?await.(comments_for_post(post.id` صدا زده می‌شه — که هر کدومشون واسه خودشون یه بار صفر تا صد رفت‌و‌آمد و درخواست کامل به Postgres رو شامل می‌شن. روی ۲ تا پست این کلاً ۳ تا کوئری تو خودش داره؛ اما روی ۱۰,۰۰۰ تا پست تبدیل می‌شه به ۱۰,۰۰۱ تا کوئری. هیچ کدوم از کدهایی که اینجا نوشته شده به مفهوم رایجی که از "یه کُدِ اشتباه و غلط (wrong code)" داریم یه باگ محسوب نمی‌شن — تک‌تک اون کوئری‌ها، همگی کدهایِ SQL کاملاً صحیحی هستن که کاملاً هم به درستی اجرا می‌شن، و تستِ `naive_and_batched_agree_on_the_result` تو مجموعه‌تست‌هامون کاملاً اثبات می‌کنه که هر دو متد دارن خروجی دیتای کاملاً برابر و یکسانی رو برمی‌گردونن. باگِ قضیه تماماً برمی‌گرده به اینکه **دقیقاً با چند تا رفت‌وبرگشت (round trips)** به این نتیجه رسیدیم، و این دقیقاً همون دلیلیه که چرا این دسته از باگ‌ها تو پروسه‌ی بررسی کُد (code review) خیلی راحت از زیر دست آدم در میرن: تو کدهای اضافه‌شده (diff) هیچ چیزی به چشم اشتباه نمیاد، مشکل دقیقاً تو *شکل و الگوی دسترسی (access pattern)* هستش، و این باگ فقط زمانی خودش رو نشون می‌ده که بشینی واقعاً تعداد کوئری‌ها رو تو مقیاس‌های بالا بشماری یا تایمِ تأخیرها رو ببینی.

## چرا راه‌حل این مشکل، استفاده از یه `LEFT JOIN` به علاوه‌یِ یه دسته‌بندیِ کاملاً ناب (pure regroup) هستش، نه صرفاً اینکه "بیاین کمتر await کنیم"

متدِ `posts_with_comments_batched` برای اینکه این حلقه‌ی تکراری رو دور بزنه نیومده یهو تو مبحث `await`ها زرنگ‌بازی در بیاره — بلکه برای دور زدنش از اساس یه سؤالِ کلاً متفاوت از Postgres پرسیده. به جای اینکه بگه "کامنتایِ پست A رو بده من، بعد برو کامنتای پست B رو بیار، ..."، میاد با استفاده از یه `LEFT JOIN` از دیتابیس می‌خواد "تک‌تک ترکیب‌ها و جفت‌های ممکنه از `(post, comment)` رو تو یه دونه خروجی همه‌رو با هم بریز جلو من"، و اون بخش مربوط به *گروه‌بندیِ (grouping)* دیتا رو — یعنی همون بخشی که قبلاً تو مدل قبلی خیلی نامرئی قایم شده بود تو مفهوم "الان داریم رو کدوم دورِ این حلقه می‌چرخیم" — خودش صریح و با کدهای زبان Rust انجامش می‌ده، اونم بعد از اینکه تمامِ داده‌ها از قبل اومدن و تو حافظه قرار گرفتن. این دقیقاً همون معامله‌ایه که تک‌تک ORMها وقتی تو متدِ `prefetch_related`شونو صدا می‌زنی اون زیر انجامش می‌دن: یدونه کوئریِ کُندتر ولی خیلی بزرگتر و صاف‌تر می‌زنن و بعد تو لایه‌ی کلاینت (client-side) خودشون می‌شینن اونو سرهم و بازسازی (reassembly) می‌کنن، به جای اینکه بیان یه عالمه کوئریِ ریز و کوچیک بزنن که از نظرِ فرمی دقیقاً منطبق با گرافی از اشیاءِ درخواستیشونه.

اینکه متدِ `group_joined_rows` فقط یه تابعِ کاملاً معمولی و همگامِ (synchronous) ساده‌ست (بدون هیچ `async`ای توش، بدون هیچ `sqlx::Error`ی، و بدونِ حضور `self&`) دقیقاً همون چیزیه که بهمون اجازه می‌ده بتونیم اونو تو یونیت‌تست‌ها و بدون نیاز به حضورِ Postgres تستش کنیم — این فقط یه فرآیند تبدیل دیتای کاملاً ناب (pure data transformation) هستش، همون انضباطِ "عملیات I/O رو بفرست تو لبه‌های برنامه، و اون منطقِ خالص و ناب رو نگه دار تو هسته و وسطِ کدها" که قبلاً تو بحثِ `InMemoryQueue` در برابر `PostgresQueue` تو اون درسِ اسباب‌بازی‌طور در مورد صف مشاغل دیدی، یا حتی فرقی که بین عملیات‌هایِ CRUDِ متدهایِ `AnimeStore` و هندلرهای axumش وجود داشت. اون سه تا تستی که تو این کریت برچسب `[ignore]#` رو ندارن، همگی مستقیماً فقط همون `group_joined_rows` رو با یه مشت آرایه از نوع `JoinedRow` که با دستِ خودشون ساختن تست می‌کنن — خبری از `[tokio::test]#` نیست، رشته‌ی اتصال به دیتابیسی (connection string) وجود نداره، و نیاز نیست اولش بزنی `sudo service postgresql start` — چون قسمت سختِ ماجرا برای "حل کردن مشکلِ N+1" اصلاً هیچ‌موقع این نبود که "آیا می‌تونی یه کدِ `LEFT JOIN` بنویسی یا نه؟"، بلکه مشکل و سؤال اصلی این بود: "آیا می‌تونی اون ردیف‌هایِ به هم چسبیده و صاف‌شده‌ی دیتابیس رو با موفقیت دوباره بازسازی کنی و به فرمتِ یه درختِ والد و فرزندی در بیاریشون؟"، و واسه جواب دادن به این سؤال از همون روز اول کلاً هیچ نیازی به دیتابیس نبود.

## چرا شمردنِ تعداد کوئری‌ها (`query_count`) از اینکه بگیم "به نظر میاد خیلی سریعتره" مهم‌تره

اضافه کردن یه `AtomicU64` به همراه دستورِ `(fetch_add(1, Ordering::SeqCst` رو تک‌تک מתدهایی که کوئری صادر می‌کنن باعث می‌شه تا همون حسِ "این نسخه‌ی بات‌شده (batched) *حس می‌کنم* خیلی سریع‌تره" تبدیل بشه به چیزی که واقعاً می‌تونی تو تست‌هات ثابتش کنی (assert کنی): تست‌های `naive_makes_one_query_per_post_plus_one` و `batched_makes_exactly_one_query_regardless_of_post_count` با دقتِ کامل دقیقاً همون تعداد کوئری‌ها رو مشخص می‌کنن و اندازه‌گیری می‌کنن (۳ تا کوئری در برابر ۱ کوئری رو ۲ تا دونه پست؛ N+1 کوئری در برابر ۱ کوئری رو N تا پست) دقیقاً همون‌طوری که تو جنگو با خیره شدن به پنلِ SQLِ تولبارِ دیباگ می‌تونستی مطمئن بشی که با اعمالِ این تغییر، تعداد کوئری‌هات از ۵۱ تا رسید به ۲ تا. نوعِ حافظه‌بندیِ `Ordering::SeqCst` ساده‌ترین (و البته برای اینجا کاملاً کافی‌ترین) روش برای تنظیمِ ترتیب‌های حافظه (memory ordering) هست — تنها کاری که این شمارنده می‌کنه صرفاً حسابداری (bookkeeping) واسه تست‌هاست، نه اینکه بخواد مثلِ اون قفلِ `Mutex` تو ساختار `InMemoryQueue` بیاد و دسترسی‌های همروند (concurrent access) رو تو یه دنیای واقعی با هم هماهنگ (coordinating) کنه، پس اصلاً هیچ دلیلِ فنی و منطقی‌ای واسه درستی و صحتِ برنامه وجود نداره که بخوای بری سمتِ یه مدل حافظه‌بندیِ ضعیف‌تر (weaker ordering).

## پاسخ به سؤالات چک‌پوینت

**سؤال ۱ (چیزی که یه درخت B-tree در اختیارت می‌ذاره):** یه جدول به تنهایی خودش هیچ ترتیبِ مشخصی نداره که کوئری بتونه ازش استفاده‌ای ببره — Postgres مجبوره تک‌تک ردیف‌ها رو یکی‌یکی چک کنه چون هیچ‌چیزی توش نیست که بهش بگه "جواب تو می‌تونه اینجا باشه" و این کار هیچ راهی جز نگاه کردنِ فیزیکی نداره. اما یه ایندکسِ مبتنی بر درخت B-tree میاد مقادیرِ اون ستونی که روش ایندکس شده رو به شکل کاملاً مرتب‌شده (sorted) تو خودش نگه می‌داره (تو قالب یه درخت متوازن (balanced tree)، که باعث می‌شه جستجو کردن، اضافه کردن، و اسکنِ بازه‌ای همه زمانشون بشه `(O(log n`)، و در کنارش هر کدوم از اونا یه پوینتر دارن که به ردیفِ اصلی خودشون اشاره می‌کنه. در نتیجه گشتن دنبال شرطِ `post_id = 42` تبدیل می‌شه به "بیا از بالا تا پایینِ این درخت یه جستجوی دودویی (binary-search) بزنیم بریم جلو" به جای اینکه "کلِ جدولو شخم بزن"، و این همون چیزیه که دقیقاً پشت پرده‌ی تفاوت بینِ کلماتِ `Seq Scan` در برابر `Index Scan` تو خروجیِ فایل README برای `EXPLAIN ANALYZE` هستش.

**سؤال ۲ (ایندکس‌ها مجانی نیستن):** هر بار که تو فیلدِ ایندکس‌شده یه دستورِ `INSERT`/`UPDATE`/`DELETE` می‌زنی، دیتابیس مجبوره علاوه بر خود جدول، اون درخت(های) B-tree رو هم که برای اون ستون وجود دارن آپدیت کنه — پس ایندکسِ بیشتر مساویه با کارِ بیشتر تو زمان نوشتن، و فضای اشغالیِ بیشتر روی دیسک، با وجود اینکه خوندن اطلاعات قراره سریع‌تر بشه. ایده‌ی "همه‌چی رو ایندکس کن" در واقع میاد سرعت نوشتن تو دیتابیس (write throughput) و حجم فضاش رو فدا می‌کنه تا رو ستون‌هایی سرعت خوندن رو بالا ببره که شاید تو واقعیت اصلاً هیچ‌وقت برایِ فیلتر کردن/جوین شدن/مرتب‌سازی استفاده نشن — تصمیم درست و اصولی اینه که فقط همون ستون‌هایی رو ایندکس کنی که تو الگوهای واقعیِ کوئری‌های خودت کاربرد و نیازشون رو احساس می‌کنی (مثل کلیدهای خارجی یعنی `comments.post_id`، یا هرچیزی که تو بخش `WHERE` یا `ORDER BY` دیده می‌شه)، نه اینکه رو کل جدول پتو بندازی و بپوشونیش (blanket coverage).

**سؤال ۳ (این اختلافِ تو شمارنده‌ی تعدادِ کوئری‌ها از کجا میاد):** فراخوانیِ `list_posts` داخلِ تابعِ `posts_with_comments_naive` واسه خودش ۱ دونه کوئری صادر (fires) می‌کنه؛ بعدش حلقه‌ی `for post in posts` میاد به ازای هر پست، متدِ `comments_for_post` رو یک بار صدا می‌زنه، که اینم واسه خودش تو هر فراخوانی ۱ کوئری می‌سازه — پس واسه ۵ تا پست مجموعش می‌شه `6 = 5 + 1` کوئری که رو مسیر این متد مصرف شده. اما تابعِ `posts_with_comments_batched` دقیقاً و بی‌کم‌وکاست ۱ دونه کوئری (همون `LEFT JOIN`) صادر می‌کنه فارغ از اینکه اصلاً چقدر پست تو سیستم وجود داره، چون تابعِ `group_joined_rows` — یعنی همون بخشی که مسئولِ مدیریت وضعیت "چندین پست با چندین کامنت" هستش — تمام کاراشو کاملاً تو فضایِ حافظه و رم انجام می‌شه، اونم تازه بعد از اینکه جوابِ همون یه دونه کوئری از سرورِ دیتابیس برگشته.

**سؤال ۴ (چرا اون راه‌حل می‌تونست کاملاً یه راه‌حل ناب و مستقل (pure) باشه):** مشکلِ N+1 تو بُن‌مایه و ذاتِ خودش یه مشکلِ ناشی از الگوهای دسترسیِ غلط (access-pattern problem) هست، نه مشکلی تو فرآیندِ تبدیلِ داده‌ها (data-transformation problem) — وقتی که *تک‌تکِ* ردیف‌ها تو حافظه‌یِ برنامه قرار گرفتن (از طریقِ یه کوئریِ `LEFT JOIN`)، تبدیل کردنِ یه لیستِ صاف و بدون ساختار (flat list) به یه درخت گروه‌بندی‌شده (grouped tree) کلاً یه پروسه‌یِ دست‌کاریِ معمولی تو حافظه‌ی خود برنامه است که نیازی به هیچ‌گونه تماس با دنیای بیرون نداره. مرزِ بین ارتباط با بیرون (I/O boundary) دقیقاً تو جمله‌ی "برو اون ردیف‌های صاف‌شده رو واکشی کن (fetch)" خلاصه می‌شه؛ بعدش دیگه اون اتفاقی که رویِ اون ردیف‌ها قراره بیفته اصلاً اهمیتی نمی‌ده که این داده‌ها از کجا اومدن، و همین دلیل و برهان به شدت محکمی بود واسه اینکه ما تابعِ `group_joined_rows` رو با دستای خودمون توسط بُردارهایی (vectors) از نوعِ `JoinedRow` آزمایش کنیم به جای اینکه به دیتابیس وصل بشیم.

**سؤال ۵ (چرا چک کردن رو تو زمان اجرا می‌خوایم، نه با ماکروهای `!query!`/`!query_as`):** ماکروهای دارای علامت `!` تو *زمانِ کامپایل* به یه دیتابیس واقعی و زنده متصل می‌شن تا کُدهای SQLی رو که نوشتی، مو به مو با اون شِمایِ (live schema) زنده نوع‌سنجی (type-check) کنن (یا کلاً با یه فایلِ آفلاین و کش‌شده‌یِ `.sqlx` که مجبوری با دیتابیست سینک و هماهنگ نگهش داری). اگه می‌خواستیم اینجا ازشون استفاده کنیم معنیش این بود که ران کردن دستورِ `cargo check -p p3-05-01-indexing-explain-analyze-n-plus-1` — و به طبعِ اون، کُل دستور `cargo build --workspace` واسه *تمامی* کدهای این مخزن — با شکست روبرو می‌شد اگه تو طول زمان بیلد یه دیتابیس Postgresِ کاملاً در حالِ اجرا با تمام مایگریشن‌هایِ درستی که روش اعمال شده، تو هر محیطِ سندباکسی، روی کامپیوترِ هر توسعه‌دهنده‌ای که داره رو این پروژه کار می‌کنه، و تو سیستم‌هایِ CI، در دسترس نبود. اینکه صرفاً یه درسِ آموزشی واسه اینکه بتونه type-check بشه بیاد و نیاز به زیرساخت واقعی داشته باشه، کلاً بیلدِ کُلِ این ورک‌اسپیس رو به خطر می‌اندازه؛ اما استفاده از APIای که چک شدنش رو تو زمان اجرا انجام میده (`sqlx::query`/`query_as`، که خودش دستی پارامترها رو bind می‌کنه و ردیف‌ها رو map می‌کنه) باعث می‌شه تمامِ این دردسرها موکول بشن به زمانی که কোئری داره *عملاً* اجرا می‌شه، که دقیقاً همون نقطه‌ایه که باعث می‌شه محدود کردن تست‌های دیتابیس‌محور با گذاشتنِ برچسبِ `[ignore]#` کلاً به جای اینکه یه نیاز همگانی برای همه جا باشه، کاملاً کفایت کنه.

**سؤال ۶ (معادل‌سازی با فضای جنگو):** تابعِ `posts_with_comments_batched` دقیقاً همون کاریه که دستورِ `("Post.objects.prefetch_related("comments` زیر پوستِ کُدها به طور خودکار برات انجام میده — یه دونه کوئری اضافه، و نتایجی که قبل از اینکه اصلاً دست تو بهشون برسه، خودشون به عنوانِ فیلدهای آبجکتِ والدِ (parent objects) خودشون دوخته می‌شن و به هم می‌چسبن. تابعِ `posts_with_comments_naive` اما دقیقاً همون بلاییه که اگه کلاً *یادت بره* متدِ `prefetch_related` رو صدا بزنی و صرفاً بیای تو یه قالب تمپلیت (template) یا تو سریالایزرت روی `()post.comments.all` حلقه بزنی (iterate)، سرت میاد — هر دسترسی، به طور تنبلانه (lazily) باعث شلیک شدنِ یه کوئریِ مجزا و مستقل از سمتِ دیتابیس می‌شه، و کلاً هیچ‌چیزی تو کدهای پایتون بهت این اخطار رو نمی‌ده که تو دقیقاً تو همین لحظه از زدن ۱ کوئری، افتادی تو تله‌ی N+1 کوئری.

**سؤال ۷ (استفاده از `[serial]#` روی هر سه‌تا تست، نه فقط یه دونه):** هر سه تا تست به صورت کاملاً مشترک از جدول‌هایِ `posts`/`comments` استفاده می‌کنن، و تک‌تک‌شون یا میان این جدول‌ها رو تو قدم اول ریست می‌کنن (`()store.reset`) یا میان یه سری ردیف‌ها یا آمار رو ازشون می‌خونن که کلاً فقط و فقط در صورتی جواب‌هایِ منطقی و درست دارن که ریست شدنِ دیتابیس توسطِ یه تست دیگه፣ نیفته دقیقاً وسطِ اجرایِ کوئری‌های خودشون تو اون لحظه (mid-query). صفتِ `[(...serial]#` فقط تو یه حالت جلویِ اجرایِ یه تست رو *هم‌زمان با اجرای یه تست دیگه که دقیقاً و مو به مو همون تگِ مشابه رو رو خودش داره* می‌گیره — تستی که بدونِ داشتن این تگ رها بشه، کلاً واسه قانونِ ممنوعیتِ (exclusion) این صفت، یه تستِ کاملاً نامرئیه و می‌تونه در کمال آرامش، همروندِ تک‌تکِ تست‌هایی که تگ‌دار هستن اجرا بشه (run concurrently). اگه تو این صفت رو حتی از رو *یکی* از اون سه تا تست هم پاک کنی، باز هم دقیقاً همون شرطِ مسابقه‌ای (race) رو از اول خلق می‌کنی که این مجموعه‌تست وقتی داشت تو همین مخزن نوشته می‌شد تجربه‌اش کرد: تحتِ شرایطِ موازی‌سازیِ پیش‌فرضِ (default parallel execution) دستورِ `cargo test` (که با اجرای خط‌به‌خط تو `--test-threads=1` هیچ‌وقت اتفاق نمی‌افتاد)، کوئری‌های تستی که اون صفت و تگ رو از روش برداشتی، می‌تونن کاملاً لابه‌لایِ اجرایِ دستورِ `()store.reset` که مال تستِ دارای تگ هست جا بشن (interleave)، که نتیجه‌اش می‌شه ایجادِ یه سری مغایرت‌ها (mismatches) تو محاسبه‌ی `query_count`/تعدادِ ردیف‌ها به شکلِ کاملاً غیردترمینستیک و شانسی که هیچ‌گونه ربطی به اینکه آیا متدهای `!()todo`ای که تو نوشتی کدهای درستی بودن یا نه، نداره.
