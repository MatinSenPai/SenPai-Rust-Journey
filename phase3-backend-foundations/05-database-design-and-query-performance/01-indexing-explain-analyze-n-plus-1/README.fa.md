# ۰۵.۱ — ایندکس‌گذاری (Indexing)، دستورِ `EXPLAIN ANALYZE`، و مشکلِ N+1

اینجا دو تا ایده‌یِ متفاوت داریم که جفتشونم در موردِ یک حقیقتِ واحد هستن: **دیتابیس فقط دقیقاً همون حداقلِ کاری که تو بهش گفتی رو انجام میده، نه حداقلِ کاری که منظورِ اصلیِ تو بوده.** بدونِ داشتنِ یه ایندکس (index)، معنیِ "این یه دونه ردیف رو برام پیدا کن" می‌شه "برو تک‌تکِ ردیف‌ها رو نگاه کن". بدونِ استفاده از کوئری‌های دسته‌ای (batched query)، معنیِ "این پست‌ها و کامنت‌هاشونو به من بده" می‌شه "به ازایِ هر پست برو یه بار از دیتابیس بپرس". هیچ‌کدوم از این دو تا اشتباه روی لپ‌تاپِ تو که توش کلاً ۱۲ تا ردیف دیتایِ تستی ریختی خودشو نشون نمی‌ده. جفتشون قراره خودشونو تو پروداکشن، ساعت ۲ نصفه‌شب و روی یه جدول با ۲ میلیون ردیف نشون بدن، و اون موقع دیگه به این اتفاق می‌گن یه حادثه‌یِ بحرانی (incident)، نه یه کامنت ساده که تو کدریویو (code review) بشه درستش کرد.

## قسمت ۱ — یه ایندکس واقعاً چیه

یه جدولِ بدون ایندکس، از نگاهِ یه کوئری، فقط یه کپه از ردیف‌هاست که بدون هیچ نظم و ترتیبِ خاصی رو هم ریخته شدن. کوئریِ `SELECT * FROM posts WHERE title = 'Frieren'` در حالی که هیچ ایندکسی روی فیلد `title` نداری، معنیش اینه که دیتابیس Postgres باید **تک‌تکِ ردیف‌ها** رو بخونه، چک کنه ببینه آیا مقدار `title` با چیزی که می‌خوای می‌خونه یا نه، و بعد بره سراغ ردیف بعدی — که به این کار می‌گن **اسکنِ ترتیبی (sequential scan)** یا همون (`Seq Scan`)، که هزینه‌اش از نظرِ تعداد ردیف‌ها میشه `O(n)`. کلاً هم واسش فرقی نمی‌کنه که تو فقط همون یه دونه ردیف رو خواسته بودی یا همه‌شونو؛ ماهیتِ *اسکن کردن* همیشه اینه که از روی تمام ردیف‌ها رد بشه.

اما دستورِ `;CREATE INDEX idx_posts_title ON posts(title)` میاد یه ساختار داده‌ی کاملاً مجزا می‌سازه — که تو Postgres به طور پیش‌فرض یه **B-tree** هستش — که مقادیرِ تایتل‌ها رو به صورت کاملاً مرتب‌شده (sorted) به همراهِ یه پوینتر به ردیفِ اصلیِ هرکدوم، کنار هم نگه می‌داره. پیدا کردن یه چیز تو یه درختِ مرتب‌شده‌یِ B-tree هزینه‌اش `O(log n)` هستش: رو یه جدولِ ۲ میلیون ردیفی، هزینه و زمانِ `O(log n)` نهایتاً می‌شه حدود ۲۱ تا مقایسه؛ در حالی که `O(n)` ممکنه تا ۲ میلیون تا مقایسه رو هم شامل بشه. این فاصله‌ی عجیب و غریبِ بینِ این دوتا، دقیقاً و دقیقاً همون دلیلیه که ایندکس‌ها اصلاً به وجود اومدن، و هرچی جدول بزرگتر بشه این فاصله هم عمیق‌تر می‌شه — منطقش دقیقاً مثل منطقِ گشتن تو یه دفترچه‌تلفنه (که حروفش مرتبه و با جستجوی دودویی یا binary-search پیدا می‌شه) تو مقایسه با گشتن تو یه کپه از رسیدهایِ خریدِ نامرتب و تو هم تو هم.

اما خب همیشه یه بهایی (trade-off) هم در کاره: داشتن یه ایندکس کلاً مجانی نیست. از این به بعد، هر دفعه که عملِ `INSERT`/`UPDATE`/`DELETE` رو فیلدی که ایندکس شده انجام بشه، باید اون درختِ B-treeِ مربوط به ایندکس هم آپدیت بشه، و تازه خودِ ایندکس هم کلی فضای ذخیره‌سازی رو دیسک اِشغال می‌کنه. ایندکس کردن تک‌تکِ ستون‌های جدول فقط "محض احتیاط"، کلاً یه ضد-الگویِ (anti-pattern) کاملاً جدی و بده، و اصلاً به معنیِ محکم‌کاری و یه تور ایمنی نیست — تو فقط باید روی اون ستون‌هایی ایندکس بسازی که تو دنیای واقعی روی اونا فیلتر می‌ذاری، join می‌زنی، یا بر اساس اونا مرتب‌سازی (sort) انجام میدی (که اکثراً همون کلیدهایِ خارجی یا foreign keys هستن و فیلدهایی که تو بخش‌های `WHERE`/`ORDER BY` پیدا می‌شن)، نه اینکه رو کل جدول ایندکس بذاری.

## قسمت ۲ — خوندنِ خروجیِ `EXPLAIN ANALYZE`

دستورِ `<EXPLAIN ANALYZE <query` در واقع میاد و واقعاً اون کوئری رو *اجرا می‌کنه* و بهت نشون می‌ده که Postgres تو دنیای واقعی دقیقاً چه نقشه‌ای (plan) براش ریخته بوده، به اضافه‌یِ تایمینگ و زمان‌بندی‌هایِ کاملاً واقعی (دستورِ `EXPLAIN`ِ خالی فقط میاد هزینه‌یِ فرضی و برنامه‌ریزی‌شده رو *بدونِ* ران کردن کوئری نشون میده — که خب این حالت واسه کوئری‌هایی که ران کردنشون تو واقعیت خیلی سنگین یا مخربه به درد می‌خوره). خروجی‌ای که پایین می‌بینی صرفاً **جنبه‌یِ نمایشی (illustrative)** داره — با دست نوشته شده تا فقط قالب و شمایلِ چیزی که قراره ببینی رو نشون بده، نه اینکه دقیقاً کپی-پیست از یه اجرای واقعی باشه — اما خب با اون چیزی که از یه جدولِ `comments` با سایز و مقیاسِ واقعی تو حالتِ بدون ایندکس در برابر حالت ایندکس‌شده می‌گیری، کاملاً تطابق داره.

**قبل از داشتن ایندکس** روی `comments.post_id`، پیدا کردنِ کامنت‌های مربوط به یه پست:

```
EXPLAIN ANALYZE SELECT * FROM comments WHERE post_id = 42;

                                            QUERY PLAN
----------------------------------------------------------------------------------------------
 Seq Scan on comments  (cost=0.00..21390.00 rows=48 width=72) (actual time=0.031..118.442 rows=48 loops=1)
   Filter: (post_id = 42)
   Rows Removed by Filter: 999952
 Planning Time: 0.112 ms
 Execution Time: 118.501 ms
```

- عبارتِ `Seq Scan on comments` — ینی یه اسکنِ کامل رو کلِ جدول زده، دقیقاً همون‌طوری که بالاتر توضیح دادیم.
- عبارتِ `Rows Removed by Filter: 999952` — یعنی عملاً کلِ اون جدولِ یه میلیون ردیفی رو از دم خونده فقط برای اینکه هر چیزی که `post_id = 42` نبوده رو بریزه دور.
- عبارتِ `actual time=0.031..118.442` — یعنی پیدا کردن ردیفِ اول ۰.۰۳۱ میلی‌ثانیه زمان برده، اما خوندنِ *کُلِ* ردیف‌ها ۱۱۸.۴۴۲ میلی‌ثانیه. و این دقیقاً همون تأخیرِ کاملاً واقعی و ملموس (user-facing latency) واسه فقط یه دونه کوئریه.

**بعد از اعمالِ** دستورِ `;CREATE INDEX idx_comments_post_id ON comments(post_id)`، برای همون کوئری قبلی:

```
EXPLAIN ANALYZE SELECT * FROM comments WHERE post_id = 42;

                                                  QUERY PLAN
---------------------------------------------------------------------------------------------------------
 Index Scan using idx_comments_post_id on comments  (cost=0.29..8.61 rows=48 width=72) (actual time=0.021..0.089 rows=48 loops=1)
   Index Cond: (post_id = 42)
 Planning Time: 0.098 ms
 Execution Time: 0.121 ms
```

- عبارتِ `Index Scan using idx_comments_post_id` — یعنی Postgres به جای خوندن کل جدول، مستقیم رفته تو درختِ B-tree گشته و دقیقاً و صاف رو همون ردیف‌هایی که با هم تطابق داشتن فرود اومده.
- بخش `cost=0.29..8.61` در برابرِ `cost=0.00..21390.00` قبلی — یعنی برآوردِ (estimate) خودِ برنامه‌ریزِ (planner) دیتابیس از هزینه‌ی این کار، کلاً ۳ تا مقیاس (سه تا صفر) اُفت کرده و کم شده.
- زمان `Execution Time: 0.121 ms` در مقایسه با `118.501 ms` قبلی — یعنی تقریباً ۱۰۰۰ برابر سریع‌تر شده، اونم رو جدولی که تازه قراره از اینم خیلی بزرگ‌تر بشه.

عادتِ کلی واسه خوندنِ این چیزا اینه: تو کوئری‌هایی که فقط چند تا دونه ردیف رو تو خروجی می‌خواستن اما رو یه جدول بزرگ ران شدن، همیشه بگرد دنبال عبارت `Seq Scan` — این دقیقاً همون سیگنالِ واضحی هست که بهت می‌گه اینجا جای یه ایندکس خالیه. اعدادی که با `cost=X..Y` نشون داده می‌شن صرفاً همون *برآوردهایِ (estimate)* برنامه‌ریزن (هزینه‌ی شروع..هزینه‌ی کل، اونم با یه سری واحدهای دلبخواهی و دل‌بخواهِ خودشون، نه بر اساس میلی‌ثانیه)؛ اما مقادیرِ `actual time=X..Y` و `rows=N` (البته زمانی که از `ANALYZE` استفاده کرده باشی) نشون‌دهنده‌یِ اتفاقاتی هستن که تو واقعیت افتادن. اگه یه روزی دیدی این دو تا خیلی با هم فرق دارن و اختلاف فاحش (disagree wildly) بینشونه، معمولاً نشونه‌ی اینه که آمار و اطلاعاتِ Postgres از اون جدول خیلی قدیمی و کهنه (stale) شده (که با ران کردن دستورِ `;ANALYZE <table>` کلاً تازه می‌شن) و مشکل از سمتِ خود کوئری نیست.

## قسمت ۳ — مشکلِ N+1

تا الان قطعاً با این مشکل مواجه شدی، منتهی فقط داشتی از اون سمتِ یه ORM بهش نگاه می‌کردی. تله‌یِ کلاسیک و معروف جنگو رو ببین:

```python
posts = Post.objects.all()               # ۱ دونه کوئری
for post in posts:
    print(post.comments.all())           # به ازای هر پست، بازم ۱ دونه کوئریِ دیگه می‌زنه — یعنی N تا کوئریِ اضافه
```

متدهای `select_related`/`prefetch_related` دقیقاً و مشخصاً برای همین به وجود اومدن که بتونن کُلِ این پروسه رو تو یه دونه یا نهایتاً دوتا کوئری جمع و جور (collapse) کنن. اما کتابخونه‌ی sqlx اصلاً هیچ ORMی نداره که بخواد این کثافت‌کاریا رو پشتش قایم کنه، که خب تو این درس، اتفاقاً این خودش یه مزیت و ویژگی (feature) حساب می‌شه: ساختارِ مشکلِ N+1 اینجا دقیقاً جلویِ چشمت و تو کدهایی که داری با دست می‌نویسی خودشو نشون می‌ده، و دیگه زیرِ جادوهایِ بارگذاریِ تنبل (lazy-loading) دفن نشده. تو فایل `src/lib.rs` ساختاری به اسم `BlogStore` وجود داره که دقیقاً دو تا نسخه‌ی متفاوت از یه کوئریِ یکسان رو که رویِ یه شِمایِ (schema) خیلی کوچیک و ساده‌یِ `posts`/`comments` ران می‌شه، برات آماده کرده:

## گشت‌وگذاری تو کدهای اولیه‌ی پروژه (starter code)

- نوع‌های `Post` / `Comment` / `PostWithComments` — فقط یه سری دیتای ساده‌ان و هیچ پیچیدگی و سوپرایز خاصی ندارن.
- نوعِ `JoinedRow` — نمایانگرِ یه ردیف از خروجیِ کاملاً صاف‌شده‌یِ (flattened) متدِ `LEFT JOIN` هستش: یه ردیف به ازایِ هر جفت از `(post, comment)`، که واسه پست‌هایی که اصلاً کامنتی ندارن، هر دو متغیرِ `comment_id`/`comment_body` کاملاً `None` هستن. و دقیقاً کُلِ دلیلی که باعث شد از `LEFT JOIN` استفاده کنیم نه یه `JOIN`ِ معمولی همینه — یه `JOIN` ساده باعث می‌شد هر پستی که هیچ کامنتی نداره کلاً تو نتایج خروجی ناپدید بشه به جای اینکه با متغیرهایِ null، یه بار تو خروجی خودش رو نشون بده.
- متدِ `group_joined_rows` — **این تابع کاملاً ناب (pure)، همگام (synchronous)، و کاملاً بی‌نیاز از هرگونه دیتابیسیه.** ردیف‌های صاف‌شده رو می‌گیره و دوباره اونا رو طوری دسته‌بندی می‌کنه که به ازای هر پست، یه خروجی به شکلِ `PostWithComments` ساخته بشه. این دقیقاً همون بخشِ حل کردنِ مشکلِ "N+1" هست که ارزش اینو داره تا به صورت جداگانه و بدونِ دخالت هیچ‌گونه زیرساختی (infrastructure) واسه‌اش یونیت‌تست (unit test) نوشته بشه، و تمامِ اون تست‌هایی که با همون دستورِ `cargo test`ِ ساده و معمولی اجرا می‌شن دقیقاً پشتشون به این تابع گرمه و همین رو تست می‌کنن.
- ساختارِ `BlogStore` — این همون تیکه‌ایه که پای Postgres رو می‌کشه وسط: توابعِ `connect`، `create_post`، `create_comment`، `list_posts`، و `comments_for_post` از قبل نوشته و کاملاً پیاده‌سازی شدن، و هر کدومشون با هر بار اجرا یه دونه به شمارنده‌یِ `query_count` اضافه می‌کنن تا تست‌ها بتونن دقیقاً و به صورت *اثبات‌شده (prove)* ببینن که یه الگوی دسترسیِ مشخص (access pattern) دقیقاً چند بار با دیتابیس رفت‌وبرگشت داشته — یعنی دقیقاً همون عددی که می‌تونستی از تو همون پنلِ SQL تولبارِ دیباگ تو جنگو بخونیش.
- تمام کوئری‌هایی که اینجا نوشته شدن دارن از توابعِ `sqlx::query`/`sqlx::query_as` استفاده می‌کنن (یعنی همون API که صحتِ کوئری‌ها رو تو *زمان اجرا (runtime)* چک می‌کنه، پارامترها با دستِ خودت `bind` می‌شن و ردیف‌ها دستی مَپ می‌شن) به جای اینکه از ماکروهای `!query!`/`!query_as` استفاده کرده باشن. ماکروها میان و SQLِ نوشته‌شده‌یِ تو رو *تو همون زمان کامپایل (at compile time)* با یه دیتابیس واقعی مطابقت و نوع‌سنجی (type-check) می‌کنن، که معنیش اینه که این کریت تو هر بار اجرا کردنِ دستور `cargo check`/`cargo clippy`، اگه یه اتصالِ زنده‌ی Postgres تو زمان بیلد نداشته باشه به طور کامل متوقف می‌شه — و خب این موضوع واسه یه کُدِ تمرینی و آموزشی (و البته واسه یه ورک‌اسپیس) که باید بتونه روی هر سیستمی بدون نیاز به زیرساختِ اضافی کامپایل بشه، کاملاً غیرقابل‌قبوله. اما APIای که چک کردن رو تو زمانِ اجرا (runtime-checked) انجام میده کلاً همه‌ی این دغدغه‌ها رو موکول می‌کنه به زمانی که کوئری واقعاً قراره ران بشه، و دقیقاً به خاطر همینم هست که صفتِ `#[ignore]` اینجا بهترین ابزارمونه: همه‌چیز تو همون حالت عادی کامپایل می‌شه و چک‌های clippy رو با موفقیت پاس می‌کنه، و فقط اون تست‌هایی که قراره واقعاً دیتابیس رو لمس کنن به یه Postgres زنده و اضافه کردنِ پارامترِ `ignored--` موقع تست گرفتن نیاز پیدا می‌کنن.

## وظیفه‌ی تو

فایل `src/lib.rs` رو باز کن. اینجا دو تا `todo!()` داری:

1. **متدِ `group_joined_rows`** — یعنی همون منطقِ نابِ مربوط به دسته‌بندی و کنارِ هم قرار دادنِ داده‌ها. پای هیچ دیتابیسی این وسط در میون نیست؛ می‌تونی خیلی راحت با اجرایِ `cargo test -p p3-05-01-indexing-explain-analyze-n-plus-1` اینو مستقیماً تستش کنی.
2. **متدِ `BlogStore::posts_with_comments_naive`** — با دستای خودت این حلقه‌ی وحشتناکِ N+1 رو بنویس: اول متد `list_posts` رو صدا بزن، بعد تو یه حلقه به ازایِ تک‌تکِ پست‌ها، متدِ `comments_for_post` رو صدا بزن. قرار نیست اینجا مشکل N+1 رو حل کنی — بلکه قراره اونو از قصد *بسازی* و پیاده‌سازی کنی، تا وقتی بعداً تو راه‌حلِ جایگزینش که تو متدِ `posts_with_comments_batched` (که از قبل برات نوشته شده) آماده‌ست خواستی نتیجه رو ببینی، مقایسه‌ی اون `()query_count` بین این دو تا متد، واقعاً یه معنی ملموس و قابل اندازه‌گیری بهت بده.

## خودت واقعیشو با چشمای خودت ببین (اختیاریه ولی می‌ارزه یه بار انجامش بدی)

```sh
sudo service postgresql start   # اگه قبلاً ران نشده بود
psql -U taskforge -h localhost -d taskforge -c "
  CREATE TABLE IF NOT EXISTS demo_posts (id serial primary key, title text);
  CREATE TABLE IF NOT EXISTS demo_comments (id serial primary key, post_id int, body text);
  INSERT INTO demo_posts (title) SELECT 'post ' || g FROM generate_series(1, 5000) g;
  INSERT INTO demo_comments (post_id, body) SELECT (g % 5000) + 1, 'comment ' || g FROM generate_series(1, 50000) g;
  EXPLAIN ANALYZE SELECT * FROM demo_comments WHERE post_id = 42;
  CREATE INDEX idx_demo_comments_post_id ON demo_comments(post_id);
  EXPLAIN ANALYZE SELECT * FROM demo_comments WHERE post_id = 42;
"
```

حالا بشین و خودت خروجیِ اون دو تا دستورِ `EXPLAIN ANALYZE` رو با هم مقایسه کن — اونجاست که دقیقاً و مو به مو می‌تونی همون جابه‌جاییِ الگو از `Seq Scan` به `Index Scan` رو که بالاتر تو مثال نمایشیِ این فایل آورده بودم، با چشمای خودت و روی یه مشت داده‌ی واقعی که همین الان تولیدشون کردی، ببینی.

بعد از اون برو و تست‌هایِ این درس رو که `#[ignore]` شده بودن روی یه Postgresِ واقعی ران کن. هر سه تای این تست‌ها دارن از جداولِ `posts`/`comments` به صورت مشترک استفاده می‌کنن و بعد از کارشون با متدِ `()store.reset` اونا رو ریست می‌کنن، پس هر سه تاشون صفتِ `#[serial(p3_05_01_indexing_db)]` رو (از کریت `serial_test`) به خودشون چسبوندن تا جلویِ رفتار پیش‌فرض `cargo test` واسه اجرای همروندِ تست‌ها رو بگیرن تا نکنه یهو ریست‌شدنِ جدول تو یه تست، بیافته دقیقاً وسطِ اجرایِ کوئری‌های تستیِ یه تستِ دیگه:

```sh
DATABASE_URL=postgres://taskforge:***@localhost:5432/taskforge \
  cargo test -p p3-05-01-indexing-explain-analyze-n-plus-1 -- --ignored
```
