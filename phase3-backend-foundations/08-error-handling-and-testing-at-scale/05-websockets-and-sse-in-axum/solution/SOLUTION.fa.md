# راه‌حل — ۳.۸.۵ WebSocket و SSE در `axum`

## `sse_frame`

```rust
pub fn sse_frame(event: Option<&str>, id: Option<u64>, data: &str) -> String {
    let mut out = String::new();
    if let Some(name) = event {
        out.push_str(&format!("event: {name}\n"));
    }
    if let Some(n) = id {
        out.push_str(&format!("id: {n}\n"));
    }
    for line in data.split('\n') {
        out.push_str(&format!("data: {line}\n"));
    }
    out.push('\n');
    out
}
```

هر فیلد یک خط است و رویداد با یک خطِ خالیِ اضافه تمام می‌شود. تنها نکته‌یِ ظریف `data` است: قالب راهی برایِ گذاشتنِ خطِ جدید داخلِ مقدارِ یک `data:` ندارد، پس هر خطِ بار یک خطِ `data:`ِ جدا می‌گیرد و مرورگر دوباره با `\n` به‌هم وصلشان می‌کند. `"".split('\n')` یک تکه‌یِ خالی می‌دهد، برای همین داده‌یِ خالی `data: ` می‌شود و `"a\n"` دو خط می‌دهد: `a` و یک خطِ خالی. تستِ `matches_what_axum_sends` نتیجه را با بایت‌هایی مقایسه می‌کند که `Event`ِ خودِ `axum` برایِ همان رویداد می‌فرستد.

## `ws_reply`

```rust
pub fn ws_reply(text: &str) -> String {
    if text == "ping" {
        "pong".to_string()
    } else if let Some(rest) = text.strip_prefix("echo ") {
        rest.to_string()
    } else {
        format!("unknown: {text}")
    }
}
```

`strip_prefix("echo ")` فاصله را جزوِ پیشوند می‌گیرد، پس خودِ کلمه‌یِ `echo` به `unknown:` می‌افتد و در `echo  two spaces` فاصله‌یِ دوم در پاسخ می‌ماند. اینکه این تابع یک `&str -> String`ِ خالص بماند همان چیزی است که پروتکل را بدونِ سوکت قابلِ تست می‌کند: `ws_reply_test` سرور نمی‌خواهد و `ws_wire_test` فقط باید ثابت کند لوله‌کشیِ دورِ آن درست است.

## `Hub::publish`

```rust
pub fn publish(&self, msg: &str) -> usize {
    self.tx.send(msg.to_string()).unwrap_or(0)
}
```

`broadcast::Sender::send` مقدارِ `Ok(تعدادِ گیرنده‌هایی که پیام به آن‌ها رسید)` برمی‌گرداند و فقط وقتی `Err` می‌دهد که اصلاً گیرنده‌ای نباشد. برایِ یک اتاقِ گفتگو، نبودنِ شنونده حالتی عادی است نه خطا، پس `unwrap_or(0)` آن را به همان عددی تبدیل می‌کند که هست.

## `events`

```rust
let stream = BroadcastStream::new(hub.subscribe()).map(|item| {
    let event = match item {
        Ok(msg) => Event::default().event("chat").data(msg),
        Err(BroadcastStreamRecvError::Lagged(n)) => {
            Event::default().event("lagged").data(n.to_string())
        }
    };
    Ok::<Event, Infallible>(event)
});
Sse::new(stream)
    .keep_alive(KeepAlive::new().interval(Duration::from_secs(15)))
    .into_response()
```

`hub.subscribe()` در بدنه‌یِ هندلر اجرا می‌شود، پیش از آنکه پاسخی وجود داشته باشد؛ پس تا وقتی کلاینت هدرها را خوانده، از قبل مشترک شده است. تستِ `publish_reaches_every_event_stream` روی همین حساب می‌کند: دو کلاینت وصل می‌کند، پیام منتشر می‌کند و `"2"` را انتظار دارد. اشتراکِ تنبل (مثلاً داخلِ یک بلوکِ `async` که فقط وقتی بدنه برایِ اولین بار poll شد اجرا می‌شود) گیرنده را دیرتر ثبت می‌کرد و پیامی که در آن فاصله منتشر شود گم می‌شد. عقب‌افتادن به داده‌ای داخلِ استریم تبدیل می‌شود (`Err(Lagged(n))` به یک رویدادِ `lagged` نگاشت می‌شود) به‌جایِ `unwrap`، پس به کلاینتِ کند خبر داده می‌شود و استریم ادامه می‌دهد. حاشیه‌نویسیِ `Infallible` به کامپایلر می‌گوید نوعِ خطایِ استریم چیست، چون هیچ چیزِ داخلِ کلوژر شکست نمی‌خورد.

## درباره‌یِ چالش (اختیاری)

یک `VecDeque<(u64, String)>` از ۱۰۰ پیامِ آخر و یک شناسه‌یِ افزایشی را داخلِ `Hub` و پشتِ یک `Mutex` نگه دار. هنگامِ اتصال، قفل را یک بار بگیر و در همان بخشِ بحرانی هم به کانال مشترک شو و هم هر پیامِ ذخیره‌شده را که شناسه‌اش از `Last-Event-ID`ِ کلاینت بزرگ‌تر است کپی کن. بازپخش را جلوی استریمِ زنده بچسبان. انجامِ هم‌زمانِ اشتراک و کپی زیرِ یک قفل است که درزِ بینِ این دو را می‌بندد: اگر جدا باشند، پیامی که بینشان منتشر شود یا دو بار بازپخش می‌شود یا هرگز دیده نمی‌شود.

## تست‌ها چه چیزی را پوشش می‌دهند و چه چیزی را نه

تست‌ها یک سرورِ واقعی را رویِ یک پورتِ موقت اجرا می‌کنند و بایت‌هایِ خام را می‌خوانند: chunkهایِ رمزگشایی‌شده برایِ SSE و فریم‌هایِ دست‌ساز برایِ WebSocket. فریم‌هایِ تکه‌تکه یا دودویی، ping و pong، ضربانِ ۳۰ثانیه‌ای و keep-alive ۱۵ثانیه‌ای تست نمی‌شوند، چون هرکدام یا انتظارِ طولانی می‌خواهد یا یک کتابخانه‌یِ کاملِ کلاینت. مسیرِ `lagged` فقط از نظرِ شکل چک می‌شود، چون اینکه عقب‌افتادنی رخ بدهد یا نه به سرعتِ خالی‌کردنِ اتاق توسطِ تسکِ سرور بستگی دارد، و تست آن را کنترل نمی‌کند.
