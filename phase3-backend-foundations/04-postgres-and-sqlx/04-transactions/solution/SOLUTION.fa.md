# راه‌حل

```rust
pub async fn transfer(
    pool: &PgPool,
    from: i64,
    to: i64,
    amount_cents: i64,
) -> Result<(), TransferError> {
    if amount_cents <= 0 {
        return Err(TransferError::AmountNotPositive(amount_cents));
    }

    let mut tx = pool.begin().await?;

    let available: i64 = sqlx::query_scalar(
        "SELECT balance_cents FROM p3_04_04_accounts WHERE id = $1 FOR UPDATE",
    )
    .bind(from)
    .fetch_optional(&mut *tx)
    .await?
    .ok_or(TransferError::AccountNotFound(from))?;

    if available < amount_cents {
        return Err(TransferError::InsufficientFunds {
            available,
            requested: amount_cents,
        });
    }

    sqlx::query("UPDATE p3_04_04_accounts SET balance_cents = balance_cents - $1 WHERE id = $2")
        .bind(amount_cents)
        .bind(from)
        .execute(&mut *tx)
        .await?;

    let credited =
        sqlx::query("UPDATE p3_04_04_accounts SET balance_cents = balance_cents + $1 WHERE id = $2")
            .bind(amount_cents)
            .bind(to)
            .execute(&mut *tx)
            .await?;
    if credited.rows_affected() == 0 {
        return Err(TransferError::AccountNotFound(to));
    }

    tx.commit().await?;
    Ok(())
}
```

## رول‌بک (rollback) دقیقاً کجاست؟

بیا بشماریم ببینیم از خطِ `()pool.begin` به بعد چند تا راهِ خروج از تابع (با خطا) وجود داره: سه تا علامتِ `?` که ممکنه با خودشون یه `sqlx::Error` بیارن، یه دونه `ok_or` واسه پیدا نشدنِ فرستنده، یه `return`ِ صریح برای شرطِ `InsufficientFunds`، و یه `return`ِ صریح دیگه برای وقتی که `0 == ()rows_affected` باشه. **هیچ‌کدوم از این راه‌های خروج هیچ حرفی از رول‌بک نمی‌زنن.** و البته نیازی هم ندارن: تک‌تک این مسیرها باعث می‌شن تا تو قبل از اینکه متدِ `()tx.commit` رو صدا بزنی، تابع رو ترک کنی و بیای بیرون، در نتیجه متغیرِ `tx` پاک (drop) می‌شه، و نوعِ `Transaction` از کتابخونه‌ی sqlx قبل از اینکه اتصال رو به استخر برگردونه، خودش یه دستورِ `ROLLBACK` می‌فرسته به دیتابیس. این دقیقاً مدلِ مالکیت (ownership) تو زبان Rustئه که داره زحمت حسابداری و دفتریِ تراکنش‌های تو رو می‌کشه — دقیقاً همون منطقی که می‌گفت وقتی `MutexGuard` drop می‌شه قفل رو هم باز می‌کنه، حالا داره رو مفاهیمِ `BEGIN`/`ROLLBACK` پیاده می‌شه.

دقیقاً به همین خاطرم هست که تستِ `a_failed_credit_rolls_back_the_debit` مهم‌ترین تستِ کلِ این درسه: کوئریِ `UPDATE` مربوط به کسر کردن (debit) از حساب مبدأ، کاملاً تو واقعیت و تو دل تراکنش ران شده بود، اما این تست ثابت کرد که مطلقاً هیچ رد و نشونی ازش باقی نموند. جنگو هم دقیقاً همین ضمانت و گارانتی رو از طریق گرفتن و کنترلِ استثناها (exceptions) در مرزِ بلوک‌های `with` بهت با `()transaction.atomic` می‌ده؛ اما sqlx این ضمانت رو به ویژگیِ `Drop` تو زبان متصل و آویزون می‌کنه، که رو *تک‌تک* راه‌های خروج از برنامه به صورت خودکار روشن و شلیک می‌شه — چه یه خروج زودرس با `return` باشه، چه علامت `?`، چه یه پنیک — اونم با صفر خطِ کدنویسی تو تک‌تک اون نقطه‌های خروج.

## چرا باید از `&mut *tx` استفاده کنی نه `&pool`

یه تراکنش فقط و فقط رو **یه دونه** اتصالِ (connection) واحد زنده می‌مونه؛ فرستادن دستور `BEGIN` روی اتصالِ A، هیچ تاثیری رو کوئری‌ای که قراره رو اتصال B اجرا بشه نداره. متغیرِ `Transaction` تو دل خودش مالکِ (owns) اون اتصالیه که از استخر کشیده بیرون، و عبارتِ `&mut *tx` با نشان‌زدایی (deref) مستقیم وصل می‌شه به همون `PgConnection` — و این همون چیزیه که واسه حالتِ "اجرا تو شکم یه تراکنش"، خصیصه‌ی `Executor` رو پیاده‌سازی کرده. اگه اشتباهاً عبارتِ `&pool` رو پاس بدی، اون کوئری می‌ره برای خودش یه اتصال *دیگه* می‌گیره و کلاً بیرون از تراکنشت ران می‌شه (که تو این حالت خودش رو هم کامیت (auto-commit) می‌کنه، و اگه رول‌بکی هم بشه اصلاً از این خبردار نمی‌شه). استفاده از `&mut` همچنین به این معنیه که بررسی‌کننده‌ی قرض‌گرفتن‌ها (borrow checker) اجبار می‌کنه که تو هر لحظه فقط و فقط روی اون تراکنش، یک دونه دستور ران بشه — یعنی تو عملاً و از نظر فیزیکی نمی‌تونی مثل حالتی که با استخرها کار می‌کردی، روی اون اتصال، چندتا کوئری همروند رو با هم ترکیب و تو هم تو هم (interleave) اجرا کنی.

## ویژگیِ `FOR UPDATE`: جلوی اون تداخلِ مخرب تو خوندن‌سپس-نوشتن (check-then-act race) رو می‌گیره

اگه این قفل وجود نداشت: دو تا تراکنش انتقال (transfers) T1 و T2 هر دوشون می‌تونستن متغیرِ `balance = 100` رو بخونن، هردوشون هم با موفقیت از سدِ بررسیِ `60 =<` می‌گذشتن، هردوشون مبلغ 60 تا از حساب کم می‌کردن، و در نهایت حساب با عدد 20- بسته می‌شد (یا حداقل تو این تمرین ما، با خطایِ قیدِ CHECKِ مربوط به دیتابیس سر اون تراکنشی که دیرتر از همه کامیت می‌شد کار متوقف می‌شد — که خب از فساد و خرابی دیتا بهتره، اما بهت یه خطایِ دیتابیسیِ خام می‌ده به جای خطای تمیز و اختصاصیِ `InsufficientFunds`). اما با استفاده از `FOR UPDATE`، دستورِ `SELECT` مربوط به تراکنش دوم (T2)، مجبور می‌شه تا زمانِ کامیت یا رول‌بکِ تراکنشِ اول (T1) صبر کنه، و تازه اون وقته که می‌تونه موجودیِ *بعد از کسرِ T1* رو بخونه، و در نتیجه قانونِ اعتبارسنجی با درستی اجرا می‌شه. این قضیه دقیقاً مشابهِ همون تابعِ `()select_for_update` تو جنگو هست، که اونم به نوبه‌ی خودش فقط داخلِ محدوده‌یِ `()transaction.atomic` کار می‌کنه — چون یه قفلِ ردیف (row lock) که هیچ تراکنشی نباشه تا دایره‌ی اِعمال (scope) اونو محدود کنه، عملاً هیچ لحظه‌ی مشخص و واضحی رو واسه رهاشدن و آزاد شدن نخواهد داشت.

با این وجود قیدِ CHECK همچنان تو فایلِ مایگریشن سر جای خودش باقی می‌مونه. اون بررسِ تو سطحِ اپلیکیشن فقط برای اینه که یه ارور و خطای *مفیدتر* به دستِ کاربر بده؛ اما اون قید تو دیتابیس، همون چیزیه که ضمانت می‌کنه هیچ‌جوره هیچ‌کس نمی‌تونه از این قانون تخطی کنه — حتی تابعی مثل `create_account` که اصلاً قبلش موجودی رو چک هم نمی‌کنه، یا اصلاً هر کدی که سال‌ها بعد قراره واسه این سیستم نوشته بشه.

## بررسی وجودِ حساب مقصد با چک کردن `()rows_affected`

واسه حساب فرستنده (sender)، وجودش به واسطه‌ی همون کوئریِ `SELECT ... FOR UPDATE` ثابت شد (که اگه سطری بود برمی‌گردوندش). واسه گیرنده (recipient) ما هیچ خوندنِ اولیه‌ای نداریم، پس خودِ دستورِ `UPDATE`ِ واریز، نقشِ همون بررسی رو بازی می‌کنه: اگه تعداد ردیف‌های آپدیت‌شده برابر صفر باشه یعنی کلاً چنین حسابی اصلاً نبوده. این کار باعث می‌شه تا از لحاظ شبکه یه رفت‌وبرگشت (round trip) صرفه‌جویی بشه نسبت به حالتی که می‌خواستیم اول `SELECT` کنیم بعد `UPDATE`، و ضمناً تو دلِ یه تراکنش هم این روش از مشکلِ شرط‌هایِ مسابقه‌ای (race-free) در امانه — چون تصمیم گرفتن بر اساس نتیجه‌ی خودِ دستورِ UPDATE امکان نداره با کاری که خودِ UPDATE کرده در تضاد باشه.

## چرا تست‌های مربوط به پایگاه‌داده اینجا کلمه‌ی `[(...serial]#` رو دور زدن

تو درس‌های 04.2 و 04.3 به این دلیل تست‌های دیتابیسی‌شون رو نوبتی و سری (serialize) کردیم که همه داشتن یه وضعیت و state مشترک رو عوض می‌کردن: یه دونه جدول که تست‌ها اونو مینداختن دور (drop)، خالیش می‌کردن (wipe) یا می‌شمردن. اما اینجا تو این درس، هر تست اکانت‌های کاملاً تازه و جدیدی برای خودش می‌سازه (کلیدهای `BIGSERIAL` هیچ‌وقت هم‌پوشانی و تصادم (collide) ندارن) و רק رو آیدیِ همون اکانت‌های ساخته‌شده هم شرط (assert) می‌ذاره — پس هیچ ردیفِ (row) مشترکی بینشون نیست که بخوان سرش مسابقه (race) بدن و تو هم تو هم برن، در نتیجه تو این سناریو، همون اجرای پیش‌فرض و همروندِ تست‌ها هم کاملاً امن (safe) هست. حتی اون فراخوانی‌هایِ موازی و همروندِ `run_migrations` هم کاملاً بی‌خطرن: ابزار مهاجرتِ (migrator) کتابخونه‌ی sqlx موقع ران شدن، کُلِ کارِ خودشو با یه قفلِ مشاوره‌ای (advisory lock) از سمتِ Postgres قفل و حفاظت می‌کنه. قانون کلیِ اینه: تست‌هایی رو سری و نوبتی اجرا کن که وضعیت‌هایِ مشترکِ تغییرپذیر (shared mutable state) دارن، نه تست‌هایی که صرفاً دارن یه دیتابیسِ یکسان رو با هم به اشتراک می‌ذارن.

## واقعیتِ مایگریشن‌های برگشت‌پذیر تو عمل

ماکروی `!sqlx::migrate` فقط و فقط فایل‌های `.up.sql` رو تو دل باینری جاسازی می‌کنه (embed) و همونا رو اجرا می‌کنه — تابعِ `run_migrations` عملکردش دقیقاً مشابه با درس 04.2 هست. اما اون فایلِ `.down.sql` مخصوصِ دستوراتِ CLI (خط فرمانه): دستورِ `sqlx migrate revert` میاد فایلِ downِ همون مایگریشنی که به عنوان آخرین نفر رو دیتابیس اعمال شده بود رو ران می‌کنه و ردیفِ مربوطه‌اش رو از جدول `_sqlx_migrations` پاک می‌کنه، در نتیجه با فراخوانیِ بعدیِ `run_migrations` دوباره فایل up از نقطه‌ی صفر اعمال می‌شه. با هر بار فراخوانی این دستور دقیقاً یک مایگریشن به عقب برمی‌گرده، از جدیدترین به قدیمی‌ترین — کلاً هیچ دستور خفنِ "همه‌رو با هم برگردون" (revert all) که بشه باهاش یه خودزنی اساسی کرد (footgun) وجود نداره. دو تا عادت خیلی خوب تو این بخش هست که به دردت می‌خوره: اول اینکه همیشه مایگریشنِ down رو دقیقاً تو همون نشست و در کنار همون فایلِ up بنویس (چون همون موقع هنوز دقیقاً یادت هست که فایل up چیکار کرده بود)، و دوم اینکه همیشه حواست باشه یه دستورِ `DROP TABLE` تو مایگریشنِ down یعنی نابودی و از بین رفتنِ همیشگیِ دیتا — رِوِرت (reverting) کردن تو محیطِ پروداکشن کلاً تصمیمِ خیلی سنگین‌تریه تا اینکه بخوای تو لپ‌تاپِ خودت رویِ محیط تستی اونو اجرا کنی.
