# ۰۴.۴ — تراکنش‌ها (Transactions)

از حساب آلیس کسر کن، بریز به حساب باب. این یعنی دو تا عملِ `UPDATE`. حالا فرض کن پروسه (process) کلاً کِرش کنه — یا یه اروری پیش بیاد و تابع تو همون نقطه‌یِ *بینِ* این دو تا عملیات کلاً برگرده (early return) — آلیس پول رو پرداخته اما باب هیچ‌وقت پولی نگرفته: پولی که کاملاً دود شده رفته هوا، اونم توسط مسیری از کُد که هیچ‌کس عمداً اونجوری ننوشته بودتش. این یه نمونه‌ی کلاسیک از مشکلِ دابل-رایت یا نوشتن دوگانه (double-write failure) هستش، و تو تمام درس‌های قبلی چون ما همیشه تو هر لحظه فقط و فقط به یه دونه دستور نیاز داشتیم، از شرش قسر دررفته بودیم. دستورات به صورت تکی و انفرادی از قبل اتمی (atomic) هستن؛ **اما تراکنش‌ها میان *مجموعه‌ای* از دستورات رو به صورتِ یکجا اتمی می‌کنن**: یعنی یا همه‌شون با هم و دست‌دردست‌ِهم کامیت (commit) می‌شن، یا اینکه انگار هیچ‌کدومشون اصلاً هیچ‌وقت اتفاق نیفتادن.

تو جنگو این کار رو با کمک یه context manager انجام می‌دادی:

```python
from django.db import transaction

with transaction.atomic():
    alice.balance -= 250; alice.save()
    bob.balance += 250; bob.save()
# اگه اجرای بلوک به طور عادی تموم بشه → COMMIT می‌کنه؛ اگه از توش یه اکستپشن بپره بیرون → ROLLBACK می‌شه
```

## ریخت و قیافه‌ی یه تراکنش تو sqlx

```rust
let mut tx = pool.begin().await?;          // همون BEGIN

sqlx::query("UPDATE ...")
    .execute(&mut *tx)                     // نکته: اینجا نوشتیم tx* mut&، نه pool&
    .await?;

tx.commit().await?;                        // همون COMMIT — قبل از این خط هیچی ذخیره (persist) نمی‌شه
```

سه تا نکته تو این کد هست که می‌ارزه بهشون خیره بشی:

- **دستورِ `()pool.begin`** میاد یه اتصال (connection) رو از استخر می‌کشه بیرون و روش دستور `BEGIN` رو صادر می‌کنه. خروجیِ این متد که از نوعِ `Transaction` هست، حالا *مالکِ (owns)* اون اتصاله تا زمانی که یا کامیت شه، یا رول‌بک (rollback) بشه، یا کلاً drop بشه — که این موضوع به شدت مهمه چون یه تراکنش فقط و فقط روی یک اتصالِ واحد و مشخص 존재 داره.
- **عبارتِ `&mut *tx`** — تک‌تکِ دستوراتی که تو اون تراکنش نوشته می‌شن باید حتماً رویِ همون یک اتصالِ دارای مالکیت اجرا بشن. اگه به جای این، اشتباهاً عبارتِ `&pool` رو پاس می‌دادی، کوئری تو می‌رفت یه اتصالِ *دیگه* رو از استخر می‌گرفت و در کمال بی‌سروصدایی کلاً *بیرون از* تراکنشِ تو اجرا می‌شد. اما سیستم نوع‌ها (types) جلوی این اشتباه رو می‌گیره: کوئری‌هایی که می‌خوان داخل تراکنش ران بشن حتماً پارامتری از نوع `&mut *tx` می‌خوان (در واقع نوعِ `Transaction` خودش رو به اون `PgConnection`ِ زیربناییش نشان‌زدایی (deref) می‌کنه).
- **عبارتِ `tx.commit().await?`** — کاملاً صریحه (explicit)، دقیقاً برخلافِ رفتارِ جنگو که موقع خروج از بلوک تو خفا کامیت می‌کرد. اگه یادت بره اینو بنویسی هم هیچ‌چیز خراب یا کُراپت (corrupt) نمی‌شه: فقط هیچ دیتایی تو دیتابیس نمی‌شینه، و تست‌هات با یه عالمه سروصدا بهت میگن که کدت fail شده.

## رول‌بک (Rollback) یه رفتار پیش‌فرضه، نه چیزی که مجبوری یادت بمونه بنویسیش

ویژگیِ خفن و کشنده‌ی این سیستم اینجاست. اگه یه `Transaction` **بدون اینکه `commit` بشه، بیاد و drop بشه** — حالا به خاطر یه `return`ِ زودرس، به خاطر یه `?` که ارور رو پاس میده به بالا، یا حتی به خاطر یه پنیک — ابزار sqlx قبل از اینکه اون اتصال رو برگردونه تو استخر، خیلی ترتمیز یه دستورِ `ROLLBACK` روش صادر می‌کنه. جنگو زمانی رول‌بک می‌کنه که یه استثنا (exception) از بلوکِ `with` فرار کنه؛ اما تو زبان Rust که اصلاً چیزی به اسم استثنا نداریم، در نتیجه sqlx میاد همون ضمانت رو وصل می‌کنه به چیزی که خودِ زبان Rust *واقعاً* تضمینش می‌کنه: یعنی متدِ `Drop` که همیشه موقع پاک شدن متغیر اجرا می‌شه. پس هر کدوم از اون علامت‌های `?` که داخلِ تابعِ `transfer` نوشته شدن، به طورِ پنهانی یه نقطه‌ی رول‌بک هم هستن — کلاً امکان نداره یادت بره رول‌بک کنی، چون رول‌بک شدن دقیقاً همون چیزیه که وقتی *یادت می‌ره* بنویسی `commit`، خودبه‌خود اتفاق می‌افته.

## وقتی الگو «چک‌کن، بعد‌بنویس» (Check-then-write) باشه، به قفل کردنِ ردیف (row lock) نیاز داری

تابعِ `transfer` مقدارِ موجودیِ (balance) فرستنده رو اول از همه می‌خونه، چکش می‌کنه، و بعد کسر (debit) می‌کنه. حالا اگه همزمان دو تا انتقال (transfer) بخوان از یه حساب انجام بشن، هر دوشون می‌تونن مقدارِ `100` رو بخونن، هردوشون می‌تونن پیش خودشون نتیجه بگیرن که موجودی واسه کسر کردنِ `60` تا کافیه، و در نهایت با همدیگه حساب رو منفی کنن (overdraw). اضافه کردنِ `SELECT ... FOR UPDATE` (که تو جنگو معادلش می‌شه `()select_for_update`) میاد اون ردیف رو قفل می‌کنه تا زمانی که تراکنش ما یا کامیت بشه یا رول‌بک بشه؛ در نتیجه انتقالِ دوم پشتِ در صبر می‌کنه و تازه بعد از اون، موجودیِ حسابِ *کسرشده* رو می‌خونه. تازه اگه با این وجود هم یه باگی بتونه از سد این بررسی‌ها رد بشه، اون شرط و قیدی (constraint) که تو فایلِ مایگریشن به شکل `CHECK (balance_cents >= 0)` نوشتیمش، همون خطِ دفاعیِ آخره که دیتابیس تو تک‌تک دفعاتی که می‌خواد چیزی رو توش بنویسه با قدرت اجراش می‌کنه، فرقی هم نداره که کدوم بخش از کد باعثش شده باشه. (همونطور که تو کامنت‌های فایل مایگریشن هم اومده، موجودی حساب‌ها همیشه بر اساس سِنت و به شکل اعداد صحیح (integer cents) نوشته می‌شن، نه اینکه از اعداد اعشاری (floats) استفاده بشه.)

## مایگریشن‌های برگشت‌پذیر (Reversible) و دستورِ `sqlx migrate revert`

درس 04.2 از مایگریشن‌هایی استفاده می‌کرد که فقط تو یه فایل نوشته می‌شدن (`0001_create_widgets.sql`) — یعنی فقط قابلیت رفتن به جلو رو داشتن (forward-only). اما پوشه‌ی `migrations/`ِ این درس، از یه استایل **برگشت‌پذیر** استفاده می‌کنه:

```
0001_create_accounts.up.sql     # این همون چیزیه که sqlx::migrate! یا دستورِ sqlx migrate run اجراش می‌کنه
0001_create_accounts.down.sql   # این *فقط و فقط* توسط دستورِ `sqlx migrate revert` اجرا می‌شه
```

تابع `run_migrations` میاد فایل‌های `.up.sql` رو دقیقاً همونطوری ران می‌کنه که با اون تک‌فایل‌ها تو درس 04.2 برخورد می‌کرد. اما اون فایلِ down واسه روزیه که یه دیپلوی خراب از آب درمیاد: دستورِ `sqlx migrate revert` (که از طریق همون ابزار sqlx-cli میاد، و می‌تونی با `cargo install sqlx-cli --no-default-features --features postgres` نصبش کنی) میاد و **جدیدترین مایگریشنی که اعمال شده** رو، با اجرایِ فایلِ downِ اون و پاک کردن ردیف مربوطه‌اش از جدولِ `_sqlx_migrations`، باطل (undo) می‌کنه — یعنی با هر بار فراخوانی یه مایگریشن رو برمی‌گردونه، از جدیدترین به سمت قدیمی‌ترین. دستورِ `migrate app 0005` تو جنگو که همون مفهوم "به عقب برگردوندن" بود دقیقاً همون ایده رو داره، با این فرق که جنگو خودش به صورت اتوماتیک متوجه می‌شه چطور برگردونتش؛ اما اینجا خودِ تویی که باید دستور `DROP TABLE` رو دستی بنویسی. یه قانونم اینجا هست: تمام فایل‌های تو یه دایرکتوریِ مایگریشن باید کلاً از یه استایل استفاده کنن — ابزار sqlx اجازه نمی‌ده فایل‌هایِ `.sql` و `up.sql./down.sql.` رو با هم و قاطی تو یه جا بذاری.

```sh
DATABASE_URL=postgres://taskforge:***@localhost:5432/p3_04_04_transactions \
  sqlx migrate revert --source phase3-backend-foundations/04-postgres-and-sqlx/04-transactions/migrations
```

## چرا این درس دوباره یه دیتابیس اختصاصی واسه خودش می‌گیره

دقیقاً همون تله‌ای که تو درس 04.2 در موردش صحبت شد: جدولِ `_sqlx_migrations` به ازای هر *دیتابیس* یدونه‌ست، و کلید ردیف‌هاش هم شماره نسخه‌ست، و مایگریشنِ این درسم دقیقاً مثل درس 04.2 و پروژه‌ی نهاییِ کپستون، همون "نسخه‌ی 1" هست — اگه از یه دیتابیس مشترک استفاده می‌کردیم همه‌چی تهش به خطایِ `VersionMismatch` می‌خورد. واسه اینکه دیتابیس رو بسازی اینو (فقط یه بار) ران کن:

```sh
sudo -u postgres psql -c "CREATE DATABASE p3_04_04_transactions OWNER taskforge;"
```
