# چک‌پوینت

1. تستِ `migrating_creates_the_widgets_table` قبل از اینکه تابع `run_migrations` رو صدا بزنه، اول با یه دستورِ `DROP TABLE IF EXISTS` شروع می‌کنه و بعدش به صورت دستی، ردیفِ رهگیریِ (tracking row) مربوط به نسخه‌ی ۱ رو پاک می‌کنه. با توجه به اینکه جدولِ `_sqlx_migrations` خودش بین تمام دفعاتی که تست ران می‌شه زنده می‌مونه و پاک نمی‌شه، چرا انجام دادنِ این کارایِ تمیزکاری (cleanup) برای اینکه نتایجِ این تست خاص معنی‌دار باشه ضروریه؟
2. اگه یه فایل دوم به اسم `0002_add_widget_price.sql` می‌ساختی که توش دستورِ `;ALTER TABLE p3_04_02_widgets ADD COLUMN price_cents BIGINT NOT NULL` نوشته شده بود، و تابع `run_migrations` رو رو دیتابیسی ران می‌کردی که از قبل مایگریشنِ `0001` روش اعمال شده بود، چه اتفاقی می‌افتاد؟ حالا در نقطه‌ی مقابل، اگه به جای این کار، می‌اومدی کدهای داخلِ همون فایلِ `0001_create_widgets.sql` رو — بعد از اینکه یک‌بار به طور کامل رو دیتابیس ران شده و اعمال شده بود — دست‌کاری (edit) می‌کردی و عوض می‌کردی، اونوقت چه اتفاقی می‌افتاد؟
3. تابعِ `run_migrations` کدهای SQLِ مایگریشن رو دقیقاً تو زمانِ کامپایل (compile time)، داخلِ باینریِ (binary) کامپایل‌شده‌ی نهایی جاسازی (embed) می‌کنه. اگه این روش رو با روشِ خوندنِ فایل‌های `sql.` از روی دیسک تو زمانِ اجرا (runtime) مقایسه کنیم، فایده‌ی عملی و واقعیِ این کار موقعِ دیپلوی (deployment) کردن پروژه چیه؟
4. جدول رهگیریِ `_sqlx_migrations` تو این درس رو با جدولِ `django_migrations` تو جنگو مقایسه کن — آیا ایده‌ی زیربنایی‌شون یکیه؟ اما کدوم بخشِ این جریان کاری (workflow) هستش که واقعاً بینشون فرق داره و متفاوت از هم عمل می‌کنن (راهنمایی: به دستورِ `makemigrations` فکر کن).
5. توابعِ `insert_widget` و `count_widgets` به جایِ `sqlx::query_as` دارن از تابعِ `sqlx::query_scalar` استفاده می‌کنن. حالا که خودت هردوشونو پیاده‌سازی کردی، بگو تفاوتِ واقعیِ بینشون چیه — و کِی استفاده از `query_scalar` کلاً انتخابِ اشتباهیه؟
6. این درس به جای استفاده از دیتابیسِ مشترکِ `taskforge` (همونی که بقیه‌ی درس‌های Postgres تو این مخزن دارن دائم ازش استفاده می‌کنن)، به دیتابیسِ کاملاً اختصاصیِ خودش یعنی `p3_04_02_migrations` متصل می‌شه. دوباره دلیلِ این موضوع رو از روی فایلِ README بخون. حالا با کلماتِ خودت بگو: دقیقاً چه ویژگی‌ای از `_sqlx_migrations` هست که باعث می‌شه به اشتراک‌گذاریش بینِ دو تا فراخوانیِ `!sqlx::migrate`ِ نامرتبط انقدر خطرناک (unsafe) بشه، جوری که صرفاً پیشوند زدن به اسمِ جداول (همون راه حلی که تمامِ درس‌های دیگه دارن ازش استفاده می‌کنن) هم نتونه این مشکل رو حل کنه؟
7. تک‌تک تست‌های این درس با صفتِ `[(serial(p3_04_02_migrations_db#]` علامت‌گذاری شدن. بیا و فقط این صفت رو از روی تستِ `inserted_widgets_are_counted` پاک کن (بذار رو اون دو تای دیگه بمونه) و دستورِ `cargo test -p p3-04-02-migrations -- --ignored` رو چندین بار پشت سر هم ران کن. چه چیزی می‌بینی؟ و چرا حذف کردن این صفت فقط و فقط از روی *یکی* از اون سه تا تست، باز هم باعث می‌شه که کلِ این مجموعه تست‌ها ناامن (unsafe) و مشکل‌دار بمونن؟
