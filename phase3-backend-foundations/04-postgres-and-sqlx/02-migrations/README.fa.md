# ۰۴.۲ — مایگریشن‌ها (Migrations)

ابزارهای `makemigrations`/`migrate` تو جنگو وظیفه‌شون اینه که تغییرات شمای دیتابیس (schema) رو به شکل یه دنباله‌ی مرتب از فایل‌های شماره‌دار رهگیری (track) کنن، هر کدوم رو که دیتابیسِ مقصد تا حالا ندیده روش اِعمال کنن، و تهش هم ثبت کنن که چی اِعمال شده تا هیچ مایگریشنی دو بار ران نشه. ماکروی `!sqlx::migrate` دقیقاً همون کارو می‌کنه، منتهی با این تفاوت که اینجا خبری از تولید خودکارِ (auto-generation) کُد از روی تفاوتِ مدل‌ها (model diffs) نیست — تو کدهای SQL رو خودت با دست می‌نویسی، و `sqlx` فقط زحمتِ ترتیب‌بندی، رهگیری، و جلوگیری از اجرایِ دوباره‌ی اونا رو می‌کشه.

## خوندنِ فایل `migrations/0001_create_widgets.sql`

```sql
CREATE TABLE p3_04_02_widgets (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

قراردادِ نام‌گذاری فایل‌ها: اول یه پیشوند عددی (یا timestamp) که ترتیب اعمال شدن رو مشخص می‌کنه، و بعدش یه توضیح کوتاه — واسه `sqlx` اصلاً مهم نیست از چه فرمتی استفاده می‌کنی، به شرطی که فایل‌ها موقعِ مرتب‌سازی (sort) دقیقاً به همون ترتیبی قرار بگیرن که می‌خوای اجرا بشن. تو پروژه‌های واقعی معمولاً به جای اینکه برنامه‌نویس‌ها فایل‌ها رو دستی بسازن، از دستور `<sqlx migrate add <name` (از طریق ابزار `sqlx-cli`) استفاده می‌کنن تا خودش یه فایل با اسم درست و تایم‌استمپ‌دار براشون تولید کنه.

## دستورِ `sqlx::migrate!("./migrations").run(pool)` تو واقعیت چیکار می‌کنه

1. تک‌تکِ فایل‌های `.sql` تو پوشه‌ی `/migrations/` رو در **زمان کامپایل (compile time)** می‌خونه (مسیرِ پوشه نسبت به فایلِ `Cargo.toml` کریت سنجیده می‌شه، و کُل متن‌های SQL مستقیماً تو دلِ باینریت جاسازی و تعبیه می‌شن (embedded) — یعنی موقع دیپلوی (deployed build) اصلاً نیازی نیست فایل‌های `.sql` جداگانه‌ای همراه با برنامه‌ات جابجا بشن).
2. تو زمان اجرا (runtime)، اگه از قبل وجود نداشته باشه، یه جدولِ حسابداری و دفتری به اسمِ `_sqlx_migrations` تو دیتابیست می‌سازه (ستون‌هاش: نسخه (version)، توضیحات، چک‌سامِ (checksum) محتویات فایل، و اینکه کِی اعمال شده).
3. بعد برای تک‌تکِ فایل‌های مایگریشن، به همون ترتیبی که دارن: اگه نسخه‌ی (version) اون فایل قبلاً تو `_sqlx_migrations` ثبت نشده باشه، میاد اونو تو دلِ یه تراکنش (transaction) ران می‌کنه و ثبتش می‌کنه؛ و اگه *قبلاً* ثبت شده باشه، کلاً از روش می‌پره و نادیده‌اش می‌گیره.

نکته‌ی سوم دقیقاً همون دلیلیه که تستِ `running_migrations_twice_is_a_safe_no_op` پاس می‌شه: اگه بعد از اولین اجرای موفقیت‌آمیز، دوباره بیای تابع `run_migrations` رو صدا بزنی تو دفعه‌ی دوم اصلاً هیچ اتفاقی نمی‌افته — چون تکلیفِ همه‌ی مایگریشن‌ها از قبل مشخص شده — به جای اینکه با خطای "رابطه یا جدول از قبل وجود داره (relation already exists)" متوقف بشه.

## چرا کُلِ تست‌های اینجا برچسب `#[serial(p3_04_02_migrations_db)]` دارن

دستور `cargo test` به طور پیش‌فرض توابع `#[test]`ِ مختلف رو **به صورت همروند (concurrently)** اجرا می‌کنه (روی ریسمان‌های سیستم‌عامل (OS threads) جداگانه)، و اینجا هم هر سه تا تست دارن از *یه دونه* دیتابیسِ Postgres واقعیِ مشترک استفاده می‌کنن — و تستِ `migrating_creates_the_widgets_table` کلاً میاد جدولی رو که اون دو تا تست دیگه قراره ازش بخونن، به صورت کاملاً فعال `DROP` می‌کنه. اگه صفتِ `#[serial]` (از کریتِ `serial_test`) وجود نداشته باشه، این وضعیت رسماً یه شرط مسابقه (race) خطرناکه: اگه زمان‌بندیِ عمل drop دقیقاً بیفته وسطِ کوئری‌هایِ تستِ دیگه، اون تست در کمال تعجب می‌بینه که جدولی که روش بود یهو دود شد رفت هوا و با خطا مواجه می‌شه — نه به خاطر اینکه منطقِ توابع `run_migrations`/`insert_widget`/`count_widgets`ت اشتباه بوده، فقط و فقط به این خاطر که دو تا تست دقیقاً تو یه لحظه دستشون رفت سمت یه دیتابیسِ زنده. صفتِ `#[serial(p3_04_02_migrations_db)]` به مجموعه‌ابزارِ تست می‌گه "هیچ‌کدوم از تست‌هایی که این برچسب رو دارن حق ندارن همزمان با همدیگه ران بشن" — تست‌ها هنوزم با همون یه بار زدنِ `cargo test` اجرا می‌شن، اما این‌بار نوبتی و یکی‌یکی اجرا می‌شن نه تو هم تو هم (interleaved)، که این کار به تنهایی کافیه تا اجرای سه تا تستی که دارن رو یه دیتابیسِ تغییرپذیرِ (mutable) Postgres مشترک می‌تازن، کاملاً قابل‌پیش‌بینی (deterministic) و بی‌نقص بشه. (تو مجموعه‌تست‌هایی که با `<...Mutex<HashMap>` تو حافظه کار می‌کردن هیچ‌وقت همچین مشکلی نداشتیم: چون هر تست ذخیره‌گاه (store) اختصاصیِ خودش رو داشت، پس اصلاً چیزی واسه مسابقه دادن (race) وجود نداشت — این مشکل دقیقاً و مشخصاً مختص تست‌های یکپارچگیِ دیتابیسِ زنده‌ست.)

## چرا خود کُدهای SQL اصلاً به `IF NOT EXISTS` نیازی ندارن

کسایی که از اسکریپت‌های اد-هاک و دستی (ad-hoc) SQL میان، غریزه‌شون اینه که برای محکم‌کاری (defensively) همه‌جا از `CREATE TABLE IF NOT EXISTS` استفاده کنن. اما اینجا، این کار فقط دوباره‌کاری و اضافه‌کاریه: خودِ جدولِ رهگیریِ `_sqlx_migrations` دقیقاً همون چیزیه که تضمین می‌کنه اعمالِ دوباره، تغییری تو سیستم نمی‌ده (idempotency guarantee) — ابزار `sqlx` به هیچ‌وجه تلاش نمی‌کنه تا یه مایگریشن رو که از قبل چک‌سامش (checksum record) ثبت شده، دوباره ران کنه، در نتیجه کدهای SQLِ زیربنایی می‌تونن (و البته واسه اینکه وقتی واقعاً یه باگِ اِعمال‌مضاعفِ (double-application) واقعی رخ می‌ده خطای تمیزتری بدن، بهتره که) با خیال راحت فرض کنن که دارن رو یه زمین تمیز و پاک (clean slate) ران می‌شن.

## چرا این درس دیتابیسِ اختصاصی خودش رو داره، و از دیتابیسِ مشترکِ `taskforge` استفاده نمی‌کنه

هر درسِ دیگه‌ای تو این ماژول که با Postgres کار داره، از همون دیتابیسِ `taskforge` استفاده می‌کنه و واسه اینکه جداولشون (tables) با هم تداخل پیدا نکنن فقط به اولِ اسمِ جداولِ *داده‌شون (data table)* یه پیشوند می‌زنن (`p3_04_02_widgets`، `p3_04_03_anime`) — این روش به خوبی کار می‌کنه چون جداولِ هر درس فقط به خودِ همون درس مربوط می‌شن. اما جدول حسابداریِ `_sqlx_migrations` (همون که ماکروی `!sqlx::migrate` می‌سازتش)، داستانش متفاوته: این جدول به ازای هر کریت (per-crate) پیشوند نمی‌خوره، بلکه تو هر *دیتابیس* کلاً فقط یه دونه از این جدول هست، که کلیدِ (key) ردیف‌هاش هم فقط و فقط همون نسخه‌ی عددیِ (numeric version) هر مایگریشونه. فایلِ `0001_create_widgets.sql` مربوط به این درس، و فایلِ `0001_create_jobs.sql` که مال خودِ کریتِ `capstone-taskforge/taskforge-storage` هست، هر دوشون "نسخه‌ی ۱" حساب می‌شن — اگه جفتشون بخوان ماکروی `!sqlx::migrate`شون رو روی *یه* دیتابیسِ یکسان ران کنن، اونی که دوم از همه اجرا بشه می‌بینه که نسخه‌ی ۱ از قبل تو اون دیتابیس ثبت شده، اونم با چک‌سامِ (checksum) یه فایلِ *دیگه*، و با ارورِ `VersionMismatch` کلاً قفل می‌کنه؛ و بدتر از اون، اجرای تست‌های این درس می‌تونه خیلی راحت و بی‌سروصدا، سابقه‌ی مایگریشنِ (migration tracking) کریتِ پروژه‌ی نهایی (capstone) رو پاک کنه و رونویسی کنه. (این کلاً یه فرضِ تئوری و الکی نیست — این یه تداخلِ کاملاً واقعیه که دقیقاً موقعِ ساخته شدن همین مخزن (repo) رخ داده، و همون دلیلیه که باعث شد این درس کلاً یه دیتابیس ایزوله برای خودش بگیره.) واسه ساختنِ یه دیتابیسِ اختصاصی فقط یه بار این دستور رو بزن:

```sh
sudo -u postgres psql -c "CREATE DATABASE p3_04_02_migrations OWNER taskforge;"
```
