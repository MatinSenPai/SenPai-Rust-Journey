# راه‌حل

```rust
pub fn share_config(config: AppConfig) -> Rc<AppConfig> {
    Rc::new(config)
}

pub fn add_owner(shared: &Rc<AppConfig>) -> Rc<AppConfig> {
    Rc::clone(shared)
}

pub fn owner_count(shared: &Rc<AppConfig>) -> usize {
    Rc::strong_count(shared)
}

pub fn same_allocation(a: &Rc<AppConfig>, b: &Rc<AppConfig>) -> bool {
    Rc::ptr_eq(a, b)
}

pub fn share_config_across_threads(config: AppConfig) -> Arc<AppConfig> {
    Arc::new(config)
}
```

پنج تک‌خط، و هرکدام دارد فقط اسمِ یک تابعِ وابسته‌ی `Rc`/`Arc` را می‌گوید — کارِ
واقعی از قبل تویِ کتابخانه‌ی استاندارد نوشته شده. نکته دقیقاً همین است:
مالکیتِ اشتراکی چیزی نیست که خودت بسازی‌اش، نوعی است که سراغش می‌روی.

## `add_owner` — همان خطی که ارزشِ خیره‌شدن دارد

فراخوانیِ `Rc::clone(shared)` اصلاً دست به آن `AppConfig`ِ رویِ هیپ نمی‌زند —
نه برایِ `app_name` یک `String` تازه ساخته می‌شود، نه `max_connections`
کپی می‌شود. تنها اتفاقی که می‌افتد این است که شمارنده‌ی داخلیِ `Rc` یکی بالا
می‌رود و تو در جواب یک پوینترِ دومِ جدید می‌گیری که به *همان* حافظه اشاره
می‌کند. دقیقاً همین است دلیلِ اینکه درس اصرار دارد بنویسی `Rc::clone(shared)`
به‌جایِ `shared.clone()`، با اینکه هر دو دقیقاً به یک فراخوانی کامپایل
می‌شوند: نوشتارِ صریح، همان‌جا تویِ محلِ فراخوانی، می‌گوید «این یک کلونِ ارزانِ
پوینتر است» — نوشتارِ نقطه‌ای این کار را نمی‌کند و خواننده مجبور می‌شود اول
برود ببیند نوعِ `shared` اصلاً چیست.

## `same_allocation` — اثبات، نه فقط ادعا

فراخوانیِ `Rc::ptr_eq(a, b)` یک سؤالِ کاملاً متفاوت از `*a == *b` می‌پرسد.
`*a == *b` می‌پرسد «آیا این دو تا `AppConfig` فیلدهایِ برابر دارند؟» — که
برایِ هر دو `AppConfig` با همان `app_name` و همان `max_connections` درست
است، حتی اگر از دو فراخوانیِ کاملاً بی‌ربطِ `Rc::new` آمده باشند. اما
`Rc::ptr_eq` می‌پرسد «آیا این دو دستگیره واقعاً به *همان* تخصیصِ هیپ اشاره
می‌کنند؟» — که فقط وقتی درست است که یکی‌شان از کلون‌کردنِ `Rc`ِ آن یکی به
دست آمده باشد، هیچ‌وقت برایِ دو `Rc` که مستقل از هم ساخته شده‌اند، هرچقدر هم
دیتاشان برابر به‌نظر برسد. تستِ
`same_allocation_is_false_for_two_equal_but_separate_rcs` دقیقاً برایِ این
ساخته شده که این دو سؤال با هم قاطی نشوند: دو `Rc<AppConfig>` از رویِ دیتایِ
کاملاً یکسان می‌سازد، اول مطمئن می‌شود `*a == *b` (دیتا برابر است)، بعد
مطمئن می‌شود `same_allocation` هنوز `false` می‌گوید (تخصیص‌ها جدا هستند).

## `owner_count` و تستِ drop

`owner_count` فقط همان `Rc::strong_count` است، زیرِ یک اسم که برایِ این درس
معنایش را روشن‌تر می‌گوید. بخشِ جالب، خودِ تابع نیست — تستِ
`dropping_an_owner_decrements_the_count` است، که دقیقاً رویِ همان قانونِ
پاکسازیِ خودکاری تکیه دارد که فاز ۱ از قبل به‌ات داده: `Drop` یک مقدار دقیقاً
همان لحظه‌ای اجرا می‌شود که اسکوپِ مالکش تمام می‌شود، بدونِ اینکه چیزی به
زمان‌بندیِ یک garbage collector سپرده شود. اسکوپِ `_second` همان بلوکِ داخلیِ
`{ }` است؛ وقتی آن بلوک بسته می‌شود، `_second` drop می‌شود، و پیاده‌سازیِ خودِ
`Drop` برایِ `Rc` است که واقعاً شمارنده را یکی کم می‌کند (و اگر همان لحظه به
صفر رسیده بود، آن `AppConfig` را هم آزاد می‌کرد). این رفتار را کاملاً رایگان
می‌گیری — همان قانونِ «عمرِ هر مقدار با تمام‌شدنِ اسکوپش تمام می‌شود» که از قبل
می‌دانستی، فقط این‌بار یک شمارنده را کم می‌کند به‌جایِ اینکه بی‌درنگ حافظه را
آزاد کند، چون آنچه اینجا از اسکوپ خارج می‌شود خودِ دستگیره‌ی `Rc` است، نه
دیتایِ زیرِ آن.

## `share_config_across_threads` — همان شکل، شمارنده‌ای دیگر

`Arc::new` دقیقاً مثلِ `Rc::new` خوانده می‌شود، چون API عمداً همین‌طور طراحی
شده. هیچ‌جایِ این تابع (یا تستش) واقعاً از مرزِ یک ریسمان رد نمی‌شود — آن بخشِ
داستان مالِ ماژول ۸ است. چیزی که امروز اهمیت دارد این است که بدانی شمارنده‌ی
`Arc<T>` با دستورالعمل‌هایِ اتمیِ پردازنده بالا و پایین می‌رود، نه با
دستورالعمل‌هایِ معمولیِ `Rc<T>` — و دقیقاً همین تنها دلیلی است که `Arc<T>`
اصلاً امن است دستِ یک ریسمانِ دوم بدهی: یک افزایشِ عددیِ معمولی در واقع یک
«بخوان، بعد بنویس» است، و اگر دو ریسمان هم‌زمان همین کار را رویِ یک شمارنده‌ی
غیراتمی انجام بدهند، ممکن است یک افزایش گم شود و شمارنده زودتر از موعد به
صفر برسد — یعنی مقدار آزاد شود درحالی‌که یک دستگیره به آن هنوز جایی زنده
است. این ایمنیِ اضافه رایگان نیست، و دقیقاً همین است دلیلِ اینکه درس هرگز
نمی‌گوید «همیشه از `Arc` استفاده کن»: هزینه‌ی شمارنده‌ی اتمی را فقط وقتی
بپرداز که یک مقدار واقعاً باید از یک ریسمان بیرون برود.
