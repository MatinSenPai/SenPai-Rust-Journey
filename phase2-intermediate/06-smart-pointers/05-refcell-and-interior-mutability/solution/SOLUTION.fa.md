# راه‌حل

```rust
pub fn increment(&self) {
    *self.inner.borrow_mut() += 1;
}

pub fn get(&self) -> i32 {
    *self.inner.borrow()
}
```

متغیر `self.inner` از نوعِ `<Rc<RefCell<i32>>` هست — متدِ `.borrow_mut()` داره از طریق همون ارجاعِ اشتراکی و معمولیه `Rc` کار خودش رو روی `RefCell` انجام می‌ده (و هیچ نیازی هم به استفاده از `&mut self` تو هیچ‌جا نیست، چون `RefCell` وظیفه‌ی بررسی تغییرپذیری رو موکول کرده به زمانِ اجرا یا همون run time)، و در نهایت یه `<RefMut<i32>` برمی‌گردونه که اون علامت `*` (نشان‌زدایی یا deref) اجازه می‌ده تا ما مقدارِ واقعیِ `i32` رو بخونیم یا روش بنویسیم. محافظ‌های `RefMut`/`Ref` (guards) بلافاصله با تموم شدن همون دستورِ (statement) خط پاک (drop) می‌شن (چون اینجا موقتن (temporaries) و تو هیچ متغیری ذخیره نشدن)، و این دقیقاً همون دلیلیه که چرا صدا زدنِ پشتِ سرِ همِ `()increment` دوبار پشت هم هرگز باعث پنیک (panic) نمی‌شه — چون قرضِ هر کدوم از فراخوانی‌ها، قبل از اینکه فراخوانیِ بعدی شروع بشه، به طور کامل آزاد می‌شه.

در مورد سؤال ۲ مرور: بدون استفاده از `RefCell`، وجودِ `<inner: Rc<i32` فقط و فقط همون دسترسیِ `&i32` رو به تک‌تکِ نسخه‌های کپی‌شده از دستگیره‌ها (clones) می‌ده — خود `Rc` اصلاً اجازه نمی‌ده که از طریق یه ارجاع اشتراکی (shared reference) چیزی تغییر داده بشه (و این دقیقاً همون قانون «یا نام مستعار، یا تغییرپذیری (aliasing XOR mutability)» از فاز ۱ هست، که چون APIِ خودِ `Rc` هیچ راهی برای تغییرِ چیزی که بهش اشاره می‌کنه ارائه نمی‌ده، این قانون حفظ می‌شه). تو این حالت تو با متدهایی مثلِ `&self` گیر می‌افتادی که فقط می‌تونستن بخونن، نه اینکه چیزی بنویسن — نوعِ `RefCell` دقیقاً همون ابزاریه که با منتقل کردنِ کنترلِ قانونِ "در هر لحظه فقط یک دسترسیِ تغییرپذیرِ مجاز است" از زمان کامپایل به زمانِ اجرا، قابلیتِ تغییرپذیری (mutation) رو دوباره زنده می‌کنه و برمی‌گردونه.
