# ۲.۶.۱ — `Box` و تخصیصِ هیپ

## در یک نگاه

بعد از این درس می‌توانی:

- توضیح بدهی `Box<T>` واقعاً چیست — یک اشاره‌گرِ هوشمند با یک مالکِ یکتا — و بگویی دقیقاً چه لحظه‌ای حافظه‌ی هیپش آزاد می‌شود.
- برایِ هر `T`ای، بدونِ اجرا کردنِ کد، بگویی `size_of::<Box<T>>()` چند است و چرا این عدد هیچ‌وقت به اندازه یا محتوایِ `T` بستگی ندارد.
- سه واقعیتی را که فازِ ۱ و فازِ ۲ تا امروز فقط به‌عنوانِ یک قرار به‌ات نشان دادند — چرا `Option<Box<T>>` رایگان است، چرا `Box<str>` دو کلمه است نه سه، چرا `Box<dyn Trait>` یک اندازه‌ی ثابت دارد — از حفظ توضیح بدهی، نه فقط تکرارشان کنی.

## چرا اهمیت دارد

از فازِ ۱ تا همین امروز، `Box<T>` شش بار جلویِ رویت آمده — و هر شش بار، درس دقیقاً همان یک تکه‌ای را گفت که همان لحظه لازم داشتی، و بعد یک قرض گذاشت برایِ بعداً:

- [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) اندازه‌اش را کنارِ `String` و `&str` گذاشت: «مالکی بدونِ ظرفیت، دو کلمه به‌جایِ سه.» بدونِ اینکه بگوید چرا دقیقاً دو کلمه.
- [۱.۵.۳](../../../phase1-fundamentals/05-your-own-types/03-enums-as-data/README.fa.md) به‌ات نشان داد `size_of::<Option<Box<i32>>>()` با `size_of::<Box<i32>>()` برابر است — «بهینه‌سازیِ جای‌خالی» — و با یک جمله رد شد.
- [۱.۶.۱](../../../phase1-fundamentals/06-absence-and-failure/01-option-and-null-safety/README.fa.md) همان واقعیت را از زاویه‌ی `Option` دوباره نشانت داد، و با یک جمله رد شد: «`Box<T>` یک اشاره‌گرِ هیپ است، مالکِ چیزی که به آن اشاره می‌کند — دقیقاً همین یک خط امروز لازم داری؛ درسِ کاملش فاز ۲ است.»
- [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) از `Box<dyn Trait>` استفاده کرد تا یک `Vec` ناهمگون بسازد، و گفت: «داستانِ کاملِ `Box`... مالِ ۲.۶.۱ است؛ امروز فقط همین یک نقشش را لازم داریم.»
- [۲.۴.۳](../../04-lifetimes-and-conversion/03-deref-asref-borrow/README.fa.md) نشانت داد `Box<T>` صفتِ `Deref` را دارد — برایِ همین یک `Box<String>` مثلِ خودِ `String` رفتار می‌کند — و همان جمله را تکرار کرد: «داستانِ کاملِ `Box`، تخصیصِ هیپ و مالکیتش، مالِ ۲.۶.۱ است.»
- [۲.۵.۲](../../05-error-handling/02-error-source-chains/README.fa.md) دقیقاً همان جمله را، این‌بار رویِ `Box<dyn Error>`، تکرار کرد.

شش بار قرض گرفته شد، صفر بار پس داده شد. امروز روزِ پس‌دادن است.

و نکته این نیست که فقط یک تعریف بشنوی. نکته این است که یک واقعیتِ واحد — اندازه‌ی `Box<T>` هرگز به اندازه یا محتوایِ `T` بستگی ندارد — هر شش‌تایِ آن قرض را یک‌جا صاف می‌کند. همین یک جمله توضیح می‌دهد چرا `Option<Box<T>>` رایگان است، چرا `Box<str>` دو کلمه است نه سه، و چرا `Box<dyn Trait>` برایِ هر نوعِ ملموسی که پشتش باشد یک اندازه‌ی ثابت دارد. تا آخرِ این درس، هر سه‌یِ این‌ها از یک قرارِ حفظی به چیزی تبدیل می‌شوند که خودت با `size_of` اثبات کرده‌ای.

## مفهوم

### `Box<T>` چیست: یک اشاره‌گرِ هوشمند با یک مالک

یک **اشاره‌گرِ هوشمند (smart pointer)** ساختاری است که مثلِ یک اشاره‌گر عمل می‌کند — می‌گذارد به دیتایی برسی — ولی رویِ آن یک قولِ اضافه هم دارد: مالکِ چیزی است که به آن اشاره می‌کند. `Box<T>` ساده‌ترینِ این خانواده است: یک مقدارِ از نوعِ `T` که رویِ هیپ جابه‌جا شده، با یک اشاره‌گرِ ساده رویِ پشته که به آن اشاره می‌کند.

```rust
let boxed: Box<i32> = Box::new(5);
println!("boxed  = {boxed}");
println!("*boxed = {}", *boxed);
```

```text
boxed  = 5
*boxed = 5
```

`Box::new(5)` عددِ `۵` را از پشته برمی‌دارد، رویِ هیپ جایش می‌دهد، و یک `Box<i32>` برمی‌گرداند که فقط یک اشاره‌گر به آن است. برایِ خواندنِ مقدارِ داخلش، `*boxed` را داری — همان عملگرِ بازکردنِ ارجاع (dereference) که از [۱.۳.۱](../../../phase1-fundamentals/03-borrowing-and-references/01-shared-and-mutable-refs/README.fa.md) می‌شناسی، فقط این‌بار به‌جایِ یک ارجاعِ قرضی، یک مالک را باز می‌کند.

اغلب حتی همین `*` هم لازم نمی‌شود. [۲.۴.۳](../../04-lifetimes-and-conversion/03-deref-asref-borrow/README.fa.md) به‌ات نشان داد `Box<T>` صفتِ `Deref` را پیاده کرده، پس کامپایلر سرِ فراخوانیِ متد، خودش دنبالِ ارجاع را می‌گیرد:

```rust
struct Point {
    x: i32,
    y: i32,
}

impl Point {
    fn distance_from_origin(&self) -> f64 {
        ((self.x * self.x + self.y * self.y) as f64).sqrt()
    }
}

let boxed_point = Box::new(Point { x: 3, y: 4 });
println!("distance = {}", boxed_point.distance_from_origin());
```

```text
distance = 5
```

`Box<Point>` خودش متدی به اسمِ `distance_from_origin` ندارد. کامپایلر یک `*` را برایت جا می‌گذارد، به `Point`ی که رویِ هیپ است می‌رسد، و همان‌جا متد را پیدا می‌کند. به این می‌گویند **بازکردنِ خودکارِ ارجاع (auto-deref)**، و پسرعموی همان **تبدیلِ ضمنیِ deref (deref coercion)** است که [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) رویِ `&String` → `&str` نشانت داد — هردو از یک صفتِ عمومی می‌آیند، نه یک ویژگیِ مخصوصِ `Box`.

و مالکیت هم دقیقاً همان قاعده‌ی همیشگی است، فقط با یک لایه‌ی غیرمستقیم‌سازیِ بیشتر: `Box` مالکِ آن مقدارِ رویِ هیپ است، و سرِ آکولادِ بسته‌ی دامنه‌اش — دقیقاً همان چیزی که [۱.۲.۵](../../../phase1-fundamentals/02-ownership-and-memory/05-drop-and-raii/README.fa.md) به RAII داد — تخریب‌گرِ `T` اجرا می‌شود و بلوکِ هیپ آزاد می‌شود:

```rust
struct Loud(String);

impl Drop for Loud {
    fn drop(&mut self) {
        println!("dropping: {}", self.0);
    }
}
```

```rust
println!("--- entering inner scope ---");
{
    let inner = Box::new(Loud(String::from("inner")));
    println!("inner alive: {}", inner.0);
}
println!("--- inner scope ended ---");
```

```text
--- entering inner scope ---
inner alive: inner
dropping: inner
--- inner scope ended ---
```

`dropping: inner` دقیقاً پیش از `--- inner scope ended ---` چاپ می‌شود، نه بعدش. تا امروز RAII را رویِ مقدارهایِ روی‌پشته دیده بودی؛ این اولین‌بار است که همان قاعده را رویِ چیزی می‌بینی که واقعاً رویِ هیپ نشسته — و رفتارش یک ذره هم فرق نکرده.

```senpai-visual
{"kind":"ownership","labels":["Box<T>: یک اشاره‌گر رویِ پشته","T: رویِ هیپ","Box مالکِ آن است","سرِ scope، هیپ آزاد می‌شود"]}
```

### چرا اصلاً بخواهی چیزی رویِ هیپ باشد

اگر هر مقداری همین الان رویِ پشته جا می‌شود و پشته سریع‌تر است — همان چیزی که [۱.۲.۱](../../../phase1-fundamentals/02-ownership-and-memory/01-stack-and-heap/README.fa.md) گفت — چرا اصلاً به این لایه‌ی اضافه نیاز داری؟ دو دلیلِ واقعی هست.

**اول: مقداری که جابه‌جا کردنش رویِ پشته گران است.** یک مقدارِ بزرگ را جابه‌جا کردن یعنی هر بایتش کپی شود. یک `Box` را جابه‌جا کردن یعنی فقط همان یک اشاره‌گر کپی شود — همیشه، فارغ از اینکه پشتش چقدر بزرگ باشد:

```rust
let big = Box::new(BigBuffer { data: [0; 100_000] });
println!("heap address before move: {big:p}");

let moved = big; // فقط اشاره‌گر جابه‌جا شد — نه ۱۰۰٬۰۰۰ بایت
println!("heap address after move:  {moved:p}");
```

```text
heap address before move: 0x1e9255c8f40
heap address after move:  0x1e9255c8f40
```

نشانیِ هیپ پیش و پس از انتقال یکی است — چون هیچ بایتی از `data` جابه‌جا نشد؛ فقط یک اشاره‌گرِ هشت‌بایتی از یک متغیر به متغیرِ دیگر رفت. خودِ عدد هر بار که اجرا کنی عوض می‌شود — سیستم‌عامل هر بار برنامه را جایِ تازه‌ای می‌گذارد، دقیقاً همان چیزی که [۱.۲.۱](../../../phase1-fundamentals/02-ownership-and-memory/01-stack-and-heap/README.fa.md) نشانت داد — ولی برابر‌بودنِ «پیش» و «پس» سرِ جایش می‌ماند. عددهایِ کاملش را در «دست‌به‌کد» می‌بینی.

**دوم، و مهم‌تر برایِ ادامه‌ی این درس: مقداری که اندازه‌اش اصلاً هنگامِ کامپایل معلوم نیست.** «بزرگ» با «نامعلوم» یک چیز نیست. یک `[u8; 100_000]` بزرگ است ولی اندازه‌اش کاملاً معلوم و ثابت است — کامپایلر می‌داند رویِ پشته چقدر فریم بردارد. ولی بعضی نوع‌ها اصلاً چنین عددی ندارند — [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) یکی‌شان را به‌ات نشان داد: `str` خامِ بدونِ `&`. برایِ این‌ها، رویِ پشته گذاشتنِ مستقیم اصلاً یک گزینه نیست — چند بند پایین‌تر می‌بینی چرا، و `Box` دقیقاً همین‌جا وارد می‌شود.

### اندازه‌ی `Box`: همیشه یک کلمه، برایِ هر `T`ِ اندازه‌دار

این ادعایِ مرکزیِ امروز است: برایِ هر `T`ی که **اندازه‌دار (Sized)** باشد — یعنی کامپایلر هنگامِ کامپایل دقیقاً می‌داند چند بایت است، که تقریباً هر نوعی که تا امروز دیده‌ای همین‌طور بوده — `Box<T>` همیشه دقیقاً یک کلمه‌ی ماشین است. یک اشاره‌گر. همین. فارغ از اینکه `T` چقدر کوچک یا بزرگ باشد.

```rust
struct Tiny;
struct Small {
    id: u32,
}
struct Large {
    buffer: [u8; 4096],
}
```

```rust
println!("size_of::<Tiny>()   = {}", size_of::<Tiny>());
println!("size_of::<Small>()  = {}", size_of::<Small>());
println!("size_of::<Large>()  = {}", size_of::<Large>());
println!("size_of::<Box<Tiny>>()  = {}", size_of::<Box<Tiny>>());
println!("size_of::<Box<Small>>() = {}", size_of::<Box<Small>>());
println!("size_of::<Box<Large>>() = {}", size_of::<Box<Large>>());
```

```text
size_of::<Tiny>()   = 0
size_of::<Small>()  = 4
size_of::<Large>()  = 4096
size_of::<Box<Tiny>>()  = 8
size_of::<Box<Small>>() = 8
size_of::<Box<Large>>() = 8
```

`Tiny` صفر بایت است. `Large` چهار هزار و نود و شش بایت است. و `Box` دورِ هرکدام دقیقاً همان هشت بایت است — همان چیزی که `&T` هم می‌بود. حتی جعبه‌کردنِ یک جعبه‌ی دیگر همین قاعده را می‌گیرد: `size_of::<Box<Box<i32>>>()` هم هشت است، چون خودِ `Box<i32>` یک نوعِ اندازه‌دار است — درست مثلِ هر `T`ِ دیگری.

این همان چیزی است که مسئله‌ی «مقدارِ بزرگ» بالا را حل می‌کند: جابه‌جا کردنِ `Box<Large>` همیشه هشت بایت است، چه `Large` چهار کیلوبایت باشد چه چهل مگابایت.

```senpai-visual
{"kind":"concept","labels":["T کوچک: چند بایت","T بزرگ: هزاران بایت","Box<T> کوچک: ۸ بایت","Box<T> بزرگ: ۸ بایت"]}
```

### بهینه‌سازیِ جای‌خالی، این‌بار با توضیحِ کامل

حالا برگرد به قرضِ [۱.۵.۳](../../../phase1-fundamentals/05-your-own-types/03-enums-as-data/README.fa.md) و [۱.۶.۱](../../../phase1-fundamentals/06-absence-and-failure/01-option-and-null-safety/README.fa.md). هر دو همین عدد را نشانت دادند:

```rust
println!("size_of::<Box<i32>>()      = {}", size_of::<Box<i32>>());
println!("size_of::<Option<Box<i32>>>() = {}", size_of::<Option<Box<i32>>>());
```

```text
size_of::<Box<i32>>()      = 8
size_of::<Option<Box<i32>>>() = 8
```

و هر دو فقط گفتند دلیلش این است که یک `Box` معتبر هرگز همه-بیت-صفر نیست — یکی به زبانِ «هرگز اشاره‌گرِ تهی نیست»، دیگری به زبانِ «هرگز همه-بیت-صفر نیست»، هردو یک واقعیت. حالا کاملش را داری. `Box::new` همیشه یک تخصیصِ واقعی می‌گیرد و یک اشاره‌گرِ واقعی برمی‌گرداند — هیچ راهِ عمومی‌ای در Rustِ ایمن وجود ندارد که یک `Box<T>` بسازی و درونش صفر باشد. یعنی از هر ۲⁶⁴ الگویِ بیتیِ ممکنِ یک اشاره‌گرِ هشت‌بایتی، دقیقاً یکی — همه‌بیت‌صفر — هرگز پیش نمی‌آید. کامپایلر همین الگویِ ناممکن را برایِ `None` قرض می‌گیرد، پس `Option<Box<T>>` هیچ بایتِ اضافه‌ای نمی‌گیرد. همین است **بهینه‌سازیِ جای‌خالی (niche optimisation)** که [۱.۵.۳](../../../phase1-fundamentals/05-your-own-types/03-enums-as-data/README.fa.md) اسمش را گذاشت.

مقایسه‌اش کن با `Option<i32>`: هر یک از آن ۲³² الگویِ بیتیِ یک `i32` یک عددِ واقعی است — هیچ الگویِ بلااستفاده‌ای نمانده که `None` قرضش بگیرد، پس `Option<i32>` باید یک بایتِ برچسبِ جدا بخرد و به هشت بایت گرد شود. تفاوت رویِ خودِ `T` نیست؛ رویِ این است که آیا `T` — اینجا `Box<T>` — یک الگویِ بیتیِ ناممکن دارد که بشود مجانی به `None` داد یا نه.

### وقتی `T` اندازه ندارد: اشاره‌گرِ چاق

تا این‌جا هر `T`ی که دیدی **اندازه‌دار (Sized)** بود. ولی [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) به‌ات یک **نوعِ بی‌اندازه (unsized type)** هم نشان داد: `str` خام، بدونِ `&`. اندازه‌اش هنگامِ کامپایل معلوم نیست — می‌تواند سه بایت باشد یا سه میلیون — پس نمی‌توانی رویِ پشته جایش بدهی، در متغیر بگذاری، یا به تابعی بدهی‌اش با مقدار. [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) هم یک نمونه‌ی دیگر داد: `dyn Trait`، وقتی نوعِ ملموسِ زیرش پاک شده و کامپایلر دیگر نمی‌داند چند بایت است.

اینجا «همیشه یک کلمه» دیگر ممکن نیست — یک کلمه فقط جا برایِ یک نشانی دارد، و برایِ یک نوعِ بی‌اندازه یک نشانیِ خام کافی نیست. `Box<T>` وقتی `T` بی‌اندازه است، به یک **اشاره‌گرِ چاق (fat pointer)** تبدیل می‌شود — دو کلمه به‌جایِ یک کلمه — دقیقاً همان چیزی که [۱.۳.۴](../../../phase1-fundamentals/03-borrowing-and-references/04-slices/README.fa.md) رویِ برش‌ها و [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) رویِ اشیایِ صفتی به‌ات نشان دادند: یک اشاره‌گر به دیتایِ واقعی، به‌اضافه‌ی هرچه برایِ دانستنِ «چقدر» یا «کدام پیاده‌سازی» لازم است.

```rust
let owned_str: Box<str> = "senpai".into();
println!("size_of::<Box<str>>() = {}", size_of::<Box<str>>());
println!("size_of::<Box<dyn Playable>>() = {}", size_of::<Box<dyn Playable>>());
```

```text
size_of::<Box<str>>() = 16
size_of::<Box<dyn Playable>>() = 16
```

دو کلمه — شانزده بایت — و **همچنان ثابت**، بدونِ توجه به اینکه رشته چند حرف است یا پشتِ `dyn Playable` کدام نوعِ ملموس نشسته. عددهایِ کاملش را در «دست‌به‌کد» می‌بینی.

```senpai-visual
{"kind":"concept","labels":["&str: اشاره‌گر + طول","Box<str>: اشاره‌گر + طول","Box<dyn Trait>: اشاره‌گر + vtable","همیشه دو کلمه، نه بیشتر"]}
```

### حلِ آن‌چه ۱.۴.۱ نشانت داد: `Box<str>`

[۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) دقیقاً همین جمله را نوشت: «`Box<str>` — مالکی بدونِ ظرفیت، دو کلمه به‌جایِ سه.» حالا می‌توانی خودت اثباتش کنی:

```rust
println!("size_of::<String>()   = {}", size_of::<String>());
println!("size_of::<Box<str>>() = {}", size_of::<Box<str>>());
println!("size_of::<&str>()     = {}", size_of::<&str>());
```

```text
size_of::<String>()   = 24
size_of::<Box<str>>() = 16
size_of::<&str>()     = 16
```

`String` سه کلمه است چون رشد می‌کند — کلمه‌ی سومش، ظرفیت، همان چیزی است که رزروِ اضافه را ردیابی می‌کند. `Box<str>` هرگز رشد نمی‌کند: اندازه‌اش همانی است که هنگامِ ساختنش تخصیص گرفته، برایِ همیشه. پس همان دو کلمه‌ی `&str` را دارد — یک اشاره‌گر، یک طول — با یک فرق: `Box<str>` **مالکِ** آن بایت‌هاست، `&str` فقط **نگاهشان می‌کند**. همان تمایزِ مالک/نما که کلِ [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) رویش بنا شده بود، اینجا هم دقیقاً همان‌جوری کار می‌کند — فقط این‌بار مالک رویِ هیپ نشسته، نه یک `struct` سه‌کلمه‌ای.

### حلِ آن‌چه ۲.۳.۷ و ۲.۵.۲ نشانت دادند: `Box<dyn Trait>`

[۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) یک `Box<dyn Summarize>` دورِ `AnimeSeries` و یک `Box<dyn Summarize>` دیگر دورِ `MangaVolume` گذاشت — دو نوعِ ملموسِ کاملاً متفاوت، با اندازه‌هایِ متفاوت — تا هردو تویِ یک `Vec` جا شوند. [۲.۵.۲](../../05-error-handling/02-error-source-chains/README.fa.md) همان کار را رویِ `Box<dyn Error>` کرد تا `ConfigError` و `ParseIntError` را پشتِ یک نوعِ برگشتیِ واحد جمع کند. هردو گفتند داستانِ کاملِ `Box` را مالِ همین درس دانستند؛ حالا داستان همین است:

```rust
struct Song {
    title: String,
}
struct Podcast {
    title: String,
    duration_minutes: u32,
}
```

```rust
println!("size_of::<Song>()    = {}", size_of::<Song>());
println!("size_of::<Podcast>() = {}", size_of::<Podcast>());
println!("size_of::<Box<dyn Playable>>() = {}", size_of::<Box<dyn Playable>>());
```

```text
size_of::<Song>()    = 24
size_of::<Podcast>() = 32
size_of::<Box<dyn Playable>>() = 16
```

`Song` و `Podcast` اندازه‌هایِ متفاوتی دارند — بیست‌وچهار در برابرِ سی‌ودو بایت. ولی `Box<dyn Playable>` برایِ هردو دقیقاً شانزده بایت است. کلمه‌ی اول همان اشاره‌گرِ به دیتایِ واقعی است — به آن `Song` یا آن `Podcast`ِ رویِ هیپ. کلمه‌ی دوم، دقیقاً همان‌طور که [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) توضیح داد، اشاره‌گر به **جدولِ متدهایِ مجازی (vtable)** آن نوعِ ملموس است — نه دیتایِ واقعی، فقط آدرسِ جایی که پیاده‌سازیِ درستِ `play` را پیدا کند. `Box` هیچ کارِ تازه‌ای اینجا نمی‌کند؛ فقط همان اشاره‌گرِ چاقِ دو‌کلمه‌ایِ `&dyn Playable` را رویِ هیپ می‌گذارد و مالکش می‌شود، همان‌طور که برایِ هر `T`ِ اندازه‌دار هم می‌کرد.

این دقیقاً همان قولی است که [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) داد: «`Box<dyn Summarize>` برایِ هردو یک اندازه‌ی ثابت است.» حالا می‌دانی چرا — و می‌دانی آن اندازه دقیقاً از کجا می‌آید.

### یک جمله جلوتر: بازگشتی، و مالکیتِ اشتراکی

دو دری که این درس عمداً باز نمی‌کند: وقتی خودِ `T` یک `Box<T>` را در دلِ خودش نگه می‌دارد — یک نوعِ بازگشتی — کارش، و همچنین شیءهایِ صفتیِ جعبه‌ای، مالِ [۲.۶.۲](../02-recursive-types-and-trait-objects/README.fa.md) است؛ و وقتی یک مالکِ تنها اصلاً کافی نیست چون چند بخشِ برنامه واقعاً باید یک مقدار را با هم نگه دارند، آن‌جاست که `Rc` و `Arc` وارد می‌شوند — مالِ [۲.۶.۳](../03-rc-and-arc/README.fa.md).

## خطاهایی که خواهی دید

### `E0308` — یک `Box<&str>` جایی که `Box<str>` خواسته شده

```text
error[E0308]: mismatched types
 --> phase2-intermediate\06-smart-pointers\01-box-and-heap-allocation\examples\05-box-str-from-literal-broken.rs:6:26
  |
6 |     let text: Box<str> = Box::new("senpai");
  |               --------   ^^^^^^^^^^^^^^^^^^ expected `Box<str>`, found `Box<&str>`
  |               |
  |               expected due to this
  |
  = note: expected struct `Box<_>`
             found struct `Box<&_>`

For more information about this error, try `rustc --explain E0308`.
```

**کامپایلر به چه اعتراض دارد:** `"senpai"` یک لیترال است، نوعش `&str` — نه `str`. `Box::new` یک مقدارِ **اندازه‌دار** می‌گیرد و همان مقدار را رویِ هیپ می‌گذارد؛ چیزی که این‌جا رویِ هیپ رفته یک `&str` بوده، پس نتیجه `Box<&str>` است — یک اشاره‌گرِ ساده به یک اشاره‌گرِ چاقِ دیگر، نه یک `Box<str>`.

**راه‌حل:** `str` را نمی‌شود با `Box::new` جعبه کرد، چون `Box::new` اصلاً یک مقدارِ `str`ِ خالی در دست ندارد که رویِ هیپ بگذارد — دقیقاً همان مشکلِ «نوعِ بی‌اندازه» که [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) نشانت داد. راهِ درست یک تبدیل است:

```rust
let text: Box<str> = "senpai".into();
```

**چرا این راه‌حل است:** `.into()` اینجا از یک `impl From<&str> for Box<str>` استفاده می‌کند که کتابخانه‌ی استاندارد نوشته — این تبدیل خودش، پشتِ صحنه، هم تخصیص می‌گیرد و هم بایت‌ها را کپی می‌کند، و نتیجه‌اش یک `Box<str>` واقعی است، نه یک `Box` دورِ یک اشاره‌گرِ دیگر. `Box::new` برایِ جعبه‌کردنِ یک مقدارِ از پیش موجود و اندازه‌دار است؛ ساختنِ یک `Box` دورِ چیزی که خودش هیچ‌وقت به‌تنهایی رویِ پشته جا نمی‌شد، همیشه از راهِ یک تبدیل می‌گذرد.

### `E0507` — جابه‌جایی از پشتِ یک ارجاعِ اشتراکی

```text
error[E0507]: cannot move out of `**boxed` which is behind a shared reference
  --> phase2-intermediate\06-smart-pointers\01-box-and-heap-allocation\examples\06-move-out-through-shared-ref-broken.rs:10:5
   |
10 |     **boxed
   |     ^^^^^^^ move occurs because `**boxed` has type `Profile`, which does not implement the `Copy` trait
   |
note: if `Profile` implemented `Clone`, you could clone the value
  --> phase2-intermediate\06-smart-pointers\01-box-and-heap-allocation\examples\06-move-out-through-shared-ref-broken.rs:5:1
   |
 5 | struct Profile {
   | ^^^^^^^^^^^^^^ consider implementing `Clone` for this type
...
10 |     **boxed
   |     ------- you could clone this value

For more information about this error, try `rustc --explain E0507`.
```

**کامپایلر به چه اعتراض دارد:** `boxed` نوعش `&Box<Profile>` است — یک ارجاعِ اشتراکی به یک `Box`. `**boxed` دو بار بازش می‌کند: یک‌بار تا به خودِ `Box` برسد، یک‌بار دیگر تا به `Profile`ِ رویِ هیپ برسد. تابع می‌خواهد آن `Profile` را **با مقدار** برگرداند — یعنی از جایش بیرونش بکشد — ولی چیزی که در دست دارد فقط یک قرض است، نه مالکیت.

**راه‌حل:** یکی از این دو — یا امضا را عوض کن تا واقعاً مالکیت بگیرد:

```rust
fn take_it(boxed: Box<Profile>) -> Profile {
    *boxed
}
```

یا اگر واقعاً فقط قرض داری، یک ارجاع برگردان، نه یک مقدار.

**چرا این راه‌حل است:** `Box<T>` هیچ استثنایی رویِ قاعده‌ی مالکیت نمی‌سازد — دقیقاً همان چیزی که [۱.۲.۴](../../../phase1-fundamentals/02-ownership-and-memory/04-ownership-across-functions/README.fa.md) رویِ مقدارهایِ معمولی به‌ات یاد داد، اینجا هم عیناً برقرار است. وقتی `take_it` واقعاً `boxed: Box<Profile>` می‌گیرد (نه `&Box<Profile>`)، تابع مالکِ آن `Box` می‌شود، و `*boxed` — این‌بار بدونِ هیچ ارجاعی جلویش — مجاز است، چون Rust به `Box` اجازه می‌دهد وقتی خودش مالکیتش را داری، مقدارِ داخلش را از جا بیرون بکشی. نکته این نیست که `Box` قاعده را دور می‌زند؛ نکته این است که مالکیت را واقعاً داشته باشی، نه فقط قرضش را.

### بساز

یک `struct` طراحی کن که در دنیایِ واقعی معنا داشته باشد و دست‌کم یک فیلدش به‌وضوح از بقیه بزرگ‌تر باشد — مثلاً یک بافرِ متن یا یک آرایه‌ی ثابت‌اندازه. اندازه‌اش را با `size_of` بسنج. بعد یک نسخه‌ی دوم بساز که همان فیلدِ بزرگ را `Box` کرده، و اندازه‌ی آن را هم بسنج.

بعد یک پاراگراف بنویس: این تفاوت کِی در کدِ واقعی مهم می‌شود؟ (سرنخ: به [۱.۵.۳](../../../phase1-fundamentals/05-your-own-types/03-enums-as-data/README.fa.md) فکر کن — همان‌جا که یک گونه‌ی خیلی بزرگ اندازه‌ی کلِ یک `enum` را بالا می‌کشید.)

### چالش (اختیاری)

**بخشِ یک.** یک `Vec<i32>` بساز، بعد با `.into_boxed_slice()` به یک `Box<[i32]>` تبدیلش کن. `size_of::<Vec<i32>>()` و `size_of::<Box<[i32]>>()` را کنارِ هم بگذار — این هم یک نوعِ بی‌اندازه است (`[i32]`، بدونِ طولِ مشخص در نوعش)، پس همان قاعده‌ی اشاره‌گرِ چاق باید برقرار باشد. یک `Box<[i32]>` با سه عنصر و یکی با پانصد عنصر بساز و اندازه‌شان را با هم مقایسه کن.

**بخشِ دو.** این تمرین به عقب برمی‌گردد، نه جلو. در [۱.۵.۳](../../../phase1-fundamentals/05-your-own-types/03-enums-as-data/README.fa.md) — بخشِ دوِ چالش — یک `enum Chain { End, Link(u32, Chain) }` نوشتی، به `E0072` خوردی، و درس گفت راه‌حلش را کامپایلر خودش نام می‌برد. برو همان کد را دوباره بساز (یا اگر آن‌جا حلش کردی، دوباره پیدایش کن)، `Box` را دورِ فیلدِ بازگشتی بگذار، و این‌بار — به‌جایِ فقط دیدنِ اینکه کامپایل می‌شود — با `size_of` بگو اندازه‌ی نهاییِ `Chain` دقیقاً چند بایت شد و چرا همان عدد است، نه عددِ دیگری.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| اشاره‌گرِ هوشمند (smart pointer) | ساختاری که مثلِ اشاره‌گر عمل می‌کند و مالکِ چیزی هم هست که به آن اشاره می‌کند | `Box<T>`، و بعداً `Rc`/`Arc` |
| `Box<T>` | ساده‌ترین اشاره‌گرِ هوشمند: یک مقدار رویِ هیپ، با یک مالکِ یکتا | هر جا مقدار بزرگ باشد یا اندازه‌اش هنگامِ کامپایل معلوم نباشد |
| اندازه‌دار (Sized) | نوعی که کامپایلر هنگامِ کامپایل دقیقاً می‌داند چند بایت است | تقریباً هر `T`ی که تا امروز دیده‌ای |
| نوعِ بی‌اندازه (unsized type) | نوعی بدونِ چنین عددی — `str`، `dyn Trait` | چرا `Box<T>` گاهی اشاره‌گرِ چاق می‌شود |
| اشاره‌گرِ چاق (fat pointer) | اشاره‌گرِ دوکلمه‌ای: دیتا + طول یا vtable | `Box<str>`، `Box<dyn Trait>` |
| بهینه‌سازیِ جای‌خالی | استفاده از یک الگویِ بیتیِ ناممکن به‌جایِ بایتِ اضافه برایِ `None` | `Option<Box<T>>` هم‌اندازه‌ی `Box<T>` است |

### الان می‌دانی

- `Box<T>` یک مقدار را رویِ هیپ می‌گذارد، مالکش می‌شود، و همان قاعده‌ی همیشگیِ RAII را دنبال می‌کند — سرِ `scope`، آزاد می‌شود.
- دو دلیلِ واقعی برایِ خواستنِ هیپ هست: مقداری که جابه‌جایی‌اش رویِ پشته گران است، و مقداری که اندازه‌اش اصلاً هنگامِ کامپایل معلوم نیست.
- برایِ هر `T`ِ اندازه‌دار، `Box<T>` همیشه دقیقاً یک کلمه است — فارغ از اینکه `T` چقدر کوچک یا بزرگ باشد.
- `Option<Box<T>>` هیچ بایتِ اضافه‌ای نمی‌گیرد، چون یک `Box` معتبر هرگز همه‌بیت‌صفر نیست و کامپایلر همان الگو را برایِ `None` قرض می‌گیرد.
- وقتی `T` بی‌اندازه است (`str`، `dyn Trait`)، `Box<T>` یک اشاره‌گرِ چاقِ دوکلمه‌ای می‌شود — بازهم ثابت، فقط این‌بار دو کلمه به‌جایِ یک کلمه.
- `Box<str>` دو کلمه است چون کلمه‌ی سومِ `String` — ظرفیت — را ندارد؛ `Box<dyn Trait>` هم‌اندازه است فارغ از اینکه پشتش کدام نوعِ ملموس نشسته.

### بعداً کامل‌تر می‌بینی

- **نوع‌هایِ بازگشتی، وقتی `T` خودش یک `Box<T>` را در دلِ خودش نگه می‌دارد** — [۲.۶.۲ — نوع‌های بازگشتی و شیء‌های صفتِ جعبه‌ای](../02-recursive-types-and-trait-objects/README.fa.md)
- **وقتی یک مالکِ تنها کافی نیست** — [۲.۶.۳ — `Rc` و `Arc`](../03-rc-and-arc/README.fa.md)
- **تغییردادنِ چیزی که فقط یک ارجاعِ اشتراکی از آن داری** — [۲.۶.۵ — `RefCell` و تغییرپذیریِ درونی](../05-refcell-and-interior-mutability/README.fa.md)

### می‌توانی توضیح بدهی؟

- `Box<T>` چیست، و کِی و کجا حافظه‌اش آزاد می‌شود؟
- دو دلیلِ واقعی برایِ خواستنِ رویِ هیپ بودن را نام ببر.
- چرا `size_of::<Box<T>>()` هیچ‌وقت به اندازه یا محتوایِ `T` بستگی ندارد؟ برایِ `T`ِ اندازه‌دار و `T`ِ بی‌اندازه هرکدام یک جمله بگو.
- چرا `Option<Box<T>>` رایگان است ولی `Option<i32>` نه؟
- چرا `Box<str>` دو کلمه است و `String` سه کلمه؟
- چرا `Box<dyn Trait>` برایِ هر نوعِ ملموسی که پشتش باشد یک اندازه دارد؟
