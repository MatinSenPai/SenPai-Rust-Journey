# ۲.۶.۲ — نوع‌های بازگشتی و شیء‌های صفتِ جعبه‌ای

## در یک نگاه

بعد از این درس می‌توانی:

- توضیح بدهی چرا یک نوعِ بازگشتیِ ساده‌لوحانه — یک `enum` که یکی از گونه‌هایش خودِ همان `enum` را مستقیم و با مقدار نگه می‌دارد — کامپایل نمی‌شود، و خطای `E0072` را دقیقاً همان‌طور بخوانی که کامپایلر معنی‌اش می‌کند، نه با حفظ‌کردنِ یک جمله‌ی کلی.
- یک ساختارِ بازگشتیِ واقعاً به‌دردبخور — یک درختِ عبارتِ ریاضی — با `Box` بسازی، و بگویی چرا جعبه‌کردنِ فقط یکی از دو فیلدِ بازگشتی کافی نیست.
- الگویِ `Vec<Box<dyn Trait>>` را به‌عنوانِ همان ترفندِ «اندازه‌ی ثابت، محتوایِ نامعلوم» تشخیص بدهی — این‌بار برایِ نوع‌هایِ متفاوتِ پشتِ یک صفتِ مشترک، نه برایِ بازگشت به خودِ نوع.

## چرا اهمیت دارد

درخت‌ها، لیست‌های پیوندی، درخت‌های نحو (ASTها که یک پارسر می‌سازد)، حتی یک ساختارِ پوشه — همه‌شان یک شکلِ مشترک دارند: «این چیز، یا خودش یک برگ است، یا از چند تا نسخه‌ی کوچک‌ترِ همان چیز ساخته شده.» تویِ پایتون این را بدونِ فکر می‌نویسی:

```python
class Node:
    def __init__(self, value, nxt=None):
        self.value = value
        self.next = nxt
```

`self.next` می‌تواند یک `Node` دیگر باشد، آن یکی هم یک `Node` دیگر، تا هر عمقی که بخواهی — و پایتون هیچ‌وقت شاکی نمی‌شود. دلیلش این نیست که پایتون باهوش‌تر است؛ دلیلش این است که هر متغیرِ پایتون، همیشه و بدونِ استثنا، فقط یک اشاره‌گر به یک شیء است — یک کلمه‌ی حافظه، فارغ از اینکه آن شیء چقدر بزرگ باشد. مفسر هیچ‌وقت مجبور نیست از قبل بداند «یک `Node` دقیقاً چند بایت جا می‌گیرد»، چون همیشه همان یک اندازه است: اندازه‌ی یک اشاره‌گر.

Rust این معامله را قبول نمی‌کند. یک مقدار، پیش‌فرض، دقیقاً همان بایت‌هایش را — نه یک اشاره‌گر به بایت‌هایش — همان‌جایی می‌گذارد که نگه‌داشته می‌شود: رویِ استک، یا داخلِ یک ساختارِ دیگر. همین یک انتخاب است که یک `i32` را تویِ یک `Vec<i32>` بدونِ هیچ لایه‌ی غیرمستقیمِ اضافه کنار هم می‌چیند، و همان چیزی است که باعث می‌شود Rust معمولاً بدونِ هزینه‌ی پنهان اجرا شود. اما همین انتخاب یک بها هم دارد: کامپایلر، برایِ هر نوعی که می‌نویسی، باید بتواند یک عددِ ثابت و نهایی بدهد — «این نوع دقیقاً همین‌قدر بایت است» — پیش از آنکه برنامه اصلاً اجرا شود. و امروز می‌بینی دقیقاً کجا این الزام به دیوار می‌خورد.

[۲.۶.۱](../01-box-and-heap-allocation/README.fa.md) یک حقیقتِ مرکزی به‌ات داد — `Box<T>`، فارغ از اینکه `T` چه باشد، همیشه دقیقاً پهنایِ یک اشاره‌گر است — و با همین حقیقت، داستانِ `Box<dyn Trait>` را کامل بست. فقط یک درِ بسته باقی گذاشت: نوعی که خودش را نگه می‌دارد. امروز همان یکی را باز می‌کنی، با همان یک حقیقت که تمامِ کار را انجام می‌دهد، و بعد داستانِ ازپیش‌حل‌شده‌ی شیءِ صفتیِ جعبه‌ای را رویِ یک موردِ واقعی و ملموس به کار می‌بندی — مجموعه‌ای از چند شکلِ متفاوت، پشتِ یک واسط. این درس، دومی از پنج درسِ ماژولِ اشاره‌گرهایِ هوشمند است: ۲.۶.۱ ابزار را ساخت، امروز اولین کاربردِ واقعی‌اش را می‌بینی.

## مفهوم

### نوعی که ادعا می‌کند خودش را در خودش نگه می‌دارد

یک عبارتِ ریاضیِ کوچک را در نظر بگیر: یا یک عدد است، یا جمعِ دو عبارتِ کوچک‌تر، یا حاصل‌ضربِ دو عبارتِ کوچک‌تر — دقیقاً همان شکلِ «برگ، یا چند نسخه‌ی کوچک‌ترِ خودش» که بالا دیدی. ترجمه‌ی مستقیمِ این جمله به یک `enum` همین است:

```rust
enum Expr {
    Num(f64),
    Add(Expr, Expr),
    Mul(Expr, Expr),
}
```

این را کامپایل کن، این خطا را می‌گیری:

```text
error[E0072]: recursive type `Expr` has infinite size
  --> phase2-intermediate\06-smart-pointers\02-recursive-types-and-trait-objects\examples\01-naive-expr-broken.rs:8:1
   |
 8 | enum Expr {
   | ^^^^^^^^^
 9 |     Num(f64),
10 |     Add(Expr, Expr),
   |         ---- recursive without indirection
   |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
   |
10 |     Add(Box<Expr>, Expr),
   |         ++++    +

For more information about this error, try `rustc --explain E0072`.
```

چرا؟ برایِ اینکه `Expr` را رویِ استک جا بدهد، کامپایلر باید بداند بزرگ‌ترین گونه‌اش دقیقاً چند بایت است. گونه‌ی `Add` خودش دو تا `Expr` کامل را با مقدار نگه می‌دارد — نه اشاره‌گر به آن‌ها، خودِ آن‌ها. پس برایِ اندازه‌ی `Add`، اول باید اندازه‌ی `Expr` را بدانی؛ همان چیزی که داری محاسبه‌اش می‌کنی. این یک تابعی نیست که یک روزی ته بکشد و جواب بدهد — یک تعریفِ دایره‌ای است که هیچ‌وقت به یک عددِ نهایی نمی‌رسد. برایِ همین کامپایلر می‌گوید «اندازه‌ی بی‌نهایت»، نه «اندازه‌ی نامعلوم»: این دو خیلی متفاوت‌اند، و بعداً همین درس فرقشان را می‌بینی.

### `Box` چرخه را می‌شکند

راه‌حل دقیقاً همان چیزی است که [۲.۶.۱](../01-box-and-heap-allocation/README.fa.md) یادت داد: فیلدِ بازگشتی را پشتِ یک `Box` بگذار.

```rust
enum Expr {
    Num(f64),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}
```

همین یک تغییر کافی است، چون حالا گونه‌ی `Add` دیگر دو تا `Expr` کامل نگه نمی‌دارد — دو تا `Box<Expr>` نگه می‌دارد، و یک `Box<Expr>`، فارغ از اینکه درونش چقدر عمیق باشد، *همیشه* دقیقاً پهنایِ یک اشاره‌گر است (۸ بایت رویِ یک ماشینِ ۶۴بیتی). حساب دیگر دایره‌ای نیست: اندازه‌ی `Add` = اندازه‌یِ یک `Box` + اندازه‌یِ یک `Box`، و این دو عدد را از قبل می‌دانی، بدونِ اینکه لازم باشد اول اندازه‌ی `Expr` را بدانی. بازگشتِ واقعی جایش را عوض کرده — از تعریفِ نوع (که باید سرِ کامپایل، محدود باشد) رفته توی هیپ (که سرِ اجرا، می‌تواند هر عمقی داشته باشد، به بهایِ یک تخصیصِ حافظه به‌ازایِ هر لایه).

حالا یک عبارتِ واقعی بساز — `(2 + 3) * 4` — و ارزیابی‌اش کن:

```rust
fn eval(expr: &Expr) -> f64 {
    match expr {
        Expr::Num(value) => *value,
        Expr::Add(left, right) => eval(left) + eval(right),
        Expr::Mul(left, right) => eval(left) * eval(right),
    }
}
```

نکته‌یِ ظریف: `expr` یک `&Expr` است، پس تویِ بازوهایِ `match`، `left` و `right` از نوعِ `&Box<Expr>` درمی‌آیند، نه `Box<Expr>` — دستِ خودت نمی‌شکند، خودِ Rust این را برایت مرتب می‌کند. و صدا زدنِ `eval(left)` هم بدونِ هیچ نشان‌زداییِ دستی کار می‌کند: `Box<Expr>` صفتِ `Deref` را پیاده کرده، پس یک `&Box<Expr>` دقیقاً همان‌جایی که یک `&Expr` انتظار می‌رود، خودش را جا می‌زند — همان تبدیلِ ضمنیِ ارجاع که [۲.۶.۱](../01-box-and-heap-allocation/README.fa.md) معرفی‌اش کرد.

```rust
// (2 + 3) * 4
let tree = Expr::Mul(
    Box::new(Expr::Add(
        Box::new(Expr::Num(2.0)),
        Box::new(Expr::Num(3.0)),
    )),
    Box::new(Expr::Num(4.0)),
);
println!("(2 + 3) * 4 = {}", eval(&tree));
```

```text
(2 + 3) * 4 = 20
```

### اثبات: اندازه هیچ‌وقت عوض نمی‌شود

حرف را با عدد ثابت کن، نه فقط با استدلال. یک `Expr` تک‌عضوی بساز، بعد یک زنجیره‌یِ ۱۰۰۰-لایه‌ای، و اندازه‌یِ خودِ هرکدام را — نه محتوایِ زیرِ اشاره‌گرهایش، خودِ مقداری که رویِ استک می‌نشیند — با هم مقایسه کن:

```rust
let shallow = Expr::Num(1.0);

let mut deep = Expr::Num(0.0);
let mut depth = 1;
for _ in 0..1_000 {
    deep = Expr::Add(Box::new(deep), Box::new(Expr::Num(1.0)));
    depth += 1;
}
```

```rust
println!(
    "size_of::<Expr>()     = {} bytes",
    std::mem::size_of::<Expr>()
);
println!(
    "size_of_val(&shallow) = {} bytes",
    std::mem::size_of_val(&shallow)
);
println!(
    "size_of_val(&deep)    = {} bytes",
    std::mem::size_of_val(&deep)
);
println!("deep tree depth       = {depth}");
println!("deep tree evaluates to = {}", eval(&deep));
```

```text
size_of::<Expr>()     = 24 bytes
size_of_val(&shallow) = 24 bytes
size_of_val(&deep)    = 24 bytes
deep tree depth       = 1001
deep tree evaluates to = 1000
```

`shallow` و ریشه‌یِ `deep` دقیقاً یک اندازه‌اند، با اینکه یکی زیرِ خودش هیچ ندارد و آن یکی زیرِ خودش ۱۰۰۰ لایه‌یِ دیگر دارد. این دقیقاً همان چیزی است که «اندازه‌ی ثابت» یعنی: خودِ `Expr`، هرجا که نشسته باشد، همیشه همان تعداد بایت است؛ عمقِ واقعیِ درخت یک خاصیتِ زمانِ اجراست، پشتِ اشاره‌گرها، نه یک خاصیتِ خودِ نوع.

یک نکته‌ی جالب: عدد `24` دقیقاً برابرِ اندازه‌ی دو تا `Box` است (`8 + 8`) به‌علاوه‌ی ۸ بایتِ دیگر برایِ یک برچسبِ صریح که می‌گوید کدام‌یک از سه گونه است — `Num`، `Add` یا `Mul`. [۲.۶.۱](../01-box-and-heap-allocation/README.fa.md) و [۱.۶.۱](../../../phase1-fundamentals/06-absence-and-failure/01-option-and-null-safety/README.fa.md) حالتی را نشانت دادند که برچسب *رایگان* درمی‌آید: `Option<Box<T>>` هیچ بایتِ جداگانه‌ای لازم ندارد، چون یک `Box` هیچ‌وقت نمی‌تواند تهی باشد، پس کامپایلر همان یک الگویِ غیرممکن را به‌عنوانِ برچسبِ `None` قرض می‌گیرد. ولی آن ترفند فقط برایِ انتخاب بینِ دقیقاً دو چیز کار می‌کند — جا دادنِ یک انتخابِ *سه‌تایی* داخلِ الگوهایِ بیتیِ خالی، خواسته‌ی سخت‌تری است، و این‌جا کامپایلر یکی پیدا نمی‌کند؛ به‌جایش بابتِ یک برچسبِ صادقانه هزینه می‌دهد. `Expr` در هر دو حالت اندازه‌ی ثابت دارد — تضمینِ اندازه‌ی ثابت هیچ‌وقت به رایگان‌بودنِ برچسب وابسته نبود، فقط به این وابسته بود که `Box` همیشه یک اشاره‌گر پهناست.

### جعبه‌کردنِ نصفه‌ونیمه هنوز هم بی‌نهایت است

پیامِ کمکیِ کامپایلر را دوباره نگاه کن: فقط گفت گونه‌یِ اولِ `Add` را جعبه کن (`Box<Expr>, Expr`)، نه هر دو تا را. اگر دقیقاً همین پیشنهاد را کورکورانه اجرا کنی:

```rust
enum Expr {
    Num(f64),
    Add(Box<Expr>, Expr),
}
```

```text
error[E0072]: recursive type `Expr` has infinite size
  --> phase2-intermediate\06-smart-pointers\02-recursive-types-and-trait-objects\examples\04-half-boxed-broken.rs:9:1
   |
 9 | enum Expr {
   | ^^^^^^^^^
10 |     Num(f64),
11 |     Add(Box<Expr>, Expr),
   |                    ---- recursive without indirection
   |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
   |
11 |     Add(Box<Expr>, Box<Expr>),
   |                    ++++    +

For more information about this error, try `rustc --explain E0072`.
```

هنوز همان `E0072`، فقط این‌بار روی فیلدِ دوم. و کاملاً منطقی است: جعبه‌کردنِ فیلدِ اول، مسیرِ *آن* فیلد را از حلقه‌یِ بازگشتی بیرون آورد، ولی فیلدِ دوم — یک `Expr` خام — همچنان مستقیم و با مقدار درونِ `Add` نشسته. حساب هنوز همان‌قدر دایره‌ای است، فقط از یک راهِ دیگر: اندازه‌ی `Add` = اندازه‌یِ `Box<Expr>` + اندازه‌یِ `Expr`، و آن دومی هنوز خودِ چیزی است که داری محاسبه‌اش می‌کنی. **قاعده این نیست که «یک فیلد را جعبه کن تا اندازه کوچک‌تر شود»؛ قاعده این است که هر مسیرِ بازگشتی باید از یک جعبه رد شود، همه‌شان، نه فقط یکی‌شان.**

پیشنهادِ کامپایلر یک راهنماست، نه یک تضمینِ کاملِ رفع‌مشکل — همیشه بعد از اعمالش، دوباره کامپایل کن و ببین آیا خطای دیگری منتظر است یا نه. (و همین‌جا: پیام‌های کمکیِ کامپایلر `Rc` و `&` را هم به‌عنوانِ راهِ حل‌هایِ ممکن اسم بردند. `&` اینجا کار نمی‌کند چون یک ارجاع مالکِ چیزی که به آن اشاره می‌کند نیست — باید یک جایِ دیگر، برایِ تمامِ عمرِ آن ارجاع، زنده نگهش دارد، و یک درختِ خودساخته چنین جایِ دیگری ندارد. `Rc` هم یک جور دیگر جعبه‌کردن است — با این تفاوت که اجازه می‌دهد چند مالک داشته باشی — و موضوعِ [۲.۶.۳](../03-rc-and-arc/README.fa.md) است.)

### شیءِ صفتِ جعبه‌ای: همان ایده، جایِ دیگر

دقیقاً همین دیوار را در [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) دیدی، فقط از زاویه‌یِ دیگری: `dyn Shape` هم اندازه‌ی معلومی سرِ کامپایل ندارد — نه چون بازگشتی است، بلکه چون *نوعِ ملموسِ زیرش می‌تواند هر چیزی باشد*، و نوع‌های ملموسِ مختلف اندازه‌های مختلف دارند. این هم دقیقاً همان چیزی است که [۱.۴.۱](../../../phase1-fundamentals/04-text-and-strings/01-string-vs-str/README.fa.md) به‌اش می‌گفت **نوعِ بی‌اندازه (unsized type)** — همان دسته‌ای که `str` و `[T]` هم تویش‌اند. دو مشکلِ کاملاً متفاوت — «شاید بی‌نهایت عمیق باشد» در برابرِ «شاید هر نوعی زیرش باشد» — و هر دو با یک جواب حل می‌شوند، چون هر دو، از دیدِ کامپایلر، دقیقاً همان شکل‌اند: «من نمی‌توانم از قبل بگویم این چقدر جا می‌گیرد.» `Box` این را با «پس بگذار همیشه دقیقاً یک اشاره‌گر جا بگیرد» جواب می‌دهد — فارغ از اینکه دلیلِ نامعلوم‌بودنِ اندازه چه بوده.

این بار مسئله بازگشت نیست — یک `Circle` هیچ‌وقت خودش را در خودش نگه نمی‌دارد — مسئله این است که چند نوعِ ملموسِ متفاوت را می‌خواهی کنارِ هم، تویِ یک `Vec` واحد نگه داری:

```rust
trait Shape {
    fn area(&self) -> f64;
}

struct Circle {
    radius: f64,
}

impl Shape for Circle {
    fn area(&self) -> f64 {
        std::f64::consts::PI * self.radius * self.radius
    }
}
```

```rust
struct Rectangle {
    width: f64,
    height: f64,
}

impl Shape for Rectangle {
    fn area(&self) -> f64 {
        self.width * self.height
    }
}
```

```rust
let shapes: Vec<Box<dyn Shape>> = vec![
    Box::new(Circle { radius: 2.0 }),
    Box::new(Rectangle {
        width: 3.0,
        height: 4.0,
    }),
];

let total: f64 = shapes.iter().map(|shape| shape.area()).sum();
println!("total area = {total:.2}");
```

```text
total area = 24.57
```

`Circle` و `Rectangle` دو ساختارِ کاملاً متفاوت‌اند، با دو اندازه‌ی متفاوت. `Box<dyn Shape>` هردو را به یک نوعِ عنصرِ یکسان — یک اشاره‌گرِ چاق، همیشه دقیقاً هم‌اندازه — تبدیل می‌کند، دقیقاً همان‌طور که [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) با `Summarize` نشانت داد. اینجا چیزِ تازه‌ای درباره‌ی ارسالِ پویا یا vtable نمی‌گویم — آن داستان را [۲.۳.۷](../../03-traits-and-generics/07-static-vs-dynamic-dispatch/README.fa.md) کامل گفت. نکته‌ی امروز فقط این است: همان `Box`، همان دلیل — «اندازه‌ی نامعلوم را به یک اندازه‌ی ثابت تبدیل کن» — این‌بار برایِ نوع‌های متفاوت به‌جایِ عمقِ نامعلوم.

## خطاهایی که خواهی دید

### `E0072` — نوعِ بازگشتی، اندازه‌یِ بی‌نهایت دارد

```text
error[E0072]: recursive type `Expr` has infinite size
  --> phase2-intermediate\06-smart-pointers\02-recursive-types-and-trait-objects\examples\01-naive-expr-broken.rs:8:1
   |
 8 | enum Expr {
   | ^^^^^^^^^
 9 |     Num(f64),
10 |     Add(Expr, Expr),
   |         ---- recursive without indirection
   |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
   |
10 |     Add(Box<Expr>, Expr),
   |         ++++    +

For more information about this error, try `rustc --explain E0072`.
```

**کامپایلر به چه اعتراض دارد:** برایِ اینکه `Expr` را رویِ استک جا بدهد، باید بزرگ‌ترین گونه‌اش را با یک عددِ ثابت اندازه بگیرد. گونه‌ی `Add` دو تا `Expr` را با مقدار (نه با اشاره‌گر) نگه می‌دارد؛ برایِ اندازه‌گیریِ هرکدام، دوباره به اندازه‌ی `Expr` نیاز داری — همان چیزی که هنوز محاسبه‌اش نکرده‌ای. این حساب هیچ عددِ نهایی‌ای ندارد.

**راه‌حل:** هر فیلدِ بازگشتی را پشتِ `Box` بگذار:

```rust
enum Expr {
    Num(f64),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}
```

**چرا این راه‌حل است:** یک `Box<Expr>`، فارغ از اینکه چه چیزی زیرش باشد یا چقدر عمیق برود، همیشه دقیقاً پهنایِ یک اشاره‌گر است. حالا اندازه‌یِ `Add` به دو تا عددِ از پیش‌معلوم بستگی دارد، نه به اندازه‌یِ خودِ `Expr`. بازگشتِ واقعی از تعریفِ نوع (که باید سرِ کامپایل محدود باشد) رفته توی هیپ (که سرِ اجرا می‌تواند هر عمقی داشته باشد).

### `E0072` — دوباره، وقتی فقط یک فیلد جعبه دارد

```text
error[E0072]: recursive type `Expr` has infinite size
  --> phase2-intermediate\06-smart-pointers\02-recursive-types-and-trait-objects\examples\04-half-boxed-broken.rs:9:1
   |
 9 | enum Expr {
   | ^^^^^^^^^
10 |     Num(f64),
11 |     Add(Box<Expr>, Expr),
   |                    ---- recursive without indirection
   |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
   |
11 |     Add(Box<Expr>, Box<Expr>),
   |                    ++++    +

For more information about this error, try `rustc --explain E0072`.
```

**کامپایلر به چه اعتراض دارد:** همان خطا، همان دلیل — فقط این‌بار زیرِ فیلدِ دوم خط کشیده، نه اولی. فیلدِ اول (`Box<Expr>`) دیگر مشکلی ندارد؛ فیلدِ دوم، یک `Expr` خام، هنوز مستقیم و با مقدار داخلِ `Add` نشسته و به‌تنهایی کافی است تا حساب دوباره دایره‌ای بماند.

**راه‌حل:** فیلدِ باقی‌مانده را هم جعبه کن — دقیقاً همان کاری که «`Box` چرخه را می‌شکند» بالا انجام داد.

**چرا این راه‌حل است:** قاعده این نیست که «اندازه‌ی `Add` را کوچک کن»؛ قاعده این است که *هر* مسیرِ بازگشتی باید از یک `Box` رد شود. یک فیلدِ خامِ باقی‌مانده، فارغ از اینکه کنارش چه چیزِ دیگری جعبه شده، به‌تنهایی برایِ نگه‌داشتنِ اندازه در حالتِ «بی‌نهایت» کافی است.

### گرم‌کردن

```rust
enum Number {
    Value(i32),
```

<details>
<summary>پاسخ</summary>

نه — `E0072`، دقیقاً همان دلیلِ `Expr`. گونه‌ی `Wrapped` یک `Number` را با مقدار نگه می‌دارد؛ برایِ اندازه‌اش دوباره به اندازه‌ی `Number` نیاز داری.

</details>

<details>
<summary>این یکی چطور؟</summary>

```rust
enum Number {
    Value(i32),
    Wrapped(Box<Number>),
}
```

</details>

<details>
<summary>پاسخ</summary>

بله. `Box<Number>` همیشه دقیقاً پهنایِ یک اشاره‌گر است، پس اندازه‌یِ `Number` دیگر به خودش بستگی ندارد.

</details>

<details>
<summary>این چه چاپ می‌کند؟</summary>

```rust
let tree = Expr::Add(Box::new(Expr::Num(10.0)), Box::new(Expr::Num(5.0)));
println!("{}", eval(&tree));
```

</details>

<details>
<summary>پاسخ</summary>

```text
15
```

`eval` مقدارِ هر دو `Num` را جمع می‌زند: `10.0 + 5.0`. (توجه کن `f64` با `{}` بدونِ `.0` چاپ می‌شود وقتی نتیجه یک عددِ صحیح باشد — دقیقاً همان چیزی که `02-boxed-expr-eval.rs` هم با `20` نشانت داد.)

</details>

<details>
<summary>این کامپایل می‌شود؟ اگر بله، <code>None</code> اینجا یعنی چه؟</summary>

```rust
struct Node {
    value: i32,
    next: Option<Box<Node>>,
}
```

</details>

<details>
<summary>پاسخ</summary>

بله. `next: Option<Box<Node>>` یعنی «شاید یک گره‌یِ بعدی باشد، شاید نه» — `None` یعنی این آخرین گره است. و به‌لطفِ بهینه‌سازیِ اشاره‌گرِ تهی که [۱.۶.۱](../../../phase1-fundamentals/06-absence-and-failure/01-option-and-null-safety/README.fa.md) نشانت داد، `Option<Box<Node>>` هیچ بایتِ اضافه‌ای نسبت به خودِ `Box<Node>` نمی‌گیرد.

</details>

بینِ `Vec<Box<dyn Shape>>` و `Vec<dyn Shape>`، یکی کامپایل می‌شود و دیگری نه. کدام‌یک، و چرا، در یک جمله؟

<details>
<summary>پاسخ</summary>

`Vec<Box<dyn Shape>>` کامپایل می‌شود. `dyn Shape` به‌تنهایی یک نوعِ بی‌اندازه است — نوع‌های ملموسِ متفاوتی مثلِ `Circle` و `Rectangle` اندازه‌های متفاوتی دارند — و `Vec` باید اندازه‌ی هر عنصرش را از پیش بداند؛ `Box` همان اندازه‌ی ثابت را می‌دهد.

</details>

### بساز

یکی از این دو را انتخاب کن (یا هردو را):

- یک گونه‌ی تازه به `Expr` اضافه کن، مثلاً `Neg(Box<Expr>)` برایِ منفی‌کردنِ یک عبارت. `eval` را (و اگر `depth`/`count_nums` را نوشته‌ای، آن‌ها را هم) برایِ گونه‌یِ تازه به‌روز کن، و در یک تست یا یک `fn main` کوچک نشان بده که `Neg(Num(5.0))` به `-5.0` می‌رسد.
- یک `Shape` سوم بساز (مثلاً `Triangle`)، آن را کنارِ یک `Circle` و یک `Rectangle` تویِ یک `Vec<Box<dyn Shape>>` بگذار، و مطمئن شو `total_area` بدونِ هیچ تغییری همچنان درست کار می‌کند.

### چالش (اختیاری)

**بخشِ یک.** `Expr` را تعمیم بده به یک `enum` جنریک — چیزی مثلِ `Tree<T> { Leaf(T), Node(Box<Tree<T>>, Box<Tree<T>>) }` — و یک `count_leaves` بنویس که تعدادِ برگ‌ها را بشمارد، فارغ از اینکه `T` چه باشد.

**بخشِ دو.** (این یکی به جلو دست می‌برد.) تصور کن دو جایِ مختلفِ یک عبارتِ بزرگ باید *دقیقاً همان* زیرِ‌عبارت را با هم به‌اشتراک بگذارند، نه هرکدام نسخه‌یِ خودشان را داشته باشند. `Box` این کار را نمی‌کند — یک `Box` دقیقاً یک مالک دارد. در یک فایلِ موقت (نه بخشی از تست‌هایِ این درس)، فیلدهایِ `Box<Expr>` را با `Rc<Expr>` عوض کن و ببین دقیقاً چه چیزی در ساختن و ارزیابیِ یک درخت عوض می‌شود و چه چیزی نه. داستانِ کاملش در [۲.۶.۳](../03-rc-and-arc/README.fa.md) است.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| نوعِ بازگشتی (recursive type) | نوعی که یکی از گونه‌ها یا فیلدهایش، مستقیم یا غیرمستقیم، خودِ همان نوع را نگه می‌دارد | درخت‌ها، لیست‌های پیوندی، ASTها |
| `E0072` | خطایِ «اندازه‌یِ بی‌نهایت»؛ کامپایلر نمی‌تواند برایِ نوع یک عددِ ثابت حساب کند | هر نوعِ بازگشتیِ بدونِ `Box` |
| درختِ عبارت (expression tree) | نمایشِ یک عبارتِ ریاضی به‌شکلِ یک درخت — برگ‌ها عددند، گره‌ها عملگر | ارزیابی، پارس‌کردن، کامپایلرهایِ کوچک |
| شیءِ صفتِ جعبه‌ای (`Box<dyn Trait>`) | همان ترفندِ اندازه‌یِ ثابت، این‌بار رویِ نوعِ پاک‌شده به‌جایِ نوعِ بازگشتی | `Vec<Box<dyn Trait>>` برایِ مجموعه‌هایِ ناهمگون |

### الان می‌دانی

- چرا یک `enum` که یکی از گونه‌هایش خودِ همان `enum` را با مقدار نگه می‌دارد کامپایل نمی‌شود: کامپایلر برایِ لایه‌چینیِ رویِ استک، به یک عددِ ثابت نیاز دارد، و این تعریف هیچ‌وقت به یک عدد ختم نمی‌شود.
- چرا جعبه‌کردنِ *هر* فیلدِ بازگشتی — نه فقط یکی‌شان — چیزی است که واقعاً رفعش می‌کند: یک `Box<T>` همیشه دقیقاً پهنایِ یک اشاره‌گر است، فارغ از عمقِ واقعیِ چیزی که زیرش هست.
- `size_of::<Expr>()` یک خاصیتِ خودِ نوع است، نه یک مقدارِ خاص؛ عمقِ واقعیِ یک درخت یک خاصیتِ زمانِ اجراست که پشتِ اشاره‌گرها زندگی می‌کند.
- `Vec<Box<dyn Trait>>` همان ترفند را، رویِ یک دلیلِ دیگر برایِ اندازه‌یِ نامعلوم (نوعِ ملموسِ زیرش می‌تواند هر چیزی باشد)، به‌کار می‌برد — نه بازگشت، ناهمگونی.

### بعداً کامل‌تر می‌بینی

- **`Rc` و `Arc` برایِ مالکیتِ اشتراکی** — وقتی یک `Box` (یک مالکِ تک) کافی نیست و چند بخشِ برنامه واقعاً باید یک زیرِ‌درخت یا یک گره را با هم به‌اشتراک بگذارند — [۲.۶.۳ — انواع `Rc` و `Arc`](../03-rc-and-arc/README.fa.md).
- **`Weak` و چرخه‌هایِ مرجع** — درختی که یک گره‌اش ناگهان به پدرِ خودش هم اشاره کند دیگر درخت نیست، یک گراف با یک چرخه است؛ `Box` به‌تنهایی این حالت را بدونِ نشتِ حافظه برایِ همیشه مدیریت نمی‌کند — [۲.۶.۴ — `Weak` و چرخه‌هایِ مرجع](../04-weak-and-reference-cycles/README.fa.md).
- **`RefCell` و تغییرپذیریِ درونی** — اگر بخواهی یک گره‌یِ به‌اشتراک‌گذاشته‌شده را هم تغییر بدهی، نه فقط بخوانی — [۲.۶.۵ — `RefCell` و تغییرپذیریِ درونی](../05-refcell-and-interior-mutability/README.fa.md).

### می‌توانی توضیح بدهی؟

- چرا `enum Expr { Num(f64), Add(Expr, Expr) }` اندازه‌ی بی‌نهایت دارد، ولی همان چیز با `Add(Box<Expr>, Box<Expr>)` اندازه‌ی ثابت دارد؟
- چرا جعبه‌کردنِ فقط یکی از دو فیلدِ `Add` کافی نیست؟ با کلماتِ خودت، نه با تکرارِ پیامِ کامپایلر.
- چرا `size_of::<Expr>()` برایِ یک درختِ ۱۰۰۰-سطحی همان عددی است که برایِ یک `Num` تنها؟
- `dyn Shape` و `Expr`ِ بدونِ‌جعبه، هر دو باعثِ خطایی درباره‌ی اندازه می‌شوند — ولی دلیلشان یکی نیست. هرکدام را در یک جمله توضیح بده.
- کامپایلر برایِ `E0072` گاهی `&` را هم پیشنهاد می‌دهد، نه فقط `Box`. چرا `&` اینجا کار نمی‌کند؟
