# راه‌حل — ۲.۲.۱ کلوژرها، `Fn`/`FnMut`/`FnOnce` و `move`

```rust
pub fn apply_twice<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(f(x))
}

pub fn make_multiplier(factor: i32) -> impl Fn(i32) -> i32 {
    move |value| value * factor
}

pub fn count_matching<F: Fn(&str) -> bool>(items: &[String], predicate: F) -> usize {
    let mut count = 0;
    for item in items {
        if predicate(item) {
            count += 1;
        }
    }
    count
}

pub fn call_n_times<F: FnMut()>(mut f: F, n: u32) {
    for _ in 0..n {
        f();
    }
}

pub fn run_once<F: FnOnce() -> String>(f: F) -> String {
    f()
}
```

هیچ‌کدام از این پنج تابع نیازی به چیزی بیشتر از همان چیزی که در «مفهوم»
دیدی نداشت — فقط این‌بار خودت باید تصمیم می‌گرفتی کدام کراند را انتخاب
کنی.

## `apply_twice` — چرا `Fn` کافی است

```rust
pub fn apply_twice<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(f(x))
}
```

`f` دو بار صدا زده می‌شود، ولی هیچ‌جا تغییرش نمی‌دهیم و هیچ‌چیزی از داخلش
بیرون نمی‌بریم — فقط با آن `f(...)` صدایش می‌زنیم. برای همین، ضعیف‌ترین و
سخت‌گیرترینِ سه‌گانه هم برایش کافی است: `Fn`. اگر اینجا `FnMut` یا
`FnOnce` می‌نوشتی، هم کامپایل می‌شد و هم تست‌ها پاس می‌کردند — ولی
دروغی به فراخواننده می‌گفتی: «شاید مجبور شوم کلوژرت را تغییر بدهم» یا
«فقط یک‌بار صدایش می‌زنم»، هیچ‌کدامش راست نیست. بندِ کوچک‌ترین trait که
واقعاً کافی است را انتخاب کن، تا فراخواننده بیشترین آزادی را داشته باشد.

## `make_multiplier` — چرا `move` اینجا اجباری است

```rust
pub fn make_multiplier(factor: i32) -> impl Fn(i32) -> i32 {
    move |value| value * factor
}
```

بدونِ `move`، `|value| value * factor` می‌خواست `factor` را از استکِ
`make_multiplier` قرض بگیرد. ولی همان لحظه که `make_multiplier` برمی‌گردد،
آن استک از بین می‌رود — کلوژر با یک ارجاع به حافظه‌ای می‌ماند که دیگر
وجود ندارد، دقیقاً همان `E0597`ای که در «خطاهایی که خواهی دید» دیدی، فقط
این‌بار روی یک پارامتر به‌جای یک متغیرِ بلوکی. `move` این را حل می‌کند:
`factor` را کامل به داخلِ کلوژر می‌برد، و کلوژر از آن به بعد مالکِ نسخه‌ی
خودش است، کاملاً مستقل از فریمِ `make_multiplier`.

## `count_matching` — یک `Fn` دیگر، این‌بار با یک حلقه‌ی معمولی

```rust
pub fn count_matching<F: Fn(&str) -> bool>(items: &[String], predicate: F) -> usize {
    let mut count = 0;
    for item in items {
        if predicate(item) {
            count += 1;
        }
    }
    count
}
```

`predicate` هم مثلِ `f` در `apply_twice` فقط خوانده می‌شود — هر بار برای
یک عنصر صدا زده می‌شود و جوابش (`true`/`false`) خوانده می‌شود، هیچ‌چیزی
تغییر نمی‌کند یا بیرون برده نمی‌شود. `Fn` دوباره کافی است. توجه کن که این
راه‌حل حتی یک آداپتورِ ایتریتور هم به‌کار نبرد — همان حلقه‌ی معمولیِ فازِ
۱، چون آداپتورها (`.iter().filter(...)`) موضوعِ درسِ بعدی‌اند.

## `call_n_times` — چرا `FnMut` اینجا واقعاً لازم است

```rust
pub fn call_n_times<F: FnMut()>(mut f: F, n: u32) {
    for _ in 0..n {
        f();
    }
}
```

دو نکته اینجا هست. اول اینکه خودِ پارامتر باید `mut f: F` باشد — صدا زدنِ
یک کلوژرِ `FnMut` نیاز به دسترسیِ انحصاری (`&mut`) به آن دارد، و Rust
اجازه نمی‌دهد از بایندی که خودش `mut` نیست، `&mut` بگیری، حتی وقتی
*نوعِ* آن بایند از قبل می‌گوید «این ممکن است تغییر کند». دوم اینکه
`f()` داخلِ حلقه در واقع کوته‌نویسیِ `FnMut::call_mut(&mut f, ())` است —
هر صدا فقط برایِ همان یک فراخوانی، `f` را دوباره به‌شکلِ تغییرپذیر قرض
می‌گیرد؛ دقیقاً همین است که اجازه می‌دهد داخلِ یک حلقه صدایش بزنی، به‌جایِ
اینکه به یک‌بار محدود باشی — همان محدودیتی که `FnOnce` را از `FnMut`
جدا می‌کند.

اگر اینجا `F: Fn()` می‌نوشتی، یک کلوژرِ کاملاً معقول مثلِ
`|| log.push("tick")` دیگر رد نمی‌شد — چون آن کلوژر `log` را تغییر
می‌دهد، فقط `FnMut` است، نه `Fn`.

## `run_once` — چرا `FnOnce` اینجا (و فقط اینجا) کافی است

```rust
pub fn run_once<F: FnOnce() -> String>(f: F) -> String {
    f()
}
```

`f` دقیقاً یک‌بار صدا زده می‌شود — همین یک خط، بدونِ حلقه. چون تعهدِ
تابع «فقط یک‌بار صدا می‌زنم» است، ضعیف‌ترین trait از هر سه‌تا هم کافی
است: `FnOnce`. همین ضعیف‌بودن است که به کلوژرهایی مثلِ
`move || owned` (که `owned` را از داخلِ خودش بیرون می‌برد و
برمی‌گرداند) هم اجازه‌ی ورود می‌دهد — کلوژری که با کراندِ `Fn` یا
`FnMut` اصلاً رد نمی‌شد.

سلسله‌مراتب یک‌طرفه است، پس هر کلوژرِ `Fn` هم بدونِ مشکل از این تابع رد
می‌شود — تست `run_once_also_accepts_a_plain_fn_closure` دقیقاً همین را
تأیید می‌کند: کلوژرِ `|| "static".to_string()` هیچ‌چیزی نمی‌گیرد، پس
`Fn` است، و `Fn` هم یک `FnOnce`ِ معتبر است.
