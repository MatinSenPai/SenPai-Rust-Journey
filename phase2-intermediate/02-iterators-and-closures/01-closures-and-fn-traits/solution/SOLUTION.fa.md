# راه‌حل

```rust
pub fn make_multiplier(factor: i32) -> impl Fn(i32) -> i32 {
    move |x| x * factor
}
```

کلمه‌ی جالب و مهمِ این کد همون کلمه‌ی `move` هستش. اگه این کلمه نباشه، کلوژرِ `factor * |x| x` سعی می‌کنه تا متغیر `factor` رو از استکِ فرم (stack frame) تابعِ `make_multiplier` *قرض بگیره (borrow)*. اما به محض اینکه `make_multiplier` کارش تموم شه و مقدار برگردونه، اون استکِ فرم هم از بین میره — در نتیجه کلوژر ما با یه ارجاع می‌مونه که داره به یه قسمت از حافظه اشاره می‌کنه که دیگه اصلاً وجود نداره، و این دقیقاً همون چیزیه که ماژول borrow checkerِ تو Rust به شدت جلوش رو می‌گیره (این دقیقاً از همون دست باگ‌هاییه که Rust رخ دادنشون رو تو زمان کامپایل غیرممکن می‌کنه، در حالی که تو زبانی مثل C، این قضیه تبدیل به یه باگ واقعی و بی‌سروصدای use-after-free می‌شد). وجودِ کلمه‌ی `move` باعث می‌شه که مقدارِ `factor` (که یه `i32` هست و نوعش از جنسِ `Copy`ئه — برگرد به فاز ۱ ماژول ۰۲.۲) *به داخلِ* خودِ کلوژر کپی بشه، در نتیجه کلوژر مالکِ نسخه‌ی کپی‌شده‌ی خودش می‌شه و این نسخه هم تا زمانی که کلوژر زنده است، زنده می‌مونه، کاملاً مستقل و بی‌نیاز از اسکوپِ تابعِ `make_multiplier`.

```rust
pub fn call_n_times<F: FnMut()>(mut f: F, n: u32) {
    for _ in 0..n {
        f();
    }
}
```

دو تا نکته اینجا قابل توجهه. اول اینکه، خودِ پارامتر ورودیمون هم باید به شکل `mut f: F` تعریف بشه — فراخوانی یه کلوژر از نوعِ `FnMut` نیازمندِ دسترسی انحصاری (`&mut`) بهشه، و Rust اصلاً بهت اجازه نمی‌ده از متغیری که خودش با `mut` تعریف نشده `&mut` بگیری، حتی با وجود اینکه *نوعِ (type)* اون متغیر یعنی `f` از قبل تو خودش کدگذاری کرده که «این نیاز به تغییر دادنِ متغیرها داره.» دوم اینکه، عبارت `()f` تو داخلِ حلقه در واقع یه خلاصه‌نویسی برای `FnMut::call_mut(&mut f, ())` هست — یعنی تو هر بار فراخوانی، متغیرِ `f` فقط برای همون یه دور از اجرایِ تابع، دوباره به صورت تغییرپذیر قرض داده می‌شه (reborrows mutably)، و دقیقاً به خاطر همینه که می‌تونی اونو تو یه حلقه بذاری و چندین بار صداش بزنی، به جای اینکه فقط محدود به یک‌بار باشی (همین محدودیت دقیقاً همون چیزیه که `FnMut` رو از `FnOnce` متمایز می‌کنه).

در مورد سؤال ۱ مرور: بدنه‌ی کلوژری مثل `} count += 1; x + 1 {|x|` داره یه متغیرِ اسیرشده رو (یعنی همون `count`) تغییر می‌ده، بنابراین traitِ `FnMut` رو پیاده‌سازی می‌کنه (و طبق اون سلسله‌مراتب، به تبعش `FnOnce` رو هم داره) — اما **هرگز** traitِ `Fn` رو پیاده‌سازی نمی‌کنه، چون شرطِ `Fn` اینه که کلوژر حتماً باید متغیرهای اسیرشده‌اش رو فقط به‌صورت غیرقابل‌تغییر (immutably) قرض بگیره. پس پاس دادنِ همچین کلوژری به تابعِ `apply_twice` که با محدودیتِ `F: Fn(i32) -> i32` تعریف شده، با یه خطایی شبیه به "expected a closure that implements the `Fn` trait, but this closure only implements `FnMut`" متوقف و کامپایل نمی‌شه. محدودیتی (bound) که تو برای یه پارامترِ generic می‌نویسی، در واقع یه *قول (promise)* در مورد اینه که فراخواننده‌ی تابع مجاز به پاس دادن چه چیزهایی هست — اینجا تابعِ `apply_twice` قول داده بود که «من فقط قراره به خوندنِ متغیرهای اسیرشده‌ی کلوژر تو نیاز داشته باشم»، پس کامپایلر هم دقیقاً همه‌ی فراخواننده‌ها رو مجبور می‌کنه که پای همین قول وایسن.
