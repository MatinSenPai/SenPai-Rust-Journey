# ۲.۷.۲ — تستِ واحد، یکپارچه و مستندات

## در یک نگاه

بعد از این درس می‌توانی:

- اسم بگذاری روی الگویی که از فاز ۰ بی‌وقفه می‌نوشتی، و بگویی `#[cfg(test)] mod tests` دقیقاً *چرا* می‌تواند به آیتم‌های خصوصی دست بزند.
- یک تستِ یکپارچگی در `tests/` بنویسی، از قبل بگویی دقیقاً به کدام آیتم‌ها دسترسی دارد و به کدام‌ها نه، و وقتی اشتباه حدس زدی خطای واقعیِ کامپایلر را بخوانی.
- یک مثالِ داخلِ کامنتِ مستندات را — شاملِ مثالی که عمداً پنیک یا `Err` نشان می‌دهد — به یک تستِ واقعی و اجراشونده تبدیل کنی، و بگویی هرکدام از این سه نوع تست دقیقاً برایِ کدام موقعیت است.

**زمان:** حدود ۵۵ دقیقه · **پیش‌نیاز:** [۲.۷.۱ — ماژول‌ها و سطحِ دسترسی](../01-modules-visibility-workspaces/README.fa.md)

## چرا اهمیت دارد

برو به همان درسِ اولی که در این دوره یک خطِ Rust نوشتی — [۰.۳ — سلام Rust](../../../phase0-setup/03-hello-rust/README.fa.md). آن‌جا، پایینِ `src/lib.rs`، همین بلوک بود:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn shouts() {
        assert_eq!(shout("here we go"), "HERE WE GO!");
    }
}
```

و همان درس یک جمله‌ی دقیق درباره‌اش گفت: «در Rust تست‌های کوچک در همان فایلی که کد را تست می‌کنند می‌مانند... این تنبلی نیست — این‌طوری تست می‌تواند به توابعِ خصوصی دست بزند که بیرون نمی‌بیندشان» — و بعد افزود: «خودت در فاز ۲ تست می‌نویسی.»

از آن روز تا همین الان، ده‌ها بار دقیقاً همین بلوک را در `src/lib.rs` کپی کردی، تغییرش دادی، پرش کردی — بدونِ اینکه یک بار درسی رسماً بگوید این *چیست*. این درس همان وعده را نقد می‌کند: اسمِ رسمیِ این بلوک را می‌گذارد، و می‌گوید *چرا* آن `assert_eq!` بالا اصلاً کار می‌کند. بعد دو خواهرش را کنارش می‌گذارد — تستی که بیرونِ کریت زندگی می‌کند و تستی که داخلِ یک کامنت زندگی می‌کند — و نشانت می‌دهد سه‌تایشان با هم یک تصویرِ کامل می‌سازند.

نکته‌ی دیگری هم در کار است. درسِ [۲.۷.۱](../01-modules-visibility-workspaces/README.fa.md) به‌ات یاد داد `pub`، `pub(crate)` و خصوصیِ ساده چه فرقی دارند — ولی آن‌جا این فرق کمی نظری ماند، چون همه‌ی کد در یک فایل بود. این‌جا دقیقاً همان قاعده‌ها یک نتیجه‌ی واقعی و ملموس پیدا می‌کنند: کدام کدت می‌تواند یک تابعِ خصوصی را صدا بزند، و کدامش حتی نمی‌تواند اسمش را ببرد.

## مفهوم

### تست‌های واحد: همان بلوکی که ماه‌هاست می‌نویسی

اول این را ببین — بدونِ `#[cfg(test)]`، فقط به‌عنوانِ یک برنامه‌ی معمولی:

```rust
fn round1(x: f64) -> f64 {
    (x * 10.0).round() / 10.0
}

fn celsius_to_fahrenheit(c: f64) -> f64 {
    round1(c * 9.0 / 5.0 + 32.0)
}

fn main() {
    println!("{}", celsius_to_fahrenheit(0.0));
    println!("{}", round1(3.14159));
}
```

```text
32
3.1
```

هیچ چیزِ عجیبی نیست: `main` تابعِ `round1` را مستقیم صدا می‌زند، با اینکه `round1` هیچ `pub`ی ندارد. چرا کار می‌کند؟ چون چیزی به اسمِ «خصوصیِ سراسری» وجود ندارد — خصوصی‌بودن همیشه نسبت به یک مرز است، و مرزش (طبقِ [۲.۷.۱](../01-modules-visibility-workspaces/README.fa.md)) ماژول و بچه‌های همان ماژول است. `main` همین‌جا، در همین فایل نوشته شده — همان ماژول. برایش هیچ دیواری نیست.

حالا **تستِ واحد (unit test)** دقیقاً همین ترفند را می‌زند:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn rounds_correctly() {
        assert_eq!(round_to_one_decimal(1.24), 1.2);
    }
}
```

`#[cfg(test)]` یعنی «این ماژول را فقط وقتی کامپایل کن که داری برایِ `cargo test` بیلد می‌گیری» — باینریِ نهایی‌ات هیچ‌وقت این کد را با خودش حمل نمی‌کند. `#[test]` هم یک تابع را به‌عنوانِ تست علامت می‌زند تا `cargo test` پیدایش کند و اجرایش کند. ولی نکته‌ی اصلی جایِ دیگری است: این `mod tests` یک زیرماژول از همان فایل است، پس دقیقاً همان قاعده‌ی بالا برایش صادق است — `use super::*;` هرچه در `src/lib.rs` هست، شاملِ آیتم‌های خصوصی، به داخلِ این ماژول می‌آورد. تستِ واحد به تابعِ خصوصی دست‌درازی نمی‌کند؛ فقط از همان امتیازی استفاده می‌کند که هر کدِ دیگرِ همین فایل هم دارد.

### تست‌های یکپارچگی: مرزِ واقعیِ کریت

هر فایلی که زیرِ پوشه‌ی سطحِ‌بالای `tests/` بگذاری یک **تستِ یکپارچگی (integration test)** است؛ Cargo آن را جورِ دیگری کامپایل می‌کند: به‌عنوانِ یک **کریتِ کاملاً مجزا**، که به کتابخانه‌ی تو دقیقاً همان‌طور وابسته است که یک کاربرِ بیرونی وابسته می‌بود:

```rust
use p2_07_02_unit_integration_doc_tests::celsius_to_fahrenheit;

#[test]
fn converts_body_temperature() {
    let result = celsius_to_fahrenheit(37.0);
    assert!((result - 98.6).abs() < 0.5);
}
```

این کامپایل می‌شود و پاس می‌شود — `celsius_to_fahrenheit` عمومی است. ولی همین فایل را با این خط به‌جایِ آن `use` تصور کن:

```text
use p2_07_02_unit_integration_doc_tests::round_to_one_decimal;
```

دیگر کامپایل نمی‌شود. نه یک باگِ ظریف، نه یک پیامِ گیج‌کننده — یک خطای صریح که می‌گوید این تابع خصوصی است. خودت هم می‌توانی امتحانش کنی: `examples/02-private-item-is-unreachable.rs` دقیقاً همین خط را دارد؛ خروجیِ کاملش در «خطاهایی که خواهی دید» است.

چرا این‌بار کامپایل نشد در حالی که تستِ واحدِ بالا بدونِ مشکل کامپایل شد؟ چون این فایل دیگر «همان ماژول» نیست. از دیدِ کامپایلر، این فایل یک مصرف‌کننده‌ی *بیرونیِ* کتابخانه‌ی توست — دقیقاً همان چیزی که [۲.۷.۱](../01-modules-visibility-workspaces/README.fa.md) گفت: `pub` یعنی «هر کسی که می‌تواند خودِ ماژول را ببیند»، و یک کریتِ دیگر هرگز نمی‌تواند یک آیتمِ خصوصی را ببیند، مهم نیست چقدر وابسته باشد. همین قاعده برایِ `pub(crate)` هم دقیقاً همین‌طور صادق است: چیزی که ۲.۷.۱ «همه‌جایِ همین کریت دیده می‌شود» نامیدش، از دیدِ یک تستِ یکپارچگی — که کریتش عوض شده — به همان اندازه‌یِ خصوصیِ ساده نامرئی است.

```senpai-visual
{"kind":"concept","labels":["src/lib.rs: یک تابعِ pub، یک تابعِ خصوصی","mod tests داخلِ همان فایل — همان مرز، هر دو را می‌بیند","tests/*.rs — کریتِ جدا، فقط pub را می‌بیند","/// doc comment — کامپایلِ جدا، فقط pub را می‌بیند"]}
```

این دقیقاً همان جایی است که تستِ یکپارچگی ارزشش را نشان می‌دهد: جایی که تستِ واحد اصلاً نمی‌تواند برود. اگر یک روز `celsius_to_fahrenheit` را از `pub` به خصوصی تغییر بدهی (یا فراموش کنی از ریشه‌ی کریت دوباره صادرش کنی)، هر تستِ واحدِ همان فایل بی‌خیال ادامه می‌دهد — چون به آن دسترسیِ ویژه دارد — ولی هر تستِ یکپارچگی، و هر کاربرِ واقعیِ کریتِ تو، همان لحظه می‌شکند. این دقیقاً همان دسته‌باگی است که تستِ واحد به‌طورِ ساختاری هرگز نمی‌تواند بگیرد: APIای که از *داخلِ* کریت کار می‌کند، ولی از بیرون یا اصلاً در دسترس نیست یا رفتارِ دیگری دارد.

### تست‌های مستندات: کامنتی که واقعاً اجرا می‌شود

```rust
/// Converts `c` from Celsius to Fahrenheit, rounded to one decimal place.
///
/// # Examples
///
/// ```
/// # use p2_07_02_unit_integration_doc_tests::celsius_to_fahrenheit;
/// assert_eq!(celsius_to_fahrenheit(0.0), 32.0);
/// ```
pub fn celsius_to_fahrenheit(c: f64) -> f64 {
    // ...
}
```

ماه‌هاست همین شکل را می‌بینی: یک کامنتِ `///`، یک عنوانِ `# Examples`، بعد یک فراخوانی و جوابش. دقیقاً همین را در [۰.۳](../../../phase0-setup/03-hello-rust/README.fa.md) هم دیدی — «`shout("here we go")` برمی‌گرداند `"HERE WE GO!"`» — و در [۱.۵.۲](../../../phase1-fundamentals/05-your-own-types/02-tuple-structs-and-newtype/README.fa.md) حتی یک بلوکِ کدِ کامل هم دیدی، برچسب‌خورده با ` ```text `. هر دو فقط برایِ *نشان‌دادنِ* شکلِ خروجی بودند؛ هیچ‌کدام هیچ‌وقت کامپایل نشدند. فرقِ بلوکِ بالا همین است: سه بک‌تیکِ خالی، بدونِ هیچ برچسبی — که پیش‌فرضش Rust است، نه متنِ ساده. همین یک تفاوت، این چند خط را از یک مثالِ تزئینی تبدیل می‌کند به کدی که `cargo test` واقعاً کامپایلش می‌کند و اجرایش می‌کند — یک **تستِ مستندات (doc test)**.

آن خطِ `# use ...;` را ببین. یک `#` و یک فاصله، درست در ابتدای خط. این خط سرِ کامپایل و اجرا حساب می‌شود، ولی از داخلِ مستنداتِ *رندرشده* پنهان می‌ماند — ترفندی برایِ قایم‌کردنِ نویزِ راه‌اندازی (مثلِ همین `use`) که خواننده‌ی مستندات لازم نیست ببیندش، ولی کامپایلر برایِ کامپایل‌کردنِ مثال بهش نیاز دارد.

یک تستِ مستندات فقط راهِ خوش‌بینانه را نشان نمی‌دهد. می‌تواند صریحاً یک پنیک را هم قول بدهد — دقیقاً همان `#[should_panic(expected = "...")]`ای که در [۱.۶.۴](../../../phase1-fundamentals/06-absence-and-failure/04-panic-vs-result/README.fa.md) رویِ یک `#[test]` نوشتی، این‌بار به شکلِ یک برچسب رویِ خودِ فنس:

```rust
/// # Panics
///
/// Panics with the message `readings must not be empty` if `readings` is
/// empty.
///
/// ```should_panic
/// # use p2_07_02_unit_integration_doc_tests::average_celsius;
/// average_celsius(&[]);
/// ```
```

یک فرق: `should_panic` فقط می‌پرسد «آیا اصلاً پنیک کرد؟» — برخلافِ `#[should_panic(expected = "...")]`، هیچ راهی برایِ چک‌کردنِ *متنِ* پیام ندارد. برایِ همین بخشِ `# Panics` بالا خودش پیامِ دقیق را با کلمه نوشته؛ فنس فقط ثابت می‌کند که پنیک واقعاً اتفاق می‌افتد.

و می‌تواند یک مسیرِ `Err` را هم مستند کند:

```rust
/// # Errors
///
/// Returns `Err` with the message `not a valid number: "<input>"` if
/// `input` cannot be parsed as a floating-point number.
///
/// ```
/// # use p2_07_02_unit_integration_doc_tests::parse_celsius;
/// assert_eq!(
///     parse_celsius("hot"),
///     Err("not a valid number: \"hot\"".to_string())
/// );
/// ```
```

هیچ برچسبِ خاصی لازم ندارد — یک `assert_eq!` معمولی رویِ یک `Result` کافی است. عنوان‌هایِ `# Examples`، `# Panics` و `# Errors` قراردادی‌اند (خودِ کتابخانه‌ی استاندارد هم همین‌ها را به‌کار می‌برد)، نه چیزی که کامپایلر بشناسد؛ آن‌چه واقعاً کامپایل و اجرا می‌شود، فقط فنس‌هایِ کد زیرِ آن‌هاست.

وقتی هر سه تابع را در `src/lib.rs` بنویسی و `cargo test` بزنی، این پنج تستِ مستندات — دوتا برایِ `average_celsius`، دوتا برایِ `parse_celsius`، یکی برایِ `celsius_to_fahrenheit` — دقیقاً همین‌طور اجرا می‌شوند:

```text

running 5 tests
test src\lib.rs - average_celsius (line 35) ... ok
test src\lib.rs - average_celsius (line 24) ... ok
test src\lib.rs - celsius_to_fahrenheit (line 11) ... ok
test src\lib.rs - parse_celsius (line 49) ... ok
test src\lib.rs - parse_celsius (line 60) ... ok

```

(این خروجی از نسخه‌ی کاملاً پیاده‌سازی‌شده گرفته شده — همان پسوندِ `_solution` در اسمِ کریت را می‌بینی. همین پنج تست، با اسمِ کریتِ خودت، وقتی کارِ بخشِ «تمرین» را تمام کنی ظاهر می‌شوند — هرچند تست‌هایِ مستندات موازی اجرا می‌شوند، پس ترتیبِ چاپشان می‌تواند بینِ اجراها فرق کند؛ چیزی که باید چک کنی همان پنج اسم و شماره‌خط است، نه ترتیبشان.) این تضمینی است که یک کامنتِ معمولی هرگز نمی‌دهد: یک مثالِ دستی که داخلِ یک متن نوشته شده، ممکن است همان لحظه‌ای که رفتارِ تابع تغییر می‌کند بی‌سروصدا کهنه و غلط شود؛ یک تستِ مستندات، درست همان لحظه، بیلد را با خطا متوقف می‌کند. نمونه‌ی واقعیِ این شکست را در «خطاهایی که خواهی دید» می‌بینی.

### سه ابزار، سه سؤال

| نوع تست | کجا زندگی می‌کند | چه چیزی می‌بیند | برایِ چه سؤالی |
|---|---|---|---|
| واحد (unit) | `#[cfg(test)] mod tests`، تهِ همان فایل | همه‌چیزِ همان کریت، شاملِ خصوصی‌ها | «آیا این تکه‌ی داخلی درست کار می‌کند؟» |
| یکپارچگی (integration) | `tests/*.rs`، کریتِ جدا | فقط APIِ `pub` | «آیا این کریت از بیرون درست کار می‌کند؟» |
| مستندات (doc test) | داخلِ کامنتِ `///`، کامپایلِ جدا | فقط APIِ `pub` | «آیا مثالِ داخلِ مستندات هنوز درست است؟» |

تستِ واحد را برایِ جزئیاتِ داخلی و حالت‌های حاشیه‌ای بگیر — همان‌جایی که دسترسی به یک تابعِ کمکیِ خصوصی، مثلِ `round_to_one_decimal`، خودِ اعتبارسنجی را ساده‌تر می‌کند. تستِ یکپارچگی را برایِ *قراردادِ* عمومیِ کریت بگیر — سؤالی که فقط از دیدِ یک مصرف‌کننده‌ی واقعی معنی دارد. و تستِ مستندات را نه به‌عنوانِ یک تستِ سوم و جداگانه، بلکه به‌عنوانِ ضمانتی رویِ چیزی که داری *به هر حال* می‌نویسی: مثالی که یک خواننده‌ی انسانی می‌بیند. سه‌تایشان با هم رقیبِ هم نیستند؛ هرکدام یک لایه از همان کریت را می‌پوشانند.

## دست‌به‌کد

اول نسخه‌ی سالم:

```sh
cargo run -p p2-07-02-unit-integration-doc-tests --example 01-preview-the-domain
```

```text
0C  -> 32F
37C -> 98.6F
round1(3.14159) called directly: 3.1
```

این فایل یک نسخه‌ی مستقل و کاملاً کارکردنی از چیزی است که در `src/lib.rs` می‌سازی — یک کپیِ محلی، نه یک `use` از کریتِ خودِ درس (برایِ همین اسم‌هایش کمی فرق دارند). دقیقاً همان چیزی که در «مفهوم» دیدی: `main` تابعِ خصوصی‌شکلِ `round1` را مستقیم صدا می‌زند، چون هر دو در همین یک فایل‌اند.

حالا دو مثالِ عمداً خراب:

```sh
cargo run -p p2-07-02-unit-integration-doc-tests --example 02-private-item-is-unreachable --features broken
cargo run -p p2-07-02-unit-integration-doc-tests --example 03-average-of-nothing-panics --features broken
```

اولی اصلاً کامپایل نمی‌شود؛ دومی کامپایل می‌شود و رویِ ورودیِ خالی پنیک می‌گیرد. هر دو خروجی، عیناً، در «خطاهایی که خواهی دید» است.

بعد این‌ها را امتحان کن:

۱. در `01-preview-the-domain.rs`، یک تابعِ خصوصیِ تازه اضافه کن و از `main` صدایش بزن. کامپایل می‌شود؟ چرا این سؤال حتی سؤال نیست؟
۲. در `02-private-item-is-unreachable.rs`، فقط اسمِ ایمپورت‌شده را از `round_to_one_decimal` به `celsius_to_fahrenheit` عوض کن (خودِ خط را دست نزن، فقط اسم). چرا همین یک تغییر کافی است تا کامپایل شود؟
۳. در `03-average-of-nothing-panics.rs`، پیش از تماسِ دومِ `average`، یک `if readings.is_empty() { return; }` رویِ ورودیِ خالی اضافه کن. آیا این دقیقاً همان کاری است که تابعِ واقعیِ `average_celsius` باید بکند، یا فرقی دارد؟ (نگاهی به «# Panics» در بخشِ مفهوم بینداز.)

## خطاهایی که خواهی دید

هر دو مثالِ زیر از همین کریت اجرا می‌شوند که، چون هنوز `todo!()`اند، کنارشان چندتا هشدارِ بی‌ربطِ «unused variable» و «never used» هم چاپ می‌شود. نادیده‌شان بگیر — همین که توابع را پیاده‌سازی کنی محو می‌شوند. خروجی‌های زیر فقط بخشِ مهم را نشان می‌دهند.

### `E0603` — تابعِ خصوصی، از بیرونِ کریت در دسترس نیست

```text
error[E0603]: function `round_to_one_decimal` is private

  --> phase2-intermediate\07-project-structure-and-testing\02-unit-integration-doc-tests\src\lib.rs:10:1
   |

   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

For more information about this error, try `rustc --explain E0603`.

```

**کامپایلر به چه اعتراض دارد:** `round_to_one_decimal` تعریف شده، ولی هیچ `pub`ی ندارد. این فایل — دقیقاً مثلِ هر فایلِ `tests/*.rs` — از دیدِ کامپایلر یک کریتِ کاملاً جداست که به کتابخانه‌ی درس وابسته است، نه بخشی از خودِ آن کریت. کامپایلر حتی می‌گوید کجا تعریف شده (آن `note:`)، ولی این کمکِ اطلاعاتی است، نه اجازه.

**راه‌حل:** به‌جایِ آن تابعِ خصوصی، همان چیزی را ایمپورت کن که واقعاً `pub` است:

```rust
use p2_07_02_unit_integration_doc_tests::celsius_to_fahrenheit;
```

**چرا این راه‌حل است:** `round_to_one_decimal` هیچ‌وقت قرار نبود بخشی از قراردادِ عمومیِ این کریت باشد — یک جزئیاتِ پیاده‌سازی است که `celsius_to_fahrenheit` پشتِ سرش پنهانش می‌کند. `pub` کردنِ اجباریِ آن فقط برایِ اینکه یک فایلِ بیرونی بتواند صدایش بزند، همان تله‌ای است که [۲.۷.۱](../01-modules-visibility-workspaces/README.fa.md) نشانش داد — انتخابِ دیده‌شدنی وسیع‌تر از نیازِ هر صداکننده‌ی واقعی — فقط این‌بار به‌جایِ یک ماژولِ دیگر، سرِ راحتیِ یک تست پیدایش شده.

### پنیکِ زمانِ اجرا — میانگینِ یک لیستِ خالی

```text
20

thread 'main' (32392) panicked at phase2-intermediate\07-project-structure-and-testing\02-unit-integration-doc-tests\examples\03-average-of-nothing-panics.rs:10:5:
readings must not be empty
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

**کامپایلر به چه اعتراض دارد:** این حتی خطایِ کامپایلر نیست — برنامه ساخته شد، اجرا شد، اولین `average(&[10.0, 20.0, 30.0])` را بی‌مشکل چاپ کرد (`20`)، و دقیقاً همان‌جایی که `average(&[])` را صدا زد پنیک گرفت. `assert!` داخلِ تابع، پیش از هر محاسبه‌ای، ورودی را چک می‌کند.

**راه‌حل:** پیش از صدا زدن، مطمئن شو ورودی خالی نیست — یا با یک چکِ صریح، یا با تغییرِ نوعِ برگشتی به چیزی که «بدونِ جواب» را هم می‌تواند نشان بدهد (`Option`، مثلاً).

**چرا این راه‌حل است:** این دقیقاً همان پنیکی است که `should_panic` رویِ `average_celsius` در بخشِ مفهوم قول داده بود — نه یک باگ، بلکه یک قراردادِ صریح: «میانگینِ هیچ‌چیز معنی ندارد، پس این تابع رویش پنیک می‌کند.» وقتی قراردادی صریح و مستند است، وظیفه‌ی صداکننده این است که رعایتش کند، نه اینکه تابع رفتارش را نرم کند.

### شکستِ یک تستِ مستندات — وقتی نمونه دیگر با واقعیت جور نیست

برایِ این یکی فایلِ مثالِ جداگانه‌ای در این درس نیست: یک doc example که همیشه خراب می‌ماند، نمی‌تواند بخشی از کدِ کامیت‌شده‌ی این درس باشد — `cargo test` برایِ همیشه قرمزش می‌کرد. به‌جایش، این خروجی را از یک کریتِ آزمایشیِ کاملاً جدا گرفته‌ام: دقیقاً همان تابعِ `celsius_to_fahrenheit`، با یک اشتباهِ عمدی در خودِ مثال (`celsius_to_fahrenheit(100.0)` را `300.0` نوشته‌ام، نه `212.0`):

```text

**راه‌حل:** خودِ مثال را درست کن، نه تابع را.

**چرا این راه‌حل است:** این دقیقاً همان لحظه‌ای است که این درس از اولش قولش را داد: یک تستِ مستندات، برخلافِ یک کامنتِ ساده، اجازه نمی‌دهد مثال از رفتارِ واقعی عقب بیفتد. یک کامنتِ معمولی همان‌جا ساکت می‌ماند و دروغ می‌گوید؛ این یکی کلِ `cargo test` را قرمز می‌کند تا مجبور شوی درستش کنی — همان لحظه، نه شش ماه بعد که یک کاربر رویِ همان مثال حساب باز کرده.

## تمرین

### گرم‌کردن

<details>
<summary>این کامپایل می‌شود؟</summary>

```rust
fn helper() -> i32 {
    42
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn calls_helper() {
        assert_eq!(helper(), 42);
    }
}
```

</details>

<details>
<summary>پاسخ</summary>

بله. `helper` هیچ `pub`ی ندارد، ولی `mod tests` زیرماژولِ همان فایل است — همان مرزِ خصوصی‌بودن. `use super::*;` هرچه در آن فایل هست، شاملِ `helper`، به داخل می‌آورد.

</details>

<details>
<summary>همان <code>helper</code> را از یک فایلِ <code>tests/foo.rs</code> با <code>use my_crate::helper؛</code> صدا بزنی، کامپایل می‌شود؟</summary>

نه. `tests/*.rs` یک کریتِ کاملاً جداست، و `helper` هرگز `pub` نشده؛ کامپایلر دقیقاً می‌گوید این تابع خصوصی است — نه «پیدا نشد»، بلکه «خصوصی است».

</details>

<details>
<summary>این یک تستِ مستندات است؟</summary>

```rust
/// `add_one(4)` is `5`.
pub fn add_one(n: i32) -> i32 {
    n + 1
}
```

</details>

<details>
<summary>پاسخ</summary>

نه. هیچ فنسِ کدی (سه بک‌تیک) در کار نیست — این فقط متنِ ساده‌ی داخلِ یک کامنت است، دقیقاً همان شکلی که در ۰.۳ و در بیشترِ درس‌های این دوره دیده‌ای. `cargo test` هیچ‌وقت آن را کامپایل یا اجرا نمی‌کند؛ اگر `add_one` روزی خراب شود، این خط بی‌سروصدا دروغ می‌گوید.

</details>

<details>
<summary>این یکی، وقتی <code>cargo test</code> اجرایش کند، چه چیزی چاپ می‌کند؟</summary>

```rust
/// ```
/// # fn double(n: i32) -> i32 { n * 2 }
/// assert_eq!(double(4), 8);
/// ```
```

</details>

<details>
<summary>پاسخ</summary>

هیچی، مگر شکست بخورد. یک `assert_eq!`ِ موفق چیزی چاپ نمی‌کند؛ فقط تست را پاس می‌کند و `cargo test` یک خطِ خلاصه در آخر نشان می‌دهد.

</details>

<details>
<summary>این تست، اگر تابعش پنیک نکند، چه می‌شود؟</summary>

```rust
#[test]
#[should_panic]
fn expects_a_panic() {
    // بدنه‌ای که پنیک نمی‌گیرد
}
```

</details>

<details>
<summary>پاسخ</summary>

FAIL می‌شود. `#[should_panic]` دقیقاً برعکسِ معمول را می‌خواهد: اگر تابع بدونِ پنیک تمام شود، همین «تمام‌شدنِ آرام» شکستِ تست است.

</details>

### تعمیر

هر دو مثالِ خراب را درست کن:

۱. `examples/02-private-item-is-unreachable.rs` را طوری درست کن که کامپایل شود — **بدونِ** اینکه `round_to_one_decimal` را در `src/lib.rs` عمومی کنی. (راهنما: چیزی که این فایل باید تستش کند از اول هم عمومی بود.)
۲. `examples/03-average-of-nothing-panics.rs` را طوری درست کن که دیگر پنیک نگیرد — **بدونِ** حذفِ `assert!` از تابعِ `average`. تماسِ دوم را با یک ورودیِ غیرخالی جایگزین کن، یا پیش از آن یک چک بگذار که وقتِ خالی‌بودن یک پیامِ دیگر چاپ کند.

### پیاده‌سازی

چهار تابع در `src/lib.rs` — هرکدام کاملاً مشخص‌شده در کامنتِ مستنداتِ خودش، و هر مثالِ داخلِ آن کامنت یک تستِ واقعی هم هست:

```sh
cargo test -p p2-07-02-unit-integration-doc-tests
```

تا وقتی هر چهارتا را ننوشته‌ای، هم `mod tests` تهِ فایل، هم `tests/public_api.rs`، هم خودِ تست‌های مستنداتِ داخلِ کامنت‌ها — هر سه شکست می‌خورند. طبیعی است؛ دقیقاً به همین دلیل این درس این‌قدر رویِ «سه‌جور تست، یک هدف» تکیه کرد.

### بساز

یک تابعِ `pub` تازه به این کریت اضافه کن — هرچیزی که دوست داری (مثلاً `pub fn format_reading(c: f64) -> String` که یک عددِ سلسیوس را به رشته‌ای مثلِ `"36.6C"` تبدیل کند) — با یک کامنتِ مستنداتِ کامل، شاملِ یک بخشِ `# Examples` که واقعاً کامپایل و اجرا شود. برایش هم یک تستِ واحد در `src/lib.rs` بنویس، هم یک تستِ یکپارچگی در `tests/public_api.rs`.

بعد این آزمایش را بکن: یکی از assertionهایِ همان مثالِ داخلِ کامنت را عمداً غلط کن (مثلاً یک عددِ اشتباه)، `cargo test` بزن و پیامِ شکست را با دقت بخوان — دقیقاً همان شکلی که در «خطاهایی که خواهی دید» دیدی، این‌بار رویِ تابعِ خودت. بعد برش‌گردان به حالتِ درست.

### چالش (اختیاری)

هر سه بخش را جدا اجرا کن و فرقشان را ببین:

```sh
cargo test -p p2-07-02-unit-integration-doc-tests --lib
cargo test -p p2-07-02-unit-integration-doc-tests --test public_api
cargo test -p p2-07-02-unit-integration-doc-tests --doc
```

بعد یکی از تست‌هایِ `src/lib.rs` را با `#[ignore]` علامت بزن (یک کامنتِ کنارش بنویس که چرا)، و با

```sh
cargo test -p p2-07-02-unit-integration-doc-tests -- --ignored
```

فقط همان یکی را اجرا کن. این دقیقاً همان مشکلی است که [۲.۷.۴](../04-property-and-snapshot-testing/README.fa.md) و [۲.۷.۵](../05-benchmarking-with-criterion/README.fa.md) با ابزارهایِ مخصوصِ خودشان کامل‌ترش می‌کنند: تست‌هایی که نباید در هر اجرایِ معمولی شرکت کنند.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| تستِ واحد (unit test) | `#[test]`ای که با خودِ کریت کامپایل می‌شود؛ به آیتم‌هایِ خصوصی هم دسترسی دارد | جزئیاتِ داخلی، حالت‌هایِ حاشیه‌ای |
| تستِ یکپارچگی (integration test) | فایلی در `tests/`، کریتِ کاملاً جدا؛ فقط `pub` | «آیا APIِ عمومی از بیرون کار می‌کند؟» |
| تستِ مستندات (doc test) | فنسِ کد داخلِ `///`؛ کامپایل و اجرا می‌شود | مستنداتی که هرگز بی‌سروصدا کهنه نمی‌شوند |
| خطِ مخفی (`# `) | داخلِ فنس کامپایل می‌شود، در مستنداتِ رندرشده دیده نمی‌شود | پنهان‌کردنِ نویزِ راه‌اندازی |
| `should_panic` | فنسی که فقط اگر پنیک بزند پاس می‌شود؛ متنِ پیام را چک نمی‌کند | مستندسازیِ صریحِ رفتارِ پنیک |
| `E0603` | «این تابع خصوصی است» | تلاش برایِ رسیدن به یک آیتمِ خصوصی از بیرونِ کریت |

### الان می‌دانی

- `#[cfg(test)] mod tests` تهِ یک فایل، یک تستِ واحد است: با خودِ کریت کامپایل می‌شود، پس به آیتم‌هایِ خصوصیِ همان فایل هم دسترسی دارد — دقیقاً همان چیزی که از فاز ۰ می‌نوشتی.
- هر فایلِ زیرِ `tests/`، یک کریتِ کاملاً جداست که فقط APIِ `pub` کتابخانه را می‌بیند — دقیقاً مثلِ یک کاربرِ بیرونی، نه یک استثنای داخلی.
- `pub(crate)`، مثلِ خصوصیِ ساده، از دیدِ یک تستِ یکپارچگی نامرئی است؛ فقط `pub` واقعی از این مرز رد می‌شود.
- یک فنسِ کدِ سه‌بک‌تیکی داخلِ `///` — بدونِ برچسب یا با برچسبِ `rust` — با `cargo test` کامپایل و اجرا می‌شود؛ همین فنس با برچسبِ `text` فقط نمایشی می‌ماند.
- خطوطِ `# ` داخلِ آن فنس سرِ اجرا حساب می‌شوند ولی از مستنداتِ رندرشده پنهان می‌مانند.
- `should_panic` قولِ یک پنیک را مستند می‌کند؛ برخلافِ `#[should_panic(expected = "...")]`، متنِ پیام را چک نمی‌کند.
- تستِ واحد برایِ جزئیاتِ داخلی، تستِ یکپارچگی برایِ قراردادِ عمومی، تستِ مستندات برایِ اینکه مثال‌هایِ داخلِ کامنت هرگز بی‌سروصدا کهنه نشوند.

### بعداً کامل‌تر می‌بینی

- **بدل‌هایِ تست، و چرا به‌ندرت به یک فریم‌ورکِ mock نیاز داری** — [۲.۷.۳ — بدل‌هایِ تست در Rust](../03-test-doubles-in-rust/README.fa.md)
- **تستِ خاصیت‌محور با `proptest`، تستِ عکس‌برداری با `insta`** — [۲.۷.۴](../04-property-and-snapshot-testing/README.fa.md)
- **سنجشِ کارایی با `criterion`** — [۲.۷.۵](../05-benchmarking-with-criterion/README.fa.md)
- **یک نوعِ خطایِ درست‌وحسابی به‌جایِ یک `String` خام** — [۲.۵.۱ — نوع‌هایِ خطایِ خودت](../../05-error-handling/01-custom-error-types/README.fa.md) و [۲.۵.۳ — `thiserror` و `anyhow`](../../05-error-handling/03-thiserror-and-anyhow/README.fa.md)

### می‌توانی توضیح بدهی؟

- چرا یک تستِ واحد می‌تواند یک تابعِ خصوصی را صدا بزند، ولی یک تستِ یکپارچگی نه؟
- یک doc example را چطور از یک بلوکِ کدِ صرفاً نمایشی جدا می‌کنی؟
- خطِ `# ` داخلِ یک فنسِ تستِ مستندات چه‌کار می‌کند و چرا لازم است؟
- `should_panic` چه چیزی را چک می‌کند و چه چیزی را چک نمی‌کند؟
- یک باگِ واقعی بگو که تستِ یکپارچگی می‌گیرد و تستِ واحد به‌طورِ ساختاری نمی‌تواند بگیرد.
