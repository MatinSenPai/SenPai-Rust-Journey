# راه‌حل — ۲.۷.۲ تستِ واحد، یکپارچه و مستندات

```rust
fn round_to_one_decimal(x: f64) -> f64 {
    (x * 10.0).round() / 10.0
}

pub fn celsius_to_fahrenheit(c: f64) -> f64 {
    round_to_one_decimal(c * 9.0 / 5.0 + 32.0)
}

pub fn average_celsius(readings: &[f64]) -> f64 {
    assert!(!readings.is_empty(), "readings must not be empty");
    let sum: f64 = readings.iter().sum();
    round_to_one_decimal(sum / readings.len() as f64)
}

pub fn parse_celsius(input: &str) -> Result<f64, String> {
    input
        .parse::<f64>()
        .map_err(|_| format!("not a valid number: {input:?}"))
}
```

هیچ نکته‌ی ظریفی در محاسبات نیست — بخشِ جذابِ این درس این است که هر تست کجا *زندگی می‌کند*، نه ریاضیاتش. سه سطحِ کاملاً متفاوت از تست همین چهار تابعِ کوچک را آزمایش می‌کنند.

## `round_to_one_decimal` — خصوصی، و فقط تستِ واحد بهش می‌رسد

بلوکِ `#[cfg(test)] mod tests` تهِ `src/lib.rs` این تابع را **مستقیم** صدا می‌زند، چون تست‌های واحد به‌عنوانِ بخشی از همین کریت کامپایل می‌شوند و قاعده‌ی خصوصی‌بودن برایِ کدِ داخلِ یک کریتِ مشترک اعمال نمی‌شود. `tests/public_api.rs` هیچ راهی برایِ حتی *نام‌بردنِ* این تابع ندارد — از دیدِ آن فایل، این کریت یک وابستگیِ بیرونی است، و `round_to_one_decimal` هیچ‌وقت `pub` نشده بود. `examples/02-private-item-is-unreachable.rs` دقیقاً همین تلاش را می‌کند و با `E0603` شکست می‌خورد.

## `average_celsius` — یک قراردادِ صریح، مستندشده در دو جا

پیاده‌سازی با یک `assert!` شروع می‌شود، نه با محاسبه — دقیقاً همان چیزی که کامنتِ بالای تابع، زیرِ `# Panics`، از قبل با کلمه گفته بود. پیامِ پنیک (`"readings must not be empty"`) عیناً همان رشته‌ای است که هم تستِ واحدِ `#[should_panic(expected = "...")]` چکش می‌کند، هم فنسِ `should_panic` داخلِ کامنت (که فقط ثابت می‌کند پنیک اتفاق می‌افتد، نه اینکه متنش را چک کند). سه‌جا — کامنت، تستِ واحد، تستِ مستندات — یک قرارداد را از سه زاویه‌ی متفاوت تکرار می‌کنند.

## `parse_celsius` — یک `Result`، با هر دو مسیرش مستند و تست‌شده

`.map_err(|_| ...)` خطایِ واقعیِ `ParseFloatError` را دور می‌ریزد و جایش یک پیامِ خودمان می‌گذارد — دقیقاً همان پیامی که هم در بخشِ `# Errors` کامنت نوشته شده، هم در تستِ مستنداتِ زیرش با `assert_eq!` چک می‌شود. (در یک کریتِ واقعی، به‌جایِ یک `String` خام، احتمالاً یک نوعِ خطایِ خودت را می‌ساختی — [۲.۵.۱](../../../05-error-handling/01-custom-error-types/README.fa.md) دقیقاً همین را یادت می‌دهد؛ اینجا سادگی را عمداً انتخاب کردیم تا تمرکز رویِ خودِ تست‌ها بماند.)

## چیزی که این درس واقعاً درباره‌اش بود

- **تستِ واحد** (`mod tests` تهِ `src/lib.rs`) به هر چهار تابع می‌رسد، شاملِ `round_to_one_decimal`ِ خصوصی — چون با خودِ کریت کامپایل می‌شود.
- **تستِ یکپارچگی** (`tests/public_api.rs`) فقط سه تابعِ `pub` را می‌بیند — دقیقاً همان چیزی که یک کاربرِ واقعیِ این کریت هم می‌بیند، نه بیشتر.
- **تستِ مستندات** (پنج فنسِ کد، داخلِ کامنت‌هایِ همین سه تابعِ `pub`) با `cargo test` واقعاً کامپایل و اجرا می‌شود؛ اگر رفتارِ یکی از توابع روزی از آنچه کامنتش قول داده فاصله بگیرد، همین‌جا و همان لحظه بیلد را می‌شکند.

هر سه با هم، رویِ یک کریتِ ۲۰‌خطی، دقیقاً همان چیزی را ثابت می‌کنند که این درس از اولش قولش را داد: این سه نوع تست رقیبِ هم نیستند، هرکدام یک لایه از همان کریت را می‌پوشانند.
