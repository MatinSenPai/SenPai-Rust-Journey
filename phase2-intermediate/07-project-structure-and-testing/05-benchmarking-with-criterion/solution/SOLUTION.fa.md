# راه‌حل

```rust
pub fn sum_of_squares_loop(n: u32) -> u64 {
    let mut total: u64 = 0;
    for i in 1..=n {
        total += (i as u64) * (i as u64);
    }
    total
}

pub fn sum_of_squares_iter(n: u32) -> u64 {
    (1..=n).map(|i| (i as u64) * (i as u64)).sum()
}
```

تبدیلِ `as u64` در هر دو پیش از ضرب اتفاق می‌افتد — `i * i` خیلی زودتر از خودِ `n` بزرگ‌شدن، رویِ `u32` سرریز می‌کرد؛ این خودِ به‌توان‌رساندن است که اول سرریز می‌کند، نه جمعِ کلی.

## عددهایِ واقعیِ تمرینِ «بساز» — و چرا غافلگیرکننده‌اند

`solution/benches/comparison.rs` همان تابعِ بنچمارکِ سومی را دارد که تمرینِ «بساز» می‌خواست، برایِ مقایسه‌ی هر دو تابع در `n = 10_000`. خودت اجرا کن: `cargo bench --manifest-path solution/Cargo.toml --bench comparison -- sum_of_squares`. خروجیِ واقعی‌اش، روی همین ماشین:

```text
sum_of_squares_loop_10000
                        time:   [5.7788 µs 5.7883 µs 5.7998 µs]
```

```text
sum_of_squares_iter_10000
                        time:   [1.9452 ns 1.9597 ns 1.9757 ns]
```

این آن مسابقه‌ی نزدیکی که از «انتزاعِ رایگان»یِ [۲.۲.۵](../../../02-iterators-and-closures/05-laziness-and-performance/README.fa.md) انتظار داری نیست — نسخه‌ی ایتریتور حدود **۳۰۰۰ برابر** سریع‌تر اندازه‌گیری شد، نه «تقریباً برابر». هر دو درست‌اند (`both_implementations_agree_across_a_range` هر `n` از ۰ تا ۴۹ را چک می‌کند)، پس این یک باگ نیست.

زمان‌گیریِ هر دو در چند `n` خیلی متفاوت، دلیلش را روشن می‌کند:

```text
n=       10000  loop=       8.6µs   iter=         0ns
n=     1000000  loop=     849.2µs   iter=         0ns
n=   100000000  loop=   55.7348ms   iter=         0ns
```

زمانِ `sum_of_squares_loop` با `n` بالا می‌رود — دقیقاً همان رفتاری که از یک حلقه‌ی صادقِ O(n) انتظار داری. زمانِ `sum_of_squares_iter` در هیچ اندازه‌ای تکان نمی‌خورد — امضایِ این است که کامپایلر کلِ زنجیره‌ی `.map().sum()` را برابرِ یک فرمولِ بسته‌ی جبری (مجموعِ `n` جمله‌ی اولِ مربع‌ها یک فرمولِ شناخته‌شده دارد) اثبات کرده و کلِ حلقه را با آن فرمول جایگزین کرده — نه اینکه سریع‌ترش کرده باشد، اصلاً اجرایش نکرده.

اینجا دقیق‌بودن مهم است، چون این یک مکانیزمِ کاملاً متفاوت از مقایسه‌ی `square`/`black_box` در متنِ درس است، نه همان ترفند که دوباره ظاهر شده باشد:

- فاصله‌ی `square(7)` در برابرِ `square(black_box(7))` **ثابت‌سازیِ سرِ کامپایل (constant folding)** بود: کامپایلر ورودیِ دقیق را می‌دانست (یک لیترالِ `۷`) و *همان یک جواب* را سرِ کامپایل از پیش حساب کرد. پیچیدنِ ورودی در `black_box` دقیقاً همین را رد می‌کند، چون کامپایلر دیگر نمی‌تواند فرض کند مقدار را می‌داند.
- این فاصله **کاهشِ قدرتِ جبری (strength reduction)** است: `black_box(n)` واقعاً مقدارِ زمانِ‌اجرایِ `n` را پنهان می‌کند — کامپایلر هیچ ایده‌ای ندارد `۱۰_۰۰۰` است یا `۱۰۰_۰۰۰_۰۰۰` — ولی لازم هم نیست بداند، چون فرمولی را اثبات کرده که برایِ *هر* `n`ای درست است. `black_box` هیچ‌وقت قرار نبوده جلویِ این را بگیرد — و شاید نباید هم بگیرد: جوابِ فرمولِ بسته دقیقاً به‌اندازه‌ی جوابِ حلقه درست است.

اینکه چرا حلقه‌ی دستی همان رفتار را نمی‌گیرد ولی زنجیره‌ی `.sum()` می‌گیرد، سؤالی است درباره‌ی اینکه کدام پاسِ LLVM کدام شکل را تشخیص می‌دهد — جوابِ قطعی‌اش نیاز به خواندنِ اسمبلیِ تولیدشده دارد، که فراتر از دامنه‌ی این درس است. درسِ صادقانه کوچک‌تر و کاربردی‌تر از «ایتریتورها ۳۰۰۰ برابر سریع‌ترند» است: تست‌هایِ واحد ثابت می‌کنند این دو تابع *چه چیزی* حساب می‌کنند؛ فقط یک بنچمارک بهت می‌گوید حسابش هم‌قیمت است یا نه — و اینجا، خروجیِ اثبات‌شده‌یِ یکسان، هزینه‌ای کاملاً متفاوت را پنهان کرده بود. این دقیقاً همان شکافی است که این درس برایِ بستنش وجود دارد.
