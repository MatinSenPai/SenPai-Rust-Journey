# ۲.۷.۱ — ماژول‌ها، دیدپذیری، صادرِ دوباره، ورک‌اسپیس‌ها

## در یک نگاه

بعد از این درس می‌توانی:

- توضیح بدهی درختِ ماژولِ Rust چطور رویِ درختِ فایل‌ها می‌نشیند — `mod foo;`
  کنارِ `foo.rs`، یا یک زیرماژولِ تودرتو کنارِ `foo/bar.rs` — و خودت یک فایلِ
  بزرگ‌شده را به همین شکل بشکنی.
- بینِ بدونِ‌تغییردهنده، `pub`، `pub(crate)` و `pub(super)` برایِ یک آیتمِ
  مشخص درست انتخاب کنی، و خطایِ واقعیِ دسترسیِ خصوصیِ `E0616` را خودت بخوانی
  و رفع کنی.
- با `pub use` یک آیتم را در یک مسیرِ کم‌عمق‌تر از جایی که واقعاً تعریف شده
  صادرِ دوباره کنی، و به `Cargo.toml`ِ ریشه‌ی همین مخزن به‌عنوانِ یک
  ورک‌اسپیسِ Cargoِ واقعی و قابل‌بازرسی اشاره کنی.

## چرا اهمیت دارد

از فازِ ۰ تا همین لحظه، هر بار `cargo run` یا `cargo test` زدی، دقیقاً یک
فایل کامپایل شد. `src/lib.rs`، یا یکی از `examples/*.rs`ها — همیشه یک فایل،
از بالا تا پایین. برایِ یک تمرینِ کوتاه، این عالی است. برایِ یک پروژه‌یِ
واقعی نیست — و امروز دقیقاً همان‌جاست که این درس شروع می‌شود.

تو پایتون، این مشکل خودش را حل می‌کند: هر فایلِ `.py` به‌طورِ خودکار یک
ماژول است، و `import foo` کار می‌کند چون فایلِ `foo.py` رویِ دیسک هست —
والسلام، هیچ اعلامِ اضافه‌ای لازم نیست. Rust این‌طور نیست. یک کریتِ Rust یک
**درختِ ماژول** است، و این درخت را خودت، صریح، با کلمه‌ی کلیدیِ `mod`
می‌سازی. هیچ فایلی به‌خودیِ‌خود یک ماژول نیست، مگر یک `mod` جایی اسمش را
ببرد.

و همین که پروژه به چند فایل تقسیم شد، یک سؤالِ تازه سر بر می‌آورد که تا
امروز اصلاً معنی نداشت: از این همه چیزی که نوشتی — تابع‌ها، فیلدها، خودِ
ماژول‌ها — کدام‌ها قرار است بقیه‌ی کدت (یا کدِ یک نفرِ دیگر، اگر این کریت را
به‌عنوانِ کتابخانه استفاده کند) ببیندشان؟ Rust جوابش را حدس نمی‌زند:
**پیش‌فرض، همه‌چیز خصوصی است.** هیچ قراردادِ نانوشته‌ای مثلِ آندرلاینِ اولِ
پایتون (که فقط *پیشنهاد* می‌کند «داخلی است»، ولی هیچ‌چیز جلویِ
استفاده‌اش را نمی‌گیرد) — اینجا خصوصی‌بودن یک خطایِ کامپایل است، نه یک
سرنخِ اسمی.

این دقیقاً همان مرزی است که
[۲.۳.۶](../../03-traits-and-generics/06-supertraits-blanket-impls-orphan-rule/README.fa.md)
یک بار دیگر، از یک درِ کاملاً متفاوت، به‌ات نشان داد: قاعده‌ی یتیم گفت یک
`impl Trait for Type` فقط وقتی مجاز است که صفت یا نوع در کریتِ خودت تعریف
شده باشد — یک مرزِ کریت، برایِ اینکه دو کریتِ بی‌ربط هرگز نتوانند رویِ هم
تصادف کنند. امروز همان مرزِ کریت را دوباره می‌بینی، این‌بار برایِ یک سؤالِ
خیلی معمولی‌تر: این کد اجازه دارد این فیلد را بخواند یا نه؟

این درس چهار چیز به‌ات می‌دهد: چطور یک ماژول را رویِ فایل‌ها پخش کنی، چهار
سطحِ دیدپذیری که Rust می‌شناسد، `pub use` برایِ نشان‌دادنِ یک APIِ تمیز رویِ
یک ساختارِ داخلیِ شلوغ، و ورک‌اسپیس — که، همین الان، از اولین خطِ این درس،
داخلِ یکی از آن‌ها هستی.

## مفهوم

### ماژول با `mod`: ساختنِ یک درخت

هر کریتِ واقعیِ Rust — نه فقط این مخزن، هر کریتی — کدش داخلِ یک درختِ ماژول
زندگی می‌کند. `mod` این درخت را می‌سازد، و می‌توانی هر چند لایه که بخواهی
توش تو بروی:

```rust
mod catalog {
    pub struct Anime {
        pub title: String,
    }

    pub mod series {
        pub struct Volume {
            pub number: u32,
        }
    }
}

let a = catalog::Anime { title: "Frieren".to_string() };
let v = catalog::series::Volume { number: 3 };
println!("{} — volume {}", a.title, v.number);
```

```text
Frieren — volume 3
```

`mod catalog { ... }` یک ماژول به اسمِ `catalog` تعریف می‌کند، دقیقاً همان‌جا
که نوشته شده — به این می‌گویند فرمِ **درون‌خطی**. رسیدن به چیزی داخلِ آن از
دو نقطه (`::`) عبور می‌کند: `catalog::Anime`، یا حتی دو لایه پایین‌تر،
`catalog::series::Volume`. هر `mod` تازه یک لایه‌ی دیگر به این مسیر اضافه
می‌کند — دقیقاً همان‌طور که پوشه‌های تودرتو یک مسیرِ فایل را طولانی‌تر
می‌کنند.

فرمِ درون‌خطی برایِ یک درسِ کوتاه خوب است — همه‌چیز تویِ یک فایل می‌ماند و
از بالا تا پایین می‌خوانیش. برایِ یک پروژه‌یِ واقعی نه؛ چند بند پایین‌تر
می‌بینی چرا و چطور همین درخت را می‌شکنی.

### دیدپذیری: خصوصی پیش‌فرض، `pub`، و `pub(crate)`

این همان قسمتی است که برنامه‌نویس‌هایِ پایتون را از همه بیشتر متعجب
می‌کند: **هر موجودیتی — struct، فیلد، تابع، حتی خودِ ماژول — به‌طورِ پیش‌فرض
فقط برایِ ماژولی که تعریفش کرده و بچه‌هایِ آن ماژول قابلِ نام‌بردن است، مگر
خلافش را بگویی.**

- **بدونِ تغییردهنده** — خصوصی. فقط داخلِ همان ماژول و ماژول‌هایِ تودرتویِ
  داخلش.
- **`pub`** — دیدنی برایِ هرکسی که می‌تواند خودِ ماژول را ببیند، شاملِ کدِ
  کاملاً بیرونِ این کریت (اگر خودِ مسیر هم قابلِ‌رسیدن باشد).
- **`pub(crate)`** — دیدنی از هر جایِ *همینِ کریت*، ولی **نه** برایِ یک
  کریتِ بیرونی که این را به‌عنوانِ کتابخانه وابستگی گرفته. این سطح تو کدِ
  واقعی خیلی رایج است: دقیقاً همان روشی که با آن می‌گویی «بقیه‌ی جاهایِ
  همین پایگاه‌کد می‌توانند ازش استفاده کنند، ولی این یک جزئیاتِ پیاده‌سازیِ
  داخلی است، نه بخشی از APIِ عمومیِ من.»

```rust
mod catalog {
    pub struct Anime {
        pub title: String,
        pub(crate) internal_rating: u8,
    }
    // ...
}

mod front_desk {
    use crate::catalog::Anime;

    pub fn describe(a: &Anime) -> String {
        format!("{} (internal rating {}/10)", a.title, a.internal_rating)
    }
}
```

`catalog` و `front_desk` خواهر و برادرند — هیچ‌کدام تویِ دیگری تودرتو نیست.
`front_desk` می‌تواند `title` را بخواند چون `pub` است. ولی
`internal_rating` را هم می‌تواند بخواند — با اینکه `front_desk` اصلاً بچه‌ی
`catalog` نیست! این دقیقاً همان چیزی است که `pub(crate)` را از خصوصیِ
معمولی جدا می‌کند: «هرجایِ این کریت»، نه «همین ماژول و بچه‌هایش». اجرایش
کن:

```sh
cargo run -p p2-07-01-modules-visibility-workspaces --example 01-inline-modules-and-visibility
```

```text
Frieren: Beyond Journey's End (internal rating 10/10)
```

و اگر `internal_rating` هیچ تغییردهنده‌ای نداشت — خصوصیِ کامل — همین خطِ
`front_desk` دیگر کامپایل نمی‌شد؛ خطایِ کاملش را در «خطاهایی که خواهی دید»
می‌بینی. برایِ یک کریتِ *بیرونی* هم که این را به‌عنوانِ کتابخانه وابستگی
گرفته، ماجرا فرق دارد: می‌تواند `title` را بخواند، ولی حتی نمی‌تواند اسمِ
`internal_rating` را بیاورد — کامپایلرِ آن کریتِ بیرونی هیچ‌وقت کدی که به
این فیلد اشاره کند تولید نمی‌کند، چون از دیدش این فیلد اصلاً وجود ندارد.
هیچ چکِ زمانِ‌اجرایی‌ای برایِ دور زدن نیست؛ همه‌چیز پیش از اجرایِ برنامه،
سرِ کامپایل، بسته می‌شود.

### `pub(super)`: دقیقاً یک پله بالاتر

یک سطحِ چهارم هست، برایِ وقتی که می‌خواهی چیزی را دقیقاً به‌اندازه‌یِ *یک
پله* بازتر از خصوصیِ معمولی کنی — نه به‌اندازه‌یِ کلِ کریت:

```rust
mod catalog {
    pub struct Anime {
        pub title: String,
    }

    pub mod series {
        use super::Anime;
        pub(super) fn shelf_code(a: &Anime) -> String {
            format!("SR-{}", a.title.len())
        }
    }
    pub fn shelf_label(a: &Anime) -> String {
        format!("{}: {}", a.title, series::shelf_code(a))
    }
}
```

`series` تویِ `catalog` تودرتوست. `shelf_code` داخلش `pub(super)` است —
یعنی «دیدنی برایِ ماژولِ والدِ مستقیمم، `catalog`، و هرجا خودِ `catalog`
دیده می‌شود؛ نه یک پله جلوتر.» `catalog::shelf_label` همان والد است، پس
می‌تواند `series::shelf_code` را صدا بزند:

```sh
cargo run -p p2-07-01-modules-visibility-workspaces --example 02-pub-super-nested-visibility
```

```text
Mushishi: SR-8
```

ولی کدِ ریشه‌یِ کریت — یک پله جلوتر از `catalog` — دیگر نمی‌تواند
`catalog::series::shelf_code` را صدا بزند، حتی با اینکه خودِ `series` هم
`pub` است و مسیرش کاملاً قابلِ‌نوشتن است. مسیر پیدا می‌شود؛ خودِ تابع پیدا
نمی‌شود. `examples/02-pub-super-nested-visibility.rs` دقیقاً همین خط را،
کامنت‌شده، تهِ `main` دارد — بازش کن و خودت ببین کدام‌یک را کامپایلر خصوصی
می‌داند.

```senpai-visual
{"kind":"concept","labels":["خصوصی: همین ماژول و بچه‌هایش","pub(super): یک پله بالاتر","pub(crate): کل همین کریت","pub: بیرونِ کریت هم"]}
```

چهار سطح، یکی روی دیگری: هرکدام دقیقاً همان چیزی را می‌بیند که سطحِ قبلی
می‌دید، به‌اضافه‌یِ کمی بیشتر.

### شکستن به فایل‌های واقعی: `mod foo;` کنارِ `foo.rs`

حالا برگرد به وعده‌یِ اولِ این بخش. `mod foo { ... }` همه‌چیز را همان‌جا
می‌نویسد. ولی می‌توانی بدنه را کلاً حذف کنی — فقط `mod foo;` — و Rust خودش
می‌رود دنبالِ محتوایش:

```text
src/
├── lib.rs        # mod catalog;
├── catalog.rs    # pub mod series;
└── catalog/
    └── series.rs
```

قاعده‌اش ساده است: وقتی فایلِ ریشه (`lib.rs`، یا `main.rs`، یا هر فایلِ
دیگری که خودِ کریت یا exampleاش از همان‌جا شروع می‌شود) می‌نویسد
`mod catalog;`، Rust دنبالِ `catalog.rs` — درست کنارِ خودش — می‌گردد. و اگر
`catalog.rs` خودش بنویسد `mod series;`، Rust این‌بار دنبالِ
`catalog/series.rs` می‌گردد: یک زیرپوشه به اسمِ ماژولِ والد، کنارِ همان
فایل.

```senpai-visual
{"kind":"concept","labels":["mod catalog; در lib.rs","دنبالِ catalog.rs می‌گردد","mod series; در catalog.rs","دنبالِ catalog/series.rs می‌گردد"]}
```

`examples/03-splitting-into-files/` همین درختِ `catalog`/`series` را که
بالاتر دیدی، عیناً، ولی این‌بار رویِ سه فایلِ واقعی، پیاده کرده — `main.rs`،
`catalog.rs`، و `catalog/series.rs`. بازش کن و از رویِ هم بخوانشان؛ اجرایش
کن:

```sh
cargo run -p p2-07-01-modules-visibility-workspaces --example 03-splitting-into-files
```

```text
Mushishi: SR-8
```

عینِ همان خروجیِ `02`. این تصادفی نیست — این کلِ نکته است. فرمِ درون‌خطی و
فرمِ چندفایلی دقیقاً یک درختِ یکسان می‌سازند؛ فقط چیدمانِ رویِ دیسک عوض شده،
نه معنایِ کد. تنها زمانی که واقعاً به فایلِ جدا نیاز داری وقتی است که یک
ماژول آن‌قدر بزرگ شده که دیگر تویِ یک صفحه جا نمی‌شود — و آن روز، این
همان کاری است که می‌کنی.

### `use` و صادرِ دوباره با `pub use`

`use` یک مسیر را می‌آورد تو اسکوپِ فعلی، تا مجبور نباشی هر بار کاملش را
بنویسی:

```rust
mod catalog {
    pub mod series {
        pub struct Anime {
            pub title: String,
        }
    }
}

mod front_desk {
    use crate::catalog::series::Anime;

    pub fn label(a: &Anime) -> String {
        format!("now showing: {}", a.title)
    }
}
```

اینجا `Anime` واقعاً سه لایه پایین است: `catalog::series::Anime`. `use`ی
که `front_desk` نوشته فقط یک میان‌بر است — چیزی صادر نمی‌کند، فقط داخلِ
همین ماژول تایپِ کمتری می‌خواهد.

`pub use` یک کارِ اضافه هم می‌کند: آن آیتم را رویِ یک مسیرِ تازه و
کم‌عمق‌تر **صادرِ دوباره** می‌کند:

```rust
pub use catalog::series::Anime;
```

حالا هرکسی — از داخلِ همین کریت یا از یک کریتِ بیرونی که این را وابستگی
گرفته — می‌تواند مستقیم بنویسد `Anime` (یا از بیرون، `این_کریت::Anime`)،
بدونِ اینکه اصلاً بداند سه لایه پایین‌تر تعریف شده. اجرایش کن:

```sh
cargo run -p p2-07-01-modules-visibility-workspaces --example 04-use-and-pub-use-reexport
```

```text
now showing: Frieren
```

نکته‌یِ مهم: این دو مسیر — `Anime`ِ صادرشده و `catalog::series::Anime`ِ
اصلی — یک `Anime` را می‌سازند، نه دو تا. `pub use` هیچ کپی‌ای نمی‌سازد، فقط
یک درِ تازه به همان یک اتاق باز می‌کند. `examples/04` دقیقاً همین را
اثبات می‌کند: یک `Anime` از راهِ مسیرِ صادرشده ساخته می‌شود، بعد به تابعی
داده می‌شود که مسیرِ داخلی را `use` کرده — و کامپایل می‌شود، چون هردو یک
نوعِ عیناً یکسان‌اند.

این دقیقاً همان الگویی است که کریت‌هایِ واقعی برایِ نشان‌دادنِ یک APIِ تمیز و
تخت، رویِ یک ساختارِ داخلیِ عمیق و تودرتو، استفاده می‌کنند: اگر فردا
`catalog::series` را به دو زیرماژولِ دیگر بشکنی، همان یک خطِ `pub use` را
عوض می‌کنی — کدِ هیچ فراخواننده‌ای که `Anime` را از مسیرِ کوتاه صدا می‌زده
نمی‌شکند.

### ورک‌اسپیس‌ها: همین مخزن، یک نمونه‌یِ واقعی

یک **ورک‌اسپیسِ Cargo (Cargo workspace)** چند کریت است که یک `Cargo.lock` و
یک پوشه‌یِ خروجیِ `target/` مشترک دارند — یک وابستگیِ مشترک بینشان فقط یک‌بار
کامپایل می‌شود، نه یک‌بار به‌ازایِ هر کریت.

نیازی نیست یکی بسازی تا ببینی چطور کار می‌کند — همین الان داخلِ یکی از
بزرگ‌ترین نمونه‌هایی هستی که می‌شود پیدا کرد. ریشه‌یِ همین مخزن یک
`Cargo.toml` دارد که خودش را یک ورک‌اسپیس اعلام می‌کند:

```toml
[workspace]
resolver = "2"
members = [
    "web-ui",
    "tools/lesson-lint",
    "phase0-setup/03-hello-rust",
    # ...
    "phase1-fundamentals/*/*",
    "phase2-intermediate/*/*",
    # ...
]
```

هر عضوِ `members` یک کریتِ جداگانه است — همین درسی که الان تویش هستی،
`p2-07-01-modules-visibility-workspaces`، یکی از همین‌هاست، از راهِ الگویِ
`"phase2-intermediate/*/*"`. ده‌ها کریتِ کوچک، یک `Cargo.lock`، یک
`target/`. برایِ همین وقتی درسی که `tokio` می‌خواهد را کامپایل می‌کنی،
`tokio` از صفر دوباره ساخته نمی‌شود — از همان کامپایلِ اولش استفاده
می‌شود.

یک واقعیتِ عجیب و کاملاً واقعی، عیناً از همین فایل: کامنتِ بالایِ همین
لیست می‌گوید یک الگویِ عضو که به صفر پوشه بخورد، خطایِ سختِ خودِ Cargo است،
نه یک بی‌عملیِ ساکت — یعنی الگویِ `"phase2-intermediate/*/*"` را نمی‌شد
اضافه کرد مگر روزی که واقعاً یک درسِ فازِ ۲ رویِ دیسک وجود داشته باشد.

یک نکته‌یِ آخر، که همین درس هم دارد بهش تکیه می‌کند: `solution/`ِ هر درس
هم یک کریت است، ولی عمداً عضوِ همین ورک‌اسپیس *نیست* — جدولِ `[workspace]`ِ
خالیِ خودش را دارد (تویِ `solution/Cargo.toml`ِ همینِ درس می‌بینیش) تا Cargo
آن را یک ریشه‌یِ کاملاً مستقل بداند، نه بخشی از این یکی.

### یادآوری: مرزِ کریت، همان‌جایی که ۲.۳.۶ هم دیدی

مرزِ کریت، امروز دومین‌بار است که سر راهت سبز می‌شود.
[۲.۳.۶](../../03-traits-and-generics/06-supertraits-blanket-impls-orphan-rule/README.fa.md)
قاعده‌یِ یتیم را یادت داد: می‌شود یک صفت را برایِ یک نوع پیاده‌سازی کرد فقط
اگر صفت یا نوع در کریتِ خودت تعریف شده باشد — یک مرزِ کریت، رویِ
*پیاده‌سازیِ صفت‌ها*. `pub(crate)` همان مرز است، رویِ *دیدنِ آیتم‌ها*: نه یک
قاعده‌یِ تازه، همان یک خط — «کریتِ من در برابرِ بقیه‌یِ دنیا» — این‌بار
به‌کار رفته برایِ یک سؤالِ کاملاً متفاوت.

## خطاهایی که خواهی دید

### `E0616` — یک فیلدِ خصوصی، از بیرونِ ماژولش

```text
error[E0616]: field `internal_rating` of struct `Anime` is private
  --> phase2-intermediate\07-project-structure-and-testing\01-modules-visibility-workspaces\examples\05-private-field-is-inaccessible-broken.rs:28:22
   |
28 |     println!("{}", a.internal_rating);
   |                      ^^^^^^^^^^^^^^^ private field

For more information about this error, try `rustc --explain E0616`.
```

**کامپایلر به چه اعتراض دارد:** `internal_rating` تویِ این نسخه هیچ
تغییردهنده‌ای ندارد — خصوصیِ کامل. دیدپذیریِ خصوصی یعنی «فقط همان ماژولی که
تعریفش کرده، و بچه‌هایِ آن ماژول.» `main` تویِ همین فایل، بیرونِ `catalog`
نوشته شده — نه خودِ `catalog`، نه بچه‌اش. پس حتی با اینکه `main` تویِ همین
کریت است، اصلاً اسمِ `internal_rating` را نمی‌تواند بیاورد.

**راه‌حل:** یکی از این دو — یا برش‌گردانش به `pub(crate)`، دقیقاً همان چیزی
که `01-inline-modules-and-visibility.rs` دارد:

```rust
pub(crate) internal_rating: u8,
```

یا، اگر نمی‌خواهی هیچ‌جایِ دیگرِ همین کریت هم مستقیم به عددِ خام دسترسی
داشته باشد، یک متدِ خواندنیِ عمومی اضافه کن:

```rust
pub fn internal_rating(&self) -> u8 {
    self.internal_rating
}
```

**چرا این راه‌حل است:** راهِ اول دقیقاً سؤالِ این درس را جواب می‌دهد — `main`
تویِ همینِ کریت است، پس `pub(crate)` برایِ دیدنش کافی است، بدونِ اینکه فیلد
را برایِ کریت‌هایِ بیرونی هم باز کنی. راهِ دوم یک قدم محافظه‌کارانه‌تر است:
فیلد همچنان خصوصیِ کامل می‌ماند، پس هیچ کدی — حتی داخلِ همین کریت — دیگر
نمی‌تواند مستقیم چیزی مثلِ `a.internal_rating = 99` بنویسد؛ فقط از پشتِ متد
می‌خواند. کدام‌یک درست است بستگی دارد به این که چقدر می‌خواهی این عدد را از
دستکاریِ مستقیم محافظت کنی؛ هردو، «خصوصیِ کامل»ی که همین خطا را داد را
پشتِ سر می‌گذارند.

## تمرین

### گرم‌کردن

<details>
<summary>این کامپایل می‌شود؟</summary>

```rust
mod a {
    fn secret() -> i32 {
        7
    }
}

mod b {
    fn try_it() {
        println!("{}", crate::a::secret());
    }
}
```

</details>

<details>
<summary>پاسخ</summary>

نه — `E0603`، «function `secret` is private». `secret` هیچ تغییردهنده‌ای
ندارد، پس فقط داخلِ `a` (و بچه‌هایِ `a`) دیدنی است. `b` یک خواهرِ `a` است،
نه بچه‌اش.

</details>

<details>
<summary>با همان دو ماژولِ بالا، اگر <code>secret</code> را <code>pub(crate)</code> کنی، آن‌وقت <code>b</code> می‌تواند صدایش بزند؟</summary>

</details>

<details>
<summary>پاسخ</summary>

بله. `pub(crate)` یعنی «هرجایِ این کریت» — و `b`، مثلِ `a`، تویِ همین کریت
است. رابطه‌یِ خواهر-برادریِ `a` و `b` دیگر مهم نیست.

</details>

<details>
<summary>اگر <code>catalog</code> خودش هیچ <code>pub</code>ی جلویِ <code>mod catalog</code> نداشته باشد، آیا <code>main</code> که تویِ همان فایل و در ریشه‌یِ کریت نوشته شده، هنوز می‌تواند <code>catalog::hello()</code> را صدا بزند (به‌شرطی که خودِ <code>hello</code> <code>pub</code> باشد)؟</summary>

</details>

<details>
<summary>پاسخ</summary>

بله. خصوصی‌بودنِ `catalog` یعنی «فقط دیدنی برایِ ماژولی که `catalog` را
تعریف کرده و بچه‌هایِ آن ماژول» — و آن ماژول همان ریشه‌یِ کریت است، جایی که
`main` هم نوشته شده. `catalog` از بیرونِ کریت واقعاً پنهان می‌شود؛ از
داخلِ همین کریت، نه.

</details>

<details>
<summary>بعد از <code>pub use catalog::series::Anime;</code>، آیا <code>catalog::series::Anime</code> هنوز هم کار می‌کند، یا فقط مسیرِ کوتاه؟</summary>

</details>

<details>
<summary>پاسخ</summary>

هردو کار می‌کنند. `pub use` مسیرِ تازه‌ای *اضافه* می‌کند؛ مسیرِ اصلی را از
بین نمی‌برد. یک تعریف، حالا از دو در قابلِ‌رسیدن.

</details>

### تعمیر

`examples/05-private-field-is-inaccessible-broken.rs` را **دو** جور درست
کن:

۱. با برگرداندنِ `internal_rating` به `pub(crate)`.
۲. بدونِ تغییرِ دیدپذیریِ فیلد — به‌جایش یک متدِ عمومیِ `internal_rating(&self) -> u8`
   اضافه کن که مقدار را برمی‌گرداند، و `main` را طوری عوض کن که به‌جایِ
   خواندنِ مستقیمِ فیلد، همین متد را صدا بزند.

بعد یک جمله بنویس: کدام‌یک بیشترِ اوقات تو یک کتابخانه‌یِ واقعی می‌بینی، و
چرا؟

### پیاده‌سازی

سه تابع در `src/lib.rs`:

```sh
cargo test -p p2-07-01-modules-visibility-workspaces
```

`Anime::public_rating_band` همان کاری را می‌کند که بالاتر دیدی — یک باندِ

### بساز

یک زیرماژولِ دومِ خودت به `catalog` اضافه کن — هر اسم، هر ایده (نقد، برچسب،
استودیو، هرچه دلت خواست). دستِ‌کم یک آیتمِ `pub` توش بگذار و یک آیتمِ دیگر
که عمداً `pub` نیست. بعد، بالایِ هرکدام، در یک کامنتِ مستندات، یک جمله
بنویس که توضیح بدهد چرا همان سطحِ دیدپذیری را برایش انتخاب کردی.

### چالش (اختیاری)

**بخشِ یک.** ریشه‌یِ همین مخزن را باز کن —
[`Cargo.toml`](../../../Cargo.toml). خطِ `"phase2-intermediate/*/*"` را
تویِ `members` پیدا کن، و کامنتی که چند خط پایین‌ترش توضیح می‌دهد چرا این
الگو نمی‌توانست از همان اول، پیش از اینکه اولین درسِ فازِ ۲ واقعاً رویِ
دیسک باشد، اضافه شود. آن قاعده را با یک جمله بازگو کن.

**بخشِ دو.** (این یکی جلوتر را نگاه می‌کند، و می‌داند که دارد این کار را
می‌کند.) یک فایلِ آزمایشی، فقط برایِ خودت، بساز: یک پوشه‌یِ `tests/` کنارِ
`src/`ِ همینِ درس، با یک تابعِ `#[test]` که `use p2_07_01_modules_visibility_workspaces::Anime;`
می‌کند و یک `Anime` می‌سازد. کامپایل می‌شود. حالا همان تابع را طوری عوض کن
که به‌جایِ `Anime`، به مسیرِ داخلیِ `catalog` برسد. کامپایل نمی‌شود — حتی با
اینکه خودت، همین چند دقیقه پیش، دیدی که `main`ِ همین کریت به همان مسیر
می‌رسید! (پاکش کن؛ لازم نیست چیزی از اینجا commit شود.) دقیقاً همین تضادِ
عجیب، موضوعِ تمام‌وکمالِ درسِ بعدی است:

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| ماژول (`mod`) | واحدِ سازمان‌دهیِ کد؛ درون‌خطی (`mod foo { ... }`) یا فایلی (`mod foo;`) | هر پروژه‌ای که از یک فایل بزرگ‌تر شود |
| خصوصیِ پیش‌فرض | دیدنی فقط برایِ ماژولِ تعریف‌کننده و بچه‌هایش | حالتِ شروع برایِ هر آیتم |
| `pub` | دیدنی هرجا خودِ ماژول دیده شود، شاملِ بیرونِ کریت | APIِ عمومی |
| `pub(crate)` | دیدنی هرجایِ همین کریت، نه بیرونش | جزئیاتِ پیاده‌سازیِ به‌اشتراک‌گذاشته‌شده |
| `pub(super)` | دیدنی فقط برایِ ماژولِ والدِ مستقیم | کاری که فقط ماژولِ والد باید بداند |
| `use` | میان‌بر زدنِ یک مسیر، بدونِ صادرِ چیزی | کوتاه‌کردنِ تایپ در همان ماژول |
| صادرِ دوباره (`pub use`) | نشان‌دادنِ یک آیتم رویِ یک مسیرِ کم‌عمق‌تر، بدونِ جابه‌جایی | APIِ عمومیِ تمیز رویِ ساختارِ داخلیِ شلوغ |
| ورک‌اسپیس (workspace) | چند کریت، یک `Cargo.lock`، یک `target/` | کریتی که همین الان تویش هستی |
| `E0616` | فیلدی خصوصی، از بیرونِ ماژولش خوانده شده | `pub(crate)` بگذار، یا یک متدِ خواننده بنویس |

### الان می‌دانی

- `mod` یک درختِ ماژول می‌سازد؛ فرمِ درون‌خطی و فرمِ فایلی (`mod foo;` کنارِ
  `foo.rs`) دقیقاً یک درختِ یکسان تولید می‌کنند.
- دیدپذیری چهار پله دارد: خصوصیِ پیش‌فرض (همین ماژول + بچه‌ها)، `pub(super)`
  (+ یک پله بالاتر)، `pub(crate)` (+ کلِ کریت)، `pub` (+ بیرونِ کریت هم).
- یک آیتمِ خصوصیِ تعریف‌شده در ریشه‌یِ کریت، از هرجایِ *همان کریت* دیدنی
  است — خصوصی‌بودن مرزِ کریت را می‌بندد، نه هر جایِ داخلِ آن را.
- `pub use` یک آیتم را رویِ یک مسیرِ تازه صادر می‌کند، بدونِ آنکه مسیرِ
  اصلی از کار بیفتد یا نوعِ دومی ساخته شود.
- یک ورک‌اسپیس چند کریت را رویِ یک `Cargo.lock` و یک `target/` مشترک نگه
  می‌دارد؛ همین مخزن، از اولین خطِ ریشه‌اش، یکی از همین‌هاست.

### بعداً کامل‌تر می‌بینی

- **تستِ واحد در برابرِ تستِ یکپارچگی — که چرا دقیقاً به همین مرزِ دیدپذیری
  تکیه دارد** —
  [۲.۷.۲ — تستِ واحد، یکپارچه و مستندات](../02-unit-integration-doc-tests/README.fa.md)

### می‌توانی توضیح بدهی؟

- چرا `pub(crate)` را از خصوصیِ معمولی جدا می‌کند، وقتی هر دو آیتم تویِ
  همان یک کریت‌اند؟
- `pub(super)` دقیقاً چقدر دیدپذیری اضافه می‌کند — و چرا «یک پله» دقیق‌تر
  از «همه‌جایِ بالاتر» است؟
- `mod foo;` را، بدونِ نگاه‌کردن به این درس، برایِ کسی توضیح بده که هنوز
  نمی‌داند Rust کجا دنبالِ فایلش می‌گردد.
- `pub use` چه چیزی را جابه‌جا می‌کند، و چه چیزی را جابه‌جا نمی‌کند؟
- چرا ریشه‌یِ این مخزن یک ورک‌اسپیس است، و اگر نبود، چه چیزی کندتر می‌شد؟
- قاعده‌ی یتیمِ ۲.۳.۶ و `pub(crate)`ِ امروز، هر دو رویِ کدام یک ایده تکیه
  دارند؟
