# ۰۶.۲ — تست‌های واحد، تست‌های یکپارچگی، و تست‌های مستندات (Doc tests)

از فاز ۰ تا الان ده‌ها بلوکِ `#[cfg(test)] mod tests` نوشتی. این درس برای این الگوی تستی اسم می‌ذاره، اون رو با دو الگوی دیگه‌ی تستی مقایسه می‌کنه، و از قصد طوری طراحی شده که بتونی تفاوتشون رو تو عمل *حس کنی*، نه اینکه فقط راجع‌بهشون بخونی.

## تست‌های واحد (Unit tests): داخل خود کریت، تواناییِ دیدنِ آیتم‌های خصوصی (private) رو دارن

هر بلوکِ `#[cfg(test)] mod tests { ... }` که تا الان نوشتی در واقع یه **تست واحد (unit test)** به حساب میاد — این تست‌ها به عنوان بخشی از همون کریتی (crate) که قراره تستش کنن کامپایل می‌شن (اون صفتِ `#[cfg(test)]` معنیش همینه که "این بلوک رو فقط وقتی کامپایل کن که داریم برای `cargo test` بیلد می‌گیریم، نه برای یه بیلد معمولی"). دقیقاً به خاطر اینکه این بلوک تو همون کریتِ *اصلی* قرار داره، تست‌های واحد می‌تونن به موجودیت‌های خصوصی (اونایی که `pub` نیستن) هم دسترسی پیدا کنن — درست همون‌طوری که تو درس قبلی دیدی که فیلدِ `pub(crate)` برای هر کدی تو هر جای کریت قابل دیدن بود. تو این درس فایل `src/lib.rs` یه تابعِ کمکی و کمکی‌کننده‌ی (helper function) کاملاً خصوصی داره، و تست واحدش مستقیماً همون تابع رو صدا می‌زنه.

## تست‌های یکپارچگی (Integration tests): یه کریتِ کاملاً مجزا، دسترسی فقط به APIِ عمومی

هر چیزی که تو سطحِ اصلی زیر پوشه‌ی `/tests` قرار می‌گیره، به عنوان یه **کریتِ جداگانه و مستقل** کامپایل می‌شه، که وابستگیش (dependency) به کتابخونه‌ی تو دقیقاً از همون جنسیه که یه کاربر خارجی موقع استفاده از کریت تو تجربه می‌کنه — یعنی فقط با `;use your_crate::whatever` کار می‌کنه و هیچ‌چیز اضافه‌تری نداره. به همین دلیله که تست‌های یکپارچگی *فقط و فقط* به آیتم‌های `pub` دسترسی دارن: اونا برخلاف تست‌های واحد که ساکنِ خودِ کریت هستن، هیچ دسترسی ویژه‌ای (special access) ندارن. این پوشه دقیقاً جای درستی برای تست کردنِ *قراردادِ* عمومیِ (public contract) کریتِ توئه — یعنی تستِ "آیا این کریت از دیدِ یه آدمِ بیرونی درست کار می‌کنه یا نه" — در نقطه‌ی مقابلِ تست‌های واحد، که می‌تونن برن تو دل‌وروده‌ی کار و جزئیات پیاده‌سازی داخلی رو چک کنن.

فایل `tests/conversion_test.rs` تو این درس، دقیقاً همون تابعِ عمومی‌ای رو تست می‌کنه که تست‌های واحدِ تو فایل `src/lib.rs` می‌کنن، اما اینجا به طور عمدی **نمی‌تونه** اون تابعِ کمکیِ خصوصی رو صدا بزنه — خودت امتحانش کن تا خطای دقیقِ کامپایلر رو با چشم خودت ببینی (سؤال مرور).

## تست‌های مستندات (Doc tests): مثال‌هایی تو مستندات که تا ابد باید درست بمونن

```rust
/// Converts Celsius to Fahrenheit.
///
/// # Examples
///
/// ```
/// # use p2_06_02_unit_integration_doc_tests::celsius_to_fahrenheit;
/// assert_eq!(celsius_to_fahrenheit(0.0), 32.0);
/// ```
pub fn celsius_to_fahrenheit(c: f64) -> f64 {
    // ...
}
```

هر بلوک کدی که با ` ```rust ` (یا فقط ` ``` ` خالی، که به طور پیش‌فرض همون Rust رو در نظر می‌گیره) داخلِ یه کامنت مستندات که با `///` شروع می‌شه نوشته بشه، توسط دستورِ `cargo test` هم کامپایل می‌شه و هم به عنوان یه تست **اجرا می‌شه**. این یه تضمینِ کاملاً متفاوت با یه کامنتِ معمولیه: یه مثال که به صورت متنی تو یه کامنت معمولی نوشته می‌شه، ممکنه همون لحظه‌ای که رفتار تابع تغییر می‌کنه بی‌سروصدا قدیمی (stale) و غلط بشه؛ اما یه تست مستندات (doc test) تو همون لحظه‌ای که همچین اتفاقی بیفته، *عملیات بیلد (build) رو با خطا متوقف می‌کنه*. خطوطی از این بلوک که با `# ` شروع می‌شن (مثل اون خطِ `use` تو مثالِ بالا)، موقع تست کامپایل و اجرا می‌شن اما از داخلِ مستنداتِ *نهایی و رندرشده (rendered)* مخفی می‌مونن — این ترفند برای قایم کردن کدهای اضافه‌ی مربوط به راه‌اندازی (setup noise مثل importها یا کدهای تکراریِ boilerplate) که خواننده‌ی مستندات نیازی به دیدنشون برای درکِ مثال نداره، استفاده می‌شه.

## وظیفه‌ی تو

هر دو تابع رو تو فایل `src/lib.rs` پیاده‌سازی کن. اون تستِ مستنداتی که بالا می‌بینی از قبل درسته و کامله — به محض اینکه تابعِ `celsius_to_fahrenheit` رو پیاده‌سازی کنی، به طور خودکار به عنوان بخشی از دستور `cargo test` پاس می‌شه.

## قدم بعدی

اول اجرا کن: `cargo test -p p2-06-02-unit-integration-doc-tests` (هر سه نوع تست با هم اجرا می‌شن، ولی تو خروجی برچسب‌هاشون جداست — مخصوصاً دنبال بخش "Doc-tests" بگرد). بعد سؤال‌های مرور رو بخون و جواب بده، و در آخر برو سراغ `solution/SOLUTION.md`.
