# چک‌پوینت

1. اون خطِ `(...) ,assert!(mid <= len` رو کلاً پاک کن و تابع رو به این شکل صدا بزن: `(split_at_mut_demo(&mut [1, 2, 3], 10`. این‌بار دیگه پنیک (panic) نمی‌کنه — تو واقعیت چه اتفاقی می‌افته؟ (اگه با اجرای این کد راحت نیستی لازم نیست حتماً اجراش کنی — فقط با استدلال ذهنی بررسیش کن: عبارتِ `(ptr.add(mid` داره ۱۰ تا عنصر روی یه آرایه ۳ عنصری میره جلو (past). آیا خودِ این عملیات به تنهایی unsafe هستش، یا فقط زمانی «اشتباه» می‌شه که تو بخوای از روی اون پوینترِ ساخته‌شده داده رو بخونی؟)
2. کامنتِ `SAFETY: //` رو دقیقاً بالای سر بلوک `unsafe` پیدا کن. این کامنت داره دقیقاً چه ادعایی (claim) می‌کنه، و وظیفه‌ی حفظِ درستی این ادعا گردن کیه — گردنِ کامپایلر یا تو؟ اگه یه نفر بعداً بیاد و اون `assert`ِ بالایی رو از `mid <= len` به یه چیزِ دیگه‌ای که یه خرده اشتباه و نامحسوس (subtly wrong) باشه تغییر بده، تکلیفِ اون مسئولیت چی می‌شه؟
3. از روی حافظه، اون پنج تا چیزی رو که `unsafe` اجازه‌ی استفاده ازشون رو می‌ده (unlock می‌کنه) نام ببر. کدوم یکی از اونا تو تمرینِ این درس استفاده شده؟
4. چرا بررسی‌کننده‌ی کامپایلر (borrow checker) خودش نمی‌تونه بررسی (verify) کنه که محدوده‌ی `[mid..]slice mut&` و `[..mid]slice mut&` هیچ هم‌پوشانی‌ای (non-overlapping) ندارن، با وجود اینکه این موضوع برای تویی که داری کد رو می‌خونی خیلی بدیهی و واضحه؟ کامپایلر برای اینکه خودش اینو بفهمه باید به چه چیزایی دسترسی و علم داشته باشه که الان نداره؟
