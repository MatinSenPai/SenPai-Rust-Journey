# ۰۶.۳ — بررسی اجمالیِ Rustِ ناایمن (`unsafe`)

این یه معرفی بااحتیاط و حساب‌شده‌ست، نه یه چیز ترسناک. اکثر کدهای زبان Rust — یعنی تک‌تک چیزایی که تا الان تو این مخزن (repo) نوشتی — اصلاً و ابداً هیچ نیازی به `unsafe` ندارن. این درس قراره از کارایی که این کلمه‌ی کلیدی واقعاً انجام میده رفعِ ابهام کنه (demystify)، تا دیگه برات یه پرچم قرمزِ مرموز و مبهم نباشه و تبدیل بشه به یه ابزارِ محدود و مشخص که درکش می‌کنی.

## کلمه‌ی `unsafe` به هیچ‌وجه بررسی‌کننده‌ی کامپایلر (borrow checker) رو خاموش نمی‌کنه

این رایج‌ترین و بزرگترین سوءتفاهمیه که وجود داره. داخلِ یه بلوکِ `unsafe`، تمامِ مفاهیم مالکیت، قرض‌گرفتن و طول‌عمرها (lifetimes) **همچنان به طور کامل و سفت‌وسخت** توسط کامپایلر اِعمال می‌شن. دستور `unsafe` فقط و فقط پنج تا عملیاتِ اضافه‌تر رو برات باز (unlock) می‌کنه، و نه هیچ‌چیز دیگه‌ای رو:

1. نشان‌زدایی کردن (Dereferencing) از یه **پوینتر خام (raw pointer)** (یعنی نوعِ `T* const` / `T* mut`).
2. فراخوانی کردنِ یه `unsafe fn` (که شامل توابع زبان C از طریق FFI هم می‌شه).
3. دسترسی پیدا کردن به یه متغیر تغییرپذیر از نوعِ `static`، یا تغییر دادنش.
4. پیاده‌سازی کردنِ یه `unsafe trait`.
5. دسترسی پیدا کردن به فیلدهای یه نوعِ `union`.

لیست کاملاً همینه که دیدی. تمامِ قوانین دیگه‌ی زبان Rust همچنان داخل بلوک `} ... { unsafe` پابرجا هستن — تو از دنیای امنِ زبان Rust خارج نشدی، فقط یه دسته کلیدِ اضافه‌ی کوچیک بهت داده شده، به اضافه‌ی تمامِ مسئولیتِ شخصی برای اینکه ازشون درست استفاده کنی. کامپایلر تو این بلوک فقط دست از بررسیِ اون قانونِ خاص (invariant) که هر کدوم از این پنج تا عملیات بهش تکیه می‌کنن برمی‌داره؛ اما بررسی هیچ‌چیز دیگه‌ای رو متوقف نمی‌کنه.

## پوینترهای خام (Raw pointers): نوعِ `T* const` و `T* mut`

برخلاف نوعِ `T&`/`mut T&`، پوینترهای خام این ویژگی‌ها رو دارن:
- می‌تونن null باشن، می‌تونن آویزون (dangling) باشن، یا حتی تراز (unaligned) نباشن — وقتی که تو یکی از اونا رو *می‌سازی*، کامپایلر هیچ‌کدوم از اینا رو چک نمی‌کنه (فقط وقتی که می‌خوای ازش *نشان‌زدایی* کنی این کار رو می‌کنه، اونم صرفاً به این معنی که نشان‌زدایی کردن از یه حافظه‌ی نامعتبر یه رفتار تعریف‌نشده (undefined behavior) هستش که الان خودِ تو مسئولی تا ازش جلوگیری کنی).
- تابعِ قانون «یا نام مستعار، یا تغییرپذیری (aliasing XOR mutability)» نیستن — تو می‌تونی به طور همزمان چندین و چند پوینترِ `T* mut` به یه داده‌ی واحد داشته باشی. اصلاً دلیلِ اصلی به وجود اومدنِ پوینترهای خام همینه: یه سری ساختار داده‌ها تو واقعیت برای ساختن کاملاً ایمن هستن، اما بیانِ این ایمنی از طریق قوانین سفت‌وسختِ فعلیِ borrow checker کلاً غیرممکنه.
- فقط و فقط داخل بلوکِ `unsafe` می‌تونن *نشان‌زدایی (dereferenced)* بشن — ساختنشون همیشه یه عملیاتِ امن و safe محسوب می‌شه؛ اما کلمه‌ی کلیدی `unsafe` و خطرِ داستان دقیقاً همون نقطه‌ایه که می‌خوای از طریقشون داده‌ای رو بخونی یا تغییر بدی.

## تمرینِ درس: تابعِ `split_at_mut`

این یه مثال کاملاً کلاسیک و استاندارد از وضعیتِ «کدهای امنِ (safe) Rust واقعاً توانایی بیان این کار رو ندارن، با وجود اینکه این کار تو عمل کاملاً ایمنه» هستش: نصف کردن یه بُرشِ (slice) تغییرپذیر به دو تا نیمه‌ی مستقل و تغییرپذیر.

```rust
fn split_at_mut_naive<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    (&mut slice[..mid], &mut slice[mid..])  // کامپایل نمی‌شه!
}
```

این کد کامپایل نمی‌شه — می‌گه داری همزمان دو بار از `slice` قرضِ `mut&` می‌گیری، و borrow checker هم هیچ راهی نداره که ببینه محدوده‌ی `[mid..]` و `[..mid]` اثبات‌شدنیَن و هرگز با هم هم‌پوشانی ندارن؛ اون فقط داره «دو تا قرضِ تغییرپذیر از یه متغیرِ یکسان» رو می‌بینه. اما تو، یعنی برنامه‌نویسِ کد، می‌دونی که این دو تا کاملاً از هم مجزا و بدونِ هم‌پوشانی (disjoint) هستن. پوینترهای خام همون روشی هستن که باهاش می‌تونی به کامپایلر بگی «اینجا رو به من اعتماد کن» — اونم فقط برای همین یه عملیاتِ کوچیک — بدون اینکه مجبور بشی ایمنیِ کدهات رو تو بقیه‌ی جاها قربانی کنی.

## وظیفه‌ی تو

تابعِ `split_at_mut_demo` رو تو فایل `src/lib.rs` با استفاده از پوینترهای خام پیاده‌سازی کن — این تابع در واقع یه نسخه‌ی ساده‌شده از متد `std::slice::split_at_mut` هستش (یه تابع واقعی تو کتابخونه‌ی استاندارد که دقیقاً با همین روش پیاده‌سازی شده).
