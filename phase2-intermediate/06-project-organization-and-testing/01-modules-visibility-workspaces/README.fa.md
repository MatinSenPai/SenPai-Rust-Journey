# ۰۶.۱ — ماژول‌ها، سطح دسترسی (visibility) و Workspaceها

## کلمه‌ی کلیدی `mod`: سازمان‌دهی کدها به شکل یه درخت

تو پایتون، هر فایلِ `.py` به طور خودکار خودش یه ماژوله — دستور `import foo` خیلی راحت کار می‌کنه چون تو هاردِ سیستمت فایلی به اسم `foo.py` وجود داره، والسلام. اما تو Rust هیچ تناظر خودکاری اینطوری وجود نداره. یه کریت (crate) تو زبان Rust در واقع یه **درخت از ماژول‌هاست**، و تو این درخت رو به صورت صریح با استفاده از کلمه‌ی کلیدی `mod` می‌سازی:

```rust
mod catalog {
    pub struct Anime {
        pub title: String,
    }
}

let a = catalog::Anime { title: "Frieren".to_string() };
```

دستورِ `mod catalog { ... }` میاد یه ماژول به اسم `catalog` رو دقیقاً همونجا (inline) تعریف می‌کنه. اما برای پروژه‌هایی که از این فراتر می‌رن، استایل خیلی رایج‌تر اینه که بنویسی `;mod catalog` (بدون بدنه) تو فایل `src/lib.rs`، و در کنارش یه فایل مجزا به اسم `src/catalog.rs` (یا `src/catalog/mod.rs`) بسازی که محتویات اصلی توش قرار می‌گیره — زبان Rust خودش می‌گرده و اون فایل رو بر اساس اسم ماژول پیدا می‌کنه. هر دوی این روش‌ها دقیقاً و مو به مو یه درختِ یکسان رو تولید می‌کنن؛ این درس برای اینکه همه‌چی تو یه فایل بمونه و بتونی از بالا تا پایین رو راحت بخونی از روشِ درون‌خطی (inline) استفاده کرده، اما بدون که تو دنیای واقعی به محض اینکه یه ماژول بزرگ می‌شه تو اونو می‌شکونی و می‌ذاریش تو یه فایل مجزا.

## سطح دسترسی: پیش‌فرض، روی حالت خصوصی (private) ئه

این دقیقاً همون قسمتیه که برنامه‌نویس‌های پایتون رو از همه بیشتر متعجب می‌کنه: **هر موجودیتی (از جمله struct، فیلد، تابع، یا خود ماژول) به طور پیش‌فرض فقط برای ماژولی که توش تعریف شده و تمام بچه‌های اون ماژول (descendants) قابل دسترسی و خصوصیه، مگه اینکه تو خلافش رو بگی.** پایتون به قراردادها تکیه می‌کنه (مثلاً یه `_` اول اسم می‌ذارن که یعنی *پیشنهاد می‌کنم* اینو یه چیز داخلی در نظر بگیری، اما هیچ‌چیزی واقعاً جلوت رو برای ایمپورت کردنش نمی‌گیره)؛ در حالی که Rust حریم خصوصی رو به زور و با خطای کامپایل اعمال می‌کنه.

- بدون تغییردهنده (modifier) — خصوصی (private). فقط تو همون ماژولی که تعریف شده و بچه‌های اون ماژول دیده می‌شه.
- `pub` — برای هر کسی که می‌تونه خودِ ماژول رو ببینه قابله دسترسیه، که شامل کدهای کاملاً خارج از این کریت هم می‌شه (البته به شرطی که خود اون ماژول قابل دسترسی (reachable) باشه، مثلاً از ریشه‌ی کریت re-export شده باشه).
- `pub(crate)` — از هر جای *داخل همین کریتِ فعلی* قابل دسترسیه، اما برای کریت‌های خارجیِ دیگه‌ای که می‌خوان از این کریت به عنوان یه کتابخونه استفاده کنن (وابستگیِ بیرونی) **قابل دیدن نیست**. این سطح از دسترسی تو کدهای واقعی خیلی خیلی رایجه: این دقیقاً همون روشیه که باهاش می‌گی «بقیه‌ی جاهای همین پایگاه کدِ (codebase) خودم می‌تونن ازش استفاده کنن، اما این صرفاً یه جزئیات پیاده‌سازیِ داخلیه، نه بخشی از APIِ عمومیِ من که بخوام به بیرون بدمش.»

```rust
mod catalog {
    pub struct Anime {
        pub title: String,           // فیلد عمومی (public)
        pub(crate) internal_rating: u8, // قابل دیدن تو کل کریت، اما نه تو API عمومی
    }
}
```

یه فراخواننده (caller) تو یه کریتِ *متفاوت* که به این کریت وابستگی (depend) داره، می‌تونه یه `Anime` بسازه و `title` رو بخونه، اما حتی نمی‌تونه اسمِ `internal_rating` رو بیاره — کامپایلر دقیقاً مثل وقتی که اصلاً `pub`ی وجود نداشته باشه، اون رو به عنوان یه فیلد خصوصی گزارش می‌ده. فقط کدهایی که تو *همین* کریت نوشته شدن (از جمله کدهای مربوط به تستِ خود همین کریت، که موقع یونیت‌تست شدن به عنوانِ بخشی از خود کریت کامپایل می‌شن — که البته تو درس بعدی در مورد تفاوت‌هاش بیشتر حرف می‌زنیم) اجازه دارن که اون رو ببینن.

## کلمه‌ی `use` و صادراتِ مجدد (Re-exporting) با `pub use`

دستورِ `use` یه مسیر (path) رو میاره تو اسکوپ فعلی تا مجبور نباشی هر دفعه اسم کاملش رو از اول تا آخر بنویسی:

```rust
use catalog::Anime;
let a = Anime { title: "Frieren".to_string() };
```

اما دستورِ `pub use` یه کار اضافه‌تر هم می‌کنه: اون یه موجودیت رو تو یه مسیر جدید و کم‌عمق‌تر **مجدداً صادر (re-export)** می‌کنه. فرض کن `Anime` تو واقعیت و در عمق سه ماژولِ تودرتو یعنی `catalog::series::Anime` زندگی می‌کنه — تایپ کردن یه همچین مسیر طولانی‌ای برای فراخواننده‌ها خیلی ناجور و دست‌وپاگیره. تو می‌تونی تو فایل ریشه‌یِ کریت اینو بنویسی:

```rust
pub use catalog::series::Anime;
```

حالا فراخواننده‌های خارجی به جای اون مسیر طولانی، مستقیماً از `my_crate::Anime` استفاده می‌کنن، با وجود اینکه در واقع محل اصلیِ تعریفِ `Anime` *هیچ تغییری نکرده*. این دقیقاً همون روشیه که کریت‌های واقعی باهاش میان یه APIِ تمیز، تخت و یک‌دست رو می‌ذارن روی یه ساختارِ تودرتو و عمیقِ ماژول‌های داخلی — قراره این الگو رو تو کتابخونه‌هایی که ازشون استفاده می‌کنی به وفور ببینی.

## ورک‌اسپیس‌ها (Workspaces) (فقط یه مفهوم ذهنی — نیازی به کدزنی نیست)

یه **ورک‌اسپیسِ Cargo (Cargo workspace)** در واقع یه گروه از کریت‌هاست که همه‌شون روی یه دونه فایلِ `Cargo.lock` و یه دونه پوشه‌ی خروجیِ بیلد (build output) به اسم `/target` مشترک هستن، پس اگه یه وابستگیِ (dependency) مشترک بینشون باشه، فقط یه بار کامپایل می‌شه نه اینکه به ازای تک‌تک کریت‌ها کامپایل بشه. کُلِ همین مخزنی (repo) که الان توشی، یه ورک‌اسپیسه (می‌تونی تو همون فایل ریشه‌ایِ `Cargo.toml` ببینیش): هر کریت برای هر درسی که می‌سازی یه عضو از همین ورک‌اسپیس به حساب میاد، برای همین وقتی تو هر جای این مخزن که باشی بزنی `cargo build`، واسه درسی مثل درسِ چهلم که از `tokio` استفاده می‌کنه، دیگه نمیاد `tokio` رو از صفر کامپایل کنه. تو این درس قرار نیست خودت یه ورک‌اسپیسِ تودرتو بسازی — فقط خواستم این اصطلاح رو بشناسی، چون همین الانش هم داری داخل یکی از اونا زندگی می‌کنی.

## وظیفه‌ی تو

تو فایل `src/lib.rs` یه ماژول کوچیک به اسم `catalog` تعریف شده که قراره نقش یه کاتالوگِ انیمه رو بازی کنه، و توش یه نوعِ (type) عمومی به اسم `Anime` داره که از ریشه‌ی کریت re-export می‌شه، به اضافه‌ی یه "امتیاز داخلی (internal rating)" که فقط تو سطحِ کریت کار می‌کنه و پشتِ `pub(crate)` پنهون شده. جاهای خالی (همون `todo!()`ها) رو پر کن.
