# راه‌حل — ۲.۳.۷ ارسالِ ایستا در برابرِ پویا، و ایمنیِ شیء

```rust
pub fn total_summary_length_generic<T: Summarize>(items: &[T]) -> usize {
    items.iter().map(|item| item.summary().len()).sum()
}

pub fn total_summary_length_dyn(items: &[Box<dyn Summarize>]) -> usize {
    items.iter().map(|item| item.summary().len()).sum()
}

pub fn lineup(series: AnimeSeries, volume: MangaVolume) -> Vec<Box<dyn Summarize>> {
    vec![Box::new(series), Box::new(volume)]
}

pub fn fibonacci() -> impl Iterator<Item = u64> {
    Fibonacci {
        current: 0,
        next: 1,
    }
}
```

## `total_summary_length_generic` و `total_summary_length_dyn` — بدنه‌ای یکسان، امضایی متفاوت

```rust
items.iter().map(|item| item.summary().len()).sum()
```

هر دو تابع دقیقاً همین یک خط را به‌عنوانِ بدنه دارند. این تصادفی نیست — دقیقاً همان چیزی است که این درس می‌خواست نشانت بدهد. هیچ‌چیزی در *حسابِ* مجموع، بینِ ارسالِ ایستا و پویا فرق نمی‌کند؛ فقط *نوعِ* `items` عوض می‌شود. `&[T]` هر عنصر را به یک نوعِ ملموسِ ثابت متعهد می‌کند، یک‌بار، توسطِ صداکننده انتخاب‌شده؛ `&[Box<dyn Summarize>]` می‌گذارد هر عنصر نوعِ ملموسِ خودش را داشته باشد، عنصر‌به‌عنصر تصمیم‌گرفته‌شده، با هزینه‌ای که سرِ هر فراخوانیِ `.summary()` پرداخت می‌شود، نه هنگامِ کامپایل. اگر اینجا دو بدنه‌ی متفاوت نوشتی، نشانه‌ی این است که چیزی پیچیده‌تر از آنچه هرکدام از این دو امضا واقعاً لازم داشت، ساختی.

## `lineup` — تبدیل، دقیقاً سرِ `Box::new` اتفاق می‌افتد، نه زودتر

```rust
vec![Box::new(series), Box::new(volume)]
```

`Box::new(series)` یک `Box<AnimeSeries>` می‌سازد؛ `Box::new(volume)` یک `Box<MangaVolume>` می‌سازد — دو نوعِ واقعاً متفاوت. چیزی که هر دو خط را به عنصرهای یک `vec![...]` واحد تبدیل می‌کند، نوعِ برگشتیِ خودِ تابع است: `Vec<Box<dyn Summarize>>`. Rust دقیقاً همان‌جا که هر عنصر باید با آن نوع جور دربیاید، یک تبدیلِ ضمنیِ اندازه‌رهاکننده (unsizing coercion) از `Box<AnimeSeries>` به `Box<dyn Summarize>` انجام می‌دهد (و همین کار را برایِ `Box<MangaVolume>` هم می‌کند)، و هر دو را تا حدِ «یک `Box` از چیزی که `Summarize` را پیاده کرده، به‌اضافه‌یِ یک vtable» پاک می‌کند. هیچ‌کدام از این دو ساختار لازم نبود از دیگری خبر داشته باشد، و هیچ‌کدام به هیچ کستِ صریحی نیاز نداشت — همان نوعِ برگشتیِ نوشته‌شده در امضا کافی بود تا این تبدیل را هدایت کند.

## `fibonacci` — قولِ نوعِ برگشتی، همان صداکردنِ سازنده

```rust
Fibonacci {
    current: 0,
    next: 1,
}
```

بدنه دقیقاً همان چیزی است که اگر نوعِ برگشتی `-> Fibonacci` بود می‌نوشتی — یک عبارتِ ساختِ ساختارِ معمولی، بدونِ هیچ چیزِ پنهان. تنها چیزی که `-> impl Iterator<Item = u64>` عوض می‌کند این است که *صداکننده* اجازه دارد چه چیزی بداند: می‌تواند رویِ هرچه برگشته `.take()`، `.filter()`، `.collect()` بزند، چون واقعاً یک `Iterator<Item = u64>` است، ولی هیچ‌وقت نمی‌تواند نامِ `Fibonacci` را خودش بنویسد، و هیچ‌وقت نمی‌تواند رویِ اینکه دقیقاً همان ساختار است حساب باز کند. این هنوز یک نوعِ ملموسِ واحد و هنگامِ‌کامپایل‌شناخته‌شده است — ارسالِ ایستا، دقیقاً مثلِ هر تابعِ دیگرِ این فایل، فقط با نامش نگه‌داشته‌شده به‌صورتِ خصوصی.

## این درس واقعاً درباره‌ی چه بود

- **مکانیزمِ ارسال کاملاً تویِ امضا زندگی می‌کند، نه هیچ‌وقت تویِ بدنه.** `total_summary_length_generic` و `total_summary_length_dyn` دقیقاً همین را ثابت می‌کنند: یک خط منطق را بینِ دو هزینه‌ی کاملاً متفاوتِ محلِ فراخوانی مشترک می‌گذارند.
- **`Box<dyn Trait>` همان چیزی است که یک `Vec` مخلوط را ممکن می‌کند.** `lineup` هیچ‌وقت نمی‌توانست به‌شکلِ `Vec<T>` برایِ هیچ `T`ِ واحدی نوشته شود — کلِ دلیلِ وجودِ `Box<dyn Summarize>` اینجا این است که به دو ساختارِ متفاوت یک نوعِ عنصرِ مشترک و باندازه بدهد.
- **`impl Trait` تویِ خروجی، هیچ هزینه‌ای هنگامِ اجرا ندارد.** بدنه‌ی `fibonacci` هیچ‌وقت بسته به نوشتارِ امضا عوض نمی‌شود؛ فقط چیزی که کامپایلر اجازه می‌دهد صداکننده *دربارهٔ* نوعِ برگشتی بگوید، عوض می‌شود.
