# راه‌حل

```rust
pub fn largest<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut max = *items.first()?;
    for &item in items {
        if item > max {
            max = item;
        }
    }
    Some(max)
}
```

متد `()items.first` خروجیِ `<Option<&T` برمی‌گردونه — یعنی یه ارجاع به عنصرِ اول، البته اگه وجود داشته باشه. عملگر `?` بلافاصله اگه بُرش (slice) خالی باشه `None` رو میده بالا (و درجا از همون خطِ اولِ تابع `largest` همون `None` رو برمی‌گردونه)، وگرنه مقدار داخلش رو باز (unwrap) می‌کنه و به `T&` می‌رسه. اون علامت `*` که اولش اومده (leading `*`) عمل نشان‌زدایی (dereferencing) رو انجام می‌ده و اون رو به `T` تبدیل می‌کنه، و این دقیقاً همونجاییه که صفتِ `Copy` ارزش خودش رو نشون میده: انجام عمل نشان‌زدایی روی یه مقدار قرضی (borrowed) برای اینکه یه نسخه‌ی *دارای مالکیتِ (owned)* کپی‌شده ازش به دست بیاریم، تنها تو صورتی مجازه که کامپایلر بدونه چطوری باید اون مقدار رو با هزینه‌ی کم تکثیر کنه (یه کپی بیتی ساده — نه نیازی به تخصیص حافظه رو heap داشته باشه، نه لازم باشه نگران باشیم که نکنه یه منطق پاکسازیِ سفارشی دوبار اجرا بشه). اگه `Copy` رو نداشتیم، عبارتِ `?()items.first*` سعی می‌کرد تا `T` رو از جایگاهش داخل `items` بکِشه بیرون (بهش میگن move کردن)، که Rust جلوی این کار رو می‌گیره — چون تو مالکِ اون جایگاه نیستی و فقط یه ارجاع اشتراکی (shared reference) بهش داری، و اگه بخوای یه متغیر رو از زیر دست یه ارجاعِ اشتراکی بکشی بیرون، یعنی داری تو `items` یه سوراخِ خالی درست می‌کنی که هیچ‌کس مالکش نیست. این همون جوابِ سؤال ۱ از مروره.

حلقه هم که به شکل `for &item in items` نوشته شده، دقیقاً از همون الگوی قدرت‌گرفته‌از `Copy` استفاده می‌کنه: متغیر `items` از جنس `&[T]` هست، پس پیمایش (iteration) روی اون تو هر مرحله یه `T&` به ما می‌ده، و همون الگویِ `&item` بلافاصله هر ارجاع رو به داخلِ یه `item`ِ دارای مالکیت (owned) کپی می‌کنه؛ اینطوری، بدنه‌ی حلقه می‌تونه خیلی راحت برای مقایسه از همون علامت `>` استفاده کنه به جای اینکه مجبور باشه با کثیف‌کاری‌هایی مثل `b* < a*` سر و کله بزنه.

در مورد سؤال ۲ مرور: دو تا. دستور `cargo build` می‌بینه که تو ماژول تست‌ها، هم از `<Stack<i32` و هم از `<Stack<String` استفاده شده، پس فرآیندِ تک‌ریختی کردن (monomorphization) میاد از هر متدِ `<Stack<T` دو تا نسخه‌ی کپیِ کاملاً مستقل تولید می‌کنه — یکی که توش تمامِ `T`ها با `i32` جایگزین شدن، و یکی هم که توش تمامِ `T`ها با `String` جایگزین شدن — دقیقاً انگار که خودت با دستِ خودت یه `StackI32` و یه `StackString` نوشته باشی. اگه تو یه جای دیگه‌ای از کد از یه نوعِ ملموسِ سوم هم استفاده می‌شد، یه نسخه‌ی سوم هم ظاهر می‌شد. هیچ‌کدوم از این اتفاقات تو سطح کدهای منبعی که می‌نویسی (source level) قابل دیدن نیستن؛ این فرآیند کاملاً یه توسعه تو زمان کامپایله (compile-time expansion)، و دقیقاً به همین دلیله که وقتی `.push()` یا `.pop()` رو صدا می‌زنی هیچ هزینه‌ای واسه چک‌کردنِ نوعِ متغیر تو زمان اجرا (runtime type-check) نمی‌پردازی — زمانی که برنامه شروع به اجرا می‌کنه، تابعی مثل `Stack<i32>::push` دیگه فقط یه تابع کاملاً معمولی و ملموس (concrete) حساب می‌شه.
