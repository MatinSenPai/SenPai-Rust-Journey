# راه‌حل

```rust
impl From<Percentage> for f64 {
    fn from(value: Percentage) -> Self {
        f64::from(value.0) / 100.0
    }
}
```

کل دلیلِ اینکه این تابع را دقیقاً کنارِ `TryFrom` تو همین فایل گذاشتیم همینه: اینجا هیچ‌چیزی برای رد کردن نیست. `value.0` یه `u8` است که از قبل، دقیقاً یک‌بار، از دروازه‌ی `TryFrom<u8> for Percentage` رد شده — تنها دروازه‌ی ورودی — پس از قبل معلوم است که تو بازه‌ی `0..=100` است. تقسیمِ یه عددِ از قبل تضمین‌شده بر `100.0` نه می‌تواند شکست بخورد، نه پنیک می‌گیرد، نه ممکن است چیزی بیرون از `0.0..=1.0` تولید کند. دقیقاً همین چیز است که این تابع را یه `From` می‌کند نه یه `TryFrom`: امضای `fn from(value: Percentage) -> f64` اصلاً جایی برای گذاشتنِ یه `Err` ندارد، حتی اگر می‌خواستی. آن `f64::from(value.0)` هم همان تبدیلِ پهن‌کننده‌ی مثالِ ۰۱ است، دوباره — یک `u8` همیشه تو یک `f64` جا می‌شود — پس همین یک تابع، بی‌سروصدا، از هر دو صفتی که این درس یادت داد استفاده می‌کند: یک `From` برای پهن‌کردنِ `u8`، و یک `From` دیگر برای توصیفِ کلِ تبدیل.

```rust
impl TryFrom<u8> for Percentage {
    type Error = ValidationError;

    fn try_from(raw: u8) -> Result<Self, Self::Error> {
        if raw <= 100 {
            Ok(Percentage(raw))
        } else {
            Err(ValidationError::PercentageOutOfRange(raw))
        }
    }
}
```

عمداً هیچ ایده‌ی پیچیده یا نبوغ‌آمیزی توش نیست — ارزشِ واقعیِ این پیاده‌سازی تو *محلِ قرارگیری‌اش* است، نه اینکه چطور نوشته شده. چون فیلدِ `Percentage` کاملاً خصوصی است، همین یک `if` تنها جای کلِ دنیاست که یک `Percentage` می‌تواند در آن متولد شود، پس هر `Percentage`ای که هر جای برنامه پیدا کنی، از زیرِ دستِ همین شرط رد شده. حالا این فیلد را `pub` کن تا آن تضمینِ سراسری، بدونِ اینکه حتی یک خط از کدِ فراخواننده‌ها عوض شود، دود شود برود هوا: آن‌وقت `Percentage(255)` هرجایی قابلِ‌ساخت می‌شود، و «آیا واقعاً بینِ ۰ تا ۱۰۰ هست؟» دوباره برمی‌گردد به یک سؤالِ code review، نه یک حقیقتِ ثبت‌شده تو دلِ سیستمِ نوع. به چیزی که تستِ `implementing_try_from_provides_try_into_for_free` نشان می‌دهد هم توجه کن: ما هیچ‌جا `TryInto` ننوشتیم. کتابخانه‌ی استاندارد یک پیاده‌سازیِ فراگیر دارد — `impl<T, U> TryInto<U> for T where U: TryFrom<T>` — دقیقاً همان پُلِ `From`/`Into` که ۱.۶.۵ نشانت داد، این‌بار برای جفتِ خطاپذیر.

```rust
impl TryFrom<String> for EmailAddress {
    type Error = ValidationError;

    fn try_from(raw: String) -> Result<Self, Self::Error> {
        let valid = matches!(
            raw.split_once('@'),
            Some((local, domain))
                if !local.is_empty() && !domain.is_empty() && !domain.contains('@')
        );

        if valid {
            Ok(EmailAddress(raw))
        } else {
            Err(ValidationError::InvalidEmail(raw))
        }
    }
}
```

شکلِ این تابع را خودِ borrow checker دیکته کرده، و ارزش دارد بفهمی چرا. نسخه‌ی «بدیهیِ» این کار — یک `match` تنها روی `raw.split_once('@')` که بازوی موفقش مستقیم `Ok(EmailAddress(raw))` برمی‌گرداند — اصلاً کامپایل نمی‌شود: `split_once` برش‌های `&str`ای برمی‌گرداند که دارند از `raw` *قرض می‌گیرند*، و آن مقدارِ زیرِ بررسیِ `match` همان قرض را تا آخرِ کلِ `match` زنده نگه می‌دارد، و تو نمی‌توانی `raw` را جابه‌جا کنی درحالی‌که هنوز قرض گرفته شده (`E0505`). پس کار به دو فاز تقسیم می‌شود: اول قرض را تا یک `bool` ساده تقلیل بده (`matches!` با یک نگهبان همین کار را در یک عبارت انجام می‌دهد)، بعد، وقتی همه‌ی قرض‌های `raw` تمام شدند، `raw` را به هرکدام از دو سمتِ `Result` که بهش تعلق دارد جابه‌جا کن. برگرداندنِ رشته‌ی ردشده داخلِ `InvalidEmail(raw)` هیچ هزینه‌ای ندارد — از اول مالکش بودیم — و اگر فراخواننده بخواهد لاگش کند یا به همان کسی که تایپش کرده نشانش بدهد، از یک `clone` نجاتش می‌دهد. خودِ اعتبارسنجی هم از قصد کمینه است: `a@b` قبول می‌شود. این انتخابِ صادقانه‌ای برای یک درس است — اعتبارسنجیِ واقعیِ ایمیل خودش یک مردابِ RFC است، و تنها چکی که واقعاً می‌تواند قابلِ‌تحویل بودن را اثبات کند، فرستادنِ یک ایمیلِ تأییدیه است.

```rust
pub fn saturating_narrow(value: u64) -> u32 {
    value.try_into().unwrap_or(u32::MAX)
}
```

این تک‌خطی دستمزدِ این است که کتابخانه‌ی استاندارد از قبل `TryFrom<u64> for u32` را پیاده‌سازی کرده: آن تبدیلِ خطاپذیر همین اول در قالبِ یک `Result` به دستت می‌رسد، پس *سیاستِ* برخورد با شکست، دیگر یک مسئله‌ی جریانِ کنترل نیست، فقط انتخابِ یک ترکیب‌گر است. عملگرِ `?` خطا را بالا می‌فرستد، `.unwrap_or(u32::MAX)` می‌چسباندش به سقف، `.unwrap()` رویش کرش می‌کند — هرکدام یک عبارت، و هرکدام کاملاً صادق درباره‌ی کاری که می‌کند. این را با `value as u32` مقایسه کن، که سیاستِ *بریدنِ بی‌صدا* را بدونِ اینکه اصلاً شبیهِ یک تصمیم باشد قایم می‌کند: `4_294_967_295u64 as u32` می‌شود `4294967295` (جا می‌شود، بدونِ غافلگیری)، ولی `4_294_967_296u64 as u32` — فقط یکی بیشتر — می‌شود `0`. فرمِ `try_into().unwrap_or(...)` همان چیزی است که تو کدِ واقعی می‌بینی، و برایِ هر جفتِ کوچک‌شونده‌ای که کتابخانه‌ی استاندارد تعریف کرده عمومیت دارد، نه فقط همین یکی.
