# ۰۴.۲ — کریت‌های `thiserror` و `anyhow`

## کریت `thiserror`: همون کدهای تکراری درس ۱، که برات تولید می‌شه

نوعِ `ConfigError` تو درس ۱ نیاز داشت که خودت با دست `impl Display` رو بنویسی (یه `match` که به ازای هر گونه (variant) یه بازو داشت) و همینطور یه بلاک خالیِ `{} impl std::error::Error for ConfigError` بنویسی. این الگو — یعنی enum در کنار `Display` و `Error` — تو پایگاه‌های کد واقعی زبان Rust اونقدر رایجه که کریت (crate) `thiserror` دقیقاً و صرفاً به این دلیل به وجود اومده تا با استفاده از attributeها این کدها رو برات تولید کنه:

```rust
#[derive(thiserror::Error, Debug)]
pub enum ConfigError {
    #[error("missing required field: {0}")]
    MissingField(String),

    #[error("invalid number for field '{field}': {source}")]
    InvalidNumber {
        field: String,
        #[source]
        source: std::num::ParseIntError,
    },
}
```

صفتِ `[(derive(thiserror::Error#]` دقیقاً همون `impl Display` و `impl std::error::Error`ای رو تولید می‌کنه که تو درس قبلی با دست می‌نوشتی:
- صفتِ `["..."]error#` روی یه گونه، تبدیل می‌شه به پیغام `Display` برای همون گونه. عبارتِ `{0}` به اولین فیلدِ یه گونه‌ی توپل (tuple variant) اشاره می‌کنه؛ و `{field}` / `{source}` هم به فیلدهای نام‌گذاری‌شده‌ی یه گونه‌ی ساختاری (struct variant) اشاره می‌کنن — سینتکسِ جاگذاری (interpolation) دقیقاً همون چیزیه که تو `!format` داری، فقط به جای اینکه تو فراخوانیِ `!write` بنویسیش، اینجا مستقیم داخل خود صفت نوشته می‌شه.
- صفتِ `[source]#` روی یه فیلد، اون رو به عنوان *علتِ زیربنایی (underlying cause)* نشونه‌گذاری می‌کنه، که در واقع میاد متد `()Error::source` رو سیم‌کشی می‌کنه و راه می‌ندازه (همون متدی که تو درس ۱ نیازی نبود دستی بازنویسی یا override بشه، چون اونجا `ConfigError` به خطای دیگه‌ای زنجیر نشده بود که لازم باشه به بیرون درز پیدا کنه و دیده بشه).
- اگه صفتِ `[from]#` رو هم روی یکی از فیلدهای این نوع‌ها اضافه کنی، thiserror *علاوه بر کارای قبلی* میاد اون بلوکِ `impl From`ای که تو درس قبل برای حالت `max_retries` دستی نوشته بودی رو هم برات تولید می‌کنه — یعنی فقط با یه صفتِ ساده، از شرِ یه بلوک کاملِ `... impl From<...> for` راحت می‌شی.

همون رفتار درس ۱ رو می‌ده، اما با کد خیلی خیلی کمتری که نیاز به نگهداری داره. کریت `thiserror` ماهیتِ یه خطای Rust رو تغییر نمی‌ده — همچنان همون دو تا traitِ همیشگی یعنی `Display` + `Error` هستن — فقط اون کدهای تکراری رو به جات می‌نویسه.

## کریت `anyhow`: برای زمانی که فراخواننده‌ها *نیازی ندارن* که روی نوعِ خطا match کنن

کریت `thiserror` به درد **کدهای کتابخونه‌ای (library code)** می‌خوره: یعنی کدهایی که فراخواننده‌شون ممکنه خیلی معقول و منطقی بخواد بنویسه `} ... => (match err { ConfigError::MissingField(f` و هر کدوم از انواعِ خطاها (failure kinds) رو یه جورِ متفاوتی هندل کنه. اما خیلی از کدها — مخصوصاً اونایی که تو بالاترین سطح یه برنامه قرار دارن — اصلاً همچین فراخواننده‌ای ندارن. تابع `()main`، منطقِ سطحِ بالای یه ابزار CLI، یه هندلر HTTP که فقط می‌خواد یه ارور ۵۰۰ برگردونه و جزئیات رو تو لاگ‌ها ثبت کنه: تو این جور جاها اصلاً مهم نیست که *کدوم یکی* از چهل مدل خطای ممکن اتفاق افتاده، فقط مهمه که *یه چیزی* خراب شده، و اونا می‌خوان این خرابی رو پاس بدن بالا به یه نقطه‌ی واحد که فقط چاپش کنه یا لاگش کنه و بعد متوقف بشه.

این همونجاییه که پای `<anyhow::Result<T` (که در واقع یه خلاصه‌نویسی برای `<Result<T, anyhow::Error>` هست) وسط میاد. نوعِ `anyhow::Error` می‌تونه **هر** نوعی که traitِ `std::error::Error` رو پیاده‌سازی کرده باشه تو دلِ خودش جا بده و کاور (wrap) کنه — و دقیقاً به همین دلیله که تو درس ۱ و این درس، به جای اینکه فقط یه `String` برگردونیم، زحمتِ پیاده‌سازیِ درستِ اون trait رو به خودمون دادیم. استفاده از `?` داخل تابعی که خروجیِ `<anyhow::Result<T` برمی‌گردونه، خیلی راحت و به طور خودکار *هر* نوعِ خطایی رو به `anyhow::Error` تبدیل می‌کنه، بدون اینکه نیازی به نوشتنِ بلوکِ `From` برای تک‌تکِ اون نوع‌ها داشته باشی.

**قانون سرانگشتی که پایگاه‌های کدِ حرفه‌ای تو Rust ازش پیروی می‌کنن اینه: `thiserror` رو تو `lib.rs` استفاده کن، و `anyhow` رو تو `main.rs`.** کتابخونه‌ها enumهایِ دقیق و قابل‌match برای خطاها ارائه می‌دن تا فراخواننده‌ها *بتونن* اگه خواستن، شکست‌های خاص رو هندل کنن. برنامه‌های اجرایی (applications) (یعنی خارجی‌ترین لایه‌ای که در واقع ران می‌شه و خودش دیگه هیچ فراخواننده‌ای نداره)، همه‌چی رو جمع و جور می‌کنن و تو قالبِ `anyhow::Error` درمیارن، چون دیگه اونجا کسی نمونده که بخواد روش `match` انجام بده.

## متد `anyhow::Context` — ردپا و خرده‌نون‌هایی (breadcrumbs) در مسیر انتقال خطا

```rust
use anyhow::Context;

pub fn load_and_parse(input: &str) -> anyhow::Result<Config> {
    parse_config(input).context("failed to load application config")
}
```

متد `("...")context.` یه خطا رو با یه پیام اضافه‌ی قابل‌خوندن برای انسان کاور (wrap) می‌کنه *بدون اینکه* خطای اصلی رو دور بندازه — با چاپ کردنِ یه `anyhow::Error`، پیامِ context نشون داده می‌شه و اگه فرمت‌های `{#:}` یا `{:?}` رو استفاده کنی، کلِ اون زنجیره‌ی خطاهایِ زیرش هم چاپ می‌شن. متد `(...)with_context(|| format.` همون نسخه‌ی تنبل (lazy) و موکول‌به‌بعدِ اونه، که وقتی به درد می‌خوره که ساختن پیامِ متنی هزینه داره (مثلاً باید مقداری فرمت‌بندی شه) و تو ترجیح می‌دی این هزینه پرداخت نشه مگه اینکه برنامه واقعاً به مسیر خطا بیفته. وقتی تو بک‌اندِ واقعی (فاز ۳ به بعد) پشته‌ی فراخوانی‌ها (call stacks) پنج شش تا تابع عمیق بشه، گذاشتنِ `(...)context.` تو هر لایه همون چیزیه که پیام مبهمِ "invalid digit found in string" رو تبدیل می‌کنه به "failed to load application config: invalid number for field 'max_retries': invalid digit found in string" — این دقیقاً تفاوتِ بینِ دیدنِ یه ردپایِ مکانیکی از استک (stack trace) با خوندن یه داستان معنادارِ خطاست.

## وظیفه‌ی تو

ساختار `ConfigError` رو با استفاده از `[(derive(thiserror::Error#]` بازنویسی کن، سعی کن رفتارِ `parse_config` دقیقاً همون چیزی که تو درس ۱ بود بمونه، و تابع `load_and_parse` رو هم با استفاده از `anyhow::Context` پیاده‌سازی کن.
