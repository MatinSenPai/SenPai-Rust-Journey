# ۰۴.۳ — مبانی طول عمر و elision

از فاز یک تا اینجا بارها کدی نوشته‌ای که به طول عمر وابسته بوده است؛ حالا می‌خواهیم رابطه‌ای را که کامپایلر خودش استنباط می‌کرد، صریح ببینیم.

## طول عمر واقعاً چیست؟

طول عمر (Lifetime) ساعت یا زمان واقعی اجرای یک مقدار نیست؛ نامی است که کامپایلر برای بازه‌ی معتبر بودن یک ارجاع به‌کار می‌برد. `'a` مثل `T` یک پارامتر عمومی است و وقتی چند ارجاع را به هم مرتبط می‌کند معنا پیدا می‌کند.

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```

این امضا عمر هیچ ارجاعی را بیشتر نمی‌کند. فقط می‌گوید خروجی در بازه‌ای معتبر است که هر دو ورودی هنوز معتبر باشند؛ طول عمر واقعی را نحوه‌ی استفاده‌ی فراخوان و بررسی کامپایلر تعیین می‌کند.

## سه قانون elision

1. هر ورودی ارجاع بدون نشانه‌گذاری lifetime مستقل می‌گیرد.
2. اگر دقیقاً یک ورودی lifetime باشد، خروجی ارجاع همان را می‌گیرد.
3. در متد دارای `&self` یا `&mut self`، خروجی ارجاع lifetime self را می‌گیرد.

برای همین `fn first_word(text: &str) -> &str` نشانه‌گذاری نمی‌خواهد، ولی `longest` با دو ورودی باید رابطه‌ی خروجی را مشخص کند.

```rust
struct Excerpt<'a> {
    text: &'a str,
}
```

struct نگهدارنده‌ی ارجاع نباید از داده‌ی مقصد بیشتر زنده بماند و برای field قانون elision نداریم.

`'static` برای ارجاع یعنی اعتبار تا پایان برنامه. در bound مثل `T: 'static` یعنی `T` borrow کوتاه‌عمر درون خود ندارد؛ `String` دارای مالکیت نیز این شرط را دارد.

در کتابخانه، برگه‌ای که به صفحه‌ای از یک کتاب اشاره می‌کند بعد از پس‌دادن همان کتاب دیگر به کارت نمی‌آید. البته طول عمر در Rust زمان روی ساعت نیست؛ کامپایلر رابطه‌ی محدوده‌ها و آخرین استفاده از هر ارجاع را بررسی می‌کند.
