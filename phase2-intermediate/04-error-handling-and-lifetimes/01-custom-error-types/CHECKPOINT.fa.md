# ایست بازرسی

۱. فرض کن `ConfigError` مانند فاز یک هنوز فقط `String` بود. بدون نوشتن کد توضیح بده فراخواننده چگونه باید «نبودن field» را از «عدد نامعتبر field» تشخیص می‌داد، وقتی فقط یک رشته دارد. چرا این روش شکننده است؟

۲. `parse_config` پس از `.parse()` مربوط به `max_retries` فقط `?` می‌گذارد، اما برای `timeout_secs` به `.map_err(...)` نیاز دارد. هر دو شکست دقیقاً variant به نام `ConfigError::InvalidNumber` را می‌سازند. دقیق توضیح بده چرا یکی با `?` خالی ممکن است و دیگری نه.

۳. بدنه‌ی `impl std::error::Error for ConfigError {}` خالی است. برای اینکه همین `impl` خالی compile شود، چه ویژگی‌هایی باید از قبل درباره‌ی `ConfigError` درست باشند؟ به requirementهای `Error` دقت کن.

۴. بالای `pub enum ConfigError` عبارت `#[derive(Debug)]` داریم و `impl Display for ConfigError` را هم دستی نوشته‌ایم. چرا **هر دو** لازم‌اند؟ یک استفاده‌ی مشخص هر trait در تست‌های این درس را بگو که دیگری نمی‌تواند فراهم کند.

۵. اگر بعداً بخواهی `ConfigError` خطای یک کتابخانه‌ی دیگر—مثلاً خطای خواندن config از فایل—را wrap کند، چه چیزی به enum اضافه می‌کنی و چه `impl` تازه‌ای اجازه می‌دهد `?` آن خطا را مانند `ParseIntError` خودکار تبدیل کند؟
