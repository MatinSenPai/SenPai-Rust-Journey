# ۰۷.۴ — مبانی `tokio`

تو درس قبلی یه `Future`، یه حلقه‌ی `Poll` و کوچیک‌ترین اجراکننده‌ی (executor) ممکن رو با دستای خودت ساختی، صرفاً به این دلیل که کریت `tokio` — زمان اجرایی (runtime) که تقریباً هر بک‌اندِ غیرهمگام (async) تو زبان Rust، از جمله تمام چیزایی که تو فاز ۳ قراره بسازی (`axum` هم دقیقاً روی همین سواره) ازش استفاده می‌کنن — دیگه برات شبیه جادو به نظر نرسه. کریتِ `tokio` دقیقاً همون ایده است که حالا به شکل درست‌وحسابی و مهندسی‌شده پیاده شده: یه زمان‌بندِ واقعی (real scheduler)، تایمرهای واقعی، I/Oِ غیرهمگامِ واقعی، که به جای اینکه `Future`های تو رو روی یه ریسمانِ (thread) تنها اجرا کنه، اون‌ها رو روی یه استخرِ کوچیک (pool) از ریسمان‌های سیستم‌عامل پخش می‌کنه.

## ماکروی `[tokio::main]#` و `[tokio::test]#`

```rust
#[tokio::main]
async fn main() {
    // بدنه‌ی این تابع تو دلِ زمانِ اجرایِ tokio ران می‌شه
}
```

صرفاً نوشتنِ `()async fn main` به تنهایی نمی‌تونه نقطه‌ی ورودِ (entry point) واقعی یه برنامه باشه — تابع `main` به خودیِ خود نمی‌تونه `async` باشه (باید یه چیزی اول از همه اون اجراکننده (executor) رو بسازه و روشنش کنه). ماکروی `[tokio::main]#` میاد و همون تابع `()fn main` همگامِ و معمولی رو که سیستم‌عامل انتظار داره به صورت خودکار برات تولید می‌کنه؛ این تابعِ تولیدشده، خودش یه runtimeِ `tokio` می‌سازه و ازش استفاده می‌کنه تا بدنه‌یِ تابعِ `()async fn main`ِ تو رو به جلو هل بده تا کامل تموم بشه. ماکروی `[tokio::test]#` هم دقیقاً همین کار رو برای توابع تست انجام می‌ده — تو این درس، تمامِ تست‌ها به جای اینکه فقط از `[test]#`ِ خالی استفاده کنن، از همین ماکرو استفاده کردن.

## دستور `tokio::spawn`: جواب دنیای غیرهمگام به `thread::spawn`

```rust
let handle = tokio::spawn(async {
    // این بخش به صورت همروند (concurrently) با هر چیزی که اینو spawn کرده اجرا می‌شه
    42
});
let result = handle.await.unwrap();
```

دستور `tokio::spawn` یه `Future` رو به عنوان یه **تسکِ (task)** کاملاً مستقل به دستِ زمان‌اجرا (runtime) می‌سپاره — از نظر مفهومی دقیقاً شبیه همون `thread::spawn` تو درس ۱ هستش، با این تفاوتِ خیلی مهم که تسک‌ها به شدت سبک‌تر و ارزون‌تر از ریسمان‌های سیستم‌عامل هستن (تو می‌تونی هزاران تسک رو به راحتی spawn کنی) و به صورت *همیاری‌طور (cooperatively)* روی یه استخرِ کوچیک از ریسمان‌های واقعی برنامه‌ریزی (schedule) می‌شن؛ یعنی اینطوری نیست که سیستم‌عامل وسطِ اجرای هر دستورالعملی که خواست یهو کنترل رو ازشون بگیره (preemption)، بلکه دقیقاً فقط تو نقاطِ `await.` بینِ تسک‌های مختلف جابه‌جا (switch) می‌شه. عبارت `handle.await` (دقت کن `()join.` نه — تسک‌ها از `await.` استفاده می‌کنن، اما ریسمان‌ها از `()join.`) تو خروجی بهت یه `<Result<T, JoinError>` می‌ده، که هم شکلش و هم دلیل وجودش دقیقاً مثل همون `Result`ای هست که تو درس ۱ از `JoinHandle::join` می‌گرفتی.

## اصلِ ماجرا: انتظار همروند (concurrent waiting)، نه محاسبات موازی (parallel computing)

```rust
// حالت ترتیبی (sequential): زمان کل ≈ جمعِ تمامِ تأخیرها
for id in ids {
    fetch_simulated(id).await;
}

// حالت همروند (concurrent): زمان کل ≈ کندترین تأخیرِ تکی
let handles: Vec<_> = ids.into_iter().map(|id| tokio::spawn(fetch_simulated(id))).collect();
for handle in handles {
    handle.await.unwrap();
}
```

این دقیقاً همون نقطه‌ی ارزش‌آفرینِ کاملِ ویژگی async برای کارهای بک‌اند هستش: اگه منتظرِ جوابِ ۱۰ تا درخواست شبکه‌ی کاملاً مستقل از هم باشی که هر کدوم ۱۰۰ میلی‌ثانیه زمان می‌برن، انجام دادنِ اونا پشت‌سرهم (و روی هر کدوم نوبتی `await` کردن) کلاً ۱۰۰۰ میلی‌ثانیه زمان می‌بره؛ اما spawn کردنِ هر ۱۰ تاشون به عنوان تسک‌های جداگانه و بعد از اون `await` کردن روی همه‌شون، سرجمع همون ~۱۰۰ میلی‌ثانیه زمان می‌بره — چون در حالی که تسک شماره‌ی ۱ منتظرِ گرفتن جواب از شبکه است، زمان‌اجرا (runtime) کاملاً آزاده که پیشرفتِ کار رو روی تسک‌های ۲ تا ۱۰ ادامه بده (و جالب اینه که همه‌ی اینا ممکنه روی یک دونه ریسمانِ مشترک اتفاق بیفته)، به جای اینکه اون ریسمان الکی منتظر بشینه و هیچ کاری نکنه (idle). ریسمان‌ها (Threads) *می‌تونن* همین تداخل و هم‌پوشانی (overlap) رو به وجود بیارن، اما spawn کردن ۱۰,۰۰۰ ریسمان سیستم‌عامل برای صبر کردن روی ۱۰,۰۰۰ درخواستِ کُند، خیلی خیلی گرون‌تر (چون هر ریسمانِ OS سربارِ واقعیِ حافظه و زمان‌بندی (scheduling) داره) از ۱۰,۰۰۰ تسکِ بسیار سبک و ارزونِ async تموم می‌شه.
