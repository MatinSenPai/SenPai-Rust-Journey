# راه‌حل

```rust
fn poll(mut self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<Self::Output> {
    if self.remaining == 0 {
        Poll::Ready(self.total_polls)
    } else {
        self.remaining -= 1;
        Poll::Pending
    }
}
```

هر بار فراخوانیِ `poll`، یا کارِ شمارش معکوس رو تموم می‌کنه (`0 == remaining`، و خروجیِ `Ready` همراه با تعداد کل pollها رو برمی‌گردونه) و یا یکی از مقدارش کم می‌کنه و تو خروجی گزارشِ `Pending` می‌ده. به این نکته دقت کن که دستورِ `1 -= self.remaining` اینجا دقیقاً و به طور مستقیم از طریقِ همون `Pin<&mut Self>` کار می‌کنه، اونم بدون اینکه بخواد با دردسرهای مخصوصِ `Pin` سر و کله بزنه — ساختارِ `Countdown` به خودیِ خود `Unpin` هست (یعنی توش هیچ دیتایِ خود-ارجاعی یا self-referential نیست)، پس در عمل `Pin` براش هیچی بیشتر از همون ارجاعِ معمولیِ `mut&` نیست. جایی که سخت‌گیری‌ها و محدودیت‌هایِ `Pin` تازه زبون باز می‌کنن و گاز می‌گیرن، سرِ فیوچرهاییه (futures) که `!Unpin` هستن (یعنی دقیقاً همون فیوچرهایی که بدنه‌ی یه تابع `async fn` تولیدشون می‌کنه، اونم بعد از اینکه یه ارجاع توشون از روی نقطه‌ی `await.` عبور می‌کنه) — که خب این موضوع برای خودش نیازمندِ مطالعه‌ی مجزاست و فعلاً تو حیطه‌ی این درس جا نمی‌گیره.

```rust
pub fn block_on<F: Future + Unpin>(mut future: F) -> F::Output {
    let waker = Waker::noop();
    let mut cx = Context::from_waker(waker);
    loop {
        match Pin::new(&mut future).poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => continue,
        }
    }
}
```

دستورِ `()Waker::noop` یه `Waker` بهمون می‌ده که موقع بیدار شدن مطلقاً هیچ کاری نمی‌کنه — که اتفاقاً برای اینجا کاملاً هم مناسبه، چون این `block_on` هیچ‌وقت در واقعیت تو خواب نمی‌ره که بخواد واسه بیدار شدنش منتظر (wait) بمونه؛ این فقط یه سره و بدونِ هیچ توقفی دور خودش می‌چرخه و همون لحظه دوباره poll می‌کنه. اما یه اجراکننده‌یِ واقعی (real executor) میاد یه `Waker`ِ *واقعی* رو پاس می‌ده تو دلِ متدِ `poll`، یه چیزی که به خودش سیم‌کشی شده، تا وقتی که یه `Future` در حالتی قرار می‌گیره که واقعاً واسه رسیدن داده از I/O صبر کرده، بتونه موقعی که داده رسید متدِ `()waker.wake` رو صدا بزنه — این دقیقاً همون سیگنالیه که اجراکننده با گرفتن اون می‌فهمه «دیگه بیدار شو، برو دوباره این یکی رو poll کن»، و دیگه نیازی نیست با چرخیدن تو یه حلقه‌ی بسته مدام الکی حدس بزنه که چی آماده‌ست و چی نیست. استفاده از متدِ `(Pin::new(&mut future` تو اینجا هم فقط و فقط به خاطر وجود محدودیت `F: Unpin` که رویِ `block_on` اعمال شده بود، یه کار مجاز به حساب میاد — برای یه فیوچر که `!Unpin` باشه، باید به جای این حتماً از ماکروی `!std::pin::pin` (پین کردن روی استک) یا `Box::pin` (پین کردن روی هیپ) استفاده می‌کردی، چون `Pin::new` مشخصاً نوعی رو می‌طلبه که خودش قول و تضمین داده باشه که هیچ مشکلی با انتقال یا move کردن نداره (که اینم دقیقاً همون معنیِ `Unpin` هستش).
