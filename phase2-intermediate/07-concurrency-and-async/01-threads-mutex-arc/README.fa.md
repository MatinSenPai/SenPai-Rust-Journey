# ۰۷.۱ — ریسمان‌ها (Threads)، قفل‌ها (`Mutex`) و `Arc`

## یک ریسمانِ واقعیِ سیستم‌عامل (OS thread)

```rust
use std::thread;

let handle = thread::spawn(|| {
    2 + 2
});

let result = handle.join().unwrap(); // صبر می‌کنه (block می‌کنه) تا ریسمان کارش تموم بشه
```

متدِ `thread::spawn` کلوژر تو رو تحویل می‌ده به سیستم‌عامل، و اونم دقیقاً تو یه ریسمان (thread) کاملاً مجزا تو سطح OS اجراش می‌کنه — یعنی موازی‌سازی (parallelism) واقعی، نه اون همروندیِ همکاری‌طورِ (cooperative) یکی-یکی‌روی-یک-هسته‌ی پایتون که به طور پیش‌فرض بهت می‌ده. (پایتون ریسمان داره، اما وجودِ GIL یا Global Interpreter Lock یعنی تو هر لحظه فقط یکیشون می‌تونه بایت‌کد پایتون رو اجرا کنه؛ تو پایتون اگه موازی‌سازی واقعی بخوای مجبوری بری سراغ `multiprocessing`، که هزینه‌اش ساختنِ پردازش‌های کاملاً جدا (separate processes) هست. ریسمان‌های زبان Rust از همون اول ریسمان‌های واقعی و سخت‌افزاریِ سیستم‌عاملن و هیچ GILی وجود نداره که بخوای دورش بزنی.)

متد `spawn` یه `<JoinHandle<T` برمی‌گردونه، که اون `T` همون چیزیه که کلوژرت برمی‌گردونه. صدا زدنِ `()join.` ریسمان فعلی رو تا زمانی که ریسمانِ تولیدشده (spawned) کارش تموم بشه متوقف (block) می‌کنه، و در نهایت بهت یه خروجی از نوعِ `<Result<T, Box<dyn Any + Send>>` برمی‌گردونه — اگه کلوژر به صورت عادی کارش تموم بشه مقدارش `(Ok(T` می‌شه، و اگه **کرش (panic)** کنه می‌شه `(...)Err`. واسه همینه که تو همه‌ی مثال‌ها `()join().unwrap.` رو می‌بینی: این یعنی داری به صراحت ادعا می‌کنی "من انتظار دارم این ریسمان موفق بشه، اگه نشد و خطا خورد، با کلی سروصدا کلاً پنیک کن." اما تو کدهای مربوط به محیطِ تولید (Production) اگه یه ریسمانِ کارگر (worker) شکست خورد و برنامه می‌تونست این شکست رو تحمل کنه، باید به جای `unwrap` کردن رو اون `Result` یه `match` بزنی و مدیریتش کنی.

## چرا کلوژرهایی که به `spawn` پاس می‌دی حتماً باید `'static` باشن

```rust
let data = vec![1, 2, 3];
let handle = thread::spawn(move || {
    println!("{data:?}"); // متغیر `data` حالا تحتِ **مالکیت (OWNED)** این کلوژره
});
handle.join().unwrap();
```

کلمه‌ی کلیدیِ `move` کلوژر رو مجبور می‌کنه که به جای قرض گرفتن (borrowing)، مالکیتِ (ownership) هر چیزی که داره بهش ارجاع می‌ده (مثل `data`) رو به طور کامل بگیره. این یه کارِ الزامیه و اصلاً سلیقه‌ای و اختیاری نیست: کلوژرِ `spawn` حتماً باید دارای طول‌عمرِ `'static` باشه، یعنی نمی‌تونه به هیچ چیزی ارجاعِ قرضی بده که شاید زودتر از خودِ اون ریسمان از بین بره و بمیره. دلیلش رو تصور کن — تابعی که `spawn` رو صدا زده می‌تونه کارش تموم شه و مقداری رو برگردونه، در نتیجه استکِ فرمش (stack frame - یعنی همون‌جایی که یه `data`ی قرض‌گرفته‌شده داشت توش زندگی می‌کرد) دقیقاً *قبل از اینکه* ریسمانِ تولیدشده اصلاً وقت کنه از اون متغیر استفاده کنه، پاک بشه و از بین بره. کامپایلر هیچ راهی نداره که بتونه اثبات کنه آیا تابعِ والد (parent) منتظرِ ریسمانِ فرزند می‌مونه یا نه، پس خیلی راحت از کامپایل کردن کلوژرِ `spawn`ای که بخواد داده‌های محلی (local) رو قرض بگیره سرباز می‌زنه. تو پایتون دستورِ `((threading.Thread(target=lambda: print(data` بدون اینکه حتی یه لحظه نیاز باشه بهش فکر کنی کار می‌کنه، چون GIL و سیستمِ زباله‌روبِ مبتنی بر شمارشگر ارجاع (reference-counted GC) اون `data` رو تا زمانی که هرچیزی بهش اشاره کنه تو خفا زنده نگه می‌دارن. زبان Rust تصمیم‌گیری راجع‌به این طول‌عمر رو به جای اینکه بذاره واسه یه اتفاقِ شانسی تو زمانِ اجرا (runtime accident)، تبدیلش کرده به یه تصمیمِ زمان کامپایل: و ترکیبِ `move` + گرفتنِ مالکیت، جواب تو به این مسئله‌ست.

## به اشتراک گذاشتنِ داده‌ها بینِ ریسمان‌ها: `<Arc<Mutex<T>>`

به محض اینکه چند تا ریسمان به صورت همزمان به یک دیتای مشترک نیاز پیدا کنن، دو تا مشکلِ *کاملاً جدا از هم* به وجود میاد:

1. **مالکیت (Ownership)** — هر مقداری باید و باید دقیقاً یک مالک داشته باشه، اما اینجا چندین ریسمان می‌خوان دستشون رو روی یه مقدارِ واحد نگه دارن. نوعِ `<Arc<T>` (از ماژول ۰۵) جوابِ این مشکل تو محیط‌های نیازمندِ thread-safe بودنِ کده: تو میای اون `Arc` رو به ازای هر ریسمان یه بار کپی (clone) می‌کنی، و اونوقت هر کدوم از اون کپی‌ها به صورت کاملاً برابر و معتبر، یه مالک برای همون حافظه‌ی مشترک و اصلیِ (underlying allocation) زیرینشون می‌شن.
2. **تغییرپذیری (Mutation)** — اگه قرار باشه هر کدوم از ریسمان‌ها روی اون مقدار مشترک *بنویسن*، اون وقت اگه دوتاشون بخوان همزمان با هم این کار رو بکنن باعث بروز data race می‌شه. نوعِ `<Mutex<T>>` (مخفف "mutual exclusion" یا انحصار متقابل) میاد یه مقدار رو تو دلِ خودش قفل می‌کنه (wrap می‌کنه) تا تو هر لحظه فقط یه ریسمان بتونه بهش دسترسی داشته باشه:

```rust
use std::sync::{Arc, Mutex};

let counter = Arc::new(Mutex::new(0));
let counter2 = Arc::clone(&counter);

thread::spawn(move || {
    let mut guard = counter2.lock().unwrap(); // صبر می‌کنه تا قفل آزاد بشه
    *guard += 1;
    // متغیر `guard` دقیقاً همینجا تو انتهای اسکوپ، پاک (drop) می‌شه — و قفل هم به طور خودکار آزاد می‌شه
}).join().unwrap();
```

متدِ `()lock.` خروجی‌ای از نوعِ `_< ,Result<MutexGuard<T>>` برمی‌گردونه (و فقط تو صورتی بهمون `Err` میده که یه ریسمانِ دیگه در حالی که قفل رو تو دست داشته پنیک کرده باشه، و اصطلاحاً قفل رو "مسموم (poison)" کرده باشه — معمولاً برای راحتی روی این `()unwrap.` صدا می‌زنن). نوعِ `MutexGuard` یه اشاره‌گر هوشمنده (smart pointer): برای اینکه بتونی مقدارِ درونی رو بخونی یا تغییر بدی، اول از روش نشان‌زدایی می‌کنی (`guard*`)، و وقتی که از اسکوپ خارج می‌شه، فرایندِ `Drop` به طور خودکار قفل رو رها (release) می‌کنه — تو تقریباً هیچ‌وقت با دستِ خودت متدِ `()unlock.` رو صدا نمی‌زنی.

**یه تمایز خیلی مهم که این درس اونو ملموسش می‌کنه:** استفاده از ریسمان‌ها (threads) به تنهایی اصلاً نیازی به `Mutex` نداره. تو فقط زمانی به این قفل نیاز پیدا می‌کنی که ریسمان‌ها بخوان با هم یه وضعیتِ *تغییرپذیر (mutable)* رو به اشتراک بذارن. اگه هر ریسمان واسه خودش به صورت کاملاً مستقل یه محاسبه‌ای رو انجام بده و در نهایت جوابش رو از طریق `JoinHandle`ِ خودش برگردونه، دیگه هیچ چیزی واسه قفل کردن وجود نداره — این تفاوت رو با مقایسه کردن دو تا تابعی که تو پایین اومده دقیق متوجه می‌شی.
