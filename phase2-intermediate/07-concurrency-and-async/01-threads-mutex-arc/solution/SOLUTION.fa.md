# راه‌حل

```rust
pub fn sum_in_threads(nums: Vec<i32>, thread_count: usize) -> i32 {
    let thread_count = thread_count.max(1);
    let chunk_size = nums.len().div_ceil(thread_count).max(1);
    let chunks: Vec<Vec<i32>> = nums.chunks(chunk_size).map(|c| c.to_vec()).collect();

    let handles: Vec<_> = chunks
        .into_iter()
        .map(|chunk| thread::spawn(move || chunk.iter().sum::<i32>()))
        .collect();

    handles.into_iter().map(|h| h.join().unwrap()).sum()
}
```

هر ریسمان برای خودش یه بخشِ (chunk) **دارایِ مالکیتِ (owned)** مجزا از نوعِ `<Vec<i32>` دریافت می‌کنه (از طریق `.to_vec()` که یه کپی از اون تیکه‌ی بُرش رو می‌سازه) و کاملاً و مطلقاً مستقل از بقیه، عملِ جمع رو روش محاسبه می‌کنه — هیچ‌چیزی *در حینِ اجرای ریسمان‌ها* بینشون به اشتراک گذاشته نمی‌شه، در نتیجه اصلاً هیچ‌چیزی وجود نداره که بخوایم با یه `Mutex` ازش محافظت کنیم. تنها "به اشتراک‌گذاری" زمانی رخ می‌ده که کار همه‌ی ریسمان‌ها کاملاً تموم شده باشه، اونم روی ریسمانِ اصلی (main thread) و از طریق `.join()` که خروجیِ تک‌تک ریسمان‌ها رو جمع‌آوری می‌کنه — که تو اون نقطه همه چیز کاملاً ترتیبی (sequential) و تو همون یه دونه ریسمانِ اصلی اتفاق می‌افته.

```rust
pub fn count_matching_in_threads(items: Vec<i32>, predicate: fn(i32) -> bool) -> i32 {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();
    for item in items {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            if predicate(item) {
                *counter.lock().unwrap() += 1;
            }
        }));
    }
    for handle in handles {
        handle.join().unwrap();
    }
    let final_count = *counter.lock().unwrap();
    final_count
}
```

حواست باشه که اون دو خطِ آخر **با هم ادغام (collapsed) نشدن** تا مستقیماً یه عبارت بازگشتیِ نهایی (tail expression) به شکلِ `()counter.lock().unwrap*` رو بسازن. اگه اونطوری می‌نوشتی با خطای `error[E0597]: borrowed value does not live long enough` موقع کامپایل مواجه می‌شدی — طبقِ قوانینی که کامپایلر برای طولِ‌عمرِ موقتِ عبارات بازگشتی نهایی داره، سعی می‌کنه تا اون محافظِ موقتیِ `MutexGuard` رو (که داره از `counter` قرض می‌گیره) دقیقاً به اندازه‌ی خودِ متغیرِ `counter` زنده نگه داره، و این موضوع تو نقطه‌ای که کل متغیرهای محلی (locals) مربوط به اون بلوکِ کد می‌خوان پاک بشن (drop بشن)، باعث ایجادِ تعارض و کلاَش می‌شه. با نسبت‌دادن (binding) اون مقدار نشان‌زدایی‌شده (و در نتیجه `Copy` شده، چون از جنس `i32` هستش) به متغیرِ `final_count` تو *همون ابتدا*، قرضِ (borrow) مربوط به اون محافظ بلافاصله و قبل از اینکه `counter` بخواد پاک (drop) بشه، به پایان می‌رسه، و در نهایت فقط همون متغیرِ ساده‌ی `i32` به عنوان خروجیِ تابع باقی می‌مونه و جون سالم به در می‌بره. این قضیه یه برهم‌کنشِ به شدت حساس و خطرناک بین `MutexGuard` و قوانین مربوط به ترتیبِ پاک‌شدن (drop-order rules) تو عبارت‌های بازگشتیِ نهاییِ Rust هستش — و اصلاً یه سناریوی فرضی و تئوری (hypothetical) نیست که بخوای نادیده‌اش بگیری.

اینجا چون هر ریسمانی مجبوره دقیقاً همون *یک دونه* شمارنده‌ی مشترک رو آپدیت کنه، اون شمارنده پیچیده شده داخل یه `<Mutex<i32>` (تا همیشه تو هر لحظه فقط یک ریسمان بتونه بهش دسترسی انحصاری داشته باشه) و خودش هم پیچیده شده تو دلِ یه `Arc` (تا هر ریسمانی بتونه کاملاً مستقل از بقیه، *مالکِ (own)* یه دستگیره به همون `Mutex`ِ مشترک بشه — یه `<Mutex<i32>`ِ خالی رو نمی‌شه به داخلِ بیشتر از یه کلوژر انتقال (move) داد، چون کلمه‌ی `move` هر کلوژر رو مجبور می‌کنه که مالکیتِ هر چیزی رو که اسیر می‌کنه به طور کامل در دست بگیره، و از طرفی هیچ مقداری نمی‌تونه همزمان بیشتر از یه مالک داشته باشه).

در مورد سؤال ۲ مرور: بدونِ حضور `Arc`، اگه بنویسی `;let counter = Mutex::new(0)` و بعدش بخوای این `counter` رو با `move` به داخلِ دو تا کلوژر `thread::spawn`ِ کاملاً مجزا بفرستی، مستقیماً با **خطای کامپایل (compile error)** مواجه می‌شی — کلوژرِ دوم در واقع داره تلاش می‌کنه مقداری رو که قبلاً توسط کلوژرِ اول انتقال داده شده و تصاحب شده بود رو دوباره انتقال بده؛ این دقیقاً همون خطایِ آشنایِ "استفاده از متغیر بعد از انتقال یا used after move" هستش که تو درس‌های مالکیت تو فاز ۱ باهاش دست‌وپنجه نرم کردی، فقط این‌بار به جای اینکه تو یه فراخوانی ساده‌ی تابع خودش رو نشون بده، داره سر از مرزهای مربوط به `thread::spawn` درمیاره. متدِ `Arc::clone` خیلی هوشمندانه این مانع رو دور می‌زنه: به جای اینکه سعی کنه خودِ اون `Mutex` رو بیشتر از یک بار انتقال (move) بده، میاد به هر ریسمانی یه کپیِ کاملاً مستقل، ارزون و *شمرده‌شده از روی ارجاع (reference-counted)* می‌ده که همون نقشِ دستگیره به سمت `Mutex`ِ مشترک رو بازی می‌کنه.
