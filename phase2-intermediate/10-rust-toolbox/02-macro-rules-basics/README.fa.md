# ۲.۱۰.۲ — مبانیِ `macro_rules!`

## در یک نگاه

بعد از این درس می‌توانی:

- یک جفتِ تطبیق‌دهنده/نسخه‌نویس با `macro_rules!` بنویسی، از مشخص‌کننده‌هایِ قطعه (`expr`، `ident`، `ty`، `pat`، `literal`، `tt`) درست استفاده کنی، و حدس بزنی یک فراخوانیِ مشخص دقیقاً به چه توکن‌هایی بسط پیدا می‌کند.
- از تکرار (`$(...)*`، `+`، `?`) برایِ پذیرفتنِ تعدادِ متغیری از آرگومان استفاده کنی، و توضیح بدهی چرا بهداشتِ ماکرو نمی‌گذارد `let`ِ خودِ ماکرو با متغیرِ هم‌نامِ فراخواننده تداخل کند.
- خطایِ واقعیِ کامپایلر را که از یک مشخص‌کننده‌ی قطعه‌یِ غلط می‌آید بخوانی و رفعش کنی، و تصمیم بگیری کِی ماکرو واقعاً ابزارِ درستی است و کِی یک تابعِ ساده یا جنریک کافی‌ست.

**زمان:** حدود ۷۰ دقیقه · **پیش‌نیاز:** [۲.۱۰.۱ — تطبیقِ الگو از نزدیک](../01-pattern-matching-depth/README.fa.md)

## چرا اهمیت دارد

از همان اولین `println!`ی که نوشتی، داشتی ماکرو صدا می‌زدی — همان علامتِ `!` نشانه‌اش بود. این درس درباره‌ی نوشتنِ ماکروی خودت است، با `macro_rules!`، سیستمِ ماکروی اعلانیِ Rust. ماکروهایِ رویه‌ای — مثلِ `#[derive(Serialize)]` — مکانیزمِ کاملاً جداگانه و سنگین‌تری‌اند که این دوره اصلاً سراغش نمی‌رود؛ همین را دانستن کافی است.

پایتون معادلِ واقعی‌ای برایِ این ندارد. دکوراتور و متاکلاس یک *شیء را در زمانِ اجرا* تغییر می‌دهند؛ یک ماکرو *کدِ منبع را در زمانِ کامپایل* تغییر می‌دهد — توکن‌هایی را که تو نوشته‌ای می‌گیرد و پیش از آنکه کامپایلرِ اصلی اصلاً چشمش به آن‌ها بیفتد، به توکن‌هایِ تازه بسطشان می‌دهد.

دلیلِ اینکه چرا Rust به این نیاز دارد و پایتون نه، یک چیزِ ساده است: توابعِ پایتون `*args` می‌گیرند و ورودی‌شان می‌تواند هر نوعی باشد، پس `max(a, b, c)` واقعاً فقط یک تابعِ معمولی است. توابعِ Rust تعدادِ ورودیِ ثابت و نوعِ ثابت دارند — پس هر چیزِ متغیر-آرگومان، مثلِ `println!`، `vec!` و `format!`، *مجبور* است ماکرو باشد؛ هیچ امضایِ تابعی نیست که «هر تعداد آرگومان، از هر نوعی» را بگیرد.

## مفهوم

### تطبیق‌دهنده و نسخه‌نویس

یک تعریفِ `macro_rules!` فهرستی از بازوهاست، هرکدام به شکلِ `(تطبیق‌دهنده) => { نسخه‌نویس }`. تطبیق‌دهنده (matcher) الگویی رویِ *توکن‌هاست* — دقیقاً مثلِ `match`، فقط این‌بار رویِ کدِ منبع؛ نسخه‌نویس (transcriber) قالبی است که توکن‌هایِ اسیرشده تویش جاگذاری می‌شوند:

```rust
macro_rules! square {
    ($x:expr) => {
        $x * $x
    };
}
```

`$x:expr` یک **مشخص‌کننده‌ی قطعه (fragment specifier)** است: می‌گوید «یک *عبارت* کامل را بگیر و اسمش را بگذار `$x`». یک `expr`ِ اسیرشده در بسط اتمی می‌ماند — گروه‌بندیِ خودش را همان‌جایی که اسیر شده نگه می‌دارد:

```rust
let a = square!(1 + 2);
println!("square!(1 + 2) = {a}");
```

```text
square!(1 + 2) = 9
```

`square!(1 + 2)` از نظرِ مفهومی به `(1 + 2) * (1 + 2)` بسط پیدا می‌کند، نه به `1 + 2 * 1 + 2` — وگرنه جواب می‌شد ۵، نه ۹.

```senpai-visual
{"kind":"concept","labels":["your tokens: square!(1 + 2)","matcher: $x:expr","transcriber template: $x * $x","expansion: (1 + 2) * (1 + 2)","compiler compiles the expansion"]}
```

نکته‌ای که کمتر کسی اول‌بار می‌بیند: چون `$x` تویِ نسخه‌نویس دوبار جاگذاری شده، هر عبارتی که پاس بدهی هم دوبار حساب می‌شود — نه یک‌بار:

```rust
let mut calls = 0;
let mut next = || {
    calls += 1;
    calls
};
let b = square!(next());
println!("square!(next()) = {b}, next() ran {calls} times");
```

```text
square!(next()) = 2, next() ran 2 times
```

`next()` یک‌بار به‌جایِ `$x`ِ اول و یک‌بار به‌جایِ `$x`ِ دوم اجرا می‌شود؛ اولی ۱ برمی‌گرداند، دومی ۲، ضرب‌شان می‌شود ۲ — نه مربعِ هیچ‌کدام. برایِ کارِ واقعی باید اول `$x` را تویِ یک `let` بریزی تا فقط یک‌بار حساب شود؛ `timed!` تویِ تمرین‌ها دقیقاً همین را از تو می‌خواهد.

### مشخص‌کننده‌های قطعه‌ی دیگر

`expr` را دیدی. باقیِ مشخص‌کننده‌هایی که واقعاً به کارت می‌آیند:

- `ident` — یک نام؛ برایِ ساختنِ متغیر یا تابعِ تازه، جایی که `expr` اصلاً اجازه نمی‌دهد.
- `ty` — یک نوع.
- `pat` — یک الگو؛ همان چیزی که ۲.۱۰.۱ رویش وقت گذاشت — یک بازویِ `match`، یا سمتِ چپِ یک `let`.
- `literal` — یک لیترالِ خام.
- `tt` — یک «درختِ توکنِ خام»: یک توکنِ تک، یا هرچه داخلِ یک جفتِ `()`، `[]` یا `{}` باشد؛ راهِ فرار، برایِ وقتی هیچ مشخص‌کننده‌ی دیگری جور در نمی‌آید.

نکته‌ی مهم: هر قطعه‌ی اسیرشده، بعدِ اسیر شدن، **مات (opaque)** می‌ماند — یک `expr` را نمی‌شود بعداً جایی گذاشت که یک `ident` یا یک `pat` می‌خواهد؛ مشخص‌کننده تعیین می‌کند قطعه چه نقشی می‌تواند بازی کند، نه محتوایِ واقعی‌اش. «خطاهایی که خواهی دید» دقیقاً همین را نشانت می‌دهد.

### تکرار

`$( ... )` با یکی از سه علامتِ `*` (صفر یا چند بار)، `+` (یک یا چند بار) یا `?` (صفر یا یک بار) بعدش، یک گروه را همان‌قدر بار تطبیق می‌دهد که در ورودی تکرار شده — و همان نحو را در نسخه‌نویس هم به‌کار می‌بری تا مقدارهایِ اسیرشده را دوباره پخش کنی:

```rust
macro_rules! string_vec {
    () => {
        Vec::<String>::new()
    };
    ( $( $s:expr ),+ $(,)? ) => {{
        let mut v = Vec::new();
        $( v.push($s.to_string()); )+
        v
    }};
}
```

بازویِ دوم می‌گوید: یک یا چند `expr`، با کاما جدا (`$( $s:expr ),+`)، به‌علاوه‌ی یک کامایِ انتهاییِ اختیاری (`$(,)?` — همان ادبِ رایجی که هر ماکروی توکاری هم رعایت می‌کند). نسخه‌نویسش یک بلوک است — دو آکولادِ تودرتو، بیرونی مالِ بازو و درونی مالِ خودِ بلوک — که یک `Vec` می‌سازد و با `$( v.push($s.to_string()); )+` یک‌بار به‌ازایِ هر عنصر پرش می‌کند:

```rust
let empty: Vec<String> = string_vec![];
let names = string_vec!["hero", "mage", "sage"];
let trailing = string_vec!["one", "two",];
println!("empty:    {empty:?}");
println!("names:    {names:?}");
println!("trailing: {trailing:?}");
```

```text
empty:    []
names:    ["hero", "mage", "sage"]
trailing: ["one", "two"]
```

بازوها همیشه از بالا به پایین امتحان می‌شوند — اولین تطبیق‌دهنده‌ای که با ورودی جور دربیاید برنده است. همین‌جا هم دو بازو لازم بود، نه یکی: اگر تنها بازو با `$( $s:expr ),*` (ستاره، نه بعلاوه) نوشته می‌شد، حالتِ خالی هم باهاش جور در می‌آمد، ولی نسخه‌نویسش همچنان `let mut v = Vec::new();` تولید می‌کرد — و `mut` رویِ متغیری که تویِ آن مسیر هیچ‌وقت تغییر نمی‌کند، یک اخطار است. جدا کردنِ حالتِ خالی به بازویِ خودش، هر دو خروجی را بی‌اخطار نگه می‌دارد.

یک بازو می‌تواند خودِ ماکرو را هم دوباره صدا بزند — بازگشت، دقیقاً همان‌طور که یک تابع می‌تواند خودش را صدا بزند. مثلِ هر بازگشتی، به یک **بازویِ پایه** نیاز دارد که برایِ کوچک‌ترین ورودی جواب بدهد و ادامه‌ی بازگشت را متوقف کند — «خطاهایی که خواهی دید» نشانت می‌دهد وقتی این بازو را فراموش کنی چه اتفاقی می‌افتد. وقتی ماکرویی که تعریفش می‌کنی، درونِ نسخه‌نویسِ خودش دوباره خودش (یا ماکروی دیگری از همان کریت) را صدا می‌زند، بهتر است با `$crate::` صدایش بزنی، نه با اسمِ لخت — این بعدِ «بهداشت» توضیحش می‌آید.

### بهداشت، در یک پاراگراف

نام‌هایی که *داخلِ* نسخه‌نویسِ یک ماکرو تعریف می‌شوند، در دامنه‌ی خودشان زندگی می‌کنند: اگر نسخه‌نویسِ یک ماکرو `let start = ...;` بسازد، و فراخواننده هم از قبل متغیری به همین اسمِ `start` داشته باشد، تداخلی رخ نمی‌دهد — از نظرِ کامپایلر، `start`ِ داخلِ ماکرو و `start`ِ فراخواننده دو نامِ کاملاً متفاوت‌اند، هرچند هجی‌شان یکی است. به این می‌گویند **بهداشت (hygiene)**، و همین است که ماکروهایِ Rust را از فاجعه‌هایِ کلاسیکِ `#define` در C دور نگه می‌دارد:

```rust
macro_rules! double_it {
    ($x:expr) => {{
        let start = $x;
        start + start
    }};
}
```

```rust
let start = 100;
let doubled = double_it!(7);
println!("caller's start: {start}");
println!("double_it!(7):  {doubled}");
```

```text
caller's start: 100
double_it!(7):  14
```

فراخواننده‌یِ `double_it!(7)` هیچ‌وقت متوجه نمی‌شود که نسخه‌نویس هم یک متغیرِ `start` دارد — و `start`ِ خودش هم دست‌نخورده می‌ماند. روی سکه‌ی دیگر: یک ماکرو *نمی‌تواند* یواشکی متغیری برایِ فراخواننده تعریف کند که او بعداً به اسمش برسد — که خودِ همین محدودیت یک قابلیت است، نه نقص.

این بهداشت فقط شاملِ نام‌هایِ محلی می‌شود — مسیرها و آیتم‌ها همچنان از دیدِ محلِ فراخوانی حل می‌شوند. برایِ همین است که `$crate` وجود دارد: داخلِ نسخه‌نویس، همیشه به کریتی اشاره می‌کند که خودِ ماکرو در آن تعریف شده، مهم نیست چه کریتی دارد صدایش می‌زند — اسکلتِ تمرین‌ها همین الگو را در هر تماسِ `$crate::unsolved(...)` نشانت می‌دهد.

### کِی ماکرو *ننویسی* (راهنماییِ صادقانه)

سراغِ ماکرو **آخرین** برو. یک تابعِ معمولی همان‌طور که نوشته شده چک می‌شود، نوعِ واقعی را در پیامِ خطا نشان می‌دهد، و کاملاً زیرِ پوششِ rust-analyzer است؛ یک ماکرو در هر بسط جداگانه چک می‌شود، خطاهایش به کدِ تولیدشده اشاره می‌کنند نه به چیزی که تو نوشته‌ای، و تکمیلِ خودکار داخلش ضعیف است. برایِ «همان منطق، رویِ چند نوع»، جنریک‌ها از قبل کافی‌اند.

دلیل‌هایِ واقعی و محدودند: ورودیِ متغیر (`max_of!`)، سینتکسی که یک تابع اصلاً نمی‌تواند بپذیرد (`"k" => "v"` یک عبارتِ معتبر نیست، پس `string_map!` مجبور است ماکرو باشد)، پیچیدنِ یک عبارت با کدِ قبل‌وبعد بدونِ اجبار به کلوژر (`timed!`)، و تولیدِ آیتم‌هایِ تکراری. اگر یک `fn` ساده برایِ مسئله‌ات کامپایل می‌شود، نسخه‌ی ماکرویش بدتر است. همین.

## خطاهایی که خواهی دید

### `E0425` — مشخص‌کننده‌ی قطعه‌ی غلط: یک `expr` را نمی‌شود جایِ یک نام گذاشت

```text
error[E0425]: cannot find value `x` in this scope
  --> phase2-intermediate\10-rust-toolbox\02-macro-rules-basics\examples\04-wrong-fragment-specifier-broken.rs:12:15
   |
12 |     make_var!(x);
   |               ^ not found in this scope

error[E0425]: cannot find value `x` in this scope
  --> phase2-intermediate\10-rust-toolbox\02-macro-rules-basics\examples\04-wrong-fragment-specifier-broken.rs:13:16
   |
13 |     println!("{x}");
   |                ^ not found in this scope

error: arbitrary expressions aren't allowed in patterns
  --> phase2-intermediate\10-rust-toolbox\02-macro-rules-basics\examples\04-wrong-fragment-specifier-broken.rs:12:15
   |
12 |     make_var!(x);
   |               ^
   |
   = note: the `expr` fragment specifier forces the metavariable's content to be an expression

For more information about this error, try `rustc --explain E0425`.
```

**کامپایلر به چه اعتراض دارد:** تطبیق‌دهنده‌یِ `make_var!` نوشته `($name:expr) => { let $name = 5; };` — یعنی `$name` را به‌عنوانِ یک **عبارت** اسیر می‌کند. ولی تویِ نسخه‌نویس، `$name` سمتِ چپِ یک `let` نشسته، جایی که کامپایلر یک **الگو** (اسمِ یک متغیرِ تازه) می‌خواهد، نه یک عبارت. همان‌طور که بخشِ «مفهوم» گفت، یک قطعه‌ی `expr` بعدِ اسیر شدن مات می‌ماند — نمی‌شود جایِ دیگری، با نقشِ دیگری، دوباره تفسیرش کرد. خودِ یادداشتِ کامپایلر همین را می‌گوید.

**راه‌حل:** مشخص‌کننده را عوض کن، نه شکلِ نسخه‌نویس را:

```rust
macro_rules! make_var {
    ($name:ident) => {
        let $name = 5;
    };
}
```

**چرا این راه‌حل است:** `ident` می‌گوید «یک نام را اسیر کن»، نه «یک عبارت را حساب کن». حالا `$name` دقیقاً همان نقشی را دارد که `let` می‌خواهد، و `make_var!(x)` واقعاً یک متغیرِ تازه به اسمِ `x` می‌سازد.


**کامپایلر به چه اعتراض دارد:** `largest_of!` فقط یک بازو دارد: `( $first:expr, $( $rest:expr ),+ $(,)? )` — یعنی «حداقل دو آرگومان: یکی جدا، و حداقل یکیِ دیگر با کاما بعدش». فراخوانیِ بازگشتیِ `largest_of!( $( $rest ),+ )` وقتی به تنها یک آرگومانِ باقی‌مانده می‌رسد (اینجا: `7`)، دیگر کامایی برایِ تطبیق با همان یک بازو ندارد — و چون بازویِ دیگری هم نیست که یک آرگومانِ تنها را بپذیرد، بسط همان‌جا با شکست متوقف می‌شود. این حتی خطایِ نوع یا قرض هم نیست؛ کامپایلر دارد می‌گوید خودِ فراخوانیِ ماکرو ناتمام مانده.

**راه‌حل:** یک بازویِ پایه برایِ حالتِ تک‌آرگومانی اضافه کن:

```rust
macro_rules! largest_of {
    ( $only:expr ) => {
        $only
    };
    ( $first:expr, $( $rest:expr ),+ $(,)? ) => {
        std::cmp::max($first, largest_of!( $( $rest ),+ ))
    };
}
```

**چرا این راه‌حل است:** حالا وقتی بازگشت به یک آرگومانِ تنها می‌رسد، بازویِ اول (`$only:expr`) پیش از بازویِ بازگشتی امتحان می‌شود و جور در می‌آید — بازوها همیشه از بالا به پایین امتحان می‌شوند. بازگشت دقیقاً همان‌جا متوقف می‌شود که باید: `largest_of!(3, 9, 7)` می‌شود `max(3, largest_of!(9, 7))`، و همان الگو برایِ `largest_of!(9, 7)` هم تکرار می‌شود، تا اینکه `largest_of!(7)` به بازویِ پایه برسد.

## تمرین

### گرم‌کردن

<details>
<summary>با تعریفِ <code>macro_rules! square { ($x:expr) => { $x * $x }; }</code>، آیا <code>square!(1 + 2)</code> به <code>1 + 2 * 1 + 2</code> بسط پیدا می‌کند یا به <code>(1 + 2) * (1 + 2)</code>؟</summary>

قبل از دیدنِ جواب، خودت فکرش را بکن.

</details>

<details>
<summary>پاسخ</summary>

به `(1 + 2) * (1 + 2)`. یک `expr`ِ اسیرشده در بسط اتمی می‌ماند — گروه‌بندیِ خودش را همان‌جایی که اسیر شده نگه می‌دارد، پس `$x * $x` نمی‌تواند تصادفی با عملگرهایِ خودِ فراخواننده قاطی شود. خودت هم می‌توانی چکش کنی: `square!(1 + 2)` برابرِ ۹ است، نه ۵.

</details>

<details>
<summary>نسخه‌نویسِ <code>timed!</code> خطِ <code>let start = Instant::now();</code> را می‌سازد. اگر کدِ فراخواننده هم از قبل متغیری به اسمِ <code>start</code> داشته باشد، این دو تداخل پیدا می‌کنند؟</summary>

قبل از دیدنِ جواب، خودت فکرش را بکن.

</details>

<details>
<summary>پاسخ</summary>

نه. نام‌هایی که *داخلِ* نسخه‌نویسِ یک ماکرو تعریف می‌شوند، در دامنه‌ی خودشان زندگی می‌کنند — بهداشت، `start`ِ داخلِ ماکرو را از `start`ِ فراخواننده جدا نگه می‌دارد، حتی با اینکه هجی‌شان یکی است.

</details>

<details>
<summary>یک ماکرو دو بازو دارد: <code>($only:expr)</code> و <code>($first:expr, $($rest:expr),+)</code>. <code>max_of!(41)</code> با کدام بازو جور درمی‌آید؟ <code>max_of!(3, 9, 7)</code> چطور؟</summary>

قبل از دیدنِ جواب، خودت فکرش را بکن.

</details>

<details>
<summary>پاسخ</summary>

`max_of!(41)` — یک آرگومان، بدونِ کاما — فقط با بازویِ اول جور درمی‌آید. `max_of!(3, 9, 7)` با بازویِ دوم جور درمی‌آید، چون شکلِ کاما-جدایِ `$first, $rest` را می‌خواهد که بازویِ اول نمی‌تواند بدهد. بازوها همیشه از بالا به پایین امتحان می‌شوند؛ اگر بازویِ اول هم می‌توانست با `3, 9, 7` جور دربیاید، همان برنده بود.

</details>

<details>
<summary>با تطبیق‌دهنده‌یِ <code>( $( $key:expr => $value:expr ),+ $(,)? )</code>، آیا <code>string_map! { "k" => "v", }</code> (با کامایِ انتهایی) جور درمی‌آید؟</summary>

قبل از دیدنِ جواب، خودت فکرش را بکن.

</details>

<details>
<summary>پاسخ</summary>

بله. `$(,)?` دقیقاً صفر یا یک کامایِ انتهایی را بعدِ آخرین عضوِ تکرار قبول می‌کند — همان ادبی که هر ماکروی توکاری (`vec!`، `println!`) هم رعایت می‌کند.

</details>

### تعمیر

هر دو مثالِ خراب را درست کن:

۱. `examples/04-wrong-fragment-specifier-broken.rs` را طوری درست کن که `make_var!(x)` واقعاً `x` را به یک متغیر بسط بدهد — مشخص‌کننده‌ی قطعه را عوض کن، نه شکلِ نسخه‌نویس را.
۲. `examples/05-missing-base-case-broken.rs` را طوری درست کن که `largest_of!(3, 9, 7)` واقعاً کامپایل و اجرا شود — یک بازویِ پایه برایِ حالتِ تک‌آرگومانی اضافه کن.

### پیاده‌سازی

سه ماکرو در `src/lib.rs` — مشخصاتِ کاملِ هرکدام همان کامنتِ مستنداتش است:

```sh
cargo test -p p2-10-02-macro-rules-basics
```

- `string_map! { "k" => "v", ... }` — یک `HashMap<String, String>` می‌سازد؛ تکرار، به‌علاوه‌ی توکنِ `=>` تویِ خودِ تطبیق‌دهنده.
- `max_of!(a, b, c, ...)` — بیشینه‌یِ متغیر-آرگومان، با بازگشت و یک بازویِ پایه.
- `timed!(expr)` — عبارت را دقیقاً یک‌بار حساب می‌کند، خروجی‌اش جفتِ `(result, elapsed)` است.

هر سه، تا وقتی بازنویسی‌شان نکنی، به یک تابعِ کمکیِ پنیک‌کننده به اسمِ `unsolved` بسط پیدا می‌کنند — کریت کامپایل می‌شود، ولی `cargo test` شکست می‌خورد. `unsolved`ها را یکی‌یکی پاک کن.

### بساز

`min_of!(a, b, c, ...)` را خودت طراحی و بنویس — همتایِ کوچکِ `max_of!`: هر تعداد آرگومان ≥ ۱، هر نوعی که `Ord` باشد، خروجی‌اش کوچک‌ترینِ آن‌هاست. هیچ اسکلتی تویِ `src/lib.rs` منتظرش نیست و هیچ تستِ پنهانی هم چکش نمی‌کند — برایِ خودت چک کن: `min_of!(3, 9, 7)` باید `3` بدهد، `min_of!(41)` باید `41` بدهد.

اگر دلت یک چیزِ دیگر خواست: یک `debug_print!(expr)`ِ کوچک بنویس که چیزی مثلِ `[file:line] expr = value` چاپ کند — با `file!()`، `line!()` و `stringify!()`. اگر این را نوشتی، تبریک می‌گویم: داری نسخه‌یِ خودت از `dbg!`ِ کتابخانه‌ی استاندارد را می‌سازی.

### چالش (اختیاری)

**بخشِ یک.** یک `list_of!` بنویس که هم لیستِ کاما-جدا و هم لیستِ سمیکالن-جدا را قبول کند:

```rust
let a: Vec<i32> = list_of!(1, 2, 3);
let b: Vec<i32> = list_of!(1; 2; 3);
```

هر دو باید `[1, 2, 3]` بدهند. سرنخ: دو بازویِ جدا بنویس، یکی برایِ هر جداکننده؛ چون تطبیق‌دهنده‌ها همیشه از بالا به پایین امتحان می‌شوند و یک `$x:expr` رویِ کاما یا سمیکالن نمی‌ایستد، هر ورودی فقط با یکی از دو بازو جور درمی‌آید.

**بخشِ دو** (این یکی به جلو نگاه می‌کند). همه‌ی ماکروهایی که تویِ این درس نوشتی، حداکثر یک لایه تکرار داشتند. یک **تی‌تی‌مانچر (tt muncher)** — تکنیکی که یک لیستِ توکنِ دلخواه را یکی‌یکی، از جلو، با بازگشت می‌جود — می‌تواند شکل‌هایِ خیلی پیچیده‌تری را هم بپذیرد. این درس سراغش نمی‌رود؛ اگر کنجکاو شدی، «بیشتر» پایینِ همین صفحه نشانت می‌دهد کجا دنبالش بگردی.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| ماکروی اعلانی (`macro_rules!`) | سیستمِ ماکرونویسیِ Rust: یک ماکرو را با بازوهایِ تطبیق‌دهنده/نسخه‌نویس تعریف می‌کند | هر جا خودِ سینتکس باید متغیر یا تازه باشد |
| تطبیق‌دهنده (matcher) | نیمه‌یِ الگوییِ یک بازو — با توکن‌هایِ فراخوانی تطبیق می‌کند | هر بازویِ `macro_rules!` |
| نسخه‌نویس (transcriber) | نیمه‌یِ قالبیِ یک بازو — توکن‌هایی که فراخوانی بهشان بسط پیدا می‌کند | هر بازویِ `macro_rules!` |
| مشخص‌کننده‌ی قطعه (fragment specifier) | `expr`، `ident`، `ty`، `pat`، `literal`، `tt` — می‌گوید یک قطعه‌ی اسیرشده چه‌جور توکنی می‌تواند باشد | هر متغیرِ `$name:specifier` در یک تطبیق‌دهنده |
| تکرار (`$(...)*`/`+`/`?`) | یک گروه را صفر-یا-چند، یک-یا-چند، یا صفر-یا-یک بار تطبیق و بازپخش می‌کند | ماکروهایِ متغیر-آرگومان |
| بهداشت (hygiene) | نام‌هایِ داخلِ یک ماکرو نمی‌توانند با نام‌هایِ فراخواننده تداخل کنند | هر `let` که تویِ نسخه‌نویس ساخته می‌شود |
| `$crate` | همیشه به کریتی اشاره می‌کند که خودِ ماکرو در آن تعریف شده، مهم نیست چه کریتی صدایش می‌زند | ماکروهایِ بازگشتی یا خودارجاع |

### الان می‌دانی

- یک تعریفِ `macro_rules!` فهرستی از بازوهاست، هرکدام «تطبیق‌دهنده => نسخه‌نویس»؛ اولین بازویی که با توکن‌هایِ فراخوانی جور دربیاید برنده است.
- یک `expr`ِ اسیرشده اتمی و مات می‌ماند — گروه‌بندی‌اش را نگه می‌دارد، و بعداً نمی‌شود با نقشِ دیگری، مثلاً یک نامِ متغیر، دوباره تفسیرش کرد.
- `$(...)*`/`+`/`?` یک گروهِ اسیرشده را صفر-یا-چند، یک-یا-چند، یا صفر-یا-یک بار در تطبیق‌دهنده و نسخه‌نویس تکرار می‌کند.
- بهداشت تضمین می‌کند نامی که یک ماکرو خودش می‌سازد با نامِ هم‌هجایِ فراخواننده تداخل نکند — ولی همین قاعده یعنی یک ماکرو هم نمی‌تواند یواشکی متغیری برایِ فراخواننده بسازد؛ فقط نام‌هایِ محلی این‌طورند، نه مسیرها، که برایشان `$crate` هست.
- ماکرویِ بازگشتی به یک بازویِ پایه نیاز دارد، وگرنه بسط جایی برایِ توقف ندارد.
- سراغِ ماکرو وقتی می‌روی که یک تابعِ ساده یا جنریک واقعاً نمی‌تواند مسئله را حل کند — ورودیِ متغیر، سینتکسِ غیرِعبارتی، یا پیچیدنِ کدِ قبل‌وبعدِ یک عبارت.

### بعداً کامل‌تر می‌بینی

- **فیچرهایِ Cargo و کامپایلِ شرطی** — همین لحظه از یک فیچر (`broken`) استفاده کردی تا مثال‌هایِ خراب را پشتِ یک پرچم نگه‌داری؛ ۲.۱۰.۳ دقیقاً همین مکانیزم را کاملش می‌کند: [۲.۱۰.۳ — فیچرهایِ cargo](../03-cargo-features/README.fa.md)

### می‌توانی توضیح بدهی؟

- چرا `square!(1 + 2)` به `(1 + 2) * (1 + 2)` بسط پیدا می‌کند، نه به `1 + 2 * 1 + 2`؟
- بهداشت دقیقاً چه چیزی را تضمین می‌کند، و چه چیزی را تضمین نمی‌کند؟
- چرا یک ماکروی بازگشتی مثلِ `max_of!` به یک بازویِ پایه نیاز دارد؟ اگر نداشته باشد چه اتفاقی می‌افتد؟
- فرقِ `$( ... )*`، `$( ... )+` و `$( ... )?` چیست؟
- یک مسئله‌یِ واقعی مثال بزن که یک تابعِ ساده حلش می‌کرد، ولی کسی به‌جایش ماکرو نوشته بود — یا برعکس، جایی که فقط ماکرو جواب می‌داد.
