# راه‌حل

```rust
#[macro_export]
macro_rules! string_map {
    () => {
        ::std::collections::HashMap::new()
    };
    ( $( $key:expr => $value:expr ),+ $(,)? ) => {{
        let mut map = ::std::collections::HashMap::new();
        $( map.insert($key.to_string(), $value.to_string()); )+
        map
    }};
}
```

چرا دو بازو؟ یک بازوی تنها با `$( ... ),*` حالتِ خالی را هم پوشش می‌داد —
ولی آن‌وقت بسطِ حالتِ خالی هم می‌شد `let mut map = ...; map`، و `mut`
روی متغیری که هیچ‌وقت تغییر نمی‌کند، یک اخطار است. جدا کردنِ بازویِ پایه،
هر دو خروجی را بی‌اخطار نگه می‌دارد. بازویِ جفت‌ها دو الگو را نشان می‌دهد
که تا ابد به کارت می‌آیند: آکولادِ دوتایی `{{ ... }}` (آکولادِ بیرونی
مالِ بازویِ ماکرو، آکولادِ درونی مالِ خودِ عبارتِ بلوک — پس بسط هم می‌تواند
دستور داشته باشد و هم مقدار برگرداند)، و `$( ... )+` در نسخه‌نویس که
مقدارهایِ اسیرشده‌ی تطبیق‌دهنده را دوباره پخش می‌کند. به `=>` تویِ خودِ
تطبیق‌دهنده هم دقت کن: دقیقاً همین توکن است که این را از یک تابع غیرممکن
می‌کند — `"k" => "v"` یک عبارتِ Rust نیست، پس فقط یک ماکرو می‌تواند این
سینتکس را قبول کند. مسیرها با `::std::collections::HashMap` نوشته شده‌اند
(کاملاً مشخص، با `::` در ابتدا) تا ماکرو حتی وقتی محلِ فراخوانی `HashMap`
را import نکرده هم کار کند — یک ماکرو *در محلِ فراخوانی* بسط پیدا می‌کند
و import‌هایِ همان‌جا را می‌بیند، نه import‌هایِ خودت را.

```rust
#[macro_export]
macro_rules! max_of {
    ( $only:expr ) => { $only };
    ( $first:expr, $( $rest:expr ),+ $(,)? ) => {
        ::std::cmp::max($first, $crate::max_of!( $( $rest ),+ ))
    };
}
```

یک شکلِ بازگشتیِ کلاسیک. `max_of!(3, 9, 7)` با بازویِ دوم جور درمی‌آید،
با `$first = 3` و `$rest = 9, 7`، و به `max(3, max_of!(9, 7))` بسط پیدا
می‌کند؛ یک دور دیگر می‌شود `max(3, max(9, max_of!(7)))`؛ حالا تک‌عبارتی
با بازویِ *اول* جور درمی‌آید (بازوها همیشه از بالا به پایین امتحان
می‌شوند) و بازگشت در `max(3, max(9, 7))` ته‌نشین می‌شود. اگر بازویِ پایه
را پاک کنی، فراخوانیِ بازگشتیِ همان بازویِ دوم، وقتی به یک آرگومانِ
باقی‌مانده برسد، دیگر کامایی برایِ تطبیق ندارد — کامپایلر با
`error: unexpected end of macro invocation` متوقف می‌شود، نه یک خطایِ نوع
یا قرض، چون خودِ فراخوانیِ ماکرو ناتمام مانده (مثالِ خرابِ همین درس،
`05-missing-base-case-broken.rs`، دقیقاً همین باگ است — تشخیصِ واقعی و
ضبط‌شده را تویِ README بخوان، نه این پاراگراف را). `$crate::max_of!` هم
جزئیاتِ نزدیک به بهداشت است: `$crate` همیشه به کریتی اشاره می‌کند که
خودِ ماکرو در آن *تعریف* شده، پس فراخوانیِ بازگشتی درست حل می‌شود حتی
وقتی کریتِ دیگری `max_of!` را بدونِ importِ همین اسمِ دقیق صدا بزند.

```rust
#[macro_export]
macro_rules! timed {
    ( $work:expr ) => {{
        let start = ::std::time::Instant::now();
        let result = $work;
        (result, start.elapsed())
    }};
}
```

دو جزئیاتِ عمدی اینجاست. اول، `let result = $work;` عبارتِ فراخواننده را
دقیقاً **یک‌بار** جاگذاری می‌کند — میان‌برِ وسوسه‌انگیزِ
`($work, start.elapsed())` هم همین‌قدر استفاده می‌کند، ولی هر
طراحی‌ای که `$work` را دوبار جاگذاری کند (مثلاً یک‌بار برایِ لاگ کردن و
یک‌بار برایِ برگرداندن) اثرهایِ جانبیِ فراخواننده را دوبار اجرا می‌کرد؛
تستِ شمارنده (همان `calls += 1` تویِ بلوک) دقیقاً برایِ گرفتنِ همین دسته
از باگ آنجاست. دوم، بهداشت در عمل: `start`ِ نسخه‌نویس نمی‌تواند با
متغیرِ `start`ِ فراخواننده تداخل کند — `timed!(start + 1)` در جایی که
`start` یک عددِ صحیح است، بی‌مشکل کار می‌کند، چون `start`ِ داخلِ ماکرو
از دیدِ کامپایلر نامِ کاملاً دیگری است. این همان تضمینی است که
`#define`ِ C هیچ‌وقت نداشت.

یک نکته‌ی صادقانه‌ی پایانی: از این سه‌تا، فقط `string_map!` و `max_of!`
واقعاً *مجبور*اند ماکرو باشند (سینتکسِ تازه، تعدادِ متغیرِ آرگومان).
`timed!` می‌توانست به شکلِ `fn timed<T>(f: impl FnOnce() -> T) -> (T, Duration)`
با یک کلوژر در محلِ فراخوانی باشد — `timed(|| work())`. ماکرو فقط سینتکسِ
کمی خوش‌تر در محلِ فراخوانی می‌خرد، به قیمتِ همه‌ی چیزهایی که README
دربارهٔ‌شان هشدار داد. تویِ کدِ واقعی، تابع را ترجیح بده؛ اینجا جایگاهش
را با یاد دادنِ الگویِ «پیچیدنِ یک عبارت» به دست آورده — همان الگویی که
تویِ کریت‌هایی مثلِ `tracing` می‌شناسیش.
