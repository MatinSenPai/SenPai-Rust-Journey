# ۲.۱۰.۳ — فیچرهایِ Cargo و کامپایلِ شرطی

## در یک نگاه

بعد از این درس می‌توانی:

- بگویی کدِ پشتِ یک `#[cfg(feature = "...")]` خاموش، تویِ باینریِ نهایی به چه شکل می‌ماند — کندتر اجرا می‌شود، یک نسخه‌ی خالی جایش می‌نشیند، یا اصلاً وجود ندارد — و همین را با رفتارِ `cfg!(feature = "...")` مقایسه کنی.
- یک وابستگیِ اختیاری سیم‌کشی کنی: `optional = true` رویِ خودِ وابستگی، `dep:name` تویِ لیستِ یک فیچر، و `default = []` تا کریتِ پایه بدونِ هیچ وابستگیِ اضافه‌ای کامپایل شود.
- بگویی چرا Cargo یک وابستگیِ مشترک را دقیقاً یک‌بار در هر بیلد کامپایل می‌کند — حتی وقتی کریت‌هایِ مختلف فیچرهایِ متفاوتی از آن خواسته‌اند — و همین را دلیلِ قانونِ «یک فیچر فقط اضافه می‌کند، هیچ‌وقت چیزی را حذف یا عوض نمی‌کند» بگذاری.

**زمان:** حدود ۵۰ دقیقه · **پیش‌نیاز:** [۲.۷.۲ — تستِ واحد، یکپارچه و مستندات](../../07-project-structure-and-testing/02-unit-integration-doc-tests/README.fa.md)

## چرا اهمیت دارد

هر کریتِ واقعی که تا امروز بازش کرده‌ای، احتمالاً یک جدولِ `[features]` تویِ `Cargo.toml`ش داشته: `tokio` نزدیکِ ۳۰ فیچر دارد، `serde` فیچرِ `derive` را دارد، و حتی خودِ همین مخزن نیمی از وابستگی‌هایش را با لیستِ فیچر روشن می‌کند. فیچرها دقیقاً همین‌اند: کلیدهایِ اختیاریِ زمانِ کامپایل — تابعِ اضافه، پیاده‌سازیِ صفتِ اضافه، وابستگیِ اضافه‌ای که فقط وقتی وارد باینری می‌شود که مصرف‌کننده خودش خواسته باشد.

نزدیک‌ترین چیزی که پایتون دارد `pip install requests[socks]` است — یک «اضافه» که وابستگیِ اختیاری را نصب می‌کند. ولی همین‌جا تشبیه می‌شکند: آن extra فقط چیزی که *نصب* می‌شود را عوض می‌کند؛ مسیرِ کد همچنان تویِ زمانِ اجرا با چیزی مثلِ `try: import socks` انتخاب می‌شود — هر دو مسیر همیشه تویِ فایلِ `.py` هستند، چه `socks` نصب باشد چه نه. تویِ Cargo، یک فیچر چیزی که *کامپایل* می‌شود را عوض می‌کند: کدِ پشتِ یک فیچرِ خاموش کند نمی‌شود، استاب هم نمی‌شود — اصلاً تویِ خروجی نیست. معادلِ Djangoای هم ندارد: `INSTALLED_APPS` اپ‌ها را موقعِ بالا آمدنِ پراسس قطع‌ووصل می‌کند؛ فیچرها این کار را پیش از آنکه خودِ کامپایلر اصلاً شروع کند انجام می‌دهند.

## مفهوم

### چیزی که از قبل می‌دانی، فقط با یک شرطِ متفاوت

[۲.۷.۲](../../07-project-structure-and-testing/02-unit-integration-doc-tests/README.fa.md) به‌ات یاد داد `#[cfg(test)]` یعنی چه: «این ماژول را فقط وقتی کامپایل کن که داری برایِ `cargo test` بیلد می‌گیری» — نه کندتر، نه استاب‌شده، اصلاً کامپایل نمی‌شود، پس تویِ باینریِ نهایی‌ات هم نیست. این درس دقیقاً همان مکانیزم را نشانت می‌دهد، فقط شرطش عوض شده: به‌جایِ «داریم تست می‌کنیم یا نه؟»، حالا «مصرف‌کننده این فیچر را خواسته یا نه؟» — و اسمِ فیچرها را خودت تویِ `Cargo.toml` می‌گذاری، نه Cargo.

### تعریفِ یک فیچر و یک وابستگیِ اختیاری

```toml
[features]
default = []
json-export = ["dep:serde", "dep:serde_json"]

[dependencies]
serde = { workspace = true, optional = true }
serde_json = { workspace = true, optional = true }
```

سه تکه‌اند. `optional = true` یعنی «این وابستگی را کامپایل نکن، مگر یک فیچر روشنش کند.» `dep:serde` تویِ لیستِ یک فیچر یعنی «روشن‌کردنِ `json-export`، وابستگیِ `serde` را هم روشن می‌کند.» و `default` همان فیچرهایی است که مصرف‌کننده وقتی هیچی نمی‌گوید می‌گیرد — مالِ ما خالی است، پس کریتِ پایه بدونِ هیچ وابستگی‌ای می‌ماند. (یک فیچر می‌تواند یک فیچرِ *دیگر* را هم روشن کند — از همینِ کریت یا از یک وابستگی، به‌شکلِ `derive = ["serde/derive"]`؛ مالِ ما فقط به `dep:` نیاز دارد — تویِ «چالش»، پایینِ همین درس، نسخه‌ی خودِ کریت را می‌سازی.)

### `#[cfg(...)]` یک آیتم را کامل حذف می‌کند

```rust
#[cfg(feature = "json-export")]
fn describe() -> &'static str {
    "compiled in"
}

#[cfg(not(feature = "json-export"))]
fn describe() -> &'static str {
    "compiled out"
}
```

تویِ یک بیلد، فقط یکی از این دو `describe` وجود دارد — نه اینکه یکی‌شان مرده و دست‌نیافتنی باشد، بلکه توکن‌هایش پیش از آنکه کامپایلر حتی نوع‌ها را بررسی کند، از درختِ کامپایل بیرون رفته‌اند. با یک `println!("{}", describe())` بعدِ این دو تعریف:

```text
describe(): compiled out
```

این خروجیِ بیلدِ پیش‌فرض است (`examples/01-cfg-vs-cfg-bang.rs`، بدونِ هیچ فیچری). با `--features json-export`:

```text
describe(): compiled in
```

### `cfg!(...)` یک بولِ زمانِ اجراست، نه یک حذف‌کننده

همان فایل یک خطِ دیگر هم دارد:

```rust
println!("cfg!(feature = \"json-export\"): {}", cfg!(feature = "json-export"));
```

```text
cfg!(feature = "json-export"): false
```

با `--features json-export`، همین خط `true` چاپ می‌کند. تفاوتش با `#[cfg(...)]` همین‌جاست: `cfg!(...)` هیچ کدی را از درخت بیرون نمی‌برد — فقط یک لیترالِ `bool` می‌گذارد، دقیقاً همان‌جایی که نوشته‌ای‌اش. یعنی اگر بخواهی به‌جایِ آن دو `describe`ِ بالا، یک `describe` بنویسی که با `if cfg!(feature = "json-export") { ... } else { ... }` شاخه بزند و تویِ شاخه‌ی اول `to_json` را صدا بزند، هر دو شاخه — چه اجرا بشوند چه نه — باید تویِ *هر* بیلدی کامپایل شوند. وقتی فیچر خاموش است، `to_json` اصلاً وجود ندارد، پس آن شاخه کامپایل نمی‌شود؛ همان خطایی که پایین‌تر، تویِ «خطاهایی که خواهی دید»، می‌بینی. کوتاه: `#[cfg(...)]` تصمیم را قبل از کامپایل می‌گیرد، `cfg!(...)` تصمیم را قبل از کامپایل *هم* می‌گیرد — منتها فقط رویِ مقدارِ یک `bool`، نه رویِ اینکه چه کدی وجود داشته باشد.

یک فایده‌ی جانبی: اگر اسمِ فیچر را غلط تایپ کنی — `examples/03-cfg-typo-warning.rs` مقدارِ `cfg!(feature = "made-up-feature")` را چاپ می‌کند، برایِ فیچری که تویِ `Cargo.toml` اصلاً اعلام نشده — کامپایلر بی‌سروصدا رد نمی‌شود؛ یک لینتِ استاندارد (`unexpected_cfgs`) هشدار می‌دهد:

```text
warning: unexpected `cfg` condition value: `made-up-feature`
  --> phase2-intermediate\10-rust-toolbox\03-cargo-features\examples\03-cfg-typo-warning.rs:11:14
   |
11 |         cfg!(feature = "made-up-feature")
   |              ^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: expected values for `feature` are: `broken`, `default`, and `json-export`
   = help: consider adding `made-up-feature` as a feature in `Cargo.toml`
   = note: see <https://doc.rust-lang.org/nightly/rustc/check-cfg/cargo-specifics.html> for more information about checking conditional configuration
```

### `#[cfg_attr(...)]`: نسخه‌ی شرطیِ یک صفت

```rust
#[derive(Debug, PartialEq)]
#[cfg_attr(feature = "json-export", derive(serde::Serialize))]
pub struct Report {
    pub label: String,
    pub count: usize,
    pub mean: f64,
    pub min: i64,
    pub max: i64,
}
```

`Report` خودش تویِ *هر دو* بیلد وجود دارد — فقط این‌که چه صفت‌هایی رویش `derive` شده‌اند فرق می‌کند. `#[cfg_attr(cond, attr)]` یعنی «فقط وقتی `cond` برقرار است، `attr` را اعمال کن» — شرطی‌کردنِ خودِ *صفت*، نه خودِ آیتم. اگر این خط را با یک `#[cfg(feature = "json-export")]`ِ ساده رویِ کلِ `struct Report` عوض می‌کردی، تویِ بیلدِ پیش‌فرض دیگر هیچ `Report`ی نبود — و `build_report`، که همیشه در دسترس است و `Option<Report>` برمی‌گرداند، دیگر کامپایل نمی‌شد؛ نوعِ برگشتی‌اش به چیزی اشاره می‌کرد که وجود نداشت.

### فیچرها باید جمع‌پذیر باشند: یکی‌سازی

تصور کن دو کریتِ دیگر این‌طور به همین کریت وابسته‌اند:

```toml
# کریتِ A
p2-10-03-cargo-features = { version = "0.1", features = ["json-export"] }

# کریتِ B، تویِ همان بیلد
p2-10-03-cargo-features = { version = "0.1" }
```

Cargo این کریت را **یک‌بار** کامپایل می‌کند — نه یک نسخه برایِ A و یک نسخه برایِ B — با **اجتماعِ** همه‌ی فیچرهایِ خواسته‌شده: چون A دارد `json-export` را می‌خواهد، B هم، بدونِ اینکه خودش خواسته باشد، یک نسخه‌ای می‌گیرد که `to_json` تویش هست. به این می‌گویند **یکی‌سازی (unification)**، و همین یک قانونِ طراحی را رویِ نویسنده‌یِ فیچر تحمیل می‌کند: روشن‌کردنِ یک فیچر فقط حق دارد چیزی **اضافه** کند، هیچ‌وقت چیزی را حذف یا رفتارِ موجود را عوض نکند. فیچری مثلِ `no-std-panic-handler` که چیزی را *حذف* می‌کند، هر وابسته‌ای را که آن را نخواسته می‌شکند — چون آن وابسته هیچ راهی ندارد که آن فیچر را خاموش نگه دارد؛ فقط می‌تواند یک فیچرِ تازه را روشن کند، هیچ‌وقت فیچرِ کریتِ دیگری را خاموش.

```senpai-visual
{"kind":"concept","labels":["کریتِ A فیچرِ json-export را می‌خواهد","کریتِ B هیچی نمی‌خواهد","Cargo یک نسخه‌ی مشترک می‌سازد","آن نسخه اجتماعِ هر دو خواسته را دارد","B هم to_json را می‌گیرد، بخواهد یا نه"]}
```

نتیجه‌اش این است: کریتت باید تویِ **هر** ترکیبِ فیچری که ادعا می‌کنی پشتیبانی می‌کنی، بیلد شود و تست‌هایش پاس شوند — دقیقاً همان چیزی که «دست‌به‌کد» و «تمرین» پایین‌تر ازت می‌خواهند.

### همان ترفند برایِ تست‌ها

```rust
#[cfg(all(test, feature = "json-export"))]
mod json_tests {
```

`all(...)` هر چند شرطی که بخواهی را با هم AND می‌کند. این ماژول فقط وقتی کامپایل می‌شود که **هم** داری تست می‌گیری **هم** `json-export` روشن است — پس `cargo test`ِ ساده حتی سراغِ کامپایل‌کردنش هم نمی‌رود، و کریتِ پایه مجبور نیست `serde_json` را ببیند.

## دست‌به‌کد

```sh
cargo run -p p2-10-03-cargo-features --example 01-cfg-vs-cfg-bang
cargo run -p p2-10-03-cargo-features --example 01-cfg-vs-cfg-bang --features json-export
```

حالا مثالِ خراب — فقط برایِ دیدنِ خطا، نه برایِ درست‌کردنش (آن تویِ «تعمیر» می‌آید):

```sh
cargo run -p p2-10-03-cargo-features --example 02-to-json-without-feature --features broken
```

بعد این دو تا را امتحان کن:

۱. `01-cfg-vs-cfg-bang` را یک‌بار دیگر، این‌بار با `--no-default-features`، اجرا کن. خروجی با اجرایِ بدونِ فیچر فرق می‌کند؟ چرا؟
۲. رویِ یک کپیِ محلی از `01-cfg-vs-cfg-bang.rs`، یک `println!` تازه اضافه کن که `cfg!(feature = "made-up-feature")` را چاپ کند — اسمی که تویِ `Cargo.toml` این کریت هیچ‌جا اعلام نشده. کامپایل نمی‌شود، `false` چاپ می‌کند، یا چیزِ دیگری؟

## خطاهایی که خواهی دید

### `E0432` — ایمپورتِ حل‌نشده

`examples/02-to-json-without-feature.rs` این‌طور شروع می‌شود:

```rust
use p2_10_03_cargo_features::{to_json, Report};
```

با `--features broken` (بدونِ `json-export`)، این‌طور شکست می‌خورد:

```text
error[E0432]: unresolved import `p2_10_03_cargo_features::to_json`
  --> phase2-intermediate\10-rust-toolbox\03-cargo-features\examples\02-to-json-without-feature.rs:8:31
   |
 8 | use p2_10_03_cargo_features::{to_json, Report};
   |                               ^^^^^^^ no `to_json` in the root
   |
note: found an item that was configured out
  --> phase2-intermediate\10-rust-toolbox\03-cargo-features\src\lib.rs:37:8
   |
36 | #[cfg(feature = "json-export")]
   |       ----------------------- the item is gated behind the `json-export` feature
37 | pub fn to_json(report: &Report) -> String {
   |        ^^^^^^^

For more information about this error, try `rustc --explain E0432`.
```

**کامپایلر به چه اعتراض دارد:** `to_json` تویِ ریشه‌یِ کریت پیدا نمی‌شود. این یک باگِ منطقی تویِ کدِ خودت نیست — `to_json` واقعاً تویِ این بیلد وجود ندارد، چون `json-export` روشن نیست. حتی خودِ کامپایلر هم دقیقاً همین را می‌گوید: «یک آیتمی پیدا کردم که *کانفیگ‌آوت* شده» — یعنی یک `#[cfg(...)]` آن را از این بیلد بیرون گذاشته.

**راه‌حل:** فیچری که `to_json` به آن نیاز دارد را روشن کن:

```sh
cargo build -p p2-10-03-cargo-features --example 02-to-json-without-feature --features broken,json-export
```

**چرا این راه‌حل است:** هیچ خطِ کدی اشتباه نبود. `to_json` همیشه پشتِ `json-export` بوده — این دقیقاً همان چیزی است که «تعریفِ یک فیچر و یک وابستگیِ اختیاری» بالاتر گفت. مشکل تویِ دستورِ ساختن بود، نه تویِ منطقِ برنامه.

## تمرین

### گرم‌کردن

<details>
<summary>وقتی این کریت را بدونِ هیچ فیچری کامپایل می‌کنی، بدنه‌ی <code>to_json</code> هنوز جایی تویِ باینریِ نهایی هست — فقط دست‌نیافتنی — یا اصلاً وجود ندارد؟</summary>

اصلاً وجود ندارد. `#[cfg(...)]` پیش از آنکه کامپایلر حتی نوع‌ها را بررسی کند اجرا می‌شود؛ وقتی شرط برقرار نیست، کلِ آیتم — امضا، بدنه، همه‌چیز — از درختِ نحوی حذف می‌شود، پیش از آنکه هیچ مرحله‌ی بعدی چیزی از آن ببیند. این با یک `if false { ... }` فرق دارد — آن کامپایل *می‌شود*، فقط بهینه‌ساز حذفش می‌کند؛ اینجا اصلاً چیزی برایِ کامپایل‌کردن نمانده.

</details>

<details>
<summary>کریتِ A به کریتِ خودت (<code>you</code>) وابسته است، با فیچرِ <code>json-export</code> روشن. کریتِ B، تویِ همان بیلد، به <code>you</code> وابسته است، بدونِ هیچ فیچری. Cargo چند نسخه از <code>you</code> کامپایل می‌کند؟</summary>

یکی. Cargo یک وابستگیِ مشترک را دقیقاً یک‌بار در هر بیلد می‌سازد، با اجتماعِ تمامِ فیچرهایِ خواسته‌شده — اینجا، `json-export` روشن، چون A آن را خواسته. B هم یک `you`ای می‌گیرد که `to_json`اش در دسترس است، حتی بدونِ اینکه خودش این را خواسته باشد. این یکی‌سازی است، و دقیقاً به همین دلیل یک فیچر فقط حق دارد اضافه کند — نه حذف، نه تغییرِ رفتارِ موجود.

</details>

<details>
<summary>این، با فیچر روشن یا خاموش، هر دو کامپایل می‌شود:</summary>

```rust
println!("{}", cfg!(feature = "json-export"));
```

حالا تصور کن بدنه را به `if cfg!(feature = "json-export") { to_json(&report) } else { String::new() }` عوض می‌کنی، بدونِ هیچ تغییرِ دیگری. با فیچرِ خاموش، این کامپایل می‌شود؟

</details>

<details>
<summary>پاسخ</summary>

نه. `cfg!(...)` فقط یک بولِ زمانِ اجراست، نه حذف‌کننده‌یِ کد. هر دو شاخه‌یِ `if` باید تویِ *هر* بیلدی — چه آن شاخه اجرا شود چه نه — به چیزهایِ واقعاً موجود اشاره کنند و نوع‌چک شوند. چون `to_json` بدونِ `json-export` وجود ندارد، شاخه‌یِ اول حل نمی‌شود — همان `E0432`ای که تویِ «خطاهایی که خواهی دید» دیدی، نه یک مقدارِ `false`.

</details>

<summary>کریتِ B می‌تواند فیچرِ <code>json-export</code> را برایِ کلِ بیلد خاموش نگه دارد، حتی اگر کریتِ A همان وابستگیِ مشترک را با آن فیچر روشن خواسته باشد؟</summary>

نه. هیچ راهی برایِ «وتو» یا خاموش‌نگه‌داشتنِ اجباریِ فیچری که کریتِ دیگری تویِ همان بیلد خواسته وجود ندارد. یک وابسته فقط می‌تواند فیچرِ *تازه* بخواهد (یا فیچرهایِ پیش‌فرض را برایِ خودش رد کند)، هرگز فیچرِ خواسته‌شده‌یِ یک وابسته‌یِ دیگر را لغو کند. این روی دیگرِ همان سکه‌ی یکی‌سازی است: اگر روشن‌کردنِ یک فیچر می‌توانست رفتار را عوض یا حذف کند، B با یک تصمیمِ بی‌ربطِ A بی‌خبر می‌شکست — همان چیزی که قانونِ جمع‌پذیری جلویش را می‌گیرد.

</details>

### تعمیر

`examples/02-to-json-without-feature.rs` دقیقاً همان `E0432`ِ بالا را می‌دهد. دو کار بکن:

۱. بدونِ دست‌زدن به کد، فقط با عوض‌کردنِ دستور، بسازش:

```sh
cargo build -p p2-10-03-cargo-features --example 02-to-json-without-feature --features broken,json-export
```

حالا کامپایل می‌شود — هیچ باگی تویِ کد نبود؛ فقط فیچری که کد به آن نیاز داشت روشن نبود.

۲. حالا رویِ یک کپیِ محلی از همین فایل کاری کن که تویِ **هر دو** حالت کامپایل شود: صدازدنِ `to_json` را پشتِ `#[cfg(feature = "json-export")]` بگذار، و برایِ نبودِ فیچر یک پیامِ جایگزین چاپ کن. هر دویِ این دستورها باید بدونِ خطا تمام شوند:

```sh
cargo build -p p2-10-03-cargo-features --example 02-to-json-without-feature --features broken
cargo build -p p2-10-03-cargo-features --example 02-to-json-without-feature --features broken,json-export
```

### پیاده‌سازی

تویِ `src/lib.rs` دو تابع مانده — مشخصاتِ دقیقِ هر دو، بالایِ خودشان، تویِ کامنتِ مستندات:

- `build_report` — همیشه در دسترس است.
- `to_json` — فقط زیرِ فیچرِ `json-export` وجود دارد.

```sh
cargo test -p p2-10-03-cargo-features
cargo test -p p2-10-03-cargo-features --features json-export
```

هر دو دستور را بزن. دومی تست‌هایِ `json_tests` را هم کامپایل و اجرا می‌کند — چیزی که دستورِ اول اصلاً کامپایلش نمی‌کند. سبزبودنِ فقط یکی از این دو یعنی نصفِ کار.

### بساز

یک فیچرِ تازه اضافه کن: `csv-export`، هم‌شکلِ `json-export` ولی بدونِ هیچ وابستگیِ تازه‌ای.

۱. تویِ `Cargo.toml`، زیرِ `[features]`: `csv-export = []`.
۲. یک `pub fn to_csv(report: &Report) -> String` بنویس، پشتِ `#[cfg(feature = "csv-export")]`، که یک خطِ CSV برمی‌گرداند: `label,count,mean,min,max`، دقیقاً به همین ترتیب، جداشده با کاما، بدونِ خطِ سرستون و بدونِ خطِ جدیدِ انتهایی — هر فیلد با فرمتِ پیش‌فرضِ `{}`ِ خودش.
۳. یک ماژولِ تست بنویس، زیرِ `#[cfg(all(test, feature = "csv-export"))]`، هم‌شکلِ `json_tests`.

هیچ وابستگیِ تازه‌ای لازم نیست — `format!` برایِ یک خطِ CSV کافی است.

### چالش (اختیاری)

یک فیچرِ سوم اضافه کن: `pretty`، که خودش هیچ کدی ندارد — فقط `json-export` را روشن می‌کند:

```toml
pretty = ["json-export"]
```

بعد یک `pub fn to_json_pretty(report: &Report) -> String` بنویس، پشتِ `#[cfg(feature = "pretty")]`، با `serde_json::to_string_pretty`. تأیید کن که `cargo build --features pretty` کامپایل می‌شود، بدونِ اینکه هیچ‌جا جداگانه `json-export` را خواسته باشی — همان الگویی که تویِ «تعریفِ یک فیچر» دیدی (`derive = ["serde/derive"]`)، این‌بار رویِ فیچرهایِ خودِ همین کریت.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| فیچر (feature) | کلیدِ اختیاریِ زمانِ کامپایل، اعلام‌شده تویِ `[features]` | هر جا یک قابلیت یا وابستگی باید اختیاری بماند |
| `optional = true` / `dep:name` | وابستگی‌ای که کامپایل نمی‌شود مگر یک فیچر روشنش کند | جدا نگه‌داشتنِ کریتِ پایه از وابستگیِ سنگین |
| `#[cfg(feature = "...")]` | حذفِ کاملِ یک آیتم، پیش از بررسیِ نوع‌ها | تابع/ساختار/ماژولی که فقط باید تویِ یک بیلد وجود داشته باشد |
| `cfg!(feature = "...")` | یک بولِ زمانِ اجرا؛ کدی را حذف نمی‌کند | شاخه‌زدن رویِ روشن/خاموش‌بودنِ فیچر، تویِ تابعی که در هر دو بیلد کامپایل می‌شود |
| `#[cfg_attr(cond, attr)]` | نسخه‌ی شرطیِ یک صفت؛ خودِ آیتم می‌ماند | مثلِ `derive`ای که فقط بعضی بیلدها لازمش دارند |
| یکی‌سازیِ فیچر (unification) | یک وابستگیِ مشترک، یک‌بار کامپایل، با اجتماعِ همه‌ی فیچرهایِ خواسته‌شده | دلیلِ اینکه فیچرها باید فقط اضافه کنند |

### الان می‌دانی

- کدِ پشتِ یک فیچرِ خاموش پیش از بررسیِ نوع‌ها حذف می‌شود — نه کندتر، نه استاب، اصلاً وجود ندارد.
- `optional = true` + `dep:name` تویِ یک فیچر تنها راهِ روشن‌کردنِ یک وابستگیِ اختیاری است؛ `default = []` یعنی کریتِ پایه به‌تنهایی هیچ‌کدام‌شان را نمی‌خواهد.
- `cfg!(...)` یک بولِ زمانِ اجراست، نه حذف‌کننده — هر دو شاخه‌ای که رویش شرط می‌گذاری باید در هر بیلد کامپایل شوند.
- `#[cfg_attr(cond, attr)]` صفت را شرطی می‌کند، نه خودِ آیتم را.
- Cargo یک وابستگیِ مشترک را دقیقاً یک‌بار می‌سازد، با اجتماعِ فیچرهایِ همه‌ی وابسته‌ها — به همین دلیل یک فیچر فقط حق دارد اضافه کند.

### بعداً کامل‌تر می‌بینی

- **سریالایزیشنِ کاملِ JSON با `derive(Serialize)` و اعتبارسنجی** — [فاز ۳ — `serde_json` و `validator`](../../../phase3-backend-foundations/03-serialization-and-validation/01-serde-json-and-validator/README.fa.md)

### می‌توانی توضیح بدهی؟

- چرا کدِ پشتِ یک فیچرِ خاموش «کندتر» یا «استاب‌شده» نیست، بلکه اصلاً وجود ندارد؟
- فرقِ `#[cfg(feature = "...")]` با `cfg!(feature = "...")` را با یک مثال نشان بده که فقط یکی‌شان روی فیچرِ خاموش کامپایل می‌شود.
- Cargo چطور تضمین می‌کند دو کریتِ مختلف که فیچرهایِ متفاوتی از یک وابستگیِ مشترک خواسته‌اند، بازهم فقط یک نسخه از آن کامپایل می‌شود؟ و این تضمین چه قانونی را رویِ نویسنده‌یِ فیچر می‌گذارد؟
- چرا `Report` از `#[cfg_attr(...)]` استفاده می‌کند، نه از یک `#[cfg(feature = "json-export")]`ِ ساده رویِ کلِ ساختار؟
