# راه‌حل

## `split_at_mut_demo`

```rust
pub fn split_at_mut_demo<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    let len = slice.len();
    assert!(mid <= len, "mid out of bounds");
    let ptr = slice.as_mut_ptr();
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}
```

متدِ `slice.as_mut_ptr()` (که خودش کاملاً امن است — ساختنِ یک اشاره‌گرِ خام هرگز نیازی به `unsafe` ندارد) یک `*mut T` به اولین عنصرِ بُرش می‌دهد. عبارتِ `ptr.add(mid)` هم یک اشاره‌گر می‌سازد که `mid` عنصر جلوتر است (این هم طبقِ قوانینِ حسابِ اشاره‌گر، محاسبه‌کردنش کاملاً امن است — فقط بازکردنِ ارجاعش یا استفاده‌ی غلط از آن است که پای خطر می‌آید). تابعِ `std::slice::from_raw_parts_mut(ptr, len)` همان عملیاتِ واقعاً `unsafe` است: از یک اشاره‌گرِ خام و یک طول، یک `&mut [T]` می‌سازد، و کلِ قراردادِ ایمنیِ این تابع (که در کتابخانه‌ی استاندارد ثبت شده) دقیقاً همان چیزی است که کامنتِ `// SAFETY:` بهش استدلال می‌کند: آن اشاره‌گر باید برایِ `len` عنصر معتبر باشد، و — که برایِ این تمرین از همه‌چیز مهم‌تر است — هیچ ارجاعِ دیگری نباید تا وقتی این بُرشِ برگردانده‌شده زنده است، به همان حافظه اشاره کند.

دقیقاً همین بخشِ آخر است که این تابع را کلاً به `unsafe` محتاج می‌کند: ما شخصاً ضمانت می‌کنیم دو بُرشِ نهایی هم‌پوشانی ندارند (`0..mid` و `mid..len`، که بر اساسِ نحوه‌ی ساخته‌شدنشان هم درست است — `mid` یک نقطه‌ی برشِ ثابت و یکتاست) — تضمینی که borrow checker هیچ راهِ توکاری برایِ بررسیِ درستی‌اش فقط از رویِ کد ندارد، چون تنها چیزی که می‌بیند «دو قرضِ تغییرپذیر از `slice`» است، بدونِ هیچ مفهومی از «این بازه‌های بایتیِ خاص کاملاً از هم مجزا هستند». `unsafe` دقیقاً همان کلمه‌ای است که می‌گوید «دارم چیزی درست را ادعا می‌کنم که سیستمِ نوع‌ها به‌تنهایی نمی‌تواند خودش بررسی کند.»

درباره‌ی سؤالِ اولِ گرم‌کردنِ README: اگر آن `assert!` نبود، `ptr.add(10)` رویِ یک بُرشِ ۳-عنصری یک اشاره‌گر می‌ساخت که از انتهای فضایِ اختصاص‌داده‌شده جلوتر است. صرفِ *محاسبه‌کردنِ* یک اشاره‌گرِ خارج از محدوده با `.add()`، خودش به‌تنهایی، رفتارِ تعریف‌نشده است (نه فقط بازکردنِ ارجاعش) — قراردادِ ایمنیِ ثبت‌شده‌ی خودِ کتابخانه‌ی استاندارد برایِ `.add()` می‌گوید نتیجه باید داخلِ همان شئِ اختصاص‌داده‌شده باشد (یا دقیقاً یک قدم بعدِ انتهایش). دقیقاً به همین دلیل، همان `assert!` در کدِ امن، *پیش از* بلوکِ `unsafe`، است که کلِ این تابع را واقعاً امن برایِ صدازدن می‌کند — اگر پاکش کنی، تست‌های این تمرین بازهم اغلب از رویِ شانس «کار می‌کنند» (رفتارِ تعریف‌نشده تضمین نمی‌کند حتماً کرش کند)، که خیلی ترسناک‌تر از یک پنیکِ تمیز است.

## `OwnedBox<T>`

```rust
pub struct OwnedBox<T> {
    ptr: *mut T,
    _marker: PhantomData<T>,
}

unsafe impl<T: Send> Send for OwnedBox<T> {}

impl<T> OwnedBox<T> {
    pub fn new(value: T) -> Self {
        Self {
            ptr: Box::into_raw(Box::new(value)),
            _marker: PhantomData,
        }
    }

    pub fn get(&self) -> &T {
        unsafe { &*self.ptr }
    }

    pub fn get_mut(&mut self) -> &mut T {
        unsafe { &mut *self.ptr }
    }
}

impl<T> Drop for OwnedBox<T> {
    fn drop(&mut self) {
        unsafe {
            drop(Box::from_raw(self.ptr));
        }
    }
}
```

`new` مقدارِ `value` را با `Box::new` رویِ هیپ می‌برد، بعد بلافاصله با `Box::into_raw` مالکیتِ همان `Box` را پس می‌دهد و فقط اشاره‌گرِ خامی را که برمی‌گرداند نگه می‌دارد. بینِ همین فراخوانی و اجرایِ `Drop::drop`، هیچ‌چیزی در سیستمِ نوع‌ها به‌جایِ `OwnedBox` مالکِ آن تخصیص نیست — خودِ `OwnedBox<T>` است که، کاملاً بر اساسِ قرارداد و با تکیه بر همین سه متد، جایِ آن مالکیت را پر می‌کند.

متدهای `get` و `get_mut` نتیجه‌ی همان کاری‌اند که `new` انجام داد: `Box::into_raw` تضمین می‌کند اشاره‌گری که برمی‌گرداند برایِ یک `T` معتبر و درست‌تراز است، و هیچ‌جایِ دیگرِ این نوع پیش از اجرایِ `Drop::drop` آن را آزاد نمی‌کند، پس بازکردنِ ارجاعش به یک `&T` (یا `&mut T`، پشتِ `&mut self`) درست و بی‌خطر است. `Drop::drop` هم دقیقاً آینه‌ی `Box::into_raw` است: `Box::from_raw` همان اشاره‌گرِ خام را می‌گیرد و `Box<T>` را دوباره دورش می‌سازد، و رهاکردنِ همان `Box`ِ بازسازی‌شده تخریب‌گرِ `T` را دقیقاً یک‌بار اجرا می‌کند — درست مثلِ هر `Box<T>`ِ دیگری.

خطِ `unsafe impl<T: Send> Send for OwnedBox<T> {}` همان چیزی است که این درس واقعاً درباره‌اش است. بدونش، `OwnedBox<T>` برایِ هر `T`ای `!Send` می‌ماند، تمام — نه به این دلیل که کامپایلر به `T` نگاه کرده و مشکلی پیدا کرده، بلکه چون همان یک فیلدِ اشاره‌گرِ خام به‌تنهایی برایِ بستنِ `Send`ِ خودکار کافی است. نوشتنِ این خط یعنی شخصاً چیزی را ضمانت می‌کنی که کامپایلر خودش نمی‌تواند اثبات کند: اینکه انتقالِ مالکیتِ یک `OwnedBox<T>` به ریسمانِ دیگر، وقتی خودِ `T` هم `Send` است، واقعاً امن است. بررسی‌اش هم آسان است، چون `OwnedBox<T>` دقیقاً مثلِ `Box<T>` رفتار می‌کند — مالکیتِ انحصاری، همیشه فقط یک چیز به آن مقدار اشاره می‌کند — و `Box<T>` هم خودش از قبل `Send` است، هر وقت `T` باشد. این `unsafe impl` چیزی فراتر از همان تضمینی که `Box` از قبل می‌دهد ادعا نمی‌کند؛ فقط همان تضمین را برایِ نوعی که کامپایلر نمی‌تواند از پشتش ببیند، دوباره بیان می‌کند.

فیلدِ `_marker: PhantomData<T>` اینجا چیزی را در کامپایل‌شدن عوض نمی‌کند — `ptr: *mut T` از قبل `T` را می‌آورد، پس حذفِ آن فیلد بازهم تمیز کامپایل می‌شود. نگهش می‌داریم چون دقیقاً همان علامتی است که هر نوعِ واقعیِ مبتنی بر اشاره‌گرِ خام در کتابخانه‌ی استاندارد با خودش حمل می‌کند: می‌گوید این اشاره‌گر یعنی مالکیتِ یک `T`، نه فقط قرضِ آن.

### چالش، بخشِ دو

قرض‌دادنِ `unsafe impl<T: Sync> Sync for OwnedBox<T> {}` رویِ همین API دقیق (`get`، `get_mut`، `Drop`، هیچ‌چیزِ دیگری) امروز یک نقضِ هم‌نامی نمی‌سازد — `get_mut` به `&mut self` نیاز دارد، و هیچ‌چیزی در `Sync` نمی‌گذارد دو ریسمان از یک `&OwnedBox<T>`ِ اشتراکی به `&mut OwnedBox<T>` برسند. خطرِ واقعی چیزی است که `Sync` از این به بعد قول می‌دهد. چون borrow checker هیچ حرفی برایِ گفتن درباره‌ی چیزی که پشتِ یک اشاره‌گرِ خام اتفاق می‌افتد ندارد، نوشتنِ متدی مثلِ `fn set(&self, value: T) { unsafe { *self.ptr = value; } }` کاملاً مجازِ Rust است — یک متدِ عمومیِ *به‌ظاهر* امن که فقط `&self` می‌خواهد، ولی بازهم از پشتِ اشاره‌گر می‌نویسد. از همان لحظه‌ای که چنین متدی وجود داشته باشد، دو ریسمانی که یک `OwnedBox<T>`ِ `Sync` را با هم به اشتراک گذاشته‌اند می‌توانند هم‌زمان صدایش بزنند: یک نوشتنِ ناهماهنگ از دو جایِ هم‌زمان، یعنی یک مسابقه‌ی داده‌ی واقعی. ماندن در `!Sync` به‌طورِ پیش‌فرض، و دادنِ آن فقط وقتی هر متدِ فعلی و آینده در برابرِ دقیقاً همین خطر بررسی شده — دقیقاً همان انتخابِ محتاطانه‌ای است که نوع‌هایِ مبتنی بر اشاره‌گرِ خامِ خودِ کتابخانه‌ی استاندارد هم دارند.
