# ۲.۱۰.۱ — تطبیقِ الگو، عمیق‌تر

## در یک نگاه

بعد از این درس می‌توانی:

- توضیح بدهی چرا `match x { n if n >= 0 => .., n if n < 0 => .. }` کامپایل نمی‌شود — با اینکه دو گارد رویِ هم همه چیز را پوشش می‌دهند — و بگویی این خطا دقیقاً از کجایِ ۱.۵.۴ می‌آید.
- یک الگویِ "یا" مثلِ `Ok(n) | Err(n)` بنویسی که دو طرفش واقعاً هم‌نوع باشند، و وقتی نباشند `E0308` را خودت بخوانی و رفعش کنی.
- بگویی چرا تطبیقِ یک `&LogEvent` یک فیلد را به‌جایِ `String`، `&String` می‌دهد، و کِی هنوز باید `ref` را با دست بنویسی.
- یک برش را بر اساسِ طولش — نه `.len()` و ایندکس‌گذاری — با `[]`، `[x]`، `[first, .., last]` تطبیق بدهی، و بگویی کامپایلر چطور ثابت می‌کند این سه‌تا هر طولی را می‌پوشانند.

[۱.۵.۴ — `match` از نزدیک](../../../phase1-fundamentals/05-your-own-types/04-match-in-depth/README.fa.md)

## چرا اهمیت دارد

[۱.۵.۴](../../../phase1-fundamentals/05-your-own-types/04-match-in-depth/README.fa.md) نصفِ راه را رفت: یک `match` که واریانت را تشخیص می‌دهد، داده‌اش را در همان قدم بیرون می‌کشد، و کامپایلر ثابت می‌کند هیچ حالتی جا نمانده. ولی همان درس سه چیز را برایِ همین‌جا گذاشت: اینکه تطبیق از پشتِ یک ارجاع اسم‌های تازه‌ای می‌سازد که خودشان هم ارجاع‌اند («حالتِ اتصالِ پیش‌فرض»، وعده‌داده‌شده برایِ همین‌جا)، اینکه الگوها رویِ برش‌ها هم کار می‌کنند — «چیزی که هنوز ندیده‌ای» — و، زیرِ یک بندِ ترکیبیِ «بعداً کامل‌تر می‌بینی»، «بقیه‌یِ زبانِ الگو»، همان‌جایی که جایگزین‌ها و اتصال‌هایِ `@` واقعاً زندگی می‌کنند.

این درس دقیقاً همان سه‌تا را کامل می‌کند، به‌علاوه‌ی یک نکته‌ی چهارم که آن‌جا اصلاً مطرح نشد: `ref`، برایِ وقتی مقدارِ مچ‌شده مالکیت‌دار است. هیچ‌کدام‌شان مفهومِ تازه‌ای نیستند — همان `match`ی است که از فاز ۱ می‌شناسی — فقط جاهایی است که آن مدلِ ساده اگر دقیق نگاهش نکنی، غافلگیرت می‌کند.

پایتونِ ۳.۱۰ به بعد همان‌طور که ۱.۵.۴ گفت، `match`/`case` دارد و شکلِ کلی‌اش را از زبان‌هایی مثلِ Rust قرض گرفته. الگوهایِ "یا" آن‌جا هم هست (`case 400 | 401 | 402:`)، ولی بدونِ الگویِ بازه‌ای رویِ اعداد و بدونِ چیزی معادلِ `@` که هم بسنجد هم نگه دارد. تطبیقِ رویِ لیست‌ها (`case [first, *rest]:`) هم هست — ولی هیچ‌کدام از این‌ها را کامپایلر ثابت نمی‌کند؛ فقط اگر `mypy` را واقعاً اجرا کنی، و آن‌هم اختیاری. این‌جا خودِ کامپایلرِ Rust است، رویِ هر بیلد، بدونِ استثنا.

## مفهوم

### یادآوریِ سریع: تا این‌جا با `match` چه داری

نگهبان (یک `if` رویِ یک بازو)، الگویِ "یا" (`|`)، اتصال با `@`، و استخراجِ تودرتو — هر چهارتا از ۱.۵.۴. همین چهارتا با هم، رویِ همین `LogEvent` و `Severity`ی که `src/lib.rs` دارد، این‌طوری به‌کار می‌آیند:

```rust
fn headline(event: &LogEvent) -> Option<String> {
    match event {
        LogEvent::Request { status, path, .. } if *status >= 500 => {
            Some(format!("5xx {status} on {path}"))
        }
        LogEvent::Message { severity: Severity::Error, text } => Some(format!("error: {text}")),
        _ => None,
    }
}
```

```text
Some("5xx 503 on /api/jobs")
Some("error: db down")
None
```

بازوی اول یک نگهبان دارد (`if *status >= 500`)؛ بازوی دوم یک استخراجِ تودرتو است — `severity: Severity::Error` خودش یک زیرالگوست، نه یک مقایسه‌ی جدا. اگر جایی از این چهارتا مطمئن نیستی، همین‌جا نگه‌دار و برگرد به ۱.۵.۴؛ از این‌جا به بعد رویِ همین‌ها می‌سازیم، دوباره توضیحشان نمی‌دهیم.

### الگوهایِ "یا": هر جایگزین باید همان نوع را بایند کند

`|` یک بازو را با چند شکلِ مختلف تطبیق می‌دهد — حتی شکل‌هایی از **واریانت‌هایِ متفاوت**، نه فقط لیترال‌هایِ یک نوع. این‌جا `status` از `Request` و `retry_after` از `RateLimited`، هر دو `u16` هستند، پس بایند کردنشان به یک اسمِ مشترک قانونی است:

```rust
match event {
    LogEvent::Request { status: n } | LogEvent::RateLimited { retry_after: n } => *n,
}
```

```text
503
30
```

قاعده‌اش این است: **کامپایلر هر بایندِ یک الگویِ "یا" را رویِ همه‌ی جایگزین‌ها چک می‌کند — هم اسمش هم نوعش.** اگر یک طرف `n: u16` بدهد و طرفِ دیگر `n: u64`، برنامه ساخته نمی‌شود؛ خطایش `E0308` است و در «خطاهایی که خواهی دید» می‌بینی‌اش. همین قاعده شاملِ خودِ اسم هم می‌شود، نه فقط نوعش — اگر یک طرف `n` بایند کند و طرفِ دیگر `m`، کامپایلر با `E0408` می‌گوید «این اسم تویِ همه‌ی جایگزین‌ها نیست»، چون هر بازو باید یک مجموعه‌ی ثابت از اسم‌ها با یک مجموعه‌ی ثابت از نوع‌ها بدهد — وگرنه بدنه‌ی بازو نمی‌داند رویِ کدام مقدار دارد کار می‌کند.

### حالتِ اتصالِ پیش‌فرض: تطبیق از پشتِ `&` رایگان قرض می‌گیرد

سؤال: در `LogEvent::Request { method, .. }`، وقتی داری یک `&LogEvent` را تطبیق می‌دهی، `method` چه نوعی دارد؟ جواب `&String` است، نه `String`:

```rust
fn method_of(event: &LogEvent) -> Option<&str> {
    match event {
        LogEvent::Request { method, .. } => Some(method.as_str()),
        _ => None,
    }
}
```

```text
Some("POST")
Request { method: "POST", path: "/login" }
```

اگر `method` واقعاً `String` بود، این بازو مجبور بود آن را از دلِ چیزی که فقط قرض گرفته‌ای بیرون بکشد (move کند) — که خطایِ کامپایل است، چون `event` مالِ تو نیست. Rust به‌جایش خودش، خودکار، هر فیلدی را که تویِ یک الگویِ پشتِ `&` بایند می‌کنی، با ارجاع می‌دهد — بدونِ اینکه چیزی بنویسی. به همین دلیل خطِ دومِ خروجی بالا هم کار می‌کند: `event` هیچ‌وقت واقعاً قرض هم نشد به‌معنایِ مصرف‌شدن، فقط خوانده شد. این رفتار اسمی دارد — **حالتِ اتصالِ پیش‌فرض (default binding mode)**، معروف به «match ergonomics» — و دقیقاً همان چیزی است که ۱.۵.۴ برایِ دیدنِ کاملش به این‌جا لینک داد. پیش از این رفتار (پیش از Rust ۲۰۱۸) باید صریح `ref method` می‌نوشتی؛ امروز خودکار است و `ref` عملاً از آن استفاده برای همین حالت کنار رفته.

```senpai-visual
{"kind":"borrowing","labels":["match &LogEvent { Request { method, .. } }","method خودکار به‌شکلِ &String بایند می‌شود","event قرض‌شده می‌ماند، چیزی move نمی‌شود","همان match رویِ یک LogEvent مالکیت‌دار","text بدونِ ref move می‌شد — ref همین را متوقف می‌کند"]}
```

### `ref`: قرض‌گرفتنِ یک فیلد از دلِ یک مقدارِ مالکیت‌دار

حالتِ اتصالِ پیش‌فرض فقط وقتی به‌کار می‌آید که خودِ مقداری که تطبیق می‌دهی یک ارجاع باشد. اگر `event` مالکیت‌دار باشد (`LogEvent`، نه `&LogEvent`)، تطبیق دادنش به‌طورِ پیش‌فرض هر فیلدی که بایند کنی را **منتقل** می‌کند:

```rust
match owned {
    LogEvent::Message { severity, ref text } => println!("[{severity}] {text}"),
    LogEvent::Request { .. } => {}
}
println!("{owned:?}");
```

```text
[2] disk 91% full
Message { severity: 2, text: "disk 91% full" }
```

`severity` یک `u8` است (`Copy`)، پس بایندِ آن با مقدار مشکلی ندارد. `text` یک `String` است — اگر بدونِ `ref` بایندش می‌کردی، از دلِ `owned` منتقل می‌شد، و خطِ آخر (`println!("{owned:?}")`) دیگر کامپایل نمی‌شد، چون `owned` دیگر کامل نیست. `ref text` می‌گوید «همین فیلد را فقط قرض بگیر، منتقلش نکن» — بدونِ اینکه بقیه‌ی `owned` را هم قرض بگیری یا از دست بدهی. این دقیقاً همان جایی است که `ref` هنوز زنده مانده: **تطبیقِ یک مقدارِ مالکیت‌دار، وقتی می‌خواهی فقط یک فیلدش را قرض بگیری، نه همه‌اش را منتقل کنی.**

### الگویِ برش‌ها: جامع بودن بر اساسِ طول

الگوها رویِ `&[T]` هم کار می‌کنند، و این‌بار «حالت» یعنی طول:

```rust
fn describe(samples: &[u64]) -> String {
    match samples {
        [] => "no samples".to_string(),
        [only] => format!("1 sample: {only}ms"),
        [first, .., last] => format!("first {first}ms, last {last}ms"),
    }
}
```

```text
[]               -> no samples
[42]             -> 1 sample: 42ms
[5, 80, 9, 12]   -> first 5ms, last 12ms
[7, 3]           -> first 7ms, last 3ms
```

سه بازو، سه طول: `[]` دقیقاً صفر عضو، `[only]` دقیقاً یک عضو، `[first, .., last]` دو عضو یا بیشتر (یکی برایِ `first` لازم است، یکی برایِ `last`، و `..` هرچه وسط ماند را می‌بلعد — حتی اگر آن وسط خالی باشد، مثلِ `[7, 3]`). کامپایلر همان‌طور که واریانت‌هایِ یک شمارشی را می‌شمرد، این سه‌تا را هم می‌شمرد: صفر، یک، دو-یا-بیشتر یک افرازِ کاملِ همه‌ی طول‌هایِ ممکن است، پس این `match` جامع است — بدونِ هیچ `_`ی.

```senpai-visual
{"kind":"concept","labels":["طول ۰: []","طول ۱: [x]","طول ۲ یا بیشتر: [first, .., last]","هر سه با هم هر طولی را می‌پوشانند"]}
```

مقایسه‌اش کن با نسخه‌ای که با `.len()` و ایندکس می‌نوشتی: `if samples.len() == 0 { .. } else if samples.len() == 1 { .. } else { samples[0]; samples[samples.len() - 1]; .. }`. اگر یکی از آن شاخه‌ها را جا می‌انداختی یا یک ایندکس را اشتباه می‌زدی، کامپایلر هیچ اعتراضی نمی‌کرد — فقط تو زمانِ اجرا پنیک می‌کردی یا عددِ غلط می‌گرفتی. الگویِ برش این اثبات را رایگان می‌دهد.

### `rest @ ..`: اسم‌گذاریِ وسط

بازوی سوم بالا، وسطِ برش را با `..` نادیده گرفت. اگر خودِ آن وسط را هم لازم داشته باشی — نه فقط اول و آخر — `@` همان کاری را می‌کند که در الگوهایِ عادی می‌کرد: به‌جایِ نادیده‌گرفتن، اسمش می‌گذارد:

```rust
fn middle(samples: &[u64]) -> &[u64] {
    match samples {
        [_, rest @ .., _] => rest,
        _ => &[],
    }
}
```

```text
[]               -> middle []
[42]             -> middle []
[7, 3]           -> middle []
[5, 80, 9, 12]   -> middle [80, 9]
```

`[_, rest @ .., _]` یعنی «یک عضوِ اول که برام مهم نیست، یک عضوِ آخر که برام مهم نیست، و هرچه وسط ماند اسمش `rest`». چون این الگو حداقل دو عضو می‌خواهد (یکی برایِ هر `_`)، برایِ برشِ صفر یا یک‌عضوی اصلاً تطبیق نمی‌خورد و بازوی `_` جوابِ خالی می‌دهد؛ برایِ دقیقاً دو عضو هم `rest` یک برشِ خالی می‌شود (چیزی بینِ دو عضوِ کناره‌هم نیست) — نه پنیک، نه خطا، فقط یک برشِ با طولِ صفر.

## خطاهایی که خواهی دید

### `E0308` — دو طرفِ یک الگویِ "یا" با هم هم‌نوع نیستند

```text
error[E0308]: mismatched types
  --> phase2-intermediate\10-rust-toolbox\01-pattern-matching-depth\examples\04-or-pattern-mismatch-broken.rs:16:81
   |
15 |     match event {
   |           ----- this expression has type `LogEvent`
16 |         LogEvent::Request { status: code } | LogEvent::Heartbeat { uptime_secs: code } => {
   |                                     ---- first introduced with type `u16` here  ^^^^ expected `u16`, found `u64`
   |
   = note: in the same arm, a binding must have the same type in all alternatives

For more information about this error, try `rustc --explain E0308`.
```

**کامپایلر به چه اعتراض دارد:** بازو یک اسمِ مشترک، `code`، رویِ هر دو جایگزینِ الگویِ "یا" بایند کرده. جایگزینِ اول (`status`) نوعش را `u16` تثبیت کرد؛ جایگزینِ دوم (`uptime_secs`) یک `u64` می‌دهد. کامپایلر نمی‌تواند تصمیم بگیرد `code` تویِ بدنه‌ی بازو کدام نوع است، پس رد می‌کند.

**راه‌حل:** دو جایگزین را دو بازوی جدا کن، هرکدام نوعِ خودش را نگه دارد:

```rust
match event {
    LogEvent::Request { status } => status.to_string(),
    LogEvent::Heartbeat { uptime_secs } => uptime_secs.to_string(),
}
```

**چرا این راه‌حل است:** حالا هیچ اسمی مجبور نیست بینِ دو نوعِ متفاوت مشترک باشد؛ هر بازو بدنه‌ی خودش را با نوعِ واقعیِ فیلدش می‌نویسد. الگویِ "یا" وقتی به‌کار می‌آید که چند شکل واقعاً یک بایندِ هم‌نوع بدهند — نه هر وقت دو جایگزین به‌نظر شبیه‌ به‌هم می‌رسند.

### `E0382` — قرضِ یک مقدارِ نیمه‌منتقل‌شده

```text
error[E0382]: borrow of partially moved value: `event`
  --> phase2-intermediate\10-rust-toolbox\01-pattern-matching-depth\examples\05-forgot-ref-broken.rs:24:16
   |
21 |         LogEvent::Message { text, .. } => println!("{text}"),
   |                             ---- value partially moved here
...
24 |     println!("{event:?}");
   |                ^^^^^ value borrowed here after partial move
   |
   = note: partial move occurs because value has type `String`, which does not implement the `Copy` trait
help: borrow this binding in the pattern to avoid moving the value
   |
21 |         LogEvent::Message { ref text, .. } => println!("{text}"),
   |                             +++

For more information about this error, try `rustc --explain E0382`.
```

**کامپایلر به چه اعتراض دارد:** `event` مالکیت‌دار است، نه ارجاع، پس تطبیقش با `text` بدونِ `ref` واقعاً `text` را از دلِ `event` منتقل می‌کند. بعد از آن، `event` دیگر کامل نیست — یک فیلدش رفته — و خطِ بعدی که کلِ `event` را می‌خواهد (`{event:?}`) چیزی ندارد که نشان بدهد.

**راه‌حل:** خودِ کامپایلر پیشنهادش را می‌دهد — `ref` جلویِ `text`:

```rust
LogEvent::Message { ref text, .. } => println!("{text}"),
```

**چرا این راه‌حل است:** `ref text` فقط یک ارجاع به `text` می‌گیرد، مالکیتش را نمی‌برد. `event` کامل می‌ماند، چون هیچ فیلدی از آن واقعاً جابه‌جا نشده — دقیقاً همان چیزی که «حالتِ اتصالِ پیش‌فرض» برایِ یک `&LogEvent` رایگان می‌دهد، این‌جا چون `event` خودش ارجاع نیست، باید صریح بخواهیش.

**کامپایلر به چه اعتراض دارد:** دو بازو مانده — یکی طولِ صفر (`[]`)، یکی طولِ دو-یا-بیشتر (`[first, .., last]`) — و بینشان یک شکافِ کامل هست: طولِ دقیقاً یک. `&[_]` دقیقاً یعنی همان — یک برشِ یک‌عضوی، هر عضوی که باشد.

**راه‌حل:** بازویِ گمشده را برگردان:

```rust
[only] => format!("1 sample: {only}ms"),
```

**چرا این راه‌حل است:** حالا سه بازو — صفر، یک، دو-یا-بیشتر — دقیقاً افرازِ همه‌ی طول‌هایِ ممکنِ یک برش است، و کامپایلر همین را ثابت می‌کند. یک زنجیره‌یِ `if/else` با `.len()` و ایندکس همین شکاف را داشت و ساکت می‌ماند — یا پنیک می‌کرد یا خروجیِ غلط می‌داد، فقط تو زمانِ اجرا و فقط اگر تست به آن طول برسد.

</details>

<details>
<summary>این کامپایل می‌شود؟ (فرض کن <code>r: Result&lt;i32, String&gt;</code>)</summary>

```rust
}
```

<details>
<summary>پاسخ</summary>

نه — `E0308`. `Ok`ِ یک `Result<i32, String>` یک `i32` می‌دهد، `Err`ش یک `String`؛ بایند کردنِ هر دو رویِ یک اسمِ مشترک، `n`، از او می‌خواهد هم‌زمان دو نوعِ متفاوت باشد.

</details>

</details>

<details>

سه‌تا: `[]` (طولِ صفر)، `[x]` (طولِ یک)، `[first, .., last]` (طولِ دو یا بیشتر). این سه با هم افرازِ کاملِ همه‌ی طول‌هایِ ممکن‌اند.

### بساز

در `src/lib.rs` یک تابعِ تازه بنویس:

```rust
pub fn middle_samples(samples: &[u64]) -> &[u64]
```

باید همان عناصرِ اکیداً بینِ اول و آخر را برگرداند — همان میانه‌ای که `[first, .., last]` تویِ `summarize_samples` هیچ‌وقت جدا اسمش نمی‌گذارد. دقیق‌تر:

- برایِ برشی با صفر یا یک عضو، «بین»ی وجود ندارد؛ خروجی یک برشِ خالی است.
- برایِ برشی با دقیقاً دو عضو هم خروجی خالی است — چیزی بینِ دو عضوِ کناره‌هم نیست.
- برایِ برشی با سه عضو یا بیشتر، خروجی همه‌ی عناصرِ اکیداً بینِ اولی و آخری است، به همان ترتیب.

مثلاً `middle_samples(&[5, 80, 9, 12])` باید `&[80, 9]` بدهد. این را با `rest @ ..` بنویس، نه با ایندکس‌گذاریِ دستی. یک تستِ کوچک هم برایش اضافه کن.

### چالش (اختیاری)

این بخش اختیاری است — اگر عجله داری ردش کن.

در `src/lib.rs` یک تابعِ تازه بنویس:

```rust
pub fn first_alert(events: &[LogEvent]) -> Option<String>
```

اگر **اولین** عضوِ `events` یک `Request` با `status >= 500` باشد، دقیقاً `format!("first event: server error {status} on {path}")` را برگردان — با `status` و `path`ِ همان اولین رویداد. برایِ هر حالتِ دیگر (برشِ خالی، یا اولین عضوی که `Request` نیست، یا `Request`ی با `status < 500`) `None` برگردان. این را با **یک** `match` تنها رویِ `events` بنویس — یک بازو که هم‌زمان شکلِ برش (فقط اولین عضو مهم است، بقیه هرچه باشند) و شکلِ تودرتویِ `Request` را با هم تطبیق می‌دهد، به‌علاوه‌ی یک نگهبان برایِ `status >= 500` — نه با `events.first()` و بعد یک `match` جدا.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| حالتِ اتصالِ پیش‌فرض (default binding mode) | تطبیقِ یک الگو از پشتِ `&`، هر فیلدی را که بایند می‌کنی خودکار با ارجاع می‌دهد | هر جا `&LogEvent` یا مشابهش را match می‌کنی |
| `ref` | بایندِ صریح‌بارجاع، برایِ وقتی مقدارِ مچ‌شده مالکیت‌دار است | قرض‌گرفتنِ یک فیلد بدونِ منتقل‌کردنِ بقیه‌ی مقدار |
| الگویِ برش | تطبیقِ `&[T]` بر اساسِ شکل — `[]`، `[x]`، `[first, .., last]` — جامع رویِ طولِ ۰ / ۱ / ۲+ | هر جا خودت وسوسه می‌شوی `.len()` و ایندکس بزنی |
| `rest @ ..` | اسم‌گذاریِ همان وسطی که `..` تنها نادیده می‌گرفت | وقتی خودِ عناصرِ میانه هم لازمت‌اند، نه فقط اول و آخر |

### الان می‌دانی

- چرا دو گاردِ رویِ‌هم‌جامع باز هم `match` را جامع نمی‌کنند — و کجایِ ۱.۵.۴ همین را با یک ترنسکریپتِ واقعی نشانت داد.
- چرا هر جایگزینِ یک الگویِ "یا" باید همان اسم‌ها را با همان نوع‌ها بایند کند، و `E0308`/`E0408` هرکدام کدام نقض را می‌گیرند.
- چرا تطبیقِ یک `&LogEvent` هر فیلدی که بایند کنی را با ارجاع می‌دهد — بدونِ اینکه چیزی بنویسی — و اسمِ این رفتار: حالتِ اتصالِ پیش‌فرض.
- کِی هنوز باید `ref` را با دست بنویسی: تطبیقِ یک مقدارِ مالکیت‌دار، وقتی فقط یک فیلدش را می‌خواهی قرض بگیری.
- کامپایلر چطور جامع‌بودنِ یک الگویِ برش را با شمردنِ طول ثابت می‌کند — `[]` / `[x]` / `[first, .., last]` برایِ ۰ / ۱ / ۲+ — و `rest @ ..` چطور خودِ آن وسط را هم اسم می‌دهد.

### بعداً کامل‌تر می‌بینی

- **`matches!` و بقیه‌ی ماکروهایِ اعلانی** — این درس فقط `match` را عمیق‌تر کرد؛ خودِ نوشتنِ یک ماکرو مالِ [۲.۱۰.۲ — مقدماتِ `macro_rules!`](../02-macro-rules-basics/README.fa.md) است.
- **تطبیقِ الگو رویِ کدهایِ واقعیِ یک بک‌اند** — پارس‌کردنِ payloadهایِ JSON، شاخه‌رفتن رویِ گونه‌هایِ خطا، مدل‌سازیِ حالتِ یک درخواست — از [فاز ۳ — پایه‌هایِ بک‌اند](../../../phase3-backend-foundations/README.fa.md) به بعد، همین چیزهایی که امروز دیدی، روزمره می‌شوند.

### می‌توانی توضیح بدهی؟

- چرا `n if n >= 0` و `n if n < 0` رویِ هم یک `match` را جامع نمی‌کنند؟
- یک الگویِ "یا" دقیقاً چه چیزی را بینِ جایگزین‌هایش یکسان می‌خواهد؟ اگر یکسان نباشد، چه خطایی می‌گیری؟
- «حالتِ اتصالِ پیش‌فرض» یعنی چه، و چرا `ref` امروز تقریباً هیچ‌وقت لازم نیست — مگر یک حالتِ خاص؟
- کامپایلر چطور ثابت می‌کند سه بازویِ `[]`/`[x]`/`[first, .., last]` هر طولی را می‌پوشانند؟ این را با زبانِ خودت، بدونِ نگاه کردن به بالا، توضیح بده.
