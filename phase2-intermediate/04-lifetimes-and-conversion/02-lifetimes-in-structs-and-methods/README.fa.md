# ۲.۴.۲ — طول‌عمر در ساختارها و متدها

## در یک نگاه

بعد از این درس می‌توانی:

- یک پارامترِ طول‌عمر به ساختاری اضافه کنی که داده‌ای را قرض گرفته، و دقیقاً بگویی این پارامتر چه قولی می‌دهد — از جمله اینکه چرا برنامه کامپایل نمی‌شود وقتی یک مقدار بخواهد از داده‌ای که به آن اشاره دارد بیشتر عمر کند (و `E0106` و `E0597` را وقتی خوردی، خودت رفع کنی).
- رویِ همان ساختار متدی بنویسی که ارجاعی برمی‌گرداند بدونِ اینکه خودت هیچ‌وقت `'a` را اسم ببری، و دقیقاً بگویی کدام‌یک از سه قانونِ حذفِ ۲.۴.۱ دارد این کار را می‌کند — و کِی یک امضا واقعاً هنوز به شکلِ صریح نیاز دارد.
- برایِ یک تکه‌کدِ واقعی تصمیم بگیری یک نوعِ تازه باید `&str` قرض بگیرد یا `String` مالک باشد — و این معامله را با صدای بلند توضیح بدهی، نه فقط نحوش را حفظ کرده باشی.

**زمان:** حدود ۴۰ دقیقه · **پیش‌نیاز:** [۲.۴.۱ — مبانیِ طول‌عمر و حذفِ آن](../01-lifetime-basics-and-elision/README.fa.md)

## چرا اهمیت دارد

۲.۴.۱ خودش، تویِ یک پرانتزِ کوتاه، به این موضوع اشاره کرد و رد شد: نگه‌داشتنِ خودِ یک ارجاع تویِ یک فیلدِ ساختار — چیزی مثلِ `struct Ticket<'a> { subject: &'a str }` — داستانِ کاملاً جداگانه‌ای دارد، و گفت همین درس سراغش می‌رود.

همان درس یک‌بار دیگر هم به این نزدیک شد، بدونِ اینکه خودش را کامل نشان بدهد: متدِ `Ticket::subject(&self) -> &str`ش قانونِ سومِ حذف را رویِ یک ساختار نشانت داد. ولی آن `Ticket` خودش هیچ طول‌عمری نداشت — فیلدش یک `String` کاملاً مالکانه بود، و متد فقط داشت داخلش را برش می‌زد. امروز همان قانونِ سوم را رویِ ساختاری می‌بینی که خودش از قبل یک `'a` دارد؛ و جوابِ اینکه این متد به `-> &'a str` نیاز دارد یا نه، آن‌قدرها هم که فکر می‌کنی بدیهی نیست.

و یک سؤالِ عملی‌تر هم پشتِ همه‌ی این‌هاست: چرا اصلاً یک ساختار باید ارجاع نگه دارد؟ چرا هر جا متنی لازم داری، یک `String` نمی‌گیری و راحت نمی‌شوی؟ جوابش یک تصمیمِ طراحیِ واقعی است، نه فقط یک قانونِ نحوی — و بخشِ آخرِ درس دقیقاً همین را باز می‌کند.

## مفهوم

### ساختاری که ارجاع نگه می‌دارد باید طول‌عمرش را اسم ببرد

فرض کن می‌خواهی یک تکه از یک متنِ بزرگ‌تر را نگه داری — مثلاً خط اولِ یک لاگِ طولانی — بدونِ اینکه کلش را کپی کنی. ساختار همین را می‌گوید:

```rust
struct Excerpt<'a> {
    text: &'a str,
}
```

فیلدِ `text` مالکِ رشته نیست؛ فقط یک ارجاع به آن است. و همان‌طور که ۲.۴.۱ نشانت داد، هیچ قانونِ حذفی برایِ فیلدهایِ ساختار وجود ندارد — اگر `<'a>` را از سرِ struct و `'a` را از جلویِ `&str` بردارید، کامپایل نمی‌شود؛ کامپایلر خودش دقیقاً همین `<'a>` را به‌ات پیشنهاد می‌دهد (کدِ کاملش در «خطاهایی که خواهی دید» است).

با پارامتر، ساختن و استفاده‌اش کاملاً معمولی است:

```rust
let article = String::from("Ownership is central. Borrowing comes next.");
let excerpt = Excerpt { text: &article };

println!("excerpt: {}", excerpt.text);
println!("source:  {article}");
```

```text
excerpt: Ownership is central. Borrowing comes next.
source:  Ownership is central. Borrowing comes next.
```

### پیامدش بار دارد: مقدارِ Excerpt نمی‌تواند از داده‌اش بیشتر عمر کند

`<'a>` فقط یک تشریفاتِ نحوی نیست. دقیقاً همان چیزی است که کامپایلر با آن، از این‌جا به بعد، هر مقدارِ `Excerpt<'a>` را دنبال می‌کند — درست به همان شکلی که یک `&str`ِ معمولی را دنبال می‌کرد. مثالِ بالا کامپایل شد چون `article` تا آخرِ استفاده از `excerpt` زنده ماند. حالا این ترتیب را برعکس کن: `article` را داخلِ یک بلوکِ کوچک‌تر بساز، و `excerpt` را بیرون از آن بلوک، بعد از پایانش، استفاده کن.

```senpai-visual

```

این دیگر کامپایل نمی‌شود — کامپایلر همان قاعده‌ای را رویِ `Excerpt` اجرا می‌کند که رویِ هر ارجاعِ دیگری اجرا می‌کرد: دارایِ یک `&article` هستی، پس نمی‌توانی از خودِ `article` بیشتر عمر کنی. تنها فرقش با یک ارجاعِ ساده این است که این‌بار آن ارجاع داخلِ یک ساختار پنهان شده — ولی کامپایلر لایِ struct را باز می‌کند و همان قرضِ زیرین را می‌بیند. کدِ کاملش، با خطایِ واقعی‌اش، تویِ `examples/03-excerpt-outlives-its-source.rs` و «خطاهایی که خواهی دید» است.

### قانونِ سومِ حذف، این‌بار رویِ متدها، کارِ واقعی انجام می‌دهد

حالا یک متد بنویس که واقعاً چیزی حساب می‌کند، نه فقط یک فیلد را برمی‌گرداند:

```rust
impl<'a> Excerpt<'a> {
    fn first_line(source: &'a str) -> Self {
        let text = source.lines().next().unwrap_or(source);
        Excerpt { text }
    }
}
```

این سازنده — چون خودش `&self` نمی‌گیرد — طول‌عمرِ `source` را صریح می‌نویسد: `source: &'a str`. هیچ قانونِ حذفی نمی‌تواند حدس بزند داده‌ی `source` قرار است تبدیل به همان `'a`یِ خودِ struct بشود؛ این را باید خودت بگویی. (اگر امتحان کنی و `&'a` را از جلویِ `source` برداری، کامپایل نمی‌شود — `rustc` می‌گوید «explicit lifetime required»، چون طول‌عمرِ حذف‌شده‌ی `source` هیچ ربطِ تضمین‌شده‌ای به `'a`یِ خودِ struct ندارد.)

حالا یک متدِ واقعی، رویِ همین struct:

```rust
impl<'a> Excerpt<'a> {
    // بدونِ 'a اینجا. قانونِ سوم: یک ورودیِ &self داریم، پس طول‌عمرِ
    // خروجیِ حذف‌شده مالِ همان قرضِ self است — نه 'aیِ خودِ struct.
    fn text(&self) -> &str {
        self.text
    }

    fn word_count(&self) -> usize {
        self.text.split_whitespace().count()
    }
}
```

شکلش انگار باید `-> &'a str` بخواهد، همان‌طور که خودِ struct می‌خواست. نمی‌خواهد. `text(&self) -> &str` بدونِ هیچ طول‌عمرِ صریحی کامپایل می‌شود و درست هم کار می‌کند — دقیقاً همان قانونِ سومِ حذف که ۲.۴.۱ معرفی کرد: چون یکی از ورودی‌ها `&self` است، طول‌عمرِ خروجیِ حذف‌شده مالِ همان قرضِ `self` می‌شود، نه مالِ `'a`یِ خودِ struct. و این دقیقاً همان چیزی است که می‌خواهی: `self.text` (که `&'a str` است) همیشه دستِ‌کم به‌اندازه‌ی خودِ قرضِ `self` عمر می‌کند — هیچ راهی نیست که یک `&Excerpt<'a>` وجود داشته باشد ولی داده‌ی زیرینش از قبل رفته باشد — پس کوتاه‌کردنِ آن به طول‌عمرِ کوتاه‌ترِ `self` همیشه امن است.

```senpai-visual
{"kind":"concept","labels":["فراخوانیِ excerpt.text()","self فقط برایِ همین فراخوانی قرض گرفته می‌شود","قانونِ سوم: خروجی به self گره می‌خورد","self.text از قبل عمرش بیشتر از self است","پس می‌شود امن کوتاهش کرد","برگشتیِ &str معتبر است"]}
```

با آن ساختار امتحانش کن:

```rust
let log_entry = String::from("connection reset by peer\nretrying in 3s\ngiving up");
let excerpt = Excerpt::first_line(&log_entry);

println!("first line: {}", excerpt.text());
println!("word count: {}", excerpt.word_count());
```

```text
first line: connection reset by peer
word count: 4
```

### قرض بگیر یا مالک باش: یک تصمیمِ طراحیِ واقعی

`Excerpt<'a>` یک قرض است، نه یک انتخابِ همیشگی. وقتی داده‌ی منبع از قبل جایی زنده است و تا وقتی به آن نیاز داری زنده می‌ماند، `&'a str` رایگان است — هیچ بایتی کپی نمی‌شود، هیچ تخصیصِ تازه‌ای اتفاق نمی‌افتد. این دقیقاً حالتِ زیر است: `logs` بیرون از تابع زنده می‌ماند، پس `Excerpt`هایی که این تابع برمی‌گرداند می‌توانند امن به آن قرض بگیرند:

```rust
fn first_lines_of<'a>(logs: &'a [String]) -> Vec<Excerpt<'a>> {
    logs.iter().map(|log| Excerpt::first_line(log)).collect()
}
```

ولی گاهی چیزی برایِ قرض‌گرفتن نداری. اگر هر رشته فقط موقتاً، وسطِ یک حلقه ساخته می‌شود — یک پاسخِ شبکه‌ای، یک بافرِ دیکد‌شده — هیچ `Excerpt<'a>`ای نمی‌تواند از آن قرض بگیرد و بعد از پایانِ همان تکرارِ حلقه هم زنده بماند. اینجا مالک‌بودن جواب است:

```rust
fn fetch_response(id: u32) -> String {
    format!("200 OK (request {id})\nbody omitted")
}

fn first_line_of_each_response(request_ids: &[u32]) -> Vec<String> {
    let mut summaries = Vec::new();
    for id in request_ids {
        let response = fetch_response(*id);
        let first_line = response.lines().next().unwrap_or("").to_string();
        summaries.push(first_line);
    }
    summaries
}
```

هر دویِ این‌ها را کنارِ هم اجرا کن:

```rust
let logs = vec![
    String::from("started\nrunning"),
    String::from("connected\nidle"),
];
for excerpt in first_lines_of(&logs) {
    println!("borrowed: {}", excerpt.text);
}

for summary in first_line_of_each_response(&[1, 2]) {
    println!("owned:    {summary}");
}
```

```text
borrowed: started
borrowed: connected
owned:    200 OK (request 1)
owned:    200 OK (request 2)
```

قاعده‌ی عملی همین است: اگر منبع، طولِ عمرش را از قبل از تو بیشتر تضمین کرده، `&'a str` بگیر — مجانی است. اگر منبع موقتی است، یا اصلاً یک منبعِ واحد نداری (مثلاً داری خودِ رشته را با `format!` می‌سازی)، `String` بگیر. این وسط یک راهِ سوم هم هست: نوعی به اسمِ `Cow<'_, str>`، دقیقاً برایِ همین حالتِ «شاید قرضی، شاید مالکی» — که ۲.۴.۴ کاملش را به‌ات نشان می‌دهد. امروز لازمش نداری؛ امروز انتخاب دوتایی است، و همین کافی است.

## خطاهایی که خواهی دید

### `E0106` — طول‌عمر مشخص نشده

```text
error[E0106]: missing lifetime specifier
 --> phase2-intermediate\04-lifetimes-and-conversion\02-lifetimes-in-structs-and-methods\examples\02-struct-without-lifetime.rs:6:11
  |
6 |     text: &str,
  |           ^ expected named lifetime parameter
  |
help: consider introducing a named lifetime parameter
  |
5 ~ struct Excerpt<'a> {
6 ~     text: &'a str,
  |

For more information about this error, try `rustc --explain E0106`.
```

**کامپایلر به چه اعتراض دارد:** فیلدِ `text` یک ارجاع است (`&str`) ولی هیچ طول‌عمری اسم برده نشده، و برایِ فیلدهایِ ساختار — برخلافِ پارامترهایِ تابع — هیچ قانونِ حذفی وجود ندارد که خودش یکی حدس بزند. کامپایلر باید دقیقاً بداند این ارجاع چقدر معتبر می‌ماند تا بتواند هر مقدارِ `Excerpt` را دنبال کند.

**راه‌حل:** دقیقاً همان چیزی که کامپایلر پیشنهاد می‌دهد:

```rust
struct Excerpt<'a> {
    text: &'a str,
}
```

**چرا این راه‌حل است:** `<'a>` رویِ خودِ struct پارامتری تعریف می‌کند که فیلدِ `text` می‌تواند به آن اشاره کند. حالا هر مقدارِ `Excerpt<'a>` مشخص است دقیقاً برایِ چه طول‌عمری معتبر است — همان چیزی که پیامِ بعدی نشانت می‌دهد وقتی این قول شکسته شود.

### `E0597` — داده‌ی قرض‌گرفته‌شده عمرِ کافی ندارد

```text
error[E0597]: `article` does not live long enough
  --> phase2-intermediate\04-lifetimes-and-conversion\02-lifetimes-in-structs-and-methods\examples\03-excerpt-outlives-its-source.rs:13:35
   |
12 |         let article = String::from("Ownership is central. Borrowing comes next.");
   |             ------- binding `article` declared here
13 |         excerpt = Excerpt { text: &article };
   |                                   ^^^^^^^^ borrowed value does not live long enough
14 |     }
   |     - `article` dropped here while still borrowed
15 |     println!("first line: {}", excerpt.text);
   |                                ------------ borrow later used here

For more information about this error, try `rustc --explain E0597`.
```

**کامپایلر به چه اعتراض دارد:** `excerpt` یک `&article` نگه داشته، ولی `article` تویِ یک بلوکِ داخلی‌تر تعریف شده و همان‌جا هم آزاد می‌شود. `excerpt` بیرون از آن بلوک هنوز استفاده می‌شود — یعنی دارد از داده‌ای استفاده می‌کند که دیگر وجود ندارد. این همان چیزی است که `<'a>` رویِ خودِ struct از اول قول داده بود جلویش را بگیرد.

**راه‌حل:** ترتیب را عوض کن تا منبع، از استفاده‌کننده‌اش بیشتر عمر کند — بدونِ پاک‌کردنِ بلوکِ داخلی:

```rust
let article = String::from("Ownership is central. Borrowing comes next.");
let excerpt;
{
    excerpt = Excerpt { text: &article };
}
println!("first line: {}", excerpt.text);
```

**چرا این راه‌حل است:** حالا `article` بیرون از هر بلوکی تعریف شده که `excerpt` می‌سازد، پس تا وقتی `excerpt` استفاده می‌شود هنوز زنده است. هیچ‌چیزی درباره‌یِ خودِ `Excerpt` عوض نشد — فقط ترتیبِ زنده‌ماندنِ داده‌ها با ترتیبِ استفاده‌شان جور شد، دقیقاً همان چیزی که کامپایلر رویِ هر ارجاعِ دیگری هم می‌خواهد.

```rust
    let id = String::from("A1029");
    coupon = Coupon { code: &id };
}
println!("{}", coupon.code);
```

</details>

نه. همان شکلِ `E0597`: `id` تویِ بلوکِ داخلی آزاد می‌شود، ولی `coupon` بیرون از آن بلوک هنوز استفاده می‌شود.

### تعمیر

هر دو مثالِ خراب را درست کن:

۱. `examples/02-struct-without-lifetime.rs` را طوری درست کن که کامپایل شود — با اضافه‌کردنِ پارامترِ طول‌عمرِ جاافتاده به struct، دقیقاً همان چیزی که پیشنهادِ کامپایلر می‌گوید.
۲. `examples/03-excerpt-outlives-its-source.rs` را طوری درست کن که کامپایل شود — بدونِ پاک‌کردنِ بلوکِ داخلی؛ به‌جایش جایِ تعریفِ `article` را عوض کن تا از `excerpt` بیشتر عمر کند.

### پیاده‌سازی

چهار بخش تویِ `src/lib.rs`:

```sh
cargo test -p p2-04-02-lifetimes-in-structs-and-methods
```

خودِ `struct Excerpt` و سازنده‌ی `first_line` از قبل کامل نوشته شده‌اند — دقیقاً همان چیزی که تویِ «مفهوم» دیدی. کارِ تو یک سازنده‌ی دیگر (`whole`)، دو متد (`text`، `word_count`)، و یک تابعِ ساده (`total_words`) است. فرمتِ دقیقِ هرکدام، بالایِ همان تابع، تویِ کامنتِ مستندات نوشته شده — چیزی حدس نزن.

### بساز

یک ساختارِ کوچکِ خودت بساز که یک `&'a str` (یا `&'a [T]`) نگه دارد — یک پارسر، یک توکنایزر، یک اعتبارسنج، هر چیزی که خودت دوست داری، فقط نه `Excerpt`. دستِ‌کم یک متد رویش بگذار که `&self` می‌گیرد و ارجاعی برمی‌گرداند، بدونِ اینکه هیچ طول‌عمرِ صریحی بنویسی. دستِ‌کم یک تست هم برایش بنویس.

### چالش (اختیاری)

کنارِ `text`، یک متدِ دومِ `Excerpt` بساز که همان `self.text` را برمی‌گرداند ولی طول‌عمرِ خودِ struct را صریح می‌نویسد — `-> &'a str` به‌جایِ `-> &str`. هر دو کامپایل می‌شوند. حالا یک تابعِ آزادِ دیگر بنویس، بیرونِ `impl`، که یک `&Excerpt<'a>` می‌گیرد و سعی می‌کند یک `&'a str` برگرداند، با صدازدنِ یکی از این دو متد. فقط یکی از آن دو اجازه می‌دهد کامپایل شود — کدام‌یک، و چرا؟ (سرنخ: به این فکر کن که نسخه‌ی حذف‌شده واقعاً خروجی‌اش را به چه چیزی گره می‌زند — به `'a` نیست.)

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| پارامترِ طول‌عمرِ ساختار | `<'a>` رویِ ساختاری که ارجاع نگه می‌دارد؛ هر مقدارِ آن نوع را به داده‌ای که قرض گرفته گره می‌زند | هر نوعی که به‌جایِ مالکِ `T`، یک `&T` نگه می‌دارد |
| `E0106` | طول‌عمر مشخص نشده | فراموش‌کردنِ `<'a>` رویِ فیلدی که ارجاع است |
| `E0597` | داده‌ی قرض‌گرفته‌شده عمرِ کافی ندارد | استفاده از یک مقدارِ ساختاری بعد از آزادشدنِ داده‌ای که قرض گرفته |
| قانونِ سومِ حذف رویِ متدها | خروجیِ حذف‌شده، طول‌عمرِ خودِ `self` را می‌گیرد، نه `'a`یِ ساختار | هر متدِ گیرنده‌ی `&self` رویِ ساختاری که طول‌عمر دارد |
| قرض بگیر یا مالک باش | `&'a str` وقتی منبع از تو بیشتر عمر می‌کند؛ `String` وقتی نمی‌کند | طراحیِ هر نوعِ تازه‌ای دورِ یک متنِ موجود |

### الان می‌دانی

- ساختاری که ارجاع نگه می‌دارد باید خودش پارامترِ طول‌عمر داشته باشد — هیچ قانونِ حذفی برایِ فیلدهایِ ساختار وجود ندارد.
- آن پارامتر بار دارد: هیچ مقداری از آن ساختار نمی‌تواند از داده‌ای که ارجاعش به آن اشاره دارد بیشتر عمر کند، دقیقاً به همان شکلی که برایِ هر قرضِ دیگری اجرا می‌شود.
- فراموش‌کردنِ آن پارامتر `E0106` است؛ اجازه‌دادن به یک مقدار که از منبعش بیشتر عمر کند `E0597` است — هر دو، پیش از اجرایِ برنامه، سرِ کامپایل گرفته می‌شوند.
- متدی که `&self` می‌گیرد رویِ چنین ساختاری تقریباً هیچ‌وقت خودش به طول‌عمرِ صریح نیاز ندارد — قانونِ سومِ حذف خروجیِ حذف‌شده را به همان قرضِ `self` گره می‌زند، و این دقیقاً درست است چون طول‌عمرِ خودِ ساختار همیشه از هر قرضی رویِ آن بیشتر است.
- تابعِ وابسته‌ای که `&self` نمی‌گیرد (یک سازنده) این کمک را نمی‌گیرد — اگر `Self`ای با طول‌عمر برمی‌گرداند، خودت باید آن طول‌عمر را صریح بنویسی.
- اینکه یک نوعِ تازه باید قرض بگیرد (`&'a str`) یا مالک باشد (`String`) یک تصمیمِ طراحیِ واقعی است، نه یک قانونِ نحوی: وقتی منبع واضح از تو بیشتر عمر می‌کند قرض بگیر؛ وقتی نمی‌کند، یا وقتی اصلاً یک منبعِ واحد برایِ قرض‌گرفتن نداری، مالک باش.

### بعداً کامل‌تر می‌بینی

- **`Deref`، `AsRef`، `Borrow`، `ToOwned` — خانواده‌ی کاملِ تبدیل‌هایِ قرضی** — [۲.۴.۳ — Deref، AsRef، Borrow، ToOwned](../03-deref-asref-borrow/README.fa.md)
- **`Cow<'_, str>` — راهِ سوم، بینِ قرض‌گرفتن و مالک‌بودن** — [۲.۴.۴ — Cow و کپی‌هنگامِ‌نوشتن](../04-cow-and-clone-on-write/README.fa.md)

### می‌توانی توضیح بدهی؟

- چرا یک ساختاری که ارجاع نگه می‌دارد باید پارامترِ طول‌عمرِ خودش را داشته باشد، وقتی خیلی از پارامترهایِ تابع اصلاً نیازی به آن ندارند؟
- `Excerpt<'a>` دقیقاً چه قولی درباره‌ی هر مقداری از آن نوع می‌دهد؟
- چرا فراموش‌کردنِ طول‌عمرِ ساختار یک خطایِ متفاوت از عمرنکردنِ کافیِ داده است؟ کامپایلر تویِ هرکدام دقیقاً از چه چیزی شاکی است؟
- چرا `fn text(&self) -> &str` نیازی به `-> &'a str` ندارد؟ کدام قانونِ حذف این کار را می‌کند، و خروجی را واقعاً به چه چیزی گره می‌زند؟
- چرا `first_line`، که `&self` نمی‌گیرد، باید طول‌عمرش را صریح بنویسد؟
- کِی سراغِ `&'a str` می‌روی برایِ یک نوعِ تازه، و کِی سراغِ `String`؟
