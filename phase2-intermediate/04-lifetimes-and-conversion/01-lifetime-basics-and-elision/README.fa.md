# ۰۴.۳ — مبانی طول‌عمر (Lifetime) و مفهوم elision

از فاز ۱ به بعد، تو داشتی کدهایی می‌نوشتی که عملکردشون کاملاً وابسته به طول‌عمرها بود، اون هم بدون اینکه حتی یه بار اسمشون رو به صورت صریح تو کدت بنویسی (مثلاً تو تابع `longest_word` تو بخش `phase1-fundamentals/04-strings-and-slices/01-string-vs-str`، یا `find_by_anime` تو ماموریت جانبی anime-quote-cli). این درس، دقیقاً همون چیزی رو که کامپایلر تا الان تو خفا برات استنتاج می‌کرد (infer می‌کرد) رو شفاف و صریح می‌کنه.

## طول‌عمر (lifetime) واقعاً چیه

طول‌عمر یه مقدار (value) نیست و تو زمان اجرا (runtime) اصلاً وجود خارجی نداره — این فقط اسمیه که کامپایلر واسه نشون دادنِ **مدت زمانی که یه ارجاع (reference) معتبر می‌مونه** روش گذاشته، و صرفاً برای بررسی کدهای تو همون زمان کامپایل (compile time) ازش استفاده می‌شه. عبارت `'a` فقط یه برچسبه (label)، دقیقاً همون‌طوری که `T` فقط یه برچسب برای یه نوعِ عمومیه (generic type) — عبارتِ `'a` به تنهایی هیچ معنی خاصی نداره؛ فقط زمانی معنادار می‌شه که روی *چندین* چیز مختلف بشینه و اعتبارشون رو به هم گره بزنه:

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```

امضای این تابع می‌گه: «اگه دو تا بُرش رشته (string slice) بهم بدی که *جفتشون* حداقل برای یه طول‌عمر به اسم `'a` معتبر باشن، منم یه بُرش رشته بهت برمی‌گردونم که اون هم برای همون `'a` معتبره.» این در واقع یه قید (constraint) روی *رابطه‌ی* بین ورودی‌ها و خروجیه، نه یه طول‌عمری که تو خودت از خودت درآورده باشی — کامپایلر هنوز هم تو هر محلِ فراخوانی (call site) خودش اون طول‌عمر واقعی و ملموس رو محاسبه و استنتاج می‌کنه؛ تو فقط داری بهش می‌گی که ورودی‌ها و خروجی چطور به هم ربط دارن.

## حذف و نادیده‌گرفتنِ طول‌عمرها (Elision): سه قانونی که باعث می‌شه تو معمولاً اینا رو ننویسی

اکثر توابعی که ارجاع می‌گیرن، هیچ نیازی به نوشتنِ صریحِ طول‌عمرها ندارن، چون کامپایلر اول از همه سه تا قانون رو روی کد پیاده می‌کنه، و فقط زمانی ازت می‌خواد که طول‌عمر رو بنویسی که این قوانین نتونن یه جواب بی‌ابهام براش پیدا کنن:

1. **هر کدوم از ارجاع‌های ورودی که طول‌عمرش نادیده گرفته شده (elided)، یه طول‌عمرِ مختص خودش می‌گیره.** یعنی امضای `(fn foo(x: &str, y: &str` تو واقعیت اینطوریه: `(fn foo<'a, 'b>(x: &'a str, y: &'b str`.
2. **اگه دقیقاً و فقط یک طول‌عمرِ ورودی وجود داشته باشه، همون طول‌عمر به تمامِ طول‌عمرهای نادیده‌گرفته‌شده‌ی خروجی هم نسبت داده می‌شه.** دقیقاً به همین دلیله که تابع `fn longest_word(text: &str) -> &str` (از فاز ۱) هیچ نیازی به `<'a>` نداشت — چون فقط یه ارجاع ورودی داشت، کامپایلر فهمید که خروجی حتماً باید از همون قرض بگیره.
3. **اگه یکی از ورودی‌ها `&self` یا `&mut self` باشه (یعنی تابع یه متد باشه)، خروجی همون طول‌عمری رو می‌گیره که مالِ `self` هست.** دقیقاً به همین دلیله که متدهایی که ارجاعی به داخل `self` برمی‌گردونن هم تقریباً هیچ‌وقت نیازی به نوشتن صریح طول‌عمرها ندارن.

اما تو تابعِ `longest` (بالاتر)، نوشتن `<'a>` اجباریه چون این تابع **دو تا** ارجاع ورودی داره (که طبق قانون ۱، به طور پیش‌فرض دو تا طول‌عمرِ جداگانه‌ی `'a` و `'b` می‌گیرن) و فقط یک ارجاعِ خروجی — هیچ‌کدوم از اون سه تا قانون نمی‌تونن تصمیم بگیرن که خروجی باید طول‌عمرش رو از کدوم یکی از این ورودی‌ها به ارث ببره، پس کامپایلر متوقف می‌شه و تو رو مجبور می‌کنه که خودت صریحاً این موضوع رو روشن کنی.

## وقتی یه ساختار (Struct) قراره یه ارجاع رو تو خودش نگه داره

```rust
struct Excerpt<'a> {
    text: &'a str,
}
```

یه struct نمی‌تونه بیشتر از داده‌ای که قرض گرفته زنده بمونه — عبارت `<'Excerpt<'a` می‌گه «هیچ مقداری از `Excerpt` نمی‌تونه بیشتر از اون `&str`ای که فیلدِ `text` داره بهش اشاره می‌کنه زنده بمونه.» این قضیه همیشه باید صریح باشه؛ هیچ قانونِ حذفی (elision rule) برای فیلدهای یه ساختار وجود نداره.

## طول‌عمر `'static`

عبارتِ `'static` یعنی «معتبر برای تمامِ ادامه‌ی زمان اجرای برنامه» — رشته‌های متنی (مثل `"hello"`) از جنس `&'static str` هستن چون مستقیماً و به صورت سخت‌افزاری تو دل همون باینری کامپایل‌شده جا داده می‌شن، نه اینکه تو زمان اجرا براشون حافظه اختصاص داده بشه. با این حال، دیدن `'static` تو یه محدودیت (bound) مثل `T: 'static` همیشه هم به معنیِ «تا ابد زنده می‌مونه» نیست — وقتی این برچسب رو یه پارامترِ نوعِ عمومی (generic type parameter) می‌شینه، معنیش دقیق‌تر این می‌شه: «شامل هیچ داده‌ی قرض‌گرفته‌شده‌ای که طول‌عمرش از این کوتاه‌تر باشه نیست.» این شاملِ تمام داده‌های کاملاً دارای مالکیت (owned) (مثل `String` یا `<Vec<T`) هم می‌شه، همون‌قدری که شامل ارجاع‌های واقعاً `'static` می‌شه.
