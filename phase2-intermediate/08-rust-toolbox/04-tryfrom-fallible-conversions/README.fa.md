# ۰۸.۴ — مبحث `TryFrom` و تبدیل‌های خطاپذیر (fallible conversions)

قبلاً تو ماژول مدیریت خطاها با خصیصه‌های `From`/`Into` آشنا شدی: صفت `From` مخصوصِ تبدیل‌هاییه که **امکان نداره شکست بخورن** — مثل `("String::from("hi`، مثلِ `(i64::from(some_u32`، یا نوع‌های خطای خودت که خطای `io::Error` رو جذب می‌کنن و تو دل خودشون جا می‌دن. اما اکثرِ تبدیل‌های جذاب و مهم *می‌تونن* با شکست مواجه بشن: هر `u8`ی نشون‌دهنده‌ی یه درصد (percentage) معتبر نیست، هر `String`ی یه آدرس ایمیل نیست، هر `u64`ی تو ظرف یه `u32` جا نمی‌شه. جواب زبان Rust به این دسته از تبدیل‌ها خصیصه‌ی `TryFrom` هست — دقیقاً با همون شکل و شمایل، منتهی با این تفاوت که یه `Result` برمی‌گردونه:

```rust
impl TryFrom<u8> for Percentage {
    type Error = ValidationError;
    fn try_from(raw: u8) -> Result<Self, Self::Error> { ... }
}
```

تعریف نوعِ `Error` به عنوان یه نوع پیوسته (associated type) تو این trait، یعنی هر تبدیلی نوعِ شکست و خطایِ *مختص خودش* رو مشخص می‌کنه — و خبری از یه استثنای کلی و عمومی (one-size-fits-all exception) نیست. و دقیقاً همون‌طوری که `From` به صورت خودکار بهت `Into` رو می‌ده، با پیاده‌سازیِ `TryFrom<u8> for Percentage` هم، زبان Rust به طور رایگان و خودکار نسخه‌ی قرینه‌اش یعنی `TryInto` رو بهت هدیه می‌ده: `?()let p: Percentage = 42u8.try_into`. تو فقط همون `TryFrom` رو پیاده‌سازی کن، و موقع استفاده هرکدوم که باعث شد کدت خواناتر و قشنگ‌تر بشه رو به کار ببر. قانون سرانگشتی برای انتخاب بین این دو تا trait اینه: اگه می‌تونی **تک‌تکِ** مقادیر ورودیِ ممکن رو تبدیل کنی برو سراغ `From`؛ اما اگه حتی *یک* مقدار ورودی هم وجود داره که باید رد (reject) بشه، برو سراغ `TryFrom` — نوشتن یه `impl From` که واسه یه سری ورودی‌های "بد" پنیک (panic) کنه، از نظر سیستم نوعِ (type system) زبان، یه دروغِ محضه.

## تبدیلِ کوچیک‌شونده‌ی اعداد (Numeric narrowing): جایی که پایتون اصلاً حتی نمی‌تونه مشکل رو ببینه

زبان پایتون فقط یه دونه نوع `int` داره که دقت و ظرفیتش نامحدوده — عددی مثلِ `64**2` هم براش یه عدد صحیحِ معمولیه، و مفهومی به اسم "تو ظرفش جا نمی‌شه" اصلاً اونجا تعریف نشده. اما تو زبان Rust که اعداد صحیح عرضِ ثابتی (fixed-width) دارن، کوچیک‌تر کردن ظرفِ متغیرها (narrowing) یه تصمیم واقعیه، و برای این کار دو تا ابزارِ کاملاً متفاوت بهت داده شده:

```rust
let big: u64 = 300;
let a = big as u8;                       // ۴۴ — بی‌سروصدا اضافه‌ها (بیت‌های بالایی) رو دور می‌ریزه!
let b: Result<u8, _> = big.try_into();   // (Err(TryFromIntError — یه خطای صادقانه می‌ده
```

استفاده از کلمه‌ی `as` هیچ‌وقت شکست نمی‌خوره؛ فقط خیلی ساده مقدار رو می‌بُره (چاپ می‌کنه) (باقی‌مانده‌ی ۳۰۰ تقسیم بر ۲۵۶ می‌شه ۴۴). بعضی وقتا، مثلاً خیلی کم پیش میاد که دقیقاً همین رفتار رو بخوای، اما اگه قرار باشه به عنوان یه رفتارِ *پیش‌فرض* در نظر گرفته بشه، کلاً یه کارخونه‌ی باگ‌سازی به حساب میاد. کتابخونه‌ی استاندارد Rust اومده و برایِ تمام جفت‌های عددی که تبدیلشون ممکنه با شکست روبرو بشه، خصیصه‌ی `TryFrom` رو پیاده‌سازی کرده؛ در نتیجه `()big.try_into` بهت یه `Result` می‌ده و باعث می‌شه حالتِ "جا نشدنِ عدد" تبدیل به یه مقدار بشه که تو **مجبوری** هندلش کنی — حالا یا با عملگر `?` پرتش کن لایه‌های بالاتر، یا با `(...)unwrap_or.` یه مقدار پیش‌فرض بهش بده، و یا اینکه روش `match` انجام بده. تو این درس تابعِ `saturating_narrow` دقیقاً همین مسیرِ دوم رو انتخاب کرده: یعنی به جای اینکه مقدار رو بُرش بده (truncate) یا برنامه رو کرش (crash) کنه، عدد رو تو سقفِ `u32::MAX` نگه می‌داره و می‌چسبونه همونجا (clamp می‌کنه).

## الگوی اعتبارسنجی با ساخت یه نوع جدید (validated-newtype pattern) ("پارس کن، فقط اعتبارسنجی نکن")

تو دنیای پایتون رفلکسِ طبیعیِ آدم‌ها نوشتنِ یه تابع بررسی‌کننده‌ست — `... :(def is_valid_email(s` — که همون اول کار صدا زده می‌شه، و بعد از اون هر کسی که تو لایه‌های پایین‌تر داره از اون مقدار استفاده می‌کنه فقط *امیدواره* که این چک‌کردن واقعاً انجام شده باشه. فرم‌های جنگو (Django forms) و کتابخونه‌ی pydantic همین ایده رو یه قدم می‌برن جلوتر: تو همون نقطه‌ی ورودِ اطلاعات اعتبارسنجی رو انجام می‌دن، و بعدش تو داخل برنامه همون `str`های ساده رو دست‌به‌دست می‌کنن. اما الگویِ رایج تو زبان Rust یه قدم از اینم فراتر میره: اون مقدار رو می‌پیچه (wrap می‌کنه) تو دلِ یه **نوعِ جدید (newtype) که کانستراکتورش (سازنده‌اش)، خودِ همون عملیات اعتبارسنجیِ**شه:

```rust
pub struct EmailAddress(String);   // فیلد کلاً خصوصیه (PRIVATE)

impl TryFrom<String> for EmailAddress { ... }   // این تنها و تنها راهِ ورود بهشه
```

چون فیلدش خصوصیه، *تنها* راهِ ممکن برای به دست آوردن یه نمونه از `EmailAddress` اینه که از دروازه‌ی `try_from` رد بشی، در نتیجه صرفِ داشتنِ یکی از اونا تو دستت، **خودش یه سندِ قطعیه برای اینکه اون مقدار از سدِ اعتبارسنجی گذشته**. یه امضای تابعی مثل `(fn notify(to: &EmailAddress` رو اصلاً نمی‌شه با یه رشته‌ی بررسی‌نشده و خام صدا زد — اینطوری، جوابِ سؤالِ "آیا کسی قبلاً اینو چک کرده؟" توسطِ خود کامپایلر (type checker) داده می‌شه، نه تو پروسه‌ی code review. این همون شعارِ معروفه که می‌گه "پارس کن، فقط اعتبارسنجی نکن (parse, don't validate)": یه تابع اعتبارسنجِ ساده که یه `bool` برمی‌گردونه، دانشی رو تولید می‌کنه که همون ثانیه دود می‌شه و می‌ره هوا؛ اما پارس کردن یه مقدار و تبدیلش به یه نوعِ غنی‌تر (richer type)، دانشی رو به وجود میاره که برای همیشه به اون مقدار می‌چسبه. (این البته همون فلسفه‌ی pydantic هم هست، اما با این تفاوت که اینجا تو زمان کامپایل اجبار می‌شه و بعد از ساخته‌شدنشون هیچ هزینه‌ای هم تو زمان اجرا (zero runtime cost) ندارن — یعنی متغیرِ `(Percentage(u8` تو حافظه دقیقاً و دقیقاً همون ۱ بایت جا رو می‌گیره.)

دو تا نکته‌ی فنی واسه تمرین‌ها. اول اینکه، به جای عمومی کردنِ (`pub`) فیلدها، واسه اون newtypeها یه متدِ دسترسی فقط-خواندنیِ (read-only accessor) صریح و روشن بنویس (مثل `()value.`، یا `()as_str.`) — اگه فیلد رو `pub` کنی، هر کسی می‌تونه خیلی راحت با نوشتنِ `()email.0 = "garbage".into` اون قانونِ حفاظتی (invariant) رو دور بزنه. دوم اینکه، تو مسیر خطاها، همون ورودیِ ردشده (rejected input) رو بذار تو دلِ خودِ خطا و برگردون (مثلاً `((InvalidEmail(String`) : فراخواننده از اولش مالکیتِ اون داده رو داده بود دستت، و برگردوندن همون داده باعث می‌شه اونا بتونن بدون اینکه نیازی به کپی کردن (clone) داشته باشن، اونو لاگ کنن یا دوباره ازش استفاده کنن.

## وظیفه‌ی تو

تو فایل `src/lib.rs` (اون enumِ مربوط به خطای `ValidationError` و پیاده‌سازیِ `Display` براش از قبل نوشته شده — اول اونا رو بخون):

- `TryFrom<u8> for Percentage` — فقط محدوده‌ی `100..=0` رو بپذیر، و بقیه رو با ارورِ `PercentageOutOfRange` رد کن.
- `TryFrom<String> for EmailAddress` — یه اعتبارسنجی که از روی قصد خیلی خیلی ساده در نظر گرفته شده: فقط باید دقیقاً یک دونه کاراکترِ `@` داشته باشه، و هر دو سمتِ `@` هم نباید خالی باشن. (اعتبارسنجی واقعی و کاملِ ایمیل خودش یه مردابه؛ خواهشاً سعی نکن از regex استفاده کنی.)
- `saturating_narrow` — تبدیل `u64` به `u32` با استفاده از `try_into`، که در صورتِ سَرریز شدنِ (overflow) مقدار، اونو بچسبونه به حدِ بالای ظرفیتش، یعنی `u32::MAX`.
