# راه‌حل

```rust
impl TryFrom<u8> for Percentage {
    type Error = ValidationError;

    fn try_from(raw: u8) -> Result<Self, Self::Error> {
        if raw <= 100 {
            Ok(Percentage(raw))
        } else {
            Err(ValidationError::PercentageOutOfRange(raw))
        }
    }
}
```

عمداً هیچ ایده‌ی پیچیده یا نبوغ‌آمیزی توش نیست — ارزشِ واقعیِ این پیاده‌سازی تو *محل قرارگیریشه (where it lives)*، نه اینکه چطوری نوشته شده. چون فیلدِ `Percentage` کاملاً خصوصیه، این دستورِ `if` دقیقاً همون یک‌دونه نقطه‌ی ممکنه تو کُل دنیاست که یه `Percentage` می‌تونه توش متولد بشه؛ پس هر جا تو هر گوشه‌ای از برنامه‌ات یه `Percentage` دیدی، می‌تونی قسم بخوری که از زیرِ دست همین شرط رد شده. بیا و این فیلد رو `pub` کن تا اون تضمینِ گلوبال و سراسری تو همون ثانیه دود بشه بره هوا، اونم بدون اینکه کدِ حتی یه دونه از فراخواننده‌ها (callers) تغییری کنه: چون اونوقت عبارتی مثلِ `Percentage(255)` می‌تونه هرجایی تو کد با موفقیت ساخته بشه، و اونوقت اون تضمین که "آیا واقعاً بین ۰ تا ۱۰۰ هست یا نه؟" دوباره برمی‌گرده سر خونه‌ی اول و تبدیل می‌شه به چیزی که باید تو جلسات بررسی کد (code-review) با اماواگر چکش کنی، نه اینکه دیگه یه حقیقتِ مسلم تو دلِ سیستم نوع‌ها (type-system) باشه.
ضمناً به چیزی که تستِ `implementing_try_from_provides_try_into_for_free` داره اثباتش می‌کنه هم توجه کن: ما هیچ‌کجا و اصلاً متدِ `TryInto` رو ننوشتیم. کتابخونه‌ی استاندارد Rust خودش یه پیاده‌سازیِ کلی (blanket impl) داره به این شکل: `impl<T, U> TryInto<U> for T where U: TryFrom<T>`، که دقیقاً معادل و قرینه‌ی همون پُلی بین `From`/`Into` هستش که از زمان ماژولِ مدیریت خطاها تا الان داشتی بهش تکیه می‌کردی.

```rust
impl TryFrom<String> for EmailAddress {
    type Error = ValidationError;

    fn try_from(raw: String) -> Result<Self, Self::Error> {
        let valid = matches!(
            raw.split_once('@'),
            Some((local, domain))
                if !local.is_empty() && !domain.is_empty() && !domain.contains('@')
        );

        if valid {
            Ok(EmailAddress(raw))
        } else {
            Err(ValidationError::InvalidEmail(raw))
        }
    }
}
```

ظاهرِ این تابع دقیقاً همون‌طوریه که بررسی‌کننده‌ی قرض‌گرفتن‌ها (borrow checker) بهمون دیکته کرده، و خیلی مهمه که بفهمیم چرا. اون نسخه‌ی خیلی "بدیهی و مشخص" — ینی اونی که توش کلاً یه دونه `match` رویِ `('@')raw.split_once` می‌زنیم و بازویِ موفقیت‌آمیزش همونجا خروجیِ `Ok(EmailAddress(raw))` برمی‌گردونه — اصلاً کامپایل نمی‌شه: متد `split_once` برش‌هایِ (slices) `&str`ای برمی‌گردونه که دارن از `raw` *قرض می‌گیرن*، و اون متغیر اصلی تو بلوکِ `match` همون قرض رو تو تمامِ طولِ بلوک `match` زنده نگه می‌داره، و تو هرگز نمی‌تونی متغیر `raw` رو تو زمانی که هنوز قرض گرفته شده، جابه‌جا و انتقال (move) بدی (خطای E0505). بنابراین ما اون پروسه رو به دو فاز می‌شکنیم: اول اون مقادیر قرضی رو بررسی می‌کنیم و تقلیلش می‌دیم به یه مقدار ساده‌ی `bool` (با استفاده از ماکرویِ `!matches` به اضافه‌یِ یه محافظِ تطبیق (guard) — همون ویژگی‌های تطبیق الگو از درسِ ۰۸.۱ که اینجا دارن ارزششون رو نشون می‌دن)، و در مرحله‌ی دوم، وقتی تمام اون قرض‌گرفتن‌ها (borrows) از بین رفتن، تازه متغیر `raw` رو به صورت کامل منتقل (move) می‌کنیم تو دلِ اون سمتی از `Result` که بهش تعلق داره. 
اون قسمتی که رشته‌ی ردشده (rejected string) رو قرار می‌دیم داخلِ `InvalidEmail(raw)` واسمون مطلقاً هیچ هزینه‌ای نداره (چون به هر حال مالکش بودیم) اما باعث می‌شه فراخواننده هروقت خواست اونو تو لاگ‌ها ثبت کنه، از دردسرِ ساختن یه کپیِ دوباره (clone) از روی اون متغیر نجات پیدا کنه — این دقیقاً همون توصیه‌ی طراحی‌ای (design note) هست که تو فایل README بهش اشاره شد و اینجا به صورت عملی و ملموس داره پیاده می‌شه. خود اعتبارسنجی هم از قصد خیلی خیلی ساده‌لوحانه در نظر گرفته شده: متنی مثل `a@b` راحت پاس می‌شه. این انتخابِ صادقانه‌ایه واسه کُدی که تو فضای آموزشی نوشته می‌شه — چون سیستمِ واقعی واسه اعتبارسنجی ایمیل پر از قوانینیه (RFC) که مثل یه مرداب می‌مونه و گیرت می‌ندازه، و تو واقعیت تنها و تنها چکی که می‌تونه اثبات کنه یه ایمیل وجود داره، اینه که بهش "یه ایمیل تایید بفرستی".

```rust
pub fn saturating_narrow(value: u64) -> u32 {
    value.try_into().unwrap_or(u32::MAX)
}
```

این خطِ تک‌دستوری (one-liner) دقیقاً همون دستمزد و جایزه‌ایه که به خاطر پیاده‌سازیِ `TryFrom<u64> for u32` توسط کتابخونه‌ی استاندارد بهمون داده شده: این نوع تبدیلِ (cast) خطاپذیر از همون اولش تو قالبِ یه `Result` به ما داده می‌شه، بنابراین تصمیم‌گیری در مورد *سیاستِ برخورد باهاش (policy)*، خیلی راحت با انتخابِ یکی از ترکیب‌کننده‌ها (combinator) انجام می‌شه. عملگرِ `?` اونو به لایه‌ی بالایی پاس می‌ده، عملگرِ `(...)unwrap_or` اونو محدود می‌کنه تا از سقفش بالاتر نره (clamps)، و متدِ `unwrap` باعث کرش (crash) می‌شه — هرکدومشون تو یه قالب مجزا، و کاملاً شفاف و صریح. 
اینو با عبارتِ `value as u32` مقایسه کن، که خیلی زیرپوستی از همون اول سیاستِ *بریدنِ بی‌صدا و خاموشِ اضافه‌ها (silent-truncation)* رو تو دل خودش رمزگذاری کرده، اونم بدون اینکه اصلاً شبیه به یه انتخاب یا تصمیم‌گیری باشه (`u64::MAX as u32` می‌شه `4294967295`… اما `u32::MAX as u64 + 1) as u32)` کلاً می‌شه `0`).
البته از نسخه‌ی 1.79 زبان Rust به بعد، متدی به اسمِ `u32::try_from(value).unwrap_or(u32::MAX)` هم دقیقاً با نامِ "saturating cast" به صورت توکار (built-in) در دسترس قرار گرفته (که بعضی‌ها تو پروژه‌هاشون با نصبِ کریت‌هایِ `num` یا نوشتنِ دستی با تابعِ `min` بهش می‌رسیدن) — اما فرمِ `(...)try_into().unwrap_or` دقیقاً همون الگویِ استاندارد و رایجیه که تو طبیعت کدهای برنامه‌نویس‌ها باهاش روبه‌رو می‌شی، و دقیقاً همون نسخه‌ایه که برای تمام جفت‌هایی که تو عملِ تبدیل، فضای ذخیره‌سازیشون کوچیک‌تر می‌شه (narrowing) هم عمومیت داره و کار می‌کنه.
