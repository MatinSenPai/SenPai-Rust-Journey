# ۰۸.۱ — مبحث Pattern matching (تطبیق الگو) به صورت عمیق

از فاز ۱ به بعد، تو مدام در حال نوشتنِ `match` بودی، اما تا الان فقط تو همون سطح ابتداییش: گونه (variant) رو پیدا کن، فیلدهاش رو اسیر کن، یه حالتِ همه‌گیر با `_` هم تهش بذار. ویژگیِ `match`/`case` که تو پایتون 3.10 اضافه شد، بخش زیادی از طراحیش رو از زبون‌هایی مثل Rust الگوبرداری کرده بود، پس اگه از ویژگیِ تطبیق الگوی ساختاری (structural pattern matching) تو پایتون استفاده کرده باشی، تقریباً نصفِ این درس برات خیلی آشنا به نظر میاد — اون نصفه‌ی دیگه‌اش دقیقاً همونجاییه که زبان Rust یه قدم جلوتر می‌ره، چون کامپایلرش *تضمین می‌کنه (proves)* که تطبیق‌های تو جامع‌ومانع (exhaustive) هستن، نه اینکه صرفاً امید داشته باشه که یادت مونده باشه یه `:case _` تهش بنویسی.

مدلی که اینجا برای مثال‌هامون استفاده می‌کنیم: یه ساختار از نوعِ enum به اسم `LogEvent` برای لاگ‌های یه وب‌سرویس — که شامل درخواست‌ها (requests)، پیام‌های لاگ، و ضربان‌های قلبِ سرور (heartbeats) می‌شه.

## محافظ‌های تطبیق (Match guards)

یه گارد (محافظ) میاد یه شرطِ منطقیِ (boolean) دلخواه رو با استفاده از پیچ‌ومهره، به انتهای یکی از بازوها (arm) وصل می‌کنه — و به دردِ شروطی می‌خوره که با الگوهایِ (patterns) خالی نمی‌شه بیانشون کرد، مثل انجام دادن مقایسه‌ها:

```rust
match event {
    LogEvent::Request { status, path, .. } if *status >= 500 => alert(path),
    _ => {}
}
```

پایتون هم دقیقاً همینو داره (`:case Request(status=s) if s >= 500`). اما تو زبان Rust یه نکته‌ی خیلی مهم وجود داره: **کامپایلر برای بررسی جامع‌بودنِ الگوها (exhaustiveness)، گاردها رو کاملاً نادیده می‌گیره.** کدی مثل `match x { n if n >= 0 => .., n if n < 0 => .. }` اصلاً کامپایل نمی‌شه، با وجود اینکه این دو تا گارد کاملاً مشخصه که همه‌چیز رو پوشش می‌دن — چون کامپایلر نمی‌تونه عبارات و شروط بولینِ دلخواه رو تحلیل و استدلال کنه، پس تو همچنان به یه بازویِ بی‌محافظ و عمومی نیاز داری.

## الگوهایِ "یا" (Or-patterns) و متغیرگذاری با `@`

علامتِ `|` اجازه می‌ده یه بازوی مشخص رو برای تطبیق دادنِ چند تا الگوی مختلف استفاده کنی؛ علامتِ `@` بهت اجازه می‌ده که *همزمان* هم الگو رو تست کنی و هم مقدارِ تطبیق‌داده‌شده رو تو یه متغیر *اسیر و ذخیره (keep)* کنی:

```rust
match status {
    301 | 302 | 307 | 308 => "redirect".to_string(),
    n @ 400..=499 => format!("client error ({n})"),
    ...
}
```

اگه `@` وجود نداشت باید بین این دو تا انتخاب می‌کردی: نوشتنِ `... => 400..=499` که الگو رو تطبیق می‌ده اما کد رو گم می‌کنه و کلاً بهت نمی‌ده، یا نوشتن یه `... => n` ساده که مقدار رو ذخیره می‌کنه اما با همه‌چیز مچ می‌شه (catch-all). اما `400..=499 @ n` هر دو کار رو برات می‌کنه. عبارت `:case 400 | 401 | 402` تو پایتون هم دقیقاً الگوهای "یا" رو داره، اما اونجا نه الگوهایِ بازه‌ای (ranges) داری و نه `@` (استفاده از کلمه‌ی `as` برای اسیر کردن تو پایتون شبیهشه، اما پایتون اصلاً اجازه نمی‌ده روی اعداد صحیح یه محدوده‌ی بازه‌ای (range-match) رو تطبیق بدی). دو تا قانون هست که ارزش حفظ کردن رو داره: بازوها از بالا به پایین تست می‌شن (پس اگه یه کد دقیق (مثل `200`) اولویت داره، اون رو بالاتر از محدوده‌ی `299..=200` قرار بده)، و قانون دوم اینکه هرکدوم از بخش‌های یه الگویِ "یا" (or-pattern) باید حتماً مقادیر اسیرشده رو با نام‌های یکسان و از یک نوعِ مشخص برگردونن — عبارت `(Ok(n) | Err(n` فقط تو صورتی مجازه که هر دو تا `n` نوع (type) یکسانی داشته باشن.

## استخراج تودرتو (Nested destructuring)

الگوها می‌تونن تا هر عمقی که دوست داری تودرتو (nest) بشن. برای تطبیق دادن با «یه `Message` که شدتِ خطاش (severity) از نوعِ `Error` باشه»، تو نمیای `severity` رو بریزی تو یه متغیر و بعد با چیزی مقایسه‌اش کنی — بلکه اون گونه (variant) موردنظرت رو *داخلِ خودِ* الگوی ساختاری (struct pattern) قرار میدی:

```rust
LogEvent::Message { severity: Severity::Error, text } => format!("error: {text}"),
```

عبارت `severity: Severity::Error` خودش یه الگو و زیرمجموعه‌ی الگوی اصلیه (sub-pattern)، نه یه مقداردهی (assignment) — اینو اینطوری بخون: «فیلدِ `severity` هم باید خودش با گونه‌یِ `Severity::Error` مچ (match) باشه». این روش تو هر سطحی از تودرتویی تو structها، enumها، توپل‌ها و ارجاع‌ها (references) کار می‌کنه، و این دقیقاً همون چیزیه که اکثر آدم‌ها بعد از اینکه مباحث ابتداییِ `match` رو یاد می‌گیرن، به شدت ازش کمتر از چیزی که باید، استفاده می‌کنن.

## الگوهای بُرش‌ها (Slice patterns)

الگوها رو می‌شه بر اساس شکلِ ظاهری‌شون، با بُرش‌ها (slices) و آرایه‌ها تطبیق داد:

```rust
match samples {
    [] => "no samples".to_string(),
    [only] => format!("1 sample: {only}ms"),
    [first, .., last] => format!("..."),
}
```

علامت `..` یعنی «هر تعداد عنصری که اصلاً برام مهم نیستن»، و اگه لازم بود وسطشو داشته باشی، می‌تونی با `.. @ rest` بهش اسم بدی. کامپایلر جامع‌بودنِ الگو (exhaustiveness) رو بر اساسِ طول (length) چک می‌کنه: حالتِ `[]`، `[x]` و `[y ,.. ,x]` به صورت اثبات‌پذیری، تمامِ حالت‌های ممکن با طول ۰، ۱ و +۲ رو پوشش می‌دن — در صورتی که اگه می‌خواستی از یه زنجیره‌یِ `if/else if` با `()len.` و ایندکس‌گذاری (indexing) استفاده کنی، هیچ‌وقت هیچ اثباتِ استاتیکِ اینطوری‌ای رو از سمت کامپایلر نمی‌گرفتی (و تازه اگه تو استفاده از یه ایندکس اشتباه کنی، کدت تو زمانِ اجرا کرش (panic) می‌کنه). این دقیقاً همون معادلِ `:[rest* ,first] match` و باز کردنِ متغیرهای قابل‌پیمایش (iterable unpacking) تو پایتونه، منتهی اینجا کامپایلر با چک کردنِ کد ایمنیش رو تضمین می‌کنه.

## حالت‌های تخصیص (Binding modes) (و اون کلمه‌ی `ref`ای که به ندرت قرار بنویسیش)

فرض کن داری یه `LogEvent&` رو با یه الگو مچ می‌کنی و می‌نویسی `} .. ,LogEvent::Request { method` — به نظرت متغیرِ `method` الان چه نوعیه (type)؟ نوعش `String&` هست، *نه* `String`. وقتی چیزی که داری مچ می‌کنی (scrutinee) خودش یه ارجاعِ قرضی (reference) باشه، زبان Rust به طور خودکار به جای اینکه سعی کنه فیلدها رو از داخل داده‌ی قرضی بکشه بیرون (move کنه)، اونا رو هم به عنوان ارجاع در نظر می‌گیره و قرض می‌گیره. به این رفتار می‌گن "match ergonomics" یا همون حالت‌های تخصیص پیش‌فرض (default binding modes)، و دقیقاً به خاطر همینه که تو کدهای مدرنِ Rust، دیگه تقریباً هیچ‌وقت اون فرمِ قدیمیِ صریح رو به شکلِ `} .. ,ref method ,LogEvent::Request {` نمی‌بینی. کلمه‌ی `ref` فقط واسه یه حالتِ به شدت نادر زنده مونده: وقتایی که داری روی یه داده‌ی *دارایِ مالکیت (owned)* عملیات `match` انجام می‌دی اما می‌خوای فقط و فقط یکی از فیلدهاشو (واسه جلوگیری از منتقل یا move شدنش) قرض بگیری. اگه قرار باشه فقط یه چیز از این بخش یادت بمونه اون اینه: **استفاده از `match` روی متغیری که با `&` قرض گرفته شده، خروجی‌ها و فیلدهای متصل‌شده (bindings) رو هم به صورتِ رایگان با `&` بهت میده**، و دقیقاً به همین دلیله که تو کد پایین و تو تابعِ `method_of`، قبل از اینکه خروجی رو برگردونه نیازه که `()as_str.` رو صدا بزنه.

## وظیفه‌ی تو

چهار تا تابع رو تو فایل `src/lib.rs` پیاده‌سازی کن — هر کدوم از این توابع مجبورت می‌کنن که از یکی از این ویژگی‌هایی که گفتیم استفاده کنی:

- تابع `describe_status` — الگوهای "یا" (or-patterns)، الگوهایِ بازه‌ای (range patterns)، اسیر کردن با `@`، و در نظر گرفتنِ ترتیبِ بازوها.
- تابع `noteworthy` — محافظ‌های تطبیق (match guards) + استخراجِ تودرتوی (nested destructuring) یه enum از داخلِ یه struct.
- تابع `method_of` — حالت‌های تخصیص (Binding modes): یعنی همونجایی که متغیر `method` به عنوانِ یه `String&` تحویل گرفته می‌شه.
- تابع `summarize_samples` — الگوهای بُرش‌ها (slice patterns)، با پوششِ جامع‌ومانع از طول‌های ۰، ۱ و +۲.

تو کامنت‌های مستندات دقیقاً همون رشته‌های متنی‌ای که تست‌ها ازت انتظار دارن، مشخص شده.
