# راه‌حل

```rust
pub fn describe_status(status: u16) -> String {
    match status {
        200 => "OK".to_string(),
        n @ 200..=299 => format!("success ({n})"),
        301 | 302 | 307 | 308 => "redirect".to_string(),
        n @ 400..=499 => format!("client error ({n})"),
        n @ 500..=599 => format!("server error ({n})"),
        other => format!("unrecognized status {other}"),
    }
}
```

اینجا دو تا نکته، دقیقاً بارِ اصلیِ کار رو به دوش می‌کشن. اول از همه، **ترتیبِ بازوها (arm order)**: الگوهای `200` و `299..=200` با هم هم‌پوشانی دارن، و بازوهای `match` هم همیشه از بالا به پایین به نوبت چک می‌شن، بنابراین اون عدد ثابتی که دقیق و تک‌مقداریه باید حتماً بالاتر نوشته بشه — اگه جای این دو تا رو با هم عوض کنی فراخوانیِ `(describe_status(200` بهت خروجیِ `"success (200)"` رو می‌ده که باعث fail شدن تستِ اولت می‌شه. کامپایلر سر این قضیه که هم‌پوشانی دارن غر نمی‌زنه (چون تو هر دو حالت هنوز هم هر دو بازو قابل دسترسی (reachable) هستن)، پس مدیریتِ این قضیه کلاً پایِ خودته.
نکته‌ی دوم، استفاده از علامت اسیرکردنِ `@`: بازوی `... => 499..=400` به تنهایی می‌تونست این مقادیر رو مچ کنه اما دیگه به خود متغیرِ کد دسترسی نداشتی و از دستش می‌دادی، و اگه هم به جاش یه دونه متغیر خالی می‌ذاشتی (مثلاً `... => n`)، اون وقت کدت رو نگه می‌داشت اما با *همه‌چیز* مچ می‌شد. در نتیجه فقط عبارتِ `499..=400 @ n` هست که بهت همزمان هر دو ویژگی رو تو یه الگوی واحد می‌ده: یعنی هم "باید تو این محدوده باشی" و هم "اینم مقدار واقعیِ اون کد".

```rust
LogEvent::Message { severity: Severity::Error, text } => Some(format!("error: {text}")),
LogEvent::Message { severity: Severity::Warning, text } if text.contains("disk") => ...
```

تو تابعِ `noteworthy`، بازوی مربوط به `Error` **به هیچ گارد و محافظی نیاز نداره** — شرطِ "severity باید Error باشه" یه شرط ساختاریه (structural)، پس جاش دقیقاً همون وسطِ خودِ الگوئه (`severity: Severity::Error` یه زیرالگو (sub-pattern) حساب می‌شه نه یه عملیاتِ انتساب یا مقداردهی (assignment)). اما بازوی مربوط به `Warning` هم به بخشِ ساختاریِ داخلِ الگو نیاز داره، و هم به بررسیِ `("text.contains("disk` — که خب این شرط با هیچ الگویی قابل بیان نیست — پس مجبوره که تو یه گارد قرار بگیره. مرزی که باید دقیقاً تو ذهنت حکش کنی همینه: چیزایی که با شکل و ظاهر (shapes) سر و کار دارن جاشون تو الگوهاست، و شروطِ بولینِ دلبخواهی جاشون تو گاردها.
یه نکته‌ی دیگه که باید بهش توجه کنی اینه: `500 =< status* if`: ازونجایی که ما با یه `LogEvent&` مچ شدیم، اون قانون حالتِ تخصیصِ پیش‌فرض (default binding modes) باعث شد که متغیر `status` به صورت `u16&` قرض گرفته بشه، در نتیجه برای اینکه بتونی با یه عدد ثابت (literal) مقایسه‌اش کنی حتماً باید از نشان‌زدایی (`*`) استفاده کنی (یا اینکه بنویسی `500& =<` که اینم جواب میده ولی خوندنش تو ذوق می‌زنه). نوشتنِ همون بازویِ نهاییِ `None => _` کاملاً اجباریه، حتی با وجود اینکه محافظ‌های ما "خیلی واضح و بدیهی" دارن کل چیزی که می‌خواستیم رو پوشش می‌دن — چون کامپایلر موقع اثباتِ جامع‌ومانع‌بودنِ (exhaustiveness) الگوها اصلاً به گاردها نگاه نمی‌کنه، پس بدون یه بازوی عمومیِ (catch-all) بی‌محافظ، این دستورِ `match` هرگز کامپایل نمی‌شه.

```rust
pub fn method_of(event: &LogEvent) -> Option<&str> {
    match event {
        LogEvent::Request { method, .. } => Some(method.as_str()),
        _ => None,
    }
}
```

کلِ دلیل وجود این تابع، فهمیدنِ یک دونه تایپِ خاصه: متغیر `method` از جنس `String&` هستش، و نه `String`، چون انجام دادنِ یه `match` که از طریق یه ارجاع (reference) کار می‌کنه، خروجی‌ها رو هم به صورت ارجاع می‌ده ("match ergonomics"). اگه متغیر قرار بود با ارزش خودِ مقدارش (by value) تو این بازو تخصیص داده بشه، اونوقت الگو تلاش می‌کرد که فیلدِ `method` رو از تو دلِ دیتایی بکِشه بیرون و منتقل (move) کنه که خودش هم کلاً داشت اون رو قرض می‌گرفت — که یعنی خطای کامپایل. تو نسخه‌های قبل از 2018 زبان Rust، تو مجبور بودی واسه رسیدن به این دسترسیِ ساده کلمه‌ی `ref method` رو صریحاً تو الگو بنویسی؛ اما امروزه این فرآیند کاملاً خودکاره، و استفاده از `ref` فقط واسه یه حالت نادر و کم‌پیدا نگه داشته شده: وقتایی که مقدارتِ دارای مالکیته (owned-scrutinee) اما تو می‌خوای فقط و فقط یه فیلد ازش رو قرض بگیری.
عبارتِ `(Some(method` خروجیِ `<Option<&String` رو برمی‌گردوند، پس اضافه کردنِ `()as_str.` اینو پل می‌زنه به همون خروجیِ `str&`ای که امضای تابع (signature) قول داده بود که برگردونه (برگردوندن `str&` کلاً یه APIِ منعطف‌تر محسوب می‌شه — اینطوری فراخواننده‌ها، چه یه `String` دستشون باشه، چه یه متنِ ثابت (literal)، و چه یه برش (slice)، همه‌شون به راحتی می‌تونن باهاش مقایسه‌هاشون رو انجام بدن).

```rust
match samples {
    [] => "no samples".to_string(),
    [only] => format!("1 sample: {only}ms"),
    [first, .., last] => format!("{} samples, first {first}ms, last {last}ms", samples.len()),
}
```

بررسیِ جامعیت برای الگوهای بُرش‌ها (Slice patterns) *از طریق اندازه‌گیری طولشون (by length)* انجام می‌شه: بازویِ `[]` حالت طولِ ۰ رو پوشش می‌ده، `[only]` طول ۱ رو، و `[last ,.. ,first]` حالتِ ۲ و بزرگتر از اون رو در بر می‌گیره (این بازو حداقل به یه عضو واسه `first` و یدونه واسه `last` نیاز داره، و اون علامت `..` همه‌ی چیزایِ بینشونو جذب می‌کنه — حتی اگه اون فضای خالی وسط کلاً صفر عنصر داشته باشه، که به همون خاطر هم فراخوانی با دقیقاً دو عنصر مثلِ `([3 ,7]&)summarize_samples` جواب میده).
اگه بازویِ `[only]` رو پاک کنی، کامپایلر همونجا یقه تو می‌گیره و بهت می‌گه که الگویِ `[_]&` پوشش داده نشده — در حالی که اگه همین کار رو با استفاده از بررسیِ طول (`()len.`) تو یه زنجیره‌یِ `else if / else / if` و خوندن از طریق ایندکس `[samples[0` انجام می‌دادی، کامپایلر با وجود اینکه کدت دقیقاً همون شکاف و نقص (gap) رو داشت بازم به راحتی می‌ذاشت کامپایل بشه و تازه تو زمان اجرا کرش (panic) می‌کرد (یا بدتر، تو سکوت مقدار اشتباه رو گزارش می‌داد). اون اثباتِ محکمِ زمانِ کامپایل (compile-time proof)، دقیقاً همون دلیلِ کاربردی‌ایه که باعث می‌شه تو دنیای واقعی ما استفاده از الگوهای بُرش رو به بررسی‌های دستی با `()len.` ترجیح بدیم.
