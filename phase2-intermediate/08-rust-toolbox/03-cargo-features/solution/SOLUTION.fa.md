# راه‌حل

```rust
pub fn build_report(label: &str, samples: &[i64]) -> Option<Report> {
    let min = samples.iter().copied().min()?;
    let max = samples.iter().copied().max()?;
    let sum: i64 = samples.iter().sum();

    Some(Report {
        label: label.to_string(),
        count: samples.len(),
        mean: sum as f64 / samples.len() as f64,
        min,
        max,
    })
}
```

هیچ‌کجا به‌طور صریح از چیزی مثلِ بررسی با متدِ `is_empty` استفاده نکردیم — متدِ `Iterator::min` تو خروجی مقدارِ `<Option<i64` برمی‌گردونه (و اگه روی یه پیمایشگرِ (iterator) خالی اعمال بشه مقدار `None` می‌ده)، و عملگر `?` روی یه `Option` وقتی داخل یه تابعی باشیم که خودش `Option` برمی‌گردونه، باعث می‌شه به محض برخورد به `None` همونجا تابع کلاً همون `None` رو برگردونه (early-return). پس تا زمانی که اصلاً اجرای ما برسه به خطِ تقسیم کردن (division)، متدِ `?()min` خودش اثبات کرده که این بُرش (slice) خالی نبوده، پس مقدارِ `()samples.len` هم محاله که صفر باشه. یه نکته‌ی خیلی ظریف تو ترتیبِ خطوطِ این کد هست: این کد فقط و فقط به این دلیل درست کار می‌کنه که اون چکِ مربوط به خالی‌بودن (emptiness signal) *زودتر از همه* تو کد اومده؛ اگه محاسبه‌ی `mean` رو می‌بردیم قبل از اون خطوطی که `?` داشتن، و اگه دست‌برقضا یه بُرش خالی بهمون می‌دادن، اونجا کُدمون سعی می‌کرد صفر رو به صفر تقسیم کنه (البته خب — در واقعیت چون تقسیم اعشاریِ float division هست، خروجیش می‌شد `NaN`، که می‌شه گفت حتی کثیف‌تر و بدتر هم هست: چون برنامه کرش نمی‌کرد، فقط یه مقدارِ فاسد و مسموم شده رو تو محاسبات پخش می‌کرد).

```rust
#[cfg(feature = "json-export")]
pub fn to_json(report: &Report) -> String {
    serde_json::to_string(report).expect("a plain struct of strings and numbers cannot fail to serialize")
}
```

چرا اینجا از متد `.expect` استفاده کردیم به جای اینکه بخوایم نوع بازگشتی رو `<serde_json::Result<String` در نظر بگیریم؟ خب متد `to_string` واقعاً می‌تونه به شکلِ کاملاً موجه و قانونی با خطا مواجه بشه — اما فقط و فقط برای اون دسته‌ای از نوع‌ها که پیاده‌سازیِ `Serialize`شون امکانِ خطا داشته باشه (مثل مَپ‌هایی که کلیدهاشون متنی نیست، یا پیاده‌سازی‌های سفارشیِ خودت که توشون ممکنه مشکلی پیش بیاد و کار متوقف (bail) بشه). ساختارِ `Report` کلاً شاملِ پنج تا فیلدِ ساده‌ست، پس تو عمل و در عالمِ واقع رسیدن به شکست واسش غیرممکنه (unreachable)، و اینکه بخوای تک‌تکِ فراخواننده‌های (callers) این تابع رو مجبور کنی یه `Result`ی رو هندل کنن که می‌دونیم هرگز قرار نیست رخ بده، فقط تولیدِ یه نویز (noise) اضافی و بی‌مورده. پیغامی هم که داخلِ `.expect` نوشته شده، منطقِ پشتِ این تصمیم رو دقیقاً تو همون نقطه‌ای که ممکنه کرش کنه مستند کرده. (حالا اگه یه زمانی تو آینده، یه فیلدی به `Report` اضافه شد که عملیاتِ `Serialize`ِ اون خطاپذیر و شکننده بود، این دقیقاً همون خطیه که باید برگردی و اصلاحش کنی — و پیغامِ `expect` هم کلاً واسه همچین هدفی به وجود اومده.)

## سیم‌کشیِ فیچرها، که درس اصلیِ این قسمت هم همینه

- فایل `Cargo.toml`: وابستگی‌های `serde`/`serde_json` با گزینه‌ی `optional = true` علامت خوردن، و شرطِ `["json-export = ["dep:serde", "dep:serde_json` تنها چیزیه که اونا رو روشن (turn on) می‌کنه. لیستِ خالیِ `[] = default` هم باعث می‌شه همون کریتِ پایه کاملاً بدون هیچ وابستگی‌ای (dependency-free) بمونه.
- خودِ ساختار از صفتِ `[(cfg_attr(feature = "json-export", derive(serde::Serialize]#` استفاده می‌کنه — یعنی یه *صفتِ (attribute)* شرطی، که در نتیجه ساختارِ `Report` چه با فیچر چه بی‌فیچر تو بیلد (build) حضور خواهد داشت. اگه از یه `[cfg]#`ِ ساده روی ساختار استفاده می‌کردی، اونوقت کلاً از بیلدِ پیش‌فرضِ برنامه حذف می‌شد و در نتیجه تابع `build_report` رو هم می‌شکوند و با ارور روبه‌رو می‌کرد.
- تابع `to_json` از همون صفتِ ساده‌ی `[("cfg(feature = "json-export]#` استفاده می‌کنه — کل این تابع اگه فیچری در کار نباشه کلاً نباید وجود خارجی داشته باشه، و با حذف شدن این تابع، بیلدِ پیش‌فرضمون هم دیگه هرگز هیچ ارجاعی به `serde_json` نمی‌ده، که دقیقاً همون دلیلیه که اصلاً بهمون این اجازه رو می‌ده تا بتونیم این وابستگی رو اختیاری (optional) کنیم.
- تست‌های مربوط به JSON کلاً پشتِ یه حصار به شکلِ `[("cfg(all(test, feature = "json-export]#` قایم شدن تا وقتی کاربر دستورِ پیش‌فرضِ `cargo test` رو زد، سیستم حتی تلاش نکنه که (و با خطا متوقف بشه تا) اینا رو کامپایل کنه.

برای اینکه از رویِ مانیفستِ داخل دایرکتوریِ `solution/` سلامتِ هر دو دنیا رو بررسی کنی، اینا رو بزن:

```bash
cargo test --manifest-path solution/Cargo.toml
cargo test --manifest-path solution/Cargo.toml --features json-export
```

اگه تو فقط و فقط همون دستور اول رو همیشه ران کنی، تابع `to_json` و تست‌هاش اصلاً رنگِ کامپایل شدن رو هم نمی‌بینن — سبز و پاس شدنِ بیلدِ پیش‌فرض (default build)، مطلقاً هیچ‌چیزی در مورد سلامتِ بیلد با فیچرهای روشن (feature build) بهت نمی‌گه. کریت‌هایِ واقعی و بزرگ تو پروسه‌های CIِ خودشون اینو به صورت اتوماتیک انجام می‌دن، به این شکل که برای هر کدوم از ترکیب‌های پشتیبانی‌شده از فیچرها یه جاب (job) تعریف می‌کنن (یا اگه تعداد این ترکیب‌ها زیاد بشه و ضرب‌دری بره بالا، از دستور `cargo hack --each-feature` استفاده می‌کنن)؛ اون انضباطی که می‌گه "تک‌تک ترکیب‌هایی که ادعا کردی رو ساپورت می‌کنی باید حتماً سبز و سالم بمونن"، در واقع همون قانونِ جمع‌پذیری (additivity) که تو فایلِ README گفته شده بود هست، که حالا تو واقعیت و عمل داره پیاده می‌شه.
