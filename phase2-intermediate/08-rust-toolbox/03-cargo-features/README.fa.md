# ۰۸.۳ — ویژگی‌ها و Featureهای Cargo

فایلِ `Cargo.toml` هر کریتِ (crate) واقعی تو دنیای بیرون رو که باز کنی، به احتمال خیلی زیاد یه جدول `[features]` توش می‌بینی: کریتِ `tokio` نزدیک به ۳۰ تا فیچر داره، `serde` فیچر `derive` رو داره، و حتی تو همین مخزنی (repo) که داری روش کار می‌کنی، خودِ فایلِ مانیفستِ ورک‌اسپیس (workspace manifest) یه سری لیستِ فیچر رو روی نصف وابستگی‌هاش روشن (enable) کرده. فیچرها در واقع **کلیدهای اختیاریِ (opt-in) زمانِ کامپایل** برای یه کریت هستن: توابع اضافی، پیاده‌سازیِ traitهای اضافی، و وابستگی‌های اضافی‌ای (extra dependencies) که فقط تو صورتی وارد باینریِ نهایی می‌شن که اون برنامه‌نویسِ مصرف‌کننده (consumer) خودش ازت خواسته باشه.

نزدیک‌ترین چیزی که پایتون به این داره همون دستور `[pip install requests[socks` هست — یه چیزِ "اضافی" که وابستگی‌های اختیاری رو نصب می‌کنه. اما این قابلیت تو پایتون فقط میاد چیزی که باید *نصب بشه* رو تغییر می‌ده؛ اون مسیرهای اجرای کُد همچنان باید تو زمان اجرا (runtime) با چیزایی مثل `try: import socks` انتخاب و فیلتر بشن. اما تو Cargo یه فیچر، چیزی که قراره **کامپایل بشه** رو تغییر می‌ده: کدی که پشت یه فیچرِ خاموش‌شده قرار داره نه اینکه بخواد با سرعت کمتری ران بشه یا یه نسخه‌ی خالی (stub) جاش بیاد، کلاً و مطلقاً *وجود خارجی نخواهد داشت* و وارد خروجی نمی‌شه. هیچ معادلی برای Django-settings هم نداره — چیزی مثل `INSTALLED_APPS` اپلیکیشن‌ها رو موقع بالا اومدن پراسس (process startup) قطع و وصل می‌کنه، در حالی که فیچرها این کار رو قبل از اینکه کامپایلر اصلاً ران بشه انجام می‌دن.

## تعریفِ فیچرها و وابستگی‌های اختیاری

```toml
[features]
default = []
json-export = ["dep:serde", "dep:serde_json"]

[dependencies]
serde = { workspace = true, optional = true }
serde_json = { workspace = true, optional = true }
```

اینجا با سه تا تیکه کار داریم. عبارت `optional = true` یعنی «این وابستگی رو کامپایل نکن مگه اینکه یه چیزی روشنش کنه.» وجودِ عبارت `dep:serde` تو یه لیست از یه فیچر یعنی «با روشن کردنِ فیچرِ `json-export`، وابستگیِ `serde` هم روشن می‌شه.» و `default` هم در واقع همون مجموعه‌فیچرهاییه که وقتی کاربرا هیچی نمی‌گن به دستشون می‌رسه — که واسه ما کاملاً خالیه، پس اون کریت پایه‌ایمون کاملاً بدون وابستگی باقی می‌مونه. (ضمن اینکه یه فیچر می‌تونه *یه فیچرِ دیگه* رو هم فعال کنه، چه تو همین کریت باشه چه تو یه وابستگی دیگه: مثل استایلِ `"derive = ["serde/derive`. مال ما فقط به همون `:dep` نیاز داره.)

## قفل کردن و حذف کردنِ کدها: `[cfg]#` و `[cfg_attr]#`

```rust
#[cfg_attr(feature = "json-export", derive(serde::Serialize))]
pub struct Report { /* ... */ }

#[cfg(feature = "json-export")]
pub fn to_json(report: &Report) -> String { /* ... */ }
```

صفتِ `[(...)]cfg#` زمانی که فیچر خاموش باشه کلاً اون موجودیت (item) رو از کد حذف می‌کنه — یعنی اون تابع، بدنه‌ی تابع، و استفاده‌اش از `serde_json`، همگی خیلی قبل‌تر از اینکه به مرحله‌ی بررسیِ نوع‌ها (type checking) برسن از بین می‌رن. اما صفتِ `[(cfg_attr(cond, attr]#` نسخه‌ی شرطی برای *یه صفتِ (attribute) دیگه* است: «صفتِ `(derive(serde::Serialize` رو فقط زمانی اعمال کن که اون فیچر روشن باشه.» این دقیقاً همون چیزیه که به خودِ structِ `Report` اجازه می‌ده تو هر دو دنیا زنده بمونه — یعنی همون ساختار، با یا بدونِ پیاده‌سازیِ serde. تست‌ها هم دقیقاً با همین روش فیلتر و جدا (gate) می‌شن: تست‌های JSON تو این درس، داخلِ ماژولی قرار دارن که بالای سرش نوشته شده `[("cfg(all(test, feature = "json-export]#`، در نتیجه اون دستور `cargo test`ِ پیش‌فرض و معمولی اصلاً سراغ کامپایل کردنشون هم نمی‌ره.

## فیچرها باید خاصیت جمع‌پذیری (additive) داشته باشن (همون مفهومِ یکی‌سازی یا unification)

اگه کریتِ A به کریتِ تو (`you`) وابستگی (depend) داشته باشه در حالی که فیچرِ `json-export` رو روشن کرده، و همزمان کریتِ B هم به `you` وابستگی داشته باشه اما بدون اون فیچر، سیستمِ Cargo فقط **یک بار** کریت `you` رو کامپایل می‌کنه، اونم با **اجتماعِ (union)** تمامِ فیچرهای درخواست‌شده — ینی A و B تو اون بیلد (build) شریک می‌شن. این مفهومِ *یکی‌سازی (unification)* تو فیچرهاست، و دقیقاً یه قانون اساسی تو طراحی رو بهت تحمیل می‌کنه: روشن کردنِ یه فیچر فقط و فقط حق داره که سطحِ API رو **اضافه و بزرگتر** کنه، هیچ‌وقتِ هیچ‌وقت نباید رفتارِ کدهای موجود رو تغییر بده یا چیزی رو حذف کنه. یه فیچر به اسم `no-std-panic-handler` که بیاد یه چیزی رو از کد *حذف* کنه، باعث شکستنِ (break) کدِ هر کریتِ وابسته‌ای می‌شه که اصلاً همچین چیزی نخواسته بوده. نتیجه‌ی این قانون: کریتِ تو باید تو *تک‌تک* ترکیب‌های ممکنی که از فیچرها وجود داره (که خودت ادعا کردی پشتیبانیشون می‌کنی) با موفقیت بیلد بشه، تست‌هاش پاس بشن، و تو خروجیِ clippy تمیز بمونه — و این دقیقاً همون درخواستی و چالشیه که تو تأییدِ (verification) این درس ازت خواسته شده.

## دستوراتی که واقعاً تو دنیای بیرون تایپشون می‌کنی

```bash
cargo test -p p2-08-03-cargo-features                          # فیچر خاموش
cargo test -p p2-08-03-cargo-features --features json-export   # فیچر روشن
cargo clippy -p p2-08-03-cargo-features --all-targets -- -D warnings
cargo clippy -p p2-08-03-cargo-features --all-targets --features json-export -- -D warnings
```

(سوییچ‌های `all-features--` و `no-default-features--` هم وجود دارن؛ با توجه به اینکه لیستِ default ما خالی بود، کارکردشون کاملاً معادلِ همون دو خط اولِ بالاست.)

## وظیفه‌ی تو

یه کریتِ خیلی کوچیک برای گرفتن آمار (stats). تو فایل `src/lib.rs`:

- تابع `build_report` — که همیشه در دسترسه: گرفتنِ لیبل، تعداد، میانگین، کمترین و بیشترین مقدار از روی یه بُرش (slice) از نمونه‌ها؛ و در صورتی که بُرش خالی باشه `None` برمی‌گردونه. (استفاده از `Option` در کنارِ عملگر `?` روی خروجی‌هایِ `Iterator::min`/`max` باعث می‌شه این تابع به شکلِ دلنشینی کوتاه بشه.)
- تابع `to_json` — که فقط و فقط تحتِ فیچرِ `json-export` وجود داره: سریالایز (serialize) کردنِ یه `Report` به کمک `serde_json`. اون صفتِ derive از قبل با استفاده از `cfg_attr` سیم‌کشی شده؛ قبل از اینکه چیزی بنویسی اول یه نگاهی بهش بنداز.

مجموعه‌ی تست‌ها (test suite) رو **تو هر دو حالت** ران کن — کل نکته‌ی این درس اینه که هر دو دنیا باید سبز (پاس) باشن.
