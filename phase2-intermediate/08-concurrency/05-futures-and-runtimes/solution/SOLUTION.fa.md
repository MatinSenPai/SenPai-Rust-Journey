# راه‌حل

`Countdown::poll` همان انشعابِ دوگانه‌ای است که هر `Future`ِ دست‌سازِ این درس داشت — یا تمام شده، یا یک قدم نزدیک‌تر:

```rust
fn poll(mut self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<Self::Output> {
    if self.remaining == 0 {
        Poll::Ready(self.total_polls)
    } else {
        self.remaining -= 1;
        Poll::Pending
    }
}
```

خطِ `self.remaining -= 1` مستقیم از پشتِ همان `Pin<&mut Self>` می‌نویسد، بدونِ هیچ دردسرِ ویژه‌ای — `Countdown` هیچ ارجاعی به فیلدهایِ خودش نگه نمی‌دارد، پس Rust به‌طور خودکار صفتِ `Unpin` را بهش می‌دهد، و برایِ یک نوعِ `Unpin`، `Pin<&mut Self>` در عمل چیزی بیشتر از یک `&mut Self`ِ معمولی نیست. `mut` روی `self` هم واقعاً لازم است، نه تزئینی: نوشتن از پشتِ `DerefMut`ِ `Pin` به یک بایندِ تغییرپذیر از خودِ `Pin` نیاز دارد، نه فقط از چیزی که به آن اشاره می‌کند.

`block_on` همان اجراکننده‌ی همه‌کاره‌ای است که در «مفهوم» ساختیم، بدونِ هیچ تغییری:

```rust
pub fn block_on<F: Future>(future: F) -> F::Output {
    let mut future = Box::pin(future);
    let waker = Waker::noop();
    let mut cx = Context::from_waker(waker);
    loop {
        match future.as_mut().poll(&mut cx) {
            Poll::Ready(value) => return value,
            Poll::Pending => continue,
        }
    }
}
```

`Box::pin(future)` همان چیزی است که می‌گذارد این یک پارامترِ جنریکِ تنها — `F: Future`، بدونِ هیچ کراندِ `Unpin`ی — واقعاً کار کند. ماشینِ وضعیتِ یک `async fn`ِ واقعی همیشه `!Unpin` است (به «خطاهایی که خواهی دید» نگاه کن — `E0277` — تا دقیقاً ببینی اگر به‌جایش `Pin::new` را امتحان کنی چه اتفاقی می‌افتد)، پس یک `block_on` که فقط `Future`هایِ `Unpin` را قبول می‌کرد، برایِ `Countdown` کار می‌کرد ولی روی هر `async fn`ِ واقعی شکست می‌خورد. جا دادنِ future یک‌بار رویِ هیپ، پشتِ `Box::pin`، کلِ این سؤال را کنار می‌زند: از آن به بعد دیگر هرگز جابه‌جا نمی‌شود، پس همیشه — چه `Unpin` باشد چه نباشد — poll کردنش امن است. دقیقاً همین چیزی است که تستِ چهارم، `block_on_also_drives_a_real_async_fn`، دارد بررسی می‌کند — همان `block_on`، این‌بار در حالِ راندنِ یک `async fn`ِ معمولی تا آخر، بدونِ هیچ فرقی با راندنِ `Countdown`.

`Waker::noop()` یک `Waker` می‌دهد که موقعِ بیدار شدن مطلقاً هیچ کاری نمی‌کند — که اینجا دقیقاً به همین دلیل خوب است: این `block_on` هیچ‌وقت واقعاً برایِ یک بیدارشدن به خواب نمی‌رود؛ فقط می‌چرخد و بلافاصله دوباره poll می‌کند، صرفِ‌نظر از هرچه باشد — که برایِ Futureهایی مثلِ `Countdown`، که همیشه سرِ همان poll بعدی یک جوابِ واقعی آماده دارند، درست است (هرچند نه بهینه). یک اجراکننده‌ی واقعی یک `Waker`ِ واقعی پاس می‌دهد، سیم‌کشی‌شده به خودش، دقیقاً برایِ اینکه یک Futureی که واقعاً منتظرِ I/O است بتواند وقتی داده رسید متدِ `.wake()` را صدا بزند — همان سیگنالی که یک اجراکننده‌ی واقعی از آن می‌فهمد کِی ارزشِ دوباره poll کردن هست، به‌جایِ اینکه مثلِ این یکی مدام در یک حلقه‌ی مشغول بچرخد.
