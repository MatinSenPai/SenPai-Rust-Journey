# راه‌حل — ۲.۸.۳ کانال‌ها و پیام‌رسانی

```rust
pub fn sum_via_channel(nums: Vec<i32>) -> i32 {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        let total: i32 = nums.iter().sum();
        tx.send(total).unwrap();
    });
    rx.recv().unwrap()
}
```

یک ریسمان، یک پیام، و تمام. `nums` به داخلِ کلوژرِ spawn‌شده منتقل می‌شود (`move ||`)، همان کلوژر مجموعش را حساب می‌کند و یک‌بار می‌فرستد، و `rx.recv()` ریسمانِ صداکننده را متوقف می‌کند تا همان مقدار (یا یک قطع‌ارتباط) برسد. چون ریسمانِ spawn‌شده همیشه قبل از تمام‌شدنش حتماً می‌فرستد، اینجا `recv()` هرگز واقعاً حالتِ قطع‌شده را نمی‌بیند.

```rust
pub fn collect_from_workers(worker_count: usize, values_per_worker: usize) -> Vec<i32> {
    let (tx, rx) = mpsc::channel();
    let mut handles = Vec::new();

    for i in 0..worker_count {
        let tx = tx.clone();
        handles.push(thread::spawn(move || {
            let start = (i * values_per_worker) as i32;
            let end = start + values_per_worker as i32;
            for value in start..end {
                tx.send(value).unwrap();
            }
        }));
    }
    drop(tx); // without this, rx.iter() below would wait forever

    let mut collected: Vec<i32> = rx.iter().collect();
    for handle in handles {
        handle.join().unwrap();
    }

    collected.sort();
    collected
}
```

خطِ `drop(tx)` بلافاصله بعدِ حلقه‌ی spawn، دقیقاً همان خطی است که اگر کدت هَنگ کرد و گیر افتاد، به احتمالِ زیاد یادت رفته بنویسیش: `rx.iter()` (که کاملاً معادلِ `for v in rx` است) فقط وقتی متوقف می‌شود که *تک‌تکِ* `Sender`ها، شاملِ هر `.clone()`، پاک شده باشند. کپیِ هر کارگر از `tx`، همین که کلوژرِ آن کارگر تمام شود، خودکار پاک می‌شود — اما `tx`ِ *اصلی* که از رویش کپی گرفتی، هنوز در اسکوپِ بیرونی زنده است تا وقتی که خودت صریح `drop`ش کنی (یا به‌طورِ طبیعی از اسکوپش خارج شود، که اینجا آن‌قدر دیر است که دیگر فایده‌ای ندارد — چون فقط بعدِ همان `rx.iter().collect()`ای اتفاق می‌افتد که خودش منتظرِ همان `tx` مانده).

هر کارگر تک‌تکِ `values_per_worker` عدد را جداگانه می‌فرستد، نه یک مقدارِ خلاصه‌شده — دقیقاً همین است که پیمایشِ مستقیمِ `rx` را اینجا انتخابِ طبیعی می‌کند، نه صدازدنِ `.recv()` به تعدادِ ثابت: سمتِ جمع‌کننده لازم نیست از قبل بداند چند پیام قرار است برسد، فقط کافی است بداند کانال کِی خودش خبر می‌دهد که دیگر تمام شده.

هر دو حالتِ لبه‌ای — `worker_count == 0` و `values_per_worker == 0` — بدونِ هیچ کدِ اضافه‌ای درست از آب درمی‌آیند: با صفر کارگر، حلقه اصلاً اجرا نمی‌شود، `drop(tx)` تنها `Sender` را فوراً پاک می‌کند، و `rx.iter()` چیزی تحویل نمی‌دهد. با صفر مقدار به‌ازایِ هر کارگر، بازه‌ی هر کارگر خالی است (`start..start`)، پس هر کارگر هیچ‌چیز نمی‌فرستد و فوراً تمام می‌شود — همان نتیجه‌ی خالی.

## این درس واقعاً درباره‌ی چه بود

- **ارسال، مالکیت را منتقل می‌کند.** هیچ‌کدام از این دو تابع هرگز نیازی نداشتند `nums` یا اعدادِ در حالِ ارسال را به اشتراک بگذارند — هر مقدار در هر لحظه دقیقاً یک مالک دارد، اول فرستنده، بعد کانال، بعد گیرنده.
- **`Sender::clone()` همان چیزی است که «چندتولیدکننده» عملاً یعنی.** تابعِ `collect_from_workers` به‌ازایِ هر کارگر یک‌بار `tx` را کلون می‌کند؛ هر کپی همان یک `Receiver` را در `rx` تغذیه می‌کند.
- **پیمایشگرِ `Receiver` حسابِ «کِی باید متوقف شوم؟» را خودش برایت نگه می‌دارد** — ولی فقط وقتی که واقعاً تک‌تکِ `Sender`ها، شاملِ همان نسخه‌ی اصلی‌ای که از رویش کلون گرفتی، رفته باشند. دقیقاً همین جزئیات است که این تمرین واقعاً می‌سنجدش.
- **هیچ‌کدام از این دو تابع به `Mutex` نیاز نداشت.** این را با `count_matching_in_threads`ِ [۲.۸.۱](../../01-threads-mutex-arc/README.fa.md) مقایسه کن، که نیاز داشت هر ریسمان یک شمارنده‌ی مشترک و در حالِ تغییر را زنده آپدیت کند — این یعنی وضعیتِ مشترک، وظیفه‌ی `Mutex`. اینجا مقدارها فقط دارند از جاهای مختلف به یک‌جا منتقل می‌شوند، بدونِ هیچ‌چیزِ مشترکی در میانه — دقیقاً همان چیزی که یک کانال مستقیماً مدلش می‌کند.
