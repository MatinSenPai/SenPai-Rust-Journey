# ۰۷.۲ — کانال‌ها و پیام‌رسانی (Channels and message passing)

تو درس قبلی دیدی که نوعِ `<Arc<Mutex<T>>` میاد یه *وضعیت (state)* رو بین ریسمان‌ها به اشتراک می‌ذاره — ینی همه‌ی ریسمان‌ها دستشون رو دراز می‌کنن تو یه جعبه‌ی واحد و نوبتی باهاش کار می‌کنن. اما کانال‌ها (Channels) یه مدل کاملاً متفاوتن: تو این مدل، به جای اینکه حافظه‌ای به اشتراک گذاشته بشه، ریسمان‌ها **به هم مقدار ارسال می‌کنن**. شعارِ کتابخونه‌ی استاندارد Rust برای این قضیه، که از زبان Go قرض گرفته شده، اینه: «با به اشتراک‌گذاری حافظه ارتباط برقرار نکنید؛ در عوض، با ارتباط برقرار کردن، حافظه رو به اشتراک بذارید.»

## نوع `mpsc`: چندتولیدکننده، یک‌مصرف‌کننده (multi-producer, single-consumer)

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

thread::spawn(move || {
    tx.send(42).unwrap();
}); // متغیر tx به داخل کلوژر منتقل (move) می‌شه، و وقتی کار ریسمان تموم شد پاک می‌شه

let received = rx.recv().unwrap(); // اینجا متوقف می‌شه تا یه مقداری برسه
assert_eq!(received, 42);
```

متدِ `()mpsc::channel` یه جفت `(Sender<T>, Receiver<T>)` (فرستنده و گیرنده) بهت برمی‌گردونه. متدِ `tx.send(v)` هیچ‌وقت برنامه رو متوقف (block) نمی‌کنه (مقادیر تو صف قرار می‌گیرن)؛ اما متدِ `()rx.recv` ریسمانِ فعلی رو متوقف می‌کنه تا یه مقداری برسه و آماده بشه، و تنها زمانی `Err` برمی‌گردونه که تمام `Sender`ها پاک (drop) شده باشن و دیگه هیچ امیدی به رسیدن هیچ مقدار جدیدی تا ابد نباشه. نوعِ `<Sender<T>` خصیصه‌ی `Clone` رو پیاده‌سازی می‌کنه — این همون بخشِ «چندتولیدکننده (multi-producer)» داستانه: به ازای هر ریسمانی که نیاز به ارسال داده داره یه بار اونو کپی (clone) می‌کنی، و اونوقت تک‌تکِ این کپی‌ها مقادیر رو به همون گیرنده‌ی *یکسان* تزریق می‌کنن.

## استفاده از `rx` به عنوان یه پیمایشگر، و چرا پاک‌کردنِ (dropping) تمام `Sender`ها مهمه

```rust
for value in rx {
    println!("{value}");
} // این حلقه زمانی تموم می‌شه که تک‌تکِ فرستنده‌ها (شامل تموم کپی‌هاشون) پاک شده باشن
```

نوعِ `<Receiver<T>` خصیصه‌ی `IntoIterator` رو پیاده‌سازی کرده، ینی به محض اینکه مقادیر از راه می‌رسن اونا رو تحویل می‌ده و هر زمان که تمامِ کپی‌هایِ مربوط به `Sender`ِ متناظرش از بین برن، به طور خودکار به پایان می‌رسه — دقیقاً به همین دلیله که وقتی چند تا ریسمانِ تولیدکننده (producer thread) رو spawn می‌کنی که هر کدومشون یه `()tx.clone`ِ مجزا برای خودشون دارن، حتماً باید بعد از اینکه همه‌ی کپی‌ها رو دست‌به‌دست کردی و تحویل دادی، خودت صریحاً `drop(tx)` (یعنی همون فرستنده‌ی *اصلی* که تو ریسمانِ والد (parent thread) نگهش داشته بودی) رو صدا بزنی — وگرنه پیمایشگرِ تو برای همیشه منتظرِ یه `Sender` می‌مونه که فقط بیکار و بلااستفاده یه گوشه افتاده، چون از کجا باید بدونه که تو دیگه قرار نیست روی اون `.send()` رو صدا بزنی.

## کانال‌ها در برابر `Mutex`: کِی کدوم رو انتخاب کنیم

- آیا فقط نیاز داری یه ریسمان بعد از اینکه کارش تموم شد، یه **نتیجه (result)** رو یک‌بار تحویل یه ریسمانِ دیگه بده؟ تو این حالت یه کانال (یا حتی استفاده از مقدار بازگشتیِ همون `JoinHandle` که قبلاً دیدیش) معمولاً روش خیلی ساده‌تری نسبت به ساختن یه وضعیت مشترکه. تابعِ `compute_async_sum` تو پایین دقیقاً همین کار رو می‌کنه.
- آیا نیاز داری که چند تا ریسمانِ مختلف به طور کاملاً مستقل، تو طول زمان **داده‌هایی رو بفرستن (feed data)** به یک جای واحد، بدون اینکه بخوان با هم سر قفل کردنِ یه کالکشنِ مشترک بجنگن؟ جواب یه کاناله. تابعِ `collect_from_producers` تو پایین دقیقاً همین کار رو می‌کنه.
- آیا نیاز داری چند تا ریسمان روی *یک* قطعه‌ی زنده و پویا از یک وضعیتِ *یکسان*، هم بخونن و هم بنویسن، جوری که هر خوندنی آخرین تغییراتِ نوشته‌شده رو ببینه؟ جواب `<Arc<Mutex<T>>` هست — چون یه کانال ذاتاً مدلِ «یه وضعیت مشترک و دائماً در حال آپدیت» رو تداعی نمی‌کنه، بلکه فقط مدلِ «بیا این مقدار رو بگیر» رو شبیه‌سازی می‌کنه.
