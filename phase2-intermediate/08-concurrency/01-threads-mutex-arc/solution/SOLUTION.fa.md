# راه‌حل — ۲.۸.۱ ریسمان‌ها، `Mutex`، `Arc`

```rust
pub fn sum_in_threads(nums: Vec<i32>, thread_count: usize) -> i32 {
    let thread_count = thread_count.max(1);
    let chunk_size = nums.len().div_ceil(thread_count).max(1);
    let chunks: Vec<Vec<i32>> = nums.chunks(chunk_size).map(|c| c.to_vec()).collect();

    let handles: Vec<_> = chunks
        .into_iter()
        .map(|chunk| thread::spawn(move || chunk.iter().sum::<i32>()))
        .collect();

    handles.into_iter().map(|h| h.join().unwrap()).sum()
}

pub fn count_matching_in_threads(items: Vec<i32>, predicate: fn(i32) -> bool) -> i32 {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();

    for item in items {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            if predicate(item) {
                *counter.lock().unwrap() += 1;
            }
        }));
    }

    for handle in handles {
        handle.join().unwrap();
    }

    let final_count = *counter.lock().unwrap();
    final_count
}
```

## `sum_in_threads` — هیچ وضعیتِ مشترکی نیست، پس هیچ `Mutex`ی هم لازم نیست

`nums` با `.chunks(chunk_size).map(|c| c.to_vec())` به چند تکه‌یِ **دارایِ مالکیت** بریده می‌شود — هر تکه با `.to_vec()` واقعاً کپی می‌شود، پس هر کلوژرِ spawnشده می‌تواند با `move` مالکیتِ تکه‌ی خودش را کامل بگیرد، بدونِ اینکه چیزی از بقیه قرض بگیرد. هر ریسمان جمعِ تکه‌ی خودش را کاملاً مستقل حساب می‌کند؛ تا وقتی دارند اجرا می‌شوند، هیچ‌چیزی بینشان مشترک نیست که بیش از یک ریسمان به آن دست بزند. تنها جایی که همه‌چیز دوباره کنارِ هم می‌آید، رویِ همان ریسمانِ فراخواننده است، بعد از هر `handle.join()` — و آن‌جا دیگر کاملاً ترتیبی است، پس جمع‌کردنِ نتیجه‌های جزئی به هیچ هماهنگی‌ای نیاز ندارد.

`thread_count.max(1)` حالتِ `thread_count`ِ برابرِ `0` را پوشش می‌دهد (که مثلِ `1` رفتار می‌کند). `chunk_size.max(1)` حالتِ مرزیِ `nums`ِ خالی را پوشش می‌دهد: بدونِ آن، هروقت `nums` خالی باشد `chunk_size` برابرِ `0` محاسبه می‌شود و `.chunks(0)` با پیامِ `chunk size must be non-zero` پنیک می‌کند — دقیقاً همان چیزی که `sums_an_empty_vec` چک می‌کند. `sums_with_more_threads_than_elements` (وقتی تعدادِ ریسمانِ درخواستی از تعدادِ عنصرها بیشتر است) به هیچ حالتِ خاصی نیاز ندارد: `.chunks()` وقتی به‌اندازه‌ی کافی نباشد، خودش فقط تکه‌هایِ کمتر و کوچک‌تر از `thread_count` می‌دهد.

## `count_matching_in_threads` — وضعیتِ واقعاً مشترک و در حالِ تغییر

اینجا هر ریسمان ممکن است، درحینِ اجرا، دستش را به همان یک `i32` برساند — دقیقاً همان شکلی که «مفهوم» برایش `Arc<Mutex<T>>` را ساخت. `Arc::clone(&counter)` به ازایِ هر آیتم یک بار اجرا می‌شود و یک دستگیره‌ی مالک به همان `Mutex`ِ زیرین به هر کلوژر می‌دهد؛ `*counter.lock().unwrap() += 1` فقط وقتی اجرا می‌شود که `predicate(item)` مقدارِ `true` بدهد، و خودِ قفل تضمین می‌کند آن افزایش هرگز با افزایشِ یک ریسمانِ دیگر قاطی نشود.

توجه کن دو خطِ آخر تویِ یک عبارتِ بازگشتیِ لختِ `*counter.lock().unwrap()` ادغام **نشده‌اند**. این دقیقاً همان `E0597`ِ خودِ ۲.۸.۱ است، از «خطاهایی که خواهی دید»: یک `MutexGuard` که تویِ آخرین عبارتِ یک تابع ساخته می‌شود از `counter` قرض می‌گیرد، و تمدیدِ طولِ‌عمرِ آن مقدارِ موقت درست همان‌جایی برخورد می‌کند که خودِ `counter` هم قرار است پاک شود. ریختنِ نتیجه اول تویِ `final_count`، قرضِ آن گارد را همان لحظه تمام می‌کند، و فقط همان `i32`ِ ساده (که `Copy` است) زنده می‌ماند تا برگردانده شود.

## تستِ اضافه: یک `HashMap`ِ مشترک، نه فقط یک `i32`

مجموعه‌ی تستِ راه‌حل یک چیز فراتر از آنچه `src/lib.rs` می‌خواهد هم دارد: `shared_hashmap_across_threads_gets_every_update`، یک `Arc<Mutex<HashMap<&str, u32>>>` که از پشتِ شش ریسمان، با `.entry(word).or_insert(0) += 1`، آپدیت می‌شود. دقیقاً همان شکلِ تمرینِ «بساز» است، این‌بار نوشته‌شده — اثباتِ اینکه هیچ‌چیزی تویِ `Arc<Mutex<T>>` مخصوصِ یک عددِ ساده نیست؛ `T` می‌تواند هر نوعی باشد که به دسترسیِ انحصاری و هماهنگ نیاز دارد، شاملِ خودِ entry API. آن را چند بار پشتِ سرِ هم اجرا کن، نه فقط یک‌بار — تست‌هایِ همروند می‌توانند تویِ یک اجرا صرفاً از رویِ شانس سبز شوند، جوری که تستِ تک‌ریسمانی هرگز نمی‌شود.

## این درس واقعاً درباره‌ی چه بود

دو کارِ جدا، رویِ هم چیده‌شده: `Arc` به هر ریسمان یک مالکِ واقعی و کاملاً برابر از همان تخصیص می‌دهد — دقیقاً همان کاری که `Rc`ِ ۲.۶.۳ از قبل می‌کرد، فقط این‌بار با شمارنده‌ای اتمیک به‌جایِ شمارنده‌ای معمولی. `Mutex` در هر لحظه فقط به یک ریسمان دسترسیِ **انحصاری** برایِ تغییرِ آنچه درونش است می‌دهد — دقیقاً همان کاری که `RefCell`ِ ۲.۶.۵ از قبل می‌کرد، فقط این‌بار با یک قفلِ سطحِ سیستم‌عامل به‌جایِ شمارنده‌ی قرضِ زمانِ‌اجرا. هیچ‌کدام از این دو نوع کارِ مفهوماً تازه‌ای نمی‌کنند؛ هردو خواهرانِ امن-برایِ-ریسمانِ ابزارهایی‌اند که از قبل داشتی، فقط همین که پایِ بیش از یک ریسمانِ سیستم‌عامل وسط بیاید، وقتِ استفاده از آن‌هاست.
