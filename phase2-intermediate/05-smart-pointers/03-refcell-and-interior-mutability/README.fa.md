# ۰۵.۳ — نوع `RefCell` و تغییرپذیری داخلی (interior mutability)

## همون قانون قبلی، منتها از زمان کامپایل جابه‌جا شده به زمان اجرا

از ماژولِ قرض‌گرفتن (borrowing) تو فاز ۱ به بعد، تو مدام به قانون «یا نام مستعار، یا تغییرپذیری (aliasing XOR mutability)» تکیه می‌کردی: تو هر نقطه‌ای، می‌تونی کلی `T&` (قرض‌های اشتراکیِ فقط‌خواندنی) **یا** دقیقاً یدونه `mut T&` (قرضِ انحصاریِ تغییرپذیر) داشته باشی — و هیچ‌وقت جفتش با هم نمی‌شه — و این کامپایلر بود که این قضیه رو *به‌صورت استاتیک* و خیلی قبل‌تر از اینکه برنامه‌ات اجرا بشه چک می‌کرد. کلِ فلسفه‌ی وجودِ `<RefCell<T>` همینه: دقیقاً **همون قانون** رو اعمال می‌کنه، با این تفاوت که به جای زمان کامپایل، تو *زمان اجرا (run time)* این کار رو انجام میده.

```rust
use std::cell::RefCell;

let cell = RefCell::new(5);

let a = cell.borrow();      // شبیه T& — اشتراکی، فقط‌خواندنی
println!("{}", *a);
drop(a);                    // باید قبل از borrow_mut تموم بشه، وگرنه کد پایین پنیک (panic) می‌کنه

let mut b = cell.borrow_mut(); // شبیه mut T& — انحصاری، تغییرپذیر
*b += 1;
```

متدهای `()borrow.` و `()borrow_mut.` هر دوشون از طریق یه ارجاع اشتراکیِ کاملاً معمولی (`<RefCell<T>&`) کار می‌کنن — واسه صدا زدنِ `()borrow_mut.` هیچ نیازی به داشتنِ `mut&` نیست. ساختار `RefCell` خودش تو پس‌زمینه آمار می‌گیره که دقیقاً چند تا قرضِ اشتراکی و چند تا قرضِ تغییرپذیر تو همین لحظه "زنده‌ان" (یعنی هنوز drop نشدن). اگه سعی کنی تو زمانی که یه قرضِ دیگه (چه اشتراکی چه تغییرپذیر) هنوز زنده‌ست بیای و `()borrow_mut` بگیری، کامپایلر اصلاً جلوت رو نمی‌گیره — بلکه برنامه تو **زمان اجرا کرش (panic) می‌کنه**، اونم با پیامی شبیه به `already borrowed: BorrowMutError`.

## اصلاً چرا آدم باید یه تضمینِ زمان کامپایل رو با یه تضمینِ زمان اجرا عوض کنه؟

چون بعضی وقتا بررسی‌کننده‌ی کامپایلر (borrow checker) از چیزی که واقعاً تو واقعیت ایمنه هم سخت‌گیرتره، مخصوصاً وقتی که واردِ چند لایه انتزاع (abstraction) می‌شی — مثلاً فرض کن داری یه بخشِ منطقی از یه ساختارِ مشترک رو تغییر می‌دی و همزمان داری یه بخش دیگه‌اش رو می‌خونی، اونم از طریق کدهایی که چکر (checker) نمی‌تونه کُلِ عمق و جریانش رو ببینه (مثل یه کال‌بک، یه متدِ trait، یا یه درخت که گره‌های فرزند توش به اشتراک گذاشته شدن). نوعِ `RefCell` یه راه فرار (escape hatch) بهت می‌ده: کامپایلر یه قدم می‌کشه عقب، و تو در عوض مسئولیتِ اینکه قوانین شکسته نشن رو به گردن می‌گیری — که اگه گند بزنی هم، کدت بدون سروصدا باعث خرابی حافظه (memory corruption) نمی‌شه، بلکه با یه پنیک پر سروصدا متوقف می‌شه. این کار **به هیچ‌وجه** `unsafe` محسوب نمی‌شه — نوعِ `RefCell` ۱۰۰٪ کُد امن تو زبان Rustئه، فقط چک کردنِ قانونش رو دیرتر از حد معمول انجام میده.

## ترکیبِ برنده‌ی بزرگ: `<Rc<RefCell<T>>`

درس قبلی: `<Rc<T>` بهت امکان داشتنِ چند مالک رو می‌ده، اما هر مالکی فقط یه دسترسی `T&` می‌گیره — یعنی دسترسیِ فقط‌خواندنی به مقدارِ مشترک. بیا و اون `T` رو بپیچون تو دلِ یه `RefCell` و اونوقت هرکدوم از اون مالک‌ها می‌تونن از طریق کپی‌های `Rc`ِ خودشون متدِ `()borrow_mut.` رو صدا بزنن و داده‌ی مشترک رو واقعاً تغییر بدن (mutate کنن):

```rust
use std::cell::RefCell;
use std::rc::Rc;

let counter = Rc::new(RefCell::new(0));
let handle = Rc::clone(&counter);

*handle.borrow_mut() += 1;
*counter.borrow_mut() += 1;

assert_eq!(*counter.borrow(), 2); // هر دو دستگیره (handle) دقیقاً یه مقدارِ مشترک رو تغییر دادن
```

این ترکیب — ینی چند تا مالکِ مختلف (`Rc`) که هر کدومشون توانایی تغییرِ یه مقدار مشترک رو دارن (`RefCell`) — دقیقاً همون روشیه که باهاش می‌تونی به یه وضعیت واقعاً مشترک و تغییرپذیر (shared, mutable state) تو کدهای تک‌ریسمانی (single-threaded) تو Rust برسی. (نسخه‌ی thread-safe این ترکیب همون `<Arc<Mutex<T>>`ئه، که تو واژه‌نامه یه نگاه گذرا بهش انداختی و تو ماژول ۰۷ با دست خودت می‌سازیش — دقیقاً همون ایده‌ست؛ فقط `Mutex` کاری رو که `RefCell` تو زمان اجرا تو **یه دونه** thread انجام میده، تو زمان اجرا روی **چندین** thread اعمال می‌کنه.)

**استفاده از این ابزار باید یه تصمیمِ کاملاً از روی قصد و فقط برای شرایط خاص باشه — نه اینکه بشه عادتِ همیشگیت.** اگه می‌تونی کدت رو طوری بازنویسی کنی که فقط یه مالک واضح وجود داشته باشه و به جاش فقط `mut&` رو پاس بدی این‌ور و اون‌ور، حتماً این کارو بکن: هم ساده‌تره، و هم کامپایلر همون موقع کامپایل اونو به طور رایگان و با هزینه‌ی اجرایِ صفر برات چک می‌کنه. فقط و فقط زمانی سراغ `<Rc<RefCell<T>>` برو که واقعاً چند تا مالکِ (owner) با طول‌عمر درازمدت داری که همه‌شون از ته دل نیازمندن یه وضعیتِ (state) مشترک رو تغییر بدن، و هیچ راهی هم وجود نداره که بشه یکیشون رو به عنوان مالک انحصاری انتخاب کرد — مثل یه درخت/گراف که گره‌های فرزند بین پدر و مادرها مشترکن، یه الگویِ آبزرور (observer pattern) که توش چند تا شنونده (listener) باید وضعیتِ مشترک رو آپدیت کنن، یا یه کَش (cache) که بینِ چند تا زیرسیستمِ (subsystems) مستقل مشترکه.
