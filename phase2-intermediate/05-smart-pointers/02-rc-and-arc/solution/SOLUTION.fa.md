# پاسخ تشریحی

```rust
pub fn clone_handle(shared: &Rc<AppConfig>) -> Rc<AppConfig> {
    Rc::clone(shared)
}
```

`Rc::clone(shared)` و `shared.clone()` دقیقاً یک متد را صدا می‌زنند. هیچ‌کدام `AppConfig` را کپی نمی‌کنند: نه `String` تازه‌ای برای `app_name` ساخته می‌شود و نه `max_connections` کپی می‌شود. فقط count داخلی یکی زیاد و pointer دوم به همان تخصیص برگردانده می‌شود. در مقابل `String::clone` buffer تازه می‌سازد و byteها را کپی می‌کند؛ به همین علت spelling صریح `Rc::clone` هزینه را بهتر نشان می‌دهد.

پاسخ پرسش سوم همان cleanup قطعی مالکیت است. scope مربوط به `_handle` بلوک داخلی است. با پایان آن، `Drop` مربوط به `Rc` خودکار اجرا و strong count کم می‌شود؛ اگر صفر شده بود، `AppConfig` هم آزاد می‌شد.

شمارنده‌ی `Rc<T>` درون یک `Cell<usize>` و غیراتمی است. «یکی زیاد کن» یک عملیات تجزیه‌ناپذیر نیست؛ دو thread می‌توانند هر دو مقدار قبلی را بخوانند و هر دو old+1 بنویسند و یک افزایش گم شود. در نتیجه داده ممکن است زودتر از موعد آزاد شود. Rust با پیاده‌نکردن `Send` برای `Rc<T>` این حالت را هنگام compile ممنوع می‌کند.

`Arc<T>` از عملیات integer اتمی استفاده می‌کند که CPU اجرای تجزیه‌ناپذیرشان را میان coreها تضمین می‌کند. به همین دلیل thread-safe و کمی گران‌تر از increment معمولی `Rc` است.
