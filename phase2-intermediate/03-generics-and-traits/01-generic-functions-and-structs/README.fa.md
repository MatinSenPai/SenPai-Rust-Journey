# ۰۳.۱ — توابع و ساختارهای Generic (عمومی)

## مشکلی که Genericها حلش می‌کنن

فرض کن تابعی می‌خوای که بزرگترین عدد رو تو یه بُرش (slice) از نوع `i32` پیدا کنه، بعداً یکی دیگه می‌خوای برای نوع `f64`، و بعدش باز یکی برای نوع `String`. تو پایتون تو فقط **یک دونه** تابع می‌نوشتی و اونو رو هر چیزی که دوست داشتی صدا می‌زدی — پایتون تا زمانی که کد واقعاً اجرا نشه نوعِ آرگومان‌ها رو چک نمی‌کنه، در نتیجه یه تابعِ واحدِ `def largest(items): ...` که تو دلش از `>` استفاده می‌کنه، بدون اینکه تو کار خاصی بکنی روی اعداد صحیح، اعشاری، رشته‌ها و هر چیزی که از `>` پشتیبانی کنه کار می‌کرد.

اما Rust نوع داده‌ها رو همون موقعِ کامپایل چک می‌کنه، پس یه امضایِ تابعِ معمولی و غیر-generic تو Rust، مجبوره فقط با یک نوعِ ملموس و مشخص قفل بشه: مثلاً `fn largest(items: &[i32]) -> i32` همیشه و همیشه فقط روی `i32` کار می‌کنه. اینکه بیای یه کپیِ تقریباً مشابه از همین تابع برای `f64` و `String` هم بنویسی جواب می‌ده، اما این دقیقاً همون مدل تکرار و دوباره‌کاریه که زبان‌های برنامه‌نویسی اصلاً به وجود اومدن تا از شرش خلاصمون کنن. راهِ حل زبان Rust **استفاده از Generics** هستش: تابع رو فقط یه بار بنویس، برای نوع‌هاش از یه نوعِ متغیرِ جایگزین (placeholder) استفاده کن (پارامتری کردن نوع)، و اجازه بده خودِ کامپایلر اون نسخه‌های ملموس رو برات تولید کنه.

```rust
fn largest<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut max = *items.first()?;
    for &item in items {
        if item > max {
            max = item;
        }
    }
    Some(max)
}
```

عبارت `<T: PartialOrd + Copy>` اینطوری خونده می‌شه: «برای یه نوعِ نامشخص به اسم `T`، به شرطی که `T` خصیصه‌ی `PartialOrd` رو پیاده‌سازی کنه (یعنی از `<`، `>`، و غیره پشتیبانی کنه) و همینطور `Copy` رو هم داشته باشه (یعنی بشه به جای منتقل‌کردن (move)، با یه کپیِ بیتیِ ساده تکثیرش کرد).» خود کلمه‌ی `T` اینجا فقط یه اسمِ جایگزینه (placeholder) — طبق عرف برنامه‌نویسیِ Rust، از یه حرفِ بزرگ تکی استفاده می‌شه که به معنی «هر نوعِ ملموسی که فراخواننده ازش استفاده کنه» هستش.

## چرا وجود یه محدودکننده‌ی Trait الزامیه

اون کلمه‌ی `PartialOrd` رو از داخل پرانتزهای شکسته تو کُد بالا پاک کن و سعی کن برنامه رو کامپایل کنی: زبان Rust جلوی اجرای `item > max` رو می‌گیره و خطایی شبیه به این می‌ده: «عملگرِ دوتاییِ `>` نمی‌تونه روی نوعِ `T` اعمال بشه.» این قضیه واسه کسایی که از دنیای پایتون میان خیلی عجیبه، جایی که تو خیلی راحت می‌نوشتی `a > b` و تازه تو *زمان اجرا (runtime)* می‌فهمیدی که آیا اصلاً اون اشیا از این عملگر پشتیبانی می‌کنن یا نه (اگه پشتیبانی نمی‌کردن یه `TypeError` می‌داد، اونم احتمالاً خیلی عمیق تو پشته‌ی فراخوانی (call stack)، و ممکنه فقط برای همون یه ورودیِ خاصی رخ می‌داد که تازه تو محیط واقعی و عملیاتی (production) گذارش به این مسیر از کد افتاده).

در عوض، Rust ازت می‌پرسه: برای یه `T` که کاملاً *دلخواه و نامعلومه*، تو دقیقاً رو چه حسابی می‌تونی درباره‌اش فرض و گمان کنی؟ هیچ حسابی — مگه اینکه خودت به صراحت بگی. عبارت `T: PartialOrd` در واقع روشِ تو برای گفتنِ این حرف به کامپایلره: «تضمین می‌کنم که هر `T`ای که این تابع قراره باهاش صدا زده بشه، از مقایسه‌های ترتیبی (ordering comparisons) پشتیبانی می‌کنه.» با همین حرف، کامپایلر هم اجازه می‌ده تو از عملگر `>` داخلِ بدنه‌ی تابع استفاده کنی، *و هم* تو محلِ فراخوانی تابع (call site)، اگه کسی بخواد تابع `largest` رو با نوعی صدا بزنه که از این عملگر پشتیبانی نمی‌کنه، مچش رو می‌گیره. اینطوری، باگ از «چیزی که یه کاربر ممکنه تو محیط واقعی باعثش بشه» تبدیل می‌شه به «چیزی که همین الان رو دستگاه خودت مانع از `cargo build` می‌شه، اونم با یه پیام خطایی که دقیقاً بهت می‌گه چی کمه.»

## ساختارهای Generic

ساختارها (Structs) هم می‌تونن پارامترهای نوع (type parameters) بگیرن:

```rust
pub struct Stack<T> {
    items: Vec<T>,
}
```

حالا هم `Stack<i32>` و هم `Stack<String>` هر دوتاشون استفاده‌های کاملاً معتبری از *همون یک* تعریفِ ساختار هستن. اینجا هم داخلِ بلاکِ `{ ... } impl<T> Stack<T>`، متغیر `T` به جای اون نوعِ ملموس و واقعی می‌شینه که یه `Stack`ِ خاص باهاش ساخته شده.

## تک‌ریختی کردن (Monomorphization)

واژه‌نامه (glossary) قبلاً این مفهوم رو تعریف کرده (بخش "Generic" رو ببین)، پس این نسخه‌ی ملموس‌شه: وقتی که تو داخل یه برنامه‌ی ثابت هم می‌نویسی `()Stack::<i32>::new` و هم `()Stack::<String>::new`، کامپایلر تو پس‌زمینه دو تا نوعِ کامپایل‌شده‌ی کاملاً مستقل و جداگانه تولید می‌کنه — یکی که توش تمامِ `T`ها با `i32` جایگزین شدن، و یکی دیگه که توش تمامِ `T`ها با `String` جایگزین شدن — دقیقاً انگار که خودت با دستت جفتشون رو جداگانه نوشته باشی. تو زمان اجرا (runtime) هیچ ماشین‌کُدِ (machine code) مشترک و "generic"ای وجود نداره، و موقع فراخوانی متدها هم خبری از هیچ تگی (tag) نیست که تازه اونجا چک بشه تا تصمیم بگیره «من الان کدوم نسخه‌ام.» این رفتار کاملاً *برخلافِ* پایتونه، که اونجا واقعاً یک دونه بدنه‌ی تابع تو زمان اجرا وجود داره و تو تک‌تکِ فراخوانی‌ها، دوباره از اول چک می‌کنه که خب الان چه نوعی بهم داده شده. استفاده از Genericها تو Rust، هزینه‌ی خودش رو از زمانِ کامپایل می‌گیره (چون کد بیشتری تولید می‌شه، پس کامپایل کردن یه مقدار کُندتر می‌شه) در عوض اینکه تو زمان اجرا هزینه‌اش (overhead) دقیقاً صفره، و خطاها هم خیلی قبل‌تر از اینکه برنامه اصلاً اجرا بشه گیر می‌افتن.
