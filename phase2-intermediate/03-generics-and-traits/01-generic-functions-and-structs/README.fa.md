# ۰۳.۱ — تابع‌ها و structهای جنریک

## جنریک‌ها چه مشکلی را حل می‌کنند؟

فرض کن تابعی می‌خواهی که بزرگ‌ترین عدد یک slice از `i32` را پیدا کند. کمی بعد همان تابع را برای `f64` و سپس برای `String` لازم داری. در پایتون **یک** تابع می‌نویسی و هر نوعی را به آن می‌دهی. پایتون نوع آرگومان‌ها را تا زمان اجرا بررسی نمی‌کند؛ پس یک `def largest(items): ...` که داخلش از `>` استفاده می‌کند، بدون کار اضافه برای int، float، string و هر چیزی که از `>` پشتیبانی کند کار خواهد کرد.

Rust نوع‌ها را هنگام compile بررسی می‌کند. بنابراین امضای غیرجنریک به یک نوع concrete قفل می‌شود: `fn largest(items: &[i32]) -> i32` فقط برای `i32` کار می‌کند. می‌توانی نسخه‌های تقریباً یکسانی برای `f64` و `String` بنویسی، اما این دقیقاً همان تکراری است که زبان برنامه‌نویسی باید حذف کند.

**جنریک (Generic)** پاسخ Rust است: تابع را یک بار و با یک نوع جای‌نگهدار بنویس؛ کامپایلر نسخه‌های concrete لازم را تولید می‌کند.

```rust
fn largest<T: PartialOrd + Copy>(items: &[T]) -> Option<T> {
    let mut max = *items.first()?;
    for &item in items {
        if item > max {
            max = item;
        }
    }
    Some(max)
}
```

عبارت `<T: PartialOrd + Copy>` یعنی «برای هر نوع `T`، به‌شرط آنکه `PartialOrd` را پیاده کند و از مقایسه‌هایی مانند `<` و `>` پشتیبانی کند، و نیز `Copy` باشد تا به‌جای move با یک کپی بیتی تکثیر شود». خود `T` فقط نام جای‌نگهدار است؛ طبق قرارداد معمول یک حرف بزرگ که به‌جای نوع concrete انتخاب‌شده‌ی فراخواننده می‌نشیند.

## چرا trait bound لازم است؟

`PartialOrd` را از bound بالا حذف کن و compile بگیر. Rust عبارت `item > max` را با خطایی شبیه `binary operation > cannot be applied to type T` رد می‌کند. برای برنامه‌نویس پایتون این رفتار شاید عجیب باشد: در پایتون `a > b` را می‌نویسی و هنگام اجرا می‌فهمی objectها آن را پشتیبانی می‌کنند یا نه. اگر نکنند `TypeError` می‌گیری؛ شاید در عمق call stack و شاید فقط برای ورودی خاصی در production.

Rust می‌پرسد: درباره‌ی یک `T` دلخواه و ناشناخته چه فرضی می‌توانی داشته باشی؟ هیچ، مگر اینکه صریح بگویی. `T: PartialOrd` قراردادی است که می‌گوید هر `T` داده‌شده به این تابع، حتماً مقایسه‌ی ترتیبی دارد. در نتیجه کامپایلر هم اجازه می‌دهد داخل تابع از `>` استفاده کنی و هم هر فراخوانی با نوع نامناسب را همان call site رد می‌کند. باگ از اتفاقی که کاربر شاید در production فعال کند، به خطای `cargo build` روی دستگاه تو تبدیل می‌شود و پیام دقیقاً قابلیت گمشده را نام می‌برد.

## structهای جنریک

struct هم می‌تواند پارامتر نوع داشته باشد:

```rust
pub struct Stack<T> {
    items: Vec<T>,
}
```

`Stack<i32>` و `Stack<String>` دو استفاده‌ی معتبر از **یک** تعریف struct هستند. داخل `impl<T> Stack<T> { ... }`، حرف `T` نماینده‌ی نوع concrete همان `Stack` است.

## یکتاسازی نوع‌ها (Monomorphization)

وقتی در یک برنامه `Stack::<i32>::new()` و `Stack::<String>::new()` را می‌نویسی، کامپایلر دو نوع کامپایل‌شده‌ی کاملاً جدا تولید می‌کند: در یکی همه‌ی `T`ها با `i32` و در دیگری با `String` جایگزین می‌شوند؛ انگار خودت هر دو را دستی نوشته باشی.

در runtime کد ماشین «جنریک» مشترکی وجود ندارد و برای هر فراخوانی tag نوع بررسی نمی‌شود. این رفتار با پایتون فرق دارد؛ آنجا یک بدنه‌ی تابع واقعاً یک بار در runtime وجود دارد و هر بار باید با نوع واقعی ورودی کار کند. جنریک‌های Rust کمی زمان compile و اندازه‌ی کد بیشتر مصرف می‌کنند، اما در عوض سربار runtime ندارند و خطاها پیش از اجرای برنامه پیدا می‌شوند.

## مثال آشنا و مرز آن

یک `Stack<T>` را مثل قفسه‌ی انبار در نظر بگیر که از ابتدا برای یک نوع کالا برچسب خورده است. قفسه‌ی «کد پیگیری» می‌تواند `u64` نگه دارد و قفسه‌ی «نام مشتری» `String`. اما برخلاف انبار واقعی، نمی‌توانی بعداً یک عضو با نوع متفاوت را لابه‌لای همان `Stack<T>` بگذاری؛ `T` برای کل نمونه ثابت است.
