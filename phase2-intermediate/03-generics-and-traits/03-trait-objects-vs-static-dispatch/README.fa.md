# ۰۳.۳ — اشیای Trait در برابر تخصیص استاتیک (static dispatch)

درس ۰۲ با یه سؤال تموم شد: آیا `<print_all_summaries<T: Summarize` می‌تونه یه بُرش (slice) بگیره که توش *هم* `AnimeSeries` باشه و *هم* `MangaVolume`؟ جواب نه هست — و فهمیدن دقیقِ اینکه *چرا نه*، و اینکه راه‌حلش چه هزینه‌ای برات داره، کلِ هدفِ این درسه.

این کریت (crate) کاملاً مستقله (نمی‌تونه کریتِ درس ۰۲ رو وارد (import) کنه)، پس یه نسخه‌ی حداقلی ازش رو دوباره تعریف می‌کنه: `;pub trait Summarize { fn summary(&self) -> String }`.

## تخصیص استاتیک (Static dispatch): نوع‌های عمومی (generics)

```rust
pub fn total_summary_length_generic<T: Summarize>(items: &[T]) -> usize {
    items.iter().map(|i| i.summary().len()).sum()
}
```

درست مثل `<largest<T` و `<Stack<T` تو درس ۰۱، این هم **تک‌ریختی (monomorphized)** می‌شه: با `[AnimeSeries]&` صداش بزن و کامپایلر یه نسخه از این تابع تولید می‌کنه که توش `T` روی `AnimeSeries` ثابت شده؛ یه جای دیگه با `[MangaVolume]&` صداش بزن و یه نسخه‌ی مجزا و جداگونه‌ی دوم دریافت می‌کنی. هر *محلِ فراخوانی (call site)* دقیقاً متعهد به یک نوعِ ملموس (concrete type) برای `T` می‌شه. به همین خاطره که یه `[T]&` هیچ‌وقت نمی‌تونه یه ترکیبِ واقعی از چند نوع رو تو خودش نگه داره — متغیر `T` یک دونه نوعه، که فقط هم یک بار برای کلِ اون بُرش (slice) انتخاب می‌شه. این رو بهش می‌گن **تخصیص استاتیک (static dispatch)**: کامپایلر تو زمان کامپایل دقیقاً می‌دونه که هر فراخوانی داره کدوم پیاده‌سازیِ `summary` رو هدف می‌گیره، و خیلی وقتا می‌تونه فراخوانی رو مستقیماً تو همون خطِ کد جاگذاری کنه (inline کنه) (یعنی اصلاً هیچ هزینه‌ی (overhead) اضافه‌ای بابتِ فراخوانی تابع وجود نداره).

## تخصیص دینامیک (Dynamic dispatch): اشیای خصیصه (trait objects)

```rust
pub fn total_summary_length_dyn(items: &[Box<dyn Summarize>]) -> usize {
    items.iter().map(|i| i.summary().len()).sum()
}
```

عبارتِ `<Box<dyn Summarize>` یه **شیءِ خصیصه (trait object)** است: یه مقدارِ تخصیص‌داده‌شده روی حافظه‌ی هیپ (`Box`) از *یک* نوعی که `Summarize` رو پیاده‌سازی می‌کنه، در حالی که نوع ملموس و واقعیِ اون پاک شده (erased). تنها چیزی که کامپایلر ازش نگه می‌داره اینه که «این شیء `Summarize` رو پیاده‌سازی می‌کنه» — نه اینکه واقعاً کدوم struct هست. زبان Rust در کنارِ اون داده‌ی boxed، یه **vtable** (جدول متدهای مجازی یا virtual method table) هم ذخیره می‌کنه: یه جدول جستجوی (lookup table) کوچیک تو زمان اجرا از پوینترهای تابع (function pointers)، یکی برای هر متدِ trait، که به پیاده‌سازیِ دقیقِ همون نوعِ ملموسی که این مقدار واقعاً داره اشاره می‌کنه. صدا زدنِ `()summary.` روی یه `dyn Summarize` یعنی: تو زمان اجرا، پوینترِ تابعِ درست رو تو vtable پیدا کن، و بعد بپر بهش — یعنی یه پرشِ اضافه‌تر از طریق پوینتر (indirection) در مقایسه با یه فراخوانیِ مستقیم که تو زمان کامپایل شناخته شده بود.

این پاک کردنِ نوع، دقیقاً همون چیزیه که بهت قابلیت ناهمگونی (heterogeneity) می‌ده:

```rust
pub fn make_mixed_collection() -> Vec<Box<dyn Summarize>> {
    vec![
        Box::new(AnimeSeries { /* ... */ }),
        Box::new(MangaVolume { /* ... */ }),
    ]
}
```

یه `<Vec<Box<dyn Summarize>>` می‌تونه یه ترکیب واقعی از نوع‌های مختلف و ملموسِ structها رو تو یه کالکشنِ واحد نگه داره، چون نوعِ *استاتیکِ* تک‌تکِ عناصر (حداقل تا جایی که به `Vec` مربوطه) یکسانه: `<Box<dyn Summarize>`. هیچ `<Vec<T>`ای با یه متغیرِ genericِ ثابت و منفردِ `T`، هرگز نمی‌تونست همچین کاری بکنه.

## کدوم رو انتخاب کنیم

**به‌طور پیش‌فرض سراغ genericها برو.** اونا سریع‌ترن (چون خبری از پرش‌های vtable نیست، و کامپایلر خیلی وقتا می‌تونه فراخوانی رو inline و بهینه‌سازی کنه)، و خطاهای مربوط به نوع (type errors) تو همون زمان کامپایل و دقیقاً تو محل فراخوانی (call site) خودشون رو نشون می‌دن، به جای اینکه لازم باشه تو زمان اجرا تست بشن. مشخصاً زمانی سراغ `dyn Trait` برو که:

- به یه **کالکشن واقعاً ناهمگون (heterogeneous collection)** نیاز داری — مثل بالا، یه `Vec` از انواعِ مختلف و ملموس که همگی تو یه trait مشترک هستن.
- می‌خوای از **پف کردن و بزرگ‌شدنِ حجم کد (code-size bloat)** که به خاطر تک‌ریختی کردنِ (monomorphizing) بدنه‌ی یه تابعِ generic برای تعداد زیادی نوعِ ملموسِ مختلف به وجود میاد (چون هرکدوم یه کپیِ کاملِ مجزا تو باینریِ نهایی می‌سازن)، جلوگیری کنی.

تو فاز ۳ دقیقاً همین سبک‌سنگین‌کردن (trade-off) رو دوباره می‌بینی: روترِ (router) فریم‌ورکِ `axum` و رجیستری‌هایِ پلاگین‌طورِ هَندلرهاش، دقیقاً به خاطر اینکه یه روتر نیاز داره تعداد زیادی از نوع‌های *مختلفِ* هندلر رو تو یه کالکشنِ واحد نگه داره، به `dyn Trait` (یا الگوهایِ شبیهِ trait-object) تکیه می‌کنن.
