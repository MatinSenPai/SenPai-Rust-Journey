# ۲.۱.۴ — انتخابِ مجموعه: جدولِ پیچیدگی و اینکه هرکدام کِی برنده است

## در یک نگاه

بعد از این درس می‌توانی:

- برای یک الگوی دسترسیِ واقعی — نه یک نام — بدونِ حدس زدن بگویی کدام‌یک از `Vec`، `HashMap`، `BTreeMap`، `HashSet`، `VecDeque` و `BinaryHeap` مناسبش است و کدام‌ها اصلاً نیستند.
- توضیح بدهی چرا یک انتخابِ غلط هم کامپایل می‌شود، هم اجرا می‌شود، هم جواب درست می‌دهد — و فقط ساکت `O(n)`ای را که `O(1)` رایگان بود، از جیبت خرج می‌کند.
- انتخابت را با صدای بلند توجیه کنی: کدام محور تصمیم را گرفت، و اگر یکی از الزام‌ها عوض شود، کدام محور اول می‌شکند.

## چرا اهمیت دارد

سه درسِ قبلی، شش تا ابزار را یکی‌یکی به‌ات دادند: مکانیکِ داخلیِ `Vec`، ترفندِ entry API روی `HashMap`، و بعد چهارتای دیگر که هرکدام یک مشکلِ مشخص را حل می‌کنند. هرکدام از آن درس‌ها یک سؤال داشت: «این ساختار چطور کار می‌کند؟» این درس یک سؤالِ کاملاً متفاوت دارد: **وقتی کدِ واقعی جلوت است و هیچ‌کس اسمِ نوع را برایت ننوشته، کدام‌یک را انتخاب می‌کنی؟**

نکته‌ی خطرناک این‌جاست: انتخابِ غلط تقریباً هیچ‌وقت خطای کامپایلر نمی‌دهد. اگر به‌جایِ `HashSet` یک `Vec` برای چک کردنِ عضویت به‌کار ببری، کد کامپایل می‌شود، اجرا می‌شود، و جوابِ درست هم می‌دهد — فقط هر چک، به‌جایِ یک نگاهِ آنی، کلِ لیست را خطی می‌گردد. با ده تا آیتم هیچ‌وقت حسش نمی‌کنی. با ده میلیون تا، سرویس‌ات پایین می‌آید و هیچ خطایی هم رویِ صفحه نیست که بگوید چرا. این دقیقاً همان سؤالی است که مصاحبه‌های فنی با «کدام ساختارِ داده؟» می‌پرسند، و همان چیزی است که در ریویوی کد یک نفر زیرِ خط می‌نویسد: «چرا این یک `Vec` است؟»

این درس چیزِ تازه‌ای از نحو یاد نمی‌دهد — همه‌ی متدهایی که پایین می‌بینی، از سه درسِ قبلی می‌شناسی‌شان. کارش این است که آن شش تا را کنارِ هم بگذارد و از تو بخواهد یک‌بار برای همیشه با یک نگاه تصمیم بگیری، نه اینکه هر بار دوباره حدس بزنی.

## مفهوم

### یک سؤال، نه شش نحو

هر شش‌تا این‌ها یک قرارداد دارند: مقدار می‌گیرند، مقدار پس می‌دهند. فرقشان در این است که به کدام سؤال جواب «ارزان» می‌دهند و به کدام سؤال جواب «گران» — یا اصلاً جواب نمی‌دهند. پنج محور هست که هر بار باید از خودت بپرسی، و ترتیبشان مهم است: هرکدام معمولاً یکی از گزینه‌ها را حذف می‌کند، تا وقتی یکی بماند.


### محور یک — با کلید پیدا می‌کنی، یا فقط پیمایش می‌کنی؟

اگر سؤالت شکلِ «مقدارِ فلان کلید چیست؟» یا «آیا فلان مقدار وجود دارد؟» است، `HashMap`/`HashSet` این را در `O(1)`ِ میانگین جواب می‌دهند — یک هش، یک جهش مستقیم به سطلِ درست.

```rust
use std::collections::HashMap;

let watch_counts: HashMap<&str, u32> = HashMap::from([
    ("Frieren", 12),
    ("Bocchi", 7),
]);

println!("{:?}", watch_counts.get("Frieren"));
println!("{:?}", watch_counts.get("Naruto"));
```

```text
Some(12)
None
```

یک `Vec` اصلاً مفهومِ «کلید» ندارد. همان سؤال را از یک `Vec<(&str, u32)>` بپرسی، تنها راهت یک حلقه‌ی دستی است که یکی‌یکی می‌گردد — دقیقاً همان کاری که در فازِ ۱ با یک لیست انجام می‌دادی:

```rust
let shows = vec![("Frieren", 12), ("Bocchi", 7)];
let mut found = None;
for (title, count) in &shows {
    if *title == "Frieren" {
        found = Some(*count);
    }
}
println!("{found:?}");
```

```text
Some(12)
```

جوابِ درست را می‌دهد — ولی برای پیدا کردنِ «Naruto» که نیست، باید هر ده‌هزار عنصر را ببیند تا مطمئن شود. (اگر واقعاً مجبوری با `Vec` بمانی، نگه‌داشتنش به‌صورت مرتب و `.binary_search()` از ۲.۱.۱ این را به `O(log n)` می‌رساند — ولی هر درج، حالا خودش `O(n)` می‌شود چون باید جای خالی باز کند. `HashMap`/`BTreeMap` هیچ‌کدام این معامله را ندارند.)

### محور دو — با اندیس پیدا می‌کنی؟

«دومین عنصر چیست؟» فقط برای `Vec` و `VecDeque` معنا دارد — هردو `O(1)` با اندیس جواب می‌دهند، چون هردو پشتِ‌صحنه یک بافرِ پیوسته‌اند.

```rust
let lineup: Vec<&str> = vec!["Frieren", "Bocchi", "Naruto"];
println!("first:   {:?}", lineup.first());
println!("index 1: {:?}", lineup.get(1));
```

```text
first:   Some("Frieren")
index 1: Some("Bocchi")
```

بقیه‌ی چهارتا اصلاً «دومین» ندارند — یک `HashMap` یا `BTreeMap` کلید دارد، نه موقعیت؛ یک `HashSet` عضو دارد؛ یک `BinaryHeap` فقط «بزرگ‌ترین» را می‌شناسد. این محور معمولاً سریع‌ترین راهِ حذف کردنِ گزینه‌هاست: اگر واقعاً به موقعیت نیاز داری، فقط دو گزینه از شش‌تا برایت مانده.

### محور سه — پیمایش به چه ترتیبی بیرون می‌آید؟

از ۲.۱.۲ می‌دانی که `HashMap` هیچ قولی درباره‌ی ترتیب نمی‌دهد. `BTreeMap` دقیقاً برعکس است: پیمایش همیشه بر اساسِ کلید، صعودی، و **رایگان** — بدونِ اینکه خودت چیزی جمع و مرتب کنی:

```rust
use std::collections::BTreeMap;

let mut by_day: BTreeMap<u32, u32> = BTreeMap::new();
by_day.insert(3, 40);
by_day.insert(1, 12);
by_day.insert(2, 25);
for (day, count) in &by_day {
    println!("day {day}: {count}");
}
```

```text
day 1: 12
day 2: 25
day 3: 40
```

`BinaryHeap` یک حالتِ سومِ عجیب است: تنها چیزی که تضمین می‌کند این است که *بعدی‌ای که پاپ می‌کنی* بزرگ‌ترین مقدارِ باقی‌مانده است. این دقیقاً شرحِ‌وظیفه‌ی یک **صفِ اولویت (priority queue)** است — ساختاری که فقط «بزرگ‌ترین (یا کوچک‌ترینِ) فعلی» را ارزان می‌دهد و درباره‌ی هیچ‌چیزِ دیگری قولی نمی‌دهد — و `BinaryHeap` دقیقاً همین است. خودِ پیمایش (`for x in &heap`) هیچ ترتیبی ندارد — همان ترتیبِ داخلیِ درختِ هیپ است، نه ترتیبِ مرتب:

```rust
use std::collections::BinaryHeap;

let ratings: BinaryHeap<u32> = BinaryHeap::from([3, 1, 4, 1, 5, 9, 2, 6]);
println!("peek: {:?}", ratings.peek());
let mut still_sorted = true;
let mut previous = u32::MAX;
for value in &ratings {
    still_sorted &= *value <= previous;
    previous = *value;
}
println!("iter() order was sorted: {still_sorted}");
```

```text
peek: Some(9)
iter() order was sorted: false
```

`peek()` درست می‌گوید ۹ بزرگ‌ترین است. ولی پیمایشِ خام، مرتب نیست — این همان تله‌ای است که تقریباً همه‌ی اولین‌بارها می‌خورند: اسمش «هیپ» است، پس فکر می‌کنند پیمایشش هم مرتب است. نیست. فقط `pop()`های پیاپی مرتب‌اند.

### محور چهار — کجا اضافه می‌کنی و برمی‌داری؟

از یک سر، از هر دو سر، یا فقط «بزرگ‌ترین»؟ سه جوابِ کاملاً متفاوت:

```rust
use std::collections::VecDeque;

let mut recent: VecDeque<&str> = VecDeque::new();
recent.push_back("ep1 released");
recent.push_back("ep2 released");
recent.push_front("server maintenance");
println!("{recent:?}");
println!("oldest: {:?}", recent.pop_front());
```

```text
["server maintenance", "ep1 released", "ep2 released"]
oldest: Some("server maintenance")
```

`Vec` فقط **عقب**اش ارزان است — `.push()`/`.pop()` در `O(1)`ِ آمورتایزد؛ جلواش `O(n)` است چون همه باید یکی جابه‌جا شوند (۲.۱.۳ همین را با خطای `E0599` نشانت داد وقتی `.pop_front()` صدا زدی — آن متد اصلاً وجود ندارد). `VecDeque` هر دو سر را `O(1)`ِ آمورتایزد می‌دهد، چون پشتِ‌صحنه یک بافرِ حلقه‌ای (ring buffer) است، نه یک بافرِ ساده. `BinaryHeap` اصلاً «سر» ندارد — فقط `push` (به هرجا که لازم باشد، `O(log n)`) و `pop`ِ همیشه-بزرگ‌ترین (هم `O(log n)`)، به‌علاوه‌ی `peek()`ِ رایگان برایِ فقط نگاه کردن.

`HashMap`/`BTreeMap`/`HashSet` هیچ‌کدام «سر» ندارند — درج و حذف با **کلید** انجام می‌شود، نه با موقعیت.

### محور پنج — سربارِ حافظه

این یکی نمی‌شود با یک `println!` نشانش داد، ولی همان‌قدر واقعی است: `Vec` و `VecDeque` فقط عناصرِ خودشان را نگه می‌دارند، پشت‌سرِهم، بدونِ هیچ بایتِ اضافه به‌ازایِ هر عنصر. `BinaryHeap` هم همین است — پشتِ‌صحنه خودش یک `Vec` است.

`HashMap`/`HashSet` عمداً هیچ‌وقت پر نمی‌شوند: برای اینکه جست‌وجو `O(1)` بماند، همیشه چند جای خالی نگه می‌دارند (ضریبِ پرشدگی، load factor) — یعنی حافظه‌ای که رزرو شده همیشه از حافظه‌ای که واقعاً استفاده می‌شود بیشتر است. `BTreeMap` سربارِ متفاوتی دارد: هر گره‌ی درخت چند ورودی و چند اشاره‌گر نگه می‌دارد — کمتر از اتلافِ یک هش‌تیبل، ولی باز هم بیشتر از یک آرایه‌ی خام. اگر حافظه واقعاً تنگ است، این محور هم به‌حساب می‌آید — ولی معمولاً آخرین محوری است که تصمیم را عوض می‌کند، نه اولین.

### جدولِ تصمیم

همه‌ی پنج محور، یک‌جا:

| مجموعه | پیمایشِ مرتب؟ | جست‌وجو با کلید؟ | جست‌وجو با اندیس؟ | اضافه/برداشتِ جلو | اضافه/برداشتِ عقب | سربارِ حافظه | کِی سراغش بروی |
|---|---|---|---|---|---|---|---|
| `Vec<T>` | ترتیبِ درج | نه (خطی، مگر مرتب+`binary_search`) | `O(1)` | `O(n)` | `O(1)` آمورتایزد | کمترین — پیوسته | ترتیب دقیقاً همان ترتیبِ درج است؛ عمدتاً با اندیس یا از عقب کار می‌کنی |
| `VecDeque<T>` | ترتیبِ درج | نه | `O(1)` | `O(1)` آمورتایزد | `O(1)` آمورتایزد | نزدیکِ `Vec` | باید از **هر دو سر** ارزان اضافه/بردار — صف، پنجره‌ی لغزان، «N تای اخیر» |
| `HashMap<K, V>` | هیچ (تصادفیِ هر اجرا) | `O(1)` میانگین | نه | کلیدمحور، نه سرمحور | کلیدمحور، نه سرمحور | بیشتر — جایِ خالیِ عمدی | با کلید جست‌وجو می‌کنی و ترتیب برایت مهم نیست |
| `BTreeMap<K, V>` | همیشه مرتب بر کلید | `O(log n)` | نه | کلیدمحور | کلیدمحور | متوسط — سربارِ گره‌ها | هم به ترتیبِ کلید نیاز داری، هم به جست‌وجویِ بازه‌ای، و `O(log n)` برایت قابلِ‌قبول است |
| `HashSet<T>` | هیچ | `O(1)` میانگین (فقط عضویت) | نه | عضومحور | عضومحور | مثلِ `HashMap` | فقط برایت مهم است «هست یا نه»، نه یک مقدارِ همراهش |
| `BinaryHeap<T>` | هیچ تضمینی (فقط `pop` بزرگ‌ترین را می‌دهد) | نه | نه | ندارد | `push` رویِ هرجا `O(log n)`؛ `pop`ِ بزرگ‌ترین `O(log n)`؛ `peek` `O(1)` | مثلِ `Vec` | مکرراً فقط «بزرگ‌ترینِ فعلی» را می‌خواهی، نه جست‌وجویِ دلخواه |

### یک تصمیمِ واقعی، قدم‌به‌قدم

بیا همین جدول را رویِ یک سؤالِ واقعی پیاده کنیم: «امروز چند ژانرِ متفاوت دیده شده؟»

- محورِ یک: سؤال شکلِ «آیا این ژانر قبلاً دیده شده؟» است — یک چکِ عضویت، نه یک مقدار. `HashMap` رد می‌شود (به یک *مقدار* برای هر کلید نیازی نیست)، `HashSet` باقی می‌ماند.
- محورِ دو: به اندیس نیازی نیست — `Vec`/`VecDeque` هم رد می‌شوند.
- محورِ سه: ترتیبِ ژانرها اهمیتی ندارد — `BTreeMap` هم چیزِ اضافه‌ای نمی‌داد، فقط هزینه‌اش بیشتر می‌شد.
- محورِ چهار: نه جلو مهم است نه عقب، نه «بزرگ‌ترین» — `BinaryHeap` هم از دور خارج.

فقط `HashSet` ماند:

```rust
use std::collections::HashSet;

let genres_seen = ["isekai", "comedy", "isekai", "drama", "comedy"];

let mut distinct: HashSet<&str> = HashSet::new();
for genre in genres_seen {
    distinct.insert(genre);
}

println!("genres logged today: {}", genres_seen.len());
println!("distinct genres:     {}", distinct.len());
```

```text
genres logged today: 5
distinct genres:     3
```

این چهار خط استدلال، همانی است که قرار است تویِ تمرین‌های زیر خودت بنویسی — فقط برایِ سه‌تا سناریوی دیگر.

**کامپایلر به چه اعتراض دارد:** `counts[0]` انگار می‌گوید «اولین ورودی را بده» — همان عادتِ `Vec`. ولی `Index` برایِ `HashMap<K, V>` رویِ `&Q` تعریف شده، نه رویِ خودِ `K` — یعنی چیزی که داخلِ کروشه می‌گذاری باید از اول یک *ارجاع به یک کلید* باشد، نه یک عدد. کامپایلر همین را می‌گوید: انتظارِ `&_` داشت، یک عددِ صِرف گرفت.

**راه‌حل:** با یک کلیدِ واقعی اندیس بزن، یا بهتر، از `.get(...)` استفاده کن که به‌جایِ پنیک، `Option` برمی‌گرداند:

```rust
let first = counts.get("Frieren");
```

**چرا این راه‌حل است:** پیشنهادِ خودِ کامپایلر (`counts[&0]`) فقط نیمِ اولِ مشکل را حل می‌کند — نوعِ کلید هنوز `String` است، نه `i32`، پس همان خط با یک خطایِ نوعِ دیگر دوباره شکست می‌خورد. مشکلِ واقعی این نبود که فراموش کردی `&` بگذاری؛ این بود که اصلاً «موقعیتِ صفر» برای یک `HashMap` معنا ندارد. تنها راهِ درست، پرسیدن با کلیدِ واقعی است.

### `E0599` — یک `HashMap` هیچ `.sort()`ی ندارد

```text
error[E0599]: no method named `sort` found for struct `HashMap<K, V, S, A>` in the current scope
  --> phase2-intermediate\01-collections\04-choosing-a-collection\examples\07-hashmap-has-no-sort.rs:15:12
   |
15 |     counts.sort();
   |            ^^^^ method not found in `HashMap<&str, u32>`

For more information about this error, try `rustc --explain E0599`.
error: could not compile `p2-01-04-choosing-a-collection` (example "07-hashmap-has-no-sort") due to 1 previous error
```

**کامپایلر به چه اعتراض دارد:** `.sort()` متدِ `Vec`/برش است، نه `HashMap`. اینجا خواستنِ ترتیب، بعد از انتخابِ ساختاری که از اول هیچ ترتیبی قول نداده بود آمده — دقیقاً محورِ سه، از سمتِ اشتباه.

**راه‌حل:** یا از اول `BTreeMap` انتخاب کن (ترتیب رایگان می‌آید)، یا اگر `HashMap` را واقعاً لازم داری، جفت‌ها را صریح در یک `Vec` جمع کن و خودت مرتب کن:

```rust
let mut by_count: Vec<(&str, u32)> = Vec::new();
for (title, count) in counts {
    by_count.push((title, count));
}
by_count.sort_by_key(|(_, count)| *count);
```

**چرا این راه‌حل است:** نمی‌شود یک ساختارِ بی‌ترتیب را در جا مرتب کرد — ترتیب باید از جایی بیاید. یا از اولِ کار ساختارِ مرتب انتخاب می‌کنی (`BTreeMap`، ترتیب رایگان)، یا آگاهانه یک قدمِ اضافه (جمع‌کردن، بعد `.sort_by_key`) برایِ رسیدن به همان ترتیب می‌پذیری. فازِ ۲.۲ همین جمع‌کردن را در یک خط می‌نویسد؛ همین حلقه‌ی دستی، امروز، همان کار را می‌کند.

### `E0599` — یک `BinaryHeap` هیچ `.remove()`ی ندارد

```text
error[E0599]: no method named `remove` found for struct `BinaryHeap<T, A>` in the current scope
  --> phase2-intermediate\01-collections\04-choosing-a-collection\examples\08-binaryheap-has-no-remove.rs:16:12
   |
16 |     scores.remove(&(10, "Yui"));
   |            ^^^^^^ method not found in `BinaryHeap<(u32, &str)>`

For more information about this error, try `rustc --explain E0599`.
error: could not compile `p2-01-04-choosing-a-collection` (example "08-binaryheap-has-no-remove") due to 1 previous error
```

**کامپایلر به چه اعتراض دارد:** `HashSet` می‌تواند یک عضوِ دلخواه را با `.remove(&value)` پیدا و حذف کند — منطقی است فکر کنی `BinaryHeap` هم همین را دارد. ندارد. `BinaryHeap` فقط برایِ یک سؤال بهینه شده: «بزرگ‌ترین چیست؟» — پیدا کردنِ یک مقدارِ دلخواهِ *غیرِ*بزرگ‌ترین در وسطِ درخت، چیزی است که اصلاً طراحی نشده.

**راه‌حل:** اگر واقعاً به حذفِ دلخواه نیاز داری، `BinaryHeap` انتخابِ درستی نبوده — برگرد به محورِ چهار: چیزی که هم «بزرگ‌ترین را بده» می‌خواهد و هم «هرکدام را که خواستم بردار»، یک ساختارِ دیگر (یا ترکیبِ دو ساختار) لازم دارد.

**چرا این راه‌حل است:** این خطا کدِ اشتباه نیست — تصمیمِ اشتباه است. `BinaryHeap` را دقیقاً برایِ همین معامله ساخته‌اند: در ازایِ اینکه هر عملیاتِ دیگری غیرممکن باشد، «بزرگ‌ترین را بده» را تا حدِ ممکن ارزان نگه می‌دارد.

### گرم‌کردن

<details>
<summary>فقط باید بدانی «آیا این شناسه را قبلاً دیده‌ام؟» — نه مقدارش، نه ترتیبش. کدام‌یک از شش‌تا، و چرا؟</summary>

`HashSet`. سؤال فقط عضویت است، هیچ مقدارِ همراه، هیچ ترتیبی لازم نیست — دقیقاً محورِ یک، ساده‌ترین حالتش.

</details>

<details>
<summary>داری یک بردِ زنده می‌سازی: امتیازها مدام آپدیت می‌شوند و باید همین حالا بگویی برنده‌ی فعلی کیست. کدام یکی وسوسه‌ات می‌کند، و دقیقاً چه چیزی را رایگان به‌ات نمی‌دهد؟</summary>

`BinaryHeap` وسوسه‌کننده است چون «بزرگ‌ترین را بده» دقیقاً کارش است. ولی آپدیت‌کردنِ امتیازِ یک نفرِ خاص (نه اضافه‌کردنِ یک ورودیِ تازه) رویِ `BinaryHeap` رایگان نیست — هیچ راهِ مستقیمی برایِ «این آیتم را پیدا کن و مقدارش را عوض کن» ندارد. همین تنش، دقیقاً موضوعِ بخشِ «بساز» است.

</details>

<details>
<summary>این چه چاپ می‌کند؟</summary>

```rust
use std::collections::BTreeMap;
let mut m = BTreeMap::new();
m.insert(5, "five");
m.insert(1, "one");
m.insert(3, "three");
for (k, _) in &m {
    print!("{k} ");
}
```

</details>

<details>
<summary>پاسخ</summary>

```text
1 3 5
```

`BTreeMap` همیشه بر اساسِ کلید، صعودی پیمایش می‌شود — با همان ترتیبی که `.insert()` صدا زده شد کاری ندارد.

</details>

<details>
<summary>این کامپایل می‌شود؟</summary>

```rust
let mut v: Vec<u32> = vec![1, 2, 3];
let first = v.pop_front();
```

</details>

<details>
<summary>پاسخ</summary>

نه. `Vec` اصلاً متدی به اسمِ `pop_front` ندارد — `E0599`. اگر واقعاً به برداشتنِ ارزان از جلو نیاز داری، `VecDeque` را می‌خواهی.

</details>

<details>
<summary>این چه چاپ می‌کند؟</summary>

```rust
use std::collections::BinaryHeap;
let mut h = BinaryHeap::from([2, 8, 5]);
println!("{:?}", h.pop());
println!("{:?}", h.pop());
```

</details>

<details>
<summary>پاسخ</summary>

```text
Some(8)
Some(5)
```

هر `pop()` بزرگ‌ترینِ باقی‌مانده را برمی‌گرداند — نه ترتیبِ درج، نه ترتیبِ داخلیِ درخت.

</details>

<details>
<summary>هم <code>Vec&lt;T&gt;</code> و هم <code>VecDeque&lt;T&gt;</code> در عقب <code>O(1)</code>ِ آمورتایزد هستند. پس کِی اصلاً سراغِ <code>VecDeque</code> می‌روی؟</summary>

وقتی به **جلو** هم نیاز داری، نه فقط عقب — یک صف، یک پنجره‌ی لغزان، «N رویدادِ اخیر». `Vec` جلواش `O(n)` است؛ `VecDeque` هر دو سرش `O(1)`ِ آمورتایزد است. اگر فقط از عقب کار داری، `Vec` ساده‌تر و کافی است.

</details>

۳. `examples/08-binaryheap-has-no-remove.rs` را طوری بازنویسی کن که واقعاً به هدفش برسد — حذفِ امتیازِ «Yui» — بدونِ `.remove()`. (سرنخ: چه چیزی از `BinaryHeap` واقعاً رایگان است؟ پاپ‌کردنِ همه و نگه‌داشتنِ همه‌چیز جز آنی که نمی‌خواهی، یک راه است؛ آیا بهتری هم هست؟)

```sh
cargo test -p p2-01-04-choosing-a-collection
```

هیچ‌کدام از امضاها اسمِ هیچ مجموعه‌ای را نمی‌گویند — این تصمیم با توست، دقیقاً همان‌طور که در «گرم‌کردن» توجیهش کردی:

- `RecentEvents` — یک ردیاب که همیشه فقط `capacity` رویدادِ آخر را نگه می‌دارد، قدیمی‌ترین اول حذف می‌شود. محورِ چهار: کدام‌یک از شش‌تا هر دو سرش ارزان است؟

### بساز

یک `Leaderboard` کوچک برایِ سریالی که الان پخش می‌شود: بیننده‌ها زیرِ اسمِ خودشان امتیاز (۰ تا ۱۰۰) ثبت می‌کنند؛ باید هر لحظه بتوانی بگویی «الان چه کسی جلوتر است؟». حداقل این دو رفتار را داشته باشد:

- ثبتِ یک امتیازِ تازه برایِ یک اسم (اگر آن اسم قبلاً امتیاز داده، جایگزینش کن، جمعش نکن).
- گزارشِ اسم و امتیازِ نفرِ اولِ فعلی.

هیچ‌یک از شش‌تا هر دویِ این‌ها را رایگان نمی‌دهد — `HashMap` آپدیتِ با نام را `O(1)` می‌دهد ولی پیدا کردنِ نفرِ اول را `O(n)`؛ `BinaryHeap` نفرِ اول را `O(1)` می‌دهد (دقیقاً همین کارِ `.peek()` است) ولی آپدیتِ با نام را اصلاً ندارد (یادت هست، بخشِ «خطاها»). یکی را انتخاب کن — یا دوتا را با هم ترکیب کن — و در یک کامنت بنویس چرا، و دقیقاً چه چیزی را با انتخابِ دیگر از دست می‌دادی.

### چالش (اختیاری)

حالا سخت‌ترش کن: بیننده‌ها می‌توانند اشتراکشان را لغو کنند (امتیازشان کاملاً پاک شود)، و به‌جایِ فقط نفرِ اول، باید سه‌تای برتر را گزارش بدهی — هر بار که کسی خواست، نه فقط یک‌بار در پایان.

`Leaderboard`ی که در «بساز» نوشتی را با همین دو قابلیتِ تازه امتحان کن. آیا همان انتخاب هنوز جواب می‌دهد؟ اگر یک تابعِ حذفِ دلخواه (`remove_by_name`) و یک گزارشِ «سه‌تای برتر» را هردو باید ارزان بدهی، کدام‌یک از شش‌تا — یا کدام ترکیب — حالا برنده است؟ یک‌ یا دو جمله کافی است؛ لازم نیست کدش را کامل بنویسی.

## جمع‌بندی

| اصطلاح | یعنی چه | کجا به‌کارت می‌آید |
|---|---|---|
| محورِ تصمیم | یک سؤال درباره‌ی الگویِ دسترسی که گزینه‌ها را کم می‌کند | هر بار که بینِ چند مجموعه انتخاب می‌کنی |
| صفِ اولویت (priority queue) | ساختاری که فقط «بزرگ‌ترین/کوچک‌ترینِ فعلی» را ارزان می‌دهد | `BinaryHeap` دقیقاً همین است |
| بافرِ حلقه‌ای (ring buffer) | بافری که به‌جایِ جابه‌جاییِ عناصر، دورِ خودش می‌چرخد | همان چیزی که `VecDeque` را در هر دو سر `O(1)` می‌کند |
| ضریبِ پرشدگی (load factor) | نسبتِ جای پرشده به جایِ کلِ یک هش‌تیبل | چرا `HashMap`/`HashSet` همیشه سربارِ اضافه دارند |

### الان می‌دانی

- پنج محور — کلید، اندیس، ترتیبِ پیمایش، سرهای اضافه/برداشت، سربارِ حافظه — و اینکه هرکدام از شش‌تا به کدامش جوابِ ارزان می‌دهد.
- انتخابِ غلط تقریباً هیچ‌وقت خطای کامپایلر نمی‌دهد؛ فقط پیچیدگیِ نامرئی‌ای اضافه می‌کند که تا داده‌ات بزرگ نشود حسش نمی‌کنی.
- `BinaryHeap` معامله‌اش را با تو روشن می‌گوید: در ازایِ اینکه هیچ عملیاتِ دیگری رایگان نیست، «بزرگ‌ترین را بده» را تا حدِ ممکن ارزان نگه می‌دارد.
- هیچ مجموعه‌ای هر پنج محور را هم‌زمان برنده نمی‌شود — گاهی هیچ‌کدام از شش‌تا هر دو الزام را رایگان نمی‌دهد، و آن‌وقت باید یا معامله کنی یا دو ساختار را با هم ترکیب کنی.
- سه تابعِ همین درس هیچ‌کدام اسمِ یک مجموعه را در امضایشان نگفتند — همان‌جایی که تصمیم واقعاً مالِ تو بود.

### بعداً کامل‌تر می‌بینی

- **آداپتورهای Iterator و `.collect()`** — هر حلقه‌ی دستی‌ای که در این درس نوشتی، آنجا به یک عبارتِ زنجیره‌ای کوتاه می‌شود — [فاز ۲ — آداپتورهای Iterator](../../02-iterators-and-closures/02-iterator-adapters/README.fa.md) و [جمع‌کردن با collect](../../02-iterators-and-closures/03-consuming-and-collecting/README.fa.md).
- **`Ord`/`Hash`/`PartialOrd` برایِ نوعِ خودت** — همه‌ی مثال‌های این درس رویِ عددها و تاپل‌ها بودند؛ گذاشتنِ یک `struct`ِ دست‌سازِ خودت داخلِ `BinaryHeap` یا به‌عنوانِ کلیدِ `HashMap`/`BTreeMap` به این‌ها نیاز دارد — [فاز ۲ — دِرایوهایِ استانداردِ دستی](../../03-traits-and-generics/04-standard-derives-by-hand/README.fa.md).
- **استفاده از این شش‌تا از بیش از یک ریسمان هم‌زمان** — هیچ‌کدامشان به‌تنهایی برایِ این امن نیست — [فاز ۲ — ریسمان‌ها، `Mutex` و `Arc`](../../08-concurrency/01-threads-mutex-arc/README.fa.md).
- **اندازه‌گیریِ واقعیِ عملکرد، نه فقط استدلال از رویِ پیچیدگیِ نظری** — این درس فقط Big-O را دلیل آورد؛ سنجیدنِ واقعیِ سرعت روی داده‌ی واقعی، مهارتِ جداگانه‌ای است — [فاز ۲ — بنچمارک با criterion](../../07-project-structure-and-testing/05-benchmarking-with-criterion/README.fa.md).

### می‌توانی توضیح بدهی؟

- برایِ یک سناریویِ فرضی، پنج محور را یکی‌یکی طی کنی و بگویی هرکدام کدام گزینه‌ها را حذف می‌کند؟
- بگویی چرا *انتخابِ مجموعه‌ی اشتباه* تقریباً هیچ‌وقت خطای کامپایلر نمی‌دهد، و دقیقاً همین بی‌خطر به‌نظر رسیدن چه خطری دارد؟
- توضیح بدهی چرا `BinaryHeap` نه `.remove()` دارد نه اندیس‌گذاری، و این نبود چه چیزی را در ازایِ چه چیزی می‌خرد؟
- بگویی چرا هیچ‌کدام از سه امضایِ تمرینِ «پیاده‌سازی» اسمِ یک مجموعه را نگفتند، و این عمداً بود؟
- برایِ سناریویِ «بساز» توضیح بدهی چرا هیچ‌یک از شش‌تا به‌تنهایی هر دو رفتار را رایگان نمی‌داد؟
