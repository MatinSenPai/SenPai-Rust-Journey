# پاسخ تشریحی

```rust
pub fn sorted_by_key(counts: HashMap<String, u32>) -> BTreeMap<String, u32> {
    counts.into_iter().collect()
}
```

نکته‌ی جالب این است که چه چیزهایی در این کد **نیستند**: نه `.sort()` داریم و نه comparator. عبارت `counts.into_iter()` جفت‌های `(String, u32)` را با همان ترتیب نامشخص `HashMap` تحویل می‌دهد، اما `.collect()` بر اساس نوع مقصد کار می‌کند. اینجا نوع مقصد از خروجی تابع، یعنی `BTreeMap<String, u32>`، استنباط می‌شود.

پیاده‌سازی `FromIterator` برای `BTreeMap` هر جفت را یکی‌یکی در درخت مرتب داخلی درج می‌کند؛ درست مثل اینکه خودت در یک حلقه `.insert()` را صدا زده باشی. مرتب‌بودن ویژگی **ساختار مقصد** است، نه ترتیب رسیدن داده‌ها. پس پاسخ پرسش اول روشن است: چیزی از ترتیب پیمایش `HashMap` نشت نمی‌کند، چون `BTreeMap` با هر درج ترتیب خودش را دوباره برقرار می‌کند.

```rust
pub fn shared_genres(a: &HashSet<String>, b: &HashSet<String>) -> HashSet<String> {
    a.intersection(b).cloned().collect()
}
```

عبارت `a.intersection(b)` یک iterator از `&String` می‌دهد؛ ارجاع‌هایی که از `a` قرض گرفته شده‌اند، نه تخصیص‌های تازه. `HashSet` نمی‌داند قرار است آن‌ها را پس از پایان فراخوانی تابع نگه داری. اما امضای تابع یک `HashSet<String>` با مالکیت مستقل وعده داده است. بنابراین نمی‌توان ارجاع‌ها را همان‌طور برگرداند؛ هم نوع خروجی با `&String` سازگار نیست و هم طول عمر قرض به `a` و `b` وابسته است.

متد `.cloned()` هر `&String` را به یک `String` دارای مالکیت تبدیل می‌کند و تخصیص heap زیرین را clone می‌کند. به همین دلیل `.collect::<HashSet<String>>()` می‌تواند type-check شود.

درباره‌ی پرسش چهارم: با `Vec<String>` باید از `vec.insert(0, title)` استفاده کنی که `O(n)` است؛ چون همه‌ی عضوهای موجود باید یک خانه به راست بروند. `VecDeque::push_front` به‌شکل سرشکن‌شده `O(1)` است، زیرا deque درونش یک ring buffer با فضای آزاد در دو سر دارد و برای افزودن به ابتدا لازم نیست عضوها را جابه‌جا کند.
